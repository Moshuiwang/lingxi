# Release 拉取代理

本文说明 `release_pull_agent.py` 及其 systemd 入口。它是主机触发层，不是部署器；每五分钟列 Release、核对附件、调用冻结控制包中的 `deploy/lingxi_deploy.py`，再把结果写入私有状态账。外部边界见 [产品合同与外部边界](../docs/产品合同与外部边界.md)、[控制包说明](control/README.md) 和 [版本发布说明](releases/README.md)。

## 一、做什么，不做什么

代理负责锁、选版、三常驻服务容器回读、核包安装、计划 / 批准编排、钩子、超时和告警；部署器负责迁移、停接收、服务更新、观察和恢复。代理不解包安装（外部索引附件缺失时只从摘要已核的 tar 里读出内嵌索引一个成员）、不开入站、不读业务私有 `.env`、飞书令牌或用户数据；告警时才按 `alert_env_file` 读三个字段。人工批准发生在 GitHub 的 Release Promotion，`approval.json` 只绑定计划摘要。

## 二、两台主机只差配置

同一份控制包、代理程序和 systemd 单元安装到两台主机；两台主机只差宿主契约、代理配置和 drop-in，不在代码中分支。代理程序文件的位置以该主机 `systemctl cat lingxi-release-pull.service` 里 `ExecStart` 实际给出的路径为准（两台主机可以不同，仓库单元里的路径只是默认值）；代理运行时以自身实际路径定位自己，自替换（§八）也只改这一份文件，代码里不写死任何一台主机的路径。

宿主契约必须精确包含 `schema host environment project deploy_root config_root bundle_root relay_root lock_path docker approval_sources`。环境只能是 `stage` / `production`，路径须绝对且无 `..`，批准来源须为 GitHub Issue / PR URL，且 `approval_sources` 恰一条；本 Trace 预发值由契约给定为 `https://github.com/Moshuiwang/lingxi/issues/770`，程序不替契约猜值。

`host` 必须等于主机的内核主机名，即 `python3 -c 'import socket;print(socket.gethostname())'` 的输出（通常即 `/etc/hostname` 的全名），不是 `hostname -s` 的短名：部署器 `preflight` 按此比对，不等即 `host_mismatch`；代理在取锁前做同一比对，不等就记 `阶段=agent 结果码=host_mismatch`、退出码 1，不创建状态目录、不写状态账、不告警（状态账尚未成形），下一轮同样停住，直到契约改对。

代理配置的必需键集合固定为 `schema repository gh_command release_manifest control_bundle_tool deployer public_config alert_env_file pre_apply_hooks poll_timeout_seconds deploy_timeout_seconds notify_on_success`；示例值分别是 schema=1、`owner/name`、六个绝对路径、钩子数组、两个正整数和布尔值。唯一的可选键是 `agent_self_update`（布尔，代理自替换开关，§八）：不写等于 `true`，既有配置文件不必为它改动；写了就必须是布尔值。

未登记的多键、缺键、相对 / 穿越路径、重复钩子、非法超时、非布尔通知开关和非布尔自替换开关都拒绝（多键、缺键与非布尔自替换开关都记 `config_shape`）；`alert_env_file` 只能是路径。`TimeoutStartSec=3600` 覆盖部署超时、900 秒观察和余量，过大超时也拒绝。

## 三、选版规则

列 Release 的结果必须由 GitHub 机器身份入口返回；草稿、非法 tag 和环境不匹配的版本一律忽略。版本比较按数字段和候选编号比较，`rc.10` 大于 `rc.9`，不是按字符串排序。

| 宿主环境 | 接受的 Release | 忽略的 Release | 生产验收 |
| --- | --- | --- | --- |
| `stage` | 最新 `isPrerelease=true` 且 tag 完全匹配 `^vX.Y.Z-rc.N$` | 正式版、草稿、其他 tag | `release_manifest.py resolve --environment stage` 继续核清单 |
| `production` | 最新 `isPrerelease=false` 且 tag 完全匹配 `^vX.Y.Z$` | 所有 rc、草稿、其他 tag | 只由 `release_manifest.py resolve --environment production` 判定 main 上的验收记录 |

代理不复制 production 验收判断，也不绕过 `resolve`。无合格版本或 `gh_command` 失败记 `release_list_unavailable`；连续三轮才发一次同键告警。

**版本只升不降**：状态账记录最高已部署版本 `highest_deployed_tag`，来源是部署器回读 `verified` 的目标、外部在位确认的目标，以及本轮按运行容器反查得到的当前版本。比较按语义版本，正式版高于同号的任何候选版（`v2.5.0-rc.3` < `v2.5.0` < `v2.5.1`），同版本不算降级。选中目标低于最高已部署版本时记 `downgrade_refused`：不下载、不 plan、不 apply，只告警一次（去重键含目标 tag 和最高已部署版本），状态账仍指向已在位的目标。写权限者把较新的正式版改成预发布或草稿，代理也不会因此自动回退；回退只能走部署器独立批准的 `recover` 恢复路径。

**运行容器反查的前提**：反查只在本轮列出的 Release 里找——跳过草稿、非法 tag 和与目标同名的项，生产还只看非预发布项——按版本从高到低逐个取正式清单，与三个运行容器的摘要逐项比对，命中即为当前版本。运行中的版本已不在这个集合里（被改成草稿，或在生产被改成预发布），就反查不到。因此「较新的正式版被改成预发布 / 草稿」这一主攻向量有两种收口：状态账已记有 `highest_deployed_tag`（代理部署过或确认过在位）时，选版一步就记 `downgrade_refused`；状态账没有记 `highest_deployed_tag`（例如生产从未由代理部署或确认在位）时反查不到运行版本，记 `unknown`（阶段 `current_release`）并告警。两种都不下载、不 plan、不部署，只是结果码不同；后者见 §十。

**只升不降的稳态与人工重置**：`highest_deployed_tag` 只会被抬高，代码里没有降低或清空它的入口。人工经部署器独立批准 `recover` 合法回到较低版本后，状态账仍记着较高版本：较高版本仍可选时，代理每轮回读容器发现摘要与已验证摘要不同，记 `external_change_detected`（部署器状态改记 `unknown`，同键只告警一条），不自动重部署、也不把低版本当作在位；较高版本已被改成草稿而选中了低版本时，每轮记 `downgrade_refused`。两种都是稳定空转，不会自愈。人工重置只能清理状态账（代码没有重置子命令，登记为后续工作项）：先决定停留在哪个版本——要停在低版本，先把较高版本的 Release 改成草稿（或删除），否则重置后代理会按普通流程重新部署较高版本；然后 `systemctl stop lingxi-release-pull.timer`，以 root 编辑 `<state-directory>/pull-agent.json`（保持 0600），把 `highest_deployed_tag`、`target_tag`、`deployer_state`、`verified_digests`、`external_change_tag`、`plan_id` 六个字段置为 `null`，`alerts` 与运行编号保留，再启动 timer。下一轮回读三个运行容器与选中版本的清单全等即记 `already_in_place_external`，状态账以该版本重建，此前处于活动状态的告警各发一条恢复。

## 四、单轮九步

每轮 stdout 每行是“时刻 阶段 结果码 键=值”；子命令输出、临时路径和配置不进日志，Release 页面按仓库 + 标签构造，不含查询串。

1. **锁**：状态目录 0600 文件用 `fcntl.flock(LOCK_EX|LOCK_NB)`，锁覆盖整轮。
2. **列发布**：经 `gh_command release list --json tagName,isPrerelease,isDraft,publishedAt` 读 Release（只请求 gh 手册列出的字段），用纯函数选版；目标低于最高已部署版本记 `downgrade_refused`。
3. **幂等 / 接续**：先判断同一 `plan_id` 是否处于目标相同的 `planned` / `running` / `unknown` 接续状态（被外部改动的同一目标不接续）；状态账已证实同一目标 `verified` 时仍回读三常驻服务容器摘要与已验证摘要比对；其余非接续轮次才解析清单并回读容器，三个运行中容器的摘要全等才记外部在位。
4. **核包**：经 `gh_command` 下载 `lingxi-control.tar`（必有）与 `control-index.json`（可选）两个附件。包摘要必须等于清单 `sha256`；外部索引附件在场时摘要必须等于清单 `index_sha256`，缺失时只从摘要已核的 tar 里读出内嵌的 `control-index.json` 成员核同一摘要、写成 0600 同名副本（日志一行 `index_source=asset|embedded` 标来源，不带路径）；任一摘要不等记 `bundle_digest_mismatch`，且不会调用控制包入口。GitHub 已对本仓库启用不可变 Release，已发布版本不能事后补附件，所以生产现网 v2.4.3 这类旧版本永远没有外部索引附件——两种来源都由清单 `index_sha256` 钉住，缺附件不放松任何摘要核对。随后调用控制包入口，不在代理里解包安装。控制包入口以包自身索引（由清单 `index_sha256` 钉住）为文件集合依据，所以代理用当前工具核对旧版本的包（接续、回读当前版本）或新版本的包都不会因两个版本打包清单不同而被拒；越界路径、缺必备文件、tar 与索引不一致仍拒。新包核对并安装之后，代理先用版本目录里的 `deploy/release_pull_agent.py` 替换自身（§八「代理程序文件的自替换」；本轮仍以旧代码跑完，任何结局都不改变本轮部署结论），再进入下一步。
5. **刷新安装收据**：非接续轮次，在新包核对、安装且包内冻结清单核对一致之后、plan 之前，把 `<config_root>/deployment-installation.json`（引导安装写定的安装收据，见[引导安装 §三.9](control/引导安装.md#9-安装收据)）的 `bundle_sha256` 刷成新包摘要：先把旧收据逐字节备份到同目录 `deployment-installation.json.prev`，再以 root 0600 原子替换并同步目录；六项人工核对 `checks` 与 `binding_version` 只核对、不改写。收据缺失、不是 0600、键集合或 `schema` 不符、`environment` / `project` 与宿主契约不符、六项核对不全为 `true`、`binding_version` 不是正整数，或写回失败，记 `installation_receipt_unusable`（日志行带 `reason=` 说明是哪一条）：不 plan、不 apply，告警一次，状态账仍指向已在位的目标。摘要已相等时记 `unchanged`、不写盘；接续轮次不动收据。
6. **接续 / plan**：目标相同且状态为 `planned` / `running` / `unknown` 时不新 plan，否则用新包内部署器生成计划并立即 0600 落账；计划里的 `channel.installation_receipt_sha256` 与 `channel.binding_version` 一律取自刚刷新的收据，有旧计划时通道其余字段才沿用旧计划。
7. **批准 / 钩子**：批准恰七键并绑定指纹；执行前核对每个钩子程序及其全部祖先目录（root 属主、无组 / 其他写权限、非符号链接），不符记 `pre_apply_hook_unsafe` 且一个都不执行；按序跑钩子，失败不 apply。
8. **apply / status**：apply 有部署超时；其他结束后必用同包 `status`，只认部署器五种状态。
9. **告警 / 状态**：记录 Release、提升、计划和批准摘要；正文不含 URL、查询串、凭据、日志原文。

## 五、幂等、接续与九处中断

幂等分两级，且接续判定先于两级在位判定，顺序不能交换：

代理先读取状态账关联的计划文件。若 `deployer_state` 是 `planned`、`running` 或 `unknown`，且该计划的 `new.tag` 等于本轮选中标签，就沿同一 `plan_id` 继续调用 `apply`，不再用镜像或容器在位结果提前收口。只有不满足接续条件时，才进入下面的状态账级和外部事实级判定。

| 级别 | 判据 | 代理动作 |
| --- | --- | --- |
| 状态账级 | 最近一次部署器状态为 `verified`，且计划目标 tag 等于本轮选中 tag | 不把 `verified` 当永久事实：仍回读三常驻服务运行容器的摘要，与状态账 `verified_digests` 逐项比对（没有记录时按该 tag 用 `release_manifest.py resolve` 取清单比对，确认在位后记下）。全等记 `already_in_place`，除列 Release、只读回读和更新状态账外零动作；容器缺失、未运行或摘要不同记 `external_change_detected`，部署器状态改记 `unknown`、立即告警，**不自动重部署**；回读本身失败记 `unknown` 但保留 `verified`，下一轮再读 |
| 外部事实级 | `scheduler`、`gateway`、`worker-queue` 三个常驻服务的运行容器均存在且处于运行中；按 `docker inspect` 的容器 `Config.Image` / `Image` 定位镜像，再回读其 `RepoDigests`，与清单中 `scheduler`、`gateway`、`worker` 的 digest 逐一相等 | 记 `already_in_place_external`；不生成计划、不下载包、不调用部署器 |

三个容器必须全部存在、运行且摘要相等；本机只拉到镜像但没有对应运行容器不算在位。`docker image inspect` / `docker inspect` 对象不存在时按退出码 `1` 且 stderr 含 `No such` 记为未安装 / 未运行，继续部署；命令找不到、守护进程不可用、其他退出码或成功输出无法解析才记 `unknown` 并立即告警。

**状态账只在 `verified` 时推进到目标**：`highest_deployed_tag` 与 `verified_digests` 只在本轮写出 `verified`（部署器 `status` 为 `verified`、外部在位、状态账级在位复核通过）时才记成本轮目标；`target_tag` 在计划落盘前同样不动，只随计划 / 批准落盘作为可接续身份记下（此时 `deployer_state` 是 `planned` 等非 `verified` 状态，不会触发上表的状态账级判定）。计划落盘前的任何失败或未知结果——`bundle_digest_mismatch`、任何阶段的 `unknown`、`downgrade_refused`、`installation_receipt_unusable`、`release_list_unavailable` 等——都不推进这三项，状态账仍指向已在位的目标，下一轮同一目标重新走完整流程。否则状态账会同时声称「目标 == 新 tag 且 `verified`」，状态账级判定就会把从未部署的新目标误判为 `already_in_place` 并把最高已部署版本抬到它：新目标被静默跳过，防降级也会拿失真的版本号拒绝真正的目标。计划落盘后的中断（`pre_apply_hook_*`、`deploy_timeout`、`failed`、`running` 等）只保留可接续身份 `target_tag` / `plan_id` / `deployer_state`，最高已部署版本与已验证摘要同样不动。

外部改动持续期间，状态账 `external_change_tag` 指向该目标：同一目标每轮只回读比对，不沿旧计划接续、不新建计划，直到容器回到已验证摘要（记 `already_in_place` 并发一条恢复）或出现更高的新目标（按普通流程以运行容器反查旧版本后部署）。人工核对后要回到已验证版本，走部署器独立批准的 `recover` 或重新走正常发布，代理不替人决定。反过来，人工经 `recover` 合法回到较低版本后，状态账的最高已部署版本不会跟着降，代理会持续记 `external_change_detected` 或 `downgrade_refused`，见 §三「只升不降的稳态与人工重置」。

**安装收据只在 plan 之前刷新，接续不动它**：部署器 apply 前按计划里的 `channel.installation_receipt_sha256` 与目标新包摘要核对 `<config_root>/deployment-installation.json`（六条校验见部署器 `installation_receipt`），所以收据的 `bundle_sha256` 必须在 plan 之前就等于新包摘要。代理只在非接续轮次、新包装好之后刷新它（§四第 5 步），计划落盘时指纹即与磁盘一致；接续轮次沿用计划里的指纹、不碰收据，中断后的接续不会因收据变化而失配。有旧计划时通道其余字段沿用旧计划，但收据指纹与 `binding_version` 一律取自刚刷新的收据——旧计划里的指纹对应的是上一版的收据，沿用它必然在 apply 前被部署器以 `installation_receipt_missing_or_mismatched` 拒绝。收据刷新后、计划落盘前中断的，属于下表之外的代理侧中断：状态账还没有新计划，下一轮按普通流程重走，收据摘要已等于新包就记 `unchanged`、不写盘，直接 plan。

部署器状态账负责九处中断的阶段接续。代理下一轮只把同一 `plan_id` 和新装控制包交回 `apply`，实际阶段由部署器回读：

| 中断位置 | 下一轮代理动作 | 下一步由谁判定 |
| --- | --- | --- |
| 计划落盘后 | 状态账已有 `planned`，沿同一计划复用有效批准并 apply | 部署器核对计划摘要与批准时间窗 |
| 部分镜像到位后 | 状态账为 `running` 或 `unknown`，不重新 plan | 部署器逐项回读旧、新镜像 |
| 停接收后 | 仍只调用同一计划的 apply | 部署器按阶段账确认停接收是否完成 |
| 迁移提交前 | 继续同一计划，禁止换迁移头 | 部署器检查迁移作业实际状态：作业没起、库头未变时以 `migration_unknown_no_retry` 停住，是设计性停机，人工续跑入口见本节末「迁移提交前中断的人工续跑」 |
| 迁移提交后 | 继续同一计划，不重复盲跑迁移 | 部署器按迁移头回读决定 |
| 首个服务更新后 | 继续同一计划 | 部署器按服务标签和配置摘要回读 |
| 全服务更新后 | 继续同一计划 | 部署器进入 15 分钟观察 |
| 观察中 | 保留 `running` / `unknown`，下一轮仍不新建计划 | 部署器完成或重新观察 |
| 完成标记前 | 继续同一计划并重新 status | 只接受部署器写出的 `verified`，否则告警或继续接续 |

计划、批准或新包摘要不能安全回读时记 `unknown` 并告警；`recover` 仍须部署器的独立批准，本代理不会把普通 apply 改成恢复。

**只在 `prepare` 失败的计划不再占着主机**：部署器 apply 在 preflight 通过后写下 `host.active.json`（`status=running`），此后以明确失败停住（`failed`）的计划代理不接续、改建新计划；新计划 apply 在主机锁内先看这份标记——指向别的未完成计划时，只有五条件全有证据才自动收敛：① 标记确属该失败计划（计划文件指纹等于标记）；② 其阶段账 `status` 为 `failed`（`unknown` / `running` 不算）；③ 阶段账只记过 `prepare` 的意图（阶段意图先于动作落盘，`stop` 及之后哪怕只是 `running` 也不收敛）；④ 旧执行者不在跑（持有主机锁即证据，旧执行者及其子进程持同一描述符）；⑤ 有可信的上一次 `verified` 指针可恢复（`host.verified.json`，没有时从 `verified` 阶段账重建）。收敛 = 把 `host.active.json` 恢复为上一次 `verified` 的指针，本机从未验证过且失败计划是在无标记状态下（首次接管）通过 preflight 的，则删除标记回到「从未由部署器部署过」（等价解除，不是验证）；失败计划的 `status` 与文件一个不改、不删，只在其阶段账追加 `released_by`，新计划阶段账追加 `released_markers` 审计（固定字段）。任一条件无证据就维持 `unfinished_host_deployment` 零动作，按 §十二 F21（#805）其余情形处置。

**首次接管手工启动的旧服务**：部署器接管之前由人手工用 Compose 启动的三个常驻服务容器没有任何 `io.lingxi.*` 标签（只有 `com.docker.compose.*`）。部署器核对服务清单时，对**被核对的两枚标签 `io.lingxi.config-sha256` / `io.lingxi.bundle-sha256` 都缺失且镜像摘要等于计划 `old` 侧登记镜像**的容器按「接管前的旧服务」接受，包括中断在「首个服务更新后」再接续时剩下的无标签旧容器；`new` 侧永不放行无标签容器，只缺一枚、或标签值不等的容器仍以 `unplanned_service_artifact_or_config` 拒绝。这条豁免只在本机首次由部署器接管时生效：`lock_path` 同目录的 `host.active.json` 不存在（本机从未由部署器部署过），或它记着的就是本计划的 `id` 且本计划阶段账记着首次接管（同一首次计划中断后接续）；它记着其它计划（本机已由部署器部署过）时，无标签容器按原规则拒绝；形状异常时取不到可信旧值，以 `previous_verified_configuration_unavailable` 停住。这不放松边界：旧镜像摘要就是计划登记并经批准的旧服务身份，而部署器自己起过的容器一定带这两枚标签。首次接管完成后三个服务都由部署器带标签重建，此后按原规则核对。

**核对旧服务用哪份配置指纹**：`old` 侧运行容器的 `io.lingxi.config-sha256` 只与部署器自己账里的可信旧值比——`host.active.json` 指向的上一次 `verified` 计划（状态目录 `<plan_id>.plan.json`，`sha256sum` 逐字等于标记里的 `plan_sha256` 才用）的 `config_sha256`，即那次部署给容器打的标签值；同一计划中断后接续取本计划阶段账在 preflight 通过时记下的 `inventory`；`recover` 取被恢复计划的 `config_sha256`。`new` 侧只取本计划的 `config_sha256`（当前 `public-config.json` 指纹）。两侧不互相冒充：请求里的 `recovery.config_sha256` 不再用于核对旧容器，当前配置不当历史值，也不读被核容器的标签自证。旧值取不到（计划文件缺失、指纹不符、标记形状异常、标记指向未 `verified` 的别的计划、接续时阶段账没有记录）时以 `previous_verified_configuration_unavailable` 在停任何服务之前停住，零动作。两侧指纹在 `plan` 输出的 `summary.configuration`（`old_verified_sha256` / `old_source` / `new_sha256`，`old_source` 是 `verified` 计划的 `plan_id`、`first_takeover` 或此刻取不到的 `unavailable`）、阶段账与 `status` 输出的 `inventory` 里分开列出。

**计划窗口过期没有自愈**：计划的时间窗由代理在生成请求时写定——`not_before` 是生成时刻前 1 秒，`expires_at` 是生成时刻加「`deploy_timeout_seconds` + 1200 秒」——批准文件的复用与新建都要求当前时刻落在窗内。计划一直停在 `planned`（例如钩子连续失败，或主机 / timer 停了超过窗口长度）直到窗口过去之后，每轮仍沿同一 `plan_id` 接续，走到批准这一步失败：日志 `阶段=approval 结果码=unknown`，状态账 `deployer_state=planned` 不变，不重新 plan、不 apply；告警按 `unknown + tag` 去重只发一条，此后每轮同码静默。代码目前没有解除入口（子命令只有 `run` 和 `status`），需人工清理状态账中该计划的文件，登记为后续工作项。人工解除按代码如实写：

1. `systemctl stop lingxi-release-pull.timer`；用只读的 `status` 子命令取当前 `plan_id`。
2. 确认部署器没有为该计划留下阶段账：状态目录中不存在 `<plan_id>.state.json`（部署器只在 apply 真正进入后才写它），且部署器的活动计划记录（`lock_path` 把 `.lock` 换成 `.active.json` 的那份文件，如 `host.active.json`）没有以未完成状态指向该计划。存在阶段账就不是本条情形，按部署器恢复契约处理，不要归档计划。
3. 把状态目录中该计划的三份文件 `<plan_id>.plan.json`、`<plan_id>.approval.json`、`<plan_id>.request.json` 移到 root 私有的归档目录（保持 0600）；`pull-agent.json` 不动，里面的 `plan_id`、`deployer_state`、`approval_sha256` 仍指向旧计划也不必手改——下一轮读不到计划文件，接续判定就不成立。
4. `systemctl start lingxi-release-pull.timer`。下一轮按普通流程走：回读三个运行容器并在已列出的 Release 中反查当前版本（前提见 §三）、下载包、由部署器生成新计划（新 `plan_id`、新时间窗）、写新批准并 apply；日志应出现 `阶段=plan 结果码=written` 且 `plan_id` 是新值。原先那条 `unknown` 告警在下一次健康结果时发一条恢复。

新计划的 `old` 只允许来自状态账中 `deployer_state == verified` 的 `plan.new`，且该计划的 `new.tag` 等于状态账 `target_tag`；外部在位只更新状态账的 `target_tag`、不更换 `plan_id`，此时该计划的 `new` 已不是运行中的版本，不得再充当 `old`。不满足时只按上述三个运行容器的 digest，在已列出的 Release 中用固定 `release_manifest.py resolve` 逐个反查正式清单。反查不到时不得猜测或伪造旧版本，收口为未知 / 外部安装事实并等待人工核对。计划中的 `recovery.target_manifest_sha256` 必须等于 `fingerprint(old)`，绝不能指向 `new`。

**迁移提交前中断的人工续跑**：部署器在阶段账写下 `migrate: running` 之后、迁移作业容器（固定名 `lingxi-migration-<plan_id>`）起来之前被打断（预发接缝 ④：整 cgroup `SIGKILL`），下一轮代理照常沿同一计划 `apply`，部署器按设计以 `migration_unknown_no_retry` 停住——阶段账里已有 `migrate` 记录就不盲跑迁移。此时停接收阶段已完成、三个常驻服务已停，库头未变、没有作业容器，这是**设计性停机**：代理每轮日志 `阶段=apply 结果码=failed` 紧接 `阶段=status 结果码=unknown`，部署器 `status` 输出的 `error` 是 `migration_unknown_no_retry`，告警只发一条，不会自愈；代理不会把 apply 改成恢复，也不替人清阶段账。

为什么不自动：迁移作业容器不带 `--rm`，容器保留本身就是证据——有容器（不论在跑、已成功还是已失败）说明迁移至少起过，是另一种情形，交 apply 按既有规则判；库头已变同理。只有「`migrate` 记录是 `running`、没有作业容器、迁移镜像回读的库头逐字等于计划 `current_heads`」三件事同时成立才是本情形；任一不成立就不是本情形，不要碰阶段账。

部署器子命令 `resume-migration` 是这条情形的可核对入口：在主机锁内核对三件事、操作者手抄的阶段账指纹与主机在途标记，全部成立才把阶段账原文归档、删掉 `stages.migrate` 这一条记录并追加一条结构化审计；阶段账 `status` 保持 `unknown` 不改，迁移仍由下一轮 apply 自己起。步骤按代码如实写（`<部署器>` 是代理当轮用的那份 `<bundle_root>/<新包摘要>/deploy/lingxi_deploy.py`，配同一份宿主契约、public-config 与状态目录；换别的版本会以 `frozen_deployer_required` 被拒）：

1. `systemctl stop lingxi-release-pull.timer`，并确认没有代理进程仍在跑。
2. `/opt/lingxi/bin/python3 -B <部署器> --host-contract <宿主契约> --public-config <public-config.json> --state-directory <状态目录> status <plan_id>`：抄下输出里的 `state_sha256`（阶段账文件原文的 sha256），并人眼核对 `stages.migrate.status` 为 `running`、`actual.job` 为 `null`。`actual.migration_heads` 此时为 `null` 属正常——服务已停，`status` 只读回读不起容器、读不到库头；库头由第 3 步的部署器用迁移镜像回读并逐字比对，结果打在输出的 `checked` 里。
3. `/opt/lingxi/bin/python3 -B <部署器> --host-contract <宿主契约> --public-config <public-config.json> --state-directory <状态目录> resume-migration <plan_id> --approval <状态目录>/<plan_id>.approval.json --acknowledge <state_sha256>`。批准就是代理为该计划生成的那份——本操作不换版本、不换迁移头，`recover` 计划一律拒绝。任一核对不成立即退出码 1、stderr 一行 JSON 只带结果码、阶段账一个字节不动：

   | 结果码 | 含义 | 人要做什么 |
   | --- | --- | --- |
   | `resume_acknowledge_mismatch` | `--acknowledge` 不等于当前阶段账文件的 sha256（没有阶段账也算） | 重新 `status` 抄当前值；抄对了仍不等说明账在你看过之后又变了，先看变了什么 |
   | `resume_no_migrate_record` | 阶段账没有 `migrate` 记录 | 没有可清的记录：直接让 timer 跑，apply 自己会起迁移 |
   | `resume_migrate_not_running` | `migrate` 记录已是 `verified` | 迁移已提交，不是本情形：让 timer 跑，按「迁移提交后」接续 |
   | `resume_host_marker_mismatch` | 主机在途标记（`lock_path` 把 `.lock` 换成 `.active.json` 的那份文件）不是本计划的未完成标记 | 本计划已被 `recover` 取代或标记被动过：不要续跑，按部署器恢复契约处理 |
   | `resume_migration_job_present` | 存在 `lingxi-migration-<plan_id>` 容器（不论状态） | 迁移至少起过：不是本情形，让 apply 按既有规则判；不要删容器 |
   | `resume_database_heads_changed` | 迁移镜像回读的库头不等于计划 `current_heads` | 库已被改过：不是本情形，先查库头从哪来 |
   | `resume_migration_apply_only` | 传入的是 `recover` 计划 | 续跑只属于 apply 计划 |
   | `approval_mismatch` / `approval_expired` / `approval_changed` | 批准与计划不匹配、窗口已过、或不是部署器已记下的那份 | 用代理生成的同一份批准；窗口已过就按上文「计划窗口过期没有自愈」处理 |

   通过时 stdout 一份 JSON：`archive`（归档路径）、`state_sha256`（新账指纹）、`checked`（回读到的作业与库头）、`resumes`（审计）。归档在状态目录下 root 私有的 `archive/<plan_id>.state.before-resume-<UTC 时刻>.json`（目录 0700、文件 0600、逐字节等于手术前的阶段账）；审计追加在阶段账 `resumes` 列表，每条只有 `time` / `stage` / `archived_state_sha256` / `acknowledged_sha256` 四个固定字段，没有自由文本。
4. `systemctl start lingxi-release-pull.timer`。
5. 下一轮日志应出现 `continuation apply_same_plan`（同一 `plan_id`），随后部署器起迁移作业容器 `lingxi-migration-<plan_id>` 并沿阶段账接续到 `verified`；服务仍停着就不重做停接收，有人手工起过服务则部署器会重新停一遍。仍停在 `migration_unknown_no_retry` 就说明中断点不在本情形，按部署器 `status` 的 `error` 与上表重新判，不要第二次手术。

## 六、沿同一计划复用批准和 Release Promotion

`approval.json` 的生成是机械绑定，不是第二次人工授权。代理读取刚生成或正在接续的计划，取得其中的 `plan_id`、`operation`、`expires_at`、`approval_source`；同一 `plan_id` 已有文件且通过对同一计划的 `validate_approval` 时原样复用，不重写 `approved_at`，因此 `approval_sha256` 保持不变。只有无文件或校验不过时才生成新文件，并把 `fingerprint(plan)` 写入 `plan_sha256`。部署器仍按原有 `validate_approval` 校验七键、计划指纹和时间窗；代理没有放宽这一语义。

人工批准发生在 GitHub 的 Release Promotion：产品负责人提升候选后，正式 Release 才取得生产可选资格。代理不等待另一个部署窗口开关，不要求一份独立签批准文件，也不把代理自动生成的 `approval.json` 当成产品负责人的点击证据。状态账中的 `candidate_run_id`、`promotion_run_id`、`release_run_id`、Release 页面 URL、`plan_id` 和 `approval_sha256` 用来回答“这次部署对应哪一次提升放行”。

**「提升即放行」的边界**：提升只是人工授权完成，不等于已部署。生效有两个前提：该正式版在 main 里已有验收记录且清单与已验收候选一致——由 `release_manifest.py resolve --environment production` 判定，代理不复制这一判断；生产主机的 timer 在跑，每 5 分钟拉取一次（`OnCalendar=*:0/5`，`AccuracySec=30s`）。正式版不合格（没有验收记录、验收记录不是 main 中的同一份、清单与候选不符）时 `resolve` 非零退出，代理在选中它的**第一轮**就记 `unknown`（阶段 `idempotence`，部署器状态 `unknown`）并立即告警，去重键 `unknown + 该 tag`，之后每轮同码不再重复；直到该版本修正为合格并部署完成，或其他合格目标确认在位，才发一条恢复。产品负责人提升后：最多等 5 分 30 秒，`journalctl -u lingxi-release-pull.service` 会出现 `阶段=release_list 结果码=selected` 且 tag 为该正式版的行；部署完成看状态账（`release_pull_agent.py ... status`）的 `last_result=verified`、`target_tag`、`promotion_run_id`，或 `notify_on_success=true` 时管理群的成功通知。一轮上限是 `TimeoutStartSec=3600`（含部署超时与 15 分钟观察）：提升一小时后仍没有 `verified` 也没有告警，按 §十逐码排查。

## 七、告警、去重和恢复

告警复用 `deploy/监控告警.md` 与 `host_health_alert.py` 的凭据形态：代理以 root 运行时，`alert_env_file` 必须指向 root 私有的独立 0600 副本，例如 `/opt/lingxi/release-pull/alert.env`；副本内容与 `host-monitor.env` 相同，只含三个 `LINGXI_FEISHU_*` 必要字段。代码继续要求文件属主等于运行者；凭据不复制进控制包、命令行、状态账或日志。

| 结果码 | 是否告警 | 去重键和恢复 |
| --- | --- | --- |
| `already_in_place` | 否 | 不建告警事件 |
| `already_in_place_external` | 否 | 不建告警事件 |
| `release_list_unavailable` | 连续至少 3 轮一次 | `结果码 + tag`；同键只发一次，之后成功选到版本发一条恢复 |
| `downgrade_refused` | 立即一次 | `结果码 + 目标 tag + 最高已部署版本`；同键不重复，选到不低于已部署版本的目标并确认在位后发一条恢复 |
| `external_change_detected` | 立即一次 | `结果码 + tag`；同键不重复，容器回到已验证摘要后发一条恢复 |
| `bundle_digest_mismatch` | 立即一次 | `结果码 + tag`；同键不重复，恢复后发一条恢复 |
| `installation_receipt_unusable` | 立即一次 | `结果码 + tag`；同键不重复，收据修正后代理自动重走并部署，`verified` 或确认在位后发一条恢复 |
| `pre_apply_hook_unsafe` | 立即一次 | `结果码 + tag`；修正钩子路径属主 / 权限后同一计划继续，部署器完成后恢复 |
| `pre_apply_hook_failed` | 立即一次 | `结果码 + tag`；钩子成功且部署器完成后恢复 |
| `deploy_timeout` | 立即一次 | `结果码 + tag`；后续真实回读恢复 |
| `failed` | 立即一次 | `结果码 + tag`；后续 verified 或外部在位恢复 |
| `unknown` | 立即一次 | `结果码 + tag`；只在客观回读确认健康时恢复 |
| `verified` | `notify_on_success=true` 时一次 | 成功事件按 `verified + tag` 去重 |
| `agent_self_update_rejected` | 立即一次 | `结果码 + tag`；同键不重复；不影响本轮部署结论，不发恢复通知（§八） |
| `agent_self_update_failed` | 立即一次 | `结果码 + tag`；同键不重复；不影响本轮部署结论，不发恢复通知（§八） |
| `alert_delivery_failed` | 不吞掉发送失败 | 保留未送达记录，下一轮重试，不把未送达视为已告警 |

正文只包含主机、环境、标签、阶段、结果码、计划 ID，降级拒绝另附最高已部署版本；投递失败只保留类别。日志 `阶段=alert` 只在本轮真正发出时记 `结果码=sent`，同键被去重的轮次记 `结果码=deduplicated`。状态账原子替换并同步目录；状态、批准和计划文件 0600，目录 0700。

## 八、安装和权限

以下尖括号是安装人替换的本机值，不是仓库默认值。控制包先装到 `<安装根>` 的版本化只读目录；`bundle_root`、`config_root`、`relay_root` 和部署根由 root 建立且不得被组 / 其他主体写入。状态目录 0700，其中 JSON、计划、批准和稳定包副本 0600。

`config_root` 下的安装收据 `deployment-installation.json`（root 0600）由引导安装写定，是代理会改写的唯一一份宿主配置：每次装新包时只把 `bundle_sha256` 刷成新包摘要，旧收据备份为同目录 `deployment-installation.json.prev`；六项 `checks` 与 `binding_version` 由人维护，代理只核对（§四第 5 步）。`config_root` 被组 / 其他主体可写时写回会被拒绝。

宿主契约写成 0600，代理配置写成不允许组 / 其他写入的 JSON；所有程序路径为绝对路径。`deployer` 仍登记在配置中，但实际调用只能来自新装版本化目录。`alert_env_file` 指向 root 私有的独立 0600 告警凭据副本，不另建应用、群或凭据格式。

代理以 root 运行时，安装人必须从既有 `host-monitor.env` 生成 root 私有的独立副本，并让配置中的 `alert_env_file` 指向该副本。例如：

```bash
install -o root -g root -m 0600 "<HOST_MONITOR_ENV_SOURCE>" "/opt/lingxi/release-pull/alert.env"
```

启用 timer 前执行 S-2-6 前置核对：确认 `alert_env_file` 指向这份独立副本，文件为 root 所有且模式恰为 `0600`，内容只含 `LINGXI_FEISHU_APP_ID`、`LINGXI_FEISHU_APP_SECRET`、`LINGXI_ADMIN_GROUP_CHAT_ID` 三字段；不得直接把由其他运行主体持有的 `host-monitor.env` 路径写入代理配置。预发另有钩子相关的前置核对项，见 §九「包装脚本以 root 运行时的私有材料」。

**代理程序文件的自替换**：代理程序文件只在引导安装时人工装一次（[引导安装 §二.4](control/引导安装.md#4-代理程序文件的首次安装)），此后由代理自己随控制包升级，人不再重装。每轮新包核对并安装之后（§四第 4 步），代理拿版本目录 `<BUNDLE_ROOT>/<控制包摘要>/deploy/release_pull_agent.py` 当候选，在位文件就是本进程实际运行的那份（`ExecStart` 路径，代码按自身路径定位、不写死）。信任来源只有一条、与部署器同一条摘要链：版本目录内 `control-index.json` 的 sha256 必须等于发布清单的 `control_bundle.index_sha256`，候选文件的 sha256 必须等于该索引里 `deploy/release_pull_agent.py` 条目的 `sha256`；不另设签名或公钥，链外文件一律不采用。判定：候选摘要等于在位摘要记 `agent_self_update_unchanged`（不写盘、不告警）；摘要不同但候选的版本标记不高于在位记 `agent_self_update_skipped_not_newer`（不替换、不告警——防降级是正常路径）；摘要不同且候选标记严格大于在位标记才替换。版本标记是代理源码里的整数常量行 `AGENT_VERSION = N`，按整行正则从文本读出、不导入不执行；在位文件没有这一行（自替换机制之前装的代理）视为 0。替换 = 在同一目录先把旧文件留成 `release_pull_agent.py.bak-<旧摘要前 8 位>`（只保留最近一份，更早的副本删除），再把候选以同样的权限位写成临时文件、落盘后原子换入在位路径并同步目录——`ExecStart` 路径上始终是完整的旧文件或新文件；换入后回读 sha256 必须等于候选，不等就把副本换回、记 `agent_self_update_failed`。本轮进程继续以旧代码跑完（不重新执行自身），新代理从下一轮起运行，审计行写 `next_round_by=<新标记>`，每轮首行 `阶段=lock 结果码=acquired` 带 `agent_version=` 标出正在运行的标记。拒绝条件：索引或候选不在摘要链上、在位路径是符号链接、在位文件不是运行者自有的普通文件、所在目录可由组 / 其他主体写入，都记 `agent_self_update_rejected`（日志行 `reason=` 指明哪一条，不进状态账和告警正文）。`agent_self_update_rejected` 与 `agent_self_update_failed` 各告警一次（去重键 `结果码 + tag`），自替换的任何结局都不改变本轮部署结论。配置键 `agent_self_update=false` 关闭整段（每轮只记一行 `agent_self_update_disabled`）。

安装两个 unit 后写本机 drop-in `lingxi-release-pull.service.d/10-local.conf`，其中 `[Service]` 为 `User=root`；仓库 service 不含活动的 `User=`。仓库 service 的 `ExecStart` 以固定符号链接 `/opt/lingxi/bin/python3` 起代理（不写死系统 `python3`：主机默认 `python3` 可低于控制包要求的 3.11；链接由引导安装「一、前提核对」用 `<PYTHON_ABSOLUTE_PATH>` 建好，代理起的清单工具与部署器沿用同一解释器）。仓库 service 里代理程序文件的路径只是默认值：代理程序文件装在别处的主机（预发即如此）在同一 drop-in 里覆盖 `ExecStart`（先写一行空的 `ExecStart=` 清掉仓库值，再写完整的一行，解释器与其余参数不变），装在默认路径的主机不必覆盖；两台主机可以不同，以 `systemctl cat` 实际给出的路径为准。执行 `systemctl daemon-reload`，核对 `systemctl cat` 的 root、`ExecStart=` 以 `/opt/lingxi/bin/python3` 开头且代理程序路径就是刚装好的那份、`/opt/lingxi/bin/python3 --version` 为 3.11 以上和 `TimeoutStartSec=3600`，再 `systemctl enable --now lingxi-release-pull.timer`。单轮可超过 timer 周期，依靠状态锁防重叠。首轮只做假命令和 `status`；真实 stage / production 链路另行授权验收，禁止现场构建或改包。

仓库 service 的 `ExecStart` 带 `-B`、`[Service]` 带 `Environment=PYTHONDONTWRITEBYTECODE=1`：代理以 root 运行，它和它起的子进程（清单工具、部署器、钩子）都不得往只读版本目录写字节码缓存，否则下一轮 `verify_install` 会以「存在可写项」拒绝已装版本（§十 `reason=control_bundle_install_failed`）。`-B` 只管代理自己、不被子进程继承，环境变量是兜底；代理、清单工具与部署器入口在代码里也各自关了缓存，所以这两项不依赖 drop-in，drop-in 里再写一遍也无害。

预发“不用即停”只需要停触发器，不删除状态账和已安装包：

```text
systemctl disable --now lingxi-release-pull.timer
```

不要手工改 unit 切换主机；差异留在契约、配置和 drop-in。锁、计划和批准文件由部署主体维护，普通业务容器不可写。

## 九、通用 pre-apply 钩子接口

`pre_apply_hooks` 按配置顺序执行，每个绝对路径程序收到同一组非秘密参数：

```text
<hook> --host-contract <宿主契约路径> --config <代理配置路径> --state-directory <状态目录路径> --plan <计划路径>
```

钩子须为可执行程序或 Python 3.11 标准库脚本；退出 0 才进入 apply，非零保持 `planned`。不得读出或打印告警凭据、调用部署器或改写计划 / 附件。S-2-3b 备份脚本按此接入并自行留证；未安装时列表必须为空。

### 钩子程序的安装路径与属主

执行前，代理对每个钩子程序**及其全部祖先目录**（直到 `/`）逐级以不跟随链接的方式核对：属主为 root、无组 / 其他写权限、不是符号链接；任一级不符记 `pre_apply_hook_unsafe`，一个钩子都不执行。这与受限通道 relay 的自检是同一条规则：任何一级能被非 root 主体改写，钩子就可能被替换。由此有两条约束：

- 不能把钩子登记成 `<BUNDLE_ROOT>/current/...`：`current` 是符号链接，核对必然不过。控制包内的样例带 `<...>` 占位，版本化目录又是只读的，不能原地改；应复制到 root 私有目录后再填本机值。
- 安装路径约定为 `/opt/lingxi/release-pull/hooks/`（与 §七的告警凭据副本同在 `/opt/lingxi/release-pull/` 下），目录与程序都是 `root:root`、`0755`；`/opt`、`/opt/lingxi`、`/opt/lingxi/release-pull` 这些祖先目录同样须 root 属主且无组 / 其他写权限。

```bash
install -d -o root -g root -m 0755 /opt/lingxi/release-pull/hooks
install -o root -g root -m 0755 \
  "<BUNDLE_ROOT>/<CONTROL_BUNDLE_SHA256>/deploy/control/examples/hooks/stage-permission-table-backup.sh" \
  /opt/lingxi/release-pull/hooks/stage-permission-table-backup.sh
# 以 root 编辑副本，把四个 <...> 占位换成本机绝对路径；随后逐级核对：
stat -c '%n %U:%G %a %F' / /opt /opt/lingxi /opt/lingxi/release-pull \
  /opt/lingxi/release-pull/hooks /opt/lingxi/release-pull/hooks/stage-permission-table-backup.sh
```

期望每一行属主 `root:root`、权限的组 / 其他位都没有写位（如 `755`、`750`、`700`），且没有一行是 `symbolic link`。`pre_apply_hooks` 里登记的就是这份副本的绝对路径。

### 包装脚本以 root 运行时的私有材料

代理以 root 运行（§八的 drop-in `User=root`），钩子随之以 root 运行；守卫要求 `--env-file` 属主等于运行者且模式恰为 `0600`、`--work-dir` 属主等于运行者且模式恰为 `0700`（见[权限发布表预发防护](权限发布表预发防护.md#安全文件与日志边界)）。因此包装脚本里的 `<SCHEDULER_ENV_FILE>` 不能直接指向部署用户持有的 scheduler 环境文件，必须像 §七的告警凭据副本一样做一份 root 私有的独立 0600 副本；`<GUARD_WORK_DIR>` 必须是 root 私有的 0700 目录（不存在时守卫以 0700 新建，已存在则属主与模式都要恰好相符）：

```bash
install -o root -g root -m 0600 "<SCHEDULER_ENV_SOURCE>" /opt/lingxi/release-pull/scheduler.env
install -d -o root -g root -m 0700 /opt/lingxi/release-pull/guard-work
```

钩子只跑守卫的 `backup`，副本只需 `LINGXI_FEISHU_APP_ID`、`LINGXI_FEISHU_APP_SECRET`、`LINGXI_PERMISSION_BITABLE_APP_TOKEN`、`LINGXI_PERMISSION_BITABLE_TABLE_ID` 四个字段（可选 `LINGXI_FEISHU_BASE_URL`），不必复制整份 scheduler 环境文件；源文件换凭据后须同步重做副本。收口用的 `ledger` / `revert` / `verify` 由人工另行执行，不经这份副本。

以上与 §八的告警凭据副本同列为 S-2-6 前置核对项，启用 timer 前逐条确认：

- `pre_apply_hooks` 恰一项，登记的是上述 root 私有副本的绝对路径；程序及全部祖先目录 root 属主、无组 / 其他写、非符号链接。
- 副本内 `<PYTHON_ABSOLUTE_PATH>`、`<GUARD_ABSOLUTE_PATH>`、`<SCHEDULER_ENV_FILE>`、`<GUARD_WORK_DIR>` 四个占位都已换成绝对路径。
- `<SCHEDULER_ENV_FILE>` 是 root 所有、模式恰为 `0600` 的独立副本，含 `backup` 所需四字段；不得直接写部署用户持有的 scheduler 环境文件。
- `<GUARD_WORK_DIR>` 是 root 所有、模式恰为 `0700` 的目录。

### 与权限发布表守卫的接法

预发的 `pre_apply_hooks` 恰有一项，使用控制包内的[宿主包装脚本样例](control/examples/hooks/stage-permission-table-backup.sh)，并参照[权限发布表预发防护](权限发布表预发防护.md)。拉取代理传给它的四个通用参数会被包装脚本忽略；脚本按本机固定配置调用守卫的 `backup`，只有守卫退出 `0` 才继续拉取、迁移或启动新镜像。生产的 `pre_apply_hooks` 必须为空。

## 十、故障语义和人的动作

| 结果码 | 含义 | 代理动作 | 人要做什么 |
| --- | --- | --- | --- |
| `concurrent_run_refused` | 上一轮仍持有锁 | 零外部动作，非零返回 | 等上一轮结束；若长期重复，查 journald 和残留进程 |
| `host_mismatch`（阶段 `agent`） | 宿主契约 `host` 不等于内核主机名（§二） | 取锁前退出码 1；不创建状态目录、不写状态账、不告警、不出网 | 用 `python3 -c 'import socket;print(socket.gethostname())'` 取值改契约的 `host`；不要改主机名去迁就契约 |
| `release_list_unavailable` | gh 入口失败、返回非法列表或没有合格版本 | 不部署；第三轮起告警并保持计数 | 查机器身份入口、出口网络、Release 是否已发布 |
| `downgrade_refused` | 选中目标低于状态账记录或运行容器反查出的最高已部署版本 | 不下载、不 plan、不 apply；告警一次，状态账仍指向已在位目标 | 核对谁改动了 Release 的预发布 / 草稿标记；确需回退走部署器独立批准的 `recover`，不要靠改 Release 标记；已合法 `recover` 到低版本后本码持续出现，按 §三「只升不降的稳态与人工重置」处理 |
| `already_in_place` | 状态账已证实同一目标完成，且本轮运行容器摘要仍与已验证摘要相等 | 只读回读容器；不下载、不部署 | 无需动作 |
| `external_change_detected` | 状态账已 `verified` 的目标，其运行容器缺失、未运行或摘要与已验证摘要不同 | 部署器状态改记 `unknown`，不自动重部署、不沿旧计划接续，每轮只回读 | 核对谁改动了容器；恢复到已验证版本或按部署器恢复契约处理；若这是人工 `recover` 到低版本的结果，按 §三「只升不降的稳态与人工重置」处理 |
| `already_in_place_external` | 三个运行中常驻服务容器的实际 digest 全部命中清单 | 不生成计划、不部署，并登记外部已在位 | 核对手工安装记录；不要重复点击或重复部署 |
| `release_manifest_invalid` / `docker_inspect_unavailable` | 清单或本机只读回读不能形成可靠事实 | 收口为 `unknown`，立即告警 | 查清单附件和 Docker 只读权限，修复后让 timer 重试 |
| `unknown`（阶段 `current_release`） | 运行容器反查不到当前版本：运行中的版本不在本轮列出的非草稿（生产还须非预发布）Release 里，或其清单解析失败 | 不下载、不 plan、不 apply；告警一次，状态账仍指向已在位目标 | 核对运行版本的 Release 是否被改成草稿 / 预发布（§三「运行容器反查的前提」）；不要手工伪造旧版本 |
| `bundle_digest_mismatch` | 控制包、外部索引附件（如有）或 tar 内嵌索引与清单摘要不等 | 删除临时目录，不安装、不 plan、不 apply；状态账仍指向已在位目标，下一轮同一目标重新下载核对，不会被判成在位 | 按 Release 摘要排查附件或篡改；不要手工解包替换 |
| `unknown`（阶段 `bundle`，日志行 `reason=control_bundle_install_failed`） | 控制包入口拒绝安装：目标版本目录 `<BUNDLE_ROOT>/<控制包摘要>/` 已存在但回读不过，最常见是目录里多出 `__pycache__` 这类可写项——成因是有人不带 `-B` 手工在版本目录里跑过脚本（清单工具 `resolve` 会加载同目录的 `deploy/control_bundle.py`）。代理与仓库 systemd 单元已从两头堵住：代理进程内关字节码缓存、子进程带 `-B` 并以 `PYTHONDONTWRITEBYTECODE=1` 兜底，清单工具与部署器入口也各自关缓存；`reason=` 只进日志，不进状态账和告警正文 | 不 plan、不 apply；告警一次（去重键 `unknown + tag`），状态账仍指向已在位目标；下一轮自动重试 | 先查该版本目录里有无 `__pycache__` 或其他可写项（`find <版本目录> -name __pycache__ -o -perm /222`）；处置 = 只删 `__pycache__` 目录、不动任何文件，下一轮自动恢复；没有可写项仍被拒时按 §四第 4 步核对包与索引 |
| `installation_receipt_unusable`（阶段 `installation_receipt`） | 新包已装好，但安装收据不能沿用：缺失、不是 root 0600、键集合 / `schema` 不符、`environment` / `project` 与宿主契约不符、六项人工核对不全为 `true`、`binding_version` 不是正整数，或备份 / 写回失败（日志 `reason=` 指明哪一条） | 不改收据、不 plan、不 apply；告警一次，状态账仍指向已在位目标；下一轮自动重试 | 按[引导安装 §三.9](control/引导安装.md#9-安装收据)核对收据：没做过的核对项不许改成 `true`，先补做对应步骤再改；`bundle_sha256` 不必手改，收据可用后代理会自己刷成新包摘要 |
| `pre_apply_hook_unsafe` | 钩子程序或其任一祖先目录非 root 属主、组 / 其他可写或为符号链接 | 一个钩子都不执行，停在 `planned`，告警，保留计划 | 按 §九「钩子程序的安装路径与属主」修正路径属主与权限后让 timer 重试同一计划；拖过计划窗口就会变成下面 `approval` 阶段的 `unknown` |
| `pre_apply_hook_failed` | 一个前置核验钩子非零或超时 | 停在 `planned`，告警，保留计划 | 查看钩子自己的脱敏证据，修复后重试同一计划 |
| `deploy_timeout` | apply 超过部署上限，结果不能由代理猜 | 保留计划并记 `unknown` 部署器状态，告警，下一轮接续 | 先查部署器 status / 宿主服务，不要手工重跑迁移 |
| `failed` | 部署器 status 明确写出失败 | 原样登记，立即告警，不另造恢复逻辑 | 按部署器状态和计划决定修复或另行批准 recover |
| `unknown` | 部署器或 Docker 无法给出可靠状态 | 保留接续材料，立即告警，不盲重试；计划落盘前的 `unknown` 不把状态账目标推进到新版本 | 先完成客观回读；必要时按部署器恢复契约处理 |
| `unknown`（阶段 `status`，紧接 `阶段=apply 结果码=failed`；部署器 `status` 的 `error=migration_unknown_no_retry`） | 迁移提交前被打断：阶段账有 `migrate: running` 记录，部署器按设计不盲跑迁移，三常驻服务已停 | 每轮沿同一计划 apply 即停；告警只发一条，不会自愈 | 按 §五「迁移提交前中断的人工续跑」用部署器 `resume-migration` 核对后续跑；有作业容器或库头已变就不是这条情形 |
| `unknown`（部署器 `status` 的 `error=env_file_unreadable` / `env_file_malformed` / `env_file_empty`） | 私有 env 文件 `<CONFIG_ROOT>/.env.<环境>.migrate`（回读迁移头）或 `.env.<环境>.scheduler`（常驻 scheduler 未运行时的业务探针）读不到、不是 UTF-8 或不合 Compose 的 env 文件语法（引号未闭合等）、去掉注释后一行都没有；部署器把该文件按 Compose 口径去引号写成用完即删的私有副本再 `docker run`，问题在 `docker run` 之前暴露，原文件不动；`.env.<环境>.migrate` 的问题在停任何服务之前就会停住 | 每轮沿同一计划接续即停；告警一次 | 核对该文件存在、是 UTF-8、按 Compose 语法书写（成对引号不必手工去掉）；修好后下一轮自动接续同一计划 |
| `failed`（部署器 `status` 的 `error=previous_verified_configuration_unavailable`） | 核对旧服务用的可信配置指纹取不到：`host.active.json` 指向的上一次 `verified` 计划文件缺失、指纹不符或形状异常，标记指向未 `verified` 的别的计划，接续时阶段账没有 preflight 记下的 `inventory`，或 `recover` 的被恢复计划读不到（§五「核对旧服务用哪份配置指纹」）；停在停任何服务之前，零动作，不拿当前配置冒充、不读容器标签自证 | 原样登记 `failed`，告警一次 | 核对状态目录里该计划文件与 `host.active.json`（还原口径见 §十二 F21（#805）步骤 3）；不要改 `public-config.json` 去迁就，也不要手工给容器打标签 |
| `failed`（部署器 `status` 的 `error=unfinished_host_deployment`） | 主机在途标记指向另一份未完成计划，且不满足 §五「只在 `prepare` 失败的计划不再占着主机」的五条件（该计划 `unknown` / `running`、已记过 `stop` 及之后的意图、标记与其计划文件对不上、上一次 `verified` 指针不可信）；停在写任何状态之前，零动作 | 每轮生成的新计划都在此停住；告警一次 | 按 §十二 F21（#805）其余情形处置：`unknown` / `running` 的计划走接续或部署器恢复契约，已进副作用阶段的走独立批准的 `recover`；不要手改标记去迁就 |
| `failed`（部署器 `status` 的 `error=public_file_configuration_changed`；同族码 `public_file_directory_required`（`files.<role>` 有登记但 `values` 没给 `LINGXI_<ROLE>_RUNTIME_CONFIG_DIR`）、`public_file_directory_permissions`（登记目录不是绝对路径、是符号链接、不是目录或组 / 其他可写）、`public_file_permissions_or_size`（登记文件是符号链接、不是普通文件、组 / 其他可写或大于 1 MiB），处置相同） | 部署器核对明确非秘密的运行文件（`deploy_runtime.py` `verify_public_files`，:229–264）：按 `values.LINGXI_<ROLE>_RUNTIME_CONFIG_DIR` 登记的目录逐个算 `system_prompt.md` / `content.override.toml` / `company_function_metric_map.toml` 现有文件的 sha256，与 `public-config.json` `files.<role>` 的登记逐项比对，不等即本码——改了文件没改登记、改了登记没改文件、登记的文件不在、目录里多出这几个名字里未登记的文件，都算。核对在 preflight（:221）停任何服务之前做，apply 进行中每个阶段前的 `check_revocation`（:328）再做一遍 | 停在 preflight，零动作：不停服务、不拉镜像、不写在途标记（在途标记只在 preflight 通过后才写），阶段账只记 `status=failed`、`error=<码>`、`stages` 为空；代理 `apply` 非零后以 `status` 收口为 `failed`，告警一次（去重键 `failed + tag`）；`failed` 的计划不接续，此后每轮新建计划都在同一处停住、同一目标不再重复告警；最高已部署版本与已验证摘要不动，状态账仍指向已在位目标。改动发生在 apply 进行中时同码在下一阶段前停住，此时在途标记已写、服务可能已停，按 §十二 F21（#805）处置 | 改提示词这类登记文件必须同批改登记：`sha256sum <目录>/<文件>` 与 `files.<role>` 的登记值逐字相等才算改完（登记值是文件原始字节的 sha256，不是 worker 审计里 strip 后的 12 位摘要）；不要把文件改回去迁就旧登记、不要手工伪造登记、也不要为了过核对删文件；核对相等后让 timer 重试即可，下一轮新建计划照常部署，同一版本不必重新发布 |
| `unknown`（阶段 `approval`，`deployer_state=planned`） | 计划时间窗已过期，批准既不能复用也不能新建 | 每轮沿同一计划走到批准即停；不重新 plan、不 apply；告警只发一条，不会自愈 | 按 §五「计划窗口过期没有自愈」归档该计划的三份文件后让 timer 重新 plan；代码没有解除入口，登记为后续 |
| `verified` | 部署器 status 明确验证成功 | 原样登记；按开关发送一次成功通知 | 回读状态账和 Release 提升编号 |
| `agent_self_update_rejected`（阶段 `agent_self_update`） | 自替换候选不在摘要链上（版本目录内索引与清单 `index_sha256` 不等、索引没有代理条目、候选文件与索引条目摘要不等），或在位路径不可替换（符号链接、不是运行者自有普通文件、所在目录可由组 / 其他主体写入）；日志行 `reason=` 指明哪一条 | 不替换；告警一次（去重键 `结果码 + tag`）；部署链照常进行，本轮部署结论不受影响 | 看审计行的 `reason=` 与 `ls -l` 在位目录（含 `.bak-*`）：链上不符先按 §四第 4 步核对包与索引，不要手工把版本目录里的文件复制到在位路径迁就；在位路径不符按 §八 修正属主 / 权限 / 链接后让 timer 重试 |
| `agent_self_update_failed`（阶段 `agent_self_update`） | 候选已在链上、判定应替换，但写副本 / 写新文件 / 换入失败（`reason=write_failed`），或换入后回读 sha256 不等于候选（`reason=readback_mismatch`）；代理已尽力把旧副本换回 | 告警一次（去重键 `结果码 + tag`）；部署链照常进行；下一轮自动重试 | `sha256sum <ExecStart 路径>` 应仍等于旧代理（`.bak-*` 若在，其前 8 位就是旧摘要）；在位文件缺失或摘要既不是旧也不是候选时，以 root 从 `.bak-*` 或版本目录里已核对的候选按 [引导安装 §二.4](control/引导安装.md#4-代理程序文件的首次安装) 重装一次，再查磁盘 / 权限 |
| `agent_self_update_skipped_not_newer`（阶段 `agent_self_update`） | 候选摘要与在位不同，但版本标记不高于在位（同标记改动或更低标记） | 不替换、不告警，只审计；部署链照常进行 | 无需动作；确要让这份候选上位，发布一个标记更高的版本，不要手工覆盖在位文件 |
| `alert_delivery_failed` | 状态结果已有，但管理群没有确认送达 | 状态账标记未送达，退出非零，下一轮重试 | 修复同一 root 私有告警副本 / 飞书出口；不要另建告警身份 |

`planned`、`running` 是部署器阶段状态，不是代理自行宣布的成功；代理只在计划 / 批准落盘时记住可接续身份，在 apply 后以 `status` 输出覆盖。状态账的最高已部署版本与已验证摘要只在 `verified` 时推进，计划落盘前的失败或未知结果连 `target_tag` 也不动（§五）：没部署的目标不会被记成已在位。任何结果不确定都优先保留原材料和人工核查入口。

## 十一、状态账和公开披露复核

状态账是 `<state-directory>/pull-agent.json`，至少含 `schema`、`host`、`environment`、`last_run_at`、`last_result`、`consecutive_failures`、`target_tag`、`release_url`、`plan_id`、`deployer_state`、`approval_sha256`、`bundle_digest`、`highest_deployed_tag`、`verified_digests`、`external_change_tag`、`alerts`，另含候选 / 提升运行编号和批准来源摘要；所有写入原子替换。部署器另在锁文件同目录维护两份指针（root 0600，原子替换）：`host.active.json` 是当前占用（在途 `running` 或已 `verified`），`host.verified.json` 只在 `verified` 收口时写、始终指向上一次验证成功的计划（`{id, plan_sha256, status}`），供失败计划占用收敛时恢复；旧版本部署器部署过的主机没有后者，首次由 v2.5.1 及之后的部署器 `verified` 时写出。

stdout 供 journald 收集，不写秘密、命令原文或查询串。状态账不是能力证明；本卡尚未在真实 stage / production 主机跑过，也没有真实 Release 下载、Docker 回读、apply、15 分钟观察或飞书告警证据，均留待独立验收。

控制包生产方必须上传 `lingxi-control.tar`；`control-index.json` 附件可选：上传了就必须与清单 `index_sha256` 相等，缺失时代理以 tar 内嵌索引为准（同一摘要钉住，包摘要、索引摘要与逐文件核对一项不减）。GitHub 已对本仓库启用不可变 Release，已发布版本不能事后补附件（`gh release upload` 返回 422），所以已发布的旧版本（如生产现网 v2.4.3）永远没有该附件，代理必须容忍；今后的发布流程是否上传该附件由发布侧决定，两种形态代理都接受。本工作树未伪造另一张卡的五份文件；最终仍由对应工作项提供并经包内索引的精确集合校验。

## 十二、已知边界

- **首次接管中断在「首个服务更新后」再走 `recover` 会停在核对服务清单**：`recover` 计划把原计划的 `old` 放到 `new` 侧，而无标签容器只在 `old` 侧享受首次接管豁免，剩下的无标签旧容器会以 `unplanned_service_artifact_or_config` 被拒。安全上是零动作——核对发生在停任何服务之前，不会停错服务——但这条恢复路径此时走不通；沿同一计划继续 `apply` 接续仍能完成接管，接管完成后 `recover` 按原规则可用。公开配置在两次部署之间改过时同理：中断在「首个服务更新后」剩下的旧容器带的是上一次的配置指纹，`recover` 计划的 `new` 侧只认当前指纹，同样停在核对服务清单；沿同一计划 `apply` 接续仍能完成。登记为已知边界，不改行为。
- **告警投递失败没有第二条通道**：飞书投递失败只在状态账留下 `alert_delivery_failed`（`alerts` 中该键 `delivery_failed=true`）并以非零退出，下一轮重试；这条失败没有接入宿主健康监控（代理状态账由 [#838](https://github.com/Moshuiwang/lingxi/issues/838) 的检查项读取）。无人值守场景下这是残余盲区：飞书出口或告警凭据副本坏掉时，故障本身和「告警发不出去」两件事都只有 journald 和状态账知道。登记为后续工作项处理，本文不把它写成已覆盖。
- **公开配置在两次部署之间被人工改动后，下一次部署在停任何服务之前停住（F20（#804），预发 rc.102 首轮实证，Trace #770 接缝⑩）——已修（v2.5.1；预发 rc.104 真实链路实证：rc.103 `verified` → 人工改 `public-config.json` → 计划 old = X / new = Y → `verified`，Trace #812 评论 5706196423）**：部署器核对 `old` 侧运行容器时改取上一次 `verified` 计划的配置指纹，`new` 侧仍取当前 `public-config.json` 的指纹（§五「核对旧服务用哪份配置指纹」）；文件在两次部署之间改过也照常进入后续阶段，改动随本次部署落到容器标签。修法在部署器侧、随控制包到达，代理不需重装。仍没有「同版本重应用」入口：只改文件不发新版本，幂等判 `already_in_place` 不重起容器，改动落不到容器上。v2.5.1 之前的现象与人工处置保留为历史——代理每轮把 `recovery.config_sha256` 写成**当前**指纹（`_build_request`），部署器拿它核旧容器标签，文件改过就不等，apply 以 `unplanned_service_artifact_or_config` 失败、失败计划逐轮堆积，当时 `public-config.json` 事实上只能还原、不能改；生产 G-3 从首次接管前就把 `values` / `files` 写全，没有撞上。当时的处置步骤：
  1. `systemctl stop lingxi-release-pull.timer`，确认没有代理进程仍在跑。
  2. 取期望指纹：`docker inspect --format '{{index .Config.Labels "io.lingxi.config-sha256"}}' <三个常驻服务容器>`，三者应相同。再算当前文件指纹——与部署器 `fingerprint` 同一编码，**不要从版本目录导入模块去算**（不带 `-B` 会写 `__pycache__`，Trace #770 接缝⑪）：`/opt/lingxi/bin/python3 -B -c 'import sys,json,hashlib;v=json.load(open(sys.argv[1],encoding="utf-8"));print(hashlib.sha256((json.dumps(v,ensure_ascii=False,sort_keys=True,indent=2)+"\n").encode()).hexdigest())' <public-config.json>`。两者不等即本情形；相等就不是，按 §十其它结果码判。
  3. 把当前文件另存到 root 私有目录（0600），再把 `public-config.json` 还原为上一次部署时那份——指纹逐字等于容器标签才算还原完成（没留副本就按差异逐项改回，直到相等）；属主权限仍 `root:root 0644`。
  4. 归档失败计划：状态目录中该 `plan_id` 的 `.plan.json` / `.approval.json` / `.request.json` / `.state.json` 移到 root 私有归档目录（0600）；阶段账 `stages` 应为空——preflight 没过就没有任何阶段，不为空就不是本情形。`pull-agent.json` 与 `host.active.json` 都不动：preflight 没过时部署器不写在途标记，它仍是上一次 `verified` 的标记。
  5. `systemctl start lingxi-release-pull.timer`。下一轮日志 `阶段=plan 结果码=written` 且 `plan_id` 是新值，`old` / `new` 两侧配置指纹相同，按普通流程部署到 `verified`。（v2.5.1 起不再需要还原文件：下一次版本部署以上一次 `verified` 的指纹核旧容器、以当前指纹描述新容器。）
- **`failed` 的计划既不接续也不释放主机在途标记（F21（#805），预发 rc.102 第二轮实证，Trace #770 接缝⑫）——已修（v2.5.1；预发 rc.104 首轮注入一次 prepare 失败 → 自动收敛 `released_markers restored_from=verified_file` → 次轮 `verified`，Trace #812 评论 5706196423）：只在 `prepare` 失败的计划，其占用由下一计划 apply 在锁内按五条件收敛**（§五「只在 `prepare` 失败的计划不再占着主机」）：标记恢复为上一次 `verified` 指针（`host.verified.json`，没有时从 `verified` 阶段账重建；本机从未验证过则删除标记作等价解除），失败计划的账与文件原地保留并追加 `released_by`，新计划账追加 `released_markers`，随后新计划照常 preflight（old 侧按 F20（#804）取恢复指针所指计划的配置指纹）并部署。`_plan_is_continuable` 仍只接续 `planned` / `running` / `unknown`，不扩到 `failed`。现象回顾：部署器 apply 在 preflight 通过后才写 `host.active.json`（`status=running`），此后以非 `Unknown` 的异常失败时不改这份标记，下一轮代理改建新计划，新计划被 `unfinished_host_deployment` 拒绝、每轮重复。**其余情形仍不自动收敛**——失败计划 `unknown` / `running`（先走接续）、阶段账已记过 `stop` 及之后的意图（服务可能已被动过）、标记与失败计划对不上、上一次 `verified` 指针不可信——人工处置按代码如实写（预发以 `s26_w4_seam12.sh` 做过一次）：
  1. `systemctl stop lingxi-release-pull.timer`，确认没有代理进程仍在跑。
  2. 用部署器 `status <失败计划 plan_id>` 看阶段账：只有 `prepare` 一条记录（`running`，或它之后没有任何阶段）才是本情形——`prepare` 只装控制包、拉镜像，不动容器；`docker ps` 三个常驻服务仍是旧版本且 healthy。阶段账里已有 `stop` 或之后的记录就不是本情形：服务已被动过，按部署器恢复契约（独立批准的 `recover`）处理，不要碰标记。
  3. 把 `host.active.json` 还原为上一次 `verified` 计划的标记 `{"id": <plan_id>, "plan_sha256": <该计划指纹>, "status": "verified"}`（root 0600，稳定编码）：上一次 `verified` 的 `plan_id` 取自状态目录里 `.state.json` 为 `verified` 的最近一份计划，计划文件本身就是稳定编码，`sha256sum <plan_id>.plan.json` 即它的 `plan_sha256`。本机从未由部署器部署过（首次接管即失败）时不是还原而是删掉这份标记，让首次接管豁免重新成立。
  4. 归档失败计划的全部文件（`.plan.json` / `.approval.json` / `.request.json` / `.state.json` / `.channel.compose.json`）到 root 私有归档目录；代理已生成的新计划（`planned`，阶段账不存在）保留，下一轮沿它接续。`pull-agent.json` 不动。
  5. `systemctl start lingxi-release-pull.timer`。下一轮日志 `continuation apply_same_plan`（新计划），preflight 通过后写下新计划的在途标记并按阶段账做到 `verified`。（手工还原标记时 `host.verified.json` 不必同步改：它只在 `verified` 收口时由部署器改写。）
