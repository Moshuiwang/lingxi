# 监控告警（S-H2-3，[Trace #373](https://github.com/Moshuiwang/lingxi/issues/373) D5 裁定）

> **产品负责人裁定原文（D5）**：不引 Prometheus；宿主 cron 健康检查脚本 → 受控管理群告警——「服务持续 unhealthy 时有人知道」这一条闭环即可。
>
> **本文交付的是脚本、去重逻辑与安装说明。** `biai-stage` 的真实安装与人为注入 unhealthy 的送达取证已于 2026-08-28 执行完成（Trace #373 S-H2-7），实际安装形态与取证结论见文末「七、已知限制 / 未验证事项」。

## 一、这一层解决什么问题

Lingxi 现在已经有**两层**告警，职责刻意不同：

| 层 | 谁在跑 | 能看见什么 | 看不见什么 |
| --- | --- | --- | --- |
| 应用内 `AlertingDuty`（`src/lingxi/core/alerting.py`，Issue #92/#153） | 挂在 scheduler/gateway/worker-queue **各自进程内部** | 数据库异常、任务滞留、飞书发送失败、开通失败等**业务级**故障；这三个进程各自装配一份，互不共享状态 | **进程自己整个挂掉**——它没法在自己已经死掉之后还发出一条"我死了"的消息 |
| 本文的宿主脚本（`scripts/ops/host_health_alert.py`） | 宿主 cron，**在容器之外** | 容器整体不健康 / 不存在 / 未运行——即 `AlertingDuty` 自己所在的进程死掉、或数据库长期不可达导致 `docker healthcheck` 判定失败这一类"连报警的人都不在了"的情形 | 任何业务级细节（哪个任务失败、哪个用户开通失败）——那些交给上面那层 |

两层不是互相替代，是互补：应用内告警覆盖"活着但出了业务问题"，宿主脚本覆盖"人（进程）已经不在了"。`docker healthcheck` 本身的两段判定语义（依赖可达 + 主循环活性）见 [`deploy/README.md`「健康检查：不开放端口，`docker exec` 语义」](README.md#健康检查不开放端口docker-exec-语义)——本文不重复，只读取它的判定结果（`docker inspect` 的 `State.Health.Status`）。

## 二、组件清单

| 文件 | 作用 |
| --- | --- |
| `scripts/ops/host_health_alert.py` | 宿主脚本本体。纯 Python3 标准库，**不 import `lingxi` 包**、不依赖任何第三方库，只用到 `docker`（读容器状态）与出站 HTTPS（飞书 API）。可在容器全灭的情况下依然跑得动 |
| `tests/test_host_health_alert_script.py` | 状态判定/去重/恢复通知的纯逻辑单测（`python -m unittest tests.test_host_health_alert_script`） |

## 三、安装

### 1. 把脚本放到宿主

脚本不进任何镜像，用 `git`/`scp` 复制到宿主任意目录即可。建议与既有的 `/opt/lingxi`（`deploy/README.md` 里 `alembic.ini` 的宿主安装根目录）同级：

```bash
install -d -m 700 /opt/lingxi/scripts /opt/lingxi/monitoring
install -m 755 scripts/ops/host_health_alert.py /opt/lingxi/scripts/host_health_alert.py
```

### 2. 建凭据文件（0600，与 `deploy/README.md` 七个 `.env.*` 同一条纪律）

凭据**不进 argv、不进日志**：脚本只接受一个文件路径参数（`--env-file`），文件内容是三行 `KEY=VALUE`。用 `install` 一步到位，不要先 `cp` 再 `chmod`（中间会留一个可读窗口）：

```bash
umask 077
install -m 600 -o "$(id -un)" -g "$(id -gn)" /dev/null /opt/lingxi/monitoring/host-monitor.env
```

文件内容（**只示例变量名，不示例取值**；`app_id`/`app_secret` 用 Lingxi 飞书自建应用凭据，`chat_id` 是受控管理群的群 ID，与 scheduler 的 `LINGXI_ADMIN_GROUP_CHAT_ID` 指向同一个群）：

```dotenv
LINGXI_FEISHU_APP_ID=
LINGXI_FEISHU_APP_SECRET=
LINGXI_ADMIN_GROUP_CHAT_ID=
```

值可以用双引号或单引号包裹（脚本会剥一层），不支持变量展开、不支持转义。`chat_id` 必须以 `oc_` 开头，脚本启动时会校验格式；权限不是 `0600`、文件缺字段、`chat_id` 格式不对，脚本会拒绝执行并以退出码 `2` 收尾（不静默降级）。

**这份凭据与容器内 `deploy/.env.<环境>.scheduler` 里的同名值是刻意重复的两份**：宿主脚本必须能在 scheduler 容器完全起不来时依然发出告警，因此不能依赖读取容器内的任何东西（`env_file:` 只注入容器，宿主进程读不到）。两份凭据指向同一个飞书应用与同一个群，不是两个不同的身份。

### 3. 装 crontab

```cron
* * * * * /usr/bin/python3 /opt/lingxi/scripts/host_health_alert.py --env-file /opt/lingxi/monitoring/host-monitor.env >> /opt/lingxi/monitoring/cron.out 2>&1
```

- 每分钟调用一次（脚本设计上支持 1–2 分钟内任意频率，取更短的 1 分钟能让「时延估算」里 cron 轮询这一段最短）。
- `--env-file` 是唯一必填参数；其余全部有默认值：`--containers` 默认 `lingxi-scheduler-1 lingxi-gateway-1 lingxi-worker-queue-1`（对应 `deploy/compose.yaml` 的 `scheduler`/`gateway`/`worker-queue` 三个常驻服务；一次性 `worker`/`migrate`/`reauthorize` job 本来就没有 `healthcheck`，不在监控范围）,`--state-file`/`--log-file`/`--lock-file` 默认落在 `/opt/lingxi/monitoring/` 下。全部参数见 `python3 host_health_alert.py --help`。
- `>> cron.out 2>&1` 只是兜底——脚本自己已经把结构化日志写进 `--log-file`（默认 `/opt/lingxi/monitoring/host-monitor.log`），`cron.out` 只用来捕获参数解析错误一类脚本还没建好 logger 之前的失败。
- 首次安装建议先跑一次 `--dry-run` 确认判定逻辑（不会真的发消息、不会落盘状态变化）：

  ```bash
  python3 /opt/lingxi/scripts/host_health_alert.py --env-file /opt/lingxi/monitoring/host-monitor.env --dry-run
  cat /opt/lingxi/monitoring/host-monitor.log
  ```

### 4. 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 本轮检查已执行完成——**不代表所有容器都健康**，健康结果体现在飞书消息与状态文件里，不体现在退出码里；拿不到单实例锁（上一轮还没跑完）也算 `0`，不是故障 |
| `2` | 脚本自身故障，本轮未能完成检查：凭据文件缺失/权限不对/字段不全、`docker` 命令不可用、状态文件写入失败。值得让 cron 的日志/退出码体现出来，需要人工介入 |

## 四、告警语义

### 触发条件（`docker inspect` 判定，三选一）

1. 容器不存在（`docker inspect <name>` 返回非零退出码）；
2. 容器存在但 `State.Running == false`（例如 `exited`/`created`）；
3. `State.Health.Status == "unhealthy"`——**这一条本身已经隐含"持续"**：docker 自己的 `healthcheck.retries`（当前三个目标服务均为 `3`，见 `deploy/compose.yaml`）要求连续三次探测失败才会把状态翻成 `unhealthy`，脚本不需要再自己攒一次连续失败计数。

`State.Health.Status == "starting"`（仍在 `start_period` 宽限期内）与没有配置 `HEALTHCHECK` 的容器都**不**触发——前者是正常启动期，后者是"这个容器本来就没有可比较的健康信号"。

### 防骚扰（去重）

同一个容器、同一个故障原因（`missing`/`stopped`/`unhealthy` 三选一）只在**首次进入**这个原因时告警一次；原因不变，后续每一轮 cron 调用都不会重复发送。原因发生变化（例如从 `unhealthy` 变成 `missing`，容器在两次探测之间被整个删除了）视为新事件，允许再发一次——两种原因指向的排查动作不同。这套去重靠 `--state-file` 指向的本地 JSON 文件记忆"上一次已经确认送达的告警态"，**只有发送成功之后才会落盘**——发送失败不落盘，保证下一轮 cron 会重新尝试同一个事件，而不是"发送失败也当作已经告警过，从此再也不重试"。

### 恢复通知

判定回到 `healthy`（或"本来就没配置 healthcheck"）时发**一条**恢复通知，随后清空该容器的记忆状态。处于告警态的容器如果观察到 `starting`（重启已开始、仍在宽限期内），既不算新的触发，也**不**确认恢复——过早发一条恢复通知，很可能几十秒后宽限期结束又立刻收到一条新的告警，制造"刚说恢复又说挂了"的噪声；这种情况下记忆状态原样保留，等下一轮拿到确定结果。

### 发送失败与单实例纪律

飞书发送失败（网络错误、超时、飞书返回业务错误码）只写本地日志文件，不抛出未捕获异常、不让 cron 因为一次网络抖动而"崩掉"；失败的事件按上面「防骚扰」所述留在下一轮重试。同一时刻只允许一个实例真正执行检查（`fcntl.flock` 独占锁，`--lock-file`）——与 `AGENTS.md`"共享的外部通道同一时刻只允许一个客户端"同一条纪律，防止两个并发实例同时读旧状态、同时判定"需要告警"，绕开去重机制各发一条重复消息。拿不到锁不是故障，只是"上一轮还没跑完"，本轮安静让路。

## 五、时延估算：从故障发生到告警送达（单一事实源）

> **本节是三服务健康检查时延推导的唯一正文**——[`deploy/生产部署runbook.md`「七、观察期」](生产部署runbook.md)引用本节的公式与数值表，不维护自己的一份（独立审查，时延口径统一）。改这里任何一个数值时，同步核对该文件的引用仍然成立。

**判定窗口的两种失败形状，worst case 不一样，分开算：**

- **A 类：依赖不可达 / 进程崩溃（健康检查命令自己立即失败或直接超时，不需要等待任何内部宽限）**——例如数据库连不上、容器直接退出。worst case 是 docker 自己的重试节奏，且每次探测都按 `timeout` 的上界计入：`retries × (interval + timeout)`。
- **B 类：主循环静默挂起（进程还活着、数据库还连得上，但主循环因为一次未捕获异常或死锁停止消费）**——这正是两段式健康检查设计要抓的那类"假健康"（见 `deploy/README.md`「健康检查」一节）。这类故障要先等活性文件年龄超过 `apps/healthcheck` 里为该角色配置的阈值，该检查才会开始报错，再叠加 docker 的重试节奏：`活性阈值 + retries × (interval + timeout)`。

**公式里为什么要加 `timeout`（此前的版本遗漏了这一项）**：Docker 的健康检查周期是"跑一次检查（最坏耗时到 `timeout` 才判定失败）→ 等 `interval` → 再跑下一次"，不是"每隔 `interval` 固定触发一次、检查耗时另算"——一次检查如果挂到 `timeout` 才被判失败，下一次检查要在这次检查结束之后再等一个 `interval` 才开始。只用 `retries × interval` 会低估最坏情形；`retries × (interval + timeout)` 把每次检查自身的最坏耗时也计进去，是更贴近实际上界的估算。

**`start_period` 为什么不进这两个公式**：`start_period` 只影响"容器刚启动、还没等到第一次成功探测"这段窗口内的失败要不要计入 `retries`（宽限期内的失败不计数，宽限期外才开始计数），管的是**服务从 `starting` 转为 `healthy` 的启动阶段**；本节两个公式建模的是"服务已经处于 `healthy` 稳态之后又出故障，需要多久才被重新判定为 `unhealthy`"——这是两个不同的时间窗口，`start_period` 不参与后者的计算（详见下方「转 healthy 判据」小节）。

**A 类公式自 Issue #409 起多了一个 `db_cache_ttl` 项**：数据库可达性探测引入了一层短期成功结果缓存（`apps/healthcheck` 里的 `_DEFAULT_DB_CACHE_TTL_SECONDS`），一次真实探测成功后，缓存年龄未超过 TTL 的后续探测直接信任缓存、跳过 `import psycopg` 与新建连接（这两项实测占单次冷启动探测成本的绝大部分，见 `src/lingxi/apps/healthcheck/__init__.py` 模块说明）。缓存只在探测成功时刷新，探测失败绝不写入——因此"依赖不可达"从"下一轮就会真实探测"变成"最坏情况下要等缓存过期（至多 `db_cache_ttl`）才会开始真实探测，随后仍按原节奏连续 `retries` 次失败"：`db_cache_ttl + retries × (interval + timeout)`。各角色的 TTL 默认取该角色活性阈值的 80%（留 20% 安全余量），由此保证新的 A 类始终不超过既有的 B 类，**不改变下面「端到端最坏情形」表格的结论**（仍以 B 类为准）。

三个目标服务的 `interval`/`timeout`/`retries`（`deploy/compose.yaml`）、活性阈值与数据库可达性缓存 TTL（均取自 `src/lingxi/apps/healthcheck/__init__.py` 的 `_DEFAULT_MAX_LIVENESS_AGE_SECONDS`/`_DEFAULT_DB_CACHE_TTL_SECONDS`）现值：

| 角色 | `interval` | `timeout` | `retries` | 活性阈值 | DB 缓存 TTL | A 类（缓存过期后 DB 不可达 / 崩溃） | B 类（静默挂起，真正的最坏情形） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| gateway | 23s | 10s | 3 | 30s | 24s | 24+99 = **123s** | 30+99 = **129s** |
| worker-queue | 29s | 10s | 3 | 60s | 48s | 48+117 = **165s** | 60+117 = **177s** |
| scheduler | 30s | 10s | 3 | 180s | 144s | 144+120 = **264s** | 180+120 = **300s** |

（B 类公式的推导：设检查按周期 `interval` 运行，故障发生在最坏相位——上一次通过检查恰好发生在活性年龄刚好达到阈值之前一瞬间，下一次检查因此要再等满一个 `interval` 才排到，随后还需要连续 `retries` 次检查都失败才会被 docker 判定为 `unhealthy`，每次检查按 `timeout` 上界计入；取上确界得到 `活性阈值 + retries × (interval + timeout)`。A 类的推导同理，只是把"活性阈值"换成"DB 缓存 TTL"：故障发生在缓存刚刚被前一次成功探测刷新之后的最坏相位，要先等满一个 TTL 缓存才会过期，随后同样叠加 `retries × (interval + timeout)`。"进程崩溃"这一子情形不经过缓存判断——容器直接退出时健康检查命令本身无法执行，由 `host_health_alert.py` 的"容器不存在/未运行"分支覆盖，不在这两个公式建模范围内，历史上也从未在此。）

**这一段 docker 侧检测完成之后，还要加上宿主监控自己的两段延迟：**

- **cron 轮询**：最坏情况是 docker 状态刚翻成 `unhealthy` 后，脚本刚好错过这一分钟的调用，要等到下一次调用才发现——按本文推荐的每分钟调用节奏，最多再加 **60s**（若按 1–2 分钟里的上限"每 2 分钟"部署，则最多再加 120s）。
- **飞书 HTTP 往返**：换令牌 + 发消息两次请求，正常网络下通常数百毫秒到数秒，本估算按 **≤5s** 计；不含飞书平台自身限流或故障导致的重试等待（那属于飞书侧行为，不在本机制控制范围，也是为什么"发送失败留给下一轮 cron 重试"而不是本地无限重试）。

**端到端最坏情形（B 类 + 每分钟 cron + 5s 网络）**：

| 角色 | 端到端最坏时延 |
| --- | --- |
| gateway | 129+60+5 = **194s（约 3.2 分钟）** |
| worker-queue | 177+60+5 = **242s（约 4.0 分钟）** |
| scheduler | 300+60+5 = **365s（约 6.1 分钟）** |

即"服务持续 unhealthy 时有人知道"这条闭环，最坏情形下大约几分钟量级——D5 裁定的"不引 Prometheus、够用即可"标准下，这个量级是刻意接受的成本（实时监控栈能把这个数字压到秒级，但那是另一条路线的取舍，不在本批范围）。

### 转 healthy 判据（与上面两个公式是不同的窗口，不要互相替代）

上面 A/B 两个公式回答"已经 `healthy` 的服务出故障后，多久会被重新判定为 `unhealthy`"；下面这条回答"服务刚启动，多久应该转为 `healthy`"——两者是**两个不同的判定窗口**，`deploy/生产部署runbook.md`「七、观察期」此前把 A 类时延（69s/119s）当成了"多久应该转 healthy"的期限，这是概念混用（独立审查，时延口径统一）：容器启动后，第一次探测在 `start_period` 内即可发生并可能成功，一旦成功容器立即转 `healthy`，不需要等 `start_period` 结束；`start_period` 只是"在它结束前，失败的探测不计入 `retries`、不会把容器判成 `unhealthy`"，不是"必须等它结束才能变 healthy"的下限。**判据**：服务应在自身 `start_period` 加一个探测周期（`interval + timeout`）内出现至少一次成功探测并转为 `healthy`（gateway `start_period` 20s、worker-queue 32s、scheduler 30s，见 `deploy/compose.yaml`）；超过这个窗口仍未转 `healthy`，才需要介入排查——这不依赖上面的 A/B 公式，公式里的数字不能拿来当这里的期限用。

## 七、已知限制 / 未验证事项

1. **本机结构化文件（源头缓冲）**——一行一样本、UTC 时间戳、按日切分，落

30 天留存窗口的清理机制（本机文件按日切分后的老文件删除、监控库 `sample` 表的
定期收缩）**不在本批范围**，留给后续运维批次接入（类比 `deploy/日志留存.md`
的 `.logrotate` 组合）；本批只保证按日切分与增量上推两个前提成立，不会因为
缺清理导致上推逻辑出错。

### 4. 监控库两层落地设计与凭据约定

- **两层**：本机文件（源头缓冲，30 天窗口目标）+ 监控库 `lingxi_monitoring`
  schema（远程可读层，样本表 + 每日聚合表 + 巡检记录表，见
  `scripts/ops/monitoring/monitoring_schema.sql`）。样本表 `sample` 用
  `(layer, host, sampled_at, payload JSONB)` 四要素设计，`(layer, host,
  sampled_at)` 唯一约束供上推脚本 `ON CONFLICT DO NOTHING` 做幂等，本机文件
  是源头兜底——上推失败本机文件不受影响，下一轮据 cursor 继续重试。
- **凭据边界**：监控库使用独立最小权限角色 `lingxi_monitoring_app`（只对
  `lingxi_monitoring` schema 有 `SELECT`/`INSERT`，无 `CREATEDB`/`CREATEROLE`/
  `SUPERUSER`），**不复用业务库凭据**；监控数据不含用户消息正文，只有计数、
  耗时、分位数与按内部 `user_id`（不透明 ULID，不是姓名/open_id）的聚合。
- **stage 私有凭据文件新增变量**：与 `deploy/README.md`「数据库凭据源」同一份
  Supabase 私有凭据文件（`/home/wangzhipeng/.config/lingxi/supabase-stage.env`，
  0600，属主为部署用户），新增一行 `MONITORING_DSN=`——**值由编排者线下配**，
  本文档与仓库不出现明文取值。业务库 DSN（供 `db_business_sample.sh` 用）沿用
  该文件已有的 `LINGXI_POSTGRES_DSN`，不需要新增变量。
- **两份 systemd EnvironmentFile 各自只装自己需要的那一个 DSN**
  （`db-business.env` 只有 `LINGXI_POSTGRES_DSN`，`push.env` 只有
  `MONITORING_DSN`）——与 `deploy/README.md`「为什么按服务拆而不是共用一份」
  同一条纪律：凭据只进真正需要它的那个进程环境，不整份共享。

## 九、AI 巡检

> issue #410「AI 巡检机制」：出问题时 AI 读监控库/文件定位；持续优化上每日一次
> AI 巡检——读昨日数据写一条巡检记录（趋势/异常/疑点）入监控库；累计约两周产出
> 代码级优化建议并落 issue。巡检先手动周期跑校准口径，稳定后再定时化——本批只
> 约定格式与落库字段，不交付定时巡检作业本身。

巡检记录写入 `lingxi_monitoring.patrol_record` 表（`monitoring_schema.sql`），
使用同一个 `lingxi_monitoring_app` 凭据。字段与格式约定：

| 字段 | 约定 |
| --- | --- |
| `patrol_date` | 巡检覆盖的自然日（通常是"昨天"，UTC） |
| `reviewed_window_start` / `reviewed_window_end` | 实际读取的样本时间窗口，通常等于 `patrol_date` 当天 00:00–24:00 UTC |
| `findings` | 巡检结论正文，中文，覆盖「趋势」（相比前几日的变化方向）、「异常」（超出正常波动范围的具体指标与数值）、「疑点」（数据本身不足以下结论、需要下一轮继续观察的点）三段；无异常时也应留一句"无异常"，不留空 |
| `anomaly_found` | 是否发现需要人工关注的异常（`true`/`false`），飞书群是否发消息由**其他机制**（本节巡检本身不直接发飞书消息，"飞书群保持安静：巡检无异常不发消息"）决定，本字段只是供后续查询筛选用的标记 |
| `follow_up_issue` | 若巡检结论产出了一个新的 GitHub Issue（issue #410"累计约两周产出代码级优化建议并落 issue"），记录该 issue 的编号或 URL；未产出则留 `NULL`，不要填占位字符串 |
| `created_by` | 固定 `'ai-patrol'`（默认值），区分人工巡检与 AI 巡检 |

写入方式（AI 巡检会话内，`psql`/等价 SQL 客户端，凭据来自监控库 DSN）：

```sql
INSERT INTO lingxi_monitoring.patrol_record
  (patrol_date, reviewed_window_start, reviewed_window_end, findings, anomaly_found, follow_up_issue)
VALUES
  ('2026-08-29', '2026-08-29T00:00:00Z', '2026-08-30T00:00:00Z',
   '趋势：任务量较前日持平；异常：无；疑点：worker-queue 容器内存占用较前日上升约 8%，暂在正常波动范围，下一轮继续观察。',
   FALSE, NULL);
```

飞书群保持安静的既有原则不变：巡检本身不触发飞书消息；真正需要人工介入的异常
仍然只经「八、5. 告警阈值接入」与「一～七」既有两层容器/阈值告警发一句简短
警报，巡检记录只是留痕供 AI 与人回读，不是另一条告警通道。
