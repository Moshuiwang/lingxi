# 监控告警（S-H2-3，[Trace #373](https://github.com/Moshuiwang/lingxi/issues/373) D5 裁定）

> **产品负责人裁定原文（D5）**：不引 Prometheus；宿主 cron 健康检查脚本 → 受控管理群告警——「服务持续 unhealthy 时有人知道」这一条闭环即可。
>
> **本文交付的是脚本、去重逻辑与安装说明。** `biai-stage` 的真实安装与人为注入 unhealthy 的送达取证已于 2026-08-28 执行完成（Trace #373 S-H2-7），实际安装形态与取证结论见文末「七、已知限制 / 未验证事项」。

## 一、这一层解决什么问题

Lingxi 现在已经有**两层**告警，职责刻意不同：

| 层 | 谁在跑 | 能看见什么 | 看不见什么 |
| --- | --- | --- | --- |
| 应用内 `AlertingDuty`（`src/lingxi/core/alerting.py`，Issue #92/#153） | 挂在 scheduler/gateway/worker-queue **各自进程内部** | 数据库异常、任务滞留、飞书发送失败、开通失败等**业务级**故障；这三个进程各自装配一份，互不共享状态 | **进程自己整个挂掉**——它没法在自己已经死掉之后还发出一条"我死了"的消息 |
| 本文的宿主脚本（`scripts/ops/host_health_alert.py`） | 宿主 cron，**在容器之外** | 容器整体不健康 / 不存在 / 未运行——即 `AlertingDuty` 自己所在的进程死掉、或数据库长期不可达导致 `docker healthcheck` 判定失败这一类"连报警的人都不在了"的情形 | 任何业务级细节（哪个任务失败、哪个用户开通失败）——那些交给上面那层 |

两层不是互相替代，是互补：应用内告警覆盖"活着但出了业务问题"，宿主脚本覆盖"人（进程）已经不在了"。`docker healthcheck` 本身的两段判定语义（依赖可达 + 主循环活性）见 [`deploy/README.md`「健康检查：不开放端口，`docker exec` 语义」](README.md#健康检查不开放端口docker-exec-语义)——本文不重复，只读取它的判定结果（`docker inspect` 的 `State.Health.Status`）。

## 二、组件清单

| 文件 | 作用 |
| --- | --- |
| `scripts/ops/host_health_alert.py` | 宿主脚本本体。纯 Python3 标准库（3.11 以上，经「三、安装」第 0 步的注入点起），**不 import `lingxi` 包**、不依赖任何第三方库，只用到 `docker`（读容器状态）与出站 HTTPS（飞书 API）。可在容器全灭的情况下依然跑得动 |

## 三、安装

### 0. Python 注入点（宿主侧所有 Python 单元共用，先于其余步骤）

宿主侧起 Python 的三个单元——`lingxi-host-monitor.service`、`lingxi-release-pull.service` 的 `ExecStart`，以及 `lingxi-resource-sample.service` 经 `Environment=LINGXI_PYTHON=` 注入给 `resource_sample.sh` 的解释器——都只指向**一个固定符号链接** `/opt/lingxi/bin/python3`，仓库单元里不出现任何一台机器的真实解释器路径。链接目标就是 [`deploy/control/引导安装.md`「一、前提核对」](control/引导安装.md#一前提核对)定下的 `<PYTHON_ABSOLUTE_PATH>`（3.11 以上；主机默认 `python3` 不作判据——预发默认 `python3` 是 3.9，2026-09-15 实读：单元写死系统 `python3` 时资源采样每分钟失败 80 分钟无人察觉、阈值告警候选版起不来；产品负责人裁定「升级系统」：主机装 3.12、单元钉住它）。

为什么是符号链接而不是 drop-in 覆盖 `ExecStart=`：drop-in 覆盖必须整行重抄（先写一行空 `ExecStart=` 清掉再写新行），仓库单元每次改 `ExecStart` 的参数，这份本机副本都会悄悄落后；链接只承载「这台机器的 Python 在哪」这一个值，与既有 `User=` 走 drop-in 的先例（`monitoring-units/10-local.conf.example`）各管各的。

```bash
# root 级；目录与链接都 root 所有、他人不可写——release-pull 以 root 跑，注入点可被
# 部署用户改写就等于把 root 的解释器交给了普通账号。<PYTHON_ABSOLUTE_PATH> 本身也
# 必须是 root 所有的系统解释器（例如发行版包装的 python3.12），不指向任何用户家目录。
sudo install -d -o root -g root -m 755 /opt/lingxi/bin
sudo ln -sfn <PYTHON_ABSOLUTE_PATH> /opt/lingxi/bin/python3
# 核对：版本 3.11 以上；目录 root:root 755；链接目标逐字等于前提核对那条路径
/opt/lingxi/bin/python3 --version
stat -c '%n %U:%G %a' /opt/lingxi/bin
readlink /opt/lingxi/bin/python3
```

装完单元后回读（本节第 3 步与「八」第 5 步各做一次）：

```bash
systemctl cat lingxi-host-monitor.service lingxi-release-pull.service | grep '^ExecStart='
systemctl cat lingxi-resource-sample.service | grep '^Environment=LINGXI_PYTHON='
```

期望：两条 `ExecStart=` 都以 `/opt/lingxi/bin/python3` 开头，`Environment=LINGXI_PYTHON=/opt/lingxi/bin/python3` 在位；drop-in 里若为 `--enable-resource-thresholds` 重抄了 host-monitor 的 `ExecStart`，重抄行同样以 `/opt/lingxi/bin/python3` 开头。以后升级主机 Python 只改链接目标（再跑一次上面的 `ln -sfn`），单元不动、不需要 `daemon-reload`；`resource_sample.sh` 在链接缺失或版本低于 3.11 时退出码 `2` 并打印实际版本，不会静默落回 PATH 上的 `python3`。

### 1. 把脚本放到宿主

脚本不进任何镜像，用 `git`/`scp` 复制到宿主任意目录即可。建议与既有的 `/opt/lingxi`（`deploy/README.md` 里 `alembic.ini` 的宿主安装根目录）同级：

```bash
install -d -m 700 /opt/lingxi/scripts /opt/lingxi/monitoring
install -m 755 scripts/ops/host_health_alert.py /opt/lingxi/scripts/host_health_alert.py
```

### 2. 建凭据文件（0600，与 `deploy/README.md` 七个 `.env.*` 同一条纪律）

凭据**不进 argv、不进日志**：脚本只接受一个文件路径参数（`--env-file`），文件内容是三行 `KEY=VALUE`。用 `install` 一步到位，不要先 `cp` 再 `chmod`（中间会留一个可读窗口）：

```bash
umask 077
install -m 600 -o "$(id -un)" -g "$(id -gn)" /dev/null /opt/lingxi/monitoring/host-monitor.env
```

文件内容（**只示例变量名，不示例取值**；`app_id`/`app_secret` 用 Lingxi 飞书自建应用凭据，`chat_id` 是受控管理群的群 ID，与 scheduler 的 `LINGXI_ADMIN_GROUP_CHAT_ID` 指向同一个群）：

```dotenv
LINGXI_FEISHU_APP_ID=
LINGXI_FEISHU_APP_SECRET=
LINGXI_ADMIN_GROUP_CHAT_ID=
```

值可以用双引号或单引号包裹（脚本会剥一层），不支持变量展开、不支持转义。`chat_id` 必须以 `oc_` 开头，脚本启动时会校验格式；权限不是 `0600`、文件缺字段、`chat_id` 格式不对，脚本会拒绝执行并以退出码 `2` 收尾（不静默降级）。

**这份凭据与容器内 `deploy/.env.<环境>.scheduler` 里的同名值是刻意重复的两份**：宿主脚本必须能在 scheduler 容器完全起不来时依然发出告警，因此不能依赖读取容器内的任何东西（`env_file:` 只注入容器，宿主进程读不到）。两份凭据指向同一个飞书应用与同一个群，不是两个不同的身份。

### 3. 装周期触发（systemd timer 为准，无 systemd 的宿主用 crontab）

**首选：systemd timer（仓库已入库单元）**——`biai-stage` 与 `biplus-prod` 都没有 cronie，实际跑的就是这条路：

```bash
sudo install -m 644 deploy/monitoring-units/lingxi-host-monitor.service \
  deploy/monitoring-units/lingxi-host-monitor.timer /etc/systemd/system/
# 本机 drop-in 提供 User=（仓库单元不写死，见 monitoring-units/10-local.conf.example）
sudo install -d -m 755 /etc/systemd/system/lingxi-host-monitor.service.d
sudo install -m 644 <本机 10-local.conf> /etc/systemd/system/lingxi-host-monitor.service.d/10-local.conf
sudo systemctl daemon-reload
sudo systemctl enable --now lingxi-host-monitor.timer
systemctl cat lingxi-host-monitor.service   # 回读：User= 必须是本机部署用户，ExecStart= 以 /opt/lingxi/bin/python3 开头（第 0 步）
systemctl list-timers 'lingxi-host-monitor.timer'
```

**备选：crontab**（宿主装了 cron 时语义等效）：

```cron
* * * * * /opt/lingxi/bin/python3 /opt/lingxi/scripts/host_health_alert.py --env-file /opt/lingxi/monitoring/host-monitor.env >> /opt/lingxi/monitoring/cron.out 2>&1
```

- 每分钟调用一次（脚本设计上支持 1–2 分钟内任意频率，取更短的 1 分钟能让「时延估算」里 cron 轮询这一段最短）。
- `--env-file` 是唯一必填参数；其余全部有默认值：`--containers` 默认 `lingxi-scheduler-1 lingxi-gateway-1 lingxi-worker-queue-1`（对应 `deploy/compose.yaml` 的 `scheduler`/`gateway`/`worker-queue` 三个常驻服务；一次性 `worker`/`migrate`/`reauthorize` job 本来就没有 `healthcheck`，不在监控范围）,`--state-file`/`--log-file`/`--lock-file` 默认落在 `/opt/lingxi/monitoring/` 下。全部参数见 `/opt/lingxi/bin/python3 /opt/lingxi/scripts/host_health_alert.py --help`。
- `>> cron.out 2>&1` 只是兜底——脚本自己已经把结构化日志写进 `--log-file`（默认 `/opt/lingxi/monitoring/host-monitor.log`），`cron.out` 只用来捕获参数解析错误一类脚本还没建好 logger 之前的失败。
- 首次安装建议先跑一次 `--dry-run` 确认判定逻辑（不会真的发消息、不会落盘状态变化）：

  ```bash
  /opt/lingxi/bin/python3 /opt/lingxi/scripts/host_health_alert.py --env-file /opt/lingxi/monitoring/host-monitor.env --dry-run
  cat /opt/lingxi/monitoring/host-monitor.log
  ```

### 4. 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 本轮检查已执行完成——**不代表所有容器都健康**，健康结果体现在飞书消息与状态文件里，不体现在退出码里；拿不到单实例锁（上一轮还没跑完）也算 `0`，不是故障 |
| `2` | 脚本自身故障，本轮未能完成检查：凭据文件缺失/权限不对/字段不全、`docker` 命令不可用、状态文件写入失败。值得让 cron 的日志/退出码体现出来，需要人工介入 |

## 四、告警语义

### 触发条件（`docker inspect` 判定，三选一）

1. 容器不存在（`docker inspect <name>` 返回非零退出码）；
2. 容器存在但 `State.Running == false`（例如 `exited`/`created`）；
3. `State.Health.Status == "unhealthy"`——**这一条本身已经隐含"持续"**：docker 自己的 `healthcheck.retries`（当前三个目标服务均为 `3`，见 `deploy/compose.yaml`）要求连续三次探测失败才会把状态翻成 `unhealthy`，脚本不需要再自己攒一次连续失败计数。

`State.Health.Status == "starting"`（仍在 `start_period` 宽限期内）与没有配置 `HEALTHCHECK` 的容器都**不**触发——前者是正常启动期，后者是"这个容器本来就没有可比较的健康信号"。

### 防骚扰（去重）

同一个容器、同一个故障原因（`missing`/`stopped`/`unhealthy` 三选一）只在**首次进入**这个原因时告警一次；原因不变，后续每一轮 cron 调用都不会重复发送。原因发生变化（例如从 `unhealthy` 变成 `missing`，容器在两次探测之间被整个删除了）视为新事件，允许再发一次——两种原因指向的排查动作不同。这套去重靠 `--state-file` 指向的本地 JSON 文件记忆"上一次已经确认送达的告警态"，**只有发送成功之后才会落盘**——发送失败不落盘，保证下一轮 cron 会重新尝试同一个事件，而不是"发送失败也当作已经告警过，从此再也不重试"。

### 恢复通知

判定回到 `healthy`（或"本来就没配置 healthcheck"）时发**一条**恢复通知，随后清空该容器的记忆状态。处于告警态的容器如果观察到 `starting`（重启已开始、仍在宽限期内），既不算新的触发，也**不**确认恢复——过早发一条恢复通知，很可能几十秒后宽限期结束又立刻收到一条新的告警，制造"刚说恢复又说挂了"的噪声；这种情况下记忆状态原样保留，等下一轮拿到确定结果。

### 发送失败与单实例纪律

飞书发送失败（网络错误、超时、飞书返回业务错误码）只写本地日志文件，不抛出未捕获异常、不让 cron 因为一次网络抖动而"崩掉"；失败的事件按上面「防骚扰」所述留在下一轮重试。同一时刻只允许一个实例真正执行检查（`fcntl.flock` 独占锁，`--lock-file`）——与 `AGENTS.md`"共享的外部通道同一时刻只允许一个客户端"同一条纪律，防止两个并发实例同时读旧状态、同时判定"需要告警"，绕开去重机制各发一条重复消息。拿不到锁不是故障，只是"上一轮还没跑完"，本轮安静让路。

### 拉取代理单元检查（默认开启）

拉取代理（[`deploy/拉取代理.md`](拉取代理.md)，`lingxi-release-pull.timer` 每五分钟触发一次 `.service`）是无人值守升级的唯一入口，它自己停摆时不会有任何进程替它出声；代理开启自替换之后，「新代理起不来」的唯一表现就是「下一轮没有发生」。本检查由同一个宿主脚本在每分钟巡检里顺带完成，**不传参数即开启**（现装的 `lingxi-host-monitor.service` 不需要改 `ExecStart`），`--disable-release-pull-check` 是逃生口。

**判据（四个键各自独立去重，共用 `--threshold-state-file` 与阈值三项同一套告警 / 恢复语义）：**

| 键 | 触发 | 说明 |
| --- | --- | --- |
| `release_pull_timer_inactive` | timer 的 `ActiveState` 不是 `active`（即 `systemctl is-active` 打印的值） | 被 `stop`、`failed`、未安装（`LoadState=not-found`，正文里会带出来）都算。此时不再判留痕过期——停摆的根因已经报过，不为同一件事发第二条 |
| `release_pull_trigger_stale` | 最近一次留痕距今超过 `--release-pull-stale-minutes`（默认 **15** 分钟 = 三个轮询周期） | 留痕 = timer 的 `LastTriggerUSec` 与 service 的 `ExecMainExitTimestamp` 二者取新；两者都没有（从未触发也从未跑完）按过期处理 |
| `release_pull_last_run_failed` | service 的 `Result` 不是 `success` **且** `ExecMainStatus` 非零 | 代理自身告警投递失败时以非零退出、`Result=exit-code`，也落在这里 |
| `release_pull_unknown` | 任何一步读不到：`systemctl` 不存在、非零退出、属性缺失或时间戳解析不了 | **读不到不算正常**——以「未知」形态告警一次，去重、恢复后一条恢复通知；这一轮三个正常判据不出结论、记忆原样保留 |

**为什么只读 systemd 属性、不读代理状态账**：宿主监控经 drop-in 以部署用户运行，代理以 root 运行，状态账 `pull-agent.json` 在 root `0700` 的状态目录里——监控读不到，也不该为了读它而升权。`systemctl show` 的属性任何用户都能查，`show` 对已停止甚至不存在的单元照常以 0 退出并打印属性，非零退出只剩「问不到 systemd 本身」一种含义（`is-active` 对非 active 单元本来就非零退出，无法当作读取失败的信号），所以脚本统一走 `systemctl show --all -p …`，子进程固定 `TZ=UTC` 让时间戳有确定时区。

**为什么判触发过期而不是完成过期**：单轮可长达一小时（含部署器的观察期），timer 在 service 仍在运行时不会再触发。只看「上一轮完成」会把一次正常的长部署判成停摆；所以 service 处于 `activating` / `active`（正在运行）时既不判过期也不判上一轮失败（运行中 systemd 会把 `Result` / 退出码重置为成功，结论要等它跑完），留痕取「触发」与「结束」二者之新则消掉了「长部署刚结束、下一个五分钟刻度还没到」这个窗口。

**参数**：`--release-pull-unit`（单元基名，默认 `lingxi-release-pull`，派生 `.timer` / `.service`）、`--release-pull-stale-minutes`（默认 15）、`--systemctl-bin`（默认 `systemctl`，测试注入用）、`--disable-release-pull-check`。

**告警正文**：`[BI Plus 宿主监控] 告警` + 判据名 + 一句话事实（单元名、timer / service 状态、上一次触发时刻（UTC）、上一轮 `Result`/退出码、留痕年龄与阈值）+ 主机名 + 时间；恢复通知同构。正文只含 systemd 属性取值与错误类别，不含凭据、宿主路径、命令原文与日志原文（`tests/test_host_health_alert_script.py` 的否定用例把带哨兵的 `ExecStart` / `Environment` 塞进桩输出与进程环境，断言零命中）。环境名不在正文里：脚本没有能推得环境的既有参数，主机名即区分预发 / 生产的依据。

**退出码不变**：本检查与阈值三项一样不改变容器主线的退出码语义——单元停摆体现在飞书消息与 `--threshold-state-file`，不体现在退出码里。

**时延估算**：停摆最坏在下一个五分钟刻度错过后开始计时，留痕过期要满 15 分钟才判定，再加最多 1 分钟巡检间隔与 ≤ 5 秒飞书往返——**最坏约 16 分钟**；timer 被停、上一轮失败这两种形态不经过过期窗口，最坏 1 分钟 + 5 秒。

## 五、时延估算：从故障发生到告警送达（单一事实源）

> **本节是三服务健康检查时延推导的唯一正文**——[`deploy/生产部署runbook.md`「七、观察期」](生产部署runbook.md)引用本节的公式与数值表，不维护自己的一份（独立审查，时延口径统一）。改这里任何一个数值时，同步核对该文件的引用仍然成立。

**判定窗口的两种失败形状，worst case 不一样，分开算：**

- **A 类：依赖不可达 / 进程崩溃（健康检查命令自己立即失败或直接超时，不需要等待任何内部宽限）**——例如数据库连不上、容器直接退出。worst case 是 docker 自己的重试节奏，且每次探测都按 `timeout` 的上界计入：`retries × (interval + timeout)`。
- **C 类：临时目录（`/tmp`）写满**（Issue #494）——健康检查每一轮都现读一次 `statvfs`，可用空间低于总量的 10% 立即判失败，不经任何缓存、也不需要等待任何内部宽限，因此 worst case 与 A 类同形：`retries × (interval + timeout)`（worker-queue = 117s）。**这一类此前完全不可见**：`/tmp` 是内存盘，活性文件是十几字节的覆盖写、不需要新页，盘 100% 满时心跳照写不误、数据库照连得上，于是"用户任务在失败、容器显示 healthy、运维查不出原因"可以无限期持续（rc22 收尾批 S-12 浸泡实测）。判红文案形如 `unhealthy role=worker reason=临时目录可用空间 0.0MiB 低于阈值 25.6MiB（总量 256.0MiB，下限比例 10%）`；阈值按**比例**而不是固定字节，因为六个服务各自的 tmpfs 上限不同（worker/worker-queue 256m，其余四个 16m）。
- **B 类：主循环静默挂起（进程还活着、数据库还连得上，但主循环因为一次未捕获异常或死锁停止消费）**——这正是两段式健康检查设计要抓的那类"假健康"（见 `deploy/README.md`「健康检查」一节）。这类故障要先等活性文件年龄超过 `apps/healthcheck` 里为该角色配置的阈值，该检查才会开始报错，再叠加 docker 的重试节奏：`活性阈值 + retries × (interval + timeout)`。

**公式里为什么要加 `timeout`（此前的版本遗漏了这一项）**：Docker 的健康检查周期是"跑一次检查（最坏耗时到 `timeout` 才判定失败）→ 等 `interval` → 再跑下一次"，不是"每隔 `interval` 固定触发一次、检查耗时另算"——一次检查如果挂到 `timeout` 才被判失败，下一次检查要在这次检查结束之后再等一个 `interval` 才开始。只用 `retries × interval` 会低估最坏情形；`retries × (interval + timeout)` 把每次检查自身的最坏耗时也计进去，是更贴近实际上界的估算。

**`start_period` 为什么不进这两个公式**：`start_period` 只影响"容器刚启动、还没等到第一次成功探测"这段窗口内的失败要不要计入 `retries`（宽限期内的失败不计数，宽限期外才开始计数），管的是**服务从 `starting` 转为 `healthy` 的启动阶段**；本节两个公式建模的是"服务已经处于 `healthy` 稳态之后又出故障，需要多久才被重新判定为 `unhealthy`"——这是两个不同的时间窗口，`start_period` 不参与后者的计算（详见下方「转 healthy 判据」小节）。

**A 类公式自 Issue #409 起多了一个 `db_cache_ttl` 项，P1-4（独立审查）修订了 TTL 取值公式与 A 类公式本身**：数据库可达性探测引入了一层短期成功结果缓存（`apps/healthcheck` 里的 `_DEFAULT_DB_CACHE_TTL_SECONDS`），一次真实探测成功后，缓存年龄未超过 TTL 的后续探测直接信任缓存、跳过 `import psycopg` 与新建连接（这两项实测占单次冷启动探测成本的绝大部分，见 `src/lingxi/apps/healthcheck/__init__.py` 模块说明）。缓存只在探测成功时刷新，探测失败绝不写入。

**旧版本（TTL 取活性阈值固定 80%）撞上了"网格量化"缺陷**：缓存是否过期只在 healthcheck 自己被调用的那个离散节拍（`interval`）上被"发现"，不是过期那一刻就立刻触发真实探测。旧版 gateway 的 TTL 是 24s，只比它自己的 `interval`（23s）多 1 秒——缓存在 t=0 刷新后，t=23 时年龄 23s 仍 ≤ 24s、命中缓存，要到 t=46 年龄才终于超过 24s、触发第一次真实探测：实际要等的不是天真假设的 24s，而是接近整整一个 `interval` 之后的 46s。叠加 `retries × (interval + timeout)` = 99s，gateway 的 A 类真实最坏时延是 **145s**，超过了同角色 B 类的 129s——直接打破"A 类不超过 B 类"这条本表格结论依赖的不变量（此前的表格用旧公式算出 123s，是一个被网格量化掩盖掉的错误数字）。

**新公式**：TTL 的取值改为 `TTL = liveness_max_age − 2 × interval`（下限 0，即禁用缓存——禁用后每一轮都做真实探测，退化为没有 TTL 项的 `retries × (interval + timeout)`，比任何非零 TTL 都更快发现故障）；A 类最坏时延公式相应改为 `(db_cache_ttl + interval) + retries × (interval + timeout)`（TTL 禁用时没有前一段，退化为 `retries × (interval + timeout)`）——多出的这个 `+ interval` 就是网格量化的安全上界（`ceil(TTL/interval) × interval < TTL + interval`，比精确值更宽松也更容易人工核对）。选"减两倍 interval"而不是一倍：要让新 A 类不超过 B 类，充分条件是 `TTL + interval ≤ liveness_max_age`，即 `TTL ≤ liveness_max_age − interval`；减两倍 interval 比这个必要条件更保守，多留出整整一个 interval 的显式安全余量，不是刚好卡线。公式实现与完整推导见 `src/lingxi/apps/healthcheck/__init__.py` 的 `_compute_db_cache_ttl_seconds`；`tests/test_liveness_and_healthcheck.py` 的 `HealthcheckTtlLatencyContractTests` 把"各角色 A 类 ≤ B 类"钉成断言，回归时会在测试阶段炸掉。

三个目标服务的 `interval`/`timeout`/`retries`（`deploy/compose.yaml`）、活性阈值与数据库可达性缓存 TTL（均取自 `src/lingxi/apps/healthcheck/__init__.py` 的 `_DEFAULT_MAX_LIVENESS_AGE_SECONDS`/`_DEFAULT_DB_CACHE_TTL_SECONDS`）现值：

| 角色 | `interval` | `timeout` | `retries` | 活性阈值 | DB 缓存 TTL | A 类（缓存过期后 DB 不可达 / 崩溃） | B 类（静默挂起，真正的最坏情形） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| gateway | 23s | 10s | 3 | 30s | 0s（禁用，见上方推导） | 99 = **99s** | 30+99 = **129s** |
| worker-queue | 29s | 10s | 3 | 60s | 2s | (2+29)+117 = **148s** | 60+117 = **177s** |
| scheduler | 30s | 10s | 3 | 180s | 120s | (120+30)+120 = **270s** | 180+120 = **300s** |

（B 类公式的推导：设检查按周期 `interval` 运行，故障发生在最坏相位——上一次通过检查恰好发生在活性年龄刚好达到阈值之前一瞬间，下一次检查因此要再等满一个 `interval` 才排到，随后还需要连续 `retries` 次检查都失败才会被 docker 判定为 `unhealthy`，每次检查按 `timeout` 上界计入；取上确界得到 `活性阈值 + retries × (interval + timeout)`。A 类的推导类似，只是把"活性阈值"换成"DB 缓存 TTL"，并多算一层网格量化：故障发生在缓存刚刚被前一次成功探测刷新之后的最坏相位，缓存要先等满一个 TTL 才会过期，过期后还要再等到下一次 healthcheck 调用（最坏再等满一个 `interval`）才会真正触发一次真实探测，随后同样叠加 `retries × (interval + timeout)`；TTL=0（禁用缓存）时没有等待缓存过期这一步，直接从第一次调用起就是真实探测，退化为只剩 `retries × (interval + timeout)`。"进程崩溃"这一子情形不经过缓存判断——容器直接退出时健康检查命令本身无法执行，由 `host_health_alert.py` 的"容器不存在/未运行"分支覆盖，不在这两个公式建模范围内，历史上也从未在此。）

**这一段 docker 侧检测完成之后，还要加上宿主监控自己的两段延迟：**

- **cron 轮询**：最坏情况是 docker 状态刚翻成 `unhealthy` 后，脚本刚好错过这一分钟的调用，要等到下一次调用才发现——按本文推荐的每分钟调用节奏，最多再加 **60s**（若按 1–2 分钟里的上限"每 2 分钟"部署，则最多再加 120s）。
- **飞书 HTTP 往返**：换令牌 + 发消息两次请求，正常网络下通常数百毫秒到数秒，本估算按 **≤5s** 计；不含飞书平台自身限流或故障导致的重试等待（那属于飞书侧行为，不在本机制控制范围，也是为什么"发送失败留给下一轮 cron 重试"而不是本地无限重试）。

**端到端最坏情形（B 类 + 每分钟 cron + 5s 网络）**：

| 角色 | 端到端最坏时延 |
| --- | --- |
| gateway | 129+60+5 = **194s（约 3.2 分钟）** |
| worker-queue | 177+60+5 = **242s（约 4.0 分钟）** |
| scheduler | 300+60+5 = **365s（约 6.1 分钟）** |

即"服务持续 unhealthy 时有人知道"这条闭环，最坏情形下大约几分钟量级——D5 裁定的"不引 Prometheus、够用即可"标准下，这个量级是刻意接受的成本（实时监控栈能把这个数字压到秒级，但那是另一条路线的取舍，不在本批范围）。

### 转 healthy 判据（与上面两个公式是不同的窗口，不要互相替代）

上面 A/B 两个公式回答"已经 `healthy` 的服务出故障后，多久会被重新判定为 `unhealthy`"；下面这条回答"服务刚启动，多久应该转为 `healthy`"——两者是**两个不同的判定窗口**，`deploy/生产部署runbook.md`「七、观察期」此前把 A 类时延（69s/119s）当成了"多久应该转 healthy"的期限，这是概念混用（独立审查，时延口径统一）：容器启动后，第一次探测在 `start_period` 内即可发生并可能成功，一旦成功容器立即转 `healthy`，不需要等 `start_period` 结束；`start_period` 只是"在它结束前，失败的探测不计入 `retries`、不会把容器判成 `unhealthy`"，不是"必须等它结束才能变 healthy"的下限。**判据**：服务应在自身 `start_period` 加一个探测周期（`interval + timeout`）内出现至少一次成功探测并转为 `healthy`（gateway `start_period` 20s、worker-queue 32s、scheduler 30s，见 `deploy/compose.yaml`）；超过这个窗口仍未转 `healthy`，才需要介入排查——这不依赖上面的 A/B 公式，公式里的数字不能拿来当这里的期限用。

- **预发峰值样本与「停 queue 时重启 gateway」恢复证据（[Issue #756](https://github.com/Moshuiwang/lingxi/issues/756) ③④，Trace #812 S-2-5，2026-09-17，候选 rc.105，预发 2 vCPU / 3.75 GiB，L4a；[评论 5709261607](https://github.com/Moshuiwang/lingxi/issues/812#issuecomment-5709261607)）**：③ 方法 = `host_health_alert.py --enable-resource-thresholds` 每分钟一样本写 `/var/log/lingxi/monitoring/resource-<日期>.log`，容器段取 `docker stats`（cgroup）瞬时值；真实问数窗口（± 5 分钟，8 样本）峰值内存 worker-queue **196.9 MiB / 2048 MiB（9.6%）**（执行中；空闲中位 26.5 MiB）、gateway 186.2 MiB / 512 MiB（36.4%）、scheduler 52.0 MiB / 512 MiB（10.2%），宿主 `mem_available` 最低 2.35 GiB；开通链窗口（18 样本）gateway 峰值 206 MiB / 40%。CPU 一分钟一采样抓不到 42 秒任务的秒级峰值，不作结论。④ T2：`docker stop worker-queue` → 一句真实问数入队（`queued`，无人领取）→ `docker restart gateway` → `docker start worker-queue` → 同一 worker 领取并 `succeeded`（attempt 1 / retry 0），`task_delivery_event` `terminal success` 恰 1 条、平台消息恰 1 个，`delivery_consumed_sequence=7`——停机期间入队的任务在恢复后一次执行、唯一送达，无重复无丢失；回退路径未用到。判定值均由 `task` / `task_delivery_event` 与监控日志写出。
- **监控自身失效是静默的**（独立审查 P2-6）：cron 被误删、`--lock-file` 因异常未释放导致长期"拿不到锁"、宿主重启后 cron 服务未随之起来等情形下，宿主监控这一整层会无声停摆——没有另一层机制监视"这个监控本身是不是还在跑"，属于当前裁定接受的边界（D5 裁定"够用即可"，不是"万无一失"），不是本卡遗漏的缺口。缓解手段是安装态核对：`biai-stage` 的 L4a 验收除了故障注入送达取证外，还应核对 crontab 条目确实存在、`cron.out`/`--log-file` 有持续新增的时间戳（证明脚本确实在被周期性调用），而不是只信"当初装过一次"。
- **拉取代理自身告警投递失败只覆盖了一半**：代理**部署类**告警的飞书投递失败以非零退出、`Result=exit-code`，「四、拉取代理单元检查」的 `release_pull_last_run_failed` 能抓到「上一轮非零退出」这一半；**自替换类（`agent_self_update_*`）与 PAT 类（`pat_*`）告警的投递失败只留 journald 一行、返回码不变，本检查完全抓不到**；失败正文与原因（到底是哪个故障没发出去）仍只在 journald 与 root 私有的状态账里，本检查读不到也不转述，`deploy/拉取代理.md` §十二 那条边界因此是「部分覆盖」而不是「已覆盖」。

## 八、AI 可读监控体系：五层采集与两层落地（S-RC20-410，Issue #410）

> **目标形态**（产品负责人 2026-08-29 于 #373 PM 回归中拍板）：AI 可读、人只
> 决策——不做看板、不装重型监控应用；数据落成结构化文件/表供 AI 直接分析；
> 飞书管理群只发**简短警报**（一句「什么异常 + 请操作 AI 处理」），细节全留给
> AI 读；人类决策菜单只有两项：扩容，或立 issue 改代码。
>
> **监控库落点**（PM 裁定，2026-08-29）：因 Supabase 免费档配额下测试＋生产两个
> 项目已用满（#411 裁定评论），监控库**不新建独立专用实例**，改落**测试实例内
> 独立 schema**（`lingxi_monitoring`）——测试与生产宿主的监控数据均推到这一个
> schema；与生产业务库是不同实例，天然解耦，零新增成本。本节与下方两小节按此
> 落点撰写；`Issue #410` 正文「数据落地」第 3 点"默认独立实例"以此为准修订。

本节交付的是这一整套体系的采集/上推脚本与监控库结构；与「一～七」的宿主容器
健康告警是**互补关系，不是替代**——那一层管"进程/容器还活不活着"，本节管"活着
的进程各项资源、数据库、业务指标是什么样，AI 能不能不登生产就分析到"。

### 1. 五层采集清单

| 层 | 指标 | 采法 | 周期 | 落点 |
| --- | --- | --- | --- | --- |
| 资源 | load、每容器 CPU/内存/PIDs、磁盘用量与增速、网卡收发累计与增速、每容器网络/块 IO | `scripts/ops/monitoring/resource_sample.sh`（bash 拉起 `docker stats` + 同目录 `_resource_sample.py` 读 `/proc`/标准库） | 1 分钟一轮（一次调用=一行样本） | `resource-YYYYMMDD.log` |
| 数据库 | 连接数（按 state 分布）、慢查询近似（active 且超 3s）、库/表大小、云库端到端往返延迟 | `scripts/ops/monitoring/db_business_sample.sh`（一次 psql 调用，见下） | 5 分钟一轮 | `db_business-YYYYMMDD.log`（`metrics.database`） |
| 业务 | 任务状态分布/耗时分位（p50/p95/p99）/队列深度与最老排队时长/投递终态分布/`task.error_kind` 分布/token 用量按用户日聚合 | 同上（数据库层与业务层共用同一次 psql 往返，理由见脚本头注） | 5 分钟一轮 | 同上（`metrics.business`） |
| 百炼 | 见「已知限制」——本批**不**新增按限流码细分的字段（issue #410「百炼层补充」②，需要额外产品代码改动，不在本 Story 范围）；当前唯一可得信号是 `task.error_kind` 分布，模型调用失败目前统一落在 `session_failed` 等既有取值里 | 随业务层同一次采样 | 5 分钟一轮 | 同上（`task_error_kind_counts` 字段） |
| 即时告警 | 磁盘 >85%、load 持续 >2×核数、采样文件停更 >10 分钟（本节新增）；服务挂/`unhealthy`（既有「一～七」宿主告警，不变） | `scripts/ops/host_health_alert.py --enable-resource-thresholds`，沿用既有飞书群通道与去重 | 与「一～七」一致，1 分钟一轮 | 飞书管理群简短警报 |

两层数据落地：

1. **本机结构化文件（源头缓冲）**——一行一样本、UTC 时间戳、按日切分，落
   `/var/log/lingxi/monitoring/`。零依赖兜底：网络断、监控库不可达时证据仍在
   本机；即时告警（磁盘/负载/停更）直接从这一层判，不依赖监控库可达。
2. **上推监控库（远程可读层）**——`scripts/ops/monitoring/push_to_monitoring.sh`
   每 5 分钟把本机文件里新增的行追加写入 `lingxi_monitoring.sample` 表；本轮有
   成功上推后另起第二个 `psql` 进程（同一 `MONITORING_DSN`）删除 30 天前样本；AI 从任意拿到监控库凭据的环境 SQL
   直读，不需要登录 stage/生产宿主。

30 天留存窗口现行机制：`push_to_monitoring.sh` 每轮成功上推后，用同一
`MONITORING_DSN` 执行有界删除，删除 `sampled_at` 早于当前时间 30 天的
`lingxi_monitoring.sample` 行，并在 `push.log` 记录 `pruned=N`。删除失败只记日志，
不改变本轮上推结果。既有监控库须重放一次 `monitoring_schema.sql`（或单独执行该
`GRANT`）后收缩才生效，否则 `push_to_monitoring.sh` 每轮记一条删除失败日志但不影响
上推；预发这一步在 S-2-6 由编排者完成并回读最旧样本。本机文件按日切分后的老文件
删除**未做**，仍由后续运维批次接入。

### 4. 监控库两层落地设计与凭据约定

- **两层**：本机文件（源头缓冲，30 天窗口目标）+ 监控库 `lingxi_monitoring`
  schema（远程可读层，样本表 + 每日聚合表 + 巡检记录表，见
  `scripts/ops/monitoring/monitoring_schema.sql`）。样本表 `sample` 用
  `(layer, host, sampled_at, payload JSONB)` 四要素设计，`(layer, host,
  sampled_at)` 唯一约束供上推脚本 `ON CONFLICT DO NOTHING` 做幂等，本机文件
  是源头兜底——上推失败本机文件不受影响，下一轮据 cursor 继续重试。
- **凭据边界**：监控库使用独立最小权限角色 `lingxi_monitoring_app`（只对
  `lingxi_monitoring` schema 有 `SELECT`/`INSERT`，无 `CREATEDB`/`CREATEROLE`/
  `SUPERUSER`），**不复用业务库凭据**；监控数据不含用户消息正文，只有计数、
  耗时、分位数与按内部 `user_id`（不透明 ULID，不是姓名/open_id）的聚合。
- **stage 私有凭据文件新增变量**：与 `deploy/README.md`「数据库凭据源」同一份
  Supabase 私有凭据文件（`/home/wangzhipeng/.config/lingxi/supabase-stage.env`，
  0600，属主为部署用户），新增一行 `MONITORING_DSN=`——**值由编排者线下配**，
  本文档与仓库不出现明文取值。业务库 DSN（供 `db_business_sample.sh` 用）沿用
  该文件已有的 `LINGXI_POSTGRES_DSN`，不需要新增变量。
- **两份 systemd EnvironmentFile 各自只装自己需要的那一个 DSN**
  （`db-business.env` 只有 `LINGXI_POSTGRES_DSN`，`push.env` 只有
  `MONITORING_DSN`）——与 `deploy/README.md`「为什么按服务拆而不是共用一份」
  同一条纪律：凭据只进真正需要它的那个进程环境，不整份共享。

## 九、AI 巡检

> issue #410「AI 巡检机制」：出问题时 AI 读监控库/文件定位；持续优化上每日一次
> AI 巡检——读昨日数据写一条巡检记录（趋势/异常/疑点）入监控库；累计约两周产出
> 代码级优化建议并落 issue。巡检先手动周期跑校准口径，稳定后再定时化——本批只
> 约定格式与落库字段，不交付定时巡检作业本身。

巡检记录写入 `lingxi_monitoring.patrol_record` 表（`monitoring_schema.sql`），
使用同一个 `lingxi_monitoring_app` 凭据。字段与格式约定：

| 字段 | 约定 |
| --- | --- |
| `patrol_date` | 巡检覆盖的自然日（通常是"昨天"，UTC） |
| `reviewed_window_start` / `reviewed_window_end` | 实际读取的样本时间窗口，通常等于 `patrol_date` 当天 00:00–24:00 UTC |
| `findings` | 巡检结论正文，中文，覆盖「趋势」（相比前几日的变化方向）、「异常」（超出正常波动范围的具体指标与数值）、「疑点」（数据本身不足以下结论、需要下一轮继续观察的点）三段；无异常时也应留一句"无异常"，不留空 |
| `anomaly_found` | 是否发现需要人工关注的异常（`true`/`false`），飞书群是否发消息由**其他机制**（本节巡检本身不直接发飞书消息，"飞书群保持安静：巡检无异常不发消息"）决定，本字段只是供后续查询筛选用的标记 |
| `follow_up_issue` | 若巡检结论产出了一个新的 GitHub Issue（issue #410"累计约两周产出代码级优化建议并落 issue"），记录该 issue 的编号或 URL；未产出则留 `NULL`，不要填占位字符串 |
| `created_by` | 固定 `'ai-patrol'`（默认值），区分人工巡检与 AI 巡检 |

写入方式（AI 巡检会话内，`psql`/等价 SQL 客户端，凭据来自监控库 DSN）：

```sql
INSERT INTO lingxi_monitoring.patrol_record
  (patrol_date, reviewed_window_start, reviewed_window_end, findings, anomaly_found, follow_up_issue)
VALUES
  ('2026-08-29', '2026-08-29T00:00:00Z', '2026-08-30T00:00:00Z',
   '趋势：任务量较前日持平；异常：无；疑点：worker-queue 容器内存占用较前日上升约 8%，暂在正常波动范围，下一轮继续观察。',
   FALSE, NULL);
```

飞书群保持安静的既有原则不变：巡检本身不触发飞书消息；真正需要人工介入的异常
仍然只经「八、5. 告警阈值接入」与「一～七」既有两层容器/阈值告警发一句简短
警报，巡检记录只是留痕供 AI 与人回读，不是另一条告警通道。

> 不再是云托管实例。托管平台自带的每日备份、监控面板随之消失，本节把这三样补回宿主侧：

### 1. 本地库容器（`deploy/compose.db.yaml`）

独立于应用编排的第二个 compose 项目（`lingxi-db`），**加入应用栈已有的网络**（应用编排没有
显式 networks，compose 给它建的默认网络叫 `lingxi_default`），应用容器以主机名 `lingxi-db`
连；宿主侧只在回环 `127.0.0.1:5432` 发布端口。值全部来自 `--env-file`，仓库文件里没有任何
一台机器的路径。

| 变量 | 必填 | 缺省 | 含义 |
| --- | --- | --- | --- |
| `LINGXI_DB_ENV_FILE` | 是 | — | 口令文件路径（root 0600，内容只有一行 `POSTGRES_PASSWORD=`） |
| `LINGXI_DB_DATA_DIR` | 是 | — | 数据目录（宿主路径，绑定挂载到容器 `/var/lib/postgresql/data`） |
| `LINGXI_DB_CONTAINER_NAME` | 否 | `lingxi-db` | 容器名；本机演练用别名与真实实例并存 |
| `LINGXI_DB_APP_NETWORK` | 否 | `lingxi_default` | 应用栈网络名（external，本文件不建不删） |
| `LINGXI_DB_HOST_PORT` | 否 | `5432` | 回环发布端口 |
| `LINGXI_DB_MEMORY_LIMIT` / `LINGXI_DB_CPU_LIMIT` | 否 | `768M` / `1.0` | 容器资源上限（主机 3.8 GB，三服务合计限额约 3 GB） |
| `LINGXI_DB_SHM_SIZE` | 否 | `256m` | `/dev/shm`，并行查询用 |
| `LINGXI_DB_SHARED_BUFFERS` / `LINGXI_DB_WORK_MEM` / `LINGXI_DB_MAINTENANCE_WORK_MEM` | 否 | `128MB` / `8MB` / `64MB` | 服务端内存参数 |
| `LINGXI_DB_MAX_CONNECTIONS` | 否 | `100` | 来源 60 是托管档位值（经连接池）；本地直连，三服务空闲栈每键 ≤ 2 + 采样器 + 备份远低于 100 |
| `LINGXI_DB_IDLE_IN_TRANSACTION_TIMEOUT` / `LINGXI_DB_IDLE_SESSION_TIMEOUT` | 否 | `0` / `0`（毫秒） | 来源实读值（Issue #859 评论 5753938437：两项均未设）；迁移只换位置不换行为，收紧另立卡 |
| `LINGXI_DB_STATEMENT_TIMEOUT` / `LINGXI_DB_LOCK_TIMEOUT` | 否 | `120000` / `0`（毫秒） | 来源实读值；应用连接自带 3 s 语句超时、迁移 60 s，服务器级只是兜底 |
| `LINGXI_DB_TIMEZONE` | 否 | `UTC` | 来源实读值 |
| `LINGXI_DB_WAL_LEVEL` | 否 | `replica` | 来源是 `logical`（托管方 realtime 所需）；应用零逻辑复制依赖（断言见 compose 注释），`replica` 更省 WAL |
| `LINGXI_DB_LOG_MIN_DURATION` | 否 | `3000`（毫秒） | 慢语句记入容器日志 |
| `LINGXI_DB_INITDB_ARGS` | 否 | `--encoding=UTF8 --locale=en_US.UTF-8 --locale-provider=icu --icu-locale=en-US --data-checksums` | 来源实读：collate / ctype `en_US.UTF-8`、locale provider ICU、ICU locale `en-US`；只在首次 initdb 生效；切换脚本 `install-pg` 按来源自动派生同形参数 |

```bash
# 1. 文件落位（root 私有目录；compose.env 不含凭据但含路径，一并 0600）
sudo install -d -m 700 -o root -g root /opt/lingxi/db
sudo install -m 644 deploy/compose.db.yaml /opt/lingxi/db/compose.db.yaml
umask 077
sudo install -m 600 -o root -g root /dev/null /opt/lingxi/db/compose.env
sudo install -m 600 -o root -g root /dev/null /opt/lingxi/db/.env.db
sudo install -d -m 700 -o root -g root /var/lib/lingxi/pgdata
# compose.env 至少两行（其余变量按上表按需追加）：
#   LINGXI_DB_ENV_FILE=/opt/lingxi/db/.env.db
#   LINGXI_DB_DATA_DIR=/var/lib/lingxi/pgdata
# .env.db 只有一行 POSTGRES_PASSWORD=<随机口令>（`read -rs` 交互写入，不进 shell 历史）

# 2. 渲染核对（输出含口令，只看不贴）→ 起容器 → healthy 回读
sudo docker compose --env-file /opt/lingxi/db/compose.env -f /opt/lingxi/db/compose.db.yaml config >/dev/null
sudo docker compose --env-file /opt/lingxi/db/compose.env -f /opt/lingxi/db/compose.db.yaml up -d
sudo docker inspect -f '{{.State.Health.Status}}' lingxi-db     # 期望 healthy（首次 initdb 约 10 秒）
sudo docker port lingxi-db                                        # 期望只有 127.0.0.1:5432
sudo docker exec lingxi-db psql -U postgres -d postgres -Atc 'show shared_buffers' -c 'show max_connections' \
  -c 'show idle_in_transaction_session_timeout' -c 'show statement_timeout' -c 'show wal_level' -c 'show data_checksums'
# 期望 locale 五项：UTF8|en_US.UTF-8|en_US.UTF-8|i|en-US（collversion 随本机 ICU 版本，不比对）
sudo docker exec lingxi-db psql -U postgres -d postgres -Atc \
  "select pg_encoding_to_char(encoding)||'|'||datcollate||'|'||datctype||'|'||datlocprovider::text||'|'||datlocale from pg_database where datname='postgres'"
```

已知边界：本地实例上 `postgres` 是超级用户，应用沿用来源库的角色名连库，等于以超级用户身份
运行；收紧为专用低权角色另立工作项。改任何参数 = 改 `compose.env` 后再 `up -d`（容器重建、
数据目录不动）；`compose down` 不带 `-v` 也不会删绑定挂载的数据目录。

### 2. 每日备份单元（`lingxi-db-backup.timer` / `scripts/ops/db_backup.sh`）

RPO 24 小时（D-5）：每日 UTC 18:30（北京 02:30）跑一轮 `pg_dump -Fc`，产物三件成组
（`.dump` / `.dump.sha256` / `.dump.counts.json`），默认保留 14 组，可选传到异机，结果写
状态文件供第 3 小节的巡检读。脚本经 `docker exec` 走容器内工具链，**不持连接串与口令**，对库
只读；产物与状态文件的字段含义见脚本头注。**本单元以 root 运行、不装 `User=` drop-in**：它要
`docker exec` 并往 root 0700 目录写未加密的全量 dump，理由写在单元文件里；批量装 drop-in
时跳过它。

```bash
# 1. 脚本与目录（备份目录 0700 root——dump 不需口令即可还原全部业务数据；状态文件所在
#    目录 0755，巡检以部署用户读它）
sudo install -m 755 scripts/ops/db_backup.sh /opt/lingxi/scripts/db_backup.sh
sudo install -d -m 755 -o root -g root /var/lib/lingxi
sudo install -d -m 700 -o root -g root /var/lib/lingxi/backups

# 2. 单元输入（0600，只放 LINGXI_DB_BACKUP_* 变量；全部有缺省，最小内容可以是空文件）
umask 077
sudo install -m 600 -o root -g root /dev/null /opt/lingxi/monitoring/db-backup.env
#   LINGXI_DB_BACKUP_CONTAINER=lingxi-db
#   LINGXI_DB_BACKUP_DIR=/var/lib/lingxi/backups
#   LINGXI_DB_BACKUP_KEEP=14
#   LINGXI_DB_BACKUP_STATUS_FILE=/var/lib/lingxi/db-backup-status.json
#   LINGXI_DB_BACKUP_TRANSFER=none            # 通了异机通道再改 scp，见第 2.1 小节

# 3. 装单元（仓库单元自带 User=root，不建 drop-in）→ 首轮手动跑一次 → 回读
sudo install -m 644 deploy/monitoring-units/lingxi-db-backup.service \
  deploy/monitoring-units/lingxi-db-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
systemctl cat lingxi-db-backup.service | grep -n '^User='    # 期望 User=root
sudo systemctl enable --now lingxi-db-backup.timer
sudo systemctl start lingxi-db-backup.service                 # 首轮，几秒内结束
systemctl show -p Result -p ExecMainStatus lingxi-db-backup.service   # 期望 Result=success
cat /var/lib/lingxi/db-backup-status.json                      # 期望 "ok":true,"error":null
sudo ls -l /var/lib/lingxi/backups                             # 期望三件一组、0600
systemctl list-timers 'lingxi-db-backup.timer'
```

失败语义：任一步失败都先写状态文件（`"ok":false` + 固定错误码：`container_missing` /
`container_unhealthy` / `backup_dir_invalid` / `disk_space_low` / `already_running` /
`dump_failed` / `checksum_failed` / `restore_list_failed` / `counts_failed` /
`transfer_failed` / `invalid_input` / `unexpected_failure`）再以非 0 退出，`systemctl`
记 `Result=failed`；被 `TimeoutStartSec=1800` 杀掉时来不及写状态，由巡检按「状态文件过旧」
兜底。本地产物在传输失败时**保留**，下一轮照常产出新的一组。

#### 2.1 异机副本（D-10.5：先探 Tailscale 节点间通道，不通则中转）

副本落 `biai-stage`（D-5）。单元以 root 跑，探测与传输用的都是 **root 的** ssh 密钥与
`known_hosts`，探测因此也要以 root 身份做：

```bash
# 只读探测（一次；accept-new 只在首次记录主机指纹，之后 BatchMode 拒绝任何交互）
sudo ssh -o BatchMode=yes -o ConnectTimeout=20 -o StrictHostKeyChecking=accept-new \
  <备份接收账号>@<接收主机 Tailscale 名> true && echo reachable
# 通：远端建目录，再把三行追加进 db-backup.env，下一轮起生效
sudo ssh <备份接收账号>@<接收主机 Tailscale 名> 'install -d -m 700 ~/lingxi-backups'
#   LINGXI_DB_BACKUP_TRANSFER=scp
#   LINGXI_DB_BACKUP_REMOTE=<备份接收账号>@<接收主机 Tailscale 名>:~/lingxi-backups
#   LINGXI_DB_BACKUP_REMOTE_LABEL=biai-stage     # 只进状态文件的短标签，不含地址
# 远端只保存，不自动清理：接收侧按保留份数另行 `ls -1t | tail -n +43 | xargs rm`（14 组 × 3 件）
```

不通：保持 `LINGXI_DB_BACKUP_TRANSFER=none`，由 tz 中转（研发机定时 `scp` 拉取后转投接收主机，
脚本待 W4 实测后补入本节）。状态文件里 `transfer.mode` 会如实写 `none`，巡检不会把它当作
「已到异机」。

#### 2.2 从副本恢复到独立实例（第 3 天演练、RTO 4 小时的兑现方式）

备份是全库 dump，恢复目标须是**新 initdb 形**的 PostgreSQL 17（`public` 在、无其它对象），
且要先预建 dump 里被 `GRANT` 引用的四个 `NOLOGIN` 角色——它们是集群级对象，不在 dump 里：

```bash
# 目标实例（任意 postgres:17 容器，例如演练脚本起的隔离实例）
psql -U postgres -d postgres -c 'CREATE ROLE lingxi_app NOLOGIN' -c 'CREATE ROLE lingxi_scheduler NOLOGIN' \
  -c 'CREATE ROLE lingxi_retention_owner NOLOGIN' -c 'CREATE ROLE lingxi_migrate NOLOGIN'
pg_restore -U postgres -d postgres --no-owner --exit-on-error < lingxi-db-<时间戳>.dump
# 逐表行数与 .counts.json 比对（同一条查询写在 db_backup.sh 第 ⑤ 步），alembic_head 相等
```

`--exit-on-error` 中途失败会留下半成品：重试前 `DROP SCHEMA public CASCADE; CREATE SCHEMA
public; DROP SCHEMA IF EXISTS extensions CASCADE;` 复位，不要在半成品上重跑。演练脚本
`scripts/ops/backup_restore_drill.sh` 的本地库形按此实现。

### 3. 宿主健康巡检的本地库检查项（`host_health_alert.py`，默认关闭）

在既有 `lingxi-host-monitor.service` 的 drop-in 里覆盖 `ExecStart` 追加参数打开，写法与第八节
`--enable-resource-thresholds` 一样（先一行空 `ExecStart=` 清掉再整行重抄，仍以
`/opt/lingxi/bin/python3` 开头）：

```ini
[Service]
ExecStart=
ExecStart=/opt/lingxi/bin/python3 /opt/lingxi/scripts/host_health_alert.py --env-file /opt/lingxi/monitoring/host-monitor.env --enable-resource-thresholds --db-container lingxi-db --db-backup-status-file /var/lib/lingxi/db-backup-status.json --db-backup-max-age-hours 26 --db-connections-alert-percent 80 --db-wal-alert-bytes 2147483648
```

| 参数 | 上方示例值 | 告警键 | 判据 |
| --- | --- | --- | --- |
| `--db-container` | `lingxi-db`（不传即不检查） | `db_container_*`（沿容器判据语义） | 容器不存在 / 未运行 / unhealthy |
| `--db-backup-status-file` | 状态文件路径（不传即不检查） | `db_backup_stale` / `db_backup_failed` / `db_backup_transfer_failed` / `db_backup_unknown` | 状态文件 `finished_at` 超过 `--db-backup-max-age-hours`（示例 26：每日一轮 + 5 分钟随机延迟留余量）；`ok=false`；`transfer.mode=scp` 且 `transfer.ok=false`；文件缺失或不合 schema |
| `--db-connections-alert-percent` | 80 | `db_connections_high` | `pg_stat_activity` 连接数 ÷ `max_connections` 超过百分比 |
| `--db-wal-alert-bytes` | 2147483648（2 GB） | `db_wal_large` | `pg_wal` 目录体量超过阈值；数据目录与应用同盘，WAL 失控要先于磁盘告警被发现 |
| （连接数 / WAL 两项共用） | — | `db_query_unknown` | 只读查询本身失败（容器可达但 psql 报错） |

巡检以部署用户运行：状态文件 0644、所在目录 0755 才读得到；连接数 / WAL 两项经
`docker exec lingxi-db psql` 只读查询，部署用户须在 docker 组（既有容器判据同一前提）。
恢复通知与去重口径与既有告警键相同。
