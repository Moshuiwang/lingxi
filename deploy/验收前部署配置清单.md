# 验收前部署配置清单（Epic D，2026-08-20）

本清单只回答一个问题：**要让首次开通链在一台机器上真的跑起来，需要配齐哪些东西，少配一样会死在哪里。**

它不是第二份部署文档——「怎么执行」在 [deploy/README.md](README.md)，「示例变量长什么样」在 [deploy/.env.example](.env.example)，两者都已经写得很细。本清单补的是那两份文档之间缺的一层：**Epic D 的七道闸（见 [Issue #203](https://github.com/Moshuiwang/lingxi/issues/203) 收口评论）分别绑定哪些配置项、缺哪一项会导致哪一条职责不注册、用户会看到什么**。这一层此前散在十几条 GitHub 评论与源码注释里，验收窗口现场现查曾经花掉半天。

> 七道闸全部开在代码里（`epic/d-first-onboarding`），**不代表任何一台机器上已经生效**。闸能不能打开，完全取决于这台机器的环境变量、卷挂载和随包配置文件是否配齐——这正是本清单要覆盖的内容。

## 一、七道闸逐道要什么

编号与命名对齐 [Issue #203](https://github.com/Moshuiwang/lingxi/issues/203)。每道闸的"依赖"只列**这道闸独有**的配置项；scheduler 启动本身必需的四项基础配置（`LINGXI_POSTGRES_DSN`、`LINGXI_DELEGATED_CREDENTIAL_KEY`、`LINGXI_FEISHU_APP_ID`、`LINGXI_FEISHU_APP_SECRET`）不在每道闸下重复——缺了它们 scheduler 进程根本起不来，属于"部署前置检查"层面的失败，不是本节要说的"进程正常运行、但某条职责悄悄不注册"这一类。

### 闸① 映射内容——「公司+职能→指标名」翻译层

- **依赖**：随包发布的配置文件 `src/lingxi/config/company_function_metric_map.toml`（构建进镜像，不经环境变量），内容需要产品负责人填入真实的公司+职能→指标名对应关系；以及 `LINGXI_MCP_TOKEN_ENCRYPT_KEY`（32 字节 base64 主密钥）——它是每日权限重算职责（唯一读取这份映射文件的职责）的前置，缺了它这份文件根本不会被读。
- **缺了会怎样**：
  - 文件本身缺失或格式非法（不是"内容为空"，是**读不出来**）→ `permission_refresh.duty_not_registered`（`reason=metric_translation_map_unavailable`），每日权限重算职责整体不注册，其余职责照常。
  - 文件能读出来但内容为空（`[companies]` 表存在、没有任何条目——这是**合法内容**，代表产品负责人还没填）→ `permission_refresh` 职责**照常注册**，但每一轮翻译判据 `metric_translation_available()` 恒 `False`，**一条发布/撤权意图都不会排进 outbox**——这一步**不会**留下 `duty_not_registered` 那条审计，只能通过"outbox 一直没有新行"这个负面事实间接判断，非常容易被误读成"一切正常，只是还没人开通"。
  - `LINGXI_MCP_TOKEN_ENCRYPT_KEY` 缺失 → `permission_refresh.duty_not_registered`（`reason=missing_environment_variable`，`variable=LINGXI_MCP_TOKEN_ENCRYPT_KEY`）。
- **用户会看到什么**：闸①本身不直接面向用户；它是闸②的输入（见下）。

### 闸② 发布闸门——onboarding 的 `publish_allowed` 判据

- **依赖**：无独立环境变量。代码固定为 `publish_allowed=lambda: metric_translation_available(metric_translation_map)`，其中 `metric_translation_map` 是 `_build_permission_refresh_duty` **唯一一次**加载的对象（同一个对象转给开通链，不另开一次文件读取）。**这意味着闸②的生效完全由闸①决定**：闸①不满足，闸②必然也不满足。
- **缺了会怎样**：翻译映射为空或不可用时，`AutoOnboardingRunner` 的发布闸拒绝任何一条新的发布/撤权写入；首次开通链在完成身份、权限匹配之后停在这一步。
- **用户会看到什么**：新用户首聊后走到发布环节被挡下，最终收到 `LX-ONBOARD-001`（已转交管理员），**不是**"没有银河权限"这类提示——这是刻意设计（见 `assembly.py` 里 `PublishGateTests` 的说明），因为一个权限完全正常的人不该被引导去银河申请一个他已经有的权限。

### 闸③ 在职状态令牌

- **依赖**：**没有独立环境变量**——它复用 scheduler 启动本就必需的四项基础凭据（凭据密钥、凭据路径、飞书 App ID/Secret），代码层面早已接好（`_build_onboarding_duty(..., employment_access_token=supply)`）。
- **真正的生效前提是一条数据，不是一个环境变量**：凭据卷 `lingxi-{stage,prod}-credentials` 里的加密凭据文件必须已经完成过一次真实授权（即"凭据丢失或过期的保底"一节里的 `reauthorize` 一次性 job 已经成功跑过一遍），持有一条有效的 `refresh_token`。**全新部署、从未做过初次授权时，这个文件不存在或为空。**
- **缺了会怎样**：这不会让 `onboarding` 职责在启动期判 `duty_not_registered`（职责本身照常注册），而是**每一次**运行期尝试取在职状态派生令牌都会失败，`OnboardingRunner` 按 `employment_read_failed_*` / `delegated_subject_read_failed_*` 一类原因收口为本侧故障（内部错误，会重试，不是"用户无权限"）。这类失败**逐个用户发生**，比"进程没起来"更难从整体健康检查里看出来，容易被误判成"个别用户的偶发问题"而不是"这台机器压根没做过初次授权"。
- **用户会看到什么**：技术失败提示（转人工），不是无权限提示。

### 闸④ 组织快照写入方——`org_snapshot_sync` 职责

- **依赖**：**没有独立环境变量**。复用两条既有令牌供给：用户身份路径复用闸③同一条 `supply`（一次性 `refresh_token` 派生），应用身份路径复用权限发布表那条 `permission_table_access_token`（tenant_access_token，由飞书 App ID/Secret 换取，不是一次性凭据）。两条供给在正式装配路径（`build_loop`）里**总能**建出来，不会是 `None`。
- **缺了会怎样**（正式路径不会触发，仅非默认调用方场景）：两条供给缺任一条 → `org_snapshot_sync.duty_not_registered`（`reason` 分 `user_access_token_unwired` / `app_access_token_unwired`）。**这道闸真正会在生产触发的失败点是运行期**：供给存在但飞书侧拒绝、或组织快照批次完整性校验不通过（两条身份路径看到的成员集合不一致等）时，职责**仍然注册**，但不置位当日完成水位，`run_once` 记 `org_snapshot_sync.read_failed`，下一轮重试。
- **少这道闸会怎样**（历史事实，2026-08-19 实测发现）：四张 `feishu_org_*` 快照表长期为空，首次开通链第一步「组织快照定位身份」查不到任何人——**即使闸①②都已开着**，所有用户的开通都会在第一步就落 `LX-ONBOARD-001`，这一步失败得早，容易被误判成花名册或权限问题。

### 闸⑤ scheduler 挂载用户环境卷（首次开通编排的写侧）

- **依赖**：三个环境变量缺一不可——`LINGXI_MCP_TOKEN_ENCRYPT_KEY`、`LINGXI_QUERY_MCP_ENDPOINT`（须以 `https://` 开头，否则启动期直接拒绝）、`LINGXI_USER_ENV_ROOT`（须是绝对且规范化路径，通常 `/var/lib/lingxi/users`）；以及 compose 层面 **scheduler 容器要挂载 `lingxi-users` 卷到 `/var/lib/lingxi/users`，且必须可写**（不能是 `:ro`）。
- **缺了会怎样**：
  - 三个环境变量缺任一个 → `onboarding.duty_not_registered`（`reason=missing_environment_variable`）。
  - 三个变量都配了，但卷没挂、或挂载路径对不上、或挂成只读 → `LocalUserEnvironment.sweep_all()`（启动期全量清扫，用于兜掉 `SIGKILL` 留下的明文令牌临时文件）会在真实容器里第一次访问该目录时抛 `UserEnvironmentError`（常见形态 `root_parent_ENOENT`：根目录的父目录都不存在），装配层据此判定「前置不齐」→ `onboarding.duty_not_registered`（`reason=user_environment_sweep_failed`，`code=<errno 符号名>`）。**这个失败只留一条容易被忽略的审计日志，容器健康检查照常通过，表面上"scheduler 工作正常"**。
- **用户会看到什么**：与闸②同一个终态——`LX-ONBOARD-001`（首聊事件原样留在库里，等配置齐了再跑，不会丢）。

### 闸⑥ worker 按用户读取问数 MCP 配置（首次开通编排的读侧）

- **依赖**：`LINGXI_USER_ENV_ROOT`——**与闸⑤是同一个裸变量名**（不带 `LINGXI_WORKER_` 前缀），必须指向**同一个挂载点**；以及 `worker-queue` 容器要挂载 `lingxi-users` 卷到 `/var/lib/lingxi/users`（只读即可，`worker-queue` 从不往这个目录写东西）。
- **缺了会怎样**：`worker-queue` 是**启动期预检**，不是运行期才发现：
  - `LINGXI_USER_ENV_ROOT` 未设置 → 日志 `worker.queue.config.invalid`（message: 队列 worker 缺少 `LINGXI_USER_ENV_ROOT`），`exit=3`。
  - 变量设了但目录打不开（卷没挂、路径写错、权限不对）→ 日志 `worker.queue.user_env_root.unavailable`（`reason=open_failed`），`exit=3`。
  - `worker-queue` 是 `restart: unless-stopped`——上面任一种情况都会让它**无限崩溃重启**，而不是"起来了但处理不了任务"。
  - 若这道预检本身有缺口（未来被绕过或移除），退化行为是**每领一个任务失败一次**（`load_user_mcp_servers` 报 `root_ENOENT` 一类错误码），运维要靠"每个任务都失败"反推"卷没挂对"——这正是当前预检要提前暴露的那类失败。
- **红线**：读不到用户自己的 `.mcp.json` 时必须失败关闭，**绝不回退到任何全进程共用的配置**——那等于用别人的令牌去查别人的数据，是越权返回数据。这条由结构约束保证（`adapters/user_mcp_config.py` 没有默认值、没有回退分支），不是运行期判断。
- **用户会看到什么**：若预检没拦住（正常情况下会被拦住并阻止启动）而是运行期才暴露，具体某个用户的问数任务会失败关闭，不会把结果发错人。

### 闸⑦ 就绪探针读得懂真实 MCP 返回

- **依赖**：代码层面已固定注入已验证的 `content_text_metrics_reader`（`assembly.py` 三处），**没有对应的环境变量**——这道闸不需要额外配置就"开着"。它真正依赖的是 `LINGXI_QUERY_MCP_ENDPOINT` 与 `LINGXI_QUERY_MCP_TIMEOUT_SECONDS`（后者可选，默认值见 `mcp_readiness.py`）**已经配置**，探针才会真的发生。
- **缺了会怎样**：`LINGXI_QUERY_MCP_ENDPOINT` 未配 → `permission_readiness.probe_not_wired`（探针那一面不装配，撤权通知与权限发布照常运行）——**就绪确认永远不会推进**，已发布的授权停在"等确认"，用户永远收不到"开通完成"，但也不会误判失败（进度原样留着，端点配好后从库里继续）。
- **历史教训（2026-08-19 才被发现，此前不在任何清单上）**：这道闸此前**从未被真实调用验证过**——真实 `list_metrics` 返回把指标塞在 `result.content[0].text` 的一段 JSON 字符串里，而不是默认 reader 唯一认的 `result.structuredContent`。不修的后果是**每个用户必然**走满 15 分钟同步超时、永远拿不到「开通完成」（不是偶发）。全部单元测试在注入的假传输层上跑，断言全绿——**只有真实调用能暴露**，这是本仓库"组件在库、从未真实调用过"这一高危形态的又一次真实案例，登记它是为了提醒：**闸门存在于代码 ≠ 真实协议面已验证**，后续任何一处依赖真实第三方响应形状的代码改动，都值得在 stage 上补一次只读真实调用，而不是只信单元测试全绿。

## 二、按进程分组：必需与可选

完整变量清单与逐条形状说明见 [deploy/.env.example](.env.example)（七个文件，按服务分文件，不入库）；这里只标出**哪些是必需、哪些是可选、可选的缺了对应哪道闸**。

| 进程 | 必需 | 可选（缺了的后果见上一节对应闸） |
| --- | --- | --- |
| `scheduler` | `LINGXI_POSTGRES_DSN`、`LINGXI_DELEGATED_CREDENTIAL_KEY`、`LINGXI_DELEGATED_CREDENTIAL_PATH`（固定为凭据卷内路径，compose 已写死）、`LINGXI_FEISHU_APP_ID`、`LINGXI_FEISHU_APP_SECRET` | `LINGXI_ADMIN_GROUP_CHAT_ID` + `LINGXI_ROSTER_BITABLE_APP_TOKEN` + `LINGXI_ROSTER_BITABLE_TABLE_ID`（花名册审计日报，与七道闸无关，独立可选）；`LINGXI_MCP_TOKEN_ENCRYPT_KEY`（闸①②⑤）；`LINGXI_PERMISSION_BITABLE_APP_TOKEN` + `LINGXI_PERMISSION_BITABLE_TABLE_ID`（权限发布"发布面"，与就绪/通知面独立）；`LINGXI_QUERY_MCP_ENDPOINT` + `LINGXI_QUERY_MCP_TIMEOUT_SECONDS`（闸⑤⑦）；`LINGXI_USER_ENV_ROOT`（闸⑤，须指向已挂载的持久卷路径）；`LINGXI_ONBOARDING_WORKERS`（开通并发线程数，默认 8，与闸门开关无关，只影响吞吐） |
| `gateway` | `LINGXI_GATEWAY_APP_ID`、`LINGXI_GATEWAY_APP_SECRET`、`LINGXI_GATEWAY_POSTGRES_DSN` | 告警装配、重连退避、卡片故障注入开关（受控验收专用）——均与七道闸无关 |
| `worker`（一次性 `turn` job） | `LINGXI_WORKER_QUESTION`、`LINGXI_WORKER_READONLY_TOOL` | 其余 `LINGXI_WORKER_*` 与模型端点凭据；**不涉及七道闸**（`turn` 模式不处理真实用户任务） |
| `worker-queue`（常驻，`mvp` profile） | `LINGXI_POSTGRES_DSN`、`LINGXI_USER_ENV_ROOT`（闸⑥，缺任一个 `exit=3`） | `LINGXI_WORKER_SESSION_ROOT`（留空使用默认推导更安全，见「已知坑」）、并发/心跳等调参项 |
| `migrate` | `LINGXI_MIGRATION_DSN` | 无 |
| `reauthorize`（一次性，`job` profile） | `LINGXI_POSTGRES_DSN`、`LINGXI_DELEGATED_CREDENTIAL_KEY`、`LINGXI_FEISHU_APP_ID/SECRET/BASE_URL/REDIRECT_URI/AUTHORIZATION_ENDPOINT/SCOPE`、`LINGXI_OAUTH_BRIDGE_URL`、`LINGXI_OAUTH_BRIDGE_TOKEN` | `LINGXI_OAUTH_BRIDGE_WAIT_SECONDS`、`LINGXI_DELEGATED_REAUTH_STATE_KEY`、`LINGXI_DELEGATED_SUBJECT_OPEN_ID` |

**七道闸只涉及 `scheduler` 与 `worker-queue` 两个进程。** `gateway`、`worker`（一次性）、`migrate`、`reauthorize` 的配置完整与否不影响闸门开关，但它们各自的必需项缺失同样会让对应进程起不来或崩溃重启，一并列在这里防止漏配。

## 三、前置资源（带外交付项）

**只写变量名与来源形态，不写任何真实值、坐标或主机名。**

### 两个持久卷

| 卷（stage / 生产） | 挂载点 | 与七道闸的关系 |
| --- | --- | --- |
| `lingxi-{stage,prod}-credentials` | `/var/lib/lingxi/credentials` | 闸③真正生效的前提——里面的加密凭据文件必须已完成过一次初次授权 |
| `lingxi-{stage,prod}-users` | `/var/lib/lingxi/users` | 闸⑤（scheduler 读写）与闸⑥（worker-queue 只读）共用同一个卷、同一个路径 |

两个卷的完整说明（备份周期、恢复策略、为什么必须是两个卷而不是一个）见 [deploy/README.md「两个持久卷」](README.md#两个持久卷)。

### 测试库迁移版本

数据库结构由 `migrate` job 跑 `alembic upgrade head` 建立（compose 的 `ENTRYPOINT` 默认 `upgrade head`，不需要手写版本号）。**本清单成文时 `epic/d-first-onboarding` 的 alembic head 是 `0065_mcp_token_and_sync_check`**——它是七道闸相关的两张表（`mcp_sync_check`、权限发布 outbox 的收尾字段）落地的那次迁移，早于它的库结构会让权限重算/发布相关职责在真库操作阶段直接报表不存在，而不是本清单描述的"职责不注册"这一类静默失败。验收前用 `docker compose ... --profile job run --rm migrate current` 核对当前库版本，与镜像内置的迁移集合是否一致；不一致时先跑 `migrate`（不带参数即 `upgrade head`），再启动常驻服务。

### 随包发布的映射文件

两份都打进镜像（`pyproject.toml` 的 `[tool.setuptools.package-data]` 声明 `lingxi.config` 下的 `*.toml` 随包发布），**不经环境变量**，因此"配置是否齐备"要靠**镜像里带的是哪个版本**而不是查某个环境变量：

- `src/lingxi/config/company_function_metric_map.toml`——闸①的核心内容，需要产品负责人提供公司+职能→指标名的对应关系；空表是合法状态但等于闸①对所有人关闭。
- `src/lingxi/config/galaxy_role_function_map.toml`——角色→职能标签映射，随包固定，权限重算与首次开通编排都读它；读不出来两条职责都不注册（`role_function_map_unavailable`）。

**验收前确认方法**：这两份文件的内容随镜像 tag 冻结，验收时应确认冻结候选镜像内置的映射文件内容与产品负责人最新拍板的版本一致（例如从候选镜像里 `docker run --rm <镜像> cat /opt/.../company_function_metric_map.toml` 之类的只读回读，而不是假设"代码里有这份文件就等于内容是对的"）。

### 主密钥一类的带外交付项

以下变量的值**只能带外交付**（一次性生成后经受控渠道交给部署方，不进任何版本控制、不进 Issue/PR 正文），此处只登记名字与来源形态：

| 变量 | 来源形态 |
| --- | --- |
| `LINGXI_DELEGATED_CREDENTIAL_KEY` | 一次性生成的 Fernet 密钥（44 字符 base64），加密专用授权凭据用 |
| `LINGXI_MCP_TOKEN_ENCRYPT_KEY` | 32 字节 base64 主密钥，与问数 MCP 侧同一把（Issue #159 交付时约定） |
| `LINGXI_FEISHU_APP_ID` / `LINGXI_FEISHU_APP_SECRET` | 飞书自建应用（"四达文档会议助手"）凭据，飞书开发者后台颁发 |
| `LINGXI_GHCR_READ_TOKEN` / `LINGXI_GHCR_READ_USER` | 部署机的 GHCR 只读拉取身份（GitHub App 或组织级 `read:packages` 令牌），来源为 stage `[ops]` Issue；**不得使用任何个人 GitHub 凭据**，也不得复用 CI 的 `GITHUB_TOKEN`（见 [deploy/README.md「主机读取身份」](README.md#2-主机读取身份p1-4)） |
| `LINGXI_OAUTH_BRIDGE_URL` / `LINGXI_OAUTH_BRIDGE_TOKEN` | 仅 `reauthorize` 一次性 job 使用，一次性正式重授权用的受控 OAuth Bridge 地址与令牌 |
| （数据）专用授权主体首次授权 | **不是环境变量**，是数据库里 `feishu_delegated_subject` 表的一行登记 + 凭据卷里的一份已授权凭据文件——由 `reauthorize` job 成功跑过一次产生。闸③依赖这条数据，见「一、闸③」 |

## 四、自检方法：配完之后怎么确认真的生效

**「日志没报错」不构成证据**——这是本仓库吃过亏的地方（Issue #203：闸⑦此前跑在注入的假传输层上，全部单元断言都绿，只有真实调用才暴露必然失败）。下面按"能看什么、能证明什么、不能证明什么"分层，不接受"没报错就算过"这一类结论。

### 第一层：进程起没起来（能证明"必需配置齐了"，不能证明任何一道闸开着）

```bash
docker compose --env-file deploy/.env.stage -f deploy/compose.yaml -f deploy/compose.stage.yaml ps
docker compose --env-file deploy/.env.stage -f deploy/compose.yaml -f deploy/compose.stage.yaml logs scheduler --tail 50
```

`healthcheck` 通过只证明两件事：数据库可达、主循环活性文件仍在更新（见 [deploy/README.md「健康检查」](README.md#健康检查不开放端口docker-exec-语义)）。**七道闸任何一道开没开，健康检查一律不知道**——一个七道闸全灭的 scheduler 照样能常年 healthy。

### 第二层：`duty_not_registered` 审计族（能证明"哪些职责在启动期就被挡住了，缺了什么"）

启动后立刻查一次，**期望结果是零命中**：

```bash
docker compose ... logs scheduler | grep -E '(roster_audit|permission_refresh|onboarding|org_snapshot_sync|permission_publish)\.duty_not_registered'
```

命中任何一条，日志的结构化字段会给出 `reason`（多数是 `missing_environment_variable`，附 `variable` 字段——只报变量名，不回显值）；对照本清单「一、七道闸逐道要什么」定位是哪一道闸。**这条只覆盖启动期就能判定的前置缺失**，覆盖不到：

- 闸①"映射内容为空但文件本身合法"——不产生 `duty_not_registered`，职责正常注册，只能靠"outbox 一直没有新行"这个负面事实间接判断（见第三层）。
- 闸③"没做过初次授权"——不产生 `duty_not_registered`，职责正常注册，运行期逐个用户失败。
- 闸⑤"权限发布面装不起来但就绪/通知面还在"——产生的是 `permission_publish.publish_not_wired`（**不是** `duty_not_registered`），因为这条职责设计成"发布面"与"就绪确认+通知面"各自独立装配，见 `assembly.py` 文档。

同理查 `permission_readiness`（闸⑤⑦相关）：

```bash
docker compose ... logs scheduler | grep -E 'permission_readiness\.(not_wired|probe_not_wired)'
```

### 第三层：真实业务事实（唯一能证明"闸真的在发挥作用，不只是没被拦住"的层级）

- **闸①②的真实证据**：`permission_publish_outbox` 表出现了新行，且状态从 `pending` 推进到 `published`（不是只看"进程没报错"）。没有真实用户触发权限重算/首次开通之前，这张表**本来就是空的**，"表是空的"本身不能区分"闸关着"和"还没有人触发"。
- **闸④的真实证据**：`feishu_org_sync_run` 记录了当日一次 `status=complete` 的批次，四张 `feishu_org_*` 表非空。
- **闸⑤⑥的真实证据**：`<LINGXI_USER_ENV_ROOT>/<user_id>/.mcp.json` 确实为某个真实开通过的用户存在（scheduler 写、worker-queue 读，两边看到同一份文件）。
- **闸⑦的真实证据**：一次真实 `list_metrics` 调用（哪怕是只读探测，不必等真实用户触发）返回的形状被 `content_text_metrics_reader` 正确解析——2026-08-19 的实测记录见 [docs/参考证据/问数MCP-list_metrics真实响应形状.md](../docs/参考证据/问数MCP-list_metrics真实响应形状.md)，任何协议面变化都应该重新做一次这类只读实测，而不是信任单元测试。

**没有真实开通旅程跑过一次，本节第三层拿不到任何证据**——这与"七道闸已开"是两件事：闸开只保证"配置层面不会挡住"，不保证"真的有一条旅程走通过"。

### 第四层：`worker-queue` 专用（崩溃循环往往比业务失败更容易被忽略）

```bash
docker compose ... logs worker-queue --tail 50 | grep -E 'worker\.queue\.(config\.invalid|user_env_root\.unavailable)'
```

`restart: unless-stopped` 会让崩溃循环持续产生"容器在运行"的假象（`docker compose ps` 显示 `Restarting` 或短暂 `Up` 后又消失）；只看 `ps` 的 `STATUS` 列容易漏掉"起来几秒又崩了"，一定要看重启次数（`docker inspect` 的 `RestartCount`）或直接看日志里这两条消息是否反复出现。

### 第五层：静态契约检查（能证明"配置文件/编排文件形状对"，不能证明"运行时真的生效"）

```bash
python3 scripts/ci/check_deploy_contract.py
```

新增的检查见下一节「六、本次改动」，覆盖闸⑤的卷挂载精确性（挂成 `:ro` 会变红）、闸⑥的 `worker-queue` 必需变量示范、以及本次新增的闸门配置项文档覆盖度检查。**这层只跑在 compose 与 `.env.example` 的源文件文本上，不连接任何真实数据库或飞书**——它能拦住"编排文件写错了"，拦不住"环境变量在真机上确实没配"，两者要分开验证。

## 五、已知会踩的坑

以下每一条都能在源码或既有文档里核实到出处，不是猜测：

1. **scheduler 的 `lingxi-users` 卷挂成 `:ro`**：首次开通编排要往这个目录写每个用户的 `.mcp.json`，只读挂载会让每一次开通都在**第一次写入时**才失败——表现形式与"完全没挂载"相同（`onboarding.duty_not_registered`，其余职责与健康检查照常正常）。`scripts/ci/check_deploy_contract.py::check_scheduler_user_volume` 已经把这条变成会变红的检查（精确解析 `volumes:` 列表，不是子串包含判断——早期版本这里有过一个假绿口子，见该函数文档字符串）。
2. **`LINGXI_USER_ENV_ROOT` 指向的路径，父目录不存在**：`LocalUserEnvironment.sweep_all()` 会抛 `root_parent_ENOENT`，装配层据此判定「前置不齐」，首次开通编排永不注册。**这个目录由 scheduler 独占创建**（`worker`/`worker-queue` 只读，不会自己 `mkdir`）——如果连父目录都不存在，说明卷根本没挂对，不是"scheduler 第一次运行时会自动建好"。
3. **`worker` 与 `worker-queue` 共用同一个 env 文件**：要么 `worker` 意外拿到数据库/飞书凭据（经 Agent SDK 继承给 Claude CLI 与每个 MCP 子进程，凭据因此流进模型执行环境），要么 `worker-queue` 拿不到 `LINGXI_POSTGRES_DSN` 而无限崩溃重启。`check_compose_contract` 里的 env_file 去重检查已经挡住"两个服务共用同一个 env_file"这件事，没有例外。
4. **`LINGXI_QUERY_MCP_ENDPOINT` 误配成 `http://`**：scheduler 启动期直接拒绝（`SchedulerConfig.from_env` 校验），不会带着这个配置跑起来再出问题——这是刻意的快速失败，为的是不让用户自己的 MCP 令牌明文上路。
5. **`LINGXI_WORKER_SESSION_ROOT` 填了一个不存在的路径**：Agent 会话 JSONL 物理清理会静默判定"本轮无文件可删"并把数据库那一侧标记为已完成，**事后改对配置也补不回来**（清理记录已经落库）。留空使用默认推导（`$HOME/.claude/projects`，镜像固定 `HOME=/tmp`）是更安全的选择——这条在 [deploy/.env.example](.env.example) 的「文件五」小节已有详细说明，这里再提醒一次是因为它的后果不可逆。
6. **`LINGXI_ROSTER_SNAPSHOT_STALE_AFTER_HOURS` 配置成一个很大的数**：等于把花名册超龄告警关掉，但配置本身看起来仍然合法（校验只挡 0~8760 小时的范围，不判断"是不是大到没意义"）——这条不属于七道闸，但同样是"配置存在 ≠ 配置有效"的一个例子。
7. **GHCR 镜像默认私有**：宿主机不登录就拉不下来，`docker compose up` 会停在 `failed to authorize ... 403 Forbidden`（[deploy/README.md](README.md) 记录为"本批实测过这个报错"）；必须先用 stage `[ops]` Issue 供给的只读拉取身份 `docker login`。
8. **`--env-file` 忘记传**：`env_file:` 只把变量注入容器，不参与 compose 文件自身的 `${VAR:?}` 插值；省掉它 compose 会直接报 `LINGXI_IMAGE_REGISTRY` 未设并退出——这不是七道闸相关的坑，但足够常见，值得放在这里一并提醒。
9. **闸①"内容为空"与"文件损坏/找不到"是两种不同的失败，容易混着排查**：前者职责照常注册、健康检查照常绿、`duty_not_registered` 不会出现，只能靠"outbox 一直没有新行"这个负面事实间接判断；后者会留下明确的 `duty_not_registered` 审计。**验收前如果只看"有没有报错"，两种情况看起来一样，但排查方向完全不同**（前者去找产品负责人要映射内容，后者去检查镜像里的文件本身）。
10. **闸③"代码接好了" ≠ "这台机器能用"**：`employment_access_token=supply` 是代码层面的接线，真正决定它能不能取到令牌的是凭据卷里那份文件有没有做过初次授权——一台从未跑过 `reauthorize` 的全新机器，闸③在配置检查层面"全绿"，但每一次开通请求在运行期都会因为拿不到令牌而失败,这类失败**不产生 `duty_not_registered`**，容易被误判成个别用户问题而不是"这台机器还没做过初次授权"。
