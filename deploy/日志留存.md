# 容器日志留存（Issue #343 / Trace #373 H2，S-H2-2）

## 背景

重部署会把旧容器换成新容器，Docker `json-file` 日志驱动的日志跟着旧容器一起消失
——**这不是"日志被清理"，而是"新容器从来没有旧容器的日志"**。2026-08-27 调查
产品负责人 08-26 04:09Z 的真实会话时，`lingxi-worker-queue-1` 已因当日重部署轮转丢
原始日志，只能靠 `innertest_content_capture` 数据库字段等效还原；这条等效来源只在
内测轮开启，硬切后会关闭，同类取证到时将没有等效来源（[#343](https://github.com/Moshuiwang/lingxi/issues/343)）。

产品要求的取证窗口是 **30 天**（≤90 天合规上限）。裁定不引入重型日志栈，方案是
两层组合：

1. **compose 的 `json-file` 驱动内上限提高**（`deploy/compose.yaml`，当前
   `max-size: 50m` / `max-file: 5`，即单服务最多 250MB）——这是容器存活期间的
   第一层缓冲，不解决跨重部署丢失，只是给下面的收集脚本留够窗口，不让还没被
   收集走的部分先被 Docker 自己的轮转吞掉。
2. **宿主侧持久收集**（本文档）——独立于容器生命周期，重部署替换容器不影响
   已经收集到宿主机的部分，这才是真正跨重部署持久的那一份。

## 组成

| 产物 | 作用 |
| --- | --- |
| `deploy/collect-container-logs.sh` | 增量收集脚本：把各 lingxi 容器当前的 stdout/stderr 追加到宿主机持久目录 |
| `deploy/lingxi-container-logs.logrotate` | logrotate 配置：30 天窗口，总量硬封顶 ≤2GB |

## 安全边界

`deploy/collect-container-logs.sh` 只读容器的 stdout/stderr（`docker logs`），
**绝不**执行会吐出容器完整配置的命令（裸 `docker inspect`）——那类命令的输出含
`Config.Env`，而 `scheduler`/`gateway`/`worker-queue` 的环境变量正好装着数据库
连接串、Fernet 密钥与飞书应用密钥（产品合同：凭据不得进入日志或任何用户交付
物）。脚本内唯一的 `docker container inspect` 调用把 `--format` 锁定为只取容器
ID，判断容器是否存在，不取任何配置字段。收集到的文件本身与容器 stdout 内容
完全一致，**不额外过滤业务正文**——业务代码本身对日志的凭据边界负责（架构设计
「横切约定」：进程只往 stdout/stderr 写结构化输出，不写凭据明文），本收集脚本
不重复也不替代那层判断，只负责"别用收集手段自己开一个新的凭据泄露口子"。

## 安装（stage 由编排者执行，本卡只交付仓库产物）

在部署主机（例如 `biai-stage`）上：

```bash
# 1. 建持久日志目录（脚本自己也会 mkdir -p，这里显式建是为了先设好属主）
sudo install -d -m 750 -o "$(id -un)" -g "$(id -gn)" /var/log/lingxi

# 2. 手动跑一次，确认脚本能找到当前容器、正常收集
cd /path/to/lingxi   # 仓库 checkout 路径
bash deploy/collect-container-logs.sh
ls -la /var/log/lingxi

# 3. 安装 logrotate 配置——**刻意不放进 /etc/logrotate.d/**（独立审查 P1-3，
#    见下方「cron 安装」的说明），改放一个系统 logrotate 不会自动扫描的路径：
sudo install -d -m 755 /etc/lingxi/logrotate.d
sudo cp deploy/lingxi-container-logs.logrotate /etc/lingxi/logrotate.d/lingxi-container-logs

# 4. 验证 logrotate 配置本身没有语法错误（-d 是纯调试预演，不会真的轮转；
#    --state 用与下面 cron 相同的路径，预演也不应该动系统默认状态文件）
sudo logrotate -d --state /var/log/lingxi/.state/logrotate.state \
  /etc/lingxi/logrotate.d/lingxi-container-logs
```

### cron 安装

**配置文件不落 `/etc/logrotate.d/`，只由下面这一条 cron 触发轮转**（独立审查
P1-3；本节修订前的版本曾建议把配置放进 `/etc/logrotate.d/` 并额外加一条自建
cron、声称"两者用同一个 `--state` 文件，不会冲突"——这个说法是错的：多数发行版
通过 `/etc/cron.daily/logrotate` 每天扫描 `/etc/logrotate.d/*` 时，用的是系统级
默认状态文件 `/var/lib/logrotate/status`，**不是**下面这条自建 cron 显式传入的
`--state /var/log/lingxi/.state/logrotate.state`——两个 state 文件互不相干，各自
独立记账"这个日志文件今天转过没有"，于是同一天里系统 daily 任务转一次、自建
cron 又转一次，一天实际转两次，30 天的窗口因此被悄悄减半，直到某一天 `rotate
30` 的名额被提前耗尽。改成配置文件放在非系统扫描路径之后，系统的
`/etc/cron.daily/logrotate` 根本看不到这份配置，只有本节这一条 cron 会触发它：

```cron
# 收集脚本：每 5 分钟增量收集一次，缩小"重部署丢失窗口"到分钟级
*/5 * * * * cd /path/to/lingxi && bash deploy/collect-container-logs.sh >> /var/log/lingxi/.collect.cron.log 2>&1

# logrotate：每小时检查一次是否需要轮转（daily + maxsize 组合，见下方「已知
# 限制」——是否真的轮转仍由 logrotate 自己按 daily/maxsize 判定，这条 cron 只
# 负责"多久检查一次"）。与上面一行同一份用户 crontab（`crontab -e` 安装，不是
# /etc/crontab 或 /etc/cron.d/ 那种带 user 字段的系统 crontab 格式，两条统一
# 用同一种格式，运行账户与收集脚本相同，需要能读写 /var/log/lingxi）。
0 * * * * /usr/sbin/logrotate --state /var/log/lingxi/.state/logrotate.state /etc/lingxi/logrotate.d/lingxi-container-logs
```

`*/5 * * * *` 的收集频率与"重部署前先手动 flush 一次"（见下）配合：日常靠 cron
保持缺口在 5 分钟级，真正重部署前再手动补一次，把缺口收紧到"从上一次 cron 触发
到这一刻"这个更小的窗口。

## 重部署前置步骤：手动 flush 一次

`deploy/README.md`「安装与升级」一节的 `up -d` 之前，**先手动跑一次收集脚本**：

```bash
bash deploy/collect-container-logs.sh
```

原因：cron 的收集间隔（建议 5 分钟）意味着重部署发生的那一刻，容器最近这几分钟
的日志可能还没被收集走；`up -d` 会用新容器替换旧容器，旧容器一旦被替换，这几
分钟的日志就真的没了（不是"要等下次 cron 才能拿到"，是"永远拿不到了"）。重部署
前手动 flush 一次，把这个窗口从"最长一个 cron 周期"收紧到"从上一次 cron 触发到
现在"，两者叠加后正常情况下丢失窗口是秒级到分钟级，不是完整周期。

## 已知限制

- **30 天是正常日志量下的预期窗口，不是 logrotate 硬保证的天数**：
  `lingxi-container-logs.logrotate` 用 `maxsize 10M` + `daily` + `rotate 30`
  组合——正常情况下每天轮转一次，30 次轮转对应 30 天；但如果某个服务某一天日志
  暴涨超过 10MB，`maxsize` 会让它提前轮转，可能在同一天内消耗多个 `rotate`
  名额，那一段时期的实际保留天数会短于 30 天。这是**为保总量上限 ≤2GB 刻意接受
  的权衡**：总量上限是硬约束（stage 磁盘紧张），保留天数在极端日志量下退化是
  可接受的代价，不是本轮要修的缺陷。
- **`maxsize` 的判定粒度＝自建 cron 的调用周期，不是连续监控**：logrotate 不是
  常驻进程，只有在被调用的那一刻才会检查"这个文件是否已经超过 `maxsize`"；上面
  「cron 安装」给的示例是每小时调用一次，因此某个服务的日志即使在某一小时内瞬间
  暴涨超过 10M，也要等到下一次整点调用才会被发现并提前轮转，这一小时内它仍然会
  继续增长（超出预算的部分计入下一轮核算前的临时超额，不是被拦住）。调高检查频率
  能缩小这个粒度，但改变不了"两次调用之间必然存在一个检查不到的窗口"这条限制；
  这与 30 天窗口在极端日志量下退化是同一类"为简单机制接受的粒度代价"，不是缺陷。
- **总量上限 ≤2GB 的核算不依赖压缩收益**：`compress`/`delaycompress` 打开后实际
  占用通常远小于 2GB（结构化日志压缩比常见在 10x 左右），但预算核算本身按"压缩
  完全不起作用"的最坏情况计算（6 服务 × 10M × 30 = 1800MB），确保即使压缩失效
  这条硬上限依然成立。
- **一次性 job 容器（`worker`/`migrate`/`reauthorize`）的收集时机受限于容器存活
  窗口**：这三个服务用 `docker compose run --rm` 启动，跑完即被移除；收集脚本
  只能在容器仍存在时收集到它的日志。如果一次性 job 从启动到被移除的时间短于
  两次 cron 触发之间的间隔，它的日志可能完全来不及被本脚本收集到（json-file
  驱动内的原始日志本身也随容器移除而消失，不是"漏收集"独有的问题）。如需保证
  一次性 job 的日志一定被收集，运维应在触发这些 job 前后各手动跑一次收集脚本
  （与"重部署前先手动 flush 一次"同一姿势）。
- **stage 的真实安装、cron 生效、跨重部署验证均未执行**——本卡只交付仓库产物
  （脚本 + logrotate 配置 + 本文档），stage 上的安装由编排者在部署时执行，是
  L4a 待验证项，不在本卡范围内。
