# 权限发布表预发防护

## 目的与风险

预发与生产共用同一张真实权限发布表，也共用同一个问数服务。表名本身没有环境列、版本列或预发标记，七个单行文本字段中的 `record_key` 与 `email` 共同回答「这一行是谁的」。权限发布批和首次开通在预发运行时，可能按同一个 `record_key` 更新生产用户的既有行，也可能给生产表中尚不存在的人新建一行。新建行还会写入 `token_cipher`；如果这份预发密文后来被生产首聊当作存量令牌沿用，解密失败就会停住开通。因此预发升级的硬前提不是“服务能启动”，而是能够证明：写表前留有完整备份、每个写入行都能被识别、必要时可以把一整批改动撤回。

本文件说明宿主侧 `deploy/permission_table_guard.py` 的边界。本卡只做离线测试，不连接真实飞书表格或数据库；删除接口也未在真实表验证。预发演示前须按末尾清单确认。

## “行可识别”的定义

本守卫不向正式表增加环境列，也不把邮箱当作撤回授权。可撤回范围唯一来自预发库 `publish_outbox` 的发布台账：

```text
status = 'published'
published_at >= backup.taken_at
external_record_id = 飞书权限表实际被操作的 record_id
```

`payload->>'record_key'` 优先作为台账展示用的键；如果 payload 已因九十天保留规则被擦除，则查询通过 `user_id` 关联 `app_user.email`。`external_record_id` 为空的台账项写成 `unresolved: true`，只能人工查看，绝不进入撤回写入范围。重复 `record_id` 在计划中去重，台账事实仍保留。

这里的“可识别”不是表中存在一列叫 `environment`，也不是“备份与现表的所有差异”。它是“这一个外部 `record_id` 确实出现在预发已发布台账里”。这个限制保护窗口期内生产侧正常写入的行：只要该行没有进入台账，撤回计划就只能把它列为台账外跳过，不会更新或删除它。

## 安全文件与日志边界

运行命令需要一个 scheduler 环境文件和一个工作目录：

```bash
python3 -B deploy/permission_table_guard.py \
  --env-file deploy/.env.<环境>.scheduler \
  --work-dir <0700 的守卫工作目录> <子命令>
```

环境文件必须是当前运行用户所有、权限严格为 `0600`；值可带单引号或双引号，读取时只剥去首尾一层引号。工作目录必须是当前用户所有、权限严格为 `0700`。脚本只读取 `LINGXI_FEISHU_APP_ID`、`LINGXI_FEISHU_APP_SECRET`、`LINGXI_PERMISSION_BITABLE_APP_TOKEN`、`LINGXI_PERMISSION_BITABLE_TABLE_ID`，并在 `ledger` 时读取 `LINGXI_POSTGRES_DSN`；飞书地址沿用 scheduler 的 `LINGXI_FEISHU_BASE_URL`，未配置时使用既有 HTTPS 默认值。

备份、台账、撤回计划都是新建的 `0600` JSON 文件，脚本不会覆盖同名旧文件。备份结构如下：

```json
{
  "schema": 1,
  "taken_at": "<UTC 时间>",
  "environment": "stage",
  "table": {"app_token_sha256": "<摘要>", "table_id": "<表标识>"},
  "row_count": 0,
  "rows": [{"record_id": "<记录标识>", "fields": {
    "record_key": "<邮箱>", "email": "<邮箱>", "name": "<姓名>",
    "permissions": "<权限文本>", "status": "<状态>",
    "updated_at": "<时间>", "token_cipher": "<密文>"
  }}]
}
```

备份中会有邮箱、姓名、权限正文和令牌密文，这是撤回所必需的内容；应用令牌只保存 SHA-256 摘要。标准输出和错误输出不打印令牌、密文、字段值、邮箱、权限正文或带查询串的地址，只打印步骤、数量、记录标识、字段名、文件路径和摘要。台账与计划不复制备份字段。

## 何时运行

### 预发升级前：`backup`

这是升级前的硬前提。拉取代理的 `pre_apply_hooks` 可以登记以下命令；备份完成退出 `0` 才允许继续拉取、迁移或启动新镜像，任何非零退出都必须停止：

```bash
python3 -B deploy/permission_table_guard.py \
  --env-file deploy/.env.<环境>.scheduler \
  --work-dir <0700 的守卫工作目录> backup
```

`backup` 使用租户令牌分页列举整表，单页 500 行，最多 50 页。页数达到上界仍声明有下一页会失败，不把“可能漏读”当成成功。写完后脚本重新读取 JSON，核对结构和行数，再计算文件 SHA-256，并输出 `backup=<路径> rows=N sha256=<摘要>`。只有这一条命令成功退出，才算备份成立。它不依赖新镜像、不访问预发库，因此满足首次升级的旧镜像约束。

### 作为拉取代理钩子

预发的 `pre_apply_hooks` 恰有一项，使用[宿主包装脚本样例](control/examples/hooks/stage-permission-table-backup.sh)，接口说明见[拉取代理的通用 pre-apply 钩子](拉取代理.md#九通用-pre-apply-钩子接口)。包装脚本忽略拉取代理传入的四个通用参数，按宿主固定配置执行本守卫的 `backup`；退出 `0` 才允许继续，非零保持 `planned`。生产的 `pre_apply_hooks` 必须为空。

拉取代理以 root 运行，包装脚本随之以 root 运行，而本守卫要求环境文件属主等于运行者且为 `0600`、工作目录属主等于运行者且为 `0700`（见「安全文件与日志边界」）。所以包装脚本里的 `<SCHEDULER_ENV_FILE>` 不能直接指向部署用户持有的 scheduler 环境文件，必须是 root 私有的独立 `0600` 副本（只需 `backup` 读取的四个飞书字段，可选 `LINGXI_FEISHU_BASE_URL`）；`<GUARD_WORK_DIR>` 必须是 root 私有的 `0700` 目录（不存在时守卫以 `0700` 新建，已存在则属主与模式都要恰好相符）。包装脚本副本本身及其全部祖先目录还须 root 属主、无组 / 其他写、非符号链接，否则拉取代理记 `pre_apply_hook_unsafe`、一个钩子都不执行。这三项与拉取代理的告警凭据副本同列为 S-2-6 前置核对项，安装步骤、路径约定和核对清单见[拉取代理 §九](拉取代理.md#九通用-pre-apply-钩子接口)。

### 预发窗口收口：`ledger`、`diff`、`revert`、`verify`

先把 `backup` 输出中的 `taken_at` 原样作为时间水位导出台账：

```bash
python3 -B deploy/permission_table_guard.py \
  --env-file deploy/.env.<环境>.scheduler \
  --work-dir <0700 的守卫工作目录> ledger --since <backup.taken_at>
```

本实现选择宿主侧方案 A：脚本调用宿主 `psql` 查询 `publish_outbox`，不依赖新镜像。查询只筛 `published` 且 `published_at >= since` 的行，台账写完也会重新读取核对。方案 B（容器内新增模块）没有实现，不能混用两套入口。

DSN 口令的处理：DSN 来自环境文件；psql 的命令行参数对同机其他用户可见（`ps` 就能看到），所以口令只经子进程的 `PGPASSWORD` 环境变量传给 psql，绝不进入 `-d` 参数。URL 形 DSN 两处口令都拆：`user:口令@` 里的 userinfo 口令和 `?password=` 查询参数（含百分号编码，两处都写时取查询参数，与 libpq 一致）；除 `password` 之外的查询参数原样保留。`postgresql://`、`postgres://`、`postgresql+psycopg://` 三种写法都接受，交给 psql 前统一归一成 `postgresql://`（scheduler 环境文件里的 SQLAlchemy 写法不必改）；其他方案名一律拒绝并以 `database_dsn_invalid` 停住。键值形 DSN 去掉 `password=` 项。日志和异常只输出分类码（`psql_not_found`、`psql_timeout`、`psql_failed`、`psql_output_invalid`），不回显 DSN 的任何部分；psql 的错误输出只用于非零退出判断，不转发到日志。

台账文件是 JSON 数组，每项含 `record_id`、`record_key`、`published_at`、`outbox_id`；外部记录标识为空的项另加 `unresolved: true`。这类项不能自动撤回，必须由人工查清。

`diff` 是只读对账，既可以只给备份，也可以附台账：

```bash
python3 -B deploy/permission_table_guard.py --env-file <scheduler env> \
  --work-dir <0700 的守卫工作目录> diff --backup <备份文件> --ledger <台账文件>
```

它重新分页读取现表，列出“更新”“新建”“删除”三类记录数和 `record_id` 清单，并给每个标识打上 `ledger` 或 `outside` 标记。没有台账的差异只用于观察，不会成为撤回依据。

`revert` 默认是干跑：

```bash
python3 -B deploy/permission_table_guard.py --env-file <scheduler env> \
  --work-dir <0700 的守卫工作目录> revert \
  --backup <备份文件> --ledger <台账文件>
```

脚本会生成 `0600` 的撤回计划，并打印还原数量、删除数量、台账外跳过数量、未解析数量、记录标识清单和 `summary_sha256`。确认前不发送 `PUT` 或 `DELETE`。

确认摘要 `summary_sha256` 的定义：它绑定备份文件摘要、台账文件摘要、撤回记录清单（还原 + 删除）、未解析清单，以及**每个撤回目标行在干跑时刻的存在状态、当前七字段内容摘要和备份中对应值的摘要**（计划文件的 `rows` 段只存这些摘要，不存字段值）。因此干跑之后、确认之前，生产若改了或删了同一台账行，重新计算出的摘要必然不同，旧的 `--confirm` 值直接失效、零写入；两次干跑的计划文件 `rows` 段逐行比对即可定位变化行。台账外的行不进入摘要：生产在窗口期新开通一个人、改一个台账外的行，都不影响摘要，因为撤回从不写它们，计划只把它们列为跳过。

只有人工核对摘要后，才可以显式执行：

```bash
python3 -B deploy/permission_table_guard.py --env-file <scheduler env> \
  --work-dir <0700 的守卫工作目录> revert \
  --backup <备份文件> --ledger <台账文件> --confirm <summary_sha256>
```

确认值错误立即退出非零，仍不写表。确认摘要相符后、发出第一条写入前，脚本再取一次现表，逐行比对每个撤回目标行的存在状态与七字段内容；任一行与确认时刻不同就停止，退出 `1`、零写入，只打印变化行的 `record_id`（`revert=stopped reason=rows_changed_before_execute changed=<记录标识>`），不打印内容。比对通过后，计划中的备份内记录逐字段 `PUT` 七个字段，随后 `GET` 读回七字段逐字核对；备份外但在台账中的记录调用记录删除接口，随后 `GET` 期望得到 HTTP 404/不存在。任何一行写入或读回不符都立即停止，输出已完成与未完成的记录标识，退出非零。

窗口纪律：干跑与确认之间的窗口要尽量短——核对完摘要就确认，不要隔着会议或换班。摘要失配、执行前比对拦停，都意味着有人动了目标行：重新干跑、重新核对、再确认，不要重试旧摘要。中断后重跑同理：本次已写入的行改变了目标行内容，旧摘要已失效，先重新干跑取新摘要；已还原且再次核对相等的记录、已不存在的删除记录会被跳过，所以重跑是安全的，且仍只使用原台账范围。

记录删除路径是飞书 `DELETE /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records/{record_id}`。本卡只实现协议调用与离线假传输，**删除接口未经真实调用验证**；S-2-6 的预发演示必须首次在受控表上验证删除、404 读回和失败后的恢复步骤。删除验证前不得把“删除成功”写成真实外部能力。

`verify` 只读复核同一台账范围：备份内记录必须等于备份七字段，备份外记录必须不存在，台账外的生产行完全忽略：

```bash
python3 -B deploy/permission_table_guard.py --env-file <scheduler env> \
  --work-dir <0700 的守卫工作目录> verify \
  --backup <备份文件> --ledger <台账文件>
```

复核通过退出 `0`；任一记录缺失、字段不等或应删除记录仍存在退出 `1`；配置、文件或外部只读调用本身失败则退出其他非零码并停住。

## 撤回边界与窗口纪律

撤回不是“把现表恢复成备份的全部差异”。备份后生产正常更新的同一行若没有对应台账，属于台账外差异，计划会显示为跳过；备份后生产新建的行若没有对应台账，也只会显示为台账外新建，不会被删。台账内记录才有写入权限：在备份中就还原七字段，不在备份中就删除。脚本不按邮箱重新搜索、不猜测记录标识、不用 `record_key` 代替 `external_record_id`。

若生产与预发同时写同一个台账内 `record_id`，现有表结构没有版本列，守卫只能靠确认摘要与执行前比对拦住执行前发生的那些改动；执行前比对到该行写入之间的极短窗口仍无法区分先后，出现读回不符即停止，并请产品负责人决定；摘要不是自动授权。台账外行的保证不覆盖同一标识的并发写入。

## 收口与清理

备份含令牌密文。`verify` 通过、真实演示记录完成且不再需要回溯后，默认按 `deploy/日志留存.md` 的口径清理 `backup-*`、`ledger-*`、`revert-plan-*`；清理前把摘要和结果记入受控工作项。若需保留，继续使用 `0700` 目录和 `0600` 文件，登记理由、到期时间和负责人，不复制到 Issue、PR、日志或共享目录。脚本不自动清理，避免误删恢复材料。

## 预发演示前检查

编排者需人工复核：scheduler 环境文件及 `0600` 属主、`0700` 工作目录、权限表凭据与坐标、预发库 DSN、备份 `taken_at`、台账路径和撤回摘要。任何值都不应写入代码、提交正文或公开日志。

本卡只有离线标准库测试与本机门禁证据，不是飞书真实链路证据。真实表首次 `backup`、`ledger`、删除调用、404 读回、整批撤回和 `verify` 回源均留给 S-2-6；此前不得声称 E-8 已真实验收。
