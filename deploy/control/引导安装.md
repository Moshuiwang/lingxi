# 控制包引导安装

预发/生产共用此 runbook。须绑定 Ops 工作项、环境、固定 Release、窗口和授权终点；不授执行权。

## 零、适用与不做

预发和生产主机拉取链路调用同一个控制包内的 `deploy/lingxi_deploy.py`，只在版本选择和环境参数上不同。预发可接受候选版，生产只接受有 main 验收记录的正式版。Release Promotion 即放行；`approval.json` 由拉取代理按 Release 生成。

本文只写控制包、受限 SSH、socket 绑定和恢复材料，不写真实主机名、账号名、公钥或受控路径；`<占位符>` 由获批 Ops 工作项提供。本文不替代 G-1、G-2、G-3 授权，不执行主机变更，不迁移数据库、持久卷、业务 env 或凭据。

不符停；未验证不入账。

## 一、前提核对

### 1. 运行条件

先定 `<PYTHON_ABSOLUTE_PATH>`，版本不低于 3.11；默认 python3 不作判据，可低于 3.11。部署主体 root；受限 relay 账号不入 sudo/Docker 组；控制包只需 Linux、Docker、Compose 2.24 以上，宿主不装依赖、不现场构建。

```bash
<PYTHON_ABSOLUTE_PATH> --version
docker version --format '{{.Server.Version}}'
docker compose version --short
test "$(id -u)" -eq 0
test -n "${LINGXI_GH_COMMAND:-}"
test -x "$LINGXI_GH_COMMAND"
```

期望：`<PYTHON_ABSOLUTE_PATH>` 输出 `3.11` 以上；默认 `python3` 不判定；Compose `2.24.0` 以上；UID `0`；`LINGXI_GH_COMMAND` 为可执行绝对路径。它只供 `release_manifest.py resolve` 只读回读 Release，不回落个人 `gh` 登录。任一不符就停，不安装、不改 SSH。

### 2. 目录规划

以下是形状和权限约定，不是实际主机值。root 先建父目录，再把实际值写入 `host-contract.json`；受限账号不能写入。

`host-contract.json` 的 `host` 必须等于主机的**内核主机名**，即 `python3 -c 'import socket;print(socket.gethostname())'` 的输出——通常就是 `/etc/hostname` 里的全名（云主机常带域后缀），**不是** `hostname -s` 的短名。部署器 `preflight` 按此比对，不等即 `host_mismatch`，每次 apply 都会在停止服务前停住；拉取代理也按同一口径在取锁前退出（日志 `阶段=agent 结果码=host_mismatch`）。写入前先用上面这条命令取值，不要手敲。

| 项目 | 路径占位 | 属主 | 权限 | 谁建 |
| --- | --- | --- | --- | --- |
| `deploy_root` | `<DEPLOY_ROOT>` | `root:root` | `0750` | root / Ops |
| `config_root` | `<CONFIG_ROOT>` | `root:root` | `0750` | root / Ops |
| `bundle_root` | `<BUNDLE_ROOT>` | `root:root` | `0755` | root / Ops |
| `relay_root` | `<RELAY_ROOT>` | `root:root` | `0755` | root / Ops |
| `lock_path` | `<DEPLOY_ROOT>/host.lock` | `root:root` | `0600` | 部署器首次加锁时 |
| 状态目录 | `<STATE_DIRECTORY>` | `root:root` | `0700` | 部署器 / Ops |
| socket 目录 | `<SOCKET_DIRECTORY>` | `<SOCKET_OWNER>:<SOCKET_GROUP>` 或 `root:<SOCKET_GROUP>` | `0750` | root / Ops |

```bash
install -d -o root -g root -m 0750 "<DEPLOY_ROOT>"
install -d -o root -g root -m 0750 "<CONFIG_ROOT>"
install -d -o root -g root -m 0755 "<BUNDLE_ROOT>"
install -d -o root -g root -m 0755 "<RELAY_ROOT>"
install -d -o root -g root -m 0700 "<STATE_DIRECTORY>"
install -d -o <SOCKET_OWNER> -g <SOCKET_GROUP> -m 0750 "<SOCKET_DIRECTORY>"
stat -c '%n %U:%G %a' "<DEPLOY_ROOT>" "<CONFIG_ROOT>" "<BUNDLE_ROOT>" "<RELAY_ROOT>" "<STATE_DIRECTORY>" "<SOCKET_DIRECTORY>"
```

期望各行符合上表，锁文件为 `root:root 600`；私有 `.env.*`、计划、批准和状态账不进控制包，私有文件 `0600`，状态目录/文件 `0700`/`0600`。不符就停，禁用 `chmod -R`。

## 二、控制包引导安装

### 1. 取 Release 附件并核对索引

在 `<STAGING_DIRECTORY>` 建暂存目录，只下载 `lingxi-control.tar`、`control-index.json` 和 manifest；不从浮动 main 取脚本。

```bash
install -d -o root -g root -m 0700 "<STAGING_DIRECTORY>"
"$LINGXI_GH_COMMAND" release download "<RELEASE_TAG>" \
  --repo Moshuiwang/lingxi \
  --pattern lingxi-control.tar \
  --pattern control-index.json \
  --dir "<STAGING_DIRECTORY>"
tar -xOf "<STAGING_DIRECTORY>/lingxi-control.tar" control-index.json \
  | cmp -s - "<STAGING_DIRECTORY>/control-index.json"
```

期望两个附件属于本次 Release，`cmp` 为 `0`；`tar -tf` 为固定集合，摘要取 manifest 的 `control_bundle.sha256`。附件缺失时（不可变 Release 的历史版本，发布流程补传 `control-index.json` 之前发布的都没有它）改从 tar 内提取：`tar -xOf lingxi-control.tar control-index.json > <STAGING_DIRECTORY>/control-index.json`，再核对其 sha256 等于 manifest 的 `control_bundle.index_sha256`；缺 tar、索引摘要不一致或有额外成员就停。

### 2. 用固定版本选择器得到摘要

使用已审查控制包的 `scripts/ci/release_manifest.py`；生产用 `production`，不得用候选版。

```bash
<PYTHON_ABSOLUTE_PATH> -B "<FIXED_RELEASE_TOOL_ROOT>/scripts/ci/release_manifest.py" resolve \
  --repository Moshuiwang/lingxi \
  --tag "<RELEASE_TAG>" \
  --environment stage \
  --output "<STAGING_DIRECTORY>/images.env" \
  --manifest-output "<STAGING_DIRECTORY>/release-manifest.json"
sha256sum "<STAGING_DIRECTORY>/lingxi-control.tar" \
  "<STAGING_DIRECTORY>/control-index.json"
```

期望输出 `部署选择已核对，只输出不含凭据的镜像配置；未部署`；manifest 含四镜像摘要、迁移头、来源提交、树摘要和控制包摘要，生产另须 main 验收记录。不符就停；`resolve` 不运行 Compose。

### 3. 校验、安装只读版本并切换当前引用

`control_bundle.py` 的 `verify` 校验 tar、索引、成员权限和文件摘要；`install` 写入 `<BUNDLE_ROOT>/<control_bundle.sha256>`；`verify_install` 回读；`activate` 最后原子切换 `<BUNDLE_ROOT>/current`。命令只用已固定工具：

```bash
PYTHONPATH="<FIXED_CONTROL_ROOT>/deploy" <PYTHON_ABSOLUTE_PATH> -B -c '
import json
from pathlib import Path
import control_bundle

staging = Path("<STAGING_DIRECTORY>")
manifest = json.loads((staging / "release-manifest.json").read_text())
expected = manifest["control_bundle"]
package = staging / "lingxi-control.tar"
root = Path("<BUNDLE_ROOT>")
control_bundle.verify(package, expected)
control_bundle.install(package, expected, root)
control_bundle.verify_install(root / expected["sha256"], expected)
control_bundle.activate(root, expected)
control_bundle.verify_install(root / expected["sha256"], expected)
print(json.dumps({"ok": True, "bundle_sha256": expected["sha256"], "current": str(root / "current")}))
'
readlink "<BUNDLE_ROOT>/current"
stat -c '%n %U:%G %a' "<BUNDLE_ROOT>/current" "<BUNDLE_ROOT>/<CONTROL_BUNDLE_SHA256>"
```

期望机读结果含 `"ok": true`，`current` 指向本次摘要目录；目录/可执行文件 `0555`，其他文件和索引 `0444`。两次 `verify_install` 均通过才完成；任一摘要、集合、权限或引用不符就停，保留旧 `current`。

## 三、受限通道安装

模板 `<占位符>` 只能由产品负责人或本次 Ops 工作项提供；公钥不写入本仓库、日志、样例或提交正文。

### 1. 专用系统账号

账号已存在且不符时停；创建系统账号，使用最小 POSIX shell `/bin/sh`，home 与 `.ssh` 由 root 管理。OpenSSH 执行 forced-command 时由用户登录 shell 调用 `-c`；不能使用 `nologin`，否则会输出 “This account is currently not available” 并退出，relay 无法启动。限制来自 `restrict,no-user-rc,command=` 和 `Match` 块，不来自 shell。

```bash
useradd --system --user-group --home-dir "<RELAY_HOME>" \
  --create-home --shell /bin/sh "<RESTRICTED_RELAY_ACCOUNT>"
install -d -o root -g root -m 0755 "<RELAY_HOME>"
install -d -o root -g root -m 0755 "<RELAY_HOME>/.ssh"
id "<RESTRICTED_RELAY_ACCOUNT>"
getent passwd "<RESTRICTED_RELAY_ACCOUNT>"
id -nG "<RESTRICTED_RELAY_ACCOUNT>"
stat -c '%n %U:%G %a' "<RELAY_HOME>" "<RELAY_HOME>/.ssh"
```

期望 shell 是 `/bin/sh`，账号不在 `sudo`、`docker`、`wheel` 等特权组，home 与 `.ssh` 是 `root:root` 且无组/其他写权限。现场 UID/GID 记入自检清单，不使用样例值。

### 2. `sshd` 的 `Match` 块

模板见 [`sshd_config.example`](sshd_config.example)，复制到受控 drop-in 只替换账号占位符；保留公钥认证、禁密码/转发/TTY/用户配置及 `PermitUserRC no`。

```bash
install -o root -g root -m 0644 \
  "<CONTROL_ROOT>/deploy/control/sshd_config.example" "<SSHD_DROPIN>"
RESTRICTED_RELAY_ACCOUNT="<ACTUAL_RELAY_ACCOUNT>"
sed -i "s|<RESTRICTED_RELAY_ACCOUNT>|${RESTRICTED_RELAY_ACCOUNT}|g" "<SSHD_DROPIN>"
grep -Fq "Match User <RESTRICTED_RELAY_ACCOUNT>" "<SSHD_DROPIN>" && exit 1
sshd -t
systemctl reload ssh
systemctl is-active --quiet ssh
```

期望 `sshd -t` 无输出且为 `0`，reload 成功且服务 active。语法、reload 或占位符不符就停；语法未通过不 reload，回退同样先 `sshd -t`。

### 3. forced-command 密钥

模板见 [`authorized_keys.example`](authorized_keys.example)。公钥由产品负责人外部给定；只替换公钥、Python 和冻结 relay 绝对路径。保留 `restrict,no-user-rc`、`command="... -I -S ..."`，不加 shell、SFTP 或任意远程命令入口。

```bash
install -o root -g root -m 0644 \
  "<CONTROL_ROOT>/deploy/control/authorized_keys.example" "<AUTHORIZED_KEYS>"
PYTHON_ABSOLUTE_PATH="<ACTUAL_PYTHON_ABSOLUTE_PATH>"
FROZEN_RELAY_ABSOLUTE_PATH="<ACTUAL_FROZEN_RELAY_ABSOLUTE_PATH>"
ADMIN_PERSONAL_PUBLIC_KEY="<ACTUAL_ADMIN_PERSONAL_PUBLIC_KEY>"
sed -i \
  -e "s|<PYTHON_ABSOLUTE_PATH>|${PYTHON_ABSOLUTE_PATH}|g" \
  -e "s|<FROZEN_RELAY_ABSOLUTE_PATH>|${FROZEN_RELAY_ABSOLUTE_PATH}|g" \
  -e "s|<ADMIN_PERSONAL_PUBLIC_KEY>|${ADMIN_PERSONAL_PUBLIC_KEY}|g" \
  "<AUTHORIZED_KEYS>"
test "$(wc -l < "<AUTHORIZED_KEYS>")" -eq 1
grep -Fq 'restrict,no-user-rc,' "<AUTHORIZED_KEYS>"
grep -Fq 'command="<PYTHON_ABSOLUTE_PATH> -I -S <FROZEN_RELAY_ABSOLUTE_PATH>"' "<AUTHORIZED_KEYS>" && exit 1
stat -c '%n %U:%G %a' "<AUTHORIZED_KEYS>"
```

期望文件一行、root 所有、`0644`，且含 `restrict,`、`no-user-rc`、固定命令和 `ssh-ed25519` 前缀。无外部公钥就停，不自行生成、不用样例占位公钥。

### 4. socket 目录、权限和容器 UID 映射

`contract.json` 固定目录 `488`/`0750`、socket `432`/`0660`，路径为 `/run/lingxi-innertest/admin.sock`；目录由 root 设 `socket_gid`，socket 由 scheduler 建立。

```bash
chown <SOCKET_OWNER_UID>:<SOCKET_GID> "<SOCKET_DIRECTORY>"
chmod 0750 "<SOCKET_DIRECTORY>"
docker inspect --format '{{.Config.User}}' "<SCHEDULER_CONTAINER>"
docker exec "<SCHEDULER_CONTAINER>" id -u
docker exec "<SCHEDULER_CONTAINER>" cat /proc/self/uid_map
stat -c '%n %u:%g %a' "<SOCKET_DIRECTORY>" "<SOCKET_DIRECTORY>/admin.sock"
```

源码结论：基线 `deploy/compose.yaml` 将 scheduler 固定为 `10001:10001`，stage/prod 未改；部署器挂载宿主 socket 到 `/run/lingxi-innertest`，只读挂载配置到 `/etc/lingxi/innertest`。Compose 未声明现场 user namespace 映射，部署器核对 `/proc/self/uid_map`，现场值未验证。

期望 scheduler UID `10001`；socket `0660`、组 `<SOCKET_GID>`、属主 `<SOCKET_OWNER_UID>`。socket 目录属主 = `<SOCKET_OWNER_UID>`（scheduler 容器 UID，现固定 `10001`）、组 = `<SOCKET_GID>`、模式 `0750`；root 不能当属主——scheduler 要在里面建 socket 和锁文件。其父目录 `0750` 且仍按 root 保护规则。`<RELAY_UID>` 不得为 `0`、`65534` 或 socket owner；`peer_uid` 取 map 且不等于 `10001`。不符就停。

### 5. `binding.json` 与名单导入

字段说明和占位值见 [`examples/binding.json`](examples/binding.json)。字段集合必须完全是 `schema_revision`、`binding_id`、`host_uid`、`peer_uid`、`uid_map_sha256`、`socket_gid`：

| 字段 | 含义 | 安装时判定 |
| --- | --- | --- |
| `schema_revision` | 绑定格式版本 | 固定为 `1` |
| `binding_id` | 数据库绑定按 `id + scope` 定位 `open_id`；行不存 UID | 三处一致；只重签 UID 时沿用现值，换 id 才进入新导入判定 |
| `host_uid` | 宿主 relay UID | 正整数，不是 `0` 或 `65534`，且不等于 scheduler UID |
| `peer_uid` | map 对应的容器内主体 UID | 由现场 map 计算，不能等于 `10001` |
| `uid_map_sha256` | `/proc/self/uid_map` 内容摘要 | 与容器内只读回读一致 |
| `socket_gid` | socket 组 GID | 正整数，不是 `0` 或 `65534`，与宿主目录和 socket 一致 |

顺序固定：读取现有 `<BINDING_ID>` → 建 root 所有的 binding 文件 → 在 `public-config.json` 写同一 `LINGXI_INNERTEST_BINDING_ID`/`LINGXI_INNERTEST_SCOPE` → 新导入时先 `plan_roster_import`，再用确认摘要单事务调用 `apply_roster_import(..., binding_id=<BINDING_ID>)`。换专用账号只重签 UID，更新四字段仍沿用 `binding_id`，不导入。两处源码（`src/lingxi/adapters/postgres_innertest.py::_principal`、`src/lingxi/adapters/postgres_innertest_roster.py::_write_import`）说明数据库行 `innertest_admin_binding(id, scope, open_id, version, enabled)` 不存 UID；容器内 `load_binding` 才校验 UID。换 id 才需新导入；`database` 作用域返回 `scope_already_database`，须产品负责人另裁，本 runbook 不覆盖。无独立导入命令，不伪造 CLI。

样例文件是合法 JSON，六个字段都是占位值（`binding-example-placeholder`、样例 UID/GID、全 `a` 的摘要），不能照抄；与三.2、三.3 同一姿势：复制样例 → 把现场值写进 shell 变量 → `sed` 按字段名替换 → 用固定 Python 解析 JSON，核对字段集合与每个值。`<ACTUAL_UID_MAP_SHA256>` 是三.4 读回的容器内 `/proc/self/uid_map` 原始字节的 SHA-256（`docker exec "<SCHEDULER_CONTAINER>" cat /proc/self/uid_map | sha256sum`），`<ACTUAL_RELAY_UID>` / `<ACTUAL_SOCKET_GID>` 取三.1、三.4 记入自检清单的现场值，`<ACTUAL_PEER_UID>` 按 map 计算。

```bash
install -o root -g root -m 0644 \
  "<CONTROL_ROOT>/deploy/control/examples/binding.json" \
  "<CONFIG_ROOT>/innertest/binding.json"
BINDING_ID="<ACTUAL_BINDING_ID>"
RELAY_UID="<ACTUAL_RELAY_UID>"
PEER_UID="<ACTUAL_PEER_UID>"
SOCKET_GID="<ACTUAL_SOCKET_GID>"
UID_MAP_SHA256="<ACTUAL_UID_MAP_SHA256>"
sed -i \
  -e "s|\"binding_id\": \"[^\"]*\"|\"binding_id\": \"${BINDING_ID}\"|" \
  -e "s|\"host_uid\": [0-9]*|\"host_uid\": ${RELAY_UID}|" \
  -e "s|\"peer_uid\": [0-9]*|\"peer_uid\": ${PEER_UID}|" \
  -e "s|\"socket_gid\": [0-9]*|\"socket_gid\": ${SOCKET_GID}|" \
  -e "s|\"uid_map_sha256\": \"[^\"]*\"|\"uid_map_sha256\": \"${UID_MAP_SHA256}\"|" \
  "<CONFIG_ROOT>/innertest/binding.json"
grep -Fq 'placeholder' "<CONFIG_ROOT>/innertest/binding.json" && exit 1
<PYTHON_ABSOLUTE_PATH> -B -c '
import json, re, sys
path, binding_id, host_uid, peer_uid, socket_gid, uid_map_sha256 = sys.argv[1:]
data = json.load(open(path, encoding="utf-8"))
expected = {
    "schema_revision": 1,
    "binding_id": binding_id,
    "host_uid": int(host_uid),
    "peer_uid": int(peer_uid),
    "uid_map_sha256": uid_map_sha256,
    "socket_gid": int(socket_gid),
}
assert set(data) == set(expected), sorted(set(data) ^ set(expected))
assert data == expected, [key for key in expected if data[key] != expected[key]]
assert re.fullmatch(r"[0-9a-f]{64}", uid_map_sha256) and set(uid_map_sha256) != {"a"}
assert all(data[key] not in (0, 65534) for key in ("host_uid", "peer_uid", "socket_gid"))
assert data["host_uid"] != 10001 and data["peer_uid"] != 10001
print(json.dumps({"ok": True, "binding_id": data["binding_id"]}))
' "<CONFIG_ROOT>/innertest/binding.json" \
  "${BINDING_ID}" "${RELAY_UID}" "${PEER_UID}" "${SOCKET_GID}" "${UID_MAP_SHA256}"
test "${BINDING_ID}" = "<PUBLIC_CONFIG_BINDING_ID>"
stat -c '%n %U:%G %a' "<CONFIG_ROOT>/innertest" "<CONFIG_ROOT>/innertest/binding.json"
```

期望：`grep placeholder` 无命中（命中即 `exit 1`，说明有占位值没替换）；Python 输出 `{"ok": true, "binding_id": "<ACTUAL_BINDING_ID>"}`，即字段集合恰为六个、每个值与现场值一致、摘要是 64 位十六进制且不是样例摘要、三个 UID/GID 不是 `0`/`65534`/scheduler UID；`binding.json`、`public-config.json` 和数据库行 `id` 三处相同；目录不被受限账号写入，执行导入时回读数据库模式及相同摘要。UID 重签沿用现有 id，不把换账号误判为换绑定。任一不符就停，不为凑齐样例直接写数据库。

### 6. `innertest-relay.json` 与冻结副本

字段说明和占位值见 [`examples/innertest-relay.json`](examples/innertest-relay.json)。

| 字段 | 含义 | 安装时判定 |
| --- | --- | --- |
| `schema_revision` | relay 配置版本 | 固定为 `1` |
| `socket_path` | relay 连接的宿主 Unix socket | 绝对路径且与 `contract.json` 及计划一致 |
| `relay_uid` | 受限账号宿主 UID | 不为 `0`、`65534`，不等于 `socket_owner_uid` |
| `socket_owner_uid` | scheduler socket 的宿主属主 UID | 由现场 UID 映射回读，不拿样例值代替 |

冻结副本只能来自控制包内 `scripts/admin/innertest_relay.py`，不能从工作树、main 或受限账号 home 复制。`activate` 调用 `control_bundle.install_relay`，在 `<RELAY_ROOT>/<安装收据摘要>/` 写 relay、配置和 `installation.json` 后切换 `current`。relay 根目录 root:root `0755`、普通配置 root:root `0644`；冻结目录/文件更严为 `0555`/`0444`，不得放宽。

```bash
readlink "<RELAY_ROOT>/current"
stat -c '%n %U:%G %a' \
  "<RELAY_ROOT>/current" \
  "<RELAY_ROOT>/<INSTALLATION_RECEIPT_SHA256>" \
  "<RELAY_ROOT>/<INSTALLATION_RECEIPT_SHA256>/innertest_relay.py" \
  "<RELAY_ROOT>/<INSTALLATION_RECEIPT_SHA256>/innertest-relay.json" \
  "<RELAY_ROOT>/<INSTALLATION_RECEIPT_SHA256>/installation.json"
sha256sum "<RELAY_ROOT>/<INSTALLATION_RECEIPT_SHA256>/innertest_relay.py"
```

`installation.json` 的 `bundle_sha256`、`relay_sha256`、`config_sha256`、`mode`、`directory_mode` 须与计划一致；部署器还核对收据摘要、引用、root 属主、非链接和不可写。任一漂移都停，回到固定候选核对。

### 7. 安装自检

按 `scripts/admin/innertest_install_check.py` 的完整清单建立临时非秘密 manifest；只读检查，不写凭据：

| 字段 | 内容 |
| --- | --- |
| `schema_revision` | `1` |
| `python` | 冻结 Python 绝对路径 |
| `relay` / `relay_sha256` | 冻结 relay 路径及其 SHA256 |
| `relay_config` | `innertest-relay.json` 路径 |
| `binding` | `binding.json` 路径 |
| `socket_directory` | 宿主 socket 目录 |
| `socket_owner_uid` | scheduler socket 目录属主 UID | 非 `0`、`65534`，且不等于 `relay_uid` |
| `socket_gid` | scheduler socket 目录组 GID | 与宿主目录和 socket 一致 |
| `relay_uid` / `relay_gid` | 受限账号 UID/GID |
| `authorized_keys` | root 管理的授权文件路径 |

```bash
<PYTHON_ABSOLUTE_PATH> -B "<CONTROL_ROOT>/scripts/admin/innertest_install_check.py" \
  "<INSTALL_CHECK_MANIFEST>"
```

期望 JSON 的 `ok` 为 `true`（`{"ok": true, ...}`）；`manual_required` 仍须逐项完成，尤其是 `sshd_effective_policy`、`credential_owner`、`three_peer_connection_probes`。`ok` 为 false、字段缺失、权限不安全、relay 摘要或 forced-command 形状不符就停。

### 8. 三路否定实测

这是 G-1 安装验收，不用成功连接替代。记录三次命令的 UTC 起止时间和同一受限账号；不把公钥、凭据或完整日志写进提交。三路都是**公钥认证成功之后**被 forced-command 与 `Match` 块限制住的，所以 sshd 日志里**不会有「拒绝」行**——它记的是 `Accepted publickey for <账号> …` 与 `session opened for user <账号>`；否定证据在客户端退出码、输出特征和远端无文件上，不在日志里找 `refused`。以下判据来自 2026-09-14 预发实测（记录见 [Issue #770 评论](https://github.com/Moshuiwang/lingxi/issues/770#issuecomment-5659078733)），实测时 relay 通道尚未接通（scheduler 还没有在 `<SOCKET_DIRECTORY>` 建立 `admin.sock`）；通道接通后 shell 路会连上 socket 而不是退出 `1`，那种状态下的表现尚未实测，不得沿用本判据，须重新实测后再写入。

```bash
# 在管理端执行；每条命令后立刻记 $? 。
ssh -o BatchMode=yes -o RequestTTY=no \
  "<RESTRICTED_RELAY_ACCOUNT>@<HOST>" bash 2>&1; echo "shell_exit=$?"
scp -q -o BatchMode=yes /dev/null \
  "<RESTRICTED_RELAY_ACCOUNT>@<HOST>:<REMOTE_PATH_PLACEHOLDER>" 2>&1; echo "scp_exit=$?"
ssh -o BatchMode=yes -t \
  "<RESTRICTED_RELAY_ACCOUNT>@<HOST>" bash 2>&1; echo "tty_exit=$?"
# 在主机上以 root 执行。
test ! -e "<REMOTE_PATH_PLACEHOLDER>"
journalctl -u ssh --since "<TEST_START_UTC>" --until "<TEST_END_UTC>" -o cat \
  | grep -F "<RESTRICTED_RELAY_ACCOUNT>"
```

判定口径（四条缺一不可）：

1. **shell**：`bash` 未被执行——forced-command 把会话交给 relay，relay 因通道未起退出，`shell_exit=1`，输出只有 relay 的固定文案「受限管理通道不可用；请按原 request_key 查询，勿重新发起。」（relay 写到标准错误，故用 `2>&1` 合并后判定）。出现任何 shell 提示符、`bash` 的报错或其他命令输出都不算。
2. **scp**：`scp_exit=255`，输出含 `Connection closed`；主机上 `test ! -e "<REMOTE_PATH_PLACEHOLDER>"` 为 `0`（远端没有文件）。
3. **TTY**：`tty_exit=255`，输出含 `PTY allocation request failed on channel 0`（`Match` 块 `PermitTTY no` 生效）。
4. **日志**：三次连接各有一行 `Accepted publickey for <RESTRICTED_RELAY_ACCOUNT> from <来源地址>`（`LogLevel VERBOSE` 时还有 `found at <AUTHORIZED_KEYS>:1`，指向 root 管理的授权文件而不是账号 home 下的文件）与 `session opened for user <RESTRICTED_RELAY_ACCOUNT>`；按时间、账号和来源主机与三条命令一一对应。日志里**不应**有 `Accepted password`、`Accepted keyboard-interactive` 或指向其他授权文件的行。

任一路退出码为 `0`、建立了 shell、远端出现文件、TTY 分配成功、输出不是上述固定特征，或日志显示非公钥认证、授权文件不是 root 管理的那一份，立即停并请产品负责人确认 G-1；本地单测不替代真实主机实测。

### 9. 安装收据

受限通道装好、自检与人工核对项做完后，root 写一份安装收据 `<CONFIG_ROOT>/deployment-installation.json`（`root:root`、`0600`），把「这台主机的受限通道核对过什么、装的是哪个控制包」固定成机读事实。部署器每次 apply 前按固定摘要核对它（`deploy_runtime.py` 的 `installation_receipt`：键集合恰为六个、`schema` 为 `1`、环境 / 项目与计划一致、`bundle_sha256` 等于目标新包摘要、`binding_version` 等于计划的绑定版本、六项核对全为 `true`，且整份收据的指纹等于计划里的 `channel.installation_receipt_sha256`），拉取代理据它生成计划。没有这份收据，拉取代理每轮记 `installation_receipt_unusable`，一次部署都不会发生。

字段集合必须完全是 `schema`、`environment`、`project`、`bundle_sha256`、`binding_version`、`checks`：

| 字段 | 含义 | 初值与判定 |
| --- | --- | --- |
| `schema` | 收据格式版本 | 固定为 `1` |
| `environment` | 主机环境 | 与 `host-contract.json` 的 `environment` 相同：`stage` 或 `production` |
| `project` | Compose 项目名 | 与 `host-contract.json` 的 `project` 相同 |
| `bundle_sha256` | 当前安装的控制包摘要 | 初值 = 二.3 装入的控制包摘要（manifest 的 `control_bundle.sha256`，即 `<CONTROL_BUNDLE_SHA256>`）；此后由拉取代理在每次装新包时刷新，人不再维护 |
| `binding_version` | 绑定版本 | 三.5 导入后数据库行 `innertest_admin_binding.version` 的现值：新导入为 `1`，只重签 UID 沿用现值；取值用固定只读入口 `docker exec "<SCHEDULER_CONTAINER>" python -m lingxi.apps.innertest_status` 输出的 `binding.version`——部署器 apply 时用同一入口回读并要求相等 |
| `checks` | 六项人工核对的结论 | 键集合固定为下表六个，值只能是 `true` / `false`；只有做过且通过的项才写 `true`，没做过或没通过的写 `false`（收据里没有「未做」这第三种值，`false` 就表示未做或未通过）。有一项 `false` 就不能部署，这是刻意的：不许为了让部署通过而先写 `true` |

六项 `checks` 各对应本章的一步证据（自检脚本 `innertest_install_check.py` 的 `manual_required` 四项在这里展开成六个键）：

| 键 | 对应 `manual_required` | 证据（做过并通过才写 `true`） |
| --- | --- | --- |
| `sudo_policy` | `sudo_effective_policy` | `sudo -l -U "<RESTRICTED_RELAY_ACCOUNT>"` 显示该账号不允许运行任何 sudo 命令（三.1：不在 sudo / wheel 组，也没有单独的 sudoers 授权） |
| `sshd_policy` | `sshd_effective_policy` | `sshd -T -C user="<RESTRICTED_RELAY_ACCOUNT>"` 输出的有效策略与三.2 模板一致：只公钥认证，禁密码、TTY、端口 / agent / X11 转发，`PermitUserRC no` |
| `credential_owner` | `credential_owner` | `stat -c '%U %a' "<AUTHORIZED_KEYS>"` 为 `root` 且无组 / 其他写权限（三.3），并且三.8 日志里 `found at <AUTHORIZED_KEYS>:1` 指向这一份，不是账号 home 下的文件 |
| `authorized_peer` | `three_peer_connection_probes` | 合法路：以受限账号经 forced-command 连入，relay 把会话转到 `admin.sock`，服务端按 peer credentials 把该 UID 识别为绑定的管理员（[Issue #668](https://github.com/Moshuiwang/lingxi/issues/668)「从合法账号 / 另一个 UID / 容器内部非授权进程三路连接验证」之一） |
| `wrong_uid_rejected` | `three_peer_connection_probes` | 另一个宿主 UID（不是 `host_uid`）连接 `admin.sock` 被服务端拒绝 |
| `container_peer_rejected` | `three_peer_connection_probes` | 容器内非授权进程连接 `admin.sock` 被服务端拒绝 |

三.8 的三路否定证明的是 shell / scp / TTY 进不来，不是对端探针；三路对端探针只能在 relay 通道接通（scheduler 已在 `<SOCKET_DIRECTORY>` 建立 `admin.sock`）之后做。三.8 的实测记录里通道尚未接通，所以那时这三个键只能写 `false`；补做后再以 root 改成 `true`。

```bash
BUNDLE_SHA256="<CONTROL_BUNDLE_SHA256>"
BINDING_VERSION="<ACTUAL_BINDING_VERSION>"
# 逗号分隔，只列做过且通过的键，例如 sudo_policy,sshd_policy,credential_owner；没列的一律写 false。
PASSED_CHECKS="<PASSED_CHECKS>"
umask 077
<PYTHON_ABSOLUTE_PATH> -B -c '
import json, re, sys
path, contract_path, bundle_sha256, binding_version, passed = sys.argv[1:]
names = ("sudo_policy", "sshd_policy", "credential_owner",
         "authorized_peer", "wrong_uid_rejected", "container_peer_rejected")
passed = {name for name in passed.split(",") if name}
assert passed <= set(names), sorted(passed - set(names))
assert re.fullmatch(r"[0-9a-f]{64}", bundle_sha256) and int(binding_version) >= 1
contract = json.load(open(contract_path, encoding="utf-8"))
receipt = {
    "schema": 1,
    "environment": contract["environment"],
    "project": contract["project"],
    "bundle_sha256": bundle_sha256,
    "binding_version": int(binding_version),
    "checks": {name: name in passed for name in names},
}
with open(path, "w", encoding="utf-8") as stream:
    json.dump(receipt, stream, ensure_ascii=False, sort_keys=True, indent=2)
    stream.write("\n")
print(json.dumps({"ok": True, "false_checks": sorted(set(names) - passed)}))
' "<CONFIG_ROOT>/deployment-installation.json" "<HOST_CONTRACT_PATH>" \
  "${BUNDLE_SHA256}" "${BINDING_VERSION}" "${PASSED_CHECKS}"
chown root:root "<CONFIG_ROOT>/deployment-installation.json"
chmod 0600 "<CONFIG_ROOT>/deployment-installation.json"
stat -c '%n %U:%G %a' "<CONFIG_ROOT>" "<CONFIG_ROOT>/deployment-installation.json"
```

期望：输出 `{"ok": true, "false_checks": [...]}`，`false_checks` 列出的就是还没做完的核对项——非空时收据存在但不可部署，补做后以 root 把对应项改成 `true`（保持 `0600`）；文件 `root:root 600`；`<CONFIG_ROOT>` 为 `root:root` 且无组 / 其他写权限（拉取代理刷新收据时会核对这一点，不符即拒绝写回）。`environment` / `project` 直接取自 `<HOST_CONTRACT_PATH>`，不手抄。

此后的维护分工：`bundle_sha256` 由拉取代理在每次装新包时刷新（旧收据逐字节备份为同目录 `deployment-installation.json.prev`，再以 `0600` 原子替换），人不再改它；`checks` 与 `binding_version` 由人维护——换绑定版本、重做或撤销某项核对时以 root 改收据。拉取代理发现收据缺失、不是 `0600`、字段集合不符、环境 / 项目不符、六项不全 `true` 或 `binding_version` 不是正整数时记 `installation_receipt_unusable`、不 plan，见[拉取代理 §四 / §十](https://github.com/Moshuiwang/lingxi/blob/main/deploy/%E6%8B%89%E5%8F%96%E4%BB%A3%E7%90%86.md)。

## 四、回退

回退按「三、受限通道安装」逆顺序执行，每步回读后再继续；不动数据库、持久卷、业务 env、旧控制包、旧镜像或业务状态账。

1. 确认账号、home 和 relay 目录只属于本次通道后删除：

   ```bash
   getent passwd "<RESTRICTED_RELAY_ACCOUNT>"
   userdel -r "<RESTRICTED_RELAY_ACCOUNT>"
   ! getent passwd "<RESTRICTED_RELAY_ACCOUNT>"
   ```

   账号仍能读回或目标不明确就停，不重复 `userdel`。

2. 移除本次 `Match` 块和授权行，保留其他 SSH 配置：

   ```bash
   rm -f -- "<SSHD_DROPIN>"
   ! test -e "<SSHD_DROPIN>"
   sshd -t
   systemctl reload ssh
   systemctl is-active --quiet ssh
   ```

   `sshd -t` 失败时不 reload；共享授权文件只移除本次行，不清空文件。

3. 确认 scheduler 已停止使用且路径已核对，再删 socket 目录：

   ```bash
   test "$(find "<SOCKET_DIRECTORY>" -maxdepth 1 -type s -name admin.sock | wc -l)" -eq 0
   rmdir -- "<SOCKET_DIRECTORY>"
   ! test -e "<SOCKET_DIRECTORY>"
   ```

   目录非空、仍有监听或路径不符就停，不递归扩大范围。

4. 删除 relay 当前引用和收据目录：

   ```bash
   rm -f -- "<RELAY_ROOT>/current"
   rm -rf -- "<RELAY_INSTALLATION_DIRECTORY>"
   ! test -e "<RELAY_ROOT>/current"
   ! test -e "<RELAY_INSTALLATION_DIRECTORY>"
   ```

   不得把 `<RELAY_ROOT>` 作为递归删除目标。

5. 最后删除绑定文件，不删除其他非秘密配置：

   ```bash
   rm -f -- "<CONFIG_ROOT>/innertest/binding.json"
   ! test -e "<CONFIG_ROOT>/innertest/binding.json"
   stat -c '%n %U:%G %a' "<CONFIG_ROOT>/innertest"
   ```

6. 同时删除三.9 的安装收据及其备份——通道拆掉后收据里的六项核对已不成立，留着会让拉取代理继续按旧结论生成计划：

   ```bash
   rm -f -- "<CONFIG_ROOT>/deployment-installation.json" "<CONFIG_ROOT>/deployment-installation.json.prev"
   ! test -e "<CONFIG_ROOT>/deployment-installation.json"
   ```

   此后拉取代理每轮记 `installation_receipt_unusable` 并只告警一次，这是预期状态；重新安装通道并按三.9 重写收据后自动恢复。

回退后数据库仍是动态名单或业务 env 仍引用内测 scope，不能记为通道已恢复；先停下请产品负责人确认处置范围。

## 五、历史恢复包规则

原始正式标签没有新发布清单时，只在恢复计划内登记 `schema="historical"` 的原始事实：原标签、仓库、提交、树、四个镜像 digest 和迁移头。不得伪造维护分支、构建编号、验收清单或新格式 Release 附件；普通新 `apply` 不接受它。

历史恢复必须建立独立 recovery plan 和独立批准，不能复用普通 apply 的批准；恢复目标、旧四镜像、旧配置、控制工具包、发布证据、兼容性证据、入口停用收据和原部署 ID 绑定在同一记录中。恢复前停用 forced-command 入口、结束 relay 会话并排空；历史版本没有 UDS handler 时不让 relay 指向不存在的 handler，也不回落任意 shell。恢复命令必须带 `--profile mvp`，回读 scheduler、gateway、worker-queue 三个常驻服务，不能只看 scheduler 已启动。

当新格式阶段、动态名单或后处理状态已经存在，而历史程序没有兼容消费者或没有独立兼容证明时，不能恢复旧版；不能通过删除阶段表、改回旧环境变量或清空卷来伪造兼容。迁移不兼容、四镜像或迁移头无法逐一核对、历史来源证据缺失、恢复批准未到、入口停用收据缺失、发现明确撤销、或发现外部平台规则未验证时，都必须停下请产品负责人决定，不把猜测写成恢复资格。

## 六、与拉取代理的接口

拉取代理安装在每台主机，只出网、不开入站，读取 `host-contract.json` 和本文安装出的版本化控制包、配置根、relay 根、状态目录及 socket 目录；它看到符合本机环境的 Release 后先核对清单与摘要，按 Release 生成 `approval.json`（产品负责人点 Release Promotion，**提升即放行**），再调用控制包内 `deploy/lingxi_deploy.py`。代理的细节见 [`deploy/拉取代理.md`](https://github.com/Moshuiwang/lingxi/blob/main/deploy/%E6%8B%89%E5%8F%96%E4%BB%A3%E7%90%86.md)，该文由另一张卡产出。

**「提升即放行」的边界**：提升 = 人工授权完成，不是部署完成。生效前提有三条：该正式版在 main 里已有验收记录且清单与已验收候选一致（由 `release_manifest.py resolve --environment production` 判定，代理不复制这一判断）；生产主机的拉取代理 timer 在跑，每 5 分钟拉取一次；目标不低于该主机已部署的最高版本（否则记 `downgrade_refused`，不回退）。正式版不合格时代理不部署：选中它的第一轮就记 `unknown` 并立即告警（去重键 `unknown + 该 tag`，之后每轮不重复），修正后自动继续。提升后最多 5 分 30 秒，`journalctl -u lingxi-release-pull.service` 会出现 `结果码=selected` 且 tag 为该正式版的行；部署完成看状态账 `status` 的 `last_result=verified`、`promotion_run_id`，或管理群的成功通知；一轮上限一小时。结果码与人的动作见拉取代理文档 §六 / §十。
