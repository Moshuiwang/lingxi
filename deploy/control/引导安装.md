# 控制包引导安装

本文是预发与生产共用的安装 runbook。执行须绑定 Ops 工作项、环境、固定 Release、窗口和授权终点；本文不授执行权。

## 零、适用与不做

预发和生产主机拉取链路调用同一个控制包内的 `deploy/lingxi_deploy.py`，只在版本选择和环境参数上不同。预发可接受候选版，生产只接受有 main 验收记录的正式版。Release Promotion 即放行；`approval.json` 由拉取代理按 Release 生成。

本文只写控制包、受限 SSH、socket 绑定和恢复材料，不写真实主机名、账号名、公钥或受控路径；`<占位符>` 由获批 Ops 工作项提供。本文不替代 G-1、G-2、G-3 授权，不执行主机变更，不迁移数据库、持久卷、业务 env 或凭据。

回读通过成功；缺料、UID 映射或日志证据记等待；摘要、权限、策略或拒绝实测不符就停。未验证值不入账。

## 一、前提核对

### 1. 运行条件

部署主体必须是 root；受限 relay 账号不加入 sudo 或 Docker 组。控制包只要求 Linux、Python 3.11 以上、Docker 和 Compose 2.24 以上，宿主不装依赖、不现场构建。

```bash
python3 --version
docker version --format '{{.Server.Version}}'
docker compose version --short
test "$(id -u)" -eq 0
test -n "${LINGXI_GH_COMMAND:-}"
test -x "$LINGXI_GH_COMMAND"
```

期望：Python 输出 `3.11` 或更高版本；Compose 输出 `2.24.0` 或更高版本；当前 UID 为 `0`；`LINGXI_GH_COMMAND` 是绝对路径且可执行。`LINGXI_GH_COMMAND` 只供 `release_manifest.py resolve` 只读回读 Release 清单，不回落个人 `gh` 登录。任何一项不符就停，不安装、不改 SSH。

### 2. 目录规划

以下是形状和权限约定，不是实际主机值。root 先建父目录，再把实际值写入 `host-contract.json`；受限账号不能写入。

| 项目 | 路径占位 | 属主 | 权限 | 谁建 |
| --- | --- | --- | --- | --- |
| `deploy_root` | `<DEPLOY_ROOT>` | `root:root` | `0750` | root / Ops |
| `config_root` | `<CONFIG_ROOT>` | `root:root` | `0750` | root / Ops |
| `bundle_root` | `<BUNDLE_ROOT>` | `root:root` | `0755` | root / Ops |
| `relay_root` | `<RELAY_ROOT>` | `root:root` | `0755` | root / Ops |
| `lock_path` | `<DEPLOY_ROOT>/host.lock` | `root:root` | `0600` | 部署器首次加锁时 |
| 状态目录 | `<STATE_DIRECTORY>` | `root:root` | `0700` | 部署器 / Ops |
| socket 目录 | `<SOCKET_DIRECTORY>` | `<SOCKET_OWNER>:<SOCKET_GROUP>` 或 `root:<SOCKET_GROUP>` | `0750` | root / Ops |

```bash
install -d -o root -g root -m 0750 "<DEPLOY_ROOT>"
install -d -o root -g root -m 0750 "<CONFIG_ROOT>"
install -d -o root -g root -m 0755 "<BUNDLE_ROOT>"
install -d -o root -g root -m 0755 "<RELAY_ROOT>"
install -d -o root -g root -m 0700 "<STATE_DIRECTORY>"
install -d -o <SOCKET_OWNER> -g <SOCKET_GROUP> -m 0750 "<SOCKET_DIRECTORY>"
stat -c '%n %U:%G %a' "<DEPLOY_ROOT>" "<CONFIG_ROOT>" "<BUNDLE_ROOT>" "<RELAY_ROOT>" "<STATE_DIRECTORY>" "<SOCKET_DIRECTORY>"
```

期望每行属主、权限与上表一致；锁文件创建后为 `root:root 600`。私有 `.env.*`、计划、批准和状态账不放进控制包；私有文件为 `0600`，状态目录为 `0700`、文件为 `0600`。不符就停，不用 `chmod -R` 覆盖未知内容。

## 二、控制包引导安装

### 1. 取 Release 附件并核对索引

在 `<STAGING_DIRECTORY>` 建立本次固定 Release 的暂存目录，只下载 `lingxi-control.tar`、`control-index.json` 和 Release manifest；不从浮动 main 取脚本。

```bash
install -d -o root -g root -m 0700 "<STAGING_DIRECTORY>"
"$LINGXI_GH_COMMAND" release download "<RELEASE_TAG>" \
  --repo Moshuiwang/lingxi \
  --pattern lingxi-control.tar \
  --pattern control-index.json \
  --dir "<STAGING_DIRECTORY>"
tar -xOf "<STAGING_DIRECTORY>/lingxi-control.tar" control-index.json \
  | cmp -s - "<STAGING_DIRECTORY>/control-index.json"
```

期望下载为本次 Release 的两个附件，`cmp` 退出码为 `0`；`tar -tf` 回读固定集合，摘要以 manifest 的 `control_bundle.sha256` 为准。附件缺失、索引不一致或有额外成员就停。

### 2. 用固定版本选择器得到摘要

使用已审查控制包中的 `scripts/ci/release_manifest.py`，明确环境；生产用 `production`，不得用候选版。

```bash
python3 -B "<FIXED_RELEASE_TOOL_ROOT>/scripts/ci/release_manifest.py" resolve \
  --repository Moshuiwang/lingxi \
  --tag "<RELEASE_TAG>" \
  --environment stage \
  --output "<STAGING_DIRECTORY>/images.env" \
  --manifest-output "<STAGING_DIRECTORY>/release-manifest.json"
sha256sum "<STAGING_DIRECTORY>/lingxi-control.tar" \
  "<STAGING_DIRECTORY>/control-index.json"
```

期望输出 `部署选择已核对，只输出不含凭据的镜像配置；未部署`，manifest 含四镜像摘要、迁移头、来源提交、树摘要和控制包摘要；生产还须有 main 验收记录。输出、摘要或执行行为不符就停；`resolve` 不运行 Compose。

### 3. 校验、安装只读版本并切换当前引用

`control_bundle.py` 的 `verify` 先完整校验 tar、索引、成员权限和每个文件摘要；`install` 再把它写入 `<BUNDLE_ROOT>/<control_bundle.sha256>` 版本目录；`verify_install` 回读目录；`activate` 最后才原子切换 `<BUNDLE_ROOT>/current`。以下命令使用已固定工具，不调用工作树的浮动文件：

```bash
PYTHONPATH="<FIXED_CONTROL_ROOT>/deploy" python3 -B -c '
import json
from pathlib import Path
import control_bundle

staging = Path("<STAGING_DIRECTORY>")
manifest = json.loads((staging / "release-manifest.json").read_text())
expected = manifest["control_bundle"]
package = staging / "lingxi-control.tar"
root = Path("<BUNDLE_ROOT>")
control_bundle.verify(package, expected)
control_bundle.install(package, expected, root)
control_bundle.verify_install(root / expected["sha256"], expected)
control_bundle.activate(root, expected)
control_bundle.verify_install(root / expected["sha256"], expected)
print(json.dumps({"ok": True, "bundle_sha256": expected["sha256"], "current": str(root / "current")}))
'
readlink "<BUNDLE_ROOT>/current"
stat -c '%n %U:%G %a' "<BUNDLE_ROOT>/current" "<BUNDLE_ROOT>/<CONTROL_BUNDLE_SHA256>"
```

期望机读结果含 `"ok": true`，`current` 指向本次摘要目录；版本目录不可写，目录为 `0555`，可执行文件为 `0555`，其他文件和索引为 `0444`。两次 `verify_install` 都通过才算完成。任一摘要、集合、权限或引用不符就停，保留旧 `current`。

## 三、受限通道安装

模板 `<占位符>` 只能由产品负责人或本次 Ops 工作项提供；公钥不写入本仓库、日志、样例或提交正文。

### 1. 专用系统账号

账号已存在且不符时停，不把普通账号改造成受限账号；创建使用系统账号、`nologin` shell，home 与 `.ssh` 由 root 管理。

```bash
useradd --system --user-group --home-dir "<RELAY_HOME>" \
  --create-home --shell /usr/sbin/nologin "<RESTRICTED_RELAY_ACCOUNT>"
install -d -o root -g root -m 0755 "<RELAY_HOME>"
install -d -o root -g root -m 0755 "<RELAY_HOME>/.ssh"
id "<RESTRICTED_RELAY_ACCOUNT>"
getent passwd "<RESTRICTED_RELAY_ACCOUNT>"
id -nG "<RESTRICTED_RELAY_ACCOUNT>"
stat -c '%n %U:%G %a' "<RELAY_HOME>" "<RELAY_HOME>/.ssh"
```

期望 shell 是 `/usr/sbin/nologin`，账号不在 `sudo`、`docker`、`wheel` 等特权组，home 与 `.ssh` 是 `root:root` 且无组/其他写权限。现场 UID/GID 记入自检清单，不使用样例值。

### 2. `sshd` 的 `Match` 块

模板见 [`sshd_config.example`](sshd_config.example)。复制到受控 drop-in，只替换账号占位符；块内保留公钥认证、禁密码、禁转发、禁 TTY、禁用户配置和 `PermitUserRC no`。

```bash
install -o root -g root -m 0644 \
  "<CONTROL_ROOT>/deploy/control/sshd_config.example" "<SSHD_DROPIN>"
grep -Fq "Match User <RESTRICTED_RELAY_ACCOUNT>" "<SSHD_DROPIN>" && exit 1
sshd -t
systemctl reload ssh
systemctl is-active --quiet ssh
```

期望 `sshd -t` 无输出且退出码为 `0`，reload 成功且服务 active。语法、reload 或占位符检查不符就停，不在语法未通过时 reload；回退同样先 `sshd -t`。

### 3. forced-command 密钥

模板见 [`authorized_keys.example`](authorized_keys.example)。产品负责人外部给出个人公钥；执行者只替换公钥、Python 和冻结 relay 的绝对路径。`restrict,no-user-rc`、`command="... -I -S ..."` 必须保留，不追加 shell、SFTP 或任意远程命令入口。

```bash
install -o root -g root -m 0644 \
  "<CONTROL_ROOT>/deploy/control/authorized_keys.example" "<AUTHORIZED_KEYS>"
test "$(wc -l < "<AUTHORIZED_KEYS>")" -eq 1
grep -Fq 'restrict,no-user-rc,' "<AUTHORIZED_KEYS>"
grep -Fq 'command="<PYTHON_ABSOLUTE_PATH> -I -S <FROZEN_RELAY_ABSOLUTE_PATH>"' "<AUTHORIZED_KEYS>" && exit 1
stat -c '%n %U:%G %a' "<AUTHORIZED_KEYS>"
```

期望文件只有一行、root 所有、权限 `0644`，且含 `restrict,`、`no-user-rc`、固定命令和 `ssh-ed25519` 前缀。没有外部给定公钥时停，不自行生成、不把样例占位公钥当授权。

### 4. socket 目录、权限和容器 UID 映射

`contract.json` 把目录 `488` 固定为 `0750`，socket `432` 固定为 `0660`，路径固定为 `/run/lingxi-innertest/admin.sock`。目录由 root 建立并设 `socket_gid`，socket 由 scheduler 建立。

```bash
chown <SOCKET_OWNER_UID>:<SOCKET_GID> "<SOCKET_DIRECTORY>"
chmod 0750 "<SOCKET_DIRECTORY>"
docker inspect --format '{{.Config.User}}' "<SCHEDULER_CONTAINER>"
docker exec "<SCHEDULER_CONTAINER>" id -u
docker exec "<SCHEDULER_CONTAINER>" cat /proc/self/uid_map
stat -c '%n %u:%g %a' "<SOCKET_DIRECTORY>" "<SOCKET_DIRECTORY>/admin.sock"
```

源码结论：基线 `deploy/compose.yaml` 将 scheduler 固定为 `10001:10001`；stage/prod 未改它。部署器把宿主 socket 目录挂到 `/run/lingxi-innertest`，配置目录只读挂到 `/etc/lingxi/innertest`。Compose 未声明现场 user namespace 映射；`/proc/self/uid_map` 由部署器核对，现场值未验证。

期望 scheduler UID 为 `10001`；socket 为 `0660`、组为 `<SOCKET_GID>`、属主为 `<SOCKET_OWNER_UID>`，父目录为 `0750` 且属主为 root 或 socket owner。`<RELAY_UID>` 不得为 `0`、`65534` 或 socket owner；`peer_uid` 是 map 对应结果且不等于 `10001`。映射、权限或 socket 不符就停。

### 5. `binding.json` 与名单导入

字段说明和占位值见 [`examples/binding.json`](examples/binding.json)。字段集合必须完全是 `schema_revision`、`binding_id`、`host_uid`、`peer_uid`、`uid_map_sha256`、`socket_gid`：

| 字段 | 含义 | 安装时判定 |
| --- | --- | --- |
| `schema_revision` | 绑定格式版本 | 固定为 `1` |
| `binding_id` | 数据库绑定和运行配置的唯一标识 | 三处完全相同，不能复用旧值 |
| `host_uid` | 宿主 relay UID | 正整数，不是 `0` 或 `65534`，且不等于 scheduler UID |
| `peer_uid` | map 对应的容器内主体 UID | 由现场 map 计算，不能等于 `10001` |
| `uid_map_sha256` | `/proc/self/uid_map` 内容摘要 | 与容器内只读回读一致 |
| `socket_gid` | socket 组 GID | 正整数，不是 `0` 或 `65534`，与宿主目录和 socket 一致 |

顺序固定：确定 `<BINDING_ID>` → 建 root 所有的 binding 文件 → 在 `public-config.json` 的 `LINGXI_INNERTEST_BINDING_ID` 与 `LINGXI_INNERTEST_SCOPE` 写同一受控值 → 调用既有导入接口。`apply_roster_import(..., binding_id=<BINDING_ID>)` 必须取同值；先用 `plan_roster_import` 得到成员集合和摘要，再用确认摘要单事务导入。当前源码无独立导入命令，本 runbook 不伪造命令行。

```bash
install -o root -g root -m 0644 \
  "<CONTROL_ROOT>/deploy/control/examples/binding.json" \
  "<CONFIG_ROOT>/innertest/binding.json"
grep -Fq '"binding_id": "<BINDING_ID>"' "<CONFIG_ROOT>/innertest/binding.json"
test "<BINDING_ID>" = "<PUBLIC_CONFIG_BINDING_ID>"
stat -c '%n %U:%G %a' "<CONFIG_ROOT>/innertest" "<CONFIG_ROOT>/innertest/binding.json"
```

期望三个位置的 `binding_id` 相同，目录不被受限账号写入，导入回读为数据库模式且摘要相同。任一不符就停，不为凑齐样例直接写数据库。

### 6. `innertest-relay.json` 与冻结副本

字段说明和占位值见 [`examples/innertest-relay.json`](examples/innertest-relay.json)。

| 字段 | 含义 | 安装时判定 |
| --- | --- | --- |
| `schema_revision` | relay 配置版本 | 固定为 `1` |
| `socket_path` | relay 连接的宿主 Unix socket | 绝对路径且与 `contract.json` 及计划一致 |
| `relay_uid` | 受限账号宿主 UID | 不为 `0`、`65534`，不等于 `socket_owner_uid` |
| `socket_owner_uid` | scheduler socket 的宿主属主 UID | 由现场 UID 映射回读，不拿样例值代替 |

冻结副本只能来自控制包内 `scripts/admin/innertest_relay.py`，不能从工作树、main 或受限账号 home 复制。`activate` 调用 `control_bundle.install_relay`，在 `<RELAY_ROOT>/<安装收据摘要>/` 形成 relay、配置和 `installation.json`，再切换 `current`。relay 根目录 root:root、`0755`；普通配置 root:root、`0644`；源码冻结目录/文件为更严的 `0555` / `0444`，不得放宽。

```bash
readlink "<RELAY_ROOT>/current"
stat -c '%n %U:%G %a' \
  "<RELAY_ROOT>/current" \
  "<RELAY_ROOT>/<INSTALLATION_RECEIPT_SHA256>" \
  "<RELAY_ROOT>/<INSTALLATION_RECEIPT_SHA256>/innertest_relay.py" \
  "<RELAY_ROOT>/<INSTALLATION_RECEIPT_SHA256>/innertest-relay.json" \
  "<RELAY_ROOT>/<INSTALLATION_RECEIPT_SHA256>/installation.json"
sha256sum "<RELAY_ROOT>/<INSTALLATION_RECEIPT_SHA256>/innertest_relay.py"
```

`installation.json` 的 `bundle_sha256`、`relay_sha256`、`config_sha256`、`mode` 和 `directory_mode` 必须与计划一致；部署器还核对收据摘要、引用、root 属主、非链接和不可写属性。任一漂移都停并回到固定候选核对。

### 7. 安装自检

按 `scripts/admin/innertest_install_check.py` 的完整清单建立临时非秘密 manifest；它只读检查，不把凭据写入清单：

| 字段 | 内容 |
| --- | --- |
| `schema_revision` | `1` |
| `python` | 冻结 Python 绝对路径 |
| `relay` / `relay_sha256` | 冻结 relay 路径及其 SHA256 |
| `relay_config` | `innertest-relay.json` 路径 |
| `binding` | `binding.json` 路径 |
| `socket_directory` | 宿主 socket 目录 |
| `relay_uid` / `relay_gid` | 受限账号 UID/GID |
| `authorized_keys` | root 管理的授权文件路径 |

```bash
python3 -B "<CONTROL_ROOT>/scripts/admin/innertest_install_check.py" \
  "<INSTALL_CHECK_MANIFEST>"
```

期望 JSON 的 `ok` 字段为 `true`（即 `{"ok": true, ...}`）；结果中的 `manual_required` 仍须逐项完成，尤其是 `sshd_effective_policy`、`credential_owner` 和 `three_peer_connection_probes`。`ok` 为 false、字段缺失、权限不安全、relay 摘要不符或 forced-command 形状不符就停。

### 8. 三路否定实测

这是 G-1 的安装验收，不用成功连接替代。记录三次命令的 UTC 起止时间和同一受限账号，不把公钥、凭据或完整日志正文写进提交；每路都必须非零退出、没有 shell/scp 文件写入，并在 sshd 日志中有对应拒绝行。

```bash
ssh -o BatchMode=yes -o RequestTTY=no \
  "<RESTRICTED_RELAY_ACCOUNT>@<HOST>" bash
scp -q -o BatchMode=yes /dev/null \
  "<RESTRICTED_RELAY_ACCOUNT>@<HOST>:<REMOTE_PATH_PLACEHOLDER>"
ssh -o BatchMode=yes -t \
  "<RESTRICTED_RELAY_ACCOUNT>@<HOST>" bash
journalctl -u ssh --since "<TEST_START_UTC>" --until "<TEST_END_UTC>" \
  -o cat | rg -i 'refused|not allowed|forced|pty|session'
```

判定口径：第一路远程 `bash`、第二路 `scp`、第三路 TTY 请求全部被拒；日志按时间、受限账号和来源主机逐条对应拒绝，不以“连接过”或“relay 进程退出”冒充拒绝。任一路退出码为 `0`、能建立 shell、能上传/写入文件、TTY 获得成功，或日志缺少对应拒绝行，立即停并请产品负责人确认 G-1 受限边界；本地单元测试不替代这三路真实主机实测。

## 四、回退

回退按「三、受限通道安装」逆顺序执行，每步回读后再继续；不动数据库、持久卷、业务 env、旧控制包、旧镜像或业务状态账。

1. 确认账号、home 和 relay 目录只属于本次通道后删除：

   ```bash
   getent passwd "<RESTRICTED_RELAY_ACCOUNT>"
   userdel -r "<RESTRICTED_RELAY_ACCOUNT>"
   ! getent passwd "<RESTRICTED_RELAY_ACCOUNT>"
   ```

   账号仍能读回或目标不明确就停，不重复 `userdel`。

2. 移除本次 `Match` 块和授权行，保留其他 SSH 配置：

   ```bash
   rm -f -- "<SSHD_DROPIN>"
   ! test -e "<SSHD_DROPIN>"
   sshd -t
   systemctl reload ssh
   systemctl is-active --quiet ssh
   ```

   `sshd -t` 失败时不 reload；共享授权文件只移除本次行，不清空文件。

3. 确认 scheduler 已停止使用且路径已核对，再删 socket 目录：

   ```bash
   test "$(find "<SOCKET_DIRECTORY>" -maxdepth 1 -type s -name admin.sock | wc -l)" -eq 0
   rmdir -- "<SOCKET_DIRECTORY>"
   ! test -e "<SOCKET_DIRECTORY>"
   ```

   目录非空、仍有监听或路径不符就停，不递归扩大范围。

4. 删除 relay 当前引用和收据目录：

   ```bash
   rm -f -- "<RELAY_ROOT>/current"
   rm -rf -- "<RELAY_INSTALLATION_DIRECTORY>"
   ! test -e "<RELAY_ROOT>/current"
   ! test -e "<RELAY_INSTALLATION_DIRECTORY>"
   ```

   不得把 `<RELAY_ROOT>` 作为递归删除目标。

5. 最后删除绑定文件，不删除其他非秘密配置：

   ```bash
   rm -f -- "<CONFIG_ROOT>/innertest/binding.json"
   ! test -e "<CONFIG_ROOT>/innertest/binding.json"
   stat -c '%n %U:%G %a' "<CONFIG_ROOT>/innertest"
   ```

回退后数据库仍是动态名单或业务 env 仍引用内测 scope，不能记为通道已恢复；先停下请产品负责人确认处置范围。

## 五、历史恢复包规则

原始正式标签没有新发布清单时，只在恢复计划内登记 `schema="historical"` 的原始事实：原标签、仓库、提交、树、四个镜像 digest 和迁移头。不得伪造维护分支、构建编号、验收清单或新格式 Release 附件；普通新 `apply` 不接受它。

历史恢复必须建立独立 recovery plan 和独立批准，不能复用普通 apply 的批准；恢复目标、旧四镜像、旧配置、控制工具包、发布证据、兼容性证据、入口停用收据和原部署 ID 绑定在同一记录中。恢复前停用 forced-command 入口、结束 relay 会话并排空；历史版本没有 UDS handler 时不让 relay 指向不存在的 handler，也不回落任意 shell。恢复命令必须带 `--profile mvp`，回读 scheduler、gateway、worker-queue 三个常驻服务，不能只看 scheduler 已启动。

当新格式阶段、动态名单或后处理状态已经存在，而历史程序没有兼容消费者或没有独立兼容证明时，不能恢复旧版；不能通过删除阶段表、改回旧环境变量或清空卷来伪造兼容。迁移不兼容、四镜像或迁移头无法逐一核对、历史来源证据缺失、恢复批准未到、入口停用收据缺失、发现明确撤销、或发现外部平台规则未验证时，都必须停下请产品负责人决定，不把猜测写成恢复资格。

## 六、与拉取代理的接口

拉取代理安装在每台主机，只出网、不开入站，读取 `host-contract.json` 和本文安装出的版本化控制包、配置根、relay 根、状态目录及 socket 目录；它看到符合本机环境的 Release 后先核对清单与摘要，按 Release 生成 `approval.json`（产品负责人点 Release Promotion，**提升即放行**），再调用控制包内 `deploy/lingxi_deploy.py`。代理的细节见 [`deploy/拉取代理.md`](https://github.com/Moshuiwang/lingxi/blob/main/deploy/%E6%8B%89%E5%8F%96%E4%BB%A3%E7%90%86.md)，该文由另一张卡产出。
