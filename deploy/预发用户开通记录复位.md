# 预发用户开通记录复位

**预发专用，生产禁用。** 本文件说明 `scripts/ops/stage_user_reset.py`：把一个预发测试账号的开通记录清掉，让他回到「从未开通」，以便重走「扩员 → 欢迎卡 → 首聊开通（存量沿用）→ 问数」的真人旅程；旅程结束账号自然恢复为开通态，不必再动。

## 范围与边界

- 只动两处：**预发库**里该用户的一行 `app_user` 及其派生行；**预发权限发布表**（`LINGXI_PERMISSION_BITABLE_*`）里该用户的一行。
- **不碰正式表**（`LINGXI_STOCK_TOKEN_BITABLE_*`），**不吊销、不解密任何令牌**：令牌库那一行随用户删除，但它只是密文副本；存量令牌本身在正式表里，重走首聊时按存量沿用路径重新采纳。
- 单次只处理一个用户，`--email` 与 `--open-id` 必须同时给出并指向同一条 `app_user`（不一致即拒），没有按邮箱模糊或多用户模式。
- 脚本本身不做任何落盘：备份走标准输出，由宿主重定向到 root 私有目录。

## 生产禁用与硬闸

任何子命令开始前先过两道闸，任一命中即退出码 `2`、零写入：

1. `LINGXI_PERMISSION_BITABLE_APP_TOKEN` 等于 `LINGXI_STOCK_TOKEN_BITABLE_APP_TOKEN`（写入面指向正式表），或后者缺失。生产的两个变量指向同一个 Base，**这道闸在生产必拦**。
2. `LINGXI_DEPLOY_ENVIRONMENT` 自称生产（判定与 `apps/worker/config.py` 的 `PRODUCTION_ENVIRONMENT_VALUES` 同一张表）。scheduler 容器目前不声明这个变量（只有两个 worker 服务声明），所以它是纵深，真正拦生产的是第 1 道。

闸门是挡误操作的，挡不住把预发 env 文件改掉再跑——不要在生产机上执行本文件里的任何命令。

## 删 / 不删清单

引用 `app_user` 的表逐一判定（按 `pg_constraint` 现查；出现清单之外的引用表脚本即拒，不静默级联）：

| 处置 | 表 | 理由 |
| --- | --- | --- |
| 删 | `app_user` | 该用户本行；`feishu_open_id` 唯一约束不是部分索引，软删除挡不住重建 |
| 删 | `publish_outbox` | 发布意图与外部记录标识（外键级联） |
| 删 | `mcp_access_token` | 令牌库该用户行，只是密文副本，不是吊销 |
| 删 | `mcp_sync_check`、`onboarding_completion_notice` | 就绪探针与开通完成通知（外键级联） |
| 删 | `local_permission_override`、`user_memory` | 本地覆盖与用户记忆（外键级联） |
| 删 | `outreach_message` | 欢迎卡的幂等事实，不删就不能重发 |
| 删 | `innertest_check`、`innertest_membership` | 扩员批次的逐人检查结果（级联）、按 `open_id` 的内测资格（无外键，邮箱须与 `--email` 一致） |
| 删 | `conversation`、`task`、`task_delivery_event`、`task_document_delivery_request`、`agent_session_cleanup` | 会话与任务历史：外键 `NO ACTION`，不删就删不掉 `app_user`；从未开通的人没有会话 |
| 置空 | `admin_action_followup.target_user_id` | 外键 `ON DELETE SET NULL`：行保留、只置空；备份记下原值，回退时写回 |
| 不删 | `operation_audit`、`pending_action`、`management_card_context`、`onboarding_failure`、`innertest_batch` / `innertest_batch_item`、`inbound_event`、`admin_registry` / `qa_corpus_reader`、快照与银河副本 | 历史事实；`inbound_event` 是「说过话」的证据，重建用户时由触发器自动采纳 |
| **默认不删、拦停待裁定** | `qa_corpus`、`innertest_content_capture` | 留存内容，但前者外键 `ON DELETE CASCADE`、后者随 `task` 级联，**删用户必随删**。两张表有行时 `plan` 判「被拦」、`apply` 退出 `2`；产品负责人裁定随删后加 `--delete-retained-content` 重新 `plan`（摘要绑定该选项） |

**未覆盖，如实登记**：用户环境目录 `<LINGXI_USER_ENV_ROOT>/<user_id>/`（含该用户 `.mcp.json`）不在脚本范围，复位后成为孤儿目录（无进程再读它，可人工清理）；Agent 会话 JSONL 的清理队列行随用户删除，对应文件不再被清理。另：欢迎卡脚本只对 `provisioning_state=active` 的人发，复位后的账号要等首聊开通完成才收得到欢迎卡。

## 运行姿势（宿主：`biai-stage`，工作副本目录内）

脚本经 stdin 喂进 scheduler 容器执行（镜像里没有 `scripts/`），凭据全部来自容器环境，不进 argv、不进输出。`<邮箱>` / `<open_id>` 用该用户的真实值，`<用户>` 用一个不含 `@` 的短名做目录名。

```bash
COMPOSE=(docker compose --env-file deploy/.env.stage -f deploy/compose.yaml -f deploy/compose.stage.yaml)

# ① 干跑：只读；列每张表将删行数与稳定摘要、预发表该行、summary_sha256 与结论
"${COMPOSE[@]}" exec -T scheduler python -B - plan --email <邮箱> --open-id <open_id> \
  < scripts/ops/stage_user_reset.py

# ② 备份：只读；完整字段（含密文列）走标准输出，宿主落 root 私有 0600 文件
BACKUP_DIR=/root/lingxi-s26-backup/<用户>-reset-$(date -u +%Y%m%dT%H%M%SZ)
sudo install -d -m 0700 "$BACKUP_DIR"
( umask 077; "${COMPOSE[@]}" exec -T scheduler python -B - backup --email <邮箱> --open-id <open_id> \
    < scripts/ops/stage_user_reset.py | sudo tee "$BACKUP_DIR/backup.json" >/dev/null )
sudo chmod 0600 "$BACKUP_DIR/backup.json"; sudo sha256sum "$BACKUP_DIR/backup.json"

# ③ 确认删除：--confirm 必须等于此刻重算的 summary_sha256（干跑之后表变了就会被拒）
"${COMPOSE[@]}" exec -T scheduler python -B - apply --email <邮箱> --open-id <open_id> \
  --confirm <summary_sha256> < scripts/ops/stage_user_reset.py

# ④ 回退：备份 JSON 走标准输入，脚本本体改由 -c 传入（stdin 已被 JSON 占用）
sudo cat "$BACKUP_DIR/backup.json" | "${COMPOSE[@]}" exec -T scheduler \
  python -B -c "$(cat scripts/ops/stage_user_reset.py)" restore --email <邮箱> --open-id <open_id>
```

留存内容表有行时，②③ 都要带 `--delete-retained-content`（裁定之后），且 `--confirm` 取带该选项的 `plan` 摘要。留痕只写备份路径、文件 sha256、各表行数与 `summary_sha256`，不贴正文。

## 判读

- `plan` 的每行摘要 = 主键 + 非敏感列的 sha256 前 16 位；输出不含令牌密文、飞书 secret 与正文。`summary_sha256` 绑定全部将删行、置空清单、预发表记录标识与留存选项——干跑之后任何一行变了，旧摘要即失效。
- `apply` 顺序：同一事务内重算摘要 → 显式置空 `admin_action_followup.target_user_id` → 按外键顺序逐表删（删掉的行数必须等于快照行数）→ 预发表删该行并读回不存在 → 才提交；提交后再回读一遍库与表。任何一步不符都回滚。
- `restore` 顺序：校验备份（结构、`environment=stage`、邮箱 / `open_id` 与命令行一致）→ 库里不得已有该用户 → 单事务按外键倒序插回（主键与时间戳原样；`app_user` 的首次 / 最近入站时间会被触发器按 `inbound_event` 现值再取一次最早 / 最晚）→ 预发表按备份七字段重建一行（`record_id` 会变化）并读回七字段一致 → 才提交。
- 退出码：`0` 跑完；`2` 什么都没做（参数、闸门、配置、定位、被拦、目标已存在）；`3` 摘要不符或表已变化，零写；`4` 预发表那一步结果不明（库侧已回滚零写，或已提交但回读不符）——重新 `plan` 看现状再决定，重跑是安全的：库侧空了就只处理表，表行没了就只处理库。

## 证据边界

预发表的删行接口与「读回不存在」形态（HTTP 404 或业务码 1254005）**未经真实调用验证**（守卫的撤回演示未做），首次在预发执行 `apply` 时以脚本输出为准；不符即退出 `4` 且库侧已回滚。库侧删除、回退、闸门与摘要比对有本机一次性真库容器的用例证据（`tests/test_stage_user_reset.py`）。
