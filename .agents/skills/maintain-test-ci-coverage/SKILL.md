# Lingxi Test 与 CI 覆盖归流

把 Test 与 CI 当作代码交付的一部分持续维护。不要因为已有检查变绿，就推断新增代码已被执行或用户入口已经可用。

## 遵守边界

- 先读取根 `AGENTS.md`，再按其路由只读取本次任务所需的产品合同、当前能力、决策、协作约定和 GitHub 工作项。
- 用户要求分析、审查或“仅思考”时保持只读，只输出缺口和建议。
- 用户已授权实现时，若新增行为缺少持续验证，优先在同一 PR 中补测试并接入 CI；不要把必要覆盖静默留给未来。
- 不读取或输出业务凭据，不在普通 PR CI 中调用 MCP、Claude Code + 百炼、飞书、JumpServer 或真实用户入口，也不产生真实消息或交付物。
- CI 通过只表示满足对应合并条件；生产发布和真实用户结果仍按项目规则由受控验收与 Ops 证明。

## 在两个检查点运行

### 实现前

1. 明确本次改动、用户可见成功与失败、权限和数据边界、外部副作用及恢复方式。
2. 检查现有测试入口和 CI 是否会实际执行待改代码。
3. 形成初始归流结论和验证计划，再开始实现。

### PR 收口前

1. 重新核对最终 diff、测试、工作流和实际运行结果。
2. 确认新增代码不是只“存在测试文件”，而是已被本地命令和 GitHub 对应检查实际执行。
3. 评估本次改动是否让现有 CI 的覆盖、运行环境或效率假设失效。
4. 输出最终归流结论；缺少合并关键证据时不得声明任务完成。

## 执行审查

### 1. 确认改动事实

- 核对分支、基线、最终 diff、关联 Issue / PR 和工作区状态。
- 识别新增或变化的模块、入口、依赖、运行时、配置、数据结构、后台任务、测试目录和工作流。
- 不把聊天计划、文件名或旧代码当作实际覆盖证据。

### 2. 映射用户风险

至少检查本次改动是否影响：

- 身份、权限、用户或会话隔离；
- 成功、处理中、等待、失败和人工处理状态；
- 外部平台未确认时不得声称完成；
- 重试、幂等、并发和重复交付；
- 数据迁移、兼容、恢复和回滚；
- 敏感信息、日志和测试产物；
- 用户实际入口与交付结果。

### 3. 区分验证层级

| 层级 | 目的 | 应放入的验证 |
| --- | --- | --- |
| 本地测试 | 让实现者在推送前快速定位问题 | 受影响单元、组件、回归、调试和探索性验证 |
| PR CI | 提供可重复的合并证据 | 所有稳定、无业务副作用且失败应阻止合并的构建、静态检查、关键单元和契约测试 |
| 较慢或受控测试 | 覆盖耗时或受限场景 | 全量回归、性能、兼容性、专用测试环境和只读外部验证 |
| 真实入口验收 | 证明用户实际可用 | 专用测试用户、发布前后真实链路和 Ops 发布后入口验收 |

尽量让本地与 CI 使用同一套仓库命令；本地可运行聚焦子集，CI 在干净环境重新运行合并所需集合。

### 4. 核对实际覆盖

- 找到 CI 的真实入口、测试发现规则和被调用命令。
- 确认新增代码目录、文件命名和测试位置会被发现。
- 确认测试不是被跳过、标记忽略、提前返回或允许失败。
- 核对预期构建产物、测试数量或模块清单没有异常下降。
- 需要 GitHub 证据时，核对本次提交对应的检查和日志；不要复用旧提交的绿灯。

### 5. 检查 CI 是否过旧

出现以下任一变化时，必须明确判断是否扩展或优化 CI：

- 新增或移动代码目录、服务、应用或入口；
- 更换语言、框架、运行时、依赖管理或构建方式；
- 修改测试命令、发现规则、文件命名、过滤条件或跳过策略；
- 引入数据库、队列、缓存、后台任务或数据迁移；
- 引入新的外部适配器、权限边界或真实副作用；
- CI 中测试或产物数量下降，关键步骤被跳过；
- CI 变慢、重复、不稳定或依赖版本过旧；
- 线上或受控验收发现了现有 CI 未捕获的问题。

优化 CI 时保留风险覆盖：优先并行、按风险触发、拆分 PR 与定时测试、删除重复检查和更新环境；不得用静默跳过、允许失败或只追求表面覆盖率换取绿灯。

### 6. 给出唯一归流结论

从以下结论中选择一项：

- **复用**：现有门禁会实际执行新增代码；说明检查名称、测试入口和运行证据。
- **扩展**：现有体系适用，但需要新增测试场景；在同一 PR 中补充并确认被执行。
- **新增**：新模块、运行时或风险没有对应门禁；在同一 PR 中新增测试入口和 CI。
- **优化**：覆盖仍必要，但 CI 的环境、发现、耗时、稳定性或分层需要调整。
- **经批准暂缓**：暂时无法自动化；必须有产品负责人明确批准、关联 Issue、人工验收、负责人和补齐条件。

“没有考虑”“已有 CI 绿色”或“以后再补”都不是有效结论。

## 按任务类型行动

- 实现或修复任务：先建立能暴露问题的回归验证，再做最小实现；按最终归流同步更新测试或 CI，并验证正向与关键负向场景。
- CI 或测试自身变更：证明新门禁能通过正确内容，也能拦截至少一个代表性错误。
- 审查任务：把未覆盖、CI 过旧或证据不足列为发现；未经授权不实施修复。
- 仅文档或纯机械改动：仍给出简短归流结论；若现有门禁确实覆盖，可选择复用。

## 固定输出

使用以下格式，不用测试数量代替用户风险：

```text

- 改动及用户风险：

- PR CI 实际覆盖：

- 较慢或受控测试：
- 真实入口验收：
- 归流结论：复用 / 扩展 / 新增 / 优化 / 经批准暂缓
- 缺失证据与阻塞：
```
