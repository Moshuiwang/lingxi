# Lingxi 产品文档

> 本目录记录不会因为一个 Issue 关闭、一次发布完成或一个人离开而失效的产品与技术事实。它与代码一起版本化，并在推送后直接作为 GitHub 仓库中的正式正文；不要在 Issue、Project 或 Wiki 中维护它的副本。

## 先判断内容该放哪里

用一个问题判断：**这个结论在当前工作单元关闭后，是否仍要约束用户体验、业务规则或团队判断？**

| 内容 | 放置位置 | 何时更新 |
| --- | --- | --- |
| 产品面对谁、承诺什么、绝不做什么、外部平台的边界——**全部规则正文** | [产品合同与外部边界](产品合同与外部边界.md) | 产品承诺或边界改变时 |
| 已实际确认的能力、已依赖但尚未验证的外部能力、尚待实现的清单（只写**现值**，按验收矩阵的产品域分节；带日期的沿革不写在这里） | [当前能力](当前能力.md) | 有可复验的证据确认变化时 |

### 产品合同、决策记录与技术设计不重复正文

规则正文只写在产品合同里。决策记录只回答“为什么这样定”，用「决定要点」一句话概括每项决定，不复制合同的规则细节。技术设计只回答“怎么实现”，引用规则时给出链接和章节名，不复制条文。三处不一致时以产品合同为准。

同一段规则维护在两个文件里，迟早会改一处漏一处，形成两个同等有效但内容不同的版本——这条分工就是为了避免它。

## 文档之间的关系

真实飞书页面验收从[浏览器验收指南](参考证据/浏览器验收.md)进入：包含账号/机器人切换、脚本输入输出、计时、首批用例和测试交接格式；跑过并验证有效的具体 case 沉淀在[浏览器验收案例库](参考证据/浏览器验收案例库.md)，供下次请求直接引用；产品证据等级仍由验证与门禁定义。

```text
GitHub Issue：提出问题、讨论、实施、验收
        │
        ├─ 关闭前提炼仍有效的结论
        ▼
仓库产品文档：合同 / 当前能力 / 决策记录
        │
        └─ 推送到 GitHub 后，成为可浏览的正式版本
```

Issue 通常是工作历史，不是长期正文；关闭 Issue 不会删除它，但也不应要求后来的人从已关闭讨论中推断现行规则。仓库文档仍是“现在应当怎样理解产品”的唯一入口。

## Issue 的关闭与回写

关闭 Issue 前，负责人逐项确认：

1. 是否改变了产品合同、当前能力或一项长期决策？若是，先更新相应仓库文档并在 Issue 中链接提交或 PR。
2. 若没有长期结论，在 Issue 中明确写“无需回写”的原因，例如：实验被否决、缺陷未改变既定规则、实现细节不影响用户承诺。
3. 在 Issue 中留下完成标准的验证结果、未完成项和风险；长期 Trace 的进度与状态以 `docs/traces/` 中实际存在的执行文件为正文。

不要把 Issue 正文复制到文档。文档只保留稳定结论；Issue 保留当时的背景、方案、讨论和证据链接。

## 新建或修改长期文档的最低要求

- 说明它回答的长期问题、适用范围和不适用范围。
- 在开头写状态或最后核对日期；事实未经验证时不得写成已具备能力。
- 链接产生该结论的 Issue、PR 或脱敏证据；链接用于追溯，正文不依赖读者打开历史才能理解。
- 后续结论取代旧结论时，更新原文或在决策记录中标明“已替代”，不要留下两个同等有效的版本。
