# Lingxi 产品文档

> 本目录记录不会因为一个 Issue 关闭、一次发布完成或一个人离开而失效的产品事实。它与代码一起版本化，并在推送后直接作为 GitHub 仓库中的正式正文；不要在 Issue、Project 或 Wiki 中维护它的副本。

## 先判断内容该放哪里

用一个问题判断：**这个结论在当前工作单元关闭后，是否仍要约束用户体验、业务规则或团队判断？**

| 内容 | 放置位置 | 何时更新 |
| --- | --- | --- |
| 产品面对谁、承诺什么、绝不做什么、外部平台的边界——**全部规则正文** | [产品合同与外部边界](产品合同与外部边界.md) | 产品承诺或边界改变时 |
| 已实际确认的能力、已依赖但尚未验证的外部能力、尚待实现的清单 | [当前能力](当前能力.md) | 有可复验的证据确认变化时 |
| 规则**为什么**定成这样、否决了哪些选择、何时需要重新评估 | [决策记录](决策记录/README.md) | 决策被接受、替代或撤销时 |
| 用什么架构、接口和数据结构**实现**合同里的规则 | [技术设计](技术设计/README.md) | 实现方案改变时 |
| 跨设备研发、固定环境名称、真实验收、生产交接与 GitHub 写入规范（TO PM 模块与代码审查规范在根目录 `AGENTS.md`） | [协作约定](协作约定.md) | 研发环境、责任边界、发布门禁或 GitHub 工作规范改变时 |
| 可复用的外部平台事实、测试方法或脱敏证据 | `docs/参考证据/` | 仅在证据仍长期有用且已脱离一次性讨论时 |
| 需求、缺陷、研究、方案比较、待决策、实施任务、验收过程和进度 | GitHub Issue / Project | 工作进行期间，完成后关闭 |
| 代码改动、审查意见和一次性验证细节 | GitHub Pull Request | 实现与审查期间 |

关联组织的唯一受控验证结论见[飞书关联组织用户身份受控验证](参考证据/飞书关联组织用户身份受控验证.md)。它只说明 Bot-Test 测试项目以用户身份可以读取什么，不能替代[产品合同与外部边界](产品合同与外部边界.md)中的开通、权限和成功宣告规则。

旧 BI AI Agent 的产品文档和代码可以用于核对已经实现过的用户管理能力，但不决定 Lingxi 的管理员入口。现行入口以[管理员通过 AI Agent 管理并由本人飞书卡片确认](决策记录/2026-07-26-管理员AI-Agent与飞书确认边界.md)为准：旧审批流、审批群命令和群内操作卡片不属于 Lingxi 的产品规则。

### 产品合同、决策记录与技术设计不重复正文

规则正文只写在产品合同里。决策记录只回答“为什么这样定”，用「决定要点」一句话概括每项决定，不复制合同的规则细节。技术设计只回答“怎么实现”，引用规则时给出链接和章节名，不复制条文。三处不一致时以产品合同为准。

同一段规则维护在两个文件里，迟早会改一处漏一处，形成两个同等有效但内容不同的版本——这条分工就是为了避免它。

## 文档之间的关系

```text
GitHub Issue：提出问题、讨论、实施、验收
        │
        ├─ 关闭前提炼仍有效的结论
        ▼
仓库产品文档：合同 / 当前能力 / 决策记录
        │
        └─ 推送到 GitHub 后，成为可浏览的正式版本
```

Issue 是工作历史，不是长期正文；关闭 Issue 不会删除它，但也不应要求后来的人从已关闭讨论中推断现行规则。仓库文档是“现在应当怎样理解产品”的唯一入口。

## Issue 的关闭与回写

关闭 Issue 前，负责人逐项确认：

1. 是否改变了产品合同、当前能力或一项长期决策？若是，先更新相应仓库文档并在 Issue 中链接提交或 PR。
2. 若没有长期结论，在 Issue 中明确写“无需回写”的原因，例如：实验被否决、缺陷未改变既定规则、实现细节不影响用户承诺。
3. 在 Issue 中留下完成标准的验证结果、未完成项和风险；Project 只反映优先级、负责人和状态。

不要把 Issue 正文复制到文档。文档只保留稳定结论；Issue 保留当时的背景、方案、讨论和证据链接。

## 新建或修改长期文档的最低要求

- 说明它回答的长期问题、适用范围和不适用范围。
- 在开头写状态或最后核对日期；事实未经验证时不得写成已具备能力。
- 链接产生该结论的 Issue、PR 或脱敏证据；链接用于追溯，正文不依赖读者打开历史才能理解。
- 后续结论取代旧结论时，更新原文或在决策记录中标明“已替代”，不要留下两个同等有效的版本。
