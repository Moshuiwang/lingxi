## 二、合同条款覆盖清单

维护机器可读映射：`产品合同条款 → 验收断言编号 → 测试用例`。CI 目标检查三条：每条已认领断言至少一个测试用例、没有引用不存在的断言编号、已验证断言确实在声明层级执行过——**这是目标形态，当前门禁只执行**下面[清单本体与门禁实际检查的三条](#清单本体与门禁实际检查的三条)所列内容。

**未认领条款不参与强制**，避免绝大多数条款尚无断言时让门禁直接全红；随切片推进，未认领项逐步归零。

#### 清单本体与门禁实际检查的三条

清单就是下表，与第一节「状态」列由同一脚本（`scripts/ci/check_acceptance_matrix.py`）解析，实际检查：

- 产品合同每个章节必须在表里出现且只出现一次；
- 「对应断言」格给出至少一个真实存在的断言编号，或写 `无对应断言`；留空即失败；
- 写 `无对应断言` 必须在「说明」里写明理由。

开头列的另外三项（测试用例绑定）尚未实装，需要测试与断言编号间的机器可读绑定，当前只有自由文本约定，留作后续。清单按章节粒度维护，不逐条抄合同规则，避免形成第二份合同正文；`V-部署-*` 等不对应合同章节的断言不要求出现在此。

**为什么不用覆盖率数字做门禁**：行覆盖率鼓励为达标而写的测试，且对"系统是否会拒绝违规行为"完全不敏感——一个 90% 覆盖率的套件可以一条否定测试都没有。合同条款覆盖清单是可数、可核对、且直接对应产品承诺的指标。
