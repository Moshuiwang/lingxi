# 产品验收矩阵

> 状态：现行产品验收矩阵；本文件所在提交进入 `main` 后生效。最后整理：2026-08-09。
>
> 本文只保存产品与部署的 `V-*` 可验证断言、认领状态和产品合同章节映射。证据层级、关口、CI 与受控环境规则看[验证与门禁](验证与门禁.md)；规划者按 GitHub [#147 长期执行计划与 Execution Trace v11](https://github.com/Moshuiwang/lingxi/issues/147) 生成或修订具体 `[tracking]` Execution Trace，实际角色、时点、冻结与修复只看获批 Trace；缺项时退回规划者修订，编排者不得从模板补合同。

实现 Story 只读取并认领与自身范围相关的断言，不需要把整份矩阵加载进每个普通任务。新增或修改产品规则时，必须同步更新对应断言与会变红的检查。

### 开通与匹配

`V-开通-04` 与 `V-开通-11…14` 的**编排半边**由 [Epic D](https://github.com/Moshuiwang/lingxi/issues/160) 的 S-D-02（正式 `OnboardingRunner`）在 L2 认领：状态只前进不回退由 `advance_provisioning_state` 的条件更新承担，终态互斥、确定性失败统一无权限、重试 / 并发 / 重入不重复创建或发布由 `tests/test_onboarding_runner.py` 钉住。**这四条的 L4a 半边（真实 Bot-Test 首次开通）仍未取得**；编排自 2026-08-18 起住在 `lingxi-scheduler`（[决策记录](../决策记录/2026-08-18-首次开通编排住在scheduler.md)），前置配置齐备前该职责**不注册**，首聊事件原样积压在库里不被认领（详见[当前能力](../当前能力.md)）——「已认领」只表示对应 Story 对交付证据负责，不代表首次开通入口已经可用。

`V-开通-01…03/06/09/15…17` 的真实存取与负向结果由 [Issue #89](https://github.com/Moshuiwang/lingxi/issues/89) 认领；`V-开通-10…14` 由其下游 [Issue #65](https://github.com/Moshuiwang/lingxi/issues/65) 认领，必须在 #89 完成并形成证据后再接入 gateway。`V-开通-07/08` 的既有身份组件证据来自已关闭的 #16，但正式入口仍随 #89/#65 复验。这里的“已认领”只表示对应 Story 对交付证据负责；在断言变为“已验证”前，不代表首次开通入口已经可用。

`V-开通-18` 由迟到就绪恢复职责（`lingxi.apps.scheduler.late_readiness_recovery.LateReadinessRecoveryDuty`，与首次开通编排同住 `lingxi-scheduler`，不改动 S-D-02 的 `OnboardingRunner` 自身）在 L2 认领，经外部独立审查（codex）一轮 F1-F4 修复定稿：判定层复用 `core/permission/mcp_readiness.py` 新增的 `ReadinessRecoveryTicker`（分类、探针调用、绑定、落库与审计与既有的阻塞式/tick 式就绪确认同一份实现，不新造判据；候选一律重新探一次，不存在"跳过探针"的分支——F2 修复），周期性回看停在 `mcp_syncing` 且已经判过 `timed_out` 的用户；就绪就在**同一个数据库事务**里把 `provisioning_state` 推进到 `active` 并排一条待发通知（`lingxi.adapters.postgres_late_readiness_recovery.PostgresLateReadinessStore.activate_after_late_readiness`，CAS 带 `expected_permission_version`——F3 修复），通知由独立的持久 outbox（`onboarding_completion_notice`，迁移 `0066`）认领 + 重试直到送达，形状照 `publish_outbox`——F1 修复，堵住了"状态已推进但通知永久丢失"这条路；未就绪（等待中 / 技术失败 / 探针未接线）绝不推进、绝不排任何通知；探针之外的未预期异常会调用 `ReadinessRecoveryTicker.record_processing_failure` 占住调度窗口，避免"毒候选"饿死正常候选，零候选/零待发通知时不记完成审计——F4 修复。以上由 `tests/test_mcp_readiness_machine.py` 的 `ReadinessRecoveryTickerTest`（判定层）、`tests/test_late_readiness_recovery.py`（编排层：F1「active 但永远不告知」不可能、F2「跳过探针」、F3「版本穿透」三条均已变异验红，另有幂等与"毒候选"用例）与 `tests/test_postgres_late_readiness_recovery.py`（候选查询、CAS 版本守卫、通知 outbox 的 claim/complete/purge 的真库形状，F1/F3 均在真实 PostgreSQL 上完成变异验红）钉住。**L4a 半边（真实等待超时后自然恢复）未取得**——本 Story 的验证全部走注入时钟、假探针与受控真库的 L2，不依赖真的等待。「停在 `mcp_syncing` 多久之后应该彻底放弃、转成需要人工介入的终态」未做产品决定：探针/推进这一半按十五分钟一次的节奏重试，直到就绪或账号被停用为止；但实际生效的重试窗口受 `publish_outbox` 内容快照九十天保留期的既有约束（并非本 Story 新引入），超过该窗口候选查询会静默排除——这一选择、含义与"并非无限期"的准确措辞登记在该模块自己的文档字符串「要试到什么时候为止」一节，不在本条断言的验证范围内。候选查询与通知认领均无带过期时间的持久租约（单实例假设下的已知边界，登记在同一模块文档「已知边界」一节，与 #250 同一判据）。

`V-开通-19` 的 L2 半边由 PR-1（Issue #282 机制修复）在真实合入后认领，测试落在 `tests/test_onboarding_runner.py`（编排层「当场收口」，含 `SYNC_TIMEOUT` 不被误收口、只在通知确认送达时才收口两条否定断言）、`tests/test_stalled_provisioning.py`（停摆收口职责的编排层：先通知后收口、`notifier=None` 时不改状态、停机中断、审计不带 open_id、通知退避、过采样不饿死新候选等否定断言）、`tests/test_postgres_stalled_provisioning.py`（候选查询真库，含未超租约/已有 `timed_out`/账号停用/未认领/最新认领被放回时不得退回历史认领五类否定断言，两职责互补一条要求对方候选集合真实非空）、`tests/test_identity_postgres_records.py`（`abort_stalled_provisioning` 与 `_PROVISIONING_ORDER` 收紧的真库 CAS，含目标为 `active`/手滑传参仍不得覆盖 `active`/停用账号/未到中途格四类否定断言）与 `tests/test_scheduler_onboarding_assembly.py`（装配断言 5）。首轮外部独立审查（opus）判 BLOCK 并给出 P2-1/P2-2/P2-3/P2-5 四项阻断修复与 P3-1/P3-2/P3-3/P3-4/P3-5 五项收尾修复，均已落地并复验通过——详见对应源码模块文档字符串与 PR 正文的返工记录。**L4a 半边（真实链路中途死亡 → 45 分钟后被扫到 → 用户收到终态 → 再发一条消息跑通到 `active`）未取得**——本 Story 的验证全部走注入时钟、可控真库与受控 fake 通知的 L2，不依赖真的等待 45 分钟；`docs/当前能力.md` 在 L4a 取得之前不得把它写成「当前能力」。

当前边界只认下面五条；形成这些断言的实现演进见[形成记录](../参考证据/验证与门禁形成记录.md)：

- `V-执行-11` 不保证发现 SDK 事件改名；事件构造由冒烟检查证明，真实触发只能由 L4a 证明。

本层**没有**区分「承载最终业务结果的调用」与「辅助调用」的信息，因此混合回合只能保守记 `UNKNOWN`。代价是真实运行中会出现较多 `UNKNOWN`（例如"先查错一个指标、换一个又查成功"的回合）。这是知情取舍：审计谎报 `OBTAINED` 比过多 `UNKNOWN` 危险得多。执行器切片接入后若能标出哪一次调用回答了用户的问题，可以在保持"不谎报"的前提下把这部分 `UNKNOWN` 收窄。

**单独成组的理由**：`V-会话-` 组约束的是上下文与串行语义，失败形态是"串味 / 并发执行"；本组约束的是事务边界与队列可用性，失败形态是"消息静默丢失 / 话题永久忙碌 / 任务永久滞留"。两者混编会让"哪些断言属于本切片"不可判定。

**本组当前覆盖不到的两件事，登记在案（#57 独立复查）：**

- **已提交的入队所占用的话题，没有回收路径。** `V-队列-02` 只覆盖"抢占后事务回滚"；一个**成功入队**的任务如果永远没有 worker 领取（S4 前半就没有消费者，S11 引入分流后还可能出现"目标版本没有对应 worker"），`conversation.running_task_id` 会一直占着，该话题此后只会回"当前任务仍在处理中"。`reclaim_stale` 只认 `status='running'` 且心跳超时的任务，`queued` 回收不到；`/stop` 只置 `stop_requested`，不释放占用。**因此 gateway 不能单独上线**，且 S11 接分流规则前必须先有 `queued` 的超时治理。
- **长连接中途静默死亡的检测未在真实环境验证。** 官方 SDK 在 `auto_reconnect=False` 下把接收循环的异常抛在一个没人 await 的 task 里，`start()` 永不返回；本批靠轮询 SDK 的私有属性 `_conn`（它在抛之前会被 `_disconnect()` 置回 `None`）来发现掉线。该私有属性一旦改名，行为降级为"没有断线检测"而不是误报重连。真实断线重连属 L4a。

### 权限发布与同步

`V-权限-01/02/03/09/10/11/12` 由 [Issue #156](https://github.com/Moshuiwang/lingxi/issues/156) 的 S-C-01（发布 outbox 与多维表格写读回）与 S-C-02（令牌签发与 MCP 就绪状态机）认领。

**2026-08-17 产品负责人裁定改写了两条断言的措辞**（依据：Trace [#203](https://github.com/Moshuiwang/lingxi/issues/203) 的 G-155 终判评论与同日三项裁定）：

- **`V-权限-06` 由「回读版本比对」改为「探针法」**。当前权限多维表格**没有版本字段**（同日全表回源核对），回读 `permission_version` 与生效范围逐项比对不可行。改写后就绪的唯一依据是用该用户自己的令牌对问数 MCP 真实执行一次 `list_metrics`，可见指标大于零才算就绪。原断言的三处要害一条不少：以目标用户身份发起、明确空结果不算就绪、服务在线与他人可用都不构成当前用户的就绪；新增一条更强的约束——结论**绑定（用户，权限版本）**。正文见[架构设计 6.4](架构设计.md#64-权限发布与-mcp-同步确认)与 `src/lingxi/core/permission/mcp_readiness.py`。
- **`V-权限-11` 由「永不写入 `token_cipher`」改为「新建行必须携带、更新行不清空不覆盖」**。没有 `token_cipher` 的行对问数 MCP 毫无意义——MCP 逐行解密该列并与请求 Bearer 明文等值匹配。凭据边界不但没有放松，反而更明确：令牌**明文与主密钥**不进数据库任何列、不进 outbox、不进日志与告警；进 outbox 与发布表的只有密文。「不覆盖」保护的是**既有令牌**（那 26 行是旧系统签发的，我们不知其明文），因此该列为**空**时补写我方密文属于填补空洞、不属于覆盖——没有这条，一次"新建成功但平台漏写那一列"的重试会走六字段更新并静默收敛成"发布完成"，而那一行对 MCP 永远无效。正文见 `src/lingxi/core/permission/publish_row.py` 与 `publish.py` 的模块文档、迁移 `0065`。

**「密文被改写」这条保证的边界（2026-08-17 编排者裁定，不做代码修复）**：识别改写要靠「这一行是我们建的」这个事实，而它记在 `publish_outbox.created_record_id` 上、**只在同一条发布意图内有效**。因此有两条路径识别不到：新权限版本产生的新意图对「上一版曾建过的行」出身为 `NULL`；以及创建结果不明、我们没拿到记录标识时（行其实建成了）。两者都不做代码修复，理由是：**改写者与旧系统的合法密文在这两条路径上不可区分**——「存量用户令牌归属」在裁定前是一个悬空的产品结（[#203](https://github.com/Moshuiwang/lingxi/issues/203)；产品负责人 2026-08-18 已按裁定 6 定为「硬切窗口统一重签」，见下文 `V-权限-11` 一节），任何猜测方向都可能把一行合法的旧记录打成永久失败；就绪探针是**功能性最终门**，带着错误密文的行永远探不成功，会以十五分钟超时转运维暴露，不产生用户可见的假成功；硬切前 Lingxi 不写正式表、硬切后旧系统停写，"外部改写"因此收窄为人工篡改场景。这两条路径的密文归属判定随存量用户令牌归属决策一并确定。

**`V-权限-07` 由 S-C-03a + S-C-03b 认领**（[Issue #156](https://github.com/Moshuiwang/lingxi/issues/156)，Trace [#203](https://github.com/Moshuiwang/lingxi/issues/203)；措辞按产品负责人 2026-08-18 裁定 5 明确）。三段链路全部在 L2：

- **重算**（S-C-03a）：`lingxi-scheduler` 的每日权限重算职责（`src/lingxi/apps/scheduler/permission_refresh.py`）按当前有效银河批次（`src/lingxi/adapters/postgres_galaxy_snapshot.py`）逐个**已开通**用户重算并排发布意图，权限有变化才推进版本、无变化判 `UNCHANGED`；「严格先花名册、再银河」不靠职责在列表里的位置，而是一条**数据判据**——花名册持久快照的 `captured_at` 不是当天就整轮不跑、不触银河、不排意图，且**不提供旁路开关**。
- **发布与就绪确认**（S-C-03b）：新增的权限发布职责（`src/lingxi/apps/scheduler/permission_publish.py`）每轮驱动 S-C-01 的发布执行器（它此前**没有任何生产调用方**），并对已发布读回一致的每一条按 tick 节奏推进 S-C-02 的就绪探针。就绪确认改用 `ReadinessTicker`（与阻塞式确认**共用同一份**判定、分类、绑定与落库实现，只替换「等待」），状态从 `mcp_sync_check` 重建，因此**一轮调度不会被十五分钟的就绪等待占住**。
- **通知**：就绪探针成功后发「范围已更新」，撤权在发布读回一致后发「暂无可用范围」（裁定 1/2），正文逐字批准并进 `content.toml` 受版本纪律门禁约束。

**通知投递的 at-most-once 残余窗口（二级审查 N2，知情接受）**：就绪终态记录已经落库、通知还没发出去时进程崩溃，这一条通知**永久丢失**（候选集不会再取回它）。不建通知 outbox 是刻意取舍——产品负责人 2026-08-18 裁定 4 要求的是「有限重试 + 审计」，不是 exactly-once；为一条告知型消息再建一张表，代价与收益不成比例。相对地，次序**先记后发**保证的是不会重复打扰用户。窗口大小 = 一次记账与一次发送之间，且发送前的每条异常路径都留有 `permission_notice.failed` 审计。

**刷新链与开通链的十五分钟不是同一个承诺（二级审查 N1 合并项，登记）**：调度停机后，tick 形态会按 offset 逐次补做欠下的探针，其中任何一次成功仍算就绪——即使发生在「发布后十五分钟」之外。合同那条十五分钟约束的是**首次开通**（用户正在等一个开通结论，超时要转运维），那条链在 Epic D 用阻塞形态、节奏由真实 `sleep` 保证。刷新链的用户已经在用 Lingxi，停机恢复后确认成功并告知，好过「因为我们自己停机所以永远不告诉他」。

**单实例假设（二级审查 N10，登记不修）**：本职责按 `lingxi-scheduler` **单副本**设计。同时跑两个实例时两边会各自取到同一批候选、各发一次探针，同一条变化可能被通知两次（`mcp_sync_check` 的 advisory 锁只保证取号不撞）。当前部署编排里 scheduler 是单副本，不做分布式租约。

**`V-权限-08` 认领的是刷新侧那一半**（写法先例：`V-权限-04/05` 的判定半边）。产品负责人 2026-08-18 裁定 3 之后，S-C-03b 交付的是：**权限从有变无 → 保留发布表那一行、把 `permissions` 序列化为空对象、`status` 维持 `approved`、`updated_at` 更新、`token_cipher` 一个字不动**（撤权行只有六个字段，因此在发布层只能走更新路径，**建不出新行**）；随后按裁定 1 在发布读回一致后通知用户。两条刻意的收窄：**在发布链上一点足迹都没有的人跳过**——判据是「既没有 `published` 过，**也没有** `pending`/`publishing` 在途」（`has_publish_footprint`），不为他新建一行空权限；既有 26 行旧系统记录也落这一路——硬切前撤权由旧系统负责。「**在途也算足迹**」这一半是产品负责人 2026-08-18 决策补充 2（留痕见 Trace [#203](https://github.com/Moshuiwang/lingxi/issues/203) 的决策评论）明确的：昨天排的授权意图还堵在 `pending`、今天这个人被撤权时若跳过，等发布面消费积压时**已经被收回的范围**会被写进外部表并触发一条「范围已更新」通知；算进来之后，撤权决定推进版本，旧意图被认领时判 `superseded`（一次外部调用都不发）。另一条收窄是**匹配阶段的失败不算撤权信号**（那是「认不出这个人是谁」，与花名册侧「仅提示、不做任何自动处置」的口径一致）。重复撤权由 `record_decision` 的内容比对判 `UNCHANGED`，不重复写外部表。**「全部角色都未映射」也走这一路**：`aggregate_permission` 判 `no_supported_function`、整体 `granted=False`，与「银河查无此人」「记录不完整」同一个出口——刷新侧因此表现为撤权（有发布足迹则清空 `permissions` 并通知，无足迹则跳过）；这正是 `V-银河-11` 末句「全部未映射时用户级拒绝」在刷新侧的落点，开通侧那一半仍属 Epic D。

**V-审计-03 的残余缺口必须写在这里，不许再声称它是绝对保证。** 产品合同第 109 / 121 行用的是绝对措辞，但实现已被证明做不到绝对——下面两类完整凭据仍会原样进入审计明细：

| 残余缺口 | 为什么不堵 |
|---|---|
| **纯字母、短于 32 字符的裸秘密**出现在错误正文、回执正文或工具名里 | 这三处不经过字段白名单，长度上界是唯一可用的规则，而它认不出纯字母短串。曾经写过"这一类由字段白名单承担"——**那句话是假的闭合**，字段白名单根本不覆盖自由文本 |

白名单字段里的**数字值**同样原样保留，这不是缺口而是设计：字段进白名单意味着已显式批准记录它，epoch 毫秒与雪花 ID 正是排障要看的事实。若某字段可能承载凭据，正确做法是不把它加进白名单。

上述残余缺口是产品负责人知情接受的当前边界，不得由实施方自行放宽。`V-执行-20` 只收紧 worker 出口：不在白名单里的工具名和最终正文会再次脱敏，审计核心的两条缺口仍存在。重新收紧必须改变允许进入审计的内容范围，不能再叠加一条猜凭据的正则；接受与收紧经过见[形成记录](../参考证据/验证与门禁形成记录.md)。

以上九十天断言和单用户删除断言只覆盖正常运行库与在线文件；数据库备份、WAL 归档和用户目录备份按产品决定明确排除，不要求删除编排修改灾备副本。灾备保存、恢复和销毁由公司的灾备与恢复规则另行验收。

### 花名册审计日报

合同「统一用户记录与权限变化」要求 Lingxi **每日比对已开通用户的花名册资料与存档**，变化经受控管理群的审计日报通知管理员人工处理；飞书账号复用换人不做自动拦截，就靠这份日报被发现。全部由 [Issue #52](https://github.com/Moshuiwang/lingxi/issues/52) 认领。

**现行口径以产品负责人 2026-08-08 的 D2 裁定为准**（[Issue #52](https://github.com/Moshuiwang/lingxi/issues/52) 决策登记、[Plan #104 D2](https://github.com/Moshuiwang/lingxi/issues/104#issuecomment-5225625313)）。D2 覆盖了 2026-08-06 的「选项 A + 甲」中的两项：

- **持久快照载体（覆盖「零新表、零迁移」）**：花名册读取要保存**最近一次成功、完整、非空**的快照，跨进程重启与常规发布都还在；源头返回空、读取失败、超时或半轮读取一律**保留上一份**、不覆盖。载体是数据库表（`roster_snapshot` / `roster_snapshot_row`，迁移 `0063_roster_snapshot`）。本节此前登记的「零新表」表述已随之作废，`V-花名册-13` 按新事实改写。
- **展示口径（覆盖「甲」＝全脱敏）**：受控管理群的审计日报**允许**展示姓名 / 工号 / 邮箱原值——不给原值时管理员无法准确定位并处理人员变化。仍不得包含凭据、令牌、认证信息或与处理无关的敏感数据，也仍然没有任何可执行入口。`V-花名册-21/22` 按新口径改写；`V-花名册-08` 保留，但理由从「脱敏承诺的落点」改为**分层**（比对层只判哪个字段变了，取值是渲染层的事）。

**没有被 D2 改动的**：比对基线仍是 `app_user` 上建档时刻存档的三字段（姓名 / 工号 / 邮箱），不是「昨天的快照」——新的持久快照是**花名册这一侧**的读取结果，用于保证比对拿到的花名册值来自一整轮可信读取，不是第二套比对基线；`V-花名册-33`（审计与日志不含花名册字段值）**照旧生效**，日志会流向排障、CI 输出与工单，不在受控管理群这个受信范围里。

**快照的保留期由产品负责人 2026-08-17 裁定**：**始终保留最近一份，豁免九十天规则**；替换即删旧，不积累历史版本；快照因源头长期读不到而超龄时按日报告警提醒、**不自动删除**（`V-花名册-47`，S-B-04 已接线）。

**本节的实现分四个已认领切片**（Trace #203 / Epic B）：S-B-01 交付花名册分页 reader 与四态完整性判定（`V-花名册-37…40`），S-B-02 交付持久快照载体与原子替换 / 空源保旧（`V-花名册-41…46`），S-B-04 交付**每日调度注册与日报接线**——把「读一轮 → 更新或保留快照 → 比对 → 日报」串成一条链、日报渲染按 D2 改造（`V-花名册-21/22`）、快照超龄告警（`V-花名册-47`）与「无可用快照时不比对」（`V-花名册-48`）；真实花名册读取与真实群送达仍属 L4a，未做。

**写侧与通知侧在 [Issue #275](https://github.com/Moshuiwang/lingxi/issues/275) 之后是两个互斥职责**（登记在此，因为它改变了 `V-花名册-29` 的判定面）。`roster_snapshot` 表是首次开通链第二步（`core/identity/onboarding_runner.py::_match`）与每日权限重算的共同数据前提，而"写快照"此前绑在 `RosterAuditDuty` 内部——它的前置里含 `LINGXI_ADMIN_GROUP_CHAT_ID`，一个纯粹服务"日报发到哪个群"的通知配置，于是**没配管理群会让快照永远不写、员工永远开通不了**（2026-08-21 首触冒烟实测坐实：`roster_snapshot` 为 0 行）。拆法：解出只依赖花名册 Base 坐标与令牌供给的 `RosterSnapshotSyncDuty`（只写不发，审计前缀 `roster_snapshot_sync.*`）；`build_loop` **只在 `RosterAuditDuty` 未装配时**才尝试装配它，两者因此互斥——管理群与 Base 坐标都齐全时仍由 `RosterAuditDuty` 一次完成「读→写→比对→发」（零行为变化），"今天到底读了几次花名册"始终唯一，不给一次性 `refresh_token` 的唯一消费者纪律增加分辨负担。断言在 `tests/test_roster_snapshot_sync_duty.py`。

**写侧的当日水位判据（冻结候选审查 2026-08-21 的 F2）**：`RosterSnapshotSyncDuty` 的 `_completed_on` **只在本轮真的换上新快照时才置位**。读取失败 / 空源 / 不完整一律走"保旧"，而 `read_roster_snapshot` 把这些结算成**正常返回值**（不抛异常），因此"写库失败原样上抛、水位不置位"那条既有纪律看不见它们——无条件置位会让一次瞬时读取失败烧掉一整天的快照写入。保旧轮与失败轮都不置位，下一 tick 重试；同日重试的重复写入是安全的（`PostgresRosterSnapshotStore.replace()` 是"同一事务删光旧行 + 整体写入"的整体替换，表里永远只有一份）。**运行期解耦的另一半（F6）**：`RosterAuditDuty.run_once` 现在**先取花名册（含快照写入）、后读比对基线**——基线读的是 `app_user`、只服务日报正文，排在前面会让它的故障把开通链的硬前提一起拖停。

纯函数断言在 `tests/test_roster_audit_diff.py`，渲染在 `tests/test_roster_daily_report.py`，职责与发送适配在 `tests/test_roster_audit_duty.py`，真库与端到端在 `tests/test_roster_audit_postgres.py`；分页 reader 与四态判定在 `tests/test_feishu_roster_reader.py`，快照替换门槛与保旧告警在 `tests/test_roster_snapshot.py`，快照载体的真库断言在 `tests/test_roster_snapshot_postgres.py`。

**本组不覆盖什么。** 真实群通知与真实花名册读取属 L4a，两者都**未验证（证据等级 1）**：`FeishuGroupMessages` 与花名册 reader 的全部断言跑在注入的假传输层上，与 `adapters/feishu_directory.py` 同一姿态；真实读取所需的专用主体凭据自 2026-08-09 起未落盘（Issue #52 的 G-READ 判定，E1-A 授权码被烧事故的直接后果），真实面改依赖后续的 bootstrap 重授权切片。持久快照的**接线**已由 S-B-04 完成（`V-花名册-47/48`）：快照链挂进了每日日报职责，保旧告警事实接到 scheduler 的结构化警告日志，面向管理员的提醒走日报本身——`core/alerting.py` 的状态机只认心跳、任务滞留与发送连续失败三类信号，刻意没有为快照新鲜度新增第四类。**花名册读取所用的短期令牌供给已由 [#215](https://github.com/Moshuiwang/lingxi/issues/215) 接上**（方案 C 主接线，产品负责人 2026-08-18 裁定接受按需消费节奏，留痕见 [#203 决策评论](https://github.com/Moshuiwang/lingxi/issues/203#issuecomment-5321623142) 第 7 项）：凭据轮换职责**仍是一次性 `refresh_token` 的唯一消费者**，它按需消费一次并把派生的短期 `access_token` 放进**进程内**持有者（不落盘、不进日志与审计，重启即空），日报侧按新鲜度取用。消费频率随之从约 5.6 天一次变成按需（令牌寿命约 2 小时，正常一天约 12 次）。**[#276](https://github.com/Moshuiwang/lingxi/issues/276)（产品负责人 2026-08-21 裁定）解除了此前"每 UTC 日至多消费一次"的自设上界**，改为两次消费的最小间隔（默认 5 分钟）与每日消费次数上界（默认 100 次）双重保护；判据仍随凭据落盘、进程内不留第二份账本副本——`refresh_consumed_at`（最近一次消费时刻）与新增的 `refresh_consumed_count`（当日消费计数），均在文件锁内、置位消费标记之前判定。**唯一消费者与频率上界是两件不同的事**：2026-08-08 授权码被烧那次事故的形状是两个客户端抢占同一条通道，不是"换取太频繁"（详见 `core/identity/access_token_supply.py` 模块文档）。因此 `V-花名册-29` 的第四个前置现在只取决于配置：三个环境变量配齐即注册。**这一段全部是 L2 事实**：真实续期返回的短期令牌寿命、真实按需消费节奏与真实日报送达仍属 L4a、未验证。部门比对与账号状态落库由定案排除；账号复用换人的自动拦截由 [#34](https://github.com/Moshuiwang/lingxi/issues/34) 永久排除；群内处置由合同排除；`audit_event` 表属 S9，当前审计走结构化日志。

**`V-花名册-47` 层级栏里的「源码扫描」在 [#215](https://github.com/Moshuiwang/lingxi/issues/215) 才真正兑现**（Epic B 冻结审查登记的 P3 清尾）：此前该栏已经这么写，但「快照载体不得出现任何按时间删除快照的路径」这半句没有任何会变红的检查——超龄告警那一半有行为用例，「不自动删」这一半要证明的是一条路径**不存在**，没有调用点可断言。现由 `tests/test_roster_snapshot.py::SnapshotHasNoTimeBasedDeletionPathTest` 承担：扫 `adapters/postgres_roster_snapshot.py`、`core/identity/roster_snapshot.py` 与所有提到 `roster_snapshot` 的 alembic 迁移，覆盖 SQL 字符串与 `op.add_column` / `op.create_table` 这类 Alembic 调用两种写法，拒绝带时间条件的删除语句、到期时间列与到期触发器，并拦住「时间在 Python 侧算好、SQL 里只剩一条无条件 `DELETE`」的命名形态。两道防空转：扫描器自证用例要求它确实提取到了适配器的 `DELETE` 与 0063 的两张建表语句；`ScannerClassifierTest` 用合成源码把四个分类器逐个钉住（四类违规必红、合法的替换式 `DELETE` 与 `ON DELETE CASCADE` 必绿）。

**它是绊线，不是安全边界，覆盖声明到此为止。** 已登记的盲区写在该测试模块的类文档里（Python 侧先算好 ID 再删、`gc`/`compact` 之类不在词表的命名、`psycopg.sql` 分段组装与动态 `EXECUTE`、`MERGE ... THEN DELETE`、分区 `DETACH`、仓库之外的运维脚本与数据库定时作业），这些仍靠人工审查兜底；反向的保守误红面（`DELETE ... RETURNING captured_at`、与到期无关的触发器、表名被插值因而按 fail closed 处理的语句）按「要求重新解释这条路径」定位，不是「一定有 bug」。交付前按[验证与门禁第八节](验证与门禁.md#八否定测试)在真实文件里种入四种违规样本各验红一次，并另做九次分类器变异（清空时间词表、打坏三个正则、摘掉 Alembic 通道、退回旧 SQL 形状、取消 fail closed、让提取器空扫、载体改名不同步）确认全部变红。

**残留风险登记**（[Issue #52](https://github.com/Moshuiwang/lingxi/issues/52) 决策登记与裁定 C2）：

- **同一处漂移每天重复上报**（产品负责人知情接受）：基线是建档存档而不是昨天的快照，漂移在人工处理前会每天重复出现在日报里。D2 的持久快照**不改变**这一条——它保的是「花名册这一轮读得可不可信」，不是「昨天的比对结论」。
- **跨重启重发一份相同日报**（知情接受，尚未消解）：`V-花名册-31` 只承诺"每个进程实例同一日至多一次"，并把"重发载荷与首次逐字段一致"作为可被用例证明的那一半。持久快照落地**不等于**这条已解决：判重水位仍在进程内存里，跨重启的真幂等要等判重水位也有持久载体（或 `audit_event` 表落地）后另行交付。S-B-04 核对并**放弃了**「拿快照 `captured_at` 当水位」这条捷径：它回答的是"快照哪天换的"，而水位要回答的是"日报哪天发出去的"——发送失败的那一天快照照样已经换成当天的，用它当水位会让重启后认为"今天已经做完"，那一天的日报**永远不会发出去**。用每天至多重发一份相同日报的噪声，换一个整天静默的失败，方向是反的。
- **快照的保留期已裁定，不再是残留**（产品负责人 2026-08-17）：**始终保留最近一份，豁免九十天规则**。快照表因此刻意没有到期时间、不在受限清理函数覆盖范围内——它是每日比对的花名册侧基线，删掉等于让比对失去基线；替换即删旧（唯一约束 + `ON DELETE CASCADE`），库里永远只有一份，不积累历史版本。**那一半已由 S-B-04 交付**：源头长期读不到导致快照超龄时按日报告警提醒管理员、**不自动删**（`V-花名册-47`）；连一份快照都没有时那一天**不比对**、改发告警（`V-花名册-48`）。

**这里的"一日"按 UTC 日切分**（判重水位、日报标题日期与投递去重键三者同源）。对国内使用者的可观察后果是：日报在北京时间每天 08:00 之后的首轮发出，而标题上的日期是 UTC 日期，与管理员的自然日相差 8 小时。是否改用固定业务时区属产品选择，尚待产品负责人裁定，本切片不改行为。

**投递不确定态另有一层保护，但它不是幂等承诺。** 请求已被飞书收下而响应在回程超时时，进程只能重试，而重试就会重复投递；同一天的每一次发送因此携带同一个投递 `uuid` 交服务端去重。平台侧的去重窗口是飞书的属性、**本切片未验证**（真实调用属 L4a），所以矩阵里承诺的是"重试携带同一个 `uuid`"这个代码事实，不是"平台一定不会重复投递"。

## 二、合同条款覆盖清单

维护一份机器可读的映射：`产品合同条款 → 验收断言编号 → 测试用例`。

CI 检查它，但**检查的不是覆盖率百分比，而是**：

- 每条**已认领**的断言至少有一个测试用例；
- 没有引用了不存在断言编号的测试；
- 已标记"已验证"的断言，其测试确实在声明的层级执行过。

**这三条是目标形态，不是当前状态**——截至 2026-08-06 它们都还没实装。门禁现在实际执行的是下面[清单本体与门禁实际检查的三条](#清单本体与门禁实际检查的三条)所列的检查，那一小节同时说明这三条为什么还没做。

**未认领的条款不参与强制**——否则第一个代码 PR 会因为绝大多数条款还没有断言而直接红掉。随着切片推进，未认领项逐步归零，这个数字本身就是实现进度的可信度量。

#### 清单本体与门禁实际检查的三条

清单就是下面这张表，与第一节各断言的「状态」列由同一个脚本（`scripts/ci/check_acceptance_matrix.py`）解析。它现在检查的是：

- **产品合同的每个章节都必须在表里出现，且只出现一次。** 合同新增或改名一节而没有登记，门禁变红——"合同条款无断言覆盖"最常见的形态就是规则先加、断言忘了加。
- **「对应断言」格要么给出至少一个断言编号，要么写 `无对应断言`；留空即失败。** 编号必须在验收矩阵里真实存在，`V-管理-01…18` 这样的区间会逐个展开核对，中间缺号一样红。
- **写 `无对应断言` 必须在「说明」里写清为什么**，不允许静默宣布某节不需要断言。

本节开头列的另外三项（每条已认领断言至少一个测试用例、没有引用不存在编号的测试、已验证断言确实在声明层级跑过）**尚未实装**：它们需要测试与断言编号之间有可靠的机器可读绑定，而当前只有测试文件头的自由文本约定（形如"认领断言：`V-开通-01`"）。本切片不把自由文本当作绑定，留作后续。

清单按**章节**粒度维护，不逐条抄合同规则——把规则复制进清单会形成第二份合同正文并各自漂移；章节内逐条规则的否定断言仍按[验证与门禁](验证与门禁.md#八否定测试)执行。反向不成立：矩阵里有些断言（`V-部署-*` 的多数）约束的是代码与部署，不对应任何合同章节，清单不要求它们出现。

**为什么不用覆盖率数字做门禁**：行覆盖率鼓励为达标而写的测试，且对"系统是否会拒绝违规行为"完全不敏感——一个 90% 覆盖率的套件可以一条否定测试都没有。合同条款覆盖清单是可数、可核对、且直接对应产品承诺的指标。

## 三、部署与迁移断言

部署方案本身在[架构设计](架构设计.md#八部署与发布)里已经定了（单机 Docker Compose、镜像 tag 即冻结版本、切 tag 回滚），**本文不重复，也不新写部署文档**。发布链路由[协作约定](../协作约定.md)规定。

但有一类东西必须现在就约束：**部署对代码的要求**。它们在写第一行代码时就被固化，事后修改要动很多处；而且架构设计里"镜像 tag 就是冻结的版本、回滚等于切 tag 重启"这条，**只有在代码满足下列约束时才成立**。

| # | 可验证断言 | 层级 | 状态 |
|---|---|---|---|
| V-部署-01 | 代码中不存在硬编码的主机名、端口、路径或密钥；全部配置来自环境变量 | L2（模式扫描） | 已认领 |
| V-部署-02 | 除用户环境目录外，进程不在容器内写入任何需要持久化的本地状态 | L2（运行期文件系统监视） | 已认领 |
| V-部署-03 | 进程收到 `SIGTERM` 后停止领取新任务、完成或安全中断在途任务、在超时内退出。**部署约束**：`LINGXI_DELEGATED_CREDENTIAL_PATH` 必须指向**跨部署持久**的宿主机挂载路径（compose 卷/绑定挂载），镜像替换与重启不得丢失——目标是部署对该凭据「零特殊处理」；文件丢失或过期时的保底是重新走一次「四达文档会议助手」授权，该保底流程写入 S11 部署手册（产品负责人 2026-08-05）。`lingxi-scheduler` 的停止宽限期必须大于「续期 HTTP 超时（当前 20 秒）+ 落盘耗时」，否则 SIGKILL 会落在「已向飞书换过新凭据、尚未写回数据库」的窗口里——Docker 默认 10 秒宽限期不满足，S11 编排时须显式加大（PR #48 独立复查发现）。`lingxi-gateway`（#57）同型认领：收到 `SIGTERM` 后停止接收新事件、完成在途事件的落库、在超时内退出，不遗留"抢占了话题但任务没写进去"的中间态——在途事件各自是一个数据库事务，要么整体落库要么整体回滚。**判定必须覆盖"连接空闲、当前没有任何用户消息"这个最常见的状态**：只在收到事件之后才检查停机信号的实现，夜间与周末根本停不下来，只能等编排层 SIGKILL；因此传输层空闲时须定期让出控制权，用例用**只产出空闲心跳**的传输层而不是持续产出事件的传输层（后者恰好是该缺陷唯一能工作的情形，会给出假绿——#57 独立复查实测） | L2（真实进程信号测试） | 已认领 |
| V-部署-04 | 日志输出到 stdout / stderr，不写日志文件、不自行轮转 | L2 | 已认领 |
| V-部署-05 | 每个数据库迁移可前滚；旧版本镜像能在新库结构上正常启动 | L2（真库：迁移后用上一版本代码跑一遍冒烟） | 已认领 |
| V-部署-06 | 镜像构建不依赖构建机的本地状态；同一提交两次构建产出等价镜像 | L2 | 已认领 |
| V-部署-07 | 容器以非 root 运行；仅持有架构设计中说明的能力（`CAP_SETUID` 等） | L2（镜像与 compose 检查） | 已认领 |
| V-部署-08 | 运行时依赖全部在 `pyproject.toml` 声明；**安全边界所依赖的外部组件锁精确版本**（`==`，不用范围），升级前必须重跑对应的受控验证 | L2（配置检查）+ 升级时 L4a | 已认领 |
| V-部署-09 | 门禁跑在 `pyproject.toml` 声明支持的解释器版本上；低于下限即失败，不得靠运行环境碰巧满足 | L2（门禁自检） | 已认领 |
| V-部署-10 | **已安装的制品**（不是 `src/` 目录）能导入全部关键模块，且必须在仓库目录之外校验；新增子目录漏进制品会红 | L2（CI 独立步骤） | 已认领 |
| V-部署-11 | 健康检查不得只证明进程 PID 存活：依赖（数据库）不可达时必须如实变红；主循环停摆（依赖可达但活性文件过期）也必须如实变红。**不新增入站监听端口**——健康检查以 `docker exec` 语义在容器内跑 `python -m lingxi.apps.healthcheck`，与被检查进程共享同一文件系统/网络命名空间 | L2（真库 up/down 负向测试 + 真实文件系统） | 已认领 |
| V-部署-12 | **常驻 queue worker**（`LINGXI_WORKER_MODE=queue`）收到 `SIGTERM` 后：停止 `claim()` 领取新任务；在途任务的 `_monitor` 把这次停机等同用户 `/stop`，在一个 `stop_poll_interval_seconds` 量级的时间内请求 Agent SDK 中断，收口为 `stopped` 终态；超过 `LINGXI_WORKER_SHUTDOWN_TIMEOUT_SECONDS`（默认 45s）仍未收口则不再等待、进程退出，任务保持 `running` 状态等待未来一次心跳超时回收，不丢结果、不重复副作用 | L2（进程内 asyncio 注入 + 真实子进程信号） | 已认领 |
| V-部署-13 | 明确命名的受控部署 profile（`mvp`）能同时启动迁移后的 scheduler、gateway、常驻 queue worker；裸 `docker compose up -d`（不带任何 profile）默认行为不变，仍只启动 scheduler | L2（`docker compose config` 结构核对） | 已认领 |

**`V-部署-13` 证据边界（PR #173 独立复核 P1-2 修复后仍需强调）**：这里的 L2 只验证
`docker compose config` 渲染出来的**结构**（service 名集合、挂载点、`profiles`、
`restart` 策略等）长对了，**不构成"三个服务真的能同时启动起来"的证据**——那
需要真实拉起容器、真实数据库、真实凭据文件，属 `biai-stage` 的 L4a，未随本条
达标。本轮修复关闭的是一个结构核对本来看不见的缺口：`worker-queue` 早先与
一次性 `worker` job 共用同一份 env 文件，而那份文件的示范文本明确写着"不放
数据库连接串"——照抄部署后 `worker-queue` 会因缺 `LINGXI_POSTGRES_DSN` 无限
崩溃重启，`docker compose config` 的结构核对对这类"容器缺必填环境变量"天生
不敏感（它渲染的是空占位 env 文件）。现在 `worker-queue` 有独立一份
`.env.<env>.worker-queue`，`deploy/.env.example` 与
`scripts/ci/check_deploy_contract.py` 的新增检查
（`check_worker_queue_env_example`）确保这份文件的模板确实带着 DSN 示范值；
`worker` 与 `worker-queue` 不再共用 env 文件，恢复"凭据按服务分文件"这条门禁
本该覆盖到的边界。

**V-部署-05 是最容易漏、代价最高的一条。** 回滚策略依赖"旧镜像能在新库上工作"，而这一点只有显式测过才成立——破坏性迁移一旦合并，回滚就从"切 tag"变成"恢复备份"。

新增可自动化的审查要求必须同步形成 `V-*` 断言和会变红的 CI；散文提醒不构成门禁。`V-部署-08/09/10` 的形成经过见[形成记录](../参考证据/验证与门禁形成记录.md)。

### 3.2 迁移机制（Alembic）

由 [Issue #53](https://github.com/Moshuiwang/lingxi/issues/53) 认领。这一组把 `V-部署-05` 的"可前滚"落到具体机制上，并守住引入 Alembic 时**新出现的**几类沉默失败。执行者是 `scripts/ci/check_alembic_revisions.py`（不连数据库）与 `scripts/ci/check_migration_chain.sh`（真库），两者都挂在 `scripts/ci/verify_repository.sh` 上。

| # | 可验证断言 | 层级 | 状态 |
|---|---|---|---|
| V-迁移-01 | 空库上 `alembic upgrade <基线>` 与顶层编号 SQL 按序建库，两者 `pg_dump --schema-only` 归一化后**零差异**（仅排除 `alembic_version` 表及其主键）。约束名、索引名、触发器定义、函数体、部分索引谓词、表达式索引、COMMENT 全部逐字节相同 | L2（真库 + diff） | 已认领 |
| V-迁移-02 | 基线不含 `IF NOT EXISTS` 一类幂等伪装：已按编号 SQL 建成的库上直接 `alembic upgrade` **必须失败**（对象已存在），失败后表结构与数据不变，且不留下 `alembic_version` 表 | L2（真库否定） | 已认领 |
| V-迁移-03 | `alembic upgrade head` 后 `alembic_version` 恰 1 行且等于 head；在 head 上重跑 `upgrade` 是空操作，结构不变 | L2（真库） | 已认领 |
| V-迁移-04 | 迁移工具链不进运行时：`src/` 下不出现 `sqlalchemy` 或 `alembic` 字样，生产进程镜像不装 SQLAlchemy | L2（门禁扫描） | 已认领 |
| V-迁移-05 | `alembic.ini` 不含可用的默认连接串；未设 `LINGXI_MIGRATION_DSN` 时迁移**明确失败**，且不回落到业务的 `LINGXI_POSTGRES_DSN` | L2（配置检查 + 真库否定） | 已认领 |
| V-迁移-06 | 门禁的迁移检查只在一次性 scratch 库上进行并在结束后删除；主测试库全程不被写入（无 `alembic_version`）。迁移与门禁输出不打印连接串 | L2（真库） | 已认领 |
| V-迁移-07 | revision 链恰好 1 个 head、1 个 base，无孤儿 revision；每个 `downgrade()` 要么真正逆转要么显式 `raise`，不存在静默空实现；基线内嵌的编号 SQL 副本与磁盘原文**逐字节**相同，且每个 `migrations/*.sql` 都被覆盖；`migrations/README.md` 记录的 head 与基线 id 与实际链一致 | L2（门禁静态检查） | 已认领 |
| V-迁移-08 | 基线**之上**的每条 revision 真往返：`downgrade` 回上一版的结果与空库直达上一版逐字节相同，再 `upgrade` 回来与往返前逐字节相同 | L2（真库往返） | 已认领 |

**V-迁移-07 补的是本次改造引入的覆盖面缩水。** 改造前的门禁写的是 `for f in migrations/*.sql`，**每个文件都保证被执行**；换成 `alembic upgrade head` 之后这个保证消失了——一条谁都不指向的孤儿 revision 只是安静地不被执行，不报任何错。多 head 时 `upgrade head` 会自己报错，孤儿不会，所以必须显式断言。

**V-迁移-02 是这一组里最容易被"修好"的一条。** 让基线在旧库上跑得通只需要加几个 `IF NOT EXISTS`，看起来还更健壮；代价是把"版本号对不上"这种响亮的错误，换成"迁移记录说做过了、实际什么都没做"这种沉默的错误。旧库的正确接管路径是先 `alembic stamp`，写在 `migrations/README.md`。

> **V-部署-08/09/10 补于 2026-07-29（Issue #29）。** 这三条此前只以散文形式存在于 `AGENTS.md` 的 Code Review Rules（"未来部署可行性"与"Test 与 CI 有效性"），**没有任何断言编号，因此从未被实装**。后果在 Issue #29 上一次性暴露了三处：执行层的只读边界依赖 Agent SDK 与 CLI 的具体事件名，而这个依赖在仓库里没有任何声明；门禁用裸 `python3`，CI 上恰好是 3.12 所以从未暴露，本地 3.9 却能跑出全绿；测试只覆盖 `src/`，新增子目录能不能进制品无人验证。
>
> **教训：要求"审查结论必须说明 X"是一条散文规则，写一段话就能满足；只有给 X 一个断言编号并让它在 CI 里变红，它才会被实装。** 本仓库凡是真正守住的约束（默认拒绝、脱敏、回执归类）都有 `V-` 编号和会变红的用例；凡是只有散文的，都没守住。新增 Code Review Rules 时应同步给出断言编号，否则它只是提醒，不是门禁。

**现在不做**：CD 流水线、发布脚本、Prometheus/Grafana 等持续监控平台、蓝绿或金丝雀发布、跨进程/跨 Worker 聚合观测（需 S9 的 DB 载体）。#92 交付的最小运行告警逻辑与可注入边界、#153 把它装进三个进程 `main()` 并加上健康检查——两者合起来仍只是 L2（真库 + 真实进程/子进程 + 真实文件系统），不等于真实生产告警与健康检查已在 `biai-stage`/`biplus-prod` 验证；这些在有可部署产物与 E4/Ops 受控窗口之前不宣称，且部分已由 `协作约定` 的发布链路覆盖。
