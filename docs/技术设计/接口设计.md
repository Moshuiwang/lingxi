## 一、接口全景与信任边界

| # | 接口 | 方向 | 信任级别 | 承载 |

## 二、通用约定

### 标识符

| 前缀 | 含义 | 示例 |
|---|---|---|
| `usr_` | Lingxi 内部用户标识 | `usr_01HXYZ...` |
| `cnv_` | 对话（私聊主窗口或话题） | `cnv_01HXYZ...` |
| `tsk_` | 任务 | `tsk_01HXYZ...` |
| `pac_` | 待确认操作 | `pac_01HXYZ...` |
| `rev_` | 开通运行异常记录 | `rev_01HXYZ...` |

统一使用 ULID（时间有序、可排序、无需协调）。**飞书侧标识（`open_id` / `user_id` / `union_id` / `chat_id`）永不作为内部主键**，只作为关联字段——它们属于外部系统，语义可能变化。

### 时间

全部使用 `TIMESTAMPTZ`，存储与传输一律 UTC，仅在面向用户的文案里转换为本地时区。

### 错误模型

所有内部接口与管理 MCP 工具返回统一信封：

```json
{
  "ok": false,
  "error": {
    "code": "target_state_changed",
    "message": "目标用户的权限版本已经变化，请重新查询后再操作。",
    "retryable": false
  },
  "trace_id": "01HXYZ..."
}
```

`message` 面向管理员或最终用户，**必须是可直接展示的中文**，不含内部标识、堆栈或表名。`code` 面向程序判断。

统一错误码：

| code | 语义 | 后续动作 |
|---|---|---|
| `not_found` | 目标不存在。**明确的终态，不做相似匹配** | 不重试 |
| `not_authorized` | 当前身份或角色无权 | 不重试 |
| `target_state_changed` | 目标状态或权限版本已变化 | 重新查询后再决定 |
| `action_expired` | 待确认操作已过期 | 不重试 |
| `already_executed` | 已执行，返回既有结果 | 返回首次结果，不重复执行 |
| `target_has_pending_action` | 同一目标已有一条在途（`pending`）待确认操作，`prepare` 被拒绝（迁移 `0068` 部分唯一索引强制，防 ABA 交错） | 先处理（确认或取消）既有那一条，再重新发起 |
| `audit_write_failed` | 审计写入失败，状态未改变 | 调用方可重试 |
| `external_unavailable` | 外部系统暂不可用 | 调用方可重试 |
| `conflict` | 并发冲突 | 调用方按最新状态重试 |
| `LX-QUEUE-001` | 消息已收到，但任务没有成功进入队列 | 用户可稍后重试；同一事件不重复提示 |
| `LX-ONBOARD-001` | 自动开通暂时无法完成，已转交管理员处理，正文带这一次事件的追溯号 | 系统或管理员继续处理；用户也可以稍后重新发送消息重试（2026-08-21 裁定改口，见产品合同） |

**范围说明（Trace #643 IN-13 核实）**：上面这张信封与错误码词表是共享词汇；本 Trace 核实过的四个接口族（送达、权限、清理、管理，详见「八、领域服务接口」8.2–8.5）**没有一处真的构造这个 JSON 对象**——彼此之间用类型化的返回对象（`dataclass`/枚举）传递结果，`code` 列的取值以字段值的身份出现（例如管理族把 `ConfirmResultKind.ALREADY_TERMINAL` 映射成字符串 `already_executed`），不是网络式响应体。这份信封示意留给未来确有 HTTP/MCP 边界的场景（管理 MCP 服务端尚未实现，见「六」）。

### 幂等

飞书入站按 `event_id` 去重（见「三」）。**内部四个接口族的幂等判据并不统一，也不是都由调用方生成一个 `idempotency_key`**（本节此前的泛称已由 Trace #643 IN-13 订正为按族分述）：权限决定靠 `permission_version` 单调递增与内容摘要比对，判的是"这一版权限和上一条仍然有效的意图是否相同"，不是某个调用方传入的键；管理待确认操作靠行状态机（`pending` 是唯一可执行态，命中终态即返回首次结果）与迁移 `0068` 的一条部分唯一索引拦同一目标的第二条在途，同样不是显式键；送达按操作分档，**七个**操作里只有 `NOTICE_SEND` 真的带平台去重键（请求体 `uuid`），其余**六个**（建卡、卡片回复、流式更新、流式关闭、文本兜底、文档写入）完全没有幂等键，只能靠"外发前先占一个预留位、只有服务端明确拒绝才释放"防止自动重投造成重复交付；清理靠到期时间戳与批量条件，已处置的行不再满足条件，重复运行天然收敛到零行，没有调用方传入键这回事。四族各自的完整判据与源码坐标见「八、领域服务接口」8.2–8.5。

### 追踪

每个入站事件生成裸 ULID `trace_id`。任务经精确事件键 LEFT JOIN 读取未过期原号，缺源或坏号保持 null；显示与日志使用持久 `tsk_ULID` 派生的 `T-ULID` 和 `reference_kind=task`，不写回 trace_id。领取、上下文、投递视图同时读取任务原创建时间。每回合用不可变配置绑定 SDK 回调，进程号记为 `worker_run_id`（旧环境变量兼容）；CLI/admin 共用参数化低敏任务投影，原事件和任务分别守各自期限，不新增迁移。

## 三、飞书入站

**3.1 消费的事件**：`im.message.receive_v1`（私聊消息立刻加表情——合同：**任何消息**都加，含未开通用户、忙碌期消息、`/stop`/`/new`）、`card.action.trigger`（卡片按钮，专用组织授权与管理确认）、`im.chat.member.bot.deleted_v1`（移除机器人记审计不自动停用）。

处理次序本身是合同要求，不能重排：

通道级认证 → `event_id` 幂等去重 → 加表情（失败只记审计）→ 查用户状态（未开通只登记意图，业务内容一律丢弃；已停用回复说明；已开通继续）→ 解析命令（`/stop`/`/new`；以 `/` 开头但不被认识的文本直接回绝、不入队，且不受下一步忙碌判定影响——执行层会把 `/` 开头文本解析成系统命令而不是用户文本，Trace #304 批次 5 直修）→ 话题忙碌判定 → `NOTIFY task_queued`。第 1 步是通道级认证而非逐事件验签（`V-接入-10`）；已开通用户第 2–7 步同一事务（`V-队列-01`）；加表情不可回滚，"已受理"回复不得在入队成功前发出（`V-队列-03`）；入队失败发 `LX-QUEUE-001`，其持久幂等事实是设计目标（`V-队列-07`）。

**3.3 卡片回调的校验**：必须校验点击人解析出的 `app_user.id` 等于 `initiated_by`、角色仍有权、`status=='pending'`、未过期、状态版本未变，分别对应 `not_authorized`/`already_executed`/`action_expired`/`target_state_changed`；不通过则不执行，原卡片转不可再操作的终态。

## 四、飞书出站

具体 API 以飞书开放平台文档为准，本文只固化**我们的调用约束**：加表情失败不阻断后续；创建卡片用 CardKit JSON 2.0，只有权威 API 明确受理才记 `platform_received`；流式更新序列号严格递增，首次失败永久切文本兜底；发送文本只发一个经可信输出检查的终态，响应不明记 `uncertain` 不自动重发；正式产物只走 #140/#97 批准路径；多维表格写入结果落 `publish_outbox`，逐字段比对。

**凭据边界**：飞书出站只由 Gateway 或受控交付服务持有机器人凭据，Worker、用户环境中**不存在**任何飞书凭据。Worker 不直接调用飞书，只提交事件到数据库；Gateway 消费事件，`platform_received` 不等于 `user_read`。

## 五、问数 MCP（消费方）

Lingxi 是问数 MCP 的**客户端**。合同规定 Lingxi 不复制其权限过滤、不验收其正确性，只做两件事：把它接给 Agent，以及在开通前确认同步。

**接入方式**：作为 MCP server 注册进 Agent SDK 的 `mcp_servers`；每个用户的连接以**该用户的身份凭据**建立，这是数据范围隔离的实际发生点。

**同步确认判定（探针法，2026-08-17 改写）**：五路互斥结论——**就绪**（该用户令牌 `list_metrics` 成功且指标 > 0）、**等待中**、**技术失败**、**明确无权限**（权限聚合为空，不发探针）、**超时**（十五分钟预算耗尽）。原「回读版本比对」判定已被取代（多维表格无版本字段）；**明确空结果只证明查询没报错，不能证明权限已同步**（`V-权限-06`）；两种执行形态（阻塞式/tick 驱动式，#156 S-C-03b）共享同一套判定。

**结果处理约束**：MCP 返回数据最新时间则展示、未返回则省略；不推断为权限不足；只有明确给出"不存在/延迟/不完整"才向用户说明，由 `execution` 模块做输出检查。

## 七、用户环境的接口

**7.1 交付接口**：用户环境内的交付 Skill 调用本机交付服务（`/run/lingxi/deliver.sock`）。**选 Unix domain socket，不选回环 TCP**：内核 `SO_PEERCRED` 给出调用方真实 uid。请求体里的用户标识不可信，服务端用 `SO_PEERCRED` 映射交付归属（合同列为阻断问题）；`source_path` 须解析后仍在调用方家目录内，拒绝 `..` 与符号链接逃逸。

`authorized` 为 `true` 才代表交付完成。授权未确认时返回 `delivered: false` 与说明，由 Agent 按合同措辞告知用户核对，**不自动重发**。

**7.2 问数 MCP：用户环境 Bearer**（2026-08-17 裁定改写）：本节此前是"本机 MCP 代理"方案，产品负责人裁定取代——worker → 问数 MCP 的逐用户令牌沿用 biai-agent 老路，**把 Bearer 写进用户环境配置**（见[决策记录](../决策记录/2026-08-18-用户环境持有问数MCP令牌.md)与[架构设计 6.9](架构设计.md)）。签发令牌后、排发布意图前写进用户家目录 `.mcp.json`（`440`），幂等、原子写入、日志脱敏，不创建账号或 `chown`。**这一条只放这一个令牌**：其余飞书凭据、MCP 主密钥都不进用户环境。

## 八、领域服务接口

进程内模块边界，列出的是**跨模块调用点**，模块内部结构不在本文约束。

| 接口 | 职责 | 模块 |
|---|---|---|
| `provision` | 写侧建档，按 `feishu_open_id` 幂等，自带事务 | `core/identity` |
| `ensure_conversation`/`should_resume_session` | 解析或创建会话 / 两小时规则判断 | `core/conversation` |
| `claim_conversation`/`discard_stale_agent_session` | 同话题串行的抢占（条件更新）；跨两小时阈值放弃旧会话，不带 `resume` | `core/conversation` |
| `clear_agent_session`/`request_stop` | `/new`/`/stop` | `core/conversation` |
| `enqueue_publish` | 权限发布入队（与业务变更同事务） | `core/permission` 接口；`adapters/postgres_permission_publish.py` 实现 |
| `issue_token` | 签发问数 MCP 令牌，幂等，只落密文 | `core/permission` |
| `confirm` | 探针法同步确认，五路分流，超时内部收口为 `timed_out` | `core/permission` |
| `decide_prepare`/`decide_confirm`/`decide_cancel` | 待确认操作生成、确认（幂等，最多成功一次）、取消 | `core/admin`（`pending_action.py`） |
| `remember_user_memory`/`list_user_memory`/`forget_user_memory`/`clear_user_memory` | 记忆登记/查询/删除/清空（Issue #357，D1 显式登记范围） | `core/conversation`（CRUD 契约，`ports.py`） |
| `render_user_memory_prompt` | 按用户记忆渲染 worker 注入提示词 | `core/user_memory` |
| `record_decision` | 权限决定落库：`permission_version` 推进与发布意图入队同一事务；`audit.record` 在事务提交**之后**调用，见 8.2 | `adapters/postgres_permission_publish_decision.py` |
| `_terminal_receipt` | 投递终态回执裁定：只认"本次终态的有效回执"，见 8.5 | `apps/gateway/delivery.py`；判据在 `core/delivery/ports.py` |
| `run_once`（`ExpiredCarrierRetentionDuty`） | 四个内容载体（`task.prompt`/`inbound_event`/`pending_action`/`queue_failure_notice`）到期脱敏或删除，四面独立事务，见 8.4 | `apps/scheduler/retention.py`（编排）；`adapters/postgres_carrier_retention.py`（落库，迁移 `0089`） |
| `record` | 写审计 | 各消费模块各自声明的 `AuditSink` 协议（无独立 `core/audit` 模块）；结构化日志实现见[代码框架](代码框架.md) |

**约定**：`enqueue_publish` 要求显式传入调用方的连接对象，不传即抛 `TypeError`（`adapters/postgres_permission_publish_decision.py:390`）；`audit.record()` 的方法签名**从不接收**事务对象（全仓 `AuditSink` 协议签名统一是 `record(action, /, **fields)`）。"同一事务"因此不是类型系统强制的，而是调用点把 `audit.record()` 写进 `with connection.transaction()` 块内部实现的一条编排纪律，且这条纪律**只在失败方向成立**——审计抛错才会让已经发生的写入一起回滚，结构化日志不参与 PostgreSQL 的提交/回滚，审计写成功后若提交才失败，日志不会跟着撤销。这条纪律**按接口族落地不同**：从"审计与业务写入同一事务、失败严格回滚"到"审计发生在提交之后、完全不在同一事务内"都有，具体见 8.2–8.5。

**函数名以代码为准**：本表列出的是跨模块调用点的当前实现名，随重构可能漂移；发现与代码不一致时，以调用点的真实签名为准并回来更新本表（2026-08-29 维护批已订正一批漂移，见 Issue #413）。

### 8.1 写侧建档服务（`identity.provision`）

把身份、花名册与银河权限确认后的人写进 `app_user` 的唯一调用面，详细合同见 `src/lingxi/core/identity/provisioning.py`。输出三态：`created`、`already_provisioned`（幂等返回既有档）、`rejected`（零行残留）。**本接口刻意不接收调用方事务对象**，与 `enqueue_publish` 的「必须传入调用方连接对象」相反（`audit.record()` 从来不接收事务对象，不构成对照，见本节上方「约定」段）——建档是编排第一步，挂在调用方事务里会占住连接与行锁。

### 8.2 权限决定的写入与审计（对应 IN-01/IN-02/IN-05）

- **身份**：由编排层触发（每日重算批，或管理员动作确认之后的 `TargetedPermissionRecompute`），不是目标用户本人的会话在写；`core/permission/targeted_recompute.py:174-225`。
- **成功时点**：`app_user.permission_version` 递增与 `publish_outbox` 新意图插入在**同一个** PostgreSQL 事务内提交（`adapters/postgres_permission_publish_decision.py:169-212`，`enqueue_publish(tx=connection)`）。这一步只代表"决定已经落库"，不代表用户此刻已经能查到——问数 MCP 侧真正生效还要等发布执行器与就绪确认（见「五」）。
- **幂等**：不是调用方传入的键，靠内容比对——`_maybe_record_unchanged`（同文件 258-286 行）拿本次权限与该用户**仍然有效**（`pending`/`publishing`/`published`）的上一条意图逐字段比对，相同则只刷新 `permission_checked_at`，不推进版本、不排新意图；本地覆盖来源读取失败一律整体不发布这个人（`LocalOverrideReadError`，`core/permission/decision_chain.py:87-119`），不会把"少了本地补授"的半份结果当正式决定发出去（IN-01）。撤销组的整组收回额外先锁目标用户的 `app_user` 行（`_lock_group_owner`，`adapters/postgres_local_permission.py:649-668`），拦住撤销与"全部"组补齐的交错（IN-02）。
- **事务范围**：`permission_version` 与 `publish_outbox` 同事务（上述）；**审计在事务之外**——`TargetedPermissionRecompute._settle_publish`/`_settle_revocation`（`core/permission/targeted_recompute.py:408-434` 与 `:437-463`）在 `record_decision()` 返回、即事务已提交**之后**才调用 `self._audit.record(...)`，审计写入失败不影响已经提交的权限决定。

### 8.3 待确认操作的事务与审计（对应 IN-09）

- **身份**：管理员本人经飞书私聊点击确认卡触发，`clicker_open_id` 经服务端角色登记表核对仍然有效（`adapters/postgres_pending_action.py:401-431`）。
- **成功时点**：业务写入（如收回一条本地权限）与终态状态更新在**同一个** `with connection.transaction()` 块内提交（`_confirm_locked`，同文件 473-532 行）；对调用方展示的"成功"取**事务内快照** `_committed_terminal_snapshot`（同文件 70-93 行），不依赖提交后再回读——那次回读只用于刷新展示，失败不改变已提交的结论（`_refresh_after_commit`，同文件 433-453 行；这正是 IN-09 修的问题：此前回读故障会被误说成"操作未执行"，管理员据此重复点击）。
- **幂等**：判据是 `pending_action.status`——只有 `pending` 能被消费，重复点击已是终态的卡片得到 `already_executed`（`ConfirmResultKind.ALREADY_TERMINAL`，`core/admin/pending_action.py:280`），返回首次结果、不重放业务动作；同一目标的第二条 `prepare` 靠迁移 `0068` 的一条部分唯一索引在插入阶段直接拒绝（`target_has_pending_action`），不是应用层判重。
- **事务范围**：审计写在业务更新**之前**、与之同一事务（`_finalize_confirm_decision`，`adapters/postgres_pending_action_execution.py:900-912`），审计抛错则整个事务回滚；但"同一事务"只在失败方向成立——结构化日志不参与 PostgreSQL 的提交/回滚，这是模块文档自己的表述（`postgres_pending_action.py:96-103`）。

### 8.4 载体到期清理的独立事务（对应 IN-04）

- **身份**：`apps/scheduler` 常驻职责按连接串执行，不代表任何用户或管理员；`ExpiredCarrierRetentionDuty` 无条件装配（`retention.py:467-492`）。
- **成功时点**：任务问题原文（`task.prompt`）、入站事件、待确认操作、队列失败通知四个内容载体各自独立处置，每一面各开一次 `with connection.transaction()`（`adapters/postgres_carrier_retention.py:142/176/207/235`），一次调用即一次提交，互不等待。
- **幂等**：靠到期时间戳与批量条件（`WHERE ... <= now() ... LIMIT 200`），已处置的行不再满足条件，重复运行天然收敛到零行，没有调用方传入的键。
- **事务范围**：`run_once()`（`retention.py:503-552`）四面**互相独立**——一面失败只记 `carrier_retention.sweep_failed` 后继续其余三面，不因一张表的一行坏数据拖住另外三张表；四面跑完才在**事务之外**记一条 `carrier_retention.partial`/`completed` 汇总审计（同文件 539-546 行），这条汇总审计与四个面各自的数据库提交完全不是同一事务，审计写失败也不会撤销已经落地的清理结果——方向与 8.3 的管理族相反，是清理场景刻意的取舍：到期清理是强制义务，不能因为一条审计日志写不进去就把已经执行过的脱敏/删除撤回。

### 8.5 投递终态的确认与幂等（对应 IN-03）

- **身份**：Gateway 投递消费循环按进程级身份执行，消费的是已提交的 `task_delivery_event`，不持有用户身份、也不逐用户区分（`apps/gateway/delivery.py` 模块文档）。
- **成功时点**：**唯一前提是"本次终态的有效回执"**——`_terminal_receipt`（`delivery.py:443-467`）只认两类证据：本轮现场取得的回执（卡片终态更新成功，或文本兜底真的拿回 `message_id`），或本轮没有任何未消费事件、任务已在 `awaiting_delivery`、投递标识已落库的"上一轮已取得、本轮只差确认"。飞书"仍在发送"码 `230049` 一律判 `UNCERTAIN`，不算成功也不算失败（`core/delivery/ports.py:158-162`）。
- **幂等**：按操作分档，`DELIVERY_OPERATIONS`（同文件 190-243 行）**七个**操作里只有 `NOTICE_SEND` 带平台去重键（请求体 `uuid`）；建卡、卡片回复、流式更新、流式关闭、文本兜底、**文档写入**这**六个都没有**幂等键，靠"外发前先占一个预留位、只有服务端明确拒绝才清空"防止自动重投造成重复交付。因此 `230049` 在场时，这六类操作一律不自动重投，只能停在 `uncertain` 等人工核对。
- **事务范围**：投递侧没有独立的 `AuditSink`——推进消费游标（`record_delivery_progress`）、确认送达（`confirm_delivery`）都是各自独立的数据库写入，失败靠告警回调与结构化日志留痕，不写审计表；这一族不存在"审计与提交是否同事务"的问题，只有"数据库写入本身是否成功"这一层。

### 8.6 管理动作持久阶段与统一停止

状态：2026-09-09 本地实现，来源 [#603](https://github.com/Moshuiwang/lingxi/issues/603)。本节描述阶段 v1 的端口与接入责任，不表示真实环境已经验收。模型与协议定义在 [followup.py](../../src/lingxi/core/admin/followup.py)，SQL 实现在 [PostgresFollowupStore](../../src/lingxi/adapters/postgres_admin_followup.py)。

| 端口 | 调用约束与结果 |
|---|---|
| `enqueue_followups` | 传入原确认事务连接与固定 `FollowupSpec` 元组；阶段登记与确认业务整体提交或回滚。唯一键冲突返回已有引用，不重置终态；容量拒绝保留原待确认动作。 |
| `claim_followup` | 按消费者职责领取一条到期、依赖成功的 v1 阶段；返回 `ClaimedFollowup` 与递增 `attempt`。不接受任意执行字符串，未知版本不领取。 |
| `mark_effect_started` / `renew_lease` | 校验当前 owner、attempt 与有效租约；外发开始标记必须先持久成功。集中续租失败后不得开始下一外部操作。 |
| `complete_followup` / `retry_followup` | 只有本代 running 可写回；完成与固定后继登记同事务。内部失败有限退避；已开始且回执无法确认的通知转 unknown，不能盲目重发。 |
| `recover_expired` | 有限扫描过期租约、关闭失败依赖和到期记录；恢复内部工作，保留外发未知语义。具体数据字段与保留路径见[数据库设计](数据库设计.md#管理动作后处理阶段)。 |
| `resolve_target` | 在 owner+attempt 条件下，由固定批次适配器同连接读取原批次身份，再核对真实 app_user 后补齐 target_user_id；不更换 subject_key 或阶段 ID。 |
| `recovery_status` | 只读返回格式版本、兼容判断、在途、可恢复及 unknown 数量；未知版本不能作为恢复完成。 |

`FollowupSpec` 不接收 open_id。既有单人动作使用内部 user_id 作为 subject_key；批次固定使用 batch_item_id，确认时 target_user_id 可空。target_version 沿用可空整数版本。trace_id 属于工作本身，pending_action_id、followup_id、批次及 attempt 贯穿日志；进程标识独立使用 run_id。只读投影 `fetch_followups` 按 trace_id 精确关联并限制九十天，`render_followups` 把 unknown 表达为“结果待核实”；既有管理员查询接线由其调用方完成。

Gateway 的实际装配使用后处理、权限重算、发布观察三个固定消费者与一个集中续租循环；重算现读当前账号事实，发布观察绑定父阶段的发布引用和版本。卡片网络刷新与权限重算独立，刷新读取当前持久状态；管理卡状态更新拒绝已被复用的旧动作。准备发卡与本人确认后阶段属于各自事务，不能混为一次自动通知授权。

`request_stop()` 关闭接收和领取，`drain_until(deadline_monotonic)` 使用绝对截止并返回 accepted、finished、recoverable、unknown、still_running。Gateway 与既有投递共用收到停止信号起的 20 秒；scheduler 生命周期 Owner 使用同一 120 秒，登记开通执行器、组织/日报后台对象，并提供 `register_background` 给 listener。超过预算只报告仍在途，不声称线程已取消；不提前关闭其活动连接。新增活动数据库操作共用进程内两槽预算，listener 至多占一槽；这不是空闲连接池上限。

批次处理器、准备卡发送及真实 listener 由后继接入，须复用以上阶段和 scheduler 预算。UDS 容量、断连事务恢复、全部后台职责在同一截止下退出，以及固定恢复制品实际消费在途阶段，仍须共同隔离验证；不能以端口存在或单个消费者测试代替。对应 [V-管理-44…48](验收矩阵-接入与管理.md#管理动作持久阶段) 与 [V-部署-28…29](验收矩阵-部署与迁移.md#管理后台共同退出与恢复)。

## 九、尚未确定的契约

|---|---|---|

| 正式产物承载、跨租户与生命周期 | #97 验证清理；#140 决定责任主体 | 维持失败关闭，不阻塞普通问数正文 |

对应记录以 [`docs/当前能力.md`](../当前能力.md) 的未验证依赖表为唯一事实源。
