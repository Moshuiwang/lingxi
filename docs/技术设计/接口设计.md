## 一、接口全景与信任边界

| # | 接口 | 方向 | 信任级别 | 承载 |
|---|---|---|---|---|
| 1 | 飞书事件与卡片回调 | 入站 | **不可信**，必须验签 | 长连接 |
| 2 | 飞书开放平台 API | 出站 | 可信外部 | HTTPS |
| 3 | 问数 MCP | 出站 | 可信外部，但**不承担其正确性** | MCP 客户端 |
| 4 | 管理 MCP | 提供方 | **按管理员个人身份鉴权** | Streamable HTTP |
| 5 | 内部交付接口 | 入站 | **半可信**：调用者是用户环境内的 Agent | Unix domain socket |
| 6 | 内部问数 MCP 代理 | 入站 | **半可信**：调用者是用户环境内的 Agent | Unix domain socket |
| 7 | 领域服务 | 进程内 | 可信 | Python 函数调用 |

**关键判断**：#5 和 #6 都是“我们自己的代码在用户可控环境里调用我们”的接口。JumpServer 用户在自己的环境里有 shell，因此两个接口都必须假定调用者可以伪造请求体，只信任**连接来源的操作系统身份**（见[七、用户环境的内部代理接口](#七用户环境的内部代理接口)）。

## 二、通用约定

### 标识符

| 前缀 | 含义 | 示例 |
|---|---|---|
| `usr_` | Lingxi 内部用户标识 | `usr_01HXYZ...` |
| `cnv_` | 对话（私聊主窗口或话题） | `cnv_01HXYZ...` |
| `tsk_` | 任务 | `tsk_01HXYZ...` |
| `pac_` | 待确认操作 | `pac_01HXYZ...` |
| `rev_` | 开通运行异常记录 | `rev_01HXYZ...` |

统一使用 ULID（时间有序、可排序、无需协调）。**飞书侧标识（`open_id` / `user_id` / `union_id` / `chat_id`）永不作为内部主键**，只作为关联字段——它们属于外部系统，语义可能变化。

### 时间

全部使用 `TIMESTAMPTZ`，存储与传输一律 UTC，仅在面向用户的文案里转换为本地时区。

### 错误模型

所有内部接口与管理 MCP 工具返回统一信封：

```json
{
  "ok": false,
  "error": {
    "code": "target_state_changed",
    "message": "目标用户的权限版本已经变化，请重新查询后再操作。",
    "retryable": false
  },
  "trace_id": "01HXYZ..."
}
```

`message` 面向管理员或最终用户，**必须是可直接展示的中文**，不含内部标识、堆栈或表名。`code` 面向程序判断。

统一错误码：

| code | 语义 | 后续动作 |
|---|---|---|
| `not_found` | 目标不存在。**明确的终态，不做相似匹配** | 不重试 |
| `not_authorized` | 当前身份或角色无权 | 不重试 |
| `target_state_changed` | 目标状态或权限版本已变化 | 重新查询后再决定 |
| `action_expired` | 待确认操作已过期 | 不重试 |
| `already_executed` | 已执行，返回既有结果 | 返回首次结果，不重复执行 |
| `audit_write_failed` | 审计写入失败，状态未改变 | 调用方可重试 |
| `external_unavailable` | 外部系统暂不可用 | 调用方可重试 |
| `conflict` | 并发冲突 | 调用方按最新状态重试 |
| `LX-QUEUE-001` | 消息已收到，但任务没有成功进入队列 | 用户可稍后重试；同一事件不重复提示 |
| `LX-ONBOARD-001` | 自动开通暂时无法完成，已转交管理员处理 | 系统或管理员继续处理；用户不重复发送 |

### 幂等

所有产生副作用的接口必须携带幂等键：飞书入站用 `event_id`，内部接口用调用方生成的 `idempotency_key`。服务端以唯一索引落库，冲突即返回首次结果。

### 追踪

每个入站事件生成一个 `trace_id`，贯穿任务、Agent 会话、MCP 调用、交付和审计。单机部署下不引入分布式追踪，用结构化日志中的同一 `trace_id` 串联即可。

## 三、飞书入站

### 3.1 消费的事件

| 事件 | 处理 |
|---|---|
| `im.message.receive_v1` | 私聊消息。立刻加表情（合同：**任何消息**都加，含未开通用户、忙碌期消息、`/stop` `/new`）→ 判定用户状态与话题忙碌 → 入队或回提示 |
| `card.action.trigger` | 卡片按钮。用于“四达文档会议助手”的专用组织资料授权，以及管理待确认操作（「确认执行」「取消」）；不用于普通员工开通。 |
| `im.chat.member.bot.deleted_v1` | 用户移除机器人。记审计，不自动停用账号 |

### 3.2 gateway 的处理次序

处理次序本身是合同要求，不能重排：

```
1. 通道级认证                握手期完成；非该通道来的事件不存在（见下）
2. event_id 落 inbound_event 冲突 → 重复投递，直接返回成功
3. 加表情                    失败 → 记审计，继续（合同：不影响后续处理）
4. 查用户状态
   ├ 未开通 → 只登记开通意图与持久状态；业务内容一律丢弃，不保存不回显
   │            发送一次“正在核对”提示后结束当前消息，不进入第 5–7 步
   │            后续由持久状态机或异步任务分事务推进：
   │            ├ 有效权限 → 提示正在开通与同步；全部完成后才提示成功
   │            ├ 无可用银河权限 → 提示去银河申请或补充权限，不进入人工等待
   │            ├ 零条/多条/冲突/资料不完整 → 统一提示无可用银河权限，不建待办
   │            ├ MCP 权限同步超时 → “权限同步未完成，已转交处理”
   │            └ 其他 Lingxi 内部意外故障 → 提示已转交管理员，错误码 `LX-ONBOARD-001`
   ├ 已停用 → 回复停用说明，结束当前消息，不进入第 5–7 步
   └ 已开通 → 继续第 5–7 步
5. 解析命令（/stop /new，仅已开通用户）
6. 话题忙碌判定（仅已开通用户）
   ├ 忙碌 且 非 /stop → 只回"当前任务仍在处理中"，不入队、不入历史
   └ 其他 → 入队 task
7. NOTIFY task_queued（仅已开通用户）
   ├ 入队成功 → 返回成功
   └ 入队失败 → 回复“消息已收到，但当前暂时无法开始处理，请稍后重试。错误码：LX-QUEUE-001”，不表示已受理，事件不标记为成功
```

**第 1 步在 2026-08-06 随 [#57](https://github.com/Moshuiwang/lingxi/issues/57) 由"验签"改写为通道级认证。** 原措辞按 Webhook 语义书写：事件经 HTTPS 回调进来，每条都带签名，因此第一步是验签。实际接入选型是官方 `lark-oapi` 的长连接（`ws.Client`），认证发生在**握手期**——应用凭据换取 endpoint 与 wss 地址，之后帧从那条已认证的连接里出来，**单条事件上没有可验的签名**。继续写"验签"会让实现去发明一个飞书并不提供的校验。

产品意图不变，承接它的是两条约束：gateway 进程**不监听任何入站端口**，且事件只从长连接通道进入。判定面比逐事件验签更严——不存在"签名对了就受理"的旁路，因为根本没有第二个入口。断言见[验证与门禁](验证与门禁.md#七关键机制验收矩阵)的 `V-接入-10`。

**已开通用户进入队列时，第 2 步到第 7 步落在同一个数据库事务里**（`V-队列-01`）。任务插入失败时事件行也不存在，飞书重投时该消息能被重新完整处理；抢占随事务回滚，话题不会永久停在"忙碌"。未开通或已停用用户只执行到第 4 步：在短事务内保存事件幂等、开通意图或终态后结束当前消息；最长十五分钟的开通过程与阶段提示必须由持久状态机或异步任务分事务推进，不能长时间占用 gateway 事务，也不能把已丢弃的首条业务内容继续入队。

第 3 步的加表情是事务内的外部调用、不可回滚——这是知情取舍，合同只承诺表情表示"已收到"，不表示已受理；任何表示"已受理"的**回复**都不得在入队成功前发出（`V-队列-03`）。入队失败时允许发送固定失败提示 `LX-QUEUE-001`，但该提示不代表任务已受理。

要同时兑现“事务回滚后消息仍可重新处理”和“相同事件的失败提示只发一次”，不能只依赖会随事务回滚的 `inbound_event` 行。实现必须为 `event_id + LX-QUEUE-001` 留下可持久回读的通知幂等事实，或提供经同等故障、并发和重启验证的等价机制，同时不得把事件误标为成功、阻止后续重新入队。该机制尚未交付前，这是设计目标而不是当前能力，验收见 `V-队列-07`。

### 3.3 卡片回调的校验

管理待确认操作的卡片回调**必须**校验（合同逐条要求）：

| 校验项 | 不通过时 |
|---|---|
| 点击人 `open_id` 解析出的 `app_user.id` == `pending_action.initiated_by` | `not_authorized` |
| 该管理员当前角色仍有权执行此动作 | `not_authorized` |
| `pending_action.status == 'pending'` | `already_executed` |
| `expires_at > now()` | `action_expired` |
| 目标对象状态版本未变 | `target_state_changed` |

任一不通过都**不执行**，并把原卡片更新为不可再操作的终态。

## 四、飞书出站

按用途分组，具体 API 以飞书开放平台文档为准，本文只固化**我们的调用约束**。

| 用途 | 约束 |
|---|---|
| 加表情 | 失败不阻断后续处理 |
| 创建卡片实体 | `update_multi=true`、CardKit JSON 2.0；记录可回读的 `card_id`，但只有权威 API 明确受理才记为 `platform_received` |
| 流式更新卡片 | 序列号严格递增；节流 ≥500ms；进程级令牌桶兜住 50 次/秒；首次失败后停止全部后续卡片更新并永久切到本任务文本兜底 |
| 发送文本 | 只向同一私聊或同一话题发送最多一个经过可信输出检查的文本终态；权威 API 响应不明记为 `uncertain`，不自动重发 |
| 正式产物 | 只调用 #140 批准且经 #97 所需真实探针验证的承载路径；创建、归属或授权、发送分别权威回读。当前无批准路径时明确失败关闭，不创建目录或文件，不阻塞普通问数正文 |
| 多维表格写入 | 权限发布通道；写入结果落 `publish_outbox`，与数据库记录逐字段比对 |

**凭据边界**：飞书出站只由 Gateway 或受控正式产物交付服务持有机器人凭据发起。Worker、用户环境、shell、进程参数与任务事件中**不存在**任何飞书凭据。

**问数结果事件边界**：Worker 不直接调用飞书。它只把已经通过跨分片可信输出检查的 `started`、`progress`、`safely_releasable_answer`、`terminal` 事件按任务严格递增地提交到数据库；Gateway 只消费已提交事件，并从最后确认序号恢复。任务终态、话题释放和等待态必须同事务收敛；业务结果与投递结果分别记录，`platform_received` 不等于 `user_read`。

## 五、问数 MCP（消费方）

Lingxi 是问数 MCP 的**客户端**。合同规定 Lingxi 不复制其权限过滤、不验收其正确性，只做两件事：把它接给 Agent，以及在开通前确认同步。

### 5.1 接入方式

作为 MCP server 注册进 Agent SDK 的 `mcp_servers`，工具以 `mcp__query__*` 命名空间暴露给 Agent。每个用户的连接以**该用户的身份凭据**建立——这是数据范围隔离的实际发生点。

### 5.2 依赖的能力

| 能力 | 用途 | 状态 |
|---|---|---|
| `list_metrics` | 用户问"你能查什么"时由 Agent 调用 | 原系统已具备 |
| `describe_metric` | 指标口径说明 | 原系统已具备 |
| 回读权限版本与范围，再按用户执行最小问数 | **开通第 8 步的同步确认** | MCP 必须返回可比对的 `permission_version`、companies 和 functions；Lingxi 逐项一致后再以目标用户发起最小查询，不能由一次 smoke 或空结果单独构造就绪判断 |

### 5.3 同步确认的判定

```
成功：MCP 返回可比对的 permission_version、已生效 companies / functions，且与 Lingxi 当前权限版本和范围逐项一致；随后目标用户最小查询返回明确成功
未就绪：版本或范围不一致、字段缺失、连接失败、鉴权失败、超时、返回无法判定的状态
```

**明确空结果只证明一次查询没有报错，不能证明权限范围已经同步。** “其他用户能查”或“服务在线”同样不能作为当前用户就绪的证据。因此 MCP 侧必须提供可回读的权限版本和生效范围，Lingxi 完成比对后再以目标用户身份发起最小查询；上游尚未提供这些字段时一律保持“权限正在同步”，并在十五分钟后转运维处理。

### 5.4 结果处理约束

- MCP 返回数据最新时间 → 展示；未返回 → 省略该字段，**不提示"数据时间未知"、不拒绝回答**；
- MCP 未返回某项数据 → **不推断为权限不足**，只说明本次未取得可用结果；
- 只有 MCP 明确给出"数据不存在 / 延迟 / 结果不完整"状态时才向用户区分说明。

这三条写进 Agent 的系统提示词，并在交付前由 `execution` 模块做一次输出检查（发现"权限不足"类措辞时记审计告警）。

## 六、管理 MCP（提供方）

协议版本：**MCP `2026-07-28`**（已正式发布的最新修订；其版本状态在官方站点当日存在不一致，规范事实与该保留见[MCP 规范 `2026-07-28` 与管理入口](../参考证据/MCP规范2026-07-28与管理入口.md)）。传输：**Streamable HTTP**。鉴权：每个管理员一份个人凭据，服务端每次从凭据解析出稳定的管理认证主体 `admin_identity`，再读取该主体绑定的唯一 `app_user`、本人飞书 `open_id` 与当前角色。数据库只保存认证提供方、主体标识和凭据指纹或版本，不保存凭据明文。

该版本对服务端形态的强制要求：

- 协议**无状态**：没有 `initialize` 握手，也没有协议级会话。每个请求在 `_meta` 自带协议版本与客户端能力；服务端必须实现 `server/discover` 公布支持的版本、能力与身份。
- 响应流断开即丢失在途请求，客户端以**新的请求 ID** 重发原请求。所有 `prepare_*` 工具必须携带调用方生成的 `idempotency_key`（见[二、通用约定](#二通用约定)的幂等）。但**协议不保证重发时的工具参数与首次一致**——`prepare_*` 的参数由模型填写，宿主完全可能生成一个新的 `idempotency_key`。因此服务端**必须再加一层自然键去重**：同一 `admin_identity` + 动作类型 + 目标对象 + 目标状态版本，在待确认操作未终结前已存在 `pending` 项时，直接返回既有项，不新建、不重发卡片。合同的「同一待确认操作最多成功执行一次」不得依赖客户端的良好行为。
- `tools/list`、`prompts/list`、`resources/list`、`resources/read`、`resources/templates/list` 的结果必须带 `ttlMs` 与 `cacheScope`。管理 MCP 的工具列表按角色不同而不同，`cacheScope` **必须**为 `private`，`ttlMs` **不超过 60 秒**。`ttlMs` 只是给客户端的提示、服务端无法强制其何时重取，因此角色收回的即时生效仍由每次调用重新解析授权保证（结构性规则 1），缓存上限只用于限制工具列表的陈旧窗口。
- Lingxi 自定义错误码不得占用规范保留的 `-32020`～`-32099` 区间。该约束针对 **JSON-RPC 层的数字错误码**，与[二、通用约定](#二通用约定)中业务信封里的字符串 `code` 是两层，不需要改动那张表。
- 不使用 `Roots`、`Sampling`、`Logging`（均已进入弃用窗口），也不启用任何可选扩展（`Tasks`、`MCP Apps`、企业托管授权均为 opt-in，首期不采用）。

同一条管理链路必须能证明三者一致：

1. 调用管理 MCP 的认证主体是 `admin_identity`；
2. 待确认操作的发起人和当前角色属于同一 `admin_identity`；
3. 确认卡只发送到该身份绑定的飞书 `open_id`，回调点击人再反查为同一 `admin_identity`。

任一映射缺失、重复或发生变化都返回 `not_authorized`，不查询目标用户、不创建待确认操作，也不根据卡片是否送达推断管理员身份。

**四条结构性规则**：

1. **工具按角色注册**：当前身份没有的角色，对应工具**不出现在工具列表里**，而不是调用后拒绝。AI Agent 看不到无权使用的能力。
2. **只读直接返回，写操作只能"准备"**：所有 `prepare_*` 工具只创建待确认操作并发卡片，**不改变任何状态**。
3. **不存在可用作授权凭证的会话标识**：`2026-07-28` 已从协议中移除会话与 `Mcp-Session-Id` 头，授权每次从个人凭据重新解析。工具按角色注册同样只能依据本次请求解析出的 `admin_identity`，不得依赖任何连接级状态。
4. **首期不下发任何 `elicitation/create`**：确认通道保持为发起管理员本人的飞书私聊卡片。`form` 模式的 `accept` 由客户端自报、服务端无从核验，不能作为「本人已确认」的证据；而只要下发任何 elicitation，就会新增一项对客户端能力声明的运行时依赖（规范禁止向未声明支持的客户端下发）。首期不值得为澄清类输入付出这项依赖，因此整体不下发，需要澄清时由 Agent 在对话内追问后重新调用工具。理由见[管理员 AI Agent 与飞书确认边界决策](../决策记录/2026-07-26-管理员AI-Agent与飞书确认边界.md)的 2026-07-29 复审。

### 6.1 只读工具

#### `list_onboarding_incidents` — 开通运行异常（运维管理员）

```json

  "inputSchema": {
    "type": "object",

```

返回每条记录的 `incident_id`、异常类型、用户标识、发生时间、当前状态和脱敏摘要。接口不返回身份或银河候选记录，也不能把确定性匹配失败恢复为待选择流程。

#### `get_user` — 用户详情（权限管理员）

```json
{
  "inputSchema": {
    "type": "object",
    "properties": {
      "user_id":  {"type": "string", "description": "Lingxi 内部用户标识"},
      "open_id":  {"type": "string", "description": "飞书 open_id"},

```

三选一。**精确匹配**：查不到即返回 `not_found`，不做模糊匹配、不返回相似姓名列表（合同："不猜测相似姓名、不自动改查其他用户"）。姓名命中多人时返回 `conflict` 并给出各自的 `user_id`，管理员只能选择本次**管理查询的目标**；该选择不得写回首次开通身份、不得选择银河权限记录，也不能让失败的开通流程继续。

#### `get_user_provisioning` — 开通与发布状态（运维管理员）

输入用户标识，返回：用户环境状态、经 #140 批准的正式产物路由状态（若存在）、多维表格发布状态与最近一次发布结果、MCP 同步确认的历次尝试与结论、当前卡在哪一步。

#### `list_failed_publishes` — 发布异常（运维管理员）

返回 `publish_outbox` 中失败或滞留的条目，含重试次数与最后错误。

#### `list_admins` — 管理员名册（超级管理员）

返回各管理员的飞书身份绑定与当前角色集合。

#### `get_pending_action` — 待确认操作状态（所有角色，仅限本人发起的）

让 Agent 能如实回答"卡片发出去了吗、确认了吗"，而不是猜测。

## 七、用户环境的内部代理接口

### 7.1 交付接口

用户环境内的交付 Skill 调用本机的交付服务，由持有凭据的服务实际执行。

**传输选 Unix domain socket，不选回环 TCP**：socket 文件的属主与权限本身就是第一道边界，且内核提供的 `SO_PEERCRED` 能给出调用方的真实 uid——而回环 TCP 上同一台机器的任何用户都能连接，身份只能靠应用层推断。

```
POST /internal/deliver          （经由 /run/lingxi/deliver.sock）
```

```json
{
  "idempotency_key": "dlv_01HXYZ...",
  "kind": "doc | sheet | image | file",
  "title": "2026 年 6 月华东区充值趋势",
  "source_path": "/var/lib/lingxi/users/usr_01H.../work/report.md",
  "trace_id": "01HXYZ..."
}
```

### 身份认定

**请求体里的任何用户标识都不可信**。服务端用 `SO_PEERCRED` 取得连接方的真实 uid，再按 `uid → internal_user_id` 映射确定交付归属。请求体里即使带了 `user_id` 也一律忽略。

理由：JumpServer 用户在自己环境里有 shell，可以任意构造请求体。如果信任请求体里的 `user_id`，任何用户都能把产物交付进他人目录——这正是合同列为阻断问题的"Lingxi 自身造成的跨用户交付泄露"。

### 路径校验

`source_path` 必须解析为规范路径后仍位于调用方自己的家目录内，拒绝 `..`、符号链接逃逸和绝对路径穿越。

### 返回

```json
{
  "ok": true,
  "delivered": true,
  "url": "https://xxx.feishu.cn/docx/...",
  "authorized": true
}
```

`authorized` 为 `true` 才代表交付完成。授权未确认时返回 `delivered: false` 与说明，由 Agent 按合同措辞告知用户核对，**不自动重发**。

### 7.2 问数 MCP 代理

用户环境和 Agent 子进程均不持有 MCP 凭据。它们经 `/run/lingxi/query-mcp.sock` 调用本机代理；代理与交付接口一样使用 `SO_PEERCRED` 取得真实 uid，映射到 `app_user`、当前启停状态和已确认的权限版本后，才代表该用户调用外部问数 MCP。

- 不接受请求体中的 `user_id`、公司、职能或凭据覆盖；
- 用户已停用、正在删除、权限尚未同步确认或 uid 无唯一映射时默认拒绝；
- 外部 MCP 凭据只存在于代理服务的受控凭据存储和内存中，不进入 shell 环境、进程参数、用户目录、Agent 会话或日志；
- 代理把调用与结果摘要交给审计出口，但不记录凭据或完整认证材料。

## 八、领域服务接口

进程内模块边界。列出的是**跨模块调用点**，模块内部结构不在本文约束。

```python
# identity：写侧建档（Issue #89；调用方是首次开通编排 OnboardingRunner）
def provision(request: ProvisioningRequest) -> ProvisioningResult   # 自带事务；按 feishu_open_id 幂等

# conversation：会话与任务生命周期
def resolve_conversation(user_id, chat_id, thread_id) -> Conversation
def should_start_new_session(conv: Conversation, now) -> bool   # 两小时规则
def try_acquire_topic(conv_id, task_id) -> bool                 # 同话题串行
def release_topic(conv_id, task_id, ended_at) -> None
def reset_context(conv_id) -> None                              # /new
def request_stop(conv_id) -> None                               # /stop

# permission：发布与同步确认
def enqueue_publish(user_id, reason, *, tx) -> PublishOutboxId   # 与业务变更同事务
def run_publish(outbox_id) -> PublishResult
def check_mcp_sync(user_id) -> SyncCheckResult                   # 回读版本/范围并比对，再执行目标用户最小查询
def sync_deadline_reached(user_id) -> bool                       # 15 分钟窗口

# admin：待确认操作
def prepare_action(actor, action_type, target, params) -> PendingAction
def confirm_action(action_id, clicker_open_id, now) -> ActionResult  # 幂等，最多成功一次
def cancel_action(action_id, clicker_open_id) -> ActionResult

# audit：审计
def record(event_type, actor, target, before, after, *, tx) -> None  # 写路径必须传 tx
```

**约定**：`enqueue_publish` 与 `audit.record` 在写路径上**必须接收调用方的事务对象**，由类型签名强制"审计与状态变更同事务"——这是合同要求，不能靠代码评审保证。

### 8.1 写侧建档服务（`identity.provision`）

身份、花名册与银河权限唯一且有效之后，把这个人写进 `app_user` 的唯一调用面。合同正文与逐条理由在 `src/lingxi/core/identity/provisioning.py` 的模块文档，本节只保留跨模块调用方（首次开通编排）必须先知道的四件事。

**输入只有两部分**：判定层产出的身份草稿（`decide_first_contact` 的 `IdentityRecordDraft`，身份六字段），以及花名册那一行的工号与邮箱**原值**。银河匹配结果决定"要不要建档"，但它的任何字段都不进 `app_user`——`AccountMatch.matched_email` 是为匹配做过小写归一的比较值，写进存档会让[每日花名册日报](../产品合同与外部边界.md)把每个含大写字母的邮箱天天报成变化。权限字段同样不在输入里（`V-开通-01`：匹配确认前不占位再回填）。

**输出三态**：`created`（本次新建）、`already_provisioned`（同一 `feishu_open_id` 已有档，幂等返回同一条）、`rejected`（约束防线拒绝，库里零行残留）。拒绝原因互不合并，且分成两类去向：

| 原因 | 触发点 | 编排层的去向 |
|---|---|---|
| `incomplete_identity` | 身份六字段「全有或全无」CHECK 拒绝，或请求没有 `feishu_open_id` | 确定性业务失败，走"无可用银河权限"终态 |
| `delegated_subject` | 专用授权账号触发器拒绝（`V-身份-02`） | 走既有"专用主体忽略"出口，不回普通员工路径 |
| `storage_integrity` | 工号/邮箱写入后回读不一致（`V-开通-15`） | **存储侧故障，不是业务结论**，走 `LX-ONBOARD-001` |

把 `storage_integrity` 并进前两类，用户会因为"我们的库把工号吞了"而被告知去银河申请一个他其实已经有的权限，因此这条分界由结果对象上的可判定属性表达，不靠调用方记得区分。识别不了的数据库拒绝一律原样抛出，不归进任何兜底原因。

**幂等是"返回已存在"而不是报错**：`OnboardingRunner.start` 按事件与用户标识幂等，且未开通首聊的对账扫描会把"已认领、没确认交接"的孤儿事件再交接一次，崩溃点可能落在编排已经跑了一半之后。重复建档若报错，一次**已经成功**的建档会被重入判成内部故障，用户拿到内部故障码而库里其实已有档。重入不回退 `provisioning_state`、不触碰权限列与 `account_state`（**不复活被停用的账号**），只按新快照刷新身份资料与花名册字段。

**`already_provisioned` 不等于"这个人现在还该被开通"**：收到它之后、继续用户环境创建与权限发布之前，编排层必须复核该用户的当前状态（`account_state` 与 `provisioning_state`）。孤儿事件的重交接窗口可以长达一整个对账扫描周期，管理员在这段时间里停用账号是真实形状，而建档服务只保证"档在、且这次重入没有把它写坏"，它不判断这个人此刻还该不该继续开通——把这条判断放进写侧等于让它悄悄替编排层做准入决定。

**事务边界**：一次调用在一个数据库事务内完成 `app_user` 的完整写入，任何拒绝整条回滚且不破坏该 `open_id` 已有的档案；返回时事务已提交，结果对后续步骤、对账扫描与日报立即可见。**跨系统原子性不在本合同内**——用户环境创建、权限发布 outbox、MCP 同步确认与飞书回复的补偿与重入属首次开通编排。本接口刻意**不接收调用方事务对象**，与上面 `enqueue_publish` / `audit.record` 的约定相反：那两个要的是"审计与状态变更同事务"，而建档是编排的第一步、后面全是跨系统长动作，挂在调用方事务里会按分钟级占住连接与行锁，更要紧的是"建档已经成功"在崩溃后不可判定，而幂等恰恰依赖它已经落地。

## 九、尚未确定的契约

下列接口形态依赖尚未验证的外部能力，实现时先撞、撞不通即回到 Issue 重新设计，**不得先向用户承诺**。

| 契约 | 依赖 | 不成立时的影响 |
|---|---|---|
| 专用关联组织 OAuth 授权 | “四达文档会议助手”取得可轮换用户 token；受控测试已验证，正式实现按飞书官方 OAuth 文档编码 | 授权失效时暂停资料同步并提示专用用户重新授权；不影响普通员工的既有问数权限 |
| 授权后可读字段范围 | 员工三类身份标识、部门、租户与在职状态的可得性，以及花名册工号、邮箱的覆盖率与唯一性（[#35](https://github.com/Moshuiwang/lingxi/issues/35)） | 统一用户记录的字段与匹配逻辑调整；匹配键为花名册取得的工号（主）与邮箱（辅），见[花名册身份链与工号邮箱匹配决策](../决策记录/2026-08-05-花名册身份链与工号邮箱匹配.md) |
| 管理卡片回调走长连接 | 飞书已记载机制；在管理员功能编码阶段验证 Python SDK 版本的事件注册、操作者身份和重复回调 | 若当前 SDK 组合不成立，管理卡片改为受控 HTTP 端点，事件仍走长连接 |
| 正式产物承载、跨租户授权与生命周期 | #97 验证跨租户协作者、继承、负向访问、清理和用户侧可达性；#140 决定责任主体、保留与清理合同 | 维持正式产物失败关闭；不得实现旧机器人专属目录或阻塞普通问数正文 |
| 问数 MCP 的按用户就绪判定 | 上游能否返回可比对的 `permission_version` 与生效 companies / functions | 未提供时不得以空结果宣告就绪，开通保持同步中并按十五分钟规则转运维处理 |
| 管理 MCP 的个人授权与飞书身份绑定 | 待选 Agent 客户端能否稳定传递个人身份 | 管理入口形态重设计 |

对应记录以 [`docs/当前能力.md`](../当前能力.md) 的未验证依赖表为唯一事实源；逐项验证由独立 Issue 认领（原汇总 [Issue #11](https://github.com/Moshuiwang/lingxi/issues/11) 已关闭）。
