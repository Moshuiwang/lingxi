### 权限发布与同步

`V-权限-01/02/03/09/10/11/12` 由 [#156](https://github.com/Moshuiwang/lingxi/issues/156) 的 S-C-01（发布 outbox 与多维表格写读回）与 S-C-02（令牌签发与 MCP 就绪状态机）认领。

**2026-08-17 产品负责人裁定改写了两条断言的措辞**（依据：Trace [#203](https://github.com/Moshuiwang/lingxi/issues/203) G-155 终判）：

- **`V-权限-06` 由「回读版本比对」改为「探针法」**：权限表无版本字段，就绪改用目标用户令牌真实执行一次 `list_metrics`、可见指标大于零才算就绪，结论绑定（用户，权限版本）。正文见[架构设计 6.4](架构设计.md#64-权限发布与-mcp-同步确认)。
- **`V-权限-11` 由「永不写入 `token_cipher`」改为「新建行必须携带、更新行不清空不覆盖」**：没有密文的行对 MCP 无意义；令牌明文与主密钥不进数据库任何列、outbox、日志与告警，进 outbox 与发布表的只有密文。正文见 `core/permission/publish_row.py` 与迁移 `0065`。

**「密文被改写」保证的边界（2026-08-17 编排者裁定，不做代码修复）**：识别改写依赖「这一行是我们建的」这一事实，只在同一条发布意图内有效，因此新版本产生的新意图对「上一版曾建过的行」、以及创建结果不明时识别不到；两者都不做代码修复——就绪探针是功能性最终门，带错误密文的行永远探不成功，会以十五分钟超时转运维，不产生假成功；密文归属随存量用户令牌归属决策一并确定（裁定 6：硬切窗口统一重签）。

**`V-权限-07` 由 S-C-03a + S-C-03b 认领**（[#156](https://github.com/Moshuiwang/lingxi/issues/156)，Trace [#203](https://github.com/Moshuiwang/lingxi/issues/203)）：

- **重算**（S-C-03a）：`lingxi-scheduler` 每日权限重算严格先花名册、再银河，权限有变化才推进版本。
- **发布与就绪确认**（S-C-03b）：每轮驱动发布执行器并按 tick 推进就绪探针，一轮调度不被十五分钟等待占住。
- **通知**：就绪成功发「范围已更新」，撤权在读回一致后发「暂无可用范围」。

**银河快照刷新口径**：MVP 期银河数据由人工 CLI 按需导入，重算职责每日消费当前有效批次；「刷新」= 消费当前批次，不承诺自动拉取。

**仍未验证的部分（不冒充已验证）**：①L4a 真实多维表格回读与真实 MCP 探针留受控窗口，翻译层硬闸已由 [#227](https://github.com/Moshuiwang/lingxi/issues/227) 落地为 `V-权限-13`；②发布/花名册所需环境变量未全配，写快照与发日报按 [#275](https://github.com/Moshuiwang/lingxi/issues/275) 已拆为互斥职责；③通知的真实私聊投递行为未验证；④权限变化通知的公司位显示内部编号而非中文名，待翻译层 Story 一并修复；⑤`mcp_sync_check` 清理需 `LINGXI_MCP_TOKEN_ENCRYPT_KEY`，未配时不装配，该表无可识别内容列不构成保留违规；⑥翻译闸落地前的遗留发布意图已用独立运维脚本一次性作废，需在部署前手动执行一次，未在 `biai-stage`/生产验证。

**通知投递的 at-most-once 残余窗口（知情接受）**：就绪落库后、通知发出前进程崩溃会丢失该条通知，不建通知 outbox 是刻意取舍（产品负责人 2026-08-18 裁定 4：有限重试 + 审计，非 exactly-once）；先记后发保证不重复打扰用户。

**刷新链与开通链的十五分钟不是同一个承诺**：十五分钟约束首次开通（Epic D 用阻塞形态、真实 `sleep`）；刷新链的用户已在用 Lingxi，停机恢复后确认成功并告知即可。

**单实例假设（登记不修）**：本职责按 `lingxi-scheduler` 单副本设计，不做分布式租约，同时跑两实例可能重复通知。

**`V-权限-08` 认领的是刷新侧那一半**：权限从有变无时保留发布表那一行、`permissions` 清空、`status` 维持 `approved`、`token_cipher` 不动（撤权行只走更新路径，建不出新行），随后通知用户；在发布链上无足迹的人跳过，"在途也算足迹"（产品负责人 2026-08-18 决策补充 2）；匹配阶段失败不算撤权信号；重复撤权判 `UNCHANGED`；「全部角色都未映射」同样走这一路（对应 `V-银河-11` 末句在刷新侧的落点）。

**`V-权限-08` 的开通侧那一半仍属 Epic D**：首次开通时的未授权提示执行点在 `OnboardingRunner`，本 Story 不认领；存量用户令牌归属（裁定 6）同样属后续切片。

`V-权限-04/05` 由 S-C-02 认领判定这一半：就绪只有探针成功一条路成立，十五分钟预算耗尽后收口为超时终态（注入时钟）。把状态推到 `active`/`manual_review`、发送成功通知、生成人工待办属 Epic D 开通编排，其真库证据随那批交付；S-C-02 不接任何进程，也不改用户状态。
