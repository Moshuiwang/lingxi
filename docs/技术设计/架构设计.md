## 一、约束前提

下面五条是全部选型的依据。**任何一条变化都要回到本文复审**，而不是在实现里悄悄适配。

| 约束 | 具体值 | 对架构的影响 |
|---|---|---|
| 用户规模 | 面向约 200 名内部用户；首期三名真实试用 | 峰值并发任务预计十余个，不需要水平扩展、分库分表或服务网格 |
| 使用场景 | 公司内部、单租户、非 7×24 关键链路 | 可以接受分钟级恢复，不需要多活或自动故障转移 |
| 团队构成 | 无其他人类开发者，由 AI 代理协作实现与维护 | 优先“少而清晰的组件、强类型约束、能被静态检查发现的错误”，而不是靠人的默契 |
| 部署环境 | 单台生产服务器 `biplus-prod`，公司内网 | 单机部署；不引入需要独立集群的中间件 |
| 执行路径 | Claude Code + 百炼（见[仅提供 Claude 执行路径决策](../决策记录/2026-07-25-仅提供Claude执行路径.md)） | 执行层用 Claude Agent SDK，不是 Messages API 手写循环，也不是 Anthropic 托管的 Managed Agents |

**关于「Claude Code + 百炼」的技术含义**：产品的 AI 执行路径是 Claude Agent SDK（Claude Code 以库的形式运行在我们自己的进程里），模型调用指向百炼提供的兼容端点。这意味着 Anthropic 平台侧的托管能力——Managed Agents、服务端工具、Files API、各类 beta 特性——**默认不可用，架构不得依赖**。可用的是 Agent SDK 本地侧的能力：内置工具、会话、hooks、子代理、MCP 客户端、Skills。

> **开工门禁**：在开始依赖执行层的业务实现前，必须在 `biai-stage` 通过下列三项。第四项已有外部证据，不重跑。门禁执行与实测结论见 [Issue #23](https://github.com/Moshuiwang/lingxi/issues/23)，事实汇总见[当前能力](../当前能力.md)。
>
> 1. **管道模式下的终止事件——已通过（2026-07-28）**。用 Python Agent SDK `0.2.128`（自带 Claude Code CLI `2.1.220`）连续跑 40 个回合（含新建会话、`resume` 恢复与两会话交替），40/40 收到非空最终正文和恰好一次终止结果，正式回合 39/39 的最终助手正文与终止结果哈希一致。结论限于该固定版本与端点组合：Agent SDK 的双向流式模式与前身项目复现故障的 `-p` 一次性模式不同，非 TTY 管道本身不再被当作承重未知。仍保留终止事件缺失监控，并且不得对已产生工具副作用的回合自动重放。背景见[Claude 执行链路的已验证事实与管道投递风险](../参考证据/Claude执行链路的已验证事实与管道投递风险.md)。
> 2. **Skill 与审计采集点——部分通过，仍阻塞**。受控 Skill 可实际加载，`PreToolUse`（188 次）、`PostToolUse`（188 次）、`Stop`（40 次）可采集；但 `PostToolUseFailure` 全轮 0 次，未被真实触发。同轮出现一次真正的权限拒绝（`Read`），没有产生任何回调；[Agent SDK Hook 参考](https://code.claude.com/docs/en/agent-sdk/hooks)显示当前 Python SDK 不提供 `PermissionDenied` 回调。因此"工具失败可完整审计"不成立。
> 3. **运行时工具边界——不通过**。同轮验证中，模型执行了一次未被明确禁用的 `CronCreate`（随后由 `CronDelete` 删除）。这证明 `allowed_tools` 加 `permission_mode="dontAsk"` **不是**严格白名单：只列出允许的 MCP 工具，不等于其他内置工具不可执行；新增内置工具默认可被调用；Skill 与 `CLAUDE.md` 的文字约束不能代替运行时强制限制。执行层必须自行实现拒绝式白名单，并把新增内置工具默认视为禁止。
> 4. **会话、恢复与 MCP 调用经百炼兼容端点运行**——前身项目已在真实百炼端点取得可回读证据（新建与恢复会话、只读 MCP 调用与回执、终止事件），不作为 Lingxi 的重跑项；证据与其边界见上述参考证据。
>
> 第 2 或第 3 项未通过时，只允许继续修复或收窄门禁，不进入依赖完整审计或严格工具边界的业务实现。

## 二、架构总览

```text
                        飞书开放平台
                             │
              长连接(WebSocket) │ 事件 + 卡片回调
                             ▼
                    ┌─────────────────┐
                    │ lingxi-gateway  │  验签 → 幂等 → 落库 → 立即返回
                    │  (常驻,轻)      │  加表情、启动自动开通、投递任务
                    └────────┬────────┘
                             │ 只写数据库，不执行业务
                             ▼
        ┌────────────────────────────────────────────┐
        │            PostgreSQL 16                    │
        │  用户 / 会话 / 任务队列 / 待确认操作 /       │
        │  发布 outbox / 审计事实(分区)                │
        └───┬──────────────┬───────────────┬─────────┘
            │ SKIP LOCKED  │               │
            ▼              ▼               ▼
   ┌────────────────┐ ┌──────────┐ ┌────────────────┐
   │ lingxi-worker  │ │ scheduler│ │ lingxi-admin   │
   │  任务执行       │ │ 定时职责  │ │  管理 MCP 服务  │
   └───────┬────────┘ └────┬─────┘ └───────┬────────┘
           │               │               │
           │ Agent SDK     │ 发布/校验/清理  │ 按角色的受控工具
           ▼               ▼               ▼
   ┌────────────────────────────────────────────────┐
   │  用户环境  /var/lib/lingxi/users/<uid>/          │
   │  会话 JSONL · 工作目录 · 交付 Skill              │
   └───────────────┬────────────────────────────────┘
                   │
        ┌──────────┴───────────┬──────────────┐
        ▼                      ▼              ▼
    问数 MCP            飞书云盘/文档      飞书多维表格
   (外部依赖)            (交付通道)        (权限发布通道)

   JumpServer ──► 同一台机器上的同一个用户环境目录（独立会话）
```

四个常驻进程 + 一个数据库，全部跑在 `biplus-prod` 上，由一份 Docker Compose 编排。

| 进程 | 职责 | 为什么单独成进程 |
|---|---|---|
| `lingxi-gateway` | 飞书事件与卡片回调的唯一入口。验签、幂等去重、写库、立刻返回；加表情、启动自动开通、发送专用授权或管理员确认卡片。**不执行任何长任务。** | 飞书回调有超时要求，长任务阻塞入口会丢事件 |
| `lingxi-worker` | 领取任务，驱动 Claude Agent SDK 会话，流式回写卡片，触发交付 | 任务是分钟级、内存重、需按用户隔离；必须能独立限并发、独立重启 |
| `lingxi-scheduler` | 权限发布重试、MCP 同步校验轮询、保留期清理、待办超时标记 | 定时职责与请求路径无关，混在一起会让重启语义不清 |
| `lingxi-admin` | 管理 MCP 服务端 | **独立的认证面和安全边界**：管理员身份体系与业务用户完全不同，进程隔离让"业务凭据不能调用管理能力"成为部署事实而非代码约定 |

进程之间**不直接通信**，只通过数据库交换状态。这消除了服务发现、重试语义和分布式事务问题：合同里"审计写不进去就不改状态""同一待确认操作最多成功执行一次"这类要求，在单库单事务里是一行 SQL 的事，跨服务则需要 saga。

## 三、为什么是模块化单体

**决定：一个代码库、一组领域模块、四个部署单元、一个数据库。**

领域模块按合同的章节切分，模块之间只通过显式接口调用，不互相读对方的表：

```
lingxi/
  core/           领域模块（无 I/O 框架依赖）
    identity/     飞书授权、身份匹配、统一用户记录
    provisioning/ 开通状态机、用户环境、云盘目录
    permission/   数据库权限、多维表格发布、MCP 同步确认
    conversation/ 会话、话题、任务生命周期
    execution/    Agent SDK 封装、流式卡片、停止与降级
    delivery/     飞书文档/表格/图片交付
    admin/        管理能力、待确认操作、角色
    audit/        审计事实写入
  adapters/       外部系统适配：feishu / mcp / jumpserver / db
  apps/           gateway / worker / scheduler / admin 四个入口
```

### 否决的选择

**微服务。** 200 用户、单团队、无独立伸缩需求、无独立发布节奏。拆分后要付出网络边界、分布式追踪、跨服务事务的成本，换来的是零收益。合同里最难的几条约束（幂等执行、审计与状态同事务）恰恰在单库里最容易正确实现。

**单进程全包。** 飞书回调必须快速返回，而 Agent 任务是分钟级；管理面与业务面是不同的安全边界。塞进一个进程后，一次 Agent 任务 OOM 会同时打掉飞书入口和管理入口，且无法分别限并发。

**按技术分层拆服务（API 层 / 逻辑层 / 数据层）。** 这种拆法让一个业务变更横跨三个服务，是微服务的成本加单体的耦合。

**事件驱动 / CQRS。** 读写模型不复杂，没有读扩展压力，引入只会增加最终一致性的推理负担。

## 四、技术栈选型

### 语言：Python 3.12

Claude Agent SDK **官方只提供 Python 和 TypeScript**（其他语言需退化到 headless CLI `-p --output-format json`）。在两者之间选 Python：

- 飞书官方开放平台 SDK 的 Python 版本成熟，长连接、卡片、云盘、多维表格都覆盖；
- MCP 官方 `python-sdk` / FastMCP 是写管理 MCP 服务端最短的路径；
- 数据与分析场景的库生态更贴合本产品的领域。

代价是异步并发模型不如 Node 直观。用 `asyncio` + 明确的进程级并发上限管理，而不是靠线程池。

**否决**：TypeScript（虽然它比 Python 多出 `SessionStart` / `SessionEnd` 等 SDK 回调，但飞书与 MCP 生态在本场景下不占优；会话生命周期可由 Lingxi 编排层可靠记录）；Go / Rust（Agent SDK 无官方支持，只能退化到 CLI 子进程并自行重建会话、工具事件与取消控制的集成边界）。

### 数据库：PostgreSQL 16

| 需要的能力 | PostgreSQL 提供 | 用在哪 |
|---|---|---|
| 无中间件的任务队列 | `SELECT … FOR UPDATE SKIP LOCKED` | 任务领取、发布 outbox 消费 |
| 免轮询唤醒 | `LISTEN` / `NOTIFY` | gateway 投递任务后立即唤醒 worker |
| 分区 + 受限到期清理 | 原生分区表、`expires_at` 与受限清理函数 | 审计、聊天及其他用户内容以每条记录的精确到期时间为上界；分区只优化已全部到期的数据删除，不能把实际保留延长到九十天以上 |
| 半结构化字段 | `JSONB` + GIN | 卡片状态快照、MCP 原始返回摘要、审计明细 |
| 写权限收紧 | 表级 `GRANT` + 触发器 | 审计表对应用角色只给 `INSERT`，`UPDATE`/`DELETE` 由触发器拒绝 |

**否决**：MySQL（分区裁剪与 `SKIP LOCKED` 可用，但 `LISTEN/NOTIFY`、`JSONB` 索引与行级安全的组合不如 PG 原生，且本项目无历史包袱）；SQLite（多进程并发写与分区不适用）；引入 Redis / RabbitMQ / Celery（见下）。

### 不引入消息中间件

任务队列直接建在 PostgreSQL 上。理由：

1. **量级不成立。** 200 用户的峰值任务数是每分钟个位数，`SKIP LOCKED` 在普通硬件上可支撑每秒数百次领取，余量三个数量级。
2. **一致性要求指向单库。** 合同要求"写操作的审计记录无法可靠保存时，用户状态不得改变"和"同一待确认操作最多成功执行一次"。任务状态、审计、业务状态在同一个事务里提交，天然满足；引入 broker 后就需要 outbox + 幂等消费者来重新达到同样的保证——为了避免这个复杂度而引入 broker，是本末倒置。
3. **少一个有状态系统。** 多一个 broker 就多一份备份、监控、版本升级和故障模式，而它不减少任何一项**已经发生**的成本。

**唯一保留的例外**：如果未来出现跨机器的 worker，或单机任务量增长两个数量级，再评估。写入[复审条件](#十一复审条件)。

### 不引入 Redis

需要跨进程共享的状态只有一处：飞书 API 的全局限流配额。飞书流式卡片的限额是 **1000 次/分、50 次/秒**，而本产品在 200 用户规模下的峰值更新频率约为并发话题数 × 2 次/秒（见[流式卡片](#63-流式卡片与降级)），距离上限有一个数量级余量。因此各进程用本地令牌桶 + 保守配额分配即可，不需要共享计数器。

### 部署：单机 Docker Compose

**否决 systemd 直接跑进程**：`docs/协作约定.md` 要求"合并并冻结明确版本；上线时不得在 `biplus-prod` 重新修改或临时拼装"。镜像 tag 就是被冻结的版本，回滚等于切 tag 重启，这条要求变成了机制而不是纪律。裸进程部署很难阻止现场改代码。

**否决 Kubernetes**：一台机器、一个团队、200 用户。K8s 的运维面（控制平面、网络插件、存储类、证书轮转）远大于它在此规模下的收益。

## 五、执行层：Claude Agent SDK

这是全系统最关键的一层，也是最容易设计错的一层。

### 5.1 为什么是 Agent SDK 而不是别的

| 方案 | 结论 |
|---|---|
| **Claude Agent SDK**（选中） | Claude Code 作为库运行在我们的进程内。自带工具循环、上下文管理、会话持久化、hooks、子代理、MCP 客户端、Skills。产物和会话都在我们自己的机器上。 |
| Messages API + 手写工具循环 | 要自己实现工具循环、上下文压缩、会话恢复。这些正是 Agent SDK 已经做好且被 Claude Code 大规模验证过的部分，重写没有收益。 |
| Anthropic Managed Agents | Anthropic 托管代理循环与沙箱。**不可用**：问数 MCP 在公司内网，数据不能出网，且执行路径已约定为百炼。 |

### 5.2 会话映射（合同要求逐条落地）

Agent SDK 的会话状态是**文件系统上的 JSONL**，通过 `resume=<session_id>` 恢复。Lingxi 的会话概念比它多一层业务规则，因此**映射关系存在数据库里，JSONL 只作为上下文载体**：

```
飞书私聊主窗口 / 每个用户创建的话题
        │  一一对应
        ▼
  conversation 行  ──► agent_session_id (可为空)
        │              last_task_ended_at
        │              running_task_id (条件更新抢占，保证同话题串行)
        ▼
  Agent SDK 会话 JSONL（用户环境目录内）
```

| 合同规则 | 实现 |
|---|---|
| 不同话题并发、互不共享上下文 | 每个 `conversation` 有独立 `agent_session_id`，独立 JSONL |
| 同一话题同时只跑一个任务 | 对 `conversation.running_task_id` 做条件更新抢占（`WHERE running_task_id IS NULL`）；影响行数为 0 即返回"当前任务仍在处理中" |
| 任务运行中的消息不入历史、不排队 | gateway 判定话题忙碌后**只记审计、只回提示**，不写入 `task` 表 |
| `/new` 清空当前对话上下文 | 置 `agent_session_id = NULL`；下一条消息不带 `resume` |
| 任务结束到下一条新任务超过两小时开新会话 | 领取任务时比较 `now() - last_task_ended_at`；超过阈值则不带 `resume`，并在卡片上告知已开启新会话 |
| 任务执行时长本身不触发新会话 | 阈值只读 `last_task_ended_at`，与任务运行时长无关 |
| `/stop` 只停当前话题 | 向该任务的执行协程发取消信号；已产生的产物不撤回 |
| 飞书与 JumpServer 不共享上下文 | 两者共用同一个用户环境**目录**（这样产物可见），但 Agent 会话存储目录分开（worker 为飞书侧设置独立的会话存储路径），互相看不到对方的 JSONL |

### 5.3 用户隔离

每个用户一个 Linux 账号 + 一个家目录 `/var/lib/lingxi/users/<internal_user_id>/`：

- worker 以该用户身份启动 Agent SDK 子进程，文件权限即隔离边界；
- JumpServer 登录进的是同一个家目录，因此产物、工作文件在两个入口下一致（合同要求"路径、归属和访问控制与飞书私聊完全一致"）；
- 用户环境里**不放任何凭据**。飞书交付和问数 MCP 都通过持有凭据的本机服务代理，见 [6.7 交付](#67-交付凭据不进用户环境)；
- Agent SDK 显式使用独立 cwd，不加载用户或项目设置源（Python `setting_sources=[]`），不启用自动记忆；只读挂载经审核的 Skills，用户不能修改共享 Skill 或借此加载额外 hooks；
- 子进程只保留切换目标 uid 和完成当前任务所必需的最小 capability；完成 uid/gid 切换后立即丢弃 `CAP_SETUID` / `CAP_SETGID`，不向 Agent 会话暴露容器管理或宿主机管理能力。

**容器化与用户身份的衔接**：worker 跑在容器里，而 JumpServer 用户登录的是宿主机 shell，两者必须落到同一组 uid 上，否则文件权限不一致。约定：

- 用户的 Linux 账号与 uid 由**宿主机**统一分配，`internal_user_id → uid` 的映射存在数据库里；
- worker 容器以 `--userns=host` 共享宿主机 uid 空间，绑定挂载 `/var/lib/lingxi/users`，并持有 `CAP_SETUID` / `CAP_SETGID`，在启动 Agent SDK 子进程前切换到目标 uid；
- 容器本身不管理账号，只使用 uid——避免容器内外两套用户库需要同步。

这是本设计里"容器化部署"与"按操作系统用户隔离"之间唯一的耦合点，实现时必须显式处理，不能默认容器内的 uid 与宿主机一致。

### 5.4 SDK 回调与编排层共同形成审计采集点

[Claude Agent SDK 官方 hooks 对照表](https://code.claude.com/docs/en/agent-sdk/hooks)显示，Python SDK 支持 `PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`Stop` 等回调，但**不支持** `SessionStart` / `SessionEnd` SDK callback。Lingxi 不通过启用项目设置文件中的 shell hooks 绕过这个限制，因为那会与 `setting_sources=[]` 的多用户隔离边界冲突。

合同要求的审计事实由 SDK 回调与 Lingxi 自己的任务编排层共同产生：

| 来源 | 采集的审计事实 |
|---|---|
| `PreToolUse` | 即将调用的 MCP 工具与参数摘要（脱敏后） |
| `PostToolUse` | 调用结果状态、数据范围摘要、耗时 |
| `PostToolUseFailure` / `Stop` | 工具失败、任务停止与终止原因 |
| Lingxi 编排层 | 在创建、恢复、轮换和结束 Agent 会话的同一事务中记录会话开始与结束、所属话题、任务和权限版本 |

审计写入失败的处理按合同分级：**读路径**（问数）审计失败记告警但不中断用户；**写路径**（管理动作、状态变更）审计失败则不改状态。

### 5.5 Skills 是交付能力的载体

合同要求"高级工作台中产生的正式产物通过统一的交付 Skill 完成交付"，并且"用户取得产物的路径、归属和访问控制与飞书私聊完全一致"。

Agent SDK 原生支持 `.claude/skills/<name>/SKILL.md`。因此：把交付实现成一个 Skill，注入每个用户环境；飞书 worker 与 JumpServer CLI 加载的是**同一份文件**。"两个入口交付一致"从此是部署事实，不是需要两处维护的约定。

## 六、核心机制

本节逐条对齐合同里最容易实现错的硬要求。

### 6.1 飞书接入：长连接而非 Webhook

`biplus-prod` 在公司内网，没有公网入站。用飞书开放平台的**长连接（WebSocket）**订阅事件与卡片回调，避免为了一个回调地址去开公网入口、配证书和反向代理——那会引入一条与产品无关的攻击面。

[飞书开放平台的卡片回调说明](https://open.feishu.cn/document/feishu-cards/card-callback-communication)已记载 `card.action.trigger` 可以通过长连接接收，因此机制不再标为“完全未知”。仍须在 `biai-stage` 使用本项目选定的 Python SDK 版本验证事件注册、操作者身份和重复回调；若当前 SDK 组合不成立，则仅卡片回调改为受控 HTTP 端点，消息事件仍走长连接。

**幂等**：飞书会重投事件。gateway 以飞书 `event_id` 为唯一键先落 `inbound_event` 表，冲突即认为重复，直接返回成功。这让"重复投递不产生重复任务"成为数据库约束而非代码判断。

### 6.2 任务队列与并发

```sql
-- worker 领取任务
UPDATE task SET status='running', worker_id=$1, started_at=now()
WHERE id = (
  SELECT id FROM task
  WHERE status='queued' AND scheduled_at <= now()
  ORDER BY scheduled_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *;
```

- **跨话题并发**：worker 进程内 `asyncio` 并发执行多个任务，上限由配置控制（默认 16）。
- **同话题串行**：由 `conversation.running_task_id` 的条件更新抢占保证（见[数据库设计](数据库设计.md#同话题串行靠条件更新不靠唯一索引)），与队列无关。
- **唤醒**：gateway 入队后 `NOTIFY task_queued`；worker `LISTEN` 到即领取。兜底轮询 2 秒一次，避免通知丢失导致任务永久滞留。
- **worker 崩溃**：`task.heartbeat_at` 超过阈值的 `running` 任务由 scheduler 重置为 `queued`，重试次数用尽转失败并通知用户。

### 6.3 流式卡片与降级

飞书 CardKit 的硬约束：卡片实体有效期 **14 天**、需 `update_multi=true` 的 JSON 2.0 结构、**序列号严格递增**、限流 **1000 次/分、50 次/秒**。

`CardStream` 组件的行为：

1. 任务开始时创建卡片实体，记 `card_id` 与初始序列号；
2. 订阅 Agent SDK 的消息流，在内存里聚合成"当前动作 + 已耗时 + 回答区内容"；
3. **按固定节流间隔推送**（默认 500ms，即每话题 2 次/秒），且内容无变化不推送；
4. 序列号由该任务内的单调计数器给出，保证递增；
5. 进程级令牌桶兜住全局 50 次/秒；
6. **任何一次创建/更新/关闭失败** → 停止卡片路径，在同一私聊或同一话题用普通文本补发完整结果（合同要求），并记审计。

合同要求状态区展示"当前动作 + 低频耗时"、完成时展示"已完成 + 总耗时"、**不展示预计剩余时间、不展示内部工具调用与过程日志**——因此 `PreToolUse` 采集的工具名只进审计，不进卡片；卡片上的"当前动作"是业务语言的映射表（如 `mcp 查询` → `正在查询数据`）。

### 6.4 权限发布与 MCP 同步确认

合同把"开通成功"押在一条硬门槛上：**发布完成后必须确认当前用户的 MCP 权限已同步且可以问数，立即校验 + 每三分钟一次 + 最多十五分钟，超时转人工。**

```
数据库权限变更
   │ 同一事务
   ▼
publish_outbox 行 (pending)
   │ scheduler/worker 消费
   ▼
写飞书多维表格 ──► 记录发布结果
   │ 成功
   ▼
provisioning_state = 'mcp_syncing'
   │ 立即一次，之后每 180s，最多 15 分钟
   ▼
回读 permission_version + companies/functions，与数据库当前版本逐项比对
   │ 一致
   ▼
以该用户身份对问数 MCP 发一次最小查询
   ├─ 明确成功 ──► provisioning_state='active'，发送开通成功卡片
   └─ 超时     ──► provisioning_state='manual_review'，建管理待办 + 通知用户"已转交处理，无需重复开通"
```

明确空结果只能证明本次查询没有报错，不能证明权限范围已经同步；版本或范围字段缺失、不一致都保持 `mcp_syncing`。MCP 侧需提供可比对字段的要求并入 Issue #11 的外部能力验证。

用 **outbox 模式**（业务写入与发布意图同事务落库，异步投递）而不是"改完权限直接调飞书 API"：后者在飞书调用失败时会留下数据库已改、发布未做的静默不一致，而合同明确要求两者不一致时不得视为发布完成。

`mcp_sync_check` 每次尝试独立记录，用于事后判断"十五分钟是不是一个现实的上限"——这是当前能力里登记的未验证依赖，需要真实数据来复审。

### 6.5 管理 MCP 与待确认操作

每次管理 MCP 调用先把个人凭据解析为唯一 `admin_identity`，再经其绑定的 `app_user` 取得本人飞书 `open_id` 和当前角色。`pending_action.initiated_by`、卡片接收人、回调点击人都必须回到同一 `admin_identity`；映射缺失、重复或变化时默认拒绝。

**执行最多一次**是这里的核心安全属性。实现：

```sql
-- 卡片回调确认时
UPDATE pending_action
SET status='executing', confirmed_by=$1, confirmed_at=now()
WHERE id=$2
  AND status='pending'
  AND expires_at > now()
  AND initiated_by=$1                    -- 只有发起人本人
  AND target_state_version=$3            -- 目标状态未变
RETURNING *;
-- 影响行数为 0 → 不执行，回复"状态已变化，请重新查询"
```

随后在**同一个事务**里：写审计 → 改业务状态 → `status='executed'`。任一步失败则整体回滚，`pending_action` 保持 `pending` 或转 `failed`，用户状态不变——直接满足合同的"审计无法写入时一律不执行"。

角色（权限管理员 / 运维管理员 / 超级管理员）在管理 MCP 的工具注册阶段过滤：**当前身份没有的角色，对应工具根本不出现在工具列表里**，而不是调用后拒绝。这样 AI Agent 不会看到它无权使用的能力，减少误导和无谓尝试。

“从当前运行环境删除用户”不是只把 `account_state` 改成一个软状态：确认后先切到 `deleting` 阻止新问数和交付，再用可恢复编排清理当前环境中的身份、权限、Agent 会话、任务内容与其他可识别运行数据；全部完成并写入脱敏审计后才进入 `deleted`。任一步失败保持不可用但未完成状态，不宣告成功。该编排不修改数据库备份、WAL 归档和用户目录备份；恢复历史备份可能重新带回历史用户内容。

超级管理员角色不增加“最后一名”数据库并发约束。若系统中已无超级管理员，普通管理入口暂停角色维护，由持有服务器 Root 权限的 Ops 运维工程师在数据库所有者权限下，把一个身份已经核实并绑定飞书的现有用户恢复为超级管理员。恢复能力不进入管理 MCP；恢复必须记录目标用户、操作者、时间与结果，上线前在受控环境演练并留下脱敏证据。

### 6.6 审计

```sql
CREATE TABLE audit_event (...) PARTITION BY RANGE (occurred_at);
-- 每条记录有精确 expires_at；受限清理函数先删除到期行，
-- 只有整个分区全部到期后才 DROP，分区不能延长保留期
REVOKE UPDATE, DELETE ON audit_event FROM lingxi_app;
-- 再加触发器拒绝普通 UPDATE/DELETE；只放行专用函数对已到期行的清理
```

- **append-only**：应用角色只有 `INSERT`；普通 `UPDATE`/`DELETE` 由权限与触发器双重阻断，已到期行只能经专用清理函数删除。
- **最长九十天**：每条正常运行中的可识别内容写入时计算 `expires_at = occurred_at + interval '2160 hours'`；scheduler 小批量调用受限清理函数，超过到期时间仍可识别视为保留违规并告警。分区只用于批量回收已经全部到期的数据。
- **写路径同事务**：状态变更与其审计在同一事务；审计失败即状态不变。
- **脱敏**：合同要求"不在审计中保存凭据、完整令牌或无关个人信息"。审计写入统一走一个 `redact()` 出口，字段白名单制——新增字段默认不记录，必须显式加入白名单。

### 6.7 交付：凭据不进用户环境

这是一条容易做错的安全边界。JumpServer 用户在自己的环境里有 shell，**任何放进用户环境的飞书凭据都等于交给用户**。

因此交付 Skill 不持有凭据，它通过本机 Unix domain socket 调用内部交付端点：

```
用户环境内的交付 Skill
   │ Unix domain socket → SO_PEERCRED 取得真实 uid
   ▼
lingxi 交付服务（持有机器人凭据）
   │ 校验：调用者身份 = 该用户环境所属用户
   ▼
飞书云盘：在该用户专属目录内创建 → 授权本人 → 确认授权成功 → 返回链接
```

合同要求"交付物的访问授权必须实际完成，才能宣告交付完成"——因此交付端点在**授权 API 返回成功之后**才回报成功；授权未确认时返回"送达状态不确定"，由 Agent 按合同措辞告知用户核对，且不自动重发。

### 6.8 高级工作台

JumpServer 承担登录、终端和会话审计，Lingxi 不重复实现。Lingxi 侧只需保证：

- 用户环境目录与飞书侧是同一个（产物一致）；
- 会话存储分开（上下文不共享）；
- 交付 Skill 已注入；
- MCP 凭据只由 Lingxi 的本机 MCP 代理服务持有；用户环境通过 Unix domain socket 调用，代理用 `SO_PEERCRED` 将真实 uid 映射到用户及其当前权限，不信任请求体中的用户标识。shell 环境、进程参数、用户目录和 Agent 子进程均不出现 MCP 凭据。

审批流程在飞书开通链路之外（合同规定），Lingxi 不实现审批，只在管理 MCP 里提供"标记某用户已获批高级工作台"的受控写操作。

## 八、部署与发布

```
biplus-prod
└── docker compose（一份 compose 文件，镜像 tag = 冻结的版本）
    ├── postgres        数据卷 + 每日逻辑备份 + WAL 归档
    ├── lingxi-gateway
    ├── lingxi-worker   挂载 /var/lib/lingxi/users
    ├── lingxi-scheduler
    └── lingxi-admin
```

- **版本冻结**：合并后 CI 构建镜像并打 tag；`biplus-prod` 只拉 tag，不构建。
- **回滚**：改 compose 里的 tag 后重启。数据库迁移用 Alembic，要求每个迁移可前滚，破坏性变更拆成"先加后删"两次发布，保证回滚时旧镜像仍能工作。
- **验收环境**：`biai-stage` 用同一份 compose，连 `Bot-Test` 与独立测试数据库。2026-07-28 实测：Docker `25.0.14`、Docker Compose `v5.2.0`，测试用 PostgreSQL 容器在运行，`Bot-Test` 凭据与百炼端点已配置并完成过真实受控验证；早先"1.22 且服务未运行"的记录已失效。Lingxi 自己的 compose 编排文件尚未落地。
- **恢复入口**：`docker compose down && docker compose up -d`；数据库从每日备份 + WAL 恢复。用户环境目录单独备份（内含用户产物与会话）。这些灾备副本不受正常运行内容的九十天期限或单用户删除操作影响，保存时间由公司的灾备与恢复规则决定，也不作为正常问数、找回、质量复核或日常审计入口；恢复历史备份可能重新带回备份时已有的用户内容。

## 十、明确不做的

按"不做过多冗余设计"的要求，以下在首期明确不做，并写明触发重新评估的条件：

| 不做 | 触发重评的条件 |
|---|---|
| 微服务拆分 | 出现独立伸缩或独立发布节奏的真实需求 |
| Kubernetes / 多机部署 | 单机资源不足，或需要可用性 SLA |
| 消息中间件（Redis / RabbitMQ / Celery） | 跨机 worker，或任务量增长两个数量级 |

| 网页管理后台 | 见[管理员 AI Agent 与飞书确认边界决策](../决策记录/2026-07-26-管理员AI-Agent与飞书确认边界.md)的复审条件 |
| 自动扩缩容、熔断降级框架 | 出现真实的容量或级联故障问题 |
| 多模型路由 / 模型 A/B | 见[仅提供 Claude 执行路径决策](../决策记录/2026-07-25-仅提供Claude执行路径.md) |

## 十一、复审条件

出现以下任一情况时，本文需要整体复审而不是局部修补：

- 用户规模超过约 1000，或峰值并发任务超过 50；
- 从单机扩展到多机，或引入可用性 SLA；
- Claude Agent SDK 不再是产品执行路径，或百炼兼容端点无法支撑 Agent SDK 所需能力；
- 问数 MCP 的职责边界变化（例如要求 Lingxi 承担数据权限过滤）；
- 飞书长连接、CardKit 流式更新或云盘权限模型发生不兼容变化；
- 管理入口从"AI Agent + 管理 MCP + 飞书确认"改为其他形态；
- 产品合同中的会话、并发、保留或审计规则发生实质变化。
