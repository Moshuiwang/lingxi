## 一、约束前提

下面五条是全部选型的依据。**任何一条变化都要回到本文复审**，而不是在实现里悄悄适配。

| 约束 | 具体值 | 对架构的影响 |
|---|---|---|
| 用户规模 | 面向约 200 名内部用户；首期三名真实试用 | 峰值并发任务预计十余个，不需要水平扩展、分库分表或服务网格 |
| 使用场景 | 公司内部、单租户、非 7×24 关键链路 | 可以接受分钟级恢复，不需要多活或自动故障转移 |
| 团队构成 | 无其他人类开发者，由 AI 代理协作实现与维护 | 优先“少而清晰的组件、强类型约束、能被静态检查发现的错误”，而不是靠人的默契 |
| 部署环境 | 单台生产服务器 `biplus-prod`，公司内网 | 单机部署；不引入需要独立集群的中间件 |
| 执行路径 | Claude Code + 百炼（见[仅提供 Claude 执行路径决策](../决策记录/2026-07-25-仅提供Claude执行路径.md)） | 执行层用 Claude Agent SDK，不是 Messages API 手写循环，也不是 Anthropic 托管的 Managed Agents |

**关于「Claude Code + 百炼」的技术含义**：产品的 AI 执行路径是 Claude Agent SDK（Claude Code 以库的形式运行在我们自己的进程里），模型调用指向百炼提供的兼容端点。这意味着 Anthropic 平台侧的托管能力——Managed Agents、服务端工具、Files API、各类 beta 特性——**默认不可用，架构不得依赖**。可用的是 Agent SDK 本地侧的能力：内置工具、会话、hooks、子代理、MCP 客户端、Skills。

> **开工门禁**：在开始依赖执行层的业务实现前，必须在 `biai-stage` 通过下列三项。第四项已有外部证据，不重跑。门禁执行与实测结论见 [Issue #23](https://github.com/Moshuiwang/lingxi/issues/23)，事实汇总见[当前能力](../当前能力.md)。
>
> 1. **管道模式下的终止事件——已通过（2026-07-28）**。用 Python Agent SDK `0.2.128`（自带 Claude Code CLI `2.1.220`）连续跑 40 个回合（含新建会话、`resume` 恢复与两会话交替），40/40 收到非空最终正文和恰好一次终止结果，正式回合 39/39 的最终助手正文与终止结果哈希一致。结论限于该固定版本与端点组合：Agent SDK 的双向流式模式与前身项目复现故障的 `-p` 一次性模式不同，非 TTY 管道本身不再被当作承重未知。仍保留终止事件缺失监控，并且不得对已产生工具副作用的回合自动重放。背景见[Claude 执行链路的已验证事实与管道投递风险](../参考证据/Claude执行链路的已验证事实与管道投递风险.md)。
> 2. **Skill 与审计采集点——已通过（2026-07-28 补测）**。受控 Skill 可实际加载，`PreToolUse`（188 次）、`PostToolUse`（188 次）、`Stop`（40 次）可采集。定向补测中 2 次真实工具执行失败（MCP 协议层 `isError=true`、MCP 进程调用中退出）均触发 `PostToolUseFailure` 且 `PostToolUse` 为 0，回调带工具名、入参与错误文本。**但审计链有两处必须由执行层自己补齐**：`PostToolUseFailure` 只覆盖「工具抛错」，被 MCP 包成正常响应的业务失败不触发它；权限拒绝没有任何 hook 回调（`PermissionDenied` / `PermissionRequest` 均为 0，且已确认不是事件名没注册上），只能靠自己在 `PreToolUse` 记账的拒绝决定加消息流中 `is_error=True` 的工具结果块合成。不需要为此改用 TypeScript SDK。
> 3. **运行时工具边界——已通过（2026-07-28 补测），但必须由执行层实现**。第一轮中模型执行了一次未被明确禁用的 `CronCreate`（随后由 `CronDelete` 删除），证明 `allowed_tools` 加 `permission_mode="dontAsk"` **不是**严格白名单。补测在 `disallowed_tools` 完全为空、hook 为唯一屏障的条件下确认：**在 `PreToolUse` 返回拒绝是执行前的真阻止**——3 次非白名单调用（`Bash`、`Write`、`CronCreate`）全部被拒且无 `PostToolUse`，文件副作用探针确认目标文件未创建，无 cron 残留；被拒回合仍正常收口，同回合内白名单工具照常执行。因此执行层**必须**实现默认拒绝、只放行显式白名单的 `PreToolUse` 屏障，新增内置工具自动落入拒绝分支。**该屏障的判定与审计组件已由 [Issue #29](https://github.com/Moshuiwang/lingxi/issues/29) 实现**（`lingxi.core.execution`），**已于 [Issue #37](https://github.com/Moshuiwang/lingxi/issues/37)（commit `0b70944`）经 `adapters/claude_agent_session.py` 的 `build_hook_matchers()` 装进真实 `ClaudeAgentOptions.hooks`，且 `lingxi-worker-queue` 自 2026-08-21 起在 `biai-stage` 真实运行、经此路径调用同一个 `ToolGateway`——组件已有生产调用方**；证据层级仍分项登记：`V-执行-01`/`V-执行-05` 已 L4a 真实复验，其余 `V-执行-02…21` 多数为 L2，见[验收矩阵](验收矩阵.md)逐条状态，不得整体上浮为 L4a。
> 4. **会话、恢复与 MCP 调用经百炼兼容端点运行**——前身项目已在真实百炼端点取得可回读证据（新建与恢复会话、只读 MCP 调用与回执、终止事件），不作为 Lingxi 的重跑项；证据与其边界见上述参考证据。
>
> **四项均已通过，跨切片开工门禁解除。**第 2、3 项通过的是「机制可行」；拒绝式白名单与合成审计链的组件**已于 commit `0b70944`（Issue #37）接入真实入口**，`lingxi-worker-queue` 是其生产调用方（2026-08-21 起在 `biai-stage` 运行）。**这不等于全部 `V-执行-01…21` 已经真实复验**：多数断言仍是 L2（CI 通过），只有 `V-执行-01`/`V-执行-05` 取得 L4a 真实回合证据（见[验收矩阵](验收矩阵.md)）；据此仍不得笼统宣称「工具失败可完整审计」，须按断言逐条引用其实际层级。

## 二、架构总览

```text
                        飞书开放平台
                             │
              长连接(WebSocket) │ 事件 + 卡片回调
                             ▼
                    ┌─────────────────┐
                    │ lingxi-gateway  │  通道级认证 → 幂等 → 落库 → 立即返回
                    │  (常驻,轻)      │  加表情、启动自动开通、投递任务、
                    │                 │  受理管理员 `/admin` 命令面（方案 A）
                    └────────┬────────┘
                             │ 只写数据库，不执行业务
                             ▼
        ┌────────────────────────────────────────────┐
        │            PostgreSQL 16                    │
        │  用户 / 会话 / 任务队列 / 待确认操作 /       │
        │  发布 outbox / 审计事实(分区)                │
        └───┬──────────────────────┬─────────────────┘
            │ SKIP LOCKED          │
            ▼                      ▼
   ┌─────────────────────┐  ┌──────────┐
   │ lingxi-worker-queue │  │ scheduler│
   │  (常驻)              │  │ 定时职责  │
   │  任务执行             │  │          │
   └──────────┬───────────┘  └────┬─────┘
              │                   │
              │ Agent SDK         │ 发布/校验/清理
              ▼                   ▼
   ┌────────────────────────────────────────────────┐
   │  用户环境  /var/lib/lingxi/users/<uid>/          │
   │  会话 JSONL · 工作目录 · 交付 Skill              │
   └───────────────┬────────────────────────────────┘
                   │
        ┌──────────┴───────────┬──────────────┐
        ▼                      ▼              ▼
    问数 MCP            飞书云盘/文档      飞书多维表格
   (外部依赖)            (交付通道)        (权限发布通道)
```

`lingxi-admin`（管理 MCP 服务端）不在上图中：它是**目标形态，尚未实现**——无代码、无镜像；MVP 现行管理入口是方案 A 私聊命令面，住在 `lingxi-gateway`（详见「六、核心机制 · 6.5」与[产品合同「管理员处理入口与安全确认」](../产品合同与外部边界.md)）。一次性作业 `lingxi-worker`（单回合 CLI）、`lingxi-migrate`、`lingxi-reauthorize` 不常驻，不出现在上图的稳态拓扑中，执行细节见「八、部署与发布」与 `deploy/README.md`。（上图是进程级拓扑，不是代码目录结构；仓库内部划分现状以[代码框架](代码框架.md)为准。）

JumpServer 高级工作台已于 2026-08-28 由产品负责人裁定取消（[决策记录](../决策记录/2026-08-28-取消JumpServer高级工作台.md)），上图不再包含它作为入口；历史设计曾让 JumpServer 与飞书 worker 共用同一台机器上的同一个用户环境目录，该耦合点随之作废。

目标生产形态是在 `biplus-prod` 运行由 Docker Compose 编排的常驻进程；PostgreSQL 由 **Supabase 云托管**（测试与生产两套实例，[Issue #40](https://github.com/Moshuiwang/lingxi/issues/40) 决策，数据边界已获产品负责人 2026-08-05 确认），各进程经出网链路连接。本地开发可用本机数据库。**现状**：`biai-stage` 自 2026-08-21 起已用这套 Compose 的 `mvp` profile 真实运行 `scheduler`/`gateway`/`worker-queue` 三容器，且已于 2026-08-29 切换至 Supabase 测试实例（[Issue #411](https://github.com/Moshuiwang/lingxi/issues/411)：迁移前滚＋全量数据迁移＋真实用户路径冒烟通过，见「八、部署与发布」验收环境一节）；`biplus-prod` 仍未安装。实际可用能力以[当前能力](../当前能力.md)为准。

| 进程 | 职责 | 为什么单独成进程 |
|---|---|---|
| `lingxi-gateway` | 飞书事件与卡片回调的唯一入口。验签、幂等去重、写库、立刻返回；加表情、启动自动开通、发送专用授权或管理员确认卡片；受理管理员 `/admin` 命令面（方案 A，见「六、核心机制 · 6.5」）。**不执行任何长任务。** | 飞书回调有超时要求，长任务阻塞入口会丢事件 |
| `lingxi-worker-queue` | 常驻队列消费者：领取任务，驱动 Claude Agent SDK 会话，流式回写卡片，触发交付；与一次性作业 `lingxi-worker`（单回合受控执行 CLI）**同镜像**，靠 `LINGXI_WORKER_MODE=queue` 切换常驻分支，见 `deploy/README.md` | 任务是分钟级、内存重、需按用户隔离；必须能独立限并发、独立重启 |
| `lingxi-scheduler` | 权限发布重试、MCP 同步校验轮询、专用授权凭据（“四达文档会议助手”`refresh_token`）到期轮换、保留期清理、待办超时标记、**首次开通编排**（2026-08-18 裁定：在职状态必须实时回读，而那条一次性 `refresh_token` 的唯一合法消费者在本进程，见[决策记录](../决策记录/2026-08-18-首次开通编排住在scheduler.md)） | 定时职责与请求路径无关，混在一起会让重启语义不清 |
| `lingxi-admin`（**目标形态，尚未实现**） | 管理 MCP 服务端；当前无代码、无镜像，是触发式未来入口，不出现在现行拓扑中 | **独立的认证面和安全边界**：管理员身份体系与业务用户完全不同，进程隔离让"业务凭据不能调用管理能力"成为部署事实而非代码约定；该理由是本进程的设计依据，落地前由方案 A（`lingxi-gateway` 内的私聊命令面）承接现行管理入口 |

进程之间**不直接通信**，只通过数据库交换状态。这消除了服务发现、重试语义和分布式事务问题：合同里"审计写不进去就不改状态""同一待确认操作最多成功执行一次"这类要求，在单库单事务里是一行 SQL 的事，跨服务则需要 saga。

## 三、为什么是模块化单体

**决定：一个代码库、一组领域模块、四个部署单元、一个数据库。**

领域模块按合同的章节切分，模块之间只通过显式接口调用，不互相读对方的表：

```
lingxi/
  core/           领域模块（无 I/O 框架依赖）
    identity/     飞书授权、身份匹配、统一用户记录
    provisioning/ 开通状态机、用户环境、云盘目录
    permission/   数据库权限、多维表格发布、MCP 同步确认
    conversation/ 会话、话题、任务生命周期
    execution/    Agent SDK 封装、流式卡片、停止与降级
    delivery/     飞书文档/表格/图片交付
    admin/        管理能力、待确认操作、角色
    audit/        审计事实写入
  adapters/       外部系统适配：feishu / mcp / jumpserver / db
  apps/           gateway / worker / scheduler / admin 四个入口
```

以上是领域切分的目标形态，不是逐字的目录清单（例如 `provisioning/`、`audit/` 未新建为独立目录，`jumpserver` 适配随 2026-08-28 决策作废）；仓库实际布局现状以[代码框架](代码框架.md)「一、仓库布局」为准。

### 否决的选择

**微服务。** 200 用户、单团队、无独立伸缩需求、无独立发布节奏。拆分后要付出网络边界、分布式追踪、跨服务事务的成本，换来的是零收益。合同里最难的几条约束（幂等执行、审计与状态同事务）恰恰在单库里最容易正确实现。

**单进程全包。** 飞书回调必须快速返回，而 Agent 任务是分钟级；管理面与业务面是不同的安全边界。塞进一个进程后，一次 Agent 任务 OOM 会同时打掉飞书入口和管理入口，且无法分别限并发。

**按技术分层拆服务（API 层 / 逻辑层 / 数据层）。** 这种拆法让一个业务变更横跨三个服务，是微服务的成本加单体的耦合。

**事件驱动 / CQRS。** 读写模型不复杂，没有读扩展压力，引入只会增加最终一致性的推理负担。

## 四、技术栈选型

### 语言：Python 3.12

Claude Agent SDK **官方只提供 Python 和 TypeScript**（其他语言需退化到 headless CLI `-p --output-format json`）。在两者之间选 Python：

- 飞书官方开放平台 SDK 的 Python 版本成熟，长连接、卡片、云盘、多维表格都覆盖；
- MCP 官方 `python-sdk` / FastMCP 是写管理 MCP 服务端最短的路径；**实现时必须选用已支持 `2026-07-28` 的版本**——该版本是破坏性修订，旧版 SDK 写出的服务端不满足无握手、`server/discover` 等强制要求；
- 数据与分析场景的库生态更贴合本产品的领域。

代价是异步并发模型不如 Node 直观。用 `asyncio` + 明确的进程级并发上限管理，而不是靠线程池。

**否决**：TypeScript（虽然它比 Python 多出 `SessionStart` / `SessionEnd` 等 SDK 回调，但飞书与 MCP 生态在本场景下不占优；会话生命周期可由 Lingxi 编排层可靠记录）；Go / Rust（Agent SDK 无官方支持，只能退化到 CLI 子进程并自行重建会话、工具事件与取消控制的集成边界）。

### 数据库：PostgreSQL 16

| 需要的能力 | PostgreSQL 提供 | 用在哪 |
|---|---|---|
| 无中间件的任务队列 | `SELECT … FOR UPDATE SKIP LOCKED` | 任务领取、发布 outbox 消费 |
| 免轮询唤醒 | `LISTEN` / `NOTIFY` | gateway 投递任务后立即唤醒 worker |
| 分区 + 受限到期清理 | 原生分区表、`expires_at` 与受限清理函数 | 审计、聊天及其他用户内容以每条记录的精确到期时间为上界；分区只优化已全部到期的数据删除，不能把实际保留延长到九十天以上 |
| 半结构化字段 | `JSONB` + GIN | 卡片状态快照、MCP 原始返回摘要、审计明细 |
| 写权限收紧 | 表级 `GRANT` + 触发器 | 审计表对应用角色只给 `INSERT`，`UPDATE`/`DELETE` 由触发器拒绝 |

**否决**：MySQL（分区裁剪与 `SKIP LOCKED` 可用，但 `LISTEN/NOTIFY`、`JSONB` 索引与行级安全的组合不如 PG 原生，且本项目无历史包袱）；SQLite（多进程并发写与分区不适用）；引入 Redis / RabbitMQ / Celery（见下）。

**托管（目标形态）**：生产与 `biai-stage` 验收使用 Supabase 云托管的 PostgreSQL（测试与生产两套实例互不冲突；本地开发用本机数据库）。`SKIP LOCKED`、`LISTEN/NOTIFY`、分区、触发器与角色权限均为 PG 原生能力，托管实例同样可用；跨公网连接的延迟与可用性依赖出网链路；连接池姿势已定为 Supavisor **session 模式**（`LISTEN` 兼容约束见 `deploy/README.md`「数据库凭据源」），备份按免费档自建本地逻辑备份路线执行（[#411](https://github.com/Moshuiwang/lingxi/issues/411) 产品负责人 2026-08-29 裁定，RPO 每日一次），恢复演练在生产部署前对照真实实例完成。**现状**：`biai-stage` 已于 2026-08-29 切换至 Supabase 测试实例（PostgreSQL 17.6，eu-west-1）并真实运行，`SKIP LOCKED`/`LISTEN/NOTIFY`/触发器/非超级用户建角色均已实测可用（#411）；本地开发仍用本机数据库。

### 不引入消息中间件

任务队列直接建在 PostgreSQL 上。理由：

1. **量级不成立。** 200 用户的峰值任务数是每分钟个位数，`SKIP LOCKED` 在普通硬件上可支撑每秒数百次领取，余量三个数量级。
2. **一致性要求指向单库。** 合同要求"写操作的审计记录无法可靠保存时，用户状态不得改变"和"同一待确认操作最多成功执行一次"。任务状态、审计、业务状态在同一个事务里提交，天然满足；引入 broker 后就需要 outbox + 幂等消费者来重新达到同样的保证——为了避免这个复杂度而引入 broker，是本末倒置。
3. **少一个有状态系统。** 多一个 broker 就多一份备份、监控、版本升级和故障模式，而它不减少任何一项**已经发生**的成本。

**唯一保留的例外**：如果未来出现跨机器的 worker，或单机任务量增长两个数量级，再评估。写入[复审条件](#十一复审条件)。

### 不引入 Redis

需要跨进程共享的状态只有一处：飞书 API 的全局限流配额。飞书流式卡片的限额是 **1000 次/分、50 次/秒**，而本产品在 200 用户规模下的峰值更新频率约为并发话题数 × 2 次/秒（见[流式卡片](#63-流式卡片与降级)），距离上限有一个数量级余量。因此各进程用本地令牌桶 + 保守配额分配即可，不需要共享计数器。

### 部署：单机 Docker Compose

**否决 systemd 直接跑进程**：`docs/协作约定.md` 要求"合并并冻结明确版本；上线时不得在 `biplus-prod` 重新修改或临时拼装"。镜像 tag 就是被冻结的版本，回滚等于切 tag 重启，这条要求变成了机制而不是纪律。裸进程部署很难阻止现场改代码。

**否决 Kubernetes**：一台机器、一个团队、200 用户。K8s 的运维面（控制平面、网络插件、存储类、证书轮转）远大于它在此规模下的收益。

## 五、执行层：Claude Agent SDK

这是全系统最关键的一层，也是最容易设计错的一层。

### 5.1 为什么是 Agent SDK 而不是别的

| 方案 | 结论 |
|---|---|
| **Claude Agent SDK**（选中） | Claude Code 作为库运行在我们的进程内。自带工具循环、上下文管理、会话持久化、hooks、子代理、MCP 客户端、Skills。产物和会话都在我们自己的机器上。 |
| Messages API + 手写工具循环 | 要自己实现工具循环、上下文压缩、会话恢复。这些正是 Agent SDK 已经做好且被 Claude Code 大规模验证过的部分，重写没有收益。 |
| Anthropic Managed Agents | Anthropic 托管代理循环与沙箱。**不可用**：执行路径已约定为百炼，且问数 MCP 只在公司内网可达，Anthropic 托管侧无法访问。 |

### 5.2 会话映射（合同要求逐条落地）

Agent SDK 的会话状态是**文件系统上的 JSONL**，通过 `resume=<session_id>` 恢复。Lingxi 的会话概念比它多一层业务规则，因此**映射关系存在数据库里，JSONL 只作为上下文载体**：

```
飞书私聊主窗口 / 每个用户创建的话题
        │  一一对应
        ▼
  conversation 行  ──► agent_session_id (可为空)
        │              last_task_ended_at
        │              running_task_id (条件更新抢占，保证同话题串行)
        ▼
  Agent SDK 会话 JSONL（用户环境目录内）
```

| 合同规则 | 实现 |
|---|---|
| 不同话题并发、互不共享上下文 | 每个 `conversation` 有独立 `agent_session_id`，独立 JSONL |
| 同一话题同时只跑一个任务 | 对 `conversation.running_task_id` 做条件更新抢占（`WHERE running_task_id IS NULL`）；影响行数为 0 即返回"当前任务仍在处理中" |
| 任务运行中的消息不入历史、不排队 | gateway 判定话题忙碌后**只记审计、只回提示**，不写入 `task` 表 |
| `/new` 清空当前对话上下文 | 置 `agent_session_id = NULL`；下一条消息不带 `resume` |
| 任务结束到下一条新任务超过两小时开新会话 | 领取任务时比较 `now() - last_task_ended_at`；超过阈值则不带 `resume`，并在卡片上告知已开启新会话 |
| 任务执行时长本身不触发新会话 | 阈值只读 `last_task_ended_at`，与任务运行时长无关 |
| `/stop` 只停当前话题 | 向该任务的执行协程发取消信号；已产生的产物不撤回 |

> 原表还有一行「飞书与 JumpServer 不共享上下文」，随 JumpServer 高级工作台 2026-08-28 取消（[决策记录](../决策记录/2026-08-28-取消JumpServer高级工作台.md)）一并删除；该行描述的独立会话存储路径设计不再有对应的产品要求。

### 5.3 用户隔离

每个用户一个 Linux 账号 + 一个家目录 `/var/lib/lingxi/users/<internal_user_id>/`：

- worker 以该用户身份启动 Agent SDK 子进程，文件权限即隔离边界；
- **飞书凭据**不进用户环境：交付通过持有凭据的本机服务代理，见 [6.7 交付：飞书凭据不进用户环境，正式产物路径失败关闭](#67-交付飞书凭据不进用户环境正式产物路径失败关闭)；
- **问数 MCP 的逐用户令牌进用户环境**（`<家目录>/.mcp.json` 的 `Authorization: Bearer`）。这条**改写了本节此前「用户环境里不放任何凭据」的承诺**，依据是产品负责人 2026-08-17 的裁定（留痕见 [Trace #203](https://github.com/Moshuiwang/lingxi/issues/203)，长期正文见[《用户环境持有问数 MCP 令牌》决策记录](../决策记录/2026-08-18-用户环境持有问数MCP令牌.md)）。补偿措施是三条**可验证**的纪律：文件 `440`、目录 `700`、日志与异常一律脱敏（实现与用例见 `src/lingxi/adapters/user_environment.py` 与 `tests/test_user_environment.py`）。**范围只有这一个令牌**：它是该用户自己的问数权限凭据，泄露面等于他本人已有的数据范围；飞书机器人凭据、专用授权凭据、MCP 主密钥一个都不进用户环境；
- Agent SDK 显式使用独立 cwd，不加载用户或项目设置源（Python `setting_sources=[]`），不启用自动记忆；只读挂载经审核的 Skills，用户不能修改共享 Skill 或借此加载额外 hooks；
- 子进程只保留切换目标 uid 和完成当前任务所必需的最小 capability；完成 uid/gid 切换后立即丢弃 `CAP_SETUID` / `CAP_SETGID`，不向 Agent 会话暴露容器管理或宿主机管理能力。

**容器化与用户身份的衔接**：worker 跑在容器里，用户家目录在宿主机上，容器内 uid 必须与宿主机上该用户的 uid 一致，否则文件权限不一致（原设计还需兼容 JumpServer 宿主机 shell 登录，JumpServer 高级工作台已于 2026-08-28 取消，见[决策记录](../决策记录/2026-08-28-取消JumpServer高级工作台.md)）。约定：

- 用户的 Linux 账号与 uid 由**宿主机**统一分配，`internal_user_id → uid` 的映射存在数据库里；
- worker 容器以 `--userns=host` 共享宿主机 uid 空间，绑定挂载 `/var/lib/lingxi/users`，并持有 `CAP_SETUID` / `CAP_SETGID`，在启动 Agent SDK 子进程前切换到目标 uid；
- 容器本身不管理账号，只使用 uid——避免容器内外两套用户库需要同步。

这是本设计里"容器化部署"与"按操作系统用户隔离"之间唯一的耦合点，实现时必须显式处理，不能默认容器内的 uid 与宿主机一致。

**当前状态与已知边界（2026-08-19；2026-08-28 因 JumpServer 取消批注）**：上述 uid 分配与 worker 降权**尚未实现**——用户环境目录的属主是运行进程本身，因此**用户之间在操作系统层没有隔离**。产品负责人 2026-08-19 裁定本轮不实现（原设为 JumpServer 高级工作台硬前置；JumpServer 已于 2026-08-28 取消，见[决策记录](../决策记录/2026-08-28-取消JumpServer高级工作台.md)，本项因此不再有任何已排定的落地载体，约束反而更关键）。在它落地之前，用户之间不被越权读取所依赖的是执行层工具白名单只含一个只读问数工具这一层，**给 Agent 增加任何具备读文件或执行命令能力的工具前必须先回到该决策**。理由、复审条件与不采用的替代方案见[用户之间的操作系统级隔离本轮不做](../决策记录/2026-08-19-用户间操作系统级隔离本轮不做.md)。

### 5.4 SDK 回调与编排层共同形成审计采集点

[Claude Agent SDK 官方 hooks 对照表](https://code.claude.com/docs/en/agent-sdk/hooks)显示，Python SDK 支持 `PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`Stop` 等回调，但**不支持** `SessionStart` / `SessionEnd` SDK callback。Lingxi 不通过启用项目设置文件中的 shell hooks 绕过这个限制，因为那会与 `setting_sources=[]` 的多用户隔离边界冲突。

合同要求的审计事实由 SDK 回调与 Lingxi 自己的任务编排层共同产生：

| 来源 | 采集的审计事实 |
|---|---|
| `PreToolUse` | 即将调用的 MCP 工具与参数摘要（脱敏后），以及**本层的放行 / 拒绝决定**——拒绝没有任何回调，只能自己记账 |
| `PostToolUse` | 调用结果状态、数据范围摘要、耗时 |
| `PostToolUseFailure` / `Stop` | 工具失败、任务停止与终止原因 |
| SDK 消息流中的工具回执 | 用户**实际**有没有拿到结果——被 MCP 包成 `isError=false` 的业务失败不触发任何失败回调；找不到 `PreToolUse` 记录的错误回执记为「本层未判定」，用于发现规则层拦截这类审计盲区 |
| Lingxi 编排层 | 在创建、恢复、轮换和结束 Agent 会话的同一事务中记录会话开始与结束、所属话题、任务和权限版本 |

第 1、3、4 行（`PreToolUse` 的自我记账、`PostToolUseFailure`、SDK 消息流中的工具回执）合成一条审计链，缺一不可；三者的实测依据与边界见[当前能力](../当前能力.md)与 [Issue #29](https://github.com/Moshuiwang/lingxi/issues/29)。实现位于 `lingxi.core.execution`，判定逻辑不依赖 SDK，因此可在 CI 中强制执行；**该组件已于 commit `0b70944`（Issue #37）接入 `lingxi-worker-queue`，2026-08-21 起在 `biai-stage` 真实运行**——组件已有生产调用方，但审计链逐条断言的验证层级仍以[验收矩阵](验收矩阵.md)为准（多数 `V-执行-*` 为 L2，只有 `V-执行-01`/`05` 达 L4a），不得整体上浮。

审计链的两条自我约束，都是独立复查逼出来的：**执行成功但找不到本层判定记录的调用必须留痕**（否则屏障失效恰好隐身，审计还会反过来断言这一回合没有任何工具调用）；**能解析成 JSON 不等于用户拿到了结果**（既没命中失败规则、又拿不出可识别的非空数据集合时记为未知，不得当作已送达）。

审计写入失败的处理按合同分级：**读路径**（问数）审计失败记告警但不中断用户；**写路径**（管理动作、状态变更）审计失败则不改状态。

### 5.5 Skills 是交付能力的载体

Agent SDK 原生支持 `.claude/skills/<name>/SKILL.md`。把交付实现成一个 Skill，注入每个用户环境，飞书 worker 加载这份文件完成交付，与产品合同「交付规则」一节要求的路径、归属和访问控制一致。（历史设计曾以「飞书与 JumpServer 两个入口加载同一份文件」保证两入口交付一致；JumpServer 高级工作台已于 2026-08-28 取消——[决策记录](../决策记录/2026-08-28-取消JumpServer高级工作台.md)——现在只有飞书一个入口，该益处不再适用。）

## 六、核心机制

本节逐条对齐合同里最容易实现错的硬要求。

### 6.1 飞书接入：长连接而非 Webhook

`biplus-prod` 在公司内网，没有公网入站。用飞书开放平台的**长连接（WebSocket）**订阅事件与卡片回调，避免为了一个回调地址去开公网入口、配证书和反向代理——那会引入一条与产品无关的攻击面。

[飞书开放平台的卡片回调说明](https://open.feishu.cn/document/feishu-cards/card-callback-communication)已记载 `card.action.trigger` 可以通过长连接接收，因此机制不再标为“完全未知”。仍须在 `biai-stage` 使用本项目选定的 Python SDK 版本验证事件注册、操作者身份和重复回调；若当前 SDK 组合不成立，则仅卡片回调改为受控 HTTP 端点，消息事件仍走长连接。

**幂等**：飞书会重投事件。gateway 以飞书 `event_id` 为唯一键先落 `inbound_event` 表，冲突即认为重复，直接返回成功。这让"重复投递不产生重复任务"成为数据库约束而非代码判断。

### 6.2 任务队列与并发

```sql
-- worker 领取任务
UPDATE task SET status='running', worker_id=$1, started_at=now()
WHERE id = (
  SELECT id FROM task
  WHERE status='queued' AND scheduled_at <= now()
  ORDER BY scheduled_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *;
```

- **跨话题并发**：worker 进程内 `asyncio` 并发执行多个任务，上限由配置控制（默认 16）。
- **同话题串行**：由 `conversation.running_task_id` 的条件更新抢占保证（见[数据库设计](数据库设计.md#同话题串行靠条件更新不靠唯一索引)），与队列无关。
- **唤醒**：gateway 入队后 `NOTIFY task_queued`；worker `LISTEN` 到即领取。兜底轮询 2 秒一次，避免通知丢失导致任务永久滞留。
- **worker 崩溃**：`task.heartbeat_at` 超过阈值的 `running` 任务由 scheduler 重置为 `queued`，重试次数用尽转失败并通知用户。

### 6.3 流式卡片与降级

飞书 CardKit 的硬约束：卡片实体有效期 **14 天**、需 `update_multi=true` 的 JSON 2.0 结构、**序列号严格递增**、限流 **1000 次/分、50 次/秒**。

`CardStream` 组件的行为：

1. 任务开始时创建卡片实体，记 `card_id` 与初始序列号；
2. 订阅 Agent SDK 的消息流，在内存里聚合成"当前动作 + 已耗时 + 回答区内容"；
3. **按固定节流间隔推送**（默认 500ms，即每话题 2 次/秒），且内容无变化不推送；
4. 序列号由该任务内的单调计数器给出，保证递增；
5. 进程级令牌桶兜住全局 50 次/秒；
6. **任何一次创建/更新/关闭失败** → 停止卡片路径，在同一私聊或同一话题用普通文本补发完整结果（合同要求），并记审计。

合同要求状态区展示"当前动作 + 低频耗时"、完成时展示"已完成 + 总耗时"、**不展示预计剩余时间、不展示内部工具调用与过程日志**——因此 `PreToolUse` 采集的工具名只进审计，不进卡片；卡片上的"当前动作"是业务语言的映射表（如 `mcp 查询` → `正在查询数据`）。

### 6.4 权限发布与 MCP 同步确认

合同把"开通成功"押在一条硬门槛上：**发布完成后必须确认当前用户的 MCP 权限已同步且可以问数，立即校验 + 每三分钟一次 + 最多十五分钟，超时转运维处理。**

```
数据库权限变更
   │ 同一事务
   ▼
publish_outbox 行 (pending)
   │ scheduler/worker 消费
   ▼
写飞书多维表格 ──► 记录发布结果
   │  新建行：写 6 列 + Lingxi 签发的 token_cipher
   │  更新行：写 6 列，既有 token_cipher 不清空不覆盖；仅当那一列为空时补写
   │ 逐字段读回一致
   ▼
provisioning_state = 'mcp_syncing'
   │ 立即一次，之后每 180s，最多 15 分钟（受控可配置，注入时钟）
   ▼
用该用户自己的明文令牌，对问数 MCP 真实执行一次 list_metrics（探针）
   ├─ 成功且可见指标 > 0 ──► 就绪：provisioning_state='active'，发送开通成功卡片
   ├─ 数据库侧权限聚合为空 ──► 明确无权限：走银河申请指引（**不发探针**）
   ├─ 明确拒绝 / 空结果    ──► 等待中：保持 mcp_syncing，下一轮再探
   ├─ 网络/协议/解密/DB    ──► 技术失败：独立记录，可分辨，仍按节奏重试
   └─ 预算耗尽            ──► 超时：provisioning_state='manual_review'，建运行异常记录
                               + 通知用户"已转交处理，无需重复开通"
```

**判定依据是探针，不是回读比对（2026-08-17 G-155 终判改写）。** 本节原先的落法是「回读 MCP 的 `permission_version` 与生效范围、与数据库逐项比对一致后再发一次最小查询」。那条路走不通：当日对正式发布表的**全表回源核对**确认表侧**没有任何版本字段**，写进去的一行不带版本，MCP 也就无从回读一个可比对的版本号。改成探针法之后，原断言的要害一条不少：调用**以目标用户身份**发起（用他自己的令牌），**明确空结果不算就绪**（可见指标必须大于零），结论**绑定（用户，权限版本）**——服务在线、他人可用、明确空结果都不构成当前用户的就绪。断言 `V-权限-06` 的措辞已同步改写。

五路结论**互斥且不可合并**，尤其两条：**「明确无权限」只能从数据库侧的权限聚合得出，绝不从 MCP 的拒绝反推**（MCP 每十五分钟才拉一次表，把它的拒绝读成"这个人没权限"，会让一个权限完全正常的用户收到"请去银河申请权限"的终态提示）；**「技术失败」不是「等待中」，更不是「就绪」**（前者要人去看网络、凭据或数据库，后者通常下一轮就好了）。

**令牌是这条链路成立的前提**：MCP 逐行解密发布表的 `token_cipher`，与请求 Bearer 明文等值匹配，解密失败即不放行。因此 Lingxi 为建档用户签发访问令牌（明文只在内存，库里只有 AES-256-CBC 密文），**新建**发布行必须带上它；**更新**既有行时**不清空、不覆盖**那一列——既有 26 行是旧系统签发的，Lingxi 不知其明文，覆盖过去等于让那些人静默失去问数能力；**唯一的例外是那一列本来就为空**，此时补写我方密文（一行没有密文的权限对 MCP 毫无意义，而这条正是「新建成功但平台漏写那一列」与「新建结果不明后重试」的收敛出口）。逐字口径以 `V-权限-11` 为准（`V-权限-11`）。加密协议、令牌与就绪记录的表结构见迁移 `0065`，判定与状态机在 `src/lingxi/core/permission/mcp_readiness.py`。

用 **outbox 模式**（业务写入与发布意图同事务落库，异步投递）而不是"改完权限直接调飞书 API"：后者在飞书调用失败时会留下数据库已改、发布未做的静默不一致，而合同明确要求两者不一致时不得视为发布完成。

`mcp_sync_check` 每次尝试独立记录，用于事后判断"十五分钟是不是一个现实的上限"——这是当前能力里登记的未验证依赖，需要真实数据来复审。

**真实问数 MCP 的协议面尚未实测**：端点形态、`list_metrics` 的返回形状与"权限还没同步"的错误形态都按未验证登记（见 `src/lingxi/adapters/query_mcp_probe.py` 的「诚实边界」），探针的传输、拒绝分类与指标计数均为可注入实现，默认实现**读不懂就落技术失败、绝不落就绪**。真实探针留受控窗口的 L4a。

**每日刷新这一侧的落法（#156 的 S-C-03b，产品负责人 2026-08-18 裁定）**：上面那条链在常驻进程里由 `lingxi-scheduler` 的权限发布职责每轮驱动，就绪确认换成 **tick 驱动**形态——判定与节奏完全复用同一份实现，只是不阻塞调度轮；进度从 `mcp_sync_check` 重建，不新增表。三条产品语义随之明确：

- **撤权 = 保行清空**：权限从有变无时，发布表那一行留着、`permissions` 写成空对象、`status` 与 `token_cipher` 都不动。消费方的权限判定是回退制，查无任何键即拒绝，因此空对象足以表达"没有可用范围"；删行不可逆，且会连带丢掉一份我们（对既有 26 行而言）不知道明文的令牌。**只对在发布链上留下过足迹的用户做**——判据是「发布成功过，**或**当前还有 `pending`/`publishing` 的意图在途」（`has_publish_footprint`），一点足迹都没有的人跳过。「在途也算」是产品负责人 2026-08-18 决策补充 2（留痕见 Trace [#203](https://github.com/Moshuiwang/lingxi/issues/203) 的决策评论）：昨天排的授权意图还堵在 `pending` 时若跳过，等发布面消费积压，已经被收回的范围会被写进外部表并触发一条"范围已更新"通知；算进来之后撤权决定推进版本，旧意图被认领时判 `superseded`，一次外部调用都不发。
- **通知触发点**：增权在**探针成功之后**通知，撤权在**发布读回一致之后**通知（没有可等的就绪）。文案是范围式的，且不承诺即时——MCP 最长十五分钟才拉一次表。
- **通知失败**：有限重试 + 审计与可见计数，**不转运维、不阻塞权限生效、不回头改任何发布或就绪状态**。

### 6.4a 组织身份资料与多维表格关联

组织快照和多维表格是两个不同的数据面：前者通过专用 User 身份取得 `user_id`、`open_id`、`union_id`、租户、部门和状态，后者通过多维表格只读 API 取得业务人员字段。当前测试架构不复制多维表格原始记录，而是在读取时用：

```text
多维表格.人员ID = feishu_org_member_snapshot.user_id
```

2026-08-05 的真实回读中，710 个不同组织快照 `user_id` 全部在多维表格「人员ID」中命中；`open_id` 没有精确交集，姓名和工号不能替代主键。具体字段、接口、分页、凭据边界、重复记录和复跑入口见[飞书组织快照与多维表格关联](飞书组织快照与多维表格关联.md)，长期选择的理由见[关联键决策](../决策记录/2026-08-05-飞书组织快照与多维表格关联键.md)。

这条关系只用于身份资料核对和受控开发验证。多维表格仍是下游通道，Lingxi 数据库仍是权限权威；关联结果未接入正式用户开通、权限发布或问数入口。

### 6.5 管理 MCP 与待确认操作

管理 MCP 服务端（`lingxi-admin`，**目标形态，尚未实现**，触发式未来入口，见「二、架构总览」与[决策记录](../决策记录/2026-08-24-管理员职责集与银河外权限动作边界.md)「实现形态」）设计为按 MCP 已正式发布的最新修订 **`2026-07-28`** 实现（该版本的状态在官方站点当日存在不一致，见[MCP 规范 `2026-07-28` 与管理入口](../参考证据/MCP规范2026-07-28与管理入口.md)）。它移除了 `initialize` 握手与协议级会话，因此授权只能逐请求从个人凭据解析——这与 `lingxi-admin` 作为独立认证面的既有设计一致，不需要额外的会话存储。接口设计第六节已按 2026-08-29 拍板精简为未来入口指路，不再重复本节协议细节。

**最终确认不走 MCP。** 该版本的 Multi Round-Trip Requests 可以把 `elicitation` 嵌进一次工具调用，向用户索取输入。但 `form` 模式的 `accept` 由客户端自报、服务端无从核验，构不成「本人已确认」所需的到场证据；`url` 模式虽能提供足够强度，却要求 Lingxi 自建带会话身份的确认端点。确认通道因此保持为发起管理员本人的飞书私聊卡片，理由、已评估的两种混合形态与复审条件见[管理员 AI Agent 与飞书确认边界决策](../决策记录/2026-07-26-管理员AI-Agent与飞书确认边界.md)的 2026-07-29 复审。

每次管理 MCP 调用先把个人凭据解析为唯一 `admin_identity`，再经其绑定的 `app_user` 取得本人飞书 `open_id` 和当前角色。`pending_action.initiated_by`、卡片接收人、回调点击人都必须回到同一 `admin_identity`；映射缺失、重复或变化时默认拒绝。

**执行最多一次**是这里的核心安全属性。实现：

```sql
-- 卡片回调确认时
UPDATE pending_action
SET status='executing', confirmed_by=$1, confirmed_at=now()
WHERE id=$2
  AND status='pending'
  AND expires_at > now()
  AND initiated_by=$1                    -- 只有发起人本人
  AND target_state_version=$3            -- 目标状态未变
RETURNING *;
-- 影响行数为 0 → 不执行，回复"状态已变化，请重新查询"
```

随后在**同一个事务**里：写审计 → 改业务状态 → `status='executed'`。任一步失败则整体回滚，`pending_action` 保持 `pending` 或转 `failed`，用户状态不变——直接满足合同的"审计无法写入时一律不执行"。

角色（权限管理员 / 运维管理员 / 超级管理员）在管理 MCP 的工具注册阶段过滤：**当前身份没有的角色，对应工具根本不出现在工具列表里**，而不是调用后拒绝。这样 AI Agent 不会看到它无权使用的能力，减少误导和无谓尝试。

“从当前运行环境删除用户”不是只把 `account_state` 改成一个软状态：确认后先切到 `deleting` 阻止新问数和交付，再用可恢复编排清理当前环境中的身份、权限、Agent 会话、任务内容与其他可识别运行数据；全部完成并写入脱敏审计后才进入 `deleted`。任一步失败保持不可用但未完成状态，不宣告成功。该编排不修改数据库备份、WAL 归档和用户目录备份；恢复历史备份可能重新带回历史用户内容。

超级管理员角色不增加“最后一名”数据库并发约束。若系统中已无超级管理员，普通管理入口暂停角色维护，由持有服务器 Root 权限的 Ops 运维工程师在数据库所有者权限下，把一个身份已经核实并绑定飞书的现有用户恢复为超级管理员。恢复能力不进入管理 MCP；恢复必须记录目标用户、操作者、时间与结果，上线前在受控环境演练并留下脱敏证据。

### 6.6 审计

```sql
CREATE TABLE audit_event (...) PARTITION BY RANGE (occurred_at);
-- 每条记录有精确 expires_at；受限清理函数先删除到期行，
-- 只有整个分区全部到期后才 DROP，分区不能延长保留期
REVOKE UPDATE, DELETE ON audit_event FROM lingxi_app;
-- 再加触发器拒绝普通 UPDATE/DELETE；只放行专用函数对已到期行的清理
```

- **append-only**：应用角色只有 `INSERT`；普通 `UPDATE`/`DELETE` 由权限与触发器双重阻断，已到期行只能经专用清理函数删除。
- **最长九十天，问数结果正文另走短期 + 会话两段规则**：普通可识别内容写入时计算不晚于来源时间后九十天的 `expires_at`；安全问数结果正文在取得已验证形态的 `platform_received` 前最长二十四小时，取得后转为随当前飞书会话保留，改由会话边界事件触发清理，不再受固定 `expires_at` 约束（[#163](../决策记录/2026-07-26-问数可信交付与数据保留边界.md) 方案 B）：`/new`、用户停用、用户权限变化一经感知立即触发清理；会话空闲满两小时由定时清理机制（scheduler 周期扫描各会话最后一次任务结束时间）到点主动触发清理，不再等待下一次任务入队时才判定（2026-08-14 补充决定）。scheduler 小批量调用受限清理函数处理前一阶段的到期行，同一 scheduler 也承担空闲会话到点清理的周期扫描；超出适用到期时间仍可识别同样视为保留违规并告警，告警覆盖全部四类触发路径，不存在“从未被判定为已结束”的空闲会话。分区只用于批量回收已经全部到期的数据。
- **写路径同事务**：状态变更与其审计在同一事务；审计失败即状态不变。
- **脱敏**：合同要求"不在审计中保存凭据、完整令牌或无关个人信息"。审计写入统一走一个 `redact()` 出口，字段白名单制——新增字段默认不记录，必须显式加入白名单。
- **`user_memory` 是独立的保留面，不走 `expires_at`/分区清理**：显式登记的记忆（术语映射/口径偏好/惯例模板，[决策记录](../决策记录/2026-08-28-用户记忆显式登记边界.md)，Issue #357）没有到期时间列，靠硬 `DELETE` 维持"清除后不可恢复"这条不变量（迁移 `0076`，无 `entry_status` 软删除、无历史版本）——`resume_user` 不恢复已清正文的既有语义（`V-管理-39`）在这里延伸为"记忆被清后同样不可恢复"。触发点三类：命令面 `/memory clear`/`/memory forget`（`core/conversation/pipeline.py`）、账号删除编排（见「六、核心机制 · 6.5」）、权限变化（`adapters/postgres_permission_publish.py`）——后两者与交付内容清除（`clear_delivered_content_for_user`）同一事务、同一姿态，不产生"账号已停用/权限已变、记忆却还在"的半套状态。

### 6.7 交付：飞书凭据不进用户环境，正式产物路径失败关闭

这是一条容易做错的安全边界。JumpServer 用户在自己的环境里有 shell，**任何放进用户环境的飞书凭据都等于交给用户**。

> **2026-08-17 裁定后的边界修订**：本节说的是**飞书凭据**。问数 MCP 的**逐用户**令牌已按产品负责人裁定改为落进用户环境的 `.mcp.json`（见 5.3 与 6.9）。两者的取舍不同：飞书机器人凭据代表**整个租户**的能力，交给任何一个用户都等于把全体用户的数据面交出去；而问数 MCP 的逐用户令牌代表的正是**这个用户本人**已有的数据范围，把它放进他自己的家目录不扩大任何人的可见面。

因此交付 Skill 不持有凭据，它通过本机 Unix domain socket 调用内部交付端点：

```
用户环境内的交付 Skill
   │ Unix domain socket → SO_PEERCRED 取得真实 uid
   ▼
Lingxi 交付服务（持有机器人凭据）
   │ 校验：调用者身份 = 该用户环境所属用户
   ├─ 无 #140 批准且已验证的承载路径 → 明确拒绝，不创建目录或产物
   ▼
已批准的正式产物路径：创建 → 归属或授权 → 发送 → 逐步权威回读
```

正式产物只有在 #140 批准的承载模型上完成创建、归属或授权、发送及必要回读后才回报成功；响应不明记为 `uncertain`，不自动重发。#140 未决定或 #97 所需证据未取得时，端点返回“当前无法安全交付正式产物”，不暴露内部路径，也不创建旧机器人目录。普通飞书问数正文由 Gateway 消费安全持久事件投递，不依赖正式产物路径，不因该失败关闭而受阻。

### 6.9 worker → 问数 MCP 的逐用户令牌：用户环境 Bearer

**2026-08-17 产品负责人裁定，正式取代本文此前的「本机 MCP 代理」方案。** 判定依据是互操作事实：现行问数 MCP 逐行解密权限发布表的 `token_cipher`，与请求 `Bearer` 明文**等值匹配**（见 6.4）。旧系统 biai-agent 的做法是把该用户的 Bearer 写进他自己的用户环境配置，Lingxi 沿用同一条路。

```
开通链签发该用户令牌（明文只在内存）
   ├─ 密文 → publish_outbox → 权限发布表 token_cipher 列
   └─ 明文 → <用户家目录>/.mcp.json 的 Authorization: Bearer（文件 440）
                    │
                    ▼
        worker 以该用户身份启动 Agent 子进程，读同一份配置调用问数 MCP
```

**这条承诺变更的代价与补偿如实登记**：

| 代价 | 补偿 |
|---|---|
| 用户在自己环境里有 shell，能读到自己的那一份令牌 | 令牌的能力**恰好等于他本人已有的数据范围**，读到它不扩大任何可见面 |
| 令牌以明文落盘 | 文件 `440`、目录 `700`、同目录临时文件 + `os.replace` 原子写（磁盘上不存在权限更宽的中间态） |
| 明文可能随日志外泄 | 写入路径的日志、审计与异常一律不带令牌、不带路径、不带文件内容（`adapters/user_environment.py`），由 `tests/test_user_environment.py` 钉住 |
| 令牌一旦发出去就换不掉 | 发布语义上**更新既有行不覆盖 `token_cipher`**（`V-权限-11`），因此不存在"库里换了、外部表没换"的静默失效；存量 26 行的处置见下 |

**存量 26 行的硬切重签留位**：既有 26 行的 `token_cipher` 由旧系统 biai-agent 签发，Lingxi 不知其明文，因此 Lingxi 的探针对这些用户必然不成功。产品负责人 2026-08-18 裁定 6：**硬切窗口由 Lingxi 统一重签、覆写发布行密文，并经用户环境链重投 `.mcp.json`**。本轮**不实施**重签动作，只留出接口位置：重签一个用户 = ①签发新令牌（当前 `issue_token` 幂等且**不覆盖**，重签需要一条显式的覆写路径，尚未实现）→ ②以新密文排一条发布意图覆写那一行 → ③调用 `LocalUserEnvironment.ensure(user_id=…, mcp_token=<新明文>)` 重投配置。第 ③ 步**已经可用**（`ensure` 对内容变化就重写，且仍是 `440`），第 ①② 步属硬切编排那一个 Story。

**发布闸门**：首次开通编排是 `record_decision` 的第三个调用点（前两个是每日重算的授权与撤权），因此它自带与 [#227](https://github.com/Moshuiwang/lingxi/issues/227) 相同的整轮判据——「职能标签 → 指标名」翻译层不可用时**一条发布意图都不排**，并在**建档之前**以 `LX-ONBOARD-001` 收口。不带这道闸，它就是那条判据的绕行入口，而绕过去的后果是往正式权限表写一行消费方读不懂的记录（外部表不可回滚）。

**已接线（2026-08-19，commit `b75735c`，Epic D 闸⑤/⑥）**：queue 模式处理每个任务时改为按 `user_id` 读 `<user_env_root>/<user_id>/.mcp.json`（`adapters/user_mcp_config.py`），不再使用全进程共用配置；`apps/worker/service.py` 的 `_process_task` 里 `UserMcpConfigError` 单独一支直接产出失败报告，从不构造真实会话——读不到就失败关闭，没有回退到共用配置的代码路径。全进程共用的 `LINGXI_WORKER_MCP_SERVERS`（`apps/worker/config.py`）只保留给没有 `user_id` 的一次性受控回合（turn 模式）使用，queue 模式下已被忽略。

**部署前置已落实**：写这份文件的是 `lingxi-scheduler`（首次开通编排住在那里，见[决策记录](../决策记录/2026-08-18-首次开通编排住在scheduler.md)），`compose.stage.yaml`/`compose.prod.yaml` 已给 scheduler 补挂 `lingxi-users` 卷（此前只挂了凭据卷）；`scripts/ci/check_deploy_contract.py:check_scheduler_user_volume` 把这条约束做成会变红的 CI 检查，防止回归。未配置 `LINGXI_USER_ENV_ROOT` 时首次开通编排**整体不注册**（留一条指名变量的审计），没有任何人认领首聊事件，也就不会出现「配了一半、认领走再烧掉」的形态。

## 八、部署与发布

```
目标生产：biplus-prod
└── Docker Compose（共用结构 + 环境覆盖，镜像 tag = 冻结的版本）
    ├── lingxi-scheduler     常驻，裸 `up` 默认启动
    ├── lingxi-gateway       常驻，需 `gateway`/`mvp` profile 显式启用（默认不启动）
    ├── lingxi-worker-queue  常驻，仅 `mvp` profile；与 lingxi-worker 同镜像，`LINGXI_WORKER_MODE=queue`
    ├── lingxi-worker        一次性作业（单回合受控执行，不常驻）
    ├── lingxi-migrate       一次性作业（部署时迁移）
    ├── lingxi-reauthorize   一次性作业，默认不启动（凭据丢失或过期时手动执行）
    └── lingxi-admin         目标形态，尚未实现——无代码、无镜像；MVP 现行管理入口是飞书私聊命令面（方案 A），不经独立进程
        （数据库不在 compose 内：Supabase 云托管——`biai-stage` 已于 2026-08-29 接入测试实例（#411），生产实例随生产部署启用，见下方「验收环境」）
```

以上是部署编排树，不是代码目录结构；仓库代码布局现状以[代码框架](代码框架.md)「一、仓库布局」为准，部署编排细节以 `deploy/README.md` 为准。

- **版本冻结**：合并后 CI 构建镜像并打 tag；`biplus-prod` 只拉 tag，不构建。tag 格式为 `<仓库前缀>/lingxi-<服务>:<YYYYMMDD>-<commit sha 前 12 位>`（例 `ghcr.io/moshuiwang/lingxi-scheduler:20260806-7a9bcf3fac4a`）：日期段标识发布批次，sha 段标识源码提交，带上 sha 才是不可变的，"回滚 = 切回上一个 tag"才有意义。禁止 `latest` 与分支名；与只固定源码的 git 标签 `l4a-accepted-*` 不混用。镜像仓库为 GHCR，CI 用 Actions 原生 `GITHUB_TOKEN` 推送（2026-08-06 产品负责人拍板，[Issue #62](https://github.com/Moshuiwang/lingxi/issues/62)）。
- **回滚**：改 compose 里的 tag 后重启。数据库迁移用 Alembic，要求每个迁移可前滚，破坏性变更拆成"先加后删"两次发布，保证回滚时旧镜像仍能工作。
- **灰度发布——设计已定，代码未落地**（2026-08-05 决策，[Issue #45](https://github.com/Moshuiwang/lingxi/issues/45)）：以下是产品负责人已批准的方案正文，但 compose 未定义灰度 worker service、任务记录未写入目标 worker 版本字段，**本机制尚未实现**。灰度**只覆盖 worker、只对新会话生效**，同一 Agent 会话从创建到结束固定同一版本。gateway 入队时按用户发起请求的时间求值分流规则（首期为试用用户白名单，规则自写、不引入特性开关平台），把目标 worker 版本不可变地写入任务记录（重试、重启、恢复不得改写；命名时与 `pending_action.target_version` 的既有语义区分）；Compose 同时运行稳定与灰度两个 worker service，按版本领取任务。回滚为**排空式**：先停止新会话进入灰度，存量灰度会话处理至自然结束；必须立即停机时明确告知用户已切回稳定版并开始新会话。会话 JSONL 的跨版本兼容性官方无承诺，未经实测不得跨版本 `resume`；两版本 worker 的总并发统一治理，`/stop` 须能定位实际承载会话的版本。完整实施约束与验收要求见 Issue #45。gateway / scheduler / admin 不灰度，沿用整体切换回滚。**生产首发不做灰度**：Trace [#373](https://github.com/Moshuiwang/lingxi/issues/373) 先行裁定 D11（产品负责人 2026-08-28 确认窗口批准）明确生产首次部署走整体切换回滚，不依赖本机制；本机制何时启用见「十、明确不做的」表「特性开关平台」一行的复审条件。
- **验收环境**：受控验收时 `biai-stage` 使用同一份 Compose，连接 `Bot-Test`。**数据库**：`biai-stage` 已于 2026-08-29 从本机 `postgres:16-alpine` 容器切换至 Supabase 云托管测试实例（[#411](https://github.com/Moshuiwang/lingxi/issues/411)：迁移链前滚至 `0078`、32 表 23,925 行数据逐表核对一致、真实用户路径冒烟通过；旧本机库与全量 dump 保留至 2026-09-05 作回退）。2026-07-28 实测：Docker `25.0.14`、Docker Compose `v5.2.0`。**Compose 安装、健康回读与切换旧 tag 演练已于 2026-08-21 起真实执行**：`mvp` profile（`scheduler`/`gateway`/`worker-queue`）在 `biai-stage` healthy 运行，其后经历多次滚动升级；`V-部署-05` 已于 2026-08-23 完成整队回滚旧候选（三容器全部 healthy 后再滚回）的真实演练（见[当前能力](../当前能力.md) 2026-08-21/08-23 记录）。`Bot-Test` 凭据与百炼端点已配置并完成过真实受控验证。
- **编排文件位置**（[Issue #62](https://github.com/Moshuiwang/lingxi/issues/62) 落地）：`deploy/compose.yaml` 是共用结构，`deploy/compose.stage.yaml` 与 `deploy/compose.prod.yaml` 是两个环境的覆盖，三者都**没有 `build:` 键**。执行步骤、回滚与恢复见 `deploy/README.md`。已发布的镜像批次包含 `scheduler`（常驻服务，默认启动）、`gateway`（常驻服务，需 `gateway`/`mvp` profile 显式启用，默认不启动）、`worker`（一次性作业，单回合 CLI）及其同镜像的常驻消费者 `worker-queue`（`LINGXI_WORKER_MODE=queue`，仅 `mvp` profile；已随 [#153](https://github.com/Moshuiwang/lingxi/issues/153) 交付并在 `biai-stage` 真实运行）、`migrate`（一次性迁移作业）与 `reauthorize`（一次性作业，默认不启动）。`lingxi-admin` 仍是目标形态，尚无代码或镜像；MVP 现行管理入口是飞书私聊命令面（方案 A），详见[产品合同「管理员处理入口与安全确认」](../产品合同与外部边界.md)与「六、核心机制 · 6.5」。

## 十、明确不做的

按"不做过多冗余设计"的要求，以下在首期明确不做，并写明触发重新评估的条件：

| 不做 | 触发重评的条件 |
|---|---|
| 微服务拆分 | 出现独立伸缩或独立发布节奏的真实需求 |
| Kubernetes / 多机部署 | 单机资源不足，或需要可用性 SLA |
| 消息中间件（Redis / RabbitMQ / Celery） | 跨机 worker，或任务量增长两个数量级 |
| 读写分离、分库分表 | 单库成为瓶颈（当前余量约三个数量级） |
| 分布式追踪、服务网格 | 进程数超过个位数 |
| 自建向量库 / RAG / text-to-SQL | 问数 MCP 不再提供相应能力 |
| 网页管理后台 | 见[管理员 AI Agent 与飞书确认边界决策](../决策记录/2026-07-26-管理员AI-Agent与飞书确认边界.md)的复审条件 |
| 把高风险动作的最终确认收回 MCP 内部（`elicitation` / MRTR） | 同上决策的复审条件之二三项同时成立：客户端稳定实现 `elicitation` 的 `url` 模式、确认者身份可由 Lingxi 独立验证、覆盖含移动端的常用终端 |
| 启用 MCP 可选扩展（`Tasks`、`MCP Apps`、企业托管授权） | 出现核心协议无法满足的真实需求；扩展默认关闭且客户端支持面仍窄 |
| 自动扩缩容、熔断降级框架 | 出现真实的容量或级联故障问题 |
| 多模型路由 / 模型 A/B | 见[仅提供 Claude 执行路径决策](../决策记录/2026-07-25-仅提供Claude执行路径.md) |
| 特性开关平台（flagd / Flipt / 商业 SaaS） | 灰度需要百分比爬坡放量，或需要不发版修改分流规则时（[Issue #45](https://github.com/Moshuiwang/lingxi/issues/45) 的方案乙升级路径） |

## 十一、复审条件

出现以下任一情况时，本文需要整体复审而不是局部修补：

- 用户规模超过约 1000，或峰值并发任务超过 50；
- 从单机扩展到多机，或引入可用性 SLA；
- Claude Agent SDK 不再是产品执行路径，或百炼兼容端点无法支撑 Agent SDK 所需能力；
- 问数 MCP 的职责边界变化（例如要求 Lingxi 承担数据权限过滤）；
- 飞书长连接、CardKit 流式更新或云盘权限模型发生不兼容变化；
- Supabase 托管形态、出网链路可用性或已确认的数据边界口径发生变化；
- 管理入口从"AI Agent + 管理 MCP + 飞书确认"改为其他形态；
- MCP 再次发布破坏性修订，或 `2026-07-28` 中本设计所依赖的特性进入弃用窗口；
- 产品合同中的会话、并发、保留或审计规则发生实质变化。
