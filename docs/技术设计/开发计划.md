## 三、排序理由

- **执行层先行（S1）。** 它是所有问数体验的承重结构；S0 虽已收口，但组件尚无执行器调用方，「组件存在不等于屏障在生效」（[当前能力](../当前能力.md)已声明）。S1 的停止线（#37 已写明）防止在未验证的入口上继续堆抽象，其 L4a 同时补上 PR #36 最终提交欠下的真实入口验证。
- **身份（S2）与权限数据（S3）两条线互相独立、也不依赖执行层，可并行。** 并行以变更包为单位，遵守协作约定「同一变更只能有一个主实施代理」。S2 属高风险（身份与用户隔离），Draft PR 前强制独立复查。
- **S4 拆成两半。** 飞书接入、幂等与队列不依赖执行器，可尽早开工；把 Agent 会话接进任务的那半边等 S1 合并，避免在未经真实入口验证的执行器上叠飞书复杂度。
- **S5 是当前最大的决策依赖聚集点。** S3 先把数据落库与匹配做通，决策（见第四节）落地后 S5 才能如实兑现「展示当前公司和职能范围」等合同承诺；在此之前不实现任何向用户展示权限范围的逻辑（展示错误的范围比不展示更糟，#17 已有此判断）。
- **探针先行原则。** 依赖未验证外部能力的切片，第一个动作是最小探针而不是编码：S5 的 MCP 可比对字段、S7 的云盘目录跨租户授权、S8 的客户端协议支持、L4a 的飞书 Web 自动登录（[验证与门禁第六节](验证与门禁.md#六受控真实链路飞书-web-与-api-回读)的关键前提，建议在 S4 期间顺带验证）。撞不通即回 Issue 重新设计，不得先向用户承诺。
- **S9 不必等主链路全通。** 保留与删除是数据库层的横切能力，表结构一成形就做，晚做会让「九十天上限」在已积累数据上追溯执行，成本更高。
- **#39（lark_oapi 内存评估）是 S4 的输入。** 非阻塞，但 S4 选择飞书接入实现方式前应先有结论，避免刚写完就换客户端。

## 五、每个切片的开工纪律

不重复既有规范，只列入口清单：

1. 领取或新建 Issue，变更类正文首个区块写 TO PM（[协作约定](../协作约定.md#变更-issue-与-to-pm)）；
2. 编码前写好验收断言并认领验证矩阵编号，含否定断言（[验证与门禁 10.2](验证与门禁.md#102-实现-issue-必须先写验收断言)）；
3. 高风险 PR（身份、权限、安全、隔离、真实交付、迁移、部署恢复）强制独立复查；真实外部风险强制 L4a；
4. PR 标注实际达到的证据层级，`docs/当前能力.md` 只回写已验证事实；
5. 达到切片停止线即收口，新发现另建 Issue，不扩大当前变更包。

## 六、复审条件

- 任一切片完成、被拆分或被替代时，更新第二节对应行（这是切片划分事实的变化，不是进度更新）；
- 第四节任一决策落地后，把受影响切片的等待项移入其 Issue 范围；
- 产品合同、架构设计的约束前提或首期验收门槛发生实质变化时，本文整体复审。
