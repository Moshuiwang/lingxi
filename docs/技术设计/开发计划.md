## 三、排序理由

- **执行层先行（S1）。** 它是所有问数体验的承重结构；S1 已补上真实 worker 入口验证，因此 S4 下半不再被「屏障尚未接线」阻塞。它仍不等于飞书入口、多轮会话或生产服务已经可用。
- **身份（S2）与权限数据（S3）两条线互相独立、也不依赖执行层，可并行。** S2 的组件和受控验收已收口；S3 与后续 S5 继续负责把已确认的身份资料用于权限发布与就绪确认。并行以变更包为单位，遵守协作约定「同一变更只能有一个主实施代理」。
- **S4 拆成两半。** 飞书接入、幂等与队列不依赖执行器，可尽早开工；Agent 会话接进任务的那半边此前等待 S1 合并，现在可按自身的消费者、流式交付和超时治理范围开工。
- **S5 是当前最大的外部验证依赖聚集点。** S3 已把数据落库与匹配组件合并；#17 的公司、职能映射、未授权和每日刷新口径已确认，S5 仍需把这些规则接到权限发布、既有用户更新和 MCP 同步确认，并通过可比对字段探针后，才能兑现「展示当前公司和职能范围」等合同承诺。
- **探针先行原则。** 依赖未验证外部能力的切片，第一个动作是最小探针而不是编码：S5 的 MCP 可比对字段、S7 的云盘目录跨租户授权、S8 的客户端协议支持、L4a 的飞书 Web 自动登录（[验证与门禁第六节](验证与门禁.md#六受控真实链路)的关键前提，建议在 S4 期间顺带验证）。撞不通即回 Issue 重新设计，不得先向用户承诺。
- **S9 不必等主链路全通。** 保留与删除是数据库层的横切能力，表结构一成形就做，晚做会让「九十天上限」在已积累数据上追溯执行，成本更高。
- **#39（lark_oapi 内存评估）是 S4 的输入。** 非阻塞，但 S4 选择飞书接入实现方式前应先有结论，避免刚写完就换客户端。

## 五、每个切片的开工纪律

不重复既有规范，只列入口清单：

1. 长期工作先由规划者按 #147 生成或修订 `[tracking]` Execution Trace；编排者从获批 Trace 领取工作项。独立工作直接领取或新建 Issue，变更类正文首个区块写 TO PM（[协作约定](../协作约定.md#变更-issue-与-to-pm)）；
2. 在编码前必须写好验收断言并认领验证矩阵编号，含否定断言（[验证与门禁 10.2](验证与门禁.md#102-story-必须先写验收断言)）；
3. 每个长期 Plan Epic Draft 前对固定候选 SHA 完成一次独立一致性审查；是否升级并记为 L3 由获批 Trace 按风险选择。普通非 Epic Draft PR 是否采用独立复查按自身合同决定；需要宣告真实外部结果时，建议安排 L4a；
4. 建议 PR 标注实际达到的证据层级；`docs/当前能力.md` 仍只回写已验证事实；
5. 达到切片停止线即收口，新发现另建 Issue，不扩大当前变更包。

## 六、复审条件

- 任一切片完成、被拆分或被替代时，更新第二节对应行（这是切片划分事实的变化，不是进度更新）；
- 第四节任一决策落地后，把受影响切片的等待项移入其 Issue 范围；
- 产品合同、架构设计的约束前提或首期验收门槛发生实质变化时，本文整体复审。
