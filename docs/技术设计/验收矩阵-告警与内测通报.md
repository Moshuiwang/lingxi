### 最小运行告警

状态机（心跳、滞留、连续失败、去重、恢复、安全摘要）由 [#92](https://github.com/Moshuiwang/lingxi/issues/92) 认领；装进三个进程 `main()` 与健康检查由 [#153](https://github.com/Moshuiwang/lingxi/issues/153) 完成。告警发送失败不得改变三进程原职责；真实进程停止、真实管理群连续失败与恢复留后续 Ops Story。

`AlertDispatcher`/`AlertingDuty` 位于 `core/alerting.py`（#153）：三个进程独立部署、互不 import `apps.<name>`，共用同一套状态机与投递/去重语义。

**预开通失败照走 `V-告警-09` 这条通道（rc25 S-8a，[#541](https://github.com/Moshuiwang/lingxi/issues/541)；编排者裁定保留，不做静默）**：管理员按名单预开通时，失败那一半仍然经 `AutoOnboardingRunner._execute` 的既有写出点落 `onboarding.result` 与失败行，并触发 `AlertKind.ONBOARDING_FAILED` 送达管理群。**为什么不因为「这是批量操作」就静默**：预开通替一个真人写正式权限表行、签发问数令牌，失败没有任何人看见，正是本批一直在打的那类静默漏接；而且这个人在预开通期间收不到任何用户可见结果，管理群是唯一会响的地方。告警正文与既有开通失败逐字同构（只有故障类别、计数、追溯号），**不含名单内容、邮箱或姓名**。**已知边界（登记，不在本批解决）**：一份大名单里多个人失败会产生**多条**告警，本批没有做批次合并或按名单聚合——名单规模变大时再议，届时的判据是「管理员还能不能从群里看出发生了什么」，不是「告警条数多不多」。另：停摆兜底捞到的预开通用户，追溯号是合成的，`/admin trace` 用它查不到入站事件（本来就没有），只查得到那一行失败原因。

**已知后果（PR #173 P2-3）**：`V-告警-02` 五类事件类型全部只由 `WorkerService._housekeep()` 产生，没有一条能到达管理群，只能靠翻容器日志；目前只有 gateway（投递失败）与 scheduler（授权续期失败）的告警真的会发进管理群。

**已知未修复缺口（PR #173 P2-2，登记不解决）**：`V-告警-01`"任一条停摆都能被单独发现"只对活性文件机制成立，对状态机本身的 `PROCESS_INACTIVE` 检查不成立——三进程都是"先记心跳、再检查心跳"落在同一循环迭代里，循环一停就没人检查停摆本身。跨三进程的看门狗改动留后续 Story；活性文件（`V-部署-11`）不受影响，容器健康检查仍可靠。

**部分收窄（Issue #191，只对 gateway 生效）**：投递消费线程死亡现在跨循环可观测（`delivery_thread_watchdog` 触发 `delivery_loop_dead:*` 并冲刷队列），瞬时数据库错误不再是常见死因。**仍未覆盖**：线程活着但卡死时同循环失明依旧成立；worker/scheduler 不受本次改动影响。

### 内测每日通报

由 [#303](https://github.com/Moshuiwang/lingxi/issues/303) S-O-01 认领。职责实现在 `apps/scheduler/daily_report.py`（`DailyReportDuty`），聚合与渲染的纯函数在 `core/daily_report.py`，六段真库读取在 `adapters/postgres_daily_report.py`；与花名册审计日报共用同一个 `FeishuGroupMessages` 出站适配器与告警接线，各自持有独立的投递去重前缀（`DAILY_REPORT_UUID_PREFIX`）。

**MCP 调用次数对照（#296 基线）在当前架构下恒为「不可判定」**：只存在于 worker 进程自己的结构化日志（`worker.task.terminal` 的 `audit.call_count`），scheduler 与 worker 是独立部署进程、不共享文件系统或日志聚合通道，没有任何代码路径能读到，明确登记为超出本 Story 范围，正文如实呈现不可判定及原因。

**token 用量与工具调用拒绝计数已脱离「恒不可判定」（Issue #304 批次 4）**：迁移 `0070` 给 `task` 表新增 `token_usage`/`guard_denied_count` 两列，`apps/worker/service.py` 的终态收口点同事务落库；这两段现在是**真实聚合**（`adapters/postgres_daily_report.py` 的哑 `SUM`/`COUNT(*) FILTER` + `core/daily_report.py` 的纯函数判定），只在查询失败或窗口内该字段**全部**为 `NULL` 时才判「不可判定」，见 `V-通报-09`。

**判重水位持久化 + 重聚合挪出主线程（Issue #325）**：内测实测坐实两处残留——scheduler 重启后同一统计窗口重发通报（判重水位只在进程内存，`_completed_on` 跨重启归零）、午夜聚合耗时挤晚同一 tick 内 `AlertingDuty` 的心跳评估、触发假 `process_inactive` 告警。迁移 `0071` 新增 `daily_report_watermark` 表（`adapters/postgres_daily_report_watermark.py`），发送成功后写入，下一轮（含重启后）判重先查这张表；六段聚合、渲染、发送与收尾整体挪进后台线程（`DailyReportDuty._aggregate_and_send`），调用方所在的线程只等一个远小于心跳超时的短上限即可拿回控制权。见 `V-通报-10`/`V-通报-11`。
