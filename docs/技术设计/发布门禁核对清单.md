# 发布门禁核对清单

> 状态：现行事实（2026-09-27 由[验证与门禁](验证与门禁.md)「五、CI 分层」整段迁入，原文逐字未改）。本文登记裁决层 `Epic Verdict` 的逐项核对清单、恢复路径与已知边界；三档门禁的分工与必需检查名称仍以[验证与门禁](验证与门禁.md#五ci-分层)为准。迁出原因是开工必读集体量预算，不是规则变化。

## 一、三档门禁与裁决的逐项核对

**三档门禁与裁决**（Issue #748）：`Story Fast`（epic 内 PR）与 `Epic Full`（`main` / `release/**` PR 的候选证明）都由 PR 自带的工作流产出，而必需检查只按名字匹配——PR 能改自己的门禁，也能放同名作业顶替；`Epic Verdict` 是只在主干存在的裁决层，App 私钥只在仅对 `main` 开放的 Environment `verdict` 里，PR 分支上的运行拿不到。裁决层由三处组成——`.github/workflows/verdict.yml`、判定纯函数 `scripts/ci/verdict_decision.py`、钉住用例 `tests/test_verdict_decision.py`——只护工作流文件的 CODEOWNERS 窄行必须同时覆盖后两者，否则改判定与改用例仍无人把关。判定逐条用例钉住：非 `pull_request` 事件或非 `ci.yml` 产出的运行不裁决；外部仓库判红；**路径 a**——信任来源是 GitHub 出具的 OIDC 身份凭证：`Epic Full` 的 `candidate` 作业在 `pull_request` 事件下向 GitHub 要一枚受众固定为 `lingxi-epic-verdict` 的凭证并留成制品；裁决层用 GitHub 的 JWKS 验签，核 `aud`、`repository`、`run_id`（= 被裁决的 run）、`event_name`（= `pull_request`）、`base_ref`（**只认默认分支** `main`；进 `release/**` 的同步 PR 一律路径 b 复跑）、`sha`（= 头提交或其临时合并提交）、`workflow_ref`（本仓 `ci.yml`），`exp` 不作否决（凭证只当签名记录，重放由 `run_id` 挡住）。凭证合格、且头提交的 `.github/workflows` 子树与凭证声明的 base 分支（运行时被合并进去的提交）相同，才采信那次 `Epic Full` 的结论，只有 `success` 算通过（`skipped` / `neutral` / `cancelled` 都判红）。**路径 b**——其余一律由 `main` 版 `ci.yml` 以 `test_ref` 检出头提交复跑一次、取复跑结论；子树不同（PR 改了门禁定义）时另贴标签「门禁定义已变更」+ 评论差异清单。残余「两步漂移」（先合入放松门禁的 PR，下一个 PR 才受益）已接受，靠标签与评论事后可查。**恢复路径**（裁决层故障时）：产品负责人临时从 `main` 与 `release/**` 两条规则集去掉 `Epic Verdict` 行 → 合并修复 PR → 加回，每步在工作项留痕。

## 二、裁决层已知边界

裁决层已知边界（不绕过许可，仅作登记）：① 路径 b 保证的是门禁**定义**来自 `main`，检查脚本与测试（`scripts/ci/*`、`tests/*`）仍来自被审 PR 的树；要收紧走「复跑检出 `main` 的 `scripts/ci` 覆盖」（Issue #748 方案评论第六节，后续）。② 假 `Epic Full` 签出的凭证 `base_ref` 不是默认分支即不采信（含 `release/**`：规则集未限创建，代码不把它当可信基线；产品负责人在规则集加创建限制作纵深）。③ `id-token: write` 只给 `candidate` 作业；本仓无云端信任策略依赖此凭证。任何系统不得信任 `aud=lingxi-epic-verdict` 的凭证；它仅是裁决核对来源的短期记录，仓库读者可下载。④ Environment `verdict` 分支、来源 App 限定属配置前提；放宽即失效，本层不防。只有 `verdict.yml` 可引用 Environment `verdict` 与 App 私钥，由受护测试钉住。
