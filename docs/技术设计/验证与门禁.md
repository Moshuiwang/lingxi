## 一、本文解决什么

两个问题，同一份答案的两面：

1. **AI 写代码前，验收标准必须已经存在。** 否则每个代理按自己的理解定义"做完了"，而模型天然倾向于实现顺利路径、少写拒绝路径。标准写在前面，它就是规格；写在后面，测试只会印证代码已有的行为。
2. **标准必须被门禁强制，而不是靠自觉。**

第二条不是假设。在本仓库已经发生过两次：

- [PR #12](https://github.com/Moshuiwang/lingxi/pull/12) 的自审中发现，「同一话题只跑一个任务」原本设计成一个**空操作**的唯一索引（`id` 已是主键，索引不增加任何约束），第二个任务会直接覆盖第一个。它被发现的唯一原因是当次代理临时起意跑了一个真 PostgreSQL——**没有任何规则要求这么做**。若没跑，这个错误会带着"CI 绿 + 自审通过"进入 main。
- `scripts/ci/verify_repository.sh` 在缺少 `shellcheck` 时硬失败，导致 Codex 与 Claude **先后两次**都没能在本机跑通完整门禁，只能跑其中几项。本机与 CI 不同构，本机验证就会静默退化。（2026-07-29 补记：`shellcheck` 一直可以用 `pip install shellcheck-py` 装上，两次都没人查——问题被记成"已知分歧"之后就停止被追问了。详见[第十一节](#十一本机门禁必须与-ci-同构)。）

这两件事共同指向一个结论：**验证能力必须是仓库的属性，不是代理的属性。**

## 三、证据层级

沿用已确立的七级阶梯（来源：用户级协作协议）。本文的作用是把每条规则钉在具体层级上，禁止把低层证据说成高层结论。

| 层级 | 含义 | 在本项目对应 |
|---|---|---|
| L0 | 产物存在 | 代码/文档写完 |
| L1 | 本机验证 | `scripts/dev/check.sh` 全绿 |
| L2 | CI 绿 | `CI / gate` 通过 |
| L3 | 高风险改动独立复查干净 | 未参与实现的代理审查无阻塞问题 |
| **L4a** | 真实试运行（**代理驱动**） | 代理在 `biai-stage` + `Bot-Test` 上通过飞书 API 与飞书 Web 驱动真实链路 |
| **L4b** | 真实试运行（**必须真人**） | 只有真人能完成的动作（见[第九节](#九谁执行何时才打断人类)） |
| L5 | 真实交付并回读 | 真实用户在真实入口完成任务并确认结果 |
| L6 | 持续采用 | 连续试用七个工作日无阻塞问题 |

**L4 拆成 a / b 是本文最重要的一次修正。** 初稿把 L4 整体定义为"分钟级人工"，等于每次涉及飞书的改动都要人点一遍——在全部代码由 AI 代理编写的前提下，这会成为开发速度的主要瓶颈，也与"验证能力必须是仓库的属性"自相矛盾。

**L4a 的证据强度与 L4b 相同**：两者都在真实外部系统上执行，区别只是执行者。代理用真实测试账号驱动真实飞书，得到的仍是真实系统的行为，不是 mock 的行为。

**硬规则**：

- `docs/当前能力.md` 的条目**只有达到 L4（a 或 b）及以上才能从"尚待实现"转为"当前能力"**。L2 绿只是所有 PR 的基础合并条件；按风险判定为适用的 L3 / L4 也必须通过后才能合并。
- PR 描述中必须标注本次达到的层级，不得用"测试通过"指代 L4/L5。
- 达到 L4 之前，任何面向用户的承诺都不成立。
- **能落到 L4a 的断言不得留在 L4b。** 把可自动化的验证留给人是浪费，也会让它实际上不被执行。

## 四、四道关口

```text
   实现 ──► 本机门禁 ──► CI 门禁 ──► 受控真实链路 ──► 真实用户验收
            (L1)        (L2/L3)      (L4a 代理驱动)    (L5/L6)
             │            │            │  L4b 仅少数     │
       与 CI 同构    可自动、无副作用   真实外部依赖    产品合同旅程
       秒级反馈      每次 PR 强制      按风险触发      首期一次 + 放量前
             └──────── 全部由代理执行 ────────┘        真人参与
```

**前三道关口全部由代理执行，无人类介入。** 第四道才需要真实业务用户，且那是产品验收（见[首期服务范围与真实验收](../决策记录/2026-07-26-首期服务范围与真实验收.md)），本文不重复。

对当前 PR **适用的关口**，准入条件是此前所有适用关口全绿。L1 / L2 对每个 PR 都适用；L3 / L4 由风险决定是否适用。低风险 PR 将 L3 / L4 标为不适用不算跳关；适用关口只有在关口本身故障时（例如 CI 平台不可用）才允许暂时跳过，此时必须在 PR 中说明原因、影响与补做计划——这条已由 `协作约定` 规定，此处不重复。

关口之间的**分工原则**：

- 能在 L1/L2 挡住的，绝不留到 L4。受控链路要占用真实外部依赖与测试账号，把可自动化的纯逻辑断言留到那里是浪费。
- **只有真实外部系统才能证伪的，绝不假装能在 CI 证明。** 用 mock 通过飞书调用的测试，证明的是 mock 的行为，不是飞书的行为。这类测试可以写（防回归），但**不计入该条规则的证据**。
- **能自动化的绝不留给人。** 判断标准见[第九节](#九谁执行何时才打断人类)。

### 风险决定是否进入 L3 / L4

每个 PR 都必须通过 L1 / L2 并由实施代理基础自审，但不把额外复查和真实外部调用平均摊到所有改动：

| 风险 | 判定 | 强制关口 |
|---|---|---|
| 低风险 | 纯文档、文案勘误、机械调整，或行为已能由本机与 CI 充分证明且不改变用户入口、权限、数据与外部依赖 | L1 / L2 + 实施代理基础自审 |
| 高风险 | 身份、权限、安全、用户隔离、数据范围、真实外部交付、数据库迁移、部署恢复，或用户关键路径与失败语义发生变化 | 在 L1 / L2 之外强制 L3 独立复查 |
| 真实外部风险（高风险子类） | 正确性只有飞书、MCP、JumpServer、Claude Code + 百炼或真实交付链路才能证伪 | 强制 L3 + L4a；确实无法自动化的部分才进入 L4b |

PR 必须分别写明风险等级、是否存在真实外部风险、判断依据、已进入的关口和不适用关口的理由。实现代理不得为了降低验证成本把高风险改动拆成多个表面低风险 PR。

**每个 PR 的基础自审必须回答两件事；进入 L3 时，由独立审核者再次核对并给出独立结论：**

1. **未来部署可行性。** 对照[部署对代码的约束](#十二部署对代码的约束)，检查是否引入生产现场构建、生产路径或配置硬编码、人工修改生产文件，以及重启或重试造成结果丢失、重复交付或无法恢复的路径。
2. **Test 与 CI 有效性。** 对照最终 diff，确认变化的行为有相称的本地验证；稳定、可重复且无真实业务副作用的合并关键检查由 PR CI 实际执行。新增或移动目录、运行时、依赖、入口或测试命令时，必须引用 CI 配置中执行它的代码或本次 CI 对应步骤输出，不能只写“已在既有测试范围内”。

已形成的不安全设计或应进入 CI 却未实际执行的关键行为是阻塞项；尚未实现的健康检查、发布包或 CD 门禁记录为后续工作。较慢、受限或会产生真实副作用的场景留给 L4；`CI / gate` 通过不能替代真实用户路径。

## 五、CI 能做什么、不能做什么

`协作约定` 规定 `CI / gate` "只运行**不触及公司系统、无业务副作用**的仓库检查"，并明确允许临时的本地依赖容器。

在这条边界内，下列检查**全部合规**：

| 检查 | 为什么不违反边界 |
|---|---|
| 静态检查（类型、lint、格式） | 无外部依赖 |
| 纯逻辑单测 | 无外部依赖 |
| **真实 PostgreSQL 容器测试** | 临时容器，无外部网络、无业务凭据、无业务系统副作用；用完即销毁 |
| 录制回放的外部接口契约测试 | 回放本地录制的脱敏响应，不发起真实调用 |
| 合同条款覆盖清单核对 | 纯文本比对 |

**「真实 PostgreSQL 可以进 CI」是本文最重要的一条判断。** 它把"数据库约束是否真的起作用"从代理的临时起意变成门禁强制项——正是 PR #12 那个空操作索引所属的错误类别。GitHub Actions 的 service container 原生支持，代价是每次构建增加数十秒。

> 该判断已由产品负责人确认，`协作约定` 的 CI 授权边界已相应更新为"不触及公司系统、无业务副作用"，并明确允许临时本地依赖容器。

下列**不能**进 CI，只能留给受控测试：

- 任何真实飞书调用（长连接、卡片、云盘、多维表格）
- 任何真实 MCP 调用
- JumpServer 登录与用户环境
- Claude Agent SDK 的真实模型调用（涉及百炼凭据与计费）

## 六、受控真实链路：飞书 Web 与 API 回读

受控真实链路（L4a）的执行者是代理，不是人。可行性来自一个事实：**飞书提供完整的 Web 端**，因此代理可以用浏览器自动化驱动真实飞书，而不必依赖真人点击。

### 双通道验证：API 回读做主断言，Web 验可见性

两条通道分工明确，不可互换：

| 通道 | 验证什么 | 为什么 |
|---|---|---|
| **飞书开放平台 API 回读** | 客观事实：文档是否创建、目录权限是否只给了本人、多维表格内容是否逐字段一致、消息是否送达 | 结构化、稳定、可精确断言；不受 UI 改版影响 |
| **飞书 Web 浏览器驱动** | 用户可见性与交互：卡片是否按预期渲染、按钮点击是否触发正确回调、流式更新是否可见、话题是否正确隔离 | 这些是"用户实际看到什么"，只有真实客户端能证明 |

**原则：凡是 API 能回读判定的，主断言走 API；Web 只用来验证人眼可见的部分。** 把全部断言压在 DOM 选择器上，会让验证套件对飞书 UI 改版极度敏感，维护成本超过收益。

### 典型链路

代理执行一次完整的受控验收，形如：

```text
API：以测试身份构造前置状态（组织资料、权限、待办）
 └─► Web：普通员工向机器人发消息
      └─► Web：观察自动开通的进度或最终结果
           └─► API 回读：状态是否真的改变、产物是否在专属目录、
                权限是否只给了本人、审计是否落库

管理员高风险动作另行验证：管理员在本人飞书私聊点击「确认执行」或「取消」，再回读动作与审计结果。专用组织资料授权只由“四达文档会议助手”在正式授权编码完成后验证，不属于普通员工旅程。
```

断言同时来自两侧：Web 侧证明用户看得到且能操作，API 侧证明系统状态真的正确。

### 前置条件与风险

| 项 | 状态 |
|---|---|
| 测试账号能否稳定自动登录飞书 Web（登录方式、二次验证、会话保持） | **未验证**，是 L4a 能否成立的关键前提 |
| 浏览器自动化在 `biai-stage` 网络环境下的可达性 | 未验证 |
| 免费租户测试账号（用于跨租户场景）的可自动化程度 | 未验证 |

**若自动登录不可行**，受影响的只是 Web 侧断言（卡片渲染与点击），API 回读侧不受影响；此时把 Web 侧断言降到 L4b 由真人抽验，而不是把整组降级。

登录凭据按[第十三节](#十三测试数据与身份边界)管理：只用测试身份，不进代码库，不进日志。

**V-执行-18…20 的层级只到 L2，`V-执行-21` 当前状态是「未验证，待 `biai-stage`」。** L2 用的是按脚本驱动的**假 SDK**：worker 照常装配，假 SDK 从 `options.hooks` 里找回回调并真的调用，拿到 `deny` 才不执行——因此删掉任何一段接线，越界探针都会真的写盘，用例随之变红。它证明的是「本侧装配是通的」，**证明不了真实 SDK 会触发这些事件**；后者只有 L4a 能答，环境通道就绪前不得把 `V-执行-18/19` 说成已在真实链路成立。

**`V-执行-20` 的做法是在 worker 的输出边界再脱敏一次，不是改审计核心。** 审计对象里未知工具名仍原样保留（那是 `V-审计-03` 知情接受的残余缺口，理由是"模型试图调用什么"是拒绝式白名单最重要的审计事实）；但那条接受的前提写明是「组件尚无调用方」。有了调用方之后，离开进程的报告与日志必须收紧：**不在白名单里的**工具名与最终正文在出口过一道自由文本脱敏。代价是含数字的 16+ 字符未知工具名在证据里只剩长度投影——白名单内的名字不过这道，正常审计的可读性不受影响。

**V-执行-08 只约束发给模型的文案，不保证结果**：L4a 实测中模型的最终正文仍出现了内部工具名。用户可见文案的内部标识过滤必须由输出侧检查器承担（`V-卡片-04`），提示词约束不能替代。

**V-执行-06 的边界**：归类规则是显式配置的结构化规则加已登记的失败措辞，不做自然语言猜测。既不匹配失败规则又拿不出可识别数据的回执归为「未知」，回合结论也是「未知」——这是刻意的，把「没报错」当成「用户拿到了结果」正是这条断言要防的错误。**能解析成 JSON 不算「拿得出可识别数据」**：MCP 回执绝大多数是 JSON，若把「可解析」当成 OK，这条断言在真实分布下几乎永远失效。首版实现就踩了这个坑，由独立复查发现。

**V-执行-11 的保障范围要说清楚，它比字面看起来窄。** 适配器只注册 `HOOK_EVENTS` 与 `OBSERVATION_ONLY_EVENTS` 里的事件名。如果 SDK 把 `PreToolUse` 改成别的名字，我们注册的那个名字**根本不会再被调用**，这条断言的留痕分支也就永远进不去——它只在「SDK 把我们已注册的 matcher 用一个认不出的事件名回调回来」时生效。**因此不得据此声称「事件改名会自动被发现」。** 事件名是否仍然有效，只有真实 SDK 的冒烟检查（`scripts/ci/check_agent_sdk_binding.py` 验证构造，L4a 验证触发）能回答。这条边界由 Codex 只读审核（PR #36）指出，原措辞确实越界了。

**V-执行-10 至 V-执行-16 由 Issue #29 的独立复查逼出**，全部是原实现真实存在的漏洞：审计对「绕过判定但执行成功」的调用完全不留痕（最危险的情况恰好隐身）、记账异常会把拒绝一起带走、按名回退把回执挂错、无回合边界、分类随 hash 种子翻转、SDK 绑定层零测试。这一组存在的理由与整个执行层相同——**审计的价值全在它不说谎**，一条假的否定结论比没有审计更糟。

**V-执行-17 是 `V-执行-06` 的第三次同类修补，值得单独记。** 前两次分别漏了「能解析成 JSON 就判 OK」和「非空顶层数组就判 OK」，这次漏的是**回合级**：单次归类全对，合成回合结论时"见到任意一条 OK 就返回 OBTAINED"又把它抵消了——`list_metrics` 成功 + `describe_metric` 失败会被写成用户拿到了结果，而这是问数的常态路径。**同一条断言在三个不同层面各破一次，说明"不把没报错当成拿到结果"必须逐层落到断言上，写在断言正文里不会自动传导到实现的每一层。**

本层**没有**区分「承载最终业务结果的调用」与「辅助调用」的信息，因此混合回合只能保守记 `UNKNOWN`。代价是真实运行中会出现较多 `UNKNOWN`（例如"先查错一个指标、换一个又查成功"的回合）。这是知情取舍：审计谎报 `OBTAINED` 比过多 `UNKNOWN` 危险得多。执行器切片接入后若能标出哪一次调用回答了用户的问题，可以在保持"不谎报"的前提下把这部分 `UNKNOWN` 收窄。

### 银河权限落库与匹配

由 [Issue #17](https://github.com/Moshuiwang/lingxi/issues/17) 的 S3 切片认领。**新建这一组而不是并入「权限发布与同步」**：那一组约束的是 Lingxi 当前有效记录如何发布出去，本组约束的是银河导出如何进来——落库结构、连接键与匹配三态。两者的失败方式不同，混在一起会让「哪些断言属于本切片」不可判定。

|---|---|
| **纯字母、短于 32 字符的裸秘密**出现在错误正文、回执正文或工具名里 | 这三处不经过字段白名单，长度上界是唯一可用的规则，而它认不出纯字母短串。曾经写过"这一类由字段白名单承担"——**那句话是假的闭合**，字段白名单根本不覆盖自由文本 |

## 八、否定测试

**这是 AI 编写代码时最容易整类缺失的部分，因此单列一节并给出硬性要求。**

模型倾向于实现并验证顺利路径。产品合同里大量规则是"不得 / 不允许 / 一律不执行"形态——这些规则**只能由否定测试证明**：一个从不尝试越界的测试套件，无法证明系统会拒绝越界。

硬性要求：

> 产品合同中每一条"不得 / 不允许 / 一律不 / 禁止"形态的规则，**必须有一条对应的否定断言**，证明系统在尝试该行为时拒绝，而不只是在正常路径下不发生。

上表中属此类的条目包括但不限于：`V-开通-01/02/03/04/06/07/08/09`、`V-身份-01/02/03/04`、`V-会话-04`、`V-执行-01/02/05/06/07/08/09/10/11/12/13`、`V-接入-01/02/03`、`V-管理-01…06/08/10/11…15/17/18`、`V-权限-01`、`V-银河-01/02/03/05/10/11/13`、`V-交付-01/02/06`、`V-审计-01/02/04…07`、`V-问数-01/05`。

> 执行层这一组整组是否定断言，原因与上一段相同：一个只调用被批准工具的测试套件，无法证明系统会拒绝未被批准的工具。因此 `V-执行-02` 必须用一个**不存在于任何名单里**的工具名来断言，而不是用一个已知的危险工具名——后者只能证明该工具被禁，证明不了默认分支是拒绝。

> 「开通与匹配」这一组是在本文的自审中补上的：按本节的要求回头核对产品合同，发现合同里 26 条否定形态的规则中，"不得先占位再回填""不允许模糊匹配""不生成人工待办""不重新进入身份核对"四条**在初稿的矩阵里整组缺失**。这正是本节存在的理由——顺利路径的条目会自然想到，拒绝路径的不会。

三类特别容易漏、必须显式写的：

1. **"不发生"与"被拒绝"的区别。** 正常流程里不会发生越权交付，不等于系统会拒绝越权交付。必须主动构造越权请求。
2. **状态机的非法迁移。** 只测 `pending → executed`，不测 `executed → executed`、`expired → executed`。
3. **权限的反向断言。** 只测"权限管理员能看到用户列表"，不测"运维管理员**看不到**"。

否定断言还必须证明自己**会变红**：权限、安全、审计、用户隔离类的新增断言，在交付前必须由验收者或未参与实现的代理故意破坏一次对应实现，确认目标用例失败，再恢复实现并在 Issue 或 PR 留下脱敏证据。不引入自动化变异工具；一次稳定、可复验的手工变异即可。一条从不变红的否定断言与没有断言等价。

## 九、谁执行、何时才打断人类

全部代码由 AI 代理编写，因此**每一处人类介入都是开发速度的直接成本**。本节固化谁执行什么，避免验证体系随时间长回"事事等人确认"。

### 默认：代理执行

| 环节 | 执行者 |
|---|---|
| 写验收断言 | **规划代理**（在实现 Issue 中，先于编码） |
| 实现与本机门禁 | 实现代理 |
| CI 门禁 | 自动 |
| 基础自审 | 每个 PR 的实施代理 |
| 独立复查（L3） | **仅高风险 PR**，由未参与本次实现的代理执行 |
| 受控真实链路（L4a） | 代理，通过飞书 API + 飞书 Web 驱动 |
| 更新 `当前能力`、回写文档、留收口信息 | 实现代理 |

### 只有四类情况才打断产品负责人

沿用已确立的协作边界，不扩充：

1. **目标或成功标准实质改变** —— 例如某条验收断言与产品合同冲突，需要改的是合同而非断言；
2. **需要新的身份、权限、预算或对外承诺** —— 例如新增测试账号、开通新的应用权限、模型调用额度；
3. **动作不可逆且恢复方案未被证明** —— 例如首次向真实用户发送消息、删除生产数据；
4. **真正的产品价值取舍** —— 例如某条规则实现代价过高，是否降低承诺。

**不属于打断范围**（代理自行完成）：断言怎么写、测试怎么组织、用哪个库、CI 怎么配、发现 bug 后怎么修、受控链路怎么跑。

### 断言的修改权限

- 实现代理**不得自行降低或删除**断言；认为断言不合理时回到 Issue 提出修改，由规划代理裁定。
- 断言的修改**只有在改变产品含义时**才升到产品负责人；纯技术表述调整（换等价的判定方式、拆分或合并断言）由代理决定。

| L4b 项 | 为什么不能自动化 |
|---|---|
| 真实业务用户判断结果"对不对、有没有用" | 这是产品判断，属 L5，本来就由三名真实试用用户承担 |

除此之外的任何断言若被标为 L4b，需要在 PR 中说明为什么不能自动化。

> **2026-08-05 补记（[Issue #37](https://github.com/Moshuiwang/lingxi/issues/37) L2 部分）。** 上述"没有调用方"的状态已经改变：`lingxi.apps.worker` 是一个可执行入口（`python -m lingxi.apps.worker`），它构造 `ToolGateway`、经 `build_hook_matchers()` 装进 `ClaudeAgentOptions.hooks`、每回合调用 `start_turn()`，并把工具回执与最终正文汇入同一个回合审计（`V-执行-18…20`）。**证据层级仍是 L2**：装配路径由假 SDK 驱动，真实 SDK 那一侧只做了构造冒烟（`scripts/ci/check_agent_sdk_binding.py`，不调模型、不用凭据）。**两条硬约束因此仍未解除**——真实事件是否触发、越界是否在真实链路被拦，要等 `V-执行-21` 的 `biai-stage` 三场景。在那之前不得声称「执行器只会调用批准的只读工具」已在真实链路成立。此外该入口不领任务、不接飞书、不写审计表，它是受控验证用的最薄执行器，不是生产 worker。

### 10.1 其余断言按切片认领，不是全量开工门槛

**[验收矩阵](#七关键机制验收矩阵)是目录，不是清单。** 没有任何单个 PR 需要满足全部断言。

每个实现切片只认领与其范围相关的断言，其余保持"未认领"。切片合并时，只有它认领的断言必须全绿。这条必须写明，否则实现代理会把矩阵读成开工前置条件，第一个切片就卡死。

| 状态 | 含义 |
|---|---|
| 未认领 | 尚无切片负责，覆盖清单**不对其做强制** |
| 已认领 | 某个 Issue 声明本切片实现它，合并前必须有对应测试且通过 |
| 已验证 | 断言已被测试覆盖并在对应层级通过 |

**这三个状态就写在验收矩阵的「状态」列里，由门禁强制。** `scripts/ci/check_acceptance_matrix.py` 解析本文的全部断言表，每一行必须给出且只给出上表三个词之一；缺列、留空，或写成别的词（例如把 [10.2](#102-实现-issue-必须先写验收断言) 里 Issue 正文用的"待实现"抄进来），门禁变红。这一列是断言状态的**唯一**机器可读落点：受控验收完成后翻转状态改的就是它，不再在散文里另写一句"某某已通过"。

初始状态（2026-08-06，[Issue #58](https://github.com/Moshuiwang/lingxi/issues/58)）按仓库中已有的明确声明填写，**本次不新增任何验收结论**：

| 填什么 | 依据 |
|---|---|
| 已认领 | 本文正文已写明由某个 Issue 认领（`V-身份-*` → #16，`V-执行-01…17` → #29，`V-执行-18…21` → #37，`V-银河-*` → #17，`V-部署-08/09/10` → #29），或 `tests/` 与 `scripts/ci/` 中已有**会执行的**检查在文件头或用例注释里显式写明认领该编号（`V-开通-01/02/03/06/07/08/09`、`V-审计-02/03`、`V-部署-01/03` 属这一类） |
| 未认领 | 以上都没有 |
| 已验证 | **本次一处都不填。** 已验证要求"断言已被测试覆盖并在对应层级通过"，而本文此前没有逐条记录哪一条在哪一层通过；成组推断等于替各切片补一个它们没做过的验收结论。由各切片在真正通过后逐条翻转 |

「本组不认领」不等于「全仓库无人认领」：`V-开通-01/02/03/06/07/08/09` 在[银河组](#银河权限落库与匹配)的说明里被排除在该切片之外，但身份切片（#16）与银河 S3 切片（#17）的测试文件已显式认领它们，因此状态列记 `已认领`。

**状态列不是证据。** `已认领` 只说明有切片负责，不说明它已经跑通；`已验证` 也只覆盖该断言在「层级」列声明的层级，声明里含 L4a / L4b / L5 而那一层尚未执行的，不得记为已验证。

### 10.2 实现 Issue 必须先写验收断言

每个实现类 Issue 在开始编码前，正文必须包含一段：

```markdown
## 验收断言

| # | 断言 | 层级 | 状态 |
|---|---|---|---|
| V-会话-01 | 两并发请求抢占同一话题，恰好一个成功 | L2 | 待实现 |
| V-会话-04 | 忙碌期消息未写入 task 表 | L2 | 待实现 |

否定断言（合同"不得"类规则）：
- V-会话-04 对应合同「该消息不进入对话历史、不排队」
```

规则：

- **断言先于代码。** Issue 领取时断言必须已经写好；实现代理不得自行降低断言。
- 断言只写"能判定真假的陈述"，不写"测试 XX 功能"。
- 认为某条断言不合理时，**回到 Issue 讨论并修改断言**，不在实现里绕过。

### 10.3 合同条款覆盖清单

维护一份机器可读的映射：`产品合同条款 → 验收断言编号 → 测试用例`。

CI 检查它，但**检查的不是覆盖率百分比，而是**：

- 每条**已认领**的断言至少有一个测试用例；
- 没有引用了不存在断言编号的测试；
- 已标记"已验证"的断言，其测试确实在声明的层级执行过。

**这三条是目标形态，不是当前状态**——截至 2026-08-06 它们都还没实装。门禁现在实际执行的是下面[清单本体与门禁实际检查的三条](#清单本体与门禁实际检查的三条)所列的检查，那一小节同时说明这三条为什么还没做。

**未认领的条款不参与强制**——否则第一个代码 PR 会因为绝大多数条款还没有断言而直接红掉。随着切片推进，未认领项逐步归零，这个数字本身就是实现进度的可信度量。

#### 清单本体与门禁实际检查的三条

清单就是下面这张表，与[状态列](#101-其余断言按切片认领不是全量开工门槛)由同一个脚本（`scripts/ci/check_acceptance_matrix.py`）解析。它现在检查的是：

- **产品合同的每个章节都必须在表里出现，且只出现一次。** 合同新增或改名一节而没有登记，门禁变红——"合同条款无断言覆盖"最常见的形态就是规则先加、断言忘了加。
- **「对应断言」格要么给出至少一个断言编号，要么写 `无对应断言`；留空即失败。** 编号必须在验收矩阵里真实存在，`V-管理-01…18` 这样的区间会逐个展开核对，中间缺号一样红。
- **写 `无对应断言` 必须在「说明」里写清为什么**，不允许静默宣布某节不需要断言。

本节开头列的另外三项（每条已认领断言至少一个测试用例、没有引用不存在编号的测试、已验证断言确实在声明层级跑过）**尚未实装**：它们需要测试与断言编号之间有可靠的机器可读绑定，而当前只有测试文件头的自由文本约定（形如"认领断言：`V-开通-01`"）。本切片不把自由文本当作绑定，留作后续。

清单按**章节**粒度维护，不逐条抄合同规则——把规则复制进清单会形成第二份合同正文并各自漂移；章节内逐条规则的否定断言覆盖仍按[第八节](#八否定测试)执行。反向不成立：矩阵里有些断言（`V-部署-*` 的多数）约束的是代码与部署，不对应任何合同章节，清单不要求它们出现。

| 合同章节 | 对应断言 | 说明 |
|---|---|---|
| 产品是什么 | 无对应断言 | 产品定位陈述，不含独立的可判定规则；其中的准入与问数前置由「首次对话与自动准入」「统一用户记录与权限变化」承担 |
| 用户与入口 | V-开通-03、V-开通-06、V-管理-08、V-管理-11、V-交付-06、V-问数-03 | — |
| 首次对话与自动准入 | V-开通-01…09、V-身份-01、V-身份-02、V-身份-04、V-银河-09、V-银河-10、V-审计-05 | — |
| 开通流程 | V-开通-01、V-开通-06、V-开通-07、V-开通-09、V-身份-02、V-身份-03、V-权限-01…06、V-银河-09 | — |
| 开通成功后 | V-权限-04、V-权限-06、V-审计-05 | — |
| 匹配结果与人工处理 | V-开通-02、V-开通-03、V-开通-06、V-开通-09、V-权限-04、V-权限-05、V-银河-09、V-银河-10、V-银河-11 | — |

沿用 PR 模板，补充要求：明确写出本次达到 L 几，以及哪些断言尚未验证。**不得用 L2 的证据陈述 L4 的结论。**

## 十一、本机门禁必须与 CI 同构

现状问题：`scripts/ci/verify_repository.sh` 在缺少 `shellcheck` 时直接失败退出，导致两个代理先后无法在本机跑通完整门禁，只能手工跑其中几项——本机验证静默退化成了部分验证。

**`shellcheck` 这一项已有立即可用的解法**（2026-07-29 实测）：它有 PyPI 分发，`pip install shellcheck-py` 即可在无 root、无系统包管理器的机器上装上，本仓库的脚本用它跑通过（实测版本 `0.11.0`）。此前两次"本机跑不通门禁"因此并不是不可解，只是没人查过——**这本身就是本节的例证：被记录成"已知分歧"的问题会停止被追问。**

但装上不等于同构：**CI 用的是 runner 镜像自带的 `shellcheck`，版本既没锁定也没打印**，与本机装的版本可能给出不同结论。所以下面第二条改成"报告版本"而不只是"报告跳过"。

改进方向（属实施工作，在对应 Issue 中落地）：

- 提供 `scripts/dev/check.sh`，在容器内运行与 CI **完全相同**的检查集，消除"本机缺依赖"这一类差异；
- 保留直接在宿主机运行的快速路径，但缺依赖时**明确报告哪几项被跳过**，而不是整体失败或静默通过；工具版本也要打印——本机与 CI 装了不同版本的 linter，是一种不会报错的分歧；
- `shellcheck` 的版本应在两侧锁到同一个，否则"本机通过"仍不能预测 CI；
- 本机门禁包含 PostgreSQL 容器测试，使数据库约束类断言在推送前即可验证。

**判断标准**：一个新代理在一台干净机器上，应当能用一条命令得到与 CI 相同的结论。做不到，则本机验证不可信。

## 十二、部署对代码的约束

部署方案本身在[架构设计](架构设计.md#八部署与发布)里已经定了（单机 Docker Compose、镜像 tag 即冻结版本、切 tag 回滚），**本文不重复，也不新写部署文档**。发布链路由 `协作约定` 规定。

但有一类东西必须现在就约束：**部署对代码的要求**。它们在写第一行代码时就被固化，事后修改要动很多处；而且架构设计里"镜像 tag 就是冻结的版本、回滚等于切 tag 重启"这条，**只有在代码满足下列约束时才成立**。

| # | 可验证断言 | 层级 | 状态 |
|---|---|---|---|
| V-部署-01 | 代码中不存在硬编码的主机名、端口、路径或密钥；全部配置来自环境变量 | L2（模式扫描） | 已认领 |
| V-部署-02 | 除用户环境目录外，进程不在容器内写入任何需要持久化的本地状态 | L2（运行期文件系统监视） | 未认领 |
| V-部署-03 | 进程收到 `SIGTERM` 后停止领取新任务、完成或安全中断在途任务、在超时内退出。**部署约束**：`LINGXI_DELEGATED_CREDENTIAL_PATH` 必须指向**跨部署持久**的宿主机挂载路径（compose 卷/绑定挂载），镜像替换与重启不得丢失——目标是部署对该凭据「零特殊处理」；文件丢失或过期时的保底是重新走一次「四达文档会议助手」授权，该保底流程写入 S11 部署手册（产品负责人 2026-08-05）。`lingxi-scheduler` 的停止宽限期必须大于「续期 HTTP 超时（当前 20 秒）+ 落盘耗时」，否则 SIGKILL 会落在「已向飞书换过新凭据、尚未写回数据库」的窗口里——Docker 默认 10 秒宽限期不满足，S11 编排时须显式加大（PR #48 独立复查发现） | L2（真实进程信号测试） | 已认领 |
| V-部署-04 | 日志输出到 stdout / stderr，不写日志文件、不自行轮转 | L2 | 未认领 |
| V-部署-05 | 每个数据库迁移可前滚；旧版本镜像能在新库结构上正常启动 | L2（真库：迁移后用上一版本代码跑一遍冒烟） | 未认领 |
| V-部署-06 | 镜像构建不依赖构建机的本地状态；同一提交两次构建产出等价镜像 | L2 | 未认领 |
| V-部署-07 | 容器以非 root 运行；仅持有架构设计中说明的能力（`CAP_SETUID` 等） | L2（镜像与 compose 检查） | 未认领 |
| V-部署-08 | 运行时依赖全部在 `pyproject.toml` 声明；**安全边界所依赖的外部组件锁精确版本**（`==`，不用范围），升级前必须重跑对应的受控验证 | L2（配置检查）+ 升级时 L4a | 已认领 |
| V-部署-09 | 门禁跑在 `pyproject.toml` 声明支持的解释器版本上；低于下限即失败，不得靠运行环境碰巧满足 | L2（门禁自检） | 已认领 |
| V-部署-10 | **已安装的制品**（不是 `src/` 目录）能导入全部关键模块，且必须在仓库目录之外校验；新增子目录漏进制品会红 | L2（CI 独立步骤） | 已认领 |

**V-部署-05 是最容易漏、代价最高的一条。** 回滚策略依赖"旧镜像能在新库上工作"，而这一点只有显式测过才成立——破坏性迁移一旦合并，回滚就从"切 tag"变成"恢复备份"。

> **V-部署-08/09/10 补于 2026-07-29（Issue #29）。** 这三条此前只以散文形式存在于 `AGENTS.md` 的 Code Review Rules（"未来部署可行性"与"Test 与 CI 有效性"），**没有任何断言编号，因此从未被实装**。后果在 Issue #29 上一次性暴露了三处：执行层的只读边界依赖 Agent SDK 与 CLI 的具体事件名，而这个依赖在仓库里没有任何声明；门禁用裸 `python3`，CI 上恰好是 3.12 所以从未暴露，本地 3.9 却能跑出全绿；测试只覆盖 `src/`，新增子目录能不能进制品无人验证。
>
> **教训：要求"审查结论必须说明 X"是一条散文规则，写一段话就能满足；只有给 X 一个断言编号并让它在 CI 里变红，它才会被实装。** 本仓库凡是真正守住的约束（默认拒绝、脱敏、回执归类）都有 `V-` 编号和会变红的用例；凡是只有散文的，都没守住。新增 Code Review Rules 时应同步给出断言编号，否则它只是提醒，不是门禁。

**现在不做**：CD 流水线、发布脚本、监控告警、健康检查细节、蓝绿或金丝雀发布。这些在有可部署产物之前是空转，且部分已由 `协作约定` 的发布链路覆盖。

## 十三、测试数据与身份边界

| 边界 | 规则 |
|---|---|
| 生产凭据 | 任何测试环节不得使用 `Bot-Prod` 凭据或生产数据库 |
| 受控测试身份 | 只用 `Bot-Test` 与独立测试数据库（见 `协作约定`） |
| 真实用户 | 只用于 L5/L6；**不得用于反复触发越权与异常路径**——那是测试账号的职责 |
| 证据留存 | 受控验证的证据脱敏后留在 PR 或 Issue；不进 `docs/` |
| 测试数据 | 不使用真实业务数据构造用例；姓名、公司、指标均用固定化名 |
| 飞书 Web 测试账号 | 仅用于受控环境；凭据由运行环境注入，**不进代码库、不进日志、不进 PR 正文**；账号与真实员工账号分离 |
| 浏览器自动化产物 | 截图与录像可能含界面上的测试数据，脱敏后方可作为证据留存 |

`biai-stage` 的可用性已在 2026-07-28 复核：Docker `25.0.14`、Docker Compose `v5.2.0`，测试用 PostgreSQL 容器在运行，`Bot-Test` 凭据、百炼兼容端点与只读测试 MCP 均已配置，并已实际支撑 [Issue #19](https://github.com/Moshuiwang/lingxi/issues/19) 的关联组织受控验证和 [Issue #23](https://github.com/Moshuiwang/lingxi/issues/23) 的执行层验证——**L4a 关口已被真实使用过**，早先"1.22 且服务未运行、`Bot-Test` 配置不完整"的记录已失效。

仍未具备的是：Lingxi 自己的 compose 编排、浏览器自动化在该网络环境下的可达性（L4b），以及云盘交付与管理 MCP 相关的外部触点（见[当前能力](../当前能力.md)的未验证依赖表）。因此可以宣告 L4a 的范围仅限于已实际跑通的飞书关联组织读取与 Agent SDK 执行链路；其余断言声称达到 L4 仍不成立。

## 十四、明确不做的

| 不做 | 原因 |
|---|---|
| 行覆盖率百分比门禁 | 鼓励凑数，且对否定路径不敏感；改用合同条款覆盖清单 |
| 把全部断言压在飞书 Web 的 DOM 上 | 对 UI 改版极度敏感；按[第六节](#六受控真实链路飞书-web-与-api-回读)，主断言走 API 回读，Web 只验人眼可见部分 |
| 飞书桌面/移动客户端的自动化 | 不可控且无 Web 端的等价收益；Web 端已能覆盖用户可见性 |
| 对 MCP 与 Claude 模型输出的断言式测试 | 输出非确定性；改为对**输出约束**（不出现权限措辞、不出现内部工具名）做检查 |
| 性能与压力测试 | 200 用户规模下余量三个数量级；出现真实容量问题再做 |
| 自动化变异测试工具、模糊测试 | 工具化成本高于收益；高风险断言仍按[否定测试](#八否定测试)执行一次手工变异 |
| 独立的测试环境集群 | `biai-stage` 单机足够 |
| 独立的部署设计文档 | 部署方案已在[架构设计](架构设计.md#八部署与发布)定稿、发布链路由 `协作约定` 规定；本文只约束[部署对代码的要求](#十二部署对代码的约束) |
| CD 流水线、监控告警、健康检查设计 | 在有可部署产物之前是空转；有产物后再做 |

## 十五、未定项与复审条件

**已确定项**：

| 项 | 结论 |
|---|---|
| 受控测试的执行频率 | 按风险触发；只有真实外部系统才能证伪的改动强制进入 L4 |
| L3 独立复查的触发范围 | 仅高风险 PR；所有 PR 仍由实施代理完成基础自审 |
| Agent SDK 真实模型调用的测试预算 | 产品负责人 2026-08-05 在 [Issue #41](https://github.com/Moshuiwang/lingxi/issues/41) 决策：**单次 L4a 验证不超过 3 个回合**，超出须先请示；不设月度总额度，不设独立测试配额或账单标记 |
| 合同条款覆盖清单的存放形式 | 实现期定（2026-08-06，[Issue #58](https://github.com/Moshuiwang/lingxi/issues/58)）：**本文的 Markdown 表格**，断言状态在[验收矩阵](#七关键机制验收矩阵)的状态列、条款映射在 [10.3](#103-合同条款覆盖清单)。不引入 YAML 或测试内注解——前者要么加解析依赖、要么让长期正文离开本文，后者把清单散进测试文件后无法回答"哪条条款还没有断言" |

**未定项**（需要产品负责人或实现期决定）：

| 项 | 待定 |
|---|---|
| 飞书 Web 自动登录的可行性 | **L4a 的关键前提**，需在实现期尽早验证；不成立时 Web 侧断言降为 L4b |
| 浏览器自动化的技术选型 | 待实现期决定 |

**复审条件**：

- 产品合同的规则新增或变化，导致验收矩阵缺项；
- `CI / gate` 的授权边界在 `协作约定` 中被修改；
- `biai-stage` 或 `Bot-Test` 的可用形态变化；
- 首期真实验收完成并进入放量阶段，验收重心从"能否上线"转为"能否持续"；
- 出现一次"CI 绿但真实环境失败"的事故——说明关口分工判断错误，需要重新划分；
- 飞书 Web 的登录方式或页面结构变化，导致 L4a 不再可自动化——此时需要重新评估哪些断言必须回到 L4b。
