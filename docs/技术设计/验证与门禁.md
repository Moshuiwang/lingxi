## 一、本文解决什么

两个问题，同一份答案的两面：

1. **AI 写代码前，验收标准必须已经存在。** 否则每个代理按自己的理解定义"做完了"，而模型天然倾向于实现顺利路径、少写拒绝路径。标准写在前面，它就是规格；写在后面，测试只会印证代码已有的行为。
2. **标准必须被门禁强制，而不是靠自觉。**

验证能力必须由仓库中的可复验门禁承载，不能依赖代理临时起意；促成这条规则的事故与工具差异见[形成记录](../参考证据/验证与门禁形成记录.md)。

## 三、证据层级

沿用已确立的七级阶梯（来源：用户级协作协议）。本文的作用是把每条规则钉在具体层级上，禁止把低层证据说成高层结论。

| 层级 | 含义 | 在本项目对应 |
|---|---|---|
| L0 | 产物存在 | 代码/文档写完 |
| L1 | 本机验证 | `scripts/dev/check.sh` 全绿 |
| L2 | CI 绿 | Story PR 的 `Story Fast` 或最终候选的 `Epic Full` 通过 |
| L3 | 高风险改动独立复查干净 | 未参与实现的代理审查无阻塞问题 |
| **L4a** | 真实试运行（**代理驱动**） | 代理在 `biai-stage` + `Bot-Test` 上通过飞书 API 与飞书 Web 驱动真实链路 |
| **L4b** | 真实试运行（**必须真人**） | 只有真人能完成的动作（见[第九节](#九谁执行何时才打断人类)） |
| L5 | 真实交付并回读 | 真实用户在真实入口完成任务并确认结果 |
| L6 | 持续采用 | 连续试用七个工作日无阻塞问题 |

**L4a 的证据强度与 L4b 相同**：两者都在真实外部系统上执行，区别只是执行者。代理用真实测试账号驱动真实飞书，得到的仍是真实系统的行为，不是 mock 的行为。

**硬规则**：

- `docs/当前能力.md` 的条目**只有达到 L4（a 或 b）及以上才能从"尚待实现"转为"当前能力"**。L2 绿只是对应 Story 或 Epic 的基础合并条件；按风险判定为适用的 L3 / L4 也必须通过后才能合并。
- PR 描述中必须标注本次达到的层级，不得用"测试通过"指代 L4/L5。
- 达到 L4 之前，任何面向用户的承诺都不成立。
- **能落到 L4a 的断言不得留在 L4b。** 把可自动化的验证留给人是浪费，也会让它实际上不被执行。

## 四、四道关口

```text
   实现 ──► 本机门禁 ──► CI 门禁 ──► 受控真实链路 ──► 真实用户验收
            (L1)        (L2/L3)      (L4a 代理驱动)    (L5/L6)
             │            │            │  L4b 仅少数     │
       与适用门禁同构 可自动、无副作用   真实外部依赖    产品合同旅程
       快速反馈      Story 快检/Epic 全检 按风险触发      首期一次 + 放量前
             └──────── 全部由代理执行 ────────┘        真人参与
```

**前三道关口全部由代理执行，无人类介入。** 第四道才需要真实业务用户，且那是产品验收（见[首期服务范围与真实验收](../决策记录/2026-07-26-首期服务范围与真实验收.md)），本文不重复。

对当前 PR **适用的关口**，准入条件是此前所有适用关口全绿。L1 / L2 对每个 PR 都适用，但 L2 不是每次都跑同一套：Story PR 使用按改动路由的 `Story Fast`，面向 `main` 的最终候选使用 `Epic Full`；迁移、部署、依赖、CI 自身和未知 Story 路径会自动升级到完整门禁。L3 / L4 由风险决定是否适用。低风险 PR 将 L3 / L4 标为不适用不算跳关；适用关口只有在关口本身故障时（例如 CI 平台不可用）才允许暂时跳过，此时必须在 PR 中说明原因、影响与补做计划——这条已由 `协作约定` 规定，此处不重复。

关口之间的**分工原则**：

- 能在 L1/L2 挡住的，绝不留到 L4。受控链路要占用真实外部依赖与测试账号，把可自动化的纯逻辑断言留到那里是浪费。
- **只有真实外部系统才能证伪的，绝不假装能在 CI 证明。** 用 mock 通过飞书调用的测试，证明的是 mock 的行为，不是飞书的行为。这类测试可以写（防回归），但**不计入该条规则的证据**。
- **能自动化的绝不留给人。** 判断标准见[第九节](#九谁执行何时才打断人类)。

### 风险决定是否进入 L3 / L4

每个 PR 都必须通过适用的 L1 / L2 并由实施代理基础自审，但不把完整门禁、额外复查和真实外部调用平均摊到所有 Story：

| 风险 | 判定 | 强制关口 |
|---|---|---|
| 低风险 | 纯文档、文案勘误、机械调整，或行为已能由本机与 CI 充分证明且不改变用户入口、权限、数据与外部依赖 | L1 + Story Fast；最终 Epic 候选再统一进入 Epic Full + 实施代理基础自审 |
| 高风险 | 身份、权限、安全、用户隔离、数据范围、真实外部交付、数据库迁移、部署恢复，或用户关键路径与失败语义发生变化 | 在 L1 / L2 之外强制 L3 独立复查 |
| 真实外部风险（高风险子类） | 正确性只有飞书、MCP、JumpServer、Claude Code + 百炼或真实交付链路才能证伪 | 强制 L3 + L4a；确实无法自动化的部分才进入 L4b |

PR 必须分别写明风险等级、是否存在真实外部风险、判断依据、已进入的关口和不适用关口的理由。实现代理不得为了降低验证成本把高风险改动拆成多个表面低风险 PR。

**每个 PR 的基础自审必须回答两件事；进入 L3 时，由独立审核者再次核对并给出独立结论：**

1. **未来部署可行性。** 对照[部署对代码的约束](#十二部署对代码的约束)，检查是否引入生产现场构建、生产路径或配置硬编码、人工修改生产文件，以及重启或重试造成结果丢失、重复交付或无法恢复的路径。
2. **Test 与 CI 有效性。** 对照最终 diff，确认变化的行为有相称的本地验证；稳定、可重复且无真实业务副作用的合并关键检查由 PR CI 实际执行。新增或移动目录、运行时、依赖、入口或测试命令时，必须引用 CI 配置中执行它的代码或本次 CI 对应步骤输出，不能只写“已在既有测试范围内”。

已形成的不安全设计或应进入 CI 却未实际执行的关键行为是阻塞项；尚未实现的健康检查、发布包或 CD 门禁记录为后续工作。较慢、受限或会产生真实副作用的场景留给 L4；`Story Fast` 或 `Epic Full` 通过不能替代真实用户路径。

## 五、CI 能做什么、不能做什么

`协作约定` 规定自动门禁只运行**不触及公司系统、无业务副作用**的仓库检查，并明确允许临时的本地依赖容器。

在这条边界内，下列检查**全部合规**：

| 检查 | 为什么不违反边界 |
|---|---|
| 静态检查（类型、lint、格式） | 无外部依赖 |
| 纯逻辑单测 | 无外部依赖 |
| **真实 PostgreSQL 容器测试** | 临时容器，无外部网络、无业务凭据、无业务系统副作用；用完即销毁 |
| 录制回放的外部接口契约测试 | 回放本地录制的脱敏响应，不发起真实调用 |
| 合同条款覆盖清单核对 | 纯文本比对 |

临时真实 PostgreSQL 容器不触及公司系统且无业务副作用，属于允许进入 CI 的 L2 检查。

### 5.1 当前 CI 分层

| 层级 | 何时运行 | 做什么 | 明确不做什么 |
|---|---|---|---|
| `Story Fast` | Story PR → `epic/**` | 纯文档门禁；或无真库、无镜像的代码快检；高风险 / 未知路径复用完整门禁 | 不默认启动 PostgreSQL、五组 extras 和四镜像双构建 |
| `Epic Full` | Epic / 独立 PR → `main`，以及被 Story 路由升级的高风险改动 | 仓库门禁、真库、全部 extras、四镜像双构建等价、部署与回滚兼容；成功后写出候选树证明 | 不发布镜像，不持有 `packages: write` |
| `Main Publish` | 已合并代码推送 → `main` | 回读成功的 `Epic Full` artifact，比对 PR、run 与 Git tree；一致后只构建一次四镜像并发布 | 不重复 gate、extras、双构建或真库验收 |

稳定 required check 名称是 `Story Fast` 与 `Epic Full`。候选提交变化会取消旧 run；main 的 Git tree 与候选证明不一致、直接推送没有关联 PR、证明过期或回读失败时，`Main Publish` 一律失败关闭。

下列**不能**进 CI，只能留给受控测试：

- 任何真实飞书调用（长连接、卡片、云盘、多维表格）
- 任何真实 MCP 调用
- JumpServer 登录与用户环境
- Claude Agent SDK 的真实模型调用（涉及百炼凭据与计费）

## 六、受控真实链路：飞书 Web 与 API 回读

受控真实链路（L4a）的执行者是代理，不是人。可行性来自一个事实：**飞书提供完整的 Web 端**，因此代理可以用浏览器自动化驱动真实飞书，而不必依赖真人点击。

### 双通道验证：API 回读做主断言，Web 验可见性

两条通道分工明确，不可互换：

| 通道 | 验证什么 | 为什么 |
|---|---|---|
| **飞书开放平台 API 回读** | 客观事实：文档是否创建、目录权限是否只给了本人、多维表格内容是否逐字段一致、消息是否送达 | 结构化、稳定、可精确断言；不受 UI 改版影响 |
| **飞书 Web 浏览器驱动** | 用户可见性与交互：卡片是否按预期渲染、按钮点击是否触发正确回调、流式更新是否可见、话题是否正确隔离 | 这些是"用户实际看到什么"，只有真实客户端能证明 |

**原则：凡是 API 能回读判定的，主断言走 API；Web 只用来验证人眼可见的部分。** 把全部断言压在 DOM 选择器上，会让验证套件对飞书 UI 改版极度敏感，维护成本超过收益。

### 典型链路

代理执行一次完整的受控验收，形如：

```text
API：以测试身份构造前置状态（组织资料、权限、待办）
 └─► Web：普通员工向机器人发消息
      └─► Web：观察自动开通的进度或最终结果
           └─► API 回读：状态是否真的改变、产物是否在专属目录、
                权限是否只给了本人、审计是否落库

管理员高风险动作另行验证：管理员在本人飞书私聊点击「确认执行」或「取消」，再回读动作与审计结果。专用组织资料授权只由“四达文档会议助手”在正式授权编码完成后验证，不属于普通员工旅程。
```

断言同时来自两侧：Web 侧证明用户看得到且能操作，API 侧证明系统状态真的正确。

### 前置条件与风险

飞书 Web 自动化的当前可用性以[当前能力](../当前能力.md)和执行前实时检查为准。若自动登录不可行，受影响的只是 Web 侧断言（卡片渲染与点击），API 回读侧仍按 L4a 执行；Web 侧改由真人按 L4b 抽验，不把整组降级。

登录凭据按[第十三节](#十三测试数据与身份边界)管理：只用测试身份，不进代码库，不进日志。

- **已提交的入队所占用的话题，没有回收路径。** `V-队列-02` 只覆盖"抢占后事务回滚"；一个**成功入队**的任务如果永远没有 worker 领取（S4 前半就没有消费者，S11 引入分流后还可能出现"目标版本没有对应 worker"），`conversation.running_task_id` 会一直占着，该话题此后只会回"当前任务仍在处理中"。`reclaim_stale` 只认 `status='running'` 且心跳超时的任务，`queued` 回收不到；`/stop` 只置 `stop_requested`，不释放占用。**因此 gateway 不能单独上线**，且 S11 接分流规则前必须先有 `queued` 的超时治理。
- **长连接中途静默死亡的检测未在真实环境验证。** 官方 SDK 在 `auto_reconnect=False` 下把接收循环的异常抛在一个没人 await 的 task 里，`start()` 永不返回；本批靠轮询 SDK 的私有属性 `_conn`（它在抛之前会被 `_disconnect()` 置回 `None`）来发现掉线。该私有属性一旦改名，行为降级为"没有断线检测"而不是误报重连。真实断线重连属 L4a。

**V-审计-03 的残余缺口必须写在这里，不许再声称它是绝对保证。** 产品合同第 109 / 121 行用的是绝对措辞，但实现已被证明做不到绝对——下面两类完整凭据仍会原样进入审计明细：

| 残余缺口 | 为什么不堵 |
|---|---|
| **纯字母、短于 32 字符的裸秘密**出现在错误正文、回执正文或工具名里 | 这三处不经过字段白名单，长度上界是唯一可用的规则，而它认不出纯字母短串。曾经写过"这一类由字段白名单承担"——**那句话是假的闭合**，字段白名单根本不覆盖自由文本 |
| **模型把凭据当成合法形态的工具名发出来**（`sk-live-...` 符合 `[A-Za-z0-9_.-]+`） | 对拒绝式白名单来说，"模型试图调用什么"是最重要的一条审计事实。把未知工具名投影成哈希或长度能堵住这条，但会让屏障的留痕失去用处——**代价大于收益，故意不堵** |

白名单字段里的**数字值**同样原样保留，这不是缺口而是设计：字段进白名单意味着已显式批准记录它，epoch 毫秒与雪花 ID 正是排障要看的事实。若某字段可能承载凭据，正确做法是不把它加进白名单。

上述残余缺口是产品负责人知情接受的当前边界，不得由实施方自行放宽。`V-执行-20` 只收紧 worker 出口：不在白名单里的工具名和最终正文会再次脱敏，审计核心的两条缺口仍存在。重新收紧必须改变允许进入审计的内容范围，不能再叠加一条猜凭据的正则；接受与收紧经过见[形成记录](../参考证据/验证与门禁形成记录.md)。

**两条残留风险已由产品负责人知情接受**（[Issue #52](https://github.com/Moshuiwang/lingxi/issues/52) 决策登记与裁定 C2）：一是 A 方案的固有语义——同一处漂移在人工处理前**每天重复**出现在日报里；二是零新表下没有持久载体，**每次进程重启后当日会重发一份内容完全相同的日报**。`V-花名册-31` 因此只承诺"每个进程实例同一日至多一次"，并把"重发载荷与首次逐字段一致"作为可被用例证明的那一半——"全天至多两次"依赖"当日至多重启一次"这个部署前提，代码断言不了，不作承诺。跨重启的真幂等等 `audit_event` 表落地后再补。

**这里的"一日"按 UTC 日切分**（判重水位、日报标题日期与投递去重键三者同源）。对国内使用者的可观察后果是：日报在北京时间每天 08:00 之后的首轮发出，而标题上的日期是 UTC 日期，与管理员的自然日相差 8 小时。是否改用固定业务时区属产品选择，尚待产品负责人裁定，本切片不改行为。

**投递不确定态另有一层保护，但它不是幂等承诺。** 请求已被飞书收下而响应在回程超时时，进程只能重试，而重试就会重复投递；同一天的每一次发送因此携带同一个投递 `uuid` 交服务端去重。平台侧的去重窗口是飞书的属性、**本切片未验证**（真实调用属 L4a），所以矩阵里承诺的是"重试携带同一个 `uuid`"这个代码事实，不是"平台一定不会重复投递"。

## 八、否定测试

**这是 AI 编写代码时最容易整类缺失的部分，因此单列一节并给出硬性要求。**

模型倾向于实现并验证顺利路径。产品合同里大量规则是"不得 / 不允许 / 一律不执行"形态——这些规则**只能由否定测试证明**：一个从不尝试越界的测试套件，无法证明系统会拒绝越界。

硬性要求：

> 产品合同中每一条"不得 / 不允许 / 一律不 / 禁止"形态的规则，**必须有一条对应的否定断言**，证明系统在尝试该行为时拒绝，而不只是在正常路径下不发生。

上表中属此类的条目包括但不限于：`V-开通-01/02/03/04/06/07/08/09`、`V-身份-01/02/03/04`、`V-会话-04`、`V-执行-01/02/05/06/07/08/09/10/11/12/13`、`V-接入-01/02/03`、`V-管理-01…06/08/10/11…15/17/18`、`V-权限-01`、`V-银河-01/02/03/05/10/11/13`、`V-交付-01/02/06`、`V-审计-01/02/04…07`、`V-问数-01/05`。

> 执行层这一组整组是否定断言，原因与上一段相同：一个只调用被批准工具的测试套件，无法证明系统会拒绝未被批准的工具。因此 `V-执行-02` 必须用一个**不存在于任何名单里**的工具名来断言，而不是用一个已知的危险工具名——后者只能证明该工具被禁，证明不了默认分支是拒绝。

三类特别容易漏、必须显式写的：

1. **"不发生"与"被拒绝"的区别。** 正常流程里不会发生越权交付，不等于系统会拒绝越权交付。必须主动构造越权请求。
2. **状态机的非法迁移。** 只测 `pending → executed`，不测 `executed → executed`、`expired → executed`。
3. **权限的反向断言。** 只测"权限管理员能看到用户列表"，不测"运维管理员**看不到**"。

否定断言还必须证明自己**会变红**：权限、安全、审计、用户隔离类的新增断言，在交付前必须由验收者或未参与实现的代理故意破坏一次对应实现，确认目标用例失败，再恢复实现并在 Issue 或 PR 留下脱敏证据。不引入自动化变异工具；一次稳定、可复验的手工变异即可。一条从不变红的否定断言与没有断言等价。

## 九、谁执行、何时才打断人类

全部代码由 AI 代理编写，因此**每一处人类介入都是开发速度的直接成本**。本节固化谁执行什么，避免验证体系随时间长回"事事等人确认"。

### 默认：代理执行

| 环节 | 执行者 |
|---|---|
| 写验收断言 | **规划代理**（在实现 Issue 中，先于编码） |
| 实现与本机门禁 | 实现代理 |
| CI 门禁 | 自动 |
| 基础自审 | 每个 PR 的实施代理 |
| 独立复查（L3） | **仅高风险 PR**，由未参与本次实现的代理执行 |
| 受控真实链路（L4a） | 代理，通过飞书 API + 飞书 Web 驱动 |
| 更新 `当前能力`、回写文档、留收口信息 | 实现代理 |

### 只有四类情况才打断产品负责人

沿用已确立的协作边界，不扩充：

1. **目标或成功标准实质改变** —— 例如某条验收断言与产品合同冲突，需要改的是合同而非断言；
2. **需要新的身份、权限、预算或对外承诺** —— 例如新增测试账号、开通新的应用权限、模型调用额度；
3. **动作不可逆且恢复方案未被证明** —— 例如首次向真实用户发送消息、删除生产数据；
4. **真正的产品价值取舍** —— 例如某条规则实现代价过高，是否降低承诺。

**不属于打断范围**（代理自行完成）：断言怎么写、测试怎么组织、用哪个库、CI 怎么配、发现 bug 后怎么修、受控链路怎么跑。

### 断言的修改权限

- 实现代理**不得自行降低或删除**断言；认为断言不合理时回到 Issue 提出修改，由规划代理裁定。
- 断言的修改**只有在改变产品含义时**才升到产品负责人；纯技术表述调整（换等价的判定方式、拆分或合并断言）由代理决定。

### L4b 只保留真正无法自动化的

当前判断只有一类必须真人：

| L4b 项 | 为什么不能自动化 |
|---|---|
| 真实业务用户判断结果"对不对、有没有用" | 这是产品判断，属 L5，本来就由三名真实试用用户承担 |

除此之外的任何断言若被标为 L4b，需要在 PR 中说明为什么不能自动化。

## 十、AI 开发流程中的前置动作

这是本文对"AI 开发前把验收想清楚"最直接的落地。

### 10.0 唯一跨切片开工门禁：Agent SDK + 百炼最小真实链路

在任何依赖执行层的业务实现 Issue 开始编码前，候选组合必须先在 `biai-stage` 通过一条无真实业务副作用的最小链路，覆盖：真实 Agent SDK + 百炼会话及恢复、真实只读 MCP、隔离 cwd 与受控 Skill、hook 与编排层审计、默认拒绝的越界探针，以及不保存凭据的脱敏证据。

该前置链路已经通过，但只证明当时受测组合可行；当前已具备的范围看[当前能力](../当前能力.md)，历史回合与补测数字看[形成记录](../参考证据/验证与门禁形成记录.md)。Agent SDK、CLI、模型端点、hook 绑定、白名单或执行器装配发生相关变化时，必须重跑受影响的 L4a，不能沿用旧提交结论。

两条持续有效的硬约束是：

- **审计链必须自己合成**。`PostToolUseFailure` 的语义是「工具抛错」，被 MCP 包成正常响应的业务失败不触发它；权限拒绝没有任何 hook 回调（已确认不是事件名未注册）。要审计「用户实际没拿到结果」和「某次调用被拒」，必须由执行层解析工具回执内容、并在自己的 `PreToolUse` 里记账拒绝决定。
- **只读边界必须由执行层强制**。默认拒绝、只放行显式白名单，新增内置工具自动落入拒绝分支；不得依赖 `allowed_tools`、`disallowed_tools` 或提示词约束。

执行层相关切片必须认领 `V-执行-18…21`。L2 只证明本侧装配；只有当前候选提交通过 `V-执行-21` 的 L4a，才能宣告真实运行时的只读边界成立。中途提交的证据不得覆盖后续改动，单回合执行器成立也不代表飞书入口、多轮会话或生产服务已经接入。

### 10.1 其余断言按切片认领，不是全量开工门槛

**[验收矩阵](#七关键机制验收矩阵)是目录，不是清单。** 没有任何单个 PR 需要满足全部断言。

每个实现切片只认领与其范围相关的断言，其余保持"未认领"。切片合并时，只有它认领的断言必须全绿。这条必须写明，否则实现代理会把矩阵读成开工前置条件，第一个切片就卡死。

| 状态 | 含义 |
|---|---|
| 未认领 | 尚无切片负责，覆盖清单**不对其做强制** |
| 已认领 | 某个 Issue 声明本切片实现它，合并前必须有对应测试且通过 |
| 已验证 | 断言已被测试覆盖并在对应层级通过 |

**这三个状态就写在验收矩阵的「状态」列里，由门禁强制。** `scripts/ci/check_acceptance_matrix.py` 解析本文的全部断言表，每一行必须给出且只给出上表三个词之一；缺列、留空，或写成别的词（例如把 [10.2](#102-实现-issue-必须先写验收断言) 里 Issue 正文用的"待实现"抄进来），门禁变红。这一列是断言状态的**唯一**机器可读落点：受控验收完成后翻转状态改的就是它，不再在散文里另写一句"某某已通过"。

初始状态（2026-08-06，[Issue #58](https://github.com/Moshuiwang/lingxi/issues/58)）按仓库中已有的明确声明填写，**本次不新增任何验收结论**：

| 填什么 | 依据 |
|---|---|
| 已认领 | 本文正文已写明由某个 Issue 认领（`V-身份-*` → #16，`V-执行-01…17` → #29，`V-执行-18…21` → #37，`V-银河-*` → #17，`V-部署-08/09/10` → #29，`V-迁移-*` → #53），或 `tests/` 与 `scripts/ci/` 中已有**会执行的**检查在文件头或用例注释里显式写明认领该编号（`V-开通-01/02/03/06/07/08/09`、`V-审计-02/03`、`V-部署-01/03` 属这一类） |
| 未认领 | 以上都没有 |
| 已验证 | **本次一处都不填。** 已验证要求"断言已被测试覆盖并在对应层级通过"，而本文此前没有逐条记录哪一条在哪一层通过；成组推断等于替各切片补一个它们没做过的验收结论。由各切片在真正通过后逐条翻转 |

「本组不认领」不等于「全仓库无人认领」：`V-开通-01/02/03/06/07/08/09` 在[银河组](#银河权限落库与匹配)的说明里被排除在该切片之外，但身份切片（#16）与银河 S3 切片（#17）的测试文件已显式认领它们，因此状态列记 `已认领`。

**状态列不是证据。** `已认领` 只说明有切片负责，不说明它已经跑通；`已验证` 也只覆盖该断言在「层级」列声明的层级，声明里含 L4a / L4b / L5 而那一层尚未执行的，不得记为已验证。

### 10.2 实现 Issue 必须先写验收断言

每个实现类 Issue 在开始编码前，正文必须包含一段：

```markdown
## 验收断言

| # | 断言 | 层级 | 状态 |
|---|---|---|---|
| V-会话-01 | 两并发请求抢占同一话题，恰好一个成功 | L2 | 待实现 |
| V-会话-04 | 忙碌期消息未写入 task 表 | L2 | 待实现 |

否定断言（合同"不得"类规则）：
- V-会话-04 对应合同「该消息不进入对话历史、不排队」
```

规则：

- **断言先于代码。** Issue 领取时断言必须已经写好；实现代理不得自行降低断言。
- 断言只写"能判定真假的陈述"，不写"测试 XX 功能"。
- 认为某条断言不合理时，**回到 Issue 讨论并修改断言**，不在实现里绕过。

### 10.3 合同条款覆盖清单

维护一份机器可读的映射：`产品合同条款 → 验收断言编号 → 测试用例`。

CI 检查它，但**检查的不是覆盖率百分比，而是**：

- 每条**已认领**的断言至少有一个测试用例；
- 没有引用了不存在断言编号的测试；
- 已标记"已验证"的断言，其测试确实在声明的层级执行过。

**这三条是目标形态，不是当前状态**——截至 2026-08-06 它们都还没实装。门禁现在实际执行的是下面[清单本体与门禁实际检查的三条](#清单本体与门禁实际检查的三条)所列的检查，那一小节同时说明这三条为什么还没做。

**未认领的条款不参与强制**——否则第一个代码 PR 会因为绝大多数条款还没有断言而直接红掉。随着切片推进，未认领项逐步归零，这个数字本身就是实现进度的可信度量。

#### 清单本体与门禁实际检查的三条

清单就是下面这张表，与[状态列](#101-其余断言按切片认领不是全量开工门槛)由同一个脚本（`scripts/ci/check_acceptance_matrix.py`）解析。它现在检查的是：

- **产品合同的每个章节都必须在表里出现，且只出现一次。** 合同新增或改名一节而没有登记，门禁变红——"合同条款无断言覆盖"最常见的形态就是规则先加、断言忘了加。
- **「对应断言」格要么给出至少一个断言编号，要么写 `无对应断言`；留空即失败。** 编号必须在验收矩阵里真实存在，`V-管理-01…18` 这样的区间会逐个展开核对，中间缺号一样红。
- **写 `无对应断言` 必须在「说明」里写清为什么**，不允许静默宣布某节不需要断言。

本节开头列的另外三项（每条已认领断言至少一个测试用例、没有引用不存在编号的测试、已验证断言确实在声明层级跑过）**尚未实装**：它们需要测试与断言编号之间有可靠的机器可读绑定，而当前只有测试文件头的自由文本约定（形如"认领断言：`V-开通-01`"）。本切片不把自由文本当作绑定，留作后续。

清单按**章节**粒度维护，不逐条抄合同规则——把规则复制进清单会形成第二份合同正文并各自漂移；章节内逐条规则的否定断言覆盖仍按[第八节](#八否定测试)执行。反向不成立：矩阵里有些断言（`V-部署-*` 的多数）约束的是代码与部署，不对应任何合同章节，清单不要求它们出现。

## 十一、本机门禁必须与 CI 同构

本机门禁不得因缺少工具或版本不一致而静默退化。当前入口是 `scripts/ci/verify_repository.sh`：缺少必需工具即失败，并报告关键工具版本；此前的 `shellcheck` 差异与修复经过见[形成记录](../参考证据/验证与门禁形成记录.md)。

改进方向（属实施工作，在对应 Issue 中落地）：

- 提供 `scripts/dev/check.sh`，在容器内运行与 CI **完全相同**的检查集，消除"本机缺依赖"这一类差异；
- 保留直接在宿主机运行的快速路径，但缺依赖时**明确报告哪几项被跳过**，而不是整体失败或静默通过；工具版本也要打印——本机与 CI 装了不同版本的 linter，是一种不会报错的分歧；
- `shellcheck` 的版本应在两侧锁到同一个，否则"本机通过"仍不能预测 CI；
- 本机门禁包含 PostgreSQL 容器测试，使数据库约束类断言在推送前即可验证。

**判断标准**：一个新代理在一台干净机器上，应当能用一条命令得到与 CI 相同的结论。做不到，则本机验证不可信。

## 十二、部署对代码的约束

部署方案本身在[架构设计](架构设计.md#八部署与发布)里已经定了（单机 Docker Compose、镜像 tag 即冻结版本、切 tag 回滚），**本文不重复，也不新写部署文档**。发布链路由 `协作约定` 规定。

但有一类东西必须现在就约束：**部署对代码的要求**。它们在写第一行代码时就被固化，事后修改要动很多处；而且架构设计里"镜像 tag 就是冻结的版本、回滚等于切 tag 重启"这条，**只有在代码满足下列约束时才成立**。

| # | 可验证断言 | 层级 | 状态 |
|---|---|---|---|
| V-部署-01 | 代码中不存在硬编码的主机名、端口、路径或密钥；全部配置来自环境变量 | L2（模式扫描） | 已认领 |
| V-部署-02 | 除用户环境目录外，进程不在容器内写入任何需要持久化的本地状态 | L2（运行期文件系统监视） | 已认领 |
| V-部署-03 | 进程收到 `SIGTERM` 后停止领取新任务、完成或安全中断在途任务、在超时内退出。**部署约束**：`LINGXI_DELEGATED_CREDENTIAL_PATH` 必须指向**跨部署持久**的宿主机挂载路径（compose 卷/绑定挂载），镜像替换与重启不得丢失——目标是部署对该凭据「零特殊处理」；文件丢失或过期时的保底是重新走一次「四达文档会议助手」授权，该保底流程写入 S11 部署手册（产品负责人 2026-08-05）。`lingxi-scheduler` 的停止宽限期必须大于「续期 HTTP 超时（当前 20 秒）+ 落盘耗时」，否则 SIGKILL 会落在「已向飞书换过新凭据、尚未写回数据库」的窗口里——Docker 默认 10 秒宽限期不满足，S11 编排时须显式加大（PR #48 独立复查发现）。`lingxi-gateway`（#57）同型认领：收到 `SIGTERM` 后停止接收新事件、完成在途事件的落库、在超时内退出，不遗留"抢占了话题但任务没写进去"的中间态——在途事件各自是一个数据库事务，要么整体落库要么整体回滚。**判定必须覆盖"连接空闲、当前没有任何用户消息"这个最常见的状态**：只在收到事件之后才检查停机信号的实现，夜间与周末根本停不下来，只能等编排层 SIGKILL；因此传输层空闲时须定期让出控制权，用例用**只产出空闲心跳**的传输层而不是持续产出事件的传输层（后者恰好是该缺陷唯一能工作的情形，会给出假绿——#57 独立复查实测） | L2（真实进程信号测试） | 已认领 |
| V-部署-04 | 日志输出到 stdout / stderr，不写日志文件、不自行轮转 | L2 | 已认领 |
| V-部署-05 | 每个数据库迁移可前滚；旧版本镜像能在新库结构上正常启动 | L2（真库：迁移后用上一版本代码跑一遍冒烟） | 已认领 |
| V-部署-06 | 镜像构建不依赖构建机的本地状态；同一提交两次构建产出等价镜像 | L2 | 已认领 |
| V-部署-07 | 容器以非 root 运行；仅持有架构设计中说明的能力（`CAP_SETUID` 等） | L2（镜像与 compose 检查） | 已认领 |
| V-部署-08 | 运行时依赖全部在 `pyproject.toml` 声明；**安全边界所依赖的外部组件锁精确版本**（`==`，不用范围），升级前必须重跑对应的受控验证 | L2（配置检查）+ 升级时 L4a | 已认领 |
| V-部署-09 | 门禁跑在 `pyproject.toml` 声明支持的解释器版本上；低于下限即失败，不得靠运行环境碰巧满足 | L2（门禁自检） | 已认领 |
| V-部署-10 | **已安装的制品**（不是 `src/` 目录）能导入全部关键模块，且必须在仓库目录之外校验；新增子目录漏进制品会红 | L2（CI 独立步骤） | 已认领 |

**V-部署-05 是最容易漏、代价最高的一条。** 回滚策略依赖"旧镜像能在新库上工作"，而这一点只有显式测过才成立——破坏性迁移一旦合并，回滚就从"切 tag"变成"恢复备份"。

新增可自动化的审查要求必须同步形成 `V-*` 断言和会变红的 CI；散文提醒不构成门禁。`V-部署-08/09/10` 的形成经过见[形成记录](../参考证据/验证与门禁形成记录.md)。

### 12.1 迁移机制（Alembic）

由 [Issue #53](https://github.com/Moshuiwang/lingxi/issues/53) 认领。这一组把 `V-部署-05` 的"可前滚"落到具体机制上，并守住引入 Alembic 时**新出现的**几类沉默失败。执行者是 `scripts/ci/check_alembic_revisions.py`（不连数据库）与 `scripts/ci/check_migration_chain.sh`（真库），两者都挂在 `scripts/ci/verify_repository.sh` 上。

| # | 可验证断言 | 层级 | 状态 |
|---|---|---|---|
| V-迁移-01 | 空库上 `alembic upgrade <基线>` 与顶层编号 SQL 按序建库，两者 `pg_dump --schema-only` 归一化后**零差异**（仅排除 `alembic_version` 表及其主键）。约束名、索引名、触发器定义、函数体、部分索引谓词、表达式索引、COMMENT 全部逐字节相同 | L2（真库 + diff） | 已认领 |
| V-迁移-02 | 基线不含 `IF NOT EXISTS` 一类幂等伪装：已按编号 SQL 建成的库上直接 `alembic upgrade` **必须失败**（对象已存在），失败后表结构与数据不变，且不留下 `alembic_version` 表 | L2（真库否定） | 已认领 |
| V-迁移-03 | `alembic upgrade head` 后 `alembic_version` 恰 1 行且等于 head；在 head 上重跑 `upgrade` 是空操作，结构不变 | L2（真库） | 已认领 |
| V-迁移-04 | 迁移工具链不进运行时：`src/` 下不出现 `sqlalchemy` 或 `alembic` 字样，生产进程镜像不装 SQLAlchemy | L2（门禁扫描） | 已认领 |
| V-迁移-05 | `alembic.ini` 不含可用的默认连接串；未设 `LINGXI_MIGRATION_DSN` 时迁移**明确失败**，且不回落到业务的 `LINGXI_POSTGRES_DSN` | L2（配置检查 + 真库否定） | 已认领 |
| V-迁移-06 | 门禁的迁移检查只在一次性 scratch 库上进行并在结束后删除；主测试库全程不被写入（无 `alembic_version`）。迁移与门禁输出不打印连接串 | L2（真库） | 已认领 |
| V-迁移-07 | revision 链恰好 1 个 head、1 个 base，无孤儿 revision；每个 `downgrade()` 要么真正逆转要么显式 `raise`，不存在静默空实现；基线内嵌的编号 SQL 副本与磁盘原文**逐字节**相同，且每个 `migrations/*.sql` 都被覆盖；`migrations/README.md` 记录的 head 与基线 id 与实际链一致 | L2（门禁静态检查） | 已认领 |
| V-迁移-08 | 基线**之上**的每条 revision 真往返：`downgrade` 回上一版的结果与空库直达上一版逐字节相同，再 `upgrade` 回来与往返前逐字节相同 | L2（真库往返） | 已认领 |

**V-迁移-07 补的是本次改造引入的覆盖面缩水。** 改造前的门禁写的是 `for f in migrations/*.sql`，**每个文件都保证被执行**；换成 `alembic upgrade head` 之后这个保证消失了——一条谁都不指向的孤儿 revision 只是安静地不被执行，不报任何错。多 head 时 `upgrade head` 会自己报错，孤儿不会，所以必须显式断言。

**V-迁移-02 是这一组里最容易被"修好"的一条。** 让基线在旧库上跑得通只需要加几个 `IF NOT EXISTS`，看起来还更健壮；代价是把"版本号对不上"这种响亮的错误，换成"迁移记录说做过了、实际什么都没做"这种沉默的错误。旧库的正确接管路径是先 `alembic stamp`，写在 `migrations/README.md`。

> **V-部署-08/09/10 补于 2026-07-29（Issue #29）。** 这三条此前只以散文形式存在于 `AGENTS.md` 的 Code Review Rules（"未来部署可行性"与"Test 与 CI 有效性"），**没有任何断言编号，因此从未被实装**。后果在 Issue #29 上一次性暴露了三处：执行层的只读边界依赖 Agent SDK 与 CLI 的具体事件名，而这个依赖在仓库里没有任何声明；门禁用裸 `python3`，CI 上恰好是 3.12 所以从未暴露，本地 3.9 却能跑出全绿；测试只覆盖 `src/`，新增子目录能不能进制品无人验证。
>
> **教训：要求"审查结论必须说明 X"是一条散文规则，写一段话就能满足；只有给 X 一个断言编号并让它在 CI 里变红，它才会被实装。** 本仓库凡是真正守住的约束（默认拒绝、脱敏、回执归类）都有 `V-` 编号和会变红的用例；凡是只有散文的，都没守住。新增 Code Review Rules 时应同步给出断言编号，否则它只是提醒，不是门禁。

**现在不做**：CD 流水线、发布脚本、监控告警、健康检查细节、蓝绿或金丝雀发布。这些在有可部署产物之前是空转，且部分已由 `协作约定` 的发布链路覆盖。

## 十三、测试数据与身份边界

| 边界 | 规则 |

`biai-stage`、`Bot-Test` 与外部触点的可用性必须在执行前实时检查；日期快照见[形成记录](../参考证据/验证与门禁形成记录.md)，未验证依赖见[当前能力](../当前能力.md)。L4 结论只覆盖当前候选提交实际跑通的断言，不得从环境可用或其他链路已通过外推。
