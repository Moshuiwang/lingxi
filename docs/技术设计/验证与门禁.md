# 验证与门禁

> 状态：现行验证与门禁；本文件所在提交进入 `main` 后生效。最后整理：2026-08-08。
>
> 本文只规定**什么证据可以支持什么结论、哪些风险必须经过哪些门禁**。规划者按 GitHub [#147 长期执行计划与 Execution Trace](https://github.com/Moshuiwang/lingxi/issues/147) 生成或修订具体 `[tracking]` Execution Trace；实际拆分、角色时点、冻结与修复只看获批 Trace。Trace 缺项时退回规划者修订，编排者不得从 #147 补合同。分支、PR、发布和权限操作看[协作约定](../协作约定.md)；全部 `V-*` 断言及认领状态看[产品验收矩阵](验收矩阵.md)。

普通文档或实现任务不需要把验收矩阵全文加载进上下文；只读取本 Story 认领的断言。

## 一、本文解决什么

1. 编码前先写清可判定的验收标准，避免实现完成后才用测试解释现状。
2. 能自动判断的标准必须由会变红的程序门禁承载，不能只靠模型阅读散文。
3. CI 绿、真实环境跑通和真实用户认可分别是不同证据，不得互相替代。

门禁的事故背景与历史工具差异见[形成记录](../参考证据/验证与门禁形成记录.md)。

## 三、证据层级

| 层级 | 含义 | 本项目中的证据 |
|---|---|---|
| L0 | 产物存在 | 代码或文档已形成 |
| L1 | 本机验证 | 与适用 CI 同构的本机检查通过 |
| L2 | CI 通过 | Story PR 的 `Story Fast` 或最终候选的 `Epic Full` 通过 |
| L3 | 可选独立复查 | 若 Plan 或 Epic 验收合同采用，由未参与实现的审核者给出无阻断结论 |
| L4a | 代理驱动的真实试运行 | 在受控环境与真实外部系统完成验证 |
| L4b | 必须真人完成的真实试运行 | 只有真人才能完成的动作 |
| L5 | 真实交付并回读 | 真实用户完成任务并确认结果 |
| L6 | 持续采用 | 连续试用七个工作日无阻断问题 |

硬规则：

- `docs/当前能力.md` 只有达到 L4a / L4b 或更高层级，才能把“尚待实现”改为“当前能力”。
- PR 必须写明实际达到的层级；不得用 L2 的结果陈述 L4 或 L5 的结论。
- 能由代理稳定完成的真实验证属于 L4a，不得长期留给人。
- 如 Plan 或 Epic 采用 L3，它表示独立判断，不能由实施者自审或 CI 绿代替。

## 四、门禁与风险参考

```text
实现 → 本机与 CI 程序检查（L1 / L2）→ 按 Plan 或 Epic 合同选择 L3 / L4 → 用户验收（L5 / L6）
```

下表用于选择相称证据，**不为单个本地 PR 新增强制的人为审查关卡**。当前长期 Plan 方法要求每个 Epic Draft 前完成一次固定候选 SHA 的独立一致性审查，但该流程检查不自动形成 L3；实际采用哪些证据层级、由谁执行，写在具体 Trace 或 Epic 的验收合同中。

| 风险 | 典型范围 | 可采用的证据 |
|---|---|---|
| 低风险 | 纯文档、勘误、机械调整，且不改变用户入口、权限、数据或外部依赖 | Story 阶段的 L1 / `Story Fast`；Epic 冻结时可汇总 `Epic Full` |
| 高风险 | 身份、权限、安全、隔离、数据范围、迁移、部署恢复、关键路径或失败语义 | L1 / L2；需要额外独立判断时可采用 L3 |
| 真实外部风险 | 只有飞书、MCP、JumpServer、Agent SDK + 百炼或真实交付链路才能证伪 | 需要宣告真实外部结果时采用 L4a；确实无法自动化的部分可采用 L4b |

本节只描述证据含义，不规定角色、时点或审查轮次。每个长期 Plan Epic Draft 前的一次独立一致性审查由具体 Trace 实例化；只有 Trace 明确选择且满足本文件的独立性与证据要求时才记为 L3。普通非 Epic Draft PR 是否采用独立复查，以及如何汇总冻结候选，由对应工作合同决定。

应避免为了降低验证成本，把同一个高风险变化拆成多个表面低风险 Story；是否需要合并处理由对应 Plan 或 Epic 决定。

## 五、CI 分层

CI 只运行无公司系统副作用的仓库检查。临时 PostgreSQL 容器、脱敏回放、静态检查和纯逻辑测试可进入 CI；真实飞书、MCP、JumpServer 和真实模型调用不进入 CI。

| 层级 | 触发 | 作用 | 不做 |
|---|---|---|---|
| `Story Fast` | Story PR → `epic/*` 或 `epic/**/*` | 文档门禁或无真库、无镜像的快速代码检查；迁移、部署、依赖、CI 自身和未知路径自动升级 | 不默认重复启动 PostgreSQL、全 extras 和四镜像双构建 |
| `Epic Full` | Epic / 独立 PR → `main`，或被升级的高风险 Story | 对纯文档候选只运行文档门禁；其余输入运行仓库门禁、真库、全部 extras、四镜像双构建等价、部署与回滚兼容，并输出候选树证明 | 不发布镜像，不持有发布权限 |
| `Main Publish` | 代码合入 `main` 后 | 回读成功的 `Epic Full` 证明；树一致后只构建一次并发布四镜像 | 不重复 gate、extras、真库和双构建 |

稳定 required check 名称是 `Story Fast` 与 `Epic Full`。候选提交变化必须取消旧结论；main 的 Git tree 与候选证明不一致、没有关联 PR、证明过期或回读失败时，`Main Publish` 关闭失败。

CI 资源原则：纯文档改动在 Story 与 main 候选都只跑文档门禁；昂贵的整体验收只在代码、门禁脚本、工作流、依赖、迁移或部署输入发生变化时运行。行为风险不能仅由路径分类器推断；若 Plan / Epic 选择完整门禁，应显式记录。Story Fast 通过不等于 Epic 已验收，Epic Full 通过也不等于真实外部链路已经通过。

### 金字塔频率纪律（2026-08-24）

验证分层同时是频率分层：每一层以下层通过为前提；层级越高成本越高，执行频率必须越低、单次覆盖的改动必须越多。

| 层 | 目标频率 |
| --- | --- |
| 本机 `docs` / `fast`（`scripts/dev/check.sh`） | 每次提交 |
| 本机 `full`（真库 gate 等价） | 每批次收口前一次 |
| CI `Story Fast` | 每个 PR |
| CI `Epic Full` | 仅冻结候选与面向 `main` 合并前 |
| L4a 受控真实链路 | 仅验收窗口 |
| L5 / L6 真实用户 | 仅里程碑 |

不允许为单个 commit 触发上层昂贵验证，除非改动命中高风险升级白名单（迁移、部署、依赖、CI 自身、安全）。批次收口时报告「本批 Epic Full 次数 / 合入 commit 数」，比率退化按方法问题处理（攒批纪律见 GitHub #147 现行方法正文）。

## 六、受控真实链路

L4a 使用真实测试身份和真实外部系统，分两个通道：

| 通道 | 主证据 |
|---|---|
| API 回读 | 状态、权限、产物、消息和审计等客观事实 |
| Web 浏览器驱动 | 用户是否看得到、能否操作、卡片与话题是否符合预期 |

API 能判定的事实以 API 为主；Web 只验用户可见交互，避免把整套验收绑定在易变化的 DOM 上。若 Web 自动登录临时不可行，只把受影响的可见性断言转为 L4b，不降低 API 回读要求。

执行前必须实时确认 `biai-stage`、`Bot-Test` 和外部触点可用；历史可用不等于当前可用。L4 结论只覆盖实际受测提交和断言。

## 七、关键机制验收矩阵

全部产品、部署与迁移断言已经独立到[产品验收矩阵](验收矩阵.md)。保留本节标题是为了兼容既有文档链接；本文不再复制矩阵正文。

实现 Story 只认领与自身范围相关的 `V-*`。新增或改变产品规则、部署约束时，必须同步更新矩阵和会变红的检查。

## 八、否定测试

产品合同中每一条“不得 / 不允许 / 一律不 / 禁止”形态的规则，都必须有主动尝试违规行为的否定断言。只测试正常路径“不发生”，不能证明系统会拒绝违规请求。

特别注意：

1. 主动构造越权请求，区分“没有发生”和“被系统拒绝”。
2. 覆盖状态机非法迁移和重复执行。
3. 同时验证“谁能看”和“谁不能看”。
4. 默认拒绝规则必须用一个不在任何名单中的未知对象证明，不能只证明某个已知危险对象被禁。

**变异验红**（硬规则；产品负责人 2026-08-27 裁定升格，Issue #304 九项裁定第 7 项；实证：#304 批次 5 审查 10 关注面/10 变异全红、两周实践）：

- 定义：新增或修改的关键防线测试，交付前临时改坏被测行为，确认目标测试确实变红，再恢复并复绿；红/绿结果与变异点写入交付报告，不能只写结论。
- 适用面：行为面修复、安全/权限/幂等类防线、本节否定用例；纯文案、纯注释或纯格式改动可豁免。
- 操作纪律：变异实测后必须清理 `__pycache__`（`find . -name __pycache__ -exec rm -rf {} +`）或全程用 `python -B`——同秒改坏又还原会留过期字节码，造成假红假绿（2026-08-26 审查者实测踩坑）。
- 审查侧：批量审查从关键测试中抽 3-5 个独立复做变异实测，核实测试本身未被异化。

## 九、验收资产的技术约束

验收资产包括断言、测试、回放、环境脚本、CI Stage 与用户旅程记录。它们必须满足：

- 行为变化与相应断言、测试或检查在同一 Story 中维护，不能在 Epic 末尾只补散文说明。
- 证据必须对应明确的候选提交；旧提交的通过记录不能覆盖新候选。
- 完整门禁和真实链路如被采用，应汇总在同一冻结候选上；统一修复后只重跑受影响检查与最终整体验收。
- 新增可自动判断的约束，应形成 `V-*` 断言和会变红的程序检查。

谁维护、何时运行，写在具体 Trace / Epic 验收合同中。每个长期 Plan Epic Draft 前必须实例化一次独立一致性审查；是否升级为 L3 仍由 Trace 按风险选择，并满足本文件的证据要求。本文不再重复角色规则。

实现者不得自行降低或删除产品断言。等价技术表述可以由代理调整；改变用户承诺、权限、数据范围或外部边界时，必须交给产品负责人决定。

## 十、AI 开发前置动作

### 10.0 Agent SDK + 百炼最小真实链路

任何依赖执行层的业务实现开始前，候选组合必须先在 `biai-stage` 通过无真实业务副作用的最小链路：真实 Agent SDK + 百炼会话及恢复、真实只读 MCP、隔离 cwd 与受控 Skill、hook 与编排层审计、默认拒绝的越界探针，以及不保存凭据的脱敏证据。

相关运行时、hook、白名单或装配变化时，必须重跑受影响的 L4a。审计链要解析实际工具回执并记录本侧拒绝决定；只读边界必须由执行层默认拒绝、显式放行，不能只依赖提示词或运行时名单。执行层相关切片认领 `V-执行-18…21`。

### 10.1 断言按 Story 认领

[产品验收矩阵](验收矩阵.md)是目录，不是要求单个 Story 全量完成的开工清单。

| 状态 | 含义 |
|---|---|
| 未认领 | 尚无 Story 负责，不作为当前 Story 合并门槛 |
| 已认领 | 已有 Story 负责，合并前必须有相称测试和证据 |
| 已验证 | 已在声明层级实际通过 |

状态只写在矩阵“状态”列，并由 `scripts/ci/check_acceptance_matrix.py` 强制；不在散文里另建进度副本。

### 10.2 Story 必须先写验收断言

每个实现 Story 在编码前至少写清：

```markdown
## 验收断言
- [ ] V-xxx：给定……当……则……

## 否定断言
- [ ] 当尝试……时，系统拒绝且不产生……

## 证据目标
- 目标层级：L2 / L3 / L4a / L4b
- 本 Story 负责：……
- 留给 Epic 整体验收：……
```

若 Story 只做内部重构且不新增用户规则，可以认领既有断言并说明“不新增断言”；不能空着。

### 10.3 合同条款覆盖清单

合同章节与断言的机器可读映射在[产品验收矩阵第二节](验收矩阵.md#二合同条款覆盖清单)。本文不再维护副本。

### 10.4 PR 证据

PR 描述必须写明风险、达到的证据层级、实际执行的检查、尚未验证的断言和恢复方式。Story PR 只证明该 Story 的增量；最终 Epic PR 汇总整体验收合同证据。

## 十一、本机与 CI 同构

本机代码门禁入口是 `scripts/ci/verify_repository.sh`；纯文档改动使用 `scripts/ci/verify_docs.sh`，不安装依赖、不启动数据库或 Docker。两者缺少自身必需工具时都必须明确失败并报告原因。

目标是新代理在干净机器上能用一条对应命令得到与 CI 相同的结论：纯文档对应 `verify_docs.sh`，代码对应 `verify_repository.sh`。Epic 冻结前的整体验收再对应 Epic Full。缺依赖时必须明确列出未执行项，不能用“部分通过”声称门禁通过。

### 一键复现与本机分层验证（`scripts/dev/check.sh`，Issue #236）

`scripts/dev/check.sh` 是本机日常回路的入口，架在 `verify_repository.sh` / `verify_docs.sh` 之上：一键建出与门禁逐位一致的依赖环境，并按改动路径只跑 CI 会对本次改动跑的那一层，不必每次全量。它不改变 `verify_repository.sh` 现有完整模式的语义，只是更方便地调用它；`verify_repository.sh` 仍是冻结前的权威入口。

三层与 CI 的对应关系（`full` 只等价于 `Epic Full` 里的 `gate` **这一个作业**，不是整条 `Epic Full` 流水线——见下表「不做什么」）：

| 本机层级 | 等价的 CI 结论 | 环境从哪来 | 不做什么 |
| --- | --- | --- | --- |
| `docs` | `Story / docs`、`Epic Full / docs` | 无需安装 | 只跑 `verify_docs.sh`，不装依赖、不起数据库或 Docker |
| `fast` | `Story / code fast` | extras、shellcheck 版本、Python 版本现读自 `.github/workflows/story.yml` 的 `fast` job | 不启动真库、不构建镜像；不跑 `workers/oauth-bridge` 的 Node 依赖校验（`npm ci`/`npm test`/`npm run check`）——Node 依赖有自己的 `package-lock.json` 保证复现，且与本入口要消灭的 Python extras 漂移场景无关 |
| `full` | `Epic Full / gate`（仅此一个作业） | extras、shellcheck 版本、Python 版本、真库镜像与认证方式现读自 `.github/workflows/ci.yml` 的 `gate` job 的 `services.postgres` 声明；额外起一次性同配方真库容器 | 不构建四镜像、不做部署契约核对、不做双路径可复现构建比对（那些仍只在 CI 的 `Epic Full / image`）；不跑 `Epic Full / extras` 那六条各自干净环境的 extra 单独验证腿；同样不跑 Node 依赖校验 |

- 层级判定复用 `scripts/ci/classify_story_changes.classify()`，与 CI 实际路由到哪一层保证一致。
- extras、shellcheck、Python 版本、真库参数由 `scripts/dev/gate_spec.py` 现读自 `ci.yml`/`story.yml`，不另写清单；解析失败响亮失败，不安静退回旧值。
- 虚拟环境默认每次重建（`--reuse-venv` 跳过）；`fast`/`full` 跑完核对工作树洁净。
- 冻结前仍须跑一次完整 CI `Epic Full`——本机 `full` 只覆盖其中的 `gate` 作业，不能替代 `extras`、`image` 两个作业。

实现细节见 [`scripts/dev/README.md`](../../scripts/dev/README.md)。

## 十二、部署对代码的约束

部署和迁移的具体 `V-部署-*`、`V-迁移-*` 断言、执行脚本和认领状态见[产品验收矩阵第三节](验收矩阵.md#三部署与迁移断言)。保留本节标题是为了兼容既有文档链接。

底线不变：不在生产现场构建，不硬编码生产路径或配置，不人工修改生产文件；重启与重试不得造成结果丢失、重复交付或无法恢复。新增可自动审查的要求，必须同时形成 `V-*` 断言和会变红的程序检查；散文提醒不构成门禁。

## 十三、测试数据与身份边界

| 边界 | 规则 |
|---|---|
| 生产凭据 | 任何测试不得使用 `Bot-Prod` 凭据或生产数据库 |
| 受控测试 | 只用 `Bot-Test`、独立测试数据库和运行环境注入的凭据 |
| 真实用户 | 只用于 L5/L6，不用于反复触发异常或越权路径 |
| 证据 | 脱敏后留在 PR 或 Issue，不进入长期产品正文 |
| 测试数据 | 使用固定化名，不用真实业务数据构造测试 |
| 浏览器产物 | 截图或录像脱敏后才能留存 |

凭据不得进入代码库、日志或 PR 正文。

## 十四、明确不做

- 不用行覆盖率百分比替代合同断言覆盖。
- 不把全部真实验收绑定到飞书 Web DOM。
- 不对非确定性模型输出做逐字断言；只检查明确的输出约束。
- 当前不引入自动化变异、模糊测试、独立测试集群或重复的部署设计正文。
- `Epic Full` 只形成发布候选证明；发布权限和动作留在 `Main Publish`。

## 十五、复审条件

出现以下情况时复审本文和验收矩阵：

- 产品合同新增或改变规则；
- `Story Fast`、`Epic Full`、`Main Publish` 的授权或职责变化；
- 外部测试身份、环境或自动登录方式变化；
- 出现一次“CI 绿但真实环境失败”的事故；
- 首期真实验收结束，工作重心从上线转为持续采用。

Agent SDK 真实模型验证仍沿用 [Issue #41](https://github.com/Moshuiwang/lingxi/issues/41) 的预算：单次 L4a 不超过 3 个回合，超出先请示。
