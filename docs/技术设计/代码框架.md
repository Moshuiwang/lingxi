### 文件体量棘轮

**这是一条新增的仓库内部工程约定，不是在固化此前已经生效的规则**——代码框架此前没有任何体量条款，Issue #238 落地时它对 `src/lingxi/` 下全部约 100 个文件同时生效。它不改变用户体验、权限、数据或外部依赖边界，属于实施代理可自裁的范围（产品负责人不需要拍板）。

不设绝对行数上限——本仓库文档字符串极重（`core/permission/publish_row.py` 980 行里很大一块是连贯的中文正文说明），一个偏低的绝对上限只会逼人把连贯逻辑劈成互相牵连、更难读的两半。改用**棘轮**：`src/lingxi/` 下已经超过 1500 行的文件只许变小、不许变大；未超过的文件不得新超过。基线登记在 `scripts/ci/size_ratchet_baseline.txt`，由 `scripts/ci/check_size_ratchet.py --refresh` 生成——记录值必须与实测行数精确相等，手工改数值会被直接判红；门禁由该脚本自动守住，不是靠这段说明。

**基线文件位置的连带成本（2026-08-19 复查确认，非假设）**：`scripts/ci/size_ratchet_baseline.txt` 与门禁脚本放在一起，是最直接、最不容易被人遗漏更新的位置；代价是 `classify_story_changes.py` 的 `FULL_PREFIXES` 把整个 `scripts/ci/` 目录标为高风险——任何 PR 只要触碰这一个数据文件（哪怕只是因为某个文件缩小、跑了一次 `--refresh`），都会从 `Story Fast` 被提级到 `Epic Full`（起真库、全部 extras、四镜像双构建）。#237、#239 两个拆分 Story 都需要在合并后重新 `--refresh`，都会各吃一次这个连带成本。未挪动文件位置：`scripts/dev/`（在 `FAST_PREFIXES` 里）语义上是"受控验证脚本"而非门禁数据，`src/lingxi/`／`tests/` 挪进去更不合适（污染正式代码树／测试资产），裸 `scripts/` 会落进分类器"未知路径一律升级"的兜底，同样触发 `full`；而修改 `classify_story_changes.py` 本身是一处影响全仓库所有 PR 分类的改动，不适合在本次三条门禁的 PR 里顺带做。因此保留现状，连带成本如实登记于此，后续如证明确实频繁造成不必要的完整门禁开销，再单独立项收窄分类规则。

**棘轮是一次性的，不是永久锁死**：一个文件一旦缩到 1500 行以下，它在基线里的登记会被 `--refresh`整条移除，此后可以自由涨回到 1499 行都不会被拦——这是「鼓励拆分」必然要接受的代价，不是漏洞。例如 2048 行的文件拆成 1448 + 600 两个文件后，两者合计的"可用余量"反而变成了约 2998 行（各自到 1499 为止）。基线也可能是**空的**（`src/lingxi/` 下没有任何文件超过阈值时）——这是合法终态，此时棘轮退化为"不许任何文件新跨过 1500 行"，仍然是它的主要价值，不代表门禁坏了。

**接受但不修的边界（阈值方案的固有性质，2026-08-19 复查确认）**：一个文件可以稳定停在 1499 行，或者把一个本该重构的大文件机械拆成两个刚好 1499 行的文件来绕开棘轮——这是任何行数阈值方案的固有局限，不是本实现的缺陷。2026-08-19 复查时 `src/lingxi/` 下最大的未登记文件是 1140 行（`mcp_readiness.py`），1400–1500 行区间零文件，阈值当前不会诱发这种边界博弈；如果将来观察到有人真的在利用这个边界，再收紧应对，不预先为一个尚未出现的问题增加复杂度。

**已知边界（明确接受，不再修，2026-08-19 三路独立复查确认）**：

1. **棘轮只在单次快照内核对"基线记录是否等于实测行数"，不核对历史。** 如果同一次改动里，文件净增的行数与基线记录的净增数值精确一致（例如把一个已登记文件从 2048 行改到 2348 行，同时把基线那条也从 2048 改成 2348），检查会看到"记录等于实测"而判绿。精确相等提供的价值是"任何净增都必须在同一次改动里对基线文件留下一处可审阅的文本 diff"，不是"净增在算法上不可能通过"。真正堵住这类绕过需要对照上一个可信基线（例如与合并基比对），但本仓库当前跑 `verify_repository.sh` 的 CI job（`ci.yml` 的 `gate`、`story.yml` 的 `fast`）都是浅克隆、不带 `fetch-depth: 0`，没有可靠的历史或 `origin/main` 引用可比，2026-08-19 复查后确认现阶段加不上。接受：`--refresh` 已经拒绝为增长背书，抬高基线只能靠手工编辑那个数字——这是刻意行为，且落在一个存在意义就是被人审阅的文件里，diff 极其显眼；本门禁的威胁模型是"无意写出来的违规"，不是"敌手蓄意绕过审阅"。
2. **基线里登记一个当前不存在的路径会被静默跳过，不会报错。** `evaluate()` 对基线里查不到对应实测文件的登记（`current.get(path) is None`）一律当作"文件已经不在扫描范围内"处理，不区分"确实被删除/拆分了"与"这条登记的路径从来就没有真实存在过"。理论上可以在一次无害 PR 里预埋一条指向未来文件名的登记，之后再落地那个文件，只要落地时精确匹配登记的行数就会绿。接受：与第 1 点同一个理由——预埋这种登记本身就是一次显眼的手工编辑，且需要后续精确凑出登记的行数，不是无意能触发的操作。

## 二、三层之间的 import 规则

架构设计的「模块化单体」靠这三条规则成立，违反任何一条都是审查阻塞项：

1. **`core/` 不 import `adapters/`、`apps/`、任何外部 SDK，也不做网络或文件 I/O。** 领域规则必须能在纯单测里被完整证伪。需要外部数据时，由调用方把数据作为参数传进来（参考 `core/identity/onboarding.py` 的现有写法，及接口设计[「八、领域服务接口」](接口设计.md#八领域服务接口)的函数形态）。
2. **`adapters/` 是外部 SDK 与协议细节的唯一落点。** 每个外部系统一个模块；SDK 类型不得泄漏进 `core/` 的函数签名。PR #36 的 `claude_agent_hooks.py`（约 30 行、唯一 import Agent SDK 的文件）是这一层的样板。
3. **`apps/` 只做组装。** 读配置、建连接、把 adapters 注入 core、处理信号与退出；不写业务规则。每个进程一个子包，以 `python -m lingxi.apps.<name>` 启动，对应 Docker Compose 的一个服务。

跨模块调用只走接口设计「八、领域服务接口」列出的函数；模块不读其他模块的表。写路径上 `enqueue_publish`、`audit.record` 必须接收调用方事务对象，由类型签名强制「审计与状态变更同事务」。

第 1 条（`core/` 不 import `adapters/`、`apps/`、任何外部 SDK）由 `scripts/ci/check_core_layering.py` 自动守住，不是靠这段注释——它用 `ast` 遍历 `core/` 每个文件的整棵语法树（含函数体内的延迟导入，本仓库的第三方 import 全部写在函数体里），2026-08-19 起接进 `verify_repository.sh`（Issue #238）。检查覆盖两层：直接 import（含 `from lingxi import adapters` 这类"别名即子模块"的写法）与**传递闭包**——`core/` 经由一个内部模块（例如 `lingxi.config.*`）间接 import 到 adapters/apps 同样会判红，复用 `check_installed_package.py` 已经写好的源码 import 解析（`source_module_files`/`_source_imports`），不重复实现同一套相对 import 与模块/符号歧义处理逻辑。SDK 类型不泄漏进 `core/` 函数签名（第 2 条后半）是该检查的直接推论：签名里引用一个未导入的类型名，要么触发导入（会被同一检查抓到），要么只能用字符串写死的前向引用去绕——这种极少见的写法目前不在扫描范围内，属于已知的残余风险。第 2 条前半（`adapters/` 是外部 SDK 与协议细节的唯一落点，即 `apps/` 不得绕过 `adapters/` 直接 import 外部 SDK）**当前没有对应的自动检查**——`check_core_layering.py` 只扫 `core/`，不扫 `apps/`；2026-08-19 复查时实测 `apps/` 当前同样零处直接 import 外部 SDK，之后若要补，成本与 `core/` 那条同样低，留待后续按需扩展。第 1 条里「不做网络或文件 I/O」与第 3 条「`apps/` 只做组装」同样仍靠测试与代码审查把守，尚未有对应的自动检查。

**三条门禁共同的扫描边界（2026-08-19 复查确认，接受不修）**：符号链接目录逃逸（`rglob` 遍历到仓库外）、`.pyi` 存根文件、`.yml`/`.toml`/`.ts` 等非扫描后缀里出现的归属或 import 违规，均不在三条门禁的扫描范围内。本仓库当前没有这类用法（无符号链接目录、无 `.pyi`、YAML/TOML/TS 里不写归属断言或分层 import），出现前不预先为假设的用法增加扫描复杂度；一旦出现，按当时的实际形态扩展相应脚本的 `SCAN_SUFFIXES`/遍历逻辑。

## 三、横切约定

- **标识、时间、错误信封、幂等、trace_id**：一律遵循接口设计[「二、通用约定」](接口设计.md#二通用约定)，不在各模块自造。ULID 生成、错误信封类型、`redact()` 脱敏出口放在 `core/` 的公共小模块中，全仓库只有一份。
- **配置**：全部来自环境变量，统一 `LINGXI_` 前缀，在 `apps/` 入口一次性读取并构造成类型化配置对象传下去；`core/`、`adapters/` 不直接读 `os.environ`。不硬编码主机、端口、路径、密钥（断言 V-部署-01）。`.env` 只用于本地与受控测试，已在 `.gitignore`。
- **凭据**：不进代码、日志、数据库。日志、数据库不存凭据明文是产品合同明令（[产品合同与外部边界](../产品合同与外部边界.md)「统一用户记录与权限变化」："飞书短期令牌、数据库认证材料、MCP 令牌明文及其他凭据不得进入用户表、日志、Issue、文档或用户交付物"）；不进代码、不进用户环境是架构设计自身的从紧要求，合同正文未规定这两处（2026-08-19 归属核对更正，[#238](https://github.com/Moshuiwang/lingxi/issues/238)）。**「不进用户环境」这条架构自设要求已于 2026-08-17 由产品负责人裁定收窄**：飞书机器人凭据、专用授权凭据与 MCP 加密主密钥仍然一律不进用户环境；**唯一的例外是逐用户的问数 MCP 令牌**，它按裁定明文落进该用户自己家目录的 `.mcp.json`（`440`），正文见[架构设计 6.9](架构设计.md)与[决策记录](../决策记录/2026-08-18-用户环境持有问数MCP令牌.md)。长期凭据放操作系统级密钥管理；测试只用固定假凭据探针。
- **日志**：结构化输出到 stdout / stderr，带 `trace_id`，不写日志文件、不自行轮转（断言 V-部署-04）。
- **进程生命周期**：收到 `SIGTERM` 后停止领取新任务、完成或安全中断在途任务、超时内退出（断言 V-部署-03）；除用户环境目录外不在容器内写持久化本地状态（断言 V-部署-02）。
- **注释与文档字符串**：中文，说明「为什么」与边界约束，不复述代码行为；对外承诺一律链接产品合同或技术设计，不复制条文。把某句规则的权威记成产品合同本身（区别于模块自己的接口/服务合同）的归属断言，必须能在[产品合同与外部边界](../产品合同与外部边界.md)正文里找到对应；这条由 `scripts/ci/check_contract_attribution.py` 自动核对（登记表 + 章节存在性 + 摘录未过期三重校验），不是靠作者写下时自觉核对一次——本条上方「凭据」那一句 2026-08-19 前就错记过一次（`用户环境` 从未出现在合同正文里），Issue #238 落地本门禁正是为了挡住同类笔误重复发生。

**归属核对的匹配机制（2026-08-19 三方复查最后一轮定稿）**：触发词是一条正则族（`(产品合同｜合同) + 可选"明确" + 归属动词` 覆盖后缀写法，`按/依据/根据 + 合同` 覆盖前缀写法），不是一份需要不断手工补漏的固定短语清单；登记表按**整行原文逐字相等 + 出现次数**核对，一行文本被复制到别处、或已登记行后面追加新内容，都会让多出来的那次出现单独判红；元排除（"合同条款覆盖清单"这类自我描述词汇）只挖掉被排除的那一段，不会连带放行同一行里的其他真实断言；合同文档解析标题时跳过代码围栏与 HTML 注释块，注释掉的旧标题不会被当成仍然有效的章节。

**已知边界（明确接受，不再修，2026-08-19 三方复查确认）**：`git ls-files` 通过 `GIT_INDEX_FILE` 等环境变量被操纵成返回空结果时，扫描范围会静默变空，门禁判绿。接受：触发它需要操作者刻意修改会影响 Git 底层行为的环境变量，与棘轮已经接受的"切换 `HOME` 绕过全局哨兵"同一档——操作者是编排者本人与受控代理，不是需要被防范的敌手。

### PostgreSQL 连接与超时

这是代码仓库约定，不是部署状态声明：

- `src/lingxi` 的正式 PostgreSQL 连接只能通过 `lingxi.adapters.postgres.connect` 建立。该工厂把 `connect_timeout=5s`、`statement_timeout=3s`、`lock_timeout=2s` 作为唯一业务默认值，以 libpq 启动参数写入每个连接，覆盖连接建立后的第一条语句和等锁等待。
- 需要覆盖时只能传入经过 `PostgresTimeouts` 校验的配置；每项必须是 `1–5` 的正整数秒，调用点不得自行传 `connect_timeout` 或 `options`，不得退回无上界等待。5 秒上界由 scheduler 的 150 秒停机宽限预算反推，门禁扫描正式代码与受控脚本，测试建库和受控测试资产不属于生产连接入口。
- Alembic 迁移工具链不依赖运行时适配器，使用 `migrations/alembic/migration_dsn.py` 的独立配置：建连 `5s`、语句 `60s`、锁等待 `10s`。这是迁移工具链隔离下的有限例外，必须保留原因和上限，不能以迁移可能较慢为由取消超时。

## 四、测试约定

- 测试框架为标准库 `unittest`，`PYTHONPATH=src python3 -m unittest discover -s tests` 必须可在无外部依赖的机器上运行；这与 CI 的执行方式一致（见 `scripts/ci/verify_repository.sh`）。
- 真实 PostgreSQL 测试通过 `LINGXI_POSTGRES_DSN` / `LINGXI_POSTGRES_CONTAINER` 环境变量启用，缺省时明确跳过并输出原因，不静默通过；数据库约束类断言（唯一索引、条件更新、触发器）必须在真库上验证，不用 mock（验证与门禁第五节）。
- 每个实现切片认领[验证与门禁](验证与门禁.md#七关键机制验收矩阵)中的断言编号，测试名或注释引用该编号；合同「不得 / 不允许」类规则必须有对应否定测试（第八节）。
- 涉及真实外部系统的行为不在 CI 里 mock 成证据；留给 `biai-stage` 的 L4a 受控链路。

- 已知的架构偏差在正式化时必须纠正：现有 `refresh_tokens.py` 的续期扫描线程挂在长连接进程内，正式实现按架构设计归入 `lingxi-scheduler`（[Issue #16 的复验记录](https://github.com/Moshuiwang/lingxi/issues/16#issuecomment-5188063325)）。

## 六、依赖与迁移

- 依赖声明只在 `pyproject.toml`，**按进程拆 optional extras**，组名与 `python -m lingxi.apps.<name>` 及 Docker Compose 的服务对齐，使镜像只装该进程真正用到的依赖（Issue #56）。CI 与 `biai-stage` 用 `pip install '.[extra]'` 安装同一声明；仓库不使用 uv 锁文件。现有分组：

  | extra | 对应进程 / 用途 | 内容 | 依据 |
  | --- | --- | --- | --- |
  | `scheduler` | `python -m lingxi.apps.scheduler`（专用授权凭据续期扫描；同一镜像承载一次性 reauthorize job） | `cryptography`、`psycopg[binary]`、`websockets` | 常驻入口 → `adapters/delegated_credentials.py`；一次性 `python -m lingxi.apps.reauthorize` → 正式 `oauth_bridge_client`；`websockets` 不用于常驻 scheduler，但由同镜像的正式重授权入口使用 |
  | `reauthorize` | `python -m lingxi.apps.reauthorize`（scheduler 镜像内的一次性正式重授权 job） | `cryptography`、`psycopg[binary]`、`websockets` | 正式 E1 换码与 delegated vault/CAS；Bridge 只主动出站接收回调，不接收终端粘贴 |
  | `worker` | `python -m lingxi.apps.worker`（最薄受控执行器） | `claude-agent-sdk==0.2.128` | 入口 → `adapters/claude_agent_hooks.py`、`adapters/claude_agent_session.py`。版本变化需重跑门禁验证，见验证与门禁 10.0 |
  | `gateway` | `python -m lingxi.apps.gateway`（飞书长连接接入与任务入队） | `lark-oapi`、`psycopg[binary]`、`websockets` | 入口 → `adapters/feishu_longconn.py`（`ws.Client`）、`adapters/feishu_outbound.py`（加表情、回文本）、`adapters/postgres_conversation/`（Issue #239 起是按读写边界拆分的包，既有调用点用到的名字全部保留，见包 __init__.py 的边界说明）。`websockets` **显式声明**：`lark-oapi` 会传递携带它，但矩阵装的是 `.[gateway]`，漏声明永远不会变红（Issue #57） |
  | `bot-test` | 第五节的 Bot-Test 受控验证资产（含常驻长连接 `adapters/feishu_onboarding.run_long_connection_bot` 与 `scripts/` 受控脚本）；`bot-test` 组本身不进生产镜像 | `cryptography`、`lark-oapi`、`psycopg[binary]`、`websockets` | `lark-oapi` 只被旧 `adapters/feishu_onboarding.py` 用；旧 `adapters/oauth_bridge.py` 与正式 `oauth_bridge_client.py` 共享 `websockets` 传输依赖 |
  | `migrate` | 部署时跑一次的**迁移作业**（`python -m alembic upgrade head`），**不是常驻进程** | `alembic>=1.19,<1.20`、`psycopg[binary]`（传递带入 SQLAlchemy、Mako、MarkupSafe、greenlet、typing-extensions） | 迁移要 DDL 权限而业务进程不要；且 `src/` 不得出现迁移工具链，挂进任何进程组都是假声明。驱动必须自己声明——alembic 不依赖任何驱动，驱动由 URL scheme 决定（Issue #53） |

  `admin` 进程待建立（第一节）。`gateway` 已于 #57 落地，长连接与发消息的依赖已从 `bot-test` 组提升成自己的组，不再挂在测试资产名下；`bot-test` 保留同名依赖是因为那套受控资产在 [#67](https://github.com/Moshuiwang/lingxi/issues/67) 交付前整体保留（第五节）。

- **`src/lingxi/` 里没有任何模块级第三方 import，全部是函数内延迟导入。** 因此「模块 import 成功」证明不了依赖装上了——一个空环境也能 import 成功。extras 的正确性由 `Epic Full / extras` 矩阵把守：每组一个干净虚拟环境，跑 `scripts/ci/check_installed_package.py --process <extra>` 显式导入该进程的第三方依赖。装在同一个环境里累加是无效的——窄的那组会白用别组带进来的包，检查就永远不会红。

  新增 extra 必须同时加进该矩阵与脚本的 `PROCESS_RUNTIME_IMPORTS`。**这条不靠自觉**：脚本做的是**三方对账**——已安装制品的 `Provides-Extra`、脚本的 `PROCESS_RUNTIME_IMPORTS`、`ci.yml` 的 `extra: [...]` 矩阵行，任意两边对不上都直接失败，且这条对账在 gate 的无参调用路径上就会跑。所以「新增一组却没人检查它」「加了声明却漏加矩阵行」都会在 gate 变红。刻意不进矩阵的组写进脚本的 `MATRIX_EXEMPT_EXTRAS` 并注明理由（目前为空）。

  > 只对账「pyproject ↔ 脚本」这半边是不够的：独立复查实测过，把新组加进 pyproject 和 `PROCESS_RUNTIME_IMPORTS`、唯独漏掉矩阵行，CI 从没在干净环境里装过它而 gate 全绿。矩阵那半边补于同一 Issue，用例见 `tests/test_ci_extras_matrix.py`。
- 外部 SDK 锁精确版本或窄区间；纯库依赖用兼容区间。升级依赖单独成提交，说明重跑了哪些验证。
- **迁移的权威来源是 Alembic 的 revision 链**（Issue #53 落地）。约定以[数据库设计「十一、迁移约定」](数据库设计.md#十一迁移约定)为准：每个迁移可前滚、破坏性变更拆两次发布、不在迁移里写业务数据。文件位置与执行方式：

  | 项 | 事实 |
  | --- | --- |
  | 配置 | 仓库根目录 `alembic.ini`（**不含默认连接串**，已加进 `ci.yml` 的 `paths:` 触发列表） |
  | revision | `migrations/alembic/versions/`，基线兼 head 为 `20260806_baseline` |
  | 连接串 | 环境变量 `LINGXI_MIGRATION_DSN`，缺失即失败，不回落到业务的 `LINGXI_POSTGRES_DSN` |
  | 依赖 | `migrate` extra（见上表），由 gate 的 `pip install '.[scheduler,migrate]'` 实际装上 |
  | 门禁 | `scripts/ci/check_alembic_revisions.py`（无需数据库）+ `scripts/ci/check_migration_chain.sh`（真库两条链对比） |
  | 进部署制品 | 镜像构建 `COPY` `migrations/` 与 `alembic.ini`，由 [#62](https://github.com/Moshuiwang/lingxi/issues/62) 落地；在那之前没有自动化部署路径 |

  顶层 `migrations/*.sql`（`006`–`012`）**是生产链的历史正文，不是测试资产**（本行此前的说法与第一节的布局表相互矛盾，2026-08-06 更正）：旧库正是按它们建成的。它们现已**冻结**——不再新增，但过渡期保留，因为旧库接管要用它们补齐到 `012`，且门禁拿它们建出的库作为 alembic 基线的等价性基准。退休条件写在 `migrations/README.md`。`migrations/testing/` 才是测试资产，按第五节的替代关系处理。

  基线 revision 是那六个文件的**逐字节副本**而非等价重写：PostgreSQL 的匿名约束名与索引名由声明顺序决定，重写会让两条血统拿到结构相同但名字不同的库，而这种分歧要到某次按名字 `DROP CONSTRAINT` 的迁移才暴露。

- **迁移工具链不进运行时。** `src/lingxi/` 里不得出现 `sqlalchemy` 或 `alembic` 字样（`check_alembic_revisions.py` 每次门禁扫描），生产进程镜像因此不装 SQLAlchemy。迁移是部署时跑一次的作业，不是常驻进程——`migrate` extra 的 `PROCESS_RUNTIME_IMPORTS` 条目里 lingxi 模块那一列刻意为空。

## 七、门禁入口

- 本机与 CI 的唯一门禁入口是 `scripts/ci/verify_repository.sh`（Bash 语法、ShellCheck、Markdown 链接、项目 Skill 核对、验收矩阵、内容目录版本纪律、alembic revision 链、Python 测试、真库测试与迁移链、行尾空白）。新增检查加进该脚本，不另起入口，保持本机与 CI 同构（验证与门禁第十一节）。`scripts/dev/check.sh`（Issue #236）架在它之上：一键建出与门禁逐位一致的依赖环境（extras、shellcheck、Python 版本现读自 `ci.yml` / `story.yml`，见 `scripts/dev/gate_spec.py`，不另写一份清单），并按 `scripts/dev/local_layer.py`（直接复用 `classify_story_changes.classify`）分层调用 `verify_docs.sh` / `verify_repository.sh`，不改变后者完整模式的语义。
- 缺依赖时应报告「哪几项被跳过」而不是整体失败——该改进已在验证与门禁第十一节登记，落地时更新本节。

### 内容目录的版本纪律

改动 `src/lingxi/config/content.toml` 里任何**用户可见文案**（`[texts]` 与 `[cards]` 下的文本），必须在同一个提交里做三件事：递增 `[meta] version` 到一个从未用过的新标识（惯例是当天日期）、运行 `python3 scripts/ci/check_content_version.py --refresh` 刷新 `content.lock.toml`、把两个文件一起提交。`check_content_version.py` 会在门禁里比对文案摘要与登记的 (version, digest)，对不上就红；`--refresh` 在版本没递增时**拒绝写入**，不能用来代替递增。只调整排版、注释或键顺序不需要递增。

这条纪律的理由：`version` 随投递与审计事件落库，是「用户当时看到的是哪一版文案」的唯一追溯依据，不被强制就会退化成不可信信号（[决策记录 2026-08-17](../决策记录/2026-08-17-content-toml-版本纪律.md)）。
