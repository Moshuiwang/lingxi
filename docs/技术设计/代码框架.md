## 一、仓库布局

## 二、三层之间的 import 规则

架构设计的「模块化单体」靠这三条规则成立，违反任何一条都是审查阻塞项：

1. **`core/` 不 import `adapters/`、`apps/`、任何外部 SDK，也不做网络或文件 I/O。** 领域规则必须能在纯单测里被完整证伪。需要外部数据时，由调用方把数据作为参数传进来（参考 `core/identity/onboarding.py` 的现有写法，及接口设计[「八、领域服务接口」](接口设计.md#八领域服务接口)的函数形态）。
2. **`adapters/` 是外部 SDK 与协议细节的唯一落点。** 每个外部系统一个模块；SDK 类型不得泄漏进 `core/` 的函数签名。PR #36 的 `claude_agent_hooks.py`（约 30 行、唯一 import Agent SDK 的文件）是这一层的样板。
3. **`apps/` 只做组装。** 读配置、建连接、把 adapters 注入 core、处理信号与退出；不写业务规则。每个进程一个子包，以 `python -m lingxi.apps.<name>` 启动，对应 Docker Compose 的一个服务。

跨模块调用只走接口设计「八、领域服务接口」列出的函数；模块不读其他模块的表。写路径上 `enqueue_publish`、`audit.record` 必须接收调用方事务对象，由类型签名强制「审计与状态变更同事务」。

边界目前由测试与代码审查把守；如出现违反案例，再把 import 检查加进 CI，不预建工具。

## 三、横切约定

- **标识、时间、错误信封、幂等、trace_id**：一律遵循接口设计[「二、通用约定」](接口设计.md#二通用约定)，不在各模块自造。ULID 生成、错误信封类型、`redact()` 脱敏出口放在 `core/` 的公共小模块中，全仓库只有一份。
- **配置**：全部来自环境变量，统一 `LINGXI_` 前缀，在 `apps/` 入口一次性读取并构造成类型化配置对象传下去；`core/`、`adapters/` 不直接读 `os.environ`。不硬编码主机、端口、路径、密钥（断言 V-部署-01）。`.env` 只用于本地与受控测试，已在 `.gitignore`。
- **凭据**：不进代码、日志、数据库、用户环境（产品合同明令）。长期凭据放操作系统级密钥管理；测试只用固定假凭据探针。
- **日志**：结构化输出到 stdout / stderr，带 `trace_id`，不写日志文件、不自行轮转（断言 V-部署-04）。
- **进程生命周期**：收到 `SIGTERM` 后停止领取新任务、完成或安全中断在途任务、超时内退出（断言 V-部署-03）；除用户环境目录外不在容器内写持久化本地状态（断言 V-部署-02）。
- **注释与文档字符串**：中文，说明「为什么」与边界约束，不复述代码行为；对外承诺一律链接产品合同或技术设计，不复制条文。

## 四、测试约定

- 测试框架为标准库 `unittest`，`PYTHONPATH=src python3 -m unittest discover -s tests` 必须可在无外部依赖的机器上运行；这与 CI 的执行方式一致（见 `scripts/ci/verify_repository.sh`）。
- 真实 PostgreSQL 测试通过 `LINGXI_POSTGRES_DSN` / `LINGXI_POSTGRES_CONTAINER` 环境变量启用，缺省时明确跳过并输出原因，不静默通过；数据库约束类断言（唯一索引、条件更新、触发器）必须在真库上验证，不用 mock（验证与门禁第五节）。
- 每个实现切片认领[验证与门禁](验证与门禁.md#七关键机制验收矩阵)中的断言编号，测试名或注释引用该编号；合同「不得 / 不允许」类规则必须有对应否定测试（第八节）。
- 涉及真实外部系统的行为不在 CI 里 mock 成证据；留给 `biai-stage` 的 L4a 受控链路。

## 五、测试资产与正式代码的边界

仓库中已有一批 **Bot-Test 测试资产**：`core/identity/onboarding.py`、`adapters/`（`oauth_bridge.py`、`feishu_onboarding.py`、`refresh_tokens.py`、`postgres_onboarding.py`）、`migrations/001–003`、`workers/oauth-bridge/`、`scripts/probe_*.py` 与 `experiments/`。它们支撑了关联组织受控验证，**不是正式员工路径，也不是生产入口**（[当前能力](../当前能力.md)已声明）。

处理规则：

- 文件头必须保留「测试资产 / 不属于正式用户路径」的声明；新增测试资产同样如此。
- 正式实现进入同名领域时，先在对应 Issue 写明替代关系：吸收、改写或废弃哪些测试资产文件，不允许两套同职责代码长期并存。
- **OAuth 桥接一组测试资产在 [#67](https://github.com/Moshuiwang/lingxi/issues/67) 交付前整体保留**（2026-08-06 登记，依据[#55 盘点](https://github.com/Moshuiwang/lingxi/issues/55#issuecomment-5201705742)）：`core/identity/onboarding.py`、`adapters/`（`oauth_bridge.py`、`feishu_onboarding.py`、`postgres_onboarding.py`、`refresh_tokens.py`）、`workers/oauth-bridge/`、`migrations/testing/001–003` 与对应测试，是「四达文档会议助手」轮换失败后重新授权的唯一实现；卡片 `card_nonce` 即 OAuth `state`，无法只保留其中一部分。替代物为 #67 的正式重授权入口，交付后按上一条整体清退。
- 测试资产中已被受控验证过的模式（如加密轮换 `refresh_token`、`open_id` 定位共享范围成员）是正式实现的参考输入，但正式代码按产品合同与技术设计重写，不直接把测试资产改名上线。
- 已知的架构偏差在正式化时必须纠正：现有 `refresh_tokens.py` 的续期扫描线程挂在长连接进程内，正式实现按架构设计归入 `lingxi-scheduler`（[Issue #16 的复验记录](https://github.com/Moshuiwang/lingxi/issues/16#issuecomment-5188063325)）。

## 六、依赖与迁移

- 依赖声明只在 `pyproject.toml`，**按进程拆 optional extras**，组名与 `python -m lingxi.apps.<name>` 及 Docker Compose 的服务对齐，使镜像只装该进程真正用到的依赖（Issue #56）。CI 与 `biai-stage` 用 `pip install '.[extra]'` 安装同一声明；仓库不使用 uv 锁文件。现有分组：

  | extra | 对应进程 / 用途 | 内容 | 依据 |
  | --- | --- | --- | --- |
  | `scheduler` | `python -m lingxi.apps.scheduler`（专用授权凭据续期扫描） | `cryptography`、`psycopg[binary]` | 入口 → `adapters/delegated_credentials.py`；同链上的 `adapters/feishu_directory.py` 只用标准库 `urllib` |
  | `worker` | `python -m lingxi.apps.worker`（最薄受控执行器） | `claude-agent-sdk==0.2.128` | 入口 → `adapters/claude_agent_hooks.py`、`adapters/claude_agent_session.py`。版本变化需重跑门禁验证，见验证与门禁 10.0 |
  | `bot-test` | 第五节的 Bot-Test 受控验证资产（含常驻长连接 `adapters/feishu_onboarding.run_long_connection_bot` 与 `scripts/` 受控脚本），**不进生产镜像** | `cryptography`、`lark-oapi`、`psycopg[binary]`、`websockets` | `lark-oapi` 只被 `adapters/feishu_onboarding.py` 用，`websockets` 只被 `adapters/oauth_bridge.py` 用 |
  | `migrate` | 部署时跑一次的**迁移作业**（`python -m alembic upgrade head`），**不是常驻进程** | `alembic>=1.19,<1.20`、`psycopg[binary]`（传递带入 SQLAlchemy、Mako、MarkupSafe、greenlet、typing-extensions） | 迁移要 DDL 权限而业务进程不要；且 `src/` 不得出现迁移工具链，挂进任何进程组都是假声明。驱动必须自己声明——alembic 不依赖任何驱动，驱动由 URL scheme 决定（Issue #53） |

  `gateway` 与 `admin` 进程待建立（第一节）；它们落地时从 `bot-test` 组把长连接与发消息的依赖提升成自己的组，而不是继续挂在测试资产名下。

- **`src/lingxi/` 里没有任何模块级第三方 import，全部是函数内延迟导入。** 因此「模块 import 成功」证明不了依赖装上了——一个空环境也能 import 成功。extras 的正确性由 `CI / extras` 矩阵把守：每组一个干净虚拟环境，跑 `scripts/ci/check_installed_package.py --process <extra>` 显式导入该进程的第三方依赖。装在同一个环境里累加是无效的——窄的那组会白用别组带进来的包，检查就永远不会红。

  新增 extra 必须同时加进该矩阵与脚本的 `PROCESS_RUNTIME_IMPORTS`。**这条不靠自觉**：脚本做的是**三方对账**——已安装制品的 `Provides-Extra`、脚本的 `PROCESS_RUNTIME_IMPORTS`、`ci.yml` 的 `extra: [...]` 矩阵行，任意两边对不上都直接失败，且这条对账在 gate 的无参调用路径上就会跑。所以「新增一组却没人检查它」「加了声明却漏加矩阵行」都会在 gate 变红。刻意不进矩阵的组写进脚本的 `MATRIX_EXEMPT_EXTRAS` 并注明理由（目前为空）。

  > 只对账「pyproject ↔ 脚本」这半边是不够的：独立复查实测过，把新组加进 pyproject 和 `PROCESS_RUNTIME_IMPORTS`、唯独漏掉矩阵行，CI 从没在干净环境里装过它而 gate 全绿。矩阵那半边补于同一 Issue，用例见 `tests/test_ci_extras_matrix.py`。
- 外部 SDK 锁精确版本或窄区间；纯库依赖用兼容区间。升级依赖单独成提交，说明重跑了哪些验证。
- **迁移的权威来源是 Alembic 的 revision 链**（Issue #53 落地）。约定以[数据库设计「十一、迁移约定」](数据库设计.md#十一迁移约定)为准：每个迁移可前滚、破坏性变更拆两次发布、不在迁移里写业务数据。文件位置与执行方式：

  | 项 | 事实 |
  | --- | --- |
  | 配置 | 仓库根目录 `alembic.ini`（**不含默认连接串**，已加进 `ci.yml` 的 `paths:` 触发列表） |
  | revision | `migrations/alembic/versions/`，基线兼 head 为 `20260806_baseline` |
  | 连接串 | 环境变量 `LINGXI_MIGRATION_DSN`，缺失即失败，不回落到业务的 `LINGXI_POSTGRES_DSN` |
  | 依赖 | `migrate` extra（见上表），由 gate 的 `pip install '.[scheduler,migrate]'` 实际装上 |
  | 门禁 | `scripts/ci/check_alembic_revisions.py`（无需数据库）+ `scripts/ci/check_migration_chain.sh`（真库两条链对比） |
  | 进部署制品 | 镜像构建 `COPY` `migrations/` 与 `alembic.ini`，由 [#62](https://github.com/Moshuiwang/lingxi/issues/62) 落地；在那之前没有自动化部署路径 |

  顶层 `migrations/*.sql`（`006`–`012`）**是生产链的历史正文，不是测试资产**（本行此前的说法与第一节的布局表相互矛盾，2026-08-06 更正）：旧库正是按它们建成的。它们现已**冻结**——不再新增，但过渡期保留，因为旧库接管要用它们补齐到 `012`，且门禁拿它们建出的库作为 alembic 基线的等价性基准。退休条件写在 `migrations/README.md`。`migrations/testing/` 才是测试资产，按第五节的替代关系处理。

  基线 revision 是那六个文件的**逐字节副本**而非等价重写：PostgreSQL 的匿名约束名与索引名由声明顺序决定，重写会让两条血统拿到结构相同但名字不同的库，而这种分歧要到某次按名字 `DROP CONSTRAINT` 的迁移才暴露。

- **迁移工具链不进运行时。** `src/lingxi/` 里不得出现 `sqlalchemy` 或 `alembic` 字样（`check_alembic_revisions.py` 每次门禁扫描），生产进程镜像因此不装 SQLAlchemy。迁移是部署时跑一次的作业，不是常驻进程——`migrate` extra 的 `PROCESS_RUNTIME_IMPORTS` 条目里 lingxi 模块那一列刻意为空。

## 七、门禁入口

- 本机与 CI 的唯一门禁入口是 `scripts/ci/verify_repository.sh`（Bash 语法、ShellCheck、Markdown 链接、项目 Skill 核对、验收矩阵、alembic revision 链、Python 测试、真库测试与迁移链、行尾空白）。新增检查加进该脚本，不另起入口，保持本机与 CI 同构（验证与门禁第十一节；`scripts/dev/check.sh` 容器化同构入口是该节已登记的待实施项）。
- 缺依赖时应报告「哪几项被跳过」而不是整体失败——该改进已在验证与门禁第十一节登记，落地时更新本节。
