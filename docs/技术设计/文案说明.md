# 用户可见文案：怎么改、怎么校验、怎么回滚

> 状态：现行。最后整理：2026-09-05（[Issue #585](https://github.com/Moshuiwang/lingxi/issues/585)）。
>
> 本文回答「要改用户看到的一句话，具体怎么做」。文案的**内容**权威仍在 `src/lingxi/config/content.toml`；版本纪律见[决策记录 2026-08-17](../决策记录/2026-08-17-content-toml-版本纪律.md)与[代码框架](代码框架.md)的「内容目录的版本纪律」；部署侧的变量与挂载登记在 [deploy/验收前部署配置清单.md](../../deploy/验收前部署配置清单.md)。

## 一、两条路径，先选一条

| | 改镜像内文案 | 改宿主机覆盖文件 |
| --- | --- | --- |
| 做什么 | 改 `src/lingxi/config/content.toml`，递增 `[meta] version`，刷新 `content.lock.toml` | 编辑宿主机上一个 TOML 文件 |
| 代价 | 走完整发布链：审核 → 门禁 → 合主干 → 构建镜像 → 预发验证 → 生产升级 | 编辑文件 + 重启三个容器 |
| 能改什么 | 全部：新增键、改占位符、改卡片、改错误码 | **只有已登记 `[texts]` 键的正文** |
| 追溯 | `content_version`（落审计与投递事件） | `content_digest`（启动日志与 `worker.task.terminal`） |
| 什么时候用 | 新增文案键、改占位符、改卡片结构、法务口径定稿 | 真机看过之后的措辞微调 |

**默认走第一条**。覆盖文件是为「已经上线、只想把一句话说得更顺」准备的，不是长期的文案存放处——镜像内那份始终是唯一的键与占位符权威。

## 二、改一句话（覆盖文件路径）

### 1. 找到键名

键名在 `src/lingxi/config/content.toml` 的 `[texts]` 段里，与用户看到的句子一一对应。例如首次开通完成那句是 `onboarding.completed`。

### 2. 写覆盖文件

只有一个 `[texts]` 表，只放要改的那几个键：

```toml
[texts]
"onboarding.completed" = "已经给你开通好了。当前可用范围：公司：{company_name}；职能：{function_name}。"
```

硬规则，违反任何一条整份文件被忽略：

- **不能新增键**：键必须已在镜像内登记。
- **占位符集合必须与镜像内同键完全相等**。上例里 `{company_name}` 与 `{function_name}` 一个都不能少、也不能多——少一个会让这句话渲染必然失败，而失败发生时一次性状态可能已经被消耗掉。
- **不能有 `[meta]`、`[cards]` 或任何别的顶层表**。版本号、卡片结构、键集合不可外置。
- **不能命中内容安全校验**：内部过程标识（`trace_id`、`mcp__`、`PreToolUse` 一类）、以及「权限不足」「预计剩余」「还需」这类会误导权限状态或承诺等待时间的固定表达。

### 3. 校验（放上宿主机之前）

```
python -m lingxi.config.content_check /path/to/content.override.toml
```

退出码 `0` 才算通过，并列出会被覆盖的键；非 `0` 会打出原因码与人话说明（不打印文件正文）。**这条命令与线上进程用的是同一段判据代码**，因此不存在「这里过了、线上被拒」。

### 4. 放到宿主机并重启

文件放 `/opt/lingxi/runtime-config/content.override.toml`（该目录已只读挂进三个常驻容器的 `/etc/lingxi/runtime`）。三份 env 文件（scheduler / gateway / worker-queue）**一起**配上同一个值：

```
LINGXI_CONTENT_OVERRIDE_PATH=/etc/lingxi/runtime/content.override.toml
```

只配其中一部分，等于让同一句话在不同路径上有两个版本。生效方式分两种情况（2026-09-05 stage 实测，Trace #606 T-4）：

- **第一次配上这个变量**：必须用 `up -d` 重建三个容器——`restart` 不会重新读取 env 文件，变量对容器不可见。
- **变量已经在、只改了覆盖文件**：用 `restart`——compose 配置没变时 `up -d` 判 up-to-date 不会重启，文件改动不会被读到。

```
# 首次加变量
docker compose --env-file deploy/.env.<环境> -f deploy/compose.yaml -f deploy/compose.<环境>.yaml \
  --profile mvp up -d
# 之后只改文件
docker compose --env-file deploy/.env.<环境> -f deploy/compose.yaml -f deploy/compose.<环境>.yaml \
  restart scheduler gateway worker-queue
```

去掉变量同理走 `up -d`；删文件不去变量走 `restart`，进程按「缺文件＝零变化」退回镜像内文案。

### 5. 确认这一版真的被读到了

每个进程启动时记一行：

```
<进程名> 内容目录 version=… digest=… override_path=… override_keys=… rejected=…
```

`digest` 是镜像内文案与覆盖文件合成的 `sha256` 前 12 位，`override_keys` 是本次被覆盖的键数，`rejected` 为空才算生效。`worker-queue` 每轮终态审计事件 `worker.task.terminal` 也带同一个 `content_digest`——用户反馈「这句话不对」时，靠它把用户当时看到的那一版定位到具体文件内容。

> `[meta] version` **不受覆盖文件影响**。它描述的是镜像内那一份，`content_version` 因此回答不了「用户看到的是哪一版」——那个问题只能看 `content_digest`。

## 三、改坏了会怎样

坏文件**整份忽略**，用户看到的仍是随镜像发布的那一版文案，进程照常运行（fail-safe，不是失败关闭：文案不是安全边界，一份写坏的运维文件不该把服务拖停）。四类判据：

| 原因码 | 含义 |
| --- | --- |
| `invalid_toml` | 不是合法 UTF-8 TOML |
| `unknown_section` / `unknown_key` | 有 `[texts]` 之外的顶层表，或键没在镜像内登记 |
| `placeholder_mismatch` | 占位符集合与镜像内同键不一致 |
| `unsafe_text` | 命中内容安全校验 |

发生时：每个进程一条结构化错误日志（`lingxi.config.content_override`，只有 `path` 与 `reason`，**正文不进日志**），`scheduler` 另发**一条**管理群告警（去重键含原因码与文件摘要，反复重启同一份坏文件不会刷屏）。

**文件不存在或变量未配不是故障**，不告警——删文件正是回滚手段。

## 四、回滚

任选一种，然后重启那三个服务：

- 删掉宿主机上的覆盖文件；
- 或删掉三份 env 里的 `LINGXI_CONTENT_OVERRIDE_PATH`。

两种都回到随镜像发布的文案，逐字相同。想回到上一版覆盖文件，就把那一版文件放回去——`digest` 可用来核对放回去的确实是想要的那一版。

## 五、边界

- **只覆盖正文**。键集合、占位符集合、`[meta] version`、`[cards]` 都不可外置。要动这些就走镜像内路径。
- **生效需要重启**，不是编辑即生效。这与 worker 的系统提示词文件（每任务现读）不同，与闸①指标映射表（启动时一次装配）相同：`core` 侧存在模块级就持有内容目录的消费点，热重载会让同一进程内两条路径读到同一句话的两个版本。
- **不覆盖管理员命令面与日报文案**——它们本来就不经 `content.toml`。
- **不改变内容目录与提示词的整体发布模型**（rc25 决策 D-9「否」仍然有效）；本机制只解决用户可见文案这一面。
