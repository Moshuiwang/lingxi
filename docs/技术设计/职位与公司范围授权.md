# 职位与公司范围本地补充授权

> 状态：#493 实现设计，L2 单测与迁移检查；不构成 stage/L4a 能力声明。最后核对：2026-08-31。
> 合同依据：[产品合同与外部边界](../产品合同与外部边界.md)「本地权限覆盖」与「管理员处理入口与安全确认」。

## 语义到权限行的展开

管理卡只收集两个产品字段：银河职位（`position_name`）和公司范围
（`company_scope`）。`src/lingxi/core/permission/position_override.py` 的纯函数
`expand_position_scope()` 按两份随包配置完成确定性展开：

1. 职位必须精确命中 `config/galaxy_role_function_map.toml` 的角色名；不做前缀、同义词或模糊匹配。
2. 职能再按 `config/company_function_metric_map.toml` 的公司×职能键转换为指标列表。
3. 单个公司只产生该公司的指标行；“全部”值为 `*`，公司数量由当前实际公司键计算，不硬编码或静默丢弃缺项。
4. 任一职位、公司或公司×职能映射缺失都失败关闭；成功结果中的 `pairs` 在待确认操作准备时冻结，确认时不重新解释配置。

确认事务仍写既有 `local_permission_override` 的公司×指标行。新增的
`position_name`、`company_scope` 和 `permission_group_id` 是展示与撤销语义的一部分：
同一次职位范围授权产生的多行共享同一个组 ID，管理卡将其聚合为一个职位+范围项，
一次撤销事务性翻转全组；旧逐指标历史行保持 `NULL`，继续逐行撤销，不迁移、不改写。

## 「2.0 迁移导入·全部」组（rc25 S-1，Issue #540）

存量用户首次开通时（`core/identity/onboarding_runner.py` 在零银河判定之前调用
`core/identity/legacy_permission_import.py` → `core/permission/legacy_diff.py`），旧表
`{"*":["*"]}` 或 `{"*":[显式列表]}` 的行落成一组 `company_id="*"` × 指标的本地授权：
`company_scope="*"`、共享同一 `lpg_` 组 ID，`pending_action` 是合成的已终态记录
（`reason='legacy_import_2_0'`、`card_delivered=FALSE`）。两种形状用两个标签：
`{"*":["*"]}` → `position_name`「2.0 迁移导入·全部」（语义＝全部指标）；
`{"*":[显式列表]}` → 「2.0 迁移导入·全部公司（指定指标）」（语义＝就这几个指标）。
与职位组的差异：

1. 展开的是**指标维**不是公司维——公司保留 `*`（问数 MCP 读侧按 `*` 回退），指标取
   `{"*":["*"]}` 时的映射全部指标并集、或旧行列出的指标；映射外公司的具体行照导入、无组。
2. **只有「2.0 迁移导入·全部」组不冻结**：每日重算与定向重算前按当前映射补齐组里缺的指标
   （同组 ID、同标签，`pending_action.reason='legacy_all_scope_refresh'`），只加不减；管理员
   单独撤销过的指标不复活，撤销过的组不参与。「指定指标」组永不自动扩指标。用户重新开通时
   沿用既有生效组（含其标签）；整组撤销过且当前无生效组则不重建。
3. 合并层对本地 `*` 组取精确形状（`merge_sources.py` 「本地 `"*"` 组」一节）：`*` 键＝组
   本身，银河/本地对某公司有值时产出具体键＝`*` ∪ 该公司值 − 该公司抑制；减到空不可表示 →
   全部写发布行调用点一律 fail-closed。要完全屏蔽该用户的某一家公司，先整组撤销再逐笔
   授权/抑制。

管理卡把这组渲染为一项「职位 2.0 迁移导入·全部（或 …全部公司（指定指标）） · 公司范围
全部（N 家公司）」，撤销按钮带组 ID，整组事务性翻转，与职位组同一条撤销路径。

### 入口卫生：值严格、公司键不查目录（rc25 S-2d，报告 P-2）

导入的**键**与**值**受两套不同的判据约束，这是刻意的不对称，不是遗漏：

- **卫生（形状）判据键值一样严**（`legacy_diff._malformed`）：非字符串、纯空白、Unicode
  `Cc`/`Cf`/`Cs`/`Co`/`Zl`/`Zp` 类别（换行、回车、制表、零宽空格、双向覆盖、代理与私用区）、
  普通空格以外的空白（如 NBSP）、以及 `*` 混进名字里而不是整体恰为 `*`（`日活*`、`1011*`），
  **任一命中即整份拒绝**，不是跳过那一条。恰为 `*` 的键与值仍是结构记号，`{"*":["*"]}` 与
  `{"*":[显式列表]}` 两种合法形状不受影响。**刻意放行**名字首尾或中间的普通空格（`" 日 活 "`）：
  它匹配不上映射里的任何指标，方向是给得更少而不是给错范围，而真实旧表导出里这类脏数据常见，
  为它整份拒绝只会平白挡住硬切。
- **目录（内容）判据只对值有要求**：**公司键一概不查目录**，映射外公司（40–43）照导入。
  理由是两者决定的东西不同——**值决定给多大范围**（读侧对 `*` 有回退制，一个 `"*"` 值等于
  「该公司全部指标，含未来新增」，而此后针对单个指标的抑制按「公司 + 指标」精确匹配，
  减不掉一个 `"*"`），**公司键只决定给哪一家公司**（写错一个公司号导入的是一条谁也用不上的
  死行）。顺手把键一起收紧既推翻已裁定的产品口径，又挡不住值这条真正的放权路径。

**同一套值卫生判据目前有两份实现，登记为技术债（rc25 S-3a P-5，本批不改代码）**：
`core/permission/legacy_diff._malformed`（差集导入侧）与
`core/permission/metric_translation._malformed_metric_name`（外置指标映射文件侧）
逐条对齐同一口径——**值严格、公司键不查目录**——但各写一份。之所以没有在本批合并：
两个文件分属同批不同 Story 的改动面，跨面合并会让两个 Story 抢同一个文件。
风险是**口径漂移**：将来只改一处，两条入口就会对同一份脏数据给出不同结论。
要合并时，先确认两侧的"公司键"语义确实相同（映射文件的键是公司，导入侧的键也是公司），
再把判据提到一个共同的模块里，并保留两侧各自的用例。

两条入口共用同一个 `classify_legacy_permissions`：首聊自动导入命中 `ValueError` →
`legacy_permissions_unparseable` → 开通链失败关闭、外部表零写入；受控导入脚本
（`scripts/ops/import_local_permission_override.py`）命中同一判据 → 退出码 2、零写入。
口径结构上不可能分叉。**用户可见的行为变化**：旧行指标名里含换行/零宽/NBSP、或含 `*` 但不
恰为 `*` 的存量用户，现在首聊会 fail-closed（`LX-ONBOARD-001` + 管理群通知），而此前是静默
导入一条匹配不上任何映射的死行。方向更保守，但对尚未首聊的存量用户是一次可见变化；生产那
批存量用户的旧行里**是否真有这类字符：未知**（尚未回源），硬切前建议先用 `--dry-run` 扫一遍。

## 「预开通预授权」组（rc25 S-8b，Issue #541）

管理员按名单预开通时（规则见[产品合同与外部边界](../产品合同与外部边界.md)「管理员预开通」），
名单里的「职位＋公司范围」经**同一个** `expand_position_scope()` 展开——与管理卡那条路径
逐字同构，没有第二套解析或校验——再冻结成一份预授权计划，随开通链落到
`adapters/postgres_local_permission.py::import_position_grant`。与上一节「2.0 迁移导入·全部」
组的差异只在来源与标记，不在机制：

1. **展开的是公司维**（和管理卡的职位组一样，不是指标维）：`position_name` 就是名单上那个
   真实银河职位名、`company_scope` 就是名单给的范围，不用合成标签。管理卡上显示的
   `local_permission_override.reason` 是「预开通预授权」。
2. **合成的 `pending_action` 用独立原因** `reason='preprovision_2_0'`（与差集导入的
   `legacy_import_2_0` 分开，否则审计上分不出「这批授权是哪条路径产生的」），
   `status='executed'`、`card_delivered=FALSE` 如实反映从未发过卡片，
   `initiated_by_open_id`/`decided_by_open_id` 取脚本的 `--initiated-by`，**不写死占位身份**。
3. **一笔的全部行共享一个新 `lpg_` 组 ID**，因此管理卡把它渲染成**一个**「职位＋公司范围」项、
   一次事务性整组撤销——「名单给错了要撤」要撤的正是这个单位。
4. **幂等与既有纪律一致**：每用户一事务、先锁 `app_user` 行；已生效的键计 `already_present`，
   **管理员撤销过的键不复活**；一行都没新增时删掉刚合成的 `pending_action`，不留孤儿终态记录。
5. **落库口不与差集导入合并成一个带开关的方法**：两者输入不同（旧表内容 vs 产品负责人核对过的
   名单）、审计原因不同，必须分得开；共用的是合成 `pending_action` 与 SAVEPOINT 包住的逐行插入
   两个模块级函数——它们才是「没有确认卡就不能写入」这条约束的落点。

**证据边界如实**：以上只有 L2（含用假游标对 INSERT 参数的直接断言）。**真库行为（外键、部分
唯一索引、SAVEPOINT 降级）未跑真库，stage 名单驱动演练一步没做**，撤销演练同样没做——
「名单给错了能不能撤」目前只有代码与单测，没有演练证据。

## 管理卡上下文与回调

`management_card_context`（迁移 `0081_management_card_context`，视觉恢复水位由
`0083_management_card_recovery` 追加，状态代数 CAS 由 `0084_management_card_state_cas`
追加）持久保存
`message_id`、`card_id`、目标标识、会话、发起人、快照指纹、上下文截止时间、状态和
整卡 `card_sequence`；独立的 `state_version` 表示业务状态代数。`pending_action.origin_card_message_id` 反向链接原管理卡，
因此确认卡、取消和后台重算可以在重启后找到同一张管理卡。首次建卡/回复后的序号基线
由发送编排保存；每次原地更新通过持久层原子递增取号，禁止调用方硬编码或倒退。

数据库状态与 CardKit 视觉状态通过 `needs_refresh`、`visual_sequence` 持久水位分离；
恢复 scanner 领取序号和清除水位时同时校验所读的 `state_version` 与 `card_sequence`，
状态推进后旧视觉放弃发送并保留水位。
状态写入后由 gateway 启动扫描一次、随后在长连接心跳中周期扫描；只有 CardKit 更新
成功才推进视觉水位，瞬时失败或 gateway 在 60 秒观察窗口内重启会在下一轮幂等重试。
这条恢复路径不创建第二张卡，也不把失败的外部调用当作已交付。

管理卡回调只在点击时做惰性检查：重新读取目标状态，比较快照指纹，并核对持久上下文
中的发起人和目标标识。上下文到期、状态读取失败、发起人不符、标识被篡改或状态已变化
都不得构造写命令；可用时原卡更新为不可操作并提示重新查询。内存兼容映射默认保留
40 分钟，持久上下文同样受严格 24 小时硬上限；内部保留窗口不是用户可见的授权期限。

成功的表单提交只建立待确认操作，并把原管理卡更新为“已提交，请在下方确认卡片上确认
（10 分钟内有效）”；“取消”按钮只关闭管理卡，不写权限。确认事务成功后的即时文案是
“操作已记录，权限正在下发”，后台重算完成后才更新为“已生效”；无法完成时展示未完成
和次日修正提示。任何重复回调沿用待确认操作和卡片 sequence 的幂等约束。

## 代码边界

- `core` 只依赖 Protocol 与纯展开/渲染逻辑；TOML、PostgreSQL、CardKit 分别留在 `adapters`。
- `TomlCompanyMetricCatalog.positions()` 只返回角色映射文件中的精确键；生产管理卡仅提供职位、公司范围、原因三个必填字段和关闭按钮，不提供本地屏蔽表单。
- 旧目录假实现仍可渲染历史卡形状以保持反序列化/单测兼容；生产装配始终使用带 `positions()` 的新目录。
- 确认/发布失败保持失败关闭并记录审计；原卡刷新只重试已落库的展示状态，不反写或推断权限状态。
