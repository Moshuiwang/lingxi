## 一、设计原则

1. **合同里的硬约束尽量落到数据库约束上。** "同一话题同时只跑一个任务""同一待确认操作最多成功执行一次""同一飞书事件只处理一次"——这些用唯一索引、部分索引和条件更新表达，而不是靠应用代码自觉。约束写在数据库里，任何代理写的任何代码路径都绕不过去。
2. **状态用 `TEXT` + `CHECK` 而非原生 `ENUM`。** 状态机会随实现演进；`CHECK` 的增删是一次普通迁移，`ALTER TYPE ... DROP VALUE` 则做不到。代价是少一点类型强度，换来的是可回滚。
3. **不存凭据。** 飞书短期令牌、数据库认证材料、MCP 令牌明文一律不入库（合同明令）。需要长期持有的外部凭据放操作系统级密钥管理，数据库里只存**是否已配置**这类布尔状态。
4. **面向删除设计保留。** 九十天是一般可识别内容的最长上限，不是统一保存期；飞书问数安全结果正文在取得已验证形态的 `platform_received` 前最长二十四小时，取得后转为随当前飞书会话保留，由会话边界事件（`/new`、会话空闲满两小时到点主动清除、停用感知、权限变化感知）触发清理，不使用固定到期时间（[#163](../决策记录/2026-07-26-问数可信交付与数据保留边界.md) 方案 B；空闲两小时到点主动清除与停用/权限变化感知即清为 2026-08-14 补充决定）。触发器与清理函数必须按内容类别使用适用期限且不得后移；按月分区只用于查询和整分区已经清空后的回收，不决定保留期限。
5. **业务实体不使用外部标识作主键。** 飞书 `open_id` 等属于外部系统，语义可能变化；用户、任务和会话等内部实体统一用 ULID。`inbound_event.feishu_event_id` 是幂等键而非业务实体标识，为保证同一事件在保留窗口内全局唯一，直接作为该表主键。

### 关于表名 `user`

合同要求"建立统一的 `user` 用户表"。`user` 是 PostgreSQL 的保留字（`SELECT user` 返回当前数据库角色），裸用会导致语法错误，加引号则每一处查询都要写 `"user"`。

**取舍：表名用 `app_user`，语义与合同的 `user` 用户表完全一致。** 这是命名层面的适配，不改变"以一条用户记录关联飞书信息、权限信息、Lingxi 信息"这条规则。

### 银河导出的落库副本（`galaxy_*`）

当前接入的是银河后台导出快照这一**临时输入来源**。它以**原始结构**落成一组 `galaxy_` 前缀的表，与上面十六张表的关系是「输入」而不是「权威」：准入与发布仍只看 `app_user` 与 `user_permission_scope`。未来正式银河权限数据库的业务结构预计与当前导出文件相近，但接入方式、刷新方式、字段映射和具体数据库设计尚未确定。

权限导入的主链路必须与来源形式解耦：文件导入只是当前的一种输入适配方式，未来数据库来源可以替换它，不应迫使权限匹配和发布主链路绑定文件格式。当前不为临时文件保留永久摘要墓碑；九十天清理后同一份旧导出可以再次导入，这一行为不作为未来正式数据库接入的规则。

| 表 | 承载什么 |
|---|---|
| `galaxy_import_batch` | 一次导入的批次、状态、来源标注、内容摘要与各表行数 |
| `galaxy_user` | 银河 `user`：`user_id` / `dept_id` / `user_name` / `nick_name` / `email` |
| `galaxy_user_role` | 银河 `user_role`：`user_id` × `role_id`（姓名列落为 `source_user_name`） |
| `galaxy_role_menu` | 银河 `role_menu`：`role_id` × `menu_id` |
| `galaxy_user_datacountry` | 银河 `sys_user_datacountry`：`user_id` × `datacountry_id`（源列大写） |
| `galaxy_country` | 银河 `sys_country`：`country_key`、中英文国名、`boss_company_id` |

DDL 以 `migrations/010`–`012` 为准，本节不复制。三条不可违反的约束写在迁移注释与[验证与门禁](验证与门禁.md#七关键机制验收矩阵)的 `V-银河-01/02/03` 里：一律按 `user_id` 连接、公司范围连接 `country_key` 而非主键 `id`、菜单一律以 `menu_id` 为准。`全非` 哨兵行原样落库，展开为通配是解释层的事。这组表**不引用 `app_user`**，导入不改动身份切片的任何结构。

冻结的历史基线和 `011` 编号 SQL 仍把 `nick_name` 注释为“人工核对辅助信息”，那只是 2026-08-08 产品决定之前的历史文本，不再构成现行规则；当前只能把姓名用于内部诊断，不能据此选择候选或继续开通。冻结基线不原地改写；需要让真实数据库注释同步时，由后续相关实现用前滚 revision 只更新注释并单独验收。

## 三、身份与权限

```sql
CREATE TABLE app_user (
    id                      TEXT PRIMARY KEY,              -- ULID, usr_*

    -- 飞书信息
    feishu_open_id          TEXT UNIQUE,
    feishu_user_id          TEXT,
    feishu_union_id         TEXT,
    display_name            TEXT,                          -- name.default_value；删除完成后清空
    display_name_locale     TEXT,                          -- 来源租户的语言；710 人实测中 11 人姓名纯拉丁，不可假定为中文
    department              TEXT,                          -- 已确认可得：成员详情的 parent_department_ids 有值率 100%
    tenant_key              TEXT,
    employee_no             TEXT,                          -- 工号，来自公司花名册多维表格；匹配银河的主键（2026-08-05 决策）
    email                   TEXT,                          -- 邮箱，来自公司花名册多维表格；匹配银河的辅键
    drive_folder_token      TEXT,                          -- 历史候选字段；#140 前不得写入或作为正式产物路由
    drive_folder_state      TEXT NOT NULL DEFAULT 'none'
        CHECK (drive_folder_state IN ('none','creating','ready','failed')),

    -- 权限信息
    permission_record_id    TEXT,                          -- 匹配到的数据库权限记录
    permission_version      BIGINT NOT NULL DEFAULT 0,     -- 每次权限变更 +1，用于乐观锁
    permission_checked_at   TIMESTAMPTZ,

    -- Lingxi 信息
    provisioning_state      TEXT NOT NULL DEFAULT 'guest'
        CHECK (provisioning_state IN (
            'guest',            -- 未开通
            'matching',         -- 权限记录匹配中（工号/邮箱）
            'manual_review',    -- 唯一成功后的运行异常待处理；不用于身份或权限匹配失败
            'provisioning',     -- 环境 / 经批准的正式产物前置 / 发布进行中
            'mcp_syncing',      -- 权限正在同步（15 分钟窗口）
            'active',           -- 开通成功
            'aborted'           -- 终止开通
        )),
    workspace_state         TEXT NOT NULL DEFAULT 'none'
        CHECK (workspace_state IN ('none','creating','ready','failed')),
    posix_uid               INTEGER UNIQUE,                -- 用户环境的宿主机 uid，交付接口据此认定归属
    publish_state           TEXT NOT NULL DEFAULT 'none'
        CHECK (publish_state IN ('none','pending','published','failed')),
    mcp_sync_state          TEXT NOT NULL DEFAULT 'none'
        CHECK (mcp_sync_state IN ('none','checking','confirmed','timeout')),
    account_state           TEXT NOT NULL DEFAULT 'enabled'
        CHECK (account_state IN ('enabled','suspended','deleting','deleted')),
    workbench_granted       BOOLEAN NOT NULL DEFAULT FALSE, -- 高级工作台，链路外审批
    erased_at               TIMESTAMPTZ,                   -- 可识别运行数据清理完成时间

    created_at              TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at              TIMESTAMPTZ NOT NULL DEFAULT now(),

    CHECK (account_state <> 'deleted' OR (
        feishu_open_id IS NULL AND feishu_user_id IS NULL AND feishu_union_id IS NULL
        AND display_name IS NULL AND department IS NULL AND tenant_key IS NULL
        AND employee_no IS NULL AND email IS NULL
        AND drive_folder_token IS NULL AND permission_record_id IS NULL
        AND posix_uid IS NULL AND erased_at IS NOT NULL
    ))
);

CREATE INDEX ON app_user (provisioning_state) WHERE provisioning_state <> 'active';
CREATE INDEX ON app_user (display_name);
```

`drive_folder_token` / `drive_folder_state` 是已经进入历史蓝本的候选字段，不是现行产品合同。#140 决定前，正式路径必须保持 `NULL` / `none`，任何代码不得把 `creating` 或 `ready` 作为 `provisioning_state='active'` 的前置或成功证据；#140 若选择非目录方案，实施者必须用前滚迁移替换或废弃这两个字段，不能借旧字段名偷渡承载模型。

`account_state='deleting'` 一经写入即禁止新的问数、交付、权限发布和工作台会话；`deleted` 只在删除编排完成后写入。进入 `deleted` 时必须清空飞书标识、姓名、部门、租户、权限记录引用、经批准的正式产物路由引用（含历史云盘 token）与宿主机 uid，只保留无法再映射到人的内部随机 ID、完成状态和 `erased_at`，用于幂等返回“已经删除”。若清理任一步失败，状态保持 `deleting` 并重试，不能向管理员或用户显示删除成功。

**五个独立状态字段而不是一个总状态**：合同把"准入""用户环境""多维表格发布""MCP 同步""启停"列为并列的五类信息，且恢复规则是"从尚未确认完成的步骤安全恢复，不重跑整个流程"。合成一个状态会丢掉"哪几步已完成"，让安全恢复无从判断。

**`permission_version` 是乐观锁的锚点**：待确认操作在准备时记下它，确认时比对——合同要求"目标状态已经变化时一律不执行"。

**飞书在职状态不落库，每次按需回读。** 飞书关联组织的可见范围**不做在职状态过滤**：710 人实测中含 5 名已冻结、1 名未加入的成员，能被定位到不等于在职（见[两条路径的连接与字段可得性](../参考证据/飞书关联组织两条路径的连接与字段可得性.md)）。因此建档、匹配与权限发布前必须实时读取成员详情的 `status` 并校验，不得依赖库中的历史快照——把它存成字段会立刻产生"库里写着在职、飞书那边已冻结"的陈旧窗口，而这个字段的唯一用途恰恰是拦截这种情况。花名册的「账号状态」同理按需回读、不落库。断言见 `V-开通-07`。

`employee_no` 与 `email` 落库的用途不同：它们是**匹配时刻的存档**，与姓名一起构成每日审计日报的比对基线（产品合同：每日比对已开通用户的花名册资料与存档，变化经审计日报通知）。比对逻辑读花名册当前值与这三个存档字段；账号状态没有存档列，以「已开通用户默认在职」为基线直接核对花名册当前值，非正常状态即进入日报。**比对基线这一侧不需要额外的历史表**——这句话在 2026-08-08 的 D2 裁定后仍然成立，但它此前被读成「本切片零新表」，这一层已被推翻：花名册**读取结果**这一侧需要一份持久快照，见下节。

```sql
CREATE TABLE user_permission_scope (
    id            BIGSERIAL PRIMARY KEY,
    user_id       TEXT NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    company       TEXT NOT NULL,
    function      TEXT NOT NULL,
    granted_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_at    TIMESTAMPTZ,                              -- 软删除，保留调岗轨迹
    UNIQUE (user_id, company, function, granted_at)
);

CREATE UNIQUE INDEX user_permission_scope_active_uniq
    ON user_permission_scope (user_id, company, function)
    WHERE revoked_at IS NULL;
```

**收回用 `revoked_at` 而非物理删除**：合同要求"调岗时只收回明确失效的范围""恢复账号时不自动恢复曾被收回的权限"。后者需要知道"曾被收回"这件事，硬删除会丢失该信息。

```sql
CREATE TABLE admin_identity (
    id                      TEXT PRIMARY KEY,               -- adm_*
    app_user_id             TEXT UNIQUE NOT NULL REFERENCES app_user(id),
    auth_provider           TEXT NOT NULL,
    auth_subject            TEXT NOT NULL,
    credential_fingerprint  TEXT NOT NULL,                  -- 指纹或版本，不是凭据明文
    bound_at                TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_at              TIMESTAMPTZ,
    UNIQUE (auth_provider, auth_subject)
);

CREATE TABLE admin_role (
    id          BIGSERIAL PRIMARY KEY,
    identity_id TEXT NOT NULL REFERENCES admin_identity(id) ON DELETE CASCADE,
    role        TEXT NOT NULL CHECK (role IN ('permission_admin','ops_admin','super_admin')),
    granted_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    granted_by  TEXT REFERENCES admin_identity(id) ON DELETE SET NULL,
    revoked_at  TIMESTAMPTZ
);

-- 同一人同一角色同时只能有一条有效记录
CREATE UNIQUE INDEX admin_role_active_uniq
    ON admin_role (identity_id, role) WHERE revoked_at IS NULL;
```

`admin_identity` 是“管理 MCP 调用人 = 确认卡接收人 = 当前角色持有人”的数据锚点：认证从 `(auth_provider, auth_subject)` 唯一解析到该行，再经 `app_user_id` 取得唯一本人飞书 `open_id`，角色只授予该身份。凭据明文由认证服务持有，不进入数据库。

不为“最后一名超级管理员”增加数据库触发器或并发锁。若系统中已无超级管理员，持有服务器 Root 权限的 Ops 运维工程师使用数据库所有者/迁移权限，为一个身份已经核实并绑定飞书的现有 `app_user` 恢复或创建 `admin_identity` 与超级管理员角色，并记录恢复对象、操作者、时间和结果。该恢复不进入管理 MCP，不提供日常调用接口；上线前必须在 `biai-stage` 演练并留下脱敏证据。

```sql
CREATE TABLE manual_review (
    id             TEXT PRIMARY KEY,                        -- rev_*
    user_id        TEXT NOT NULL REFERENCES app_user(id),
    reason         TEXT NOT NULL
        CHECK (reason IN ('workspace_error','publish_error','mcp_sync_timeout')),
    detail         JSONB NOT NULL DEFAULT '{}'::jsonb,      -- 脱敏摘要
    status         TEXT NOT NULL DEFAULT 'open'
        CHECK (status IN ('open','resolved','aborted')),
    opened_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    resolved_at    TIMESTAMPTZ,
    resolved_by    TEXT REFERENCES admin_identity(id) ON DELETE SET NULL,
    expires_at     TIMESTAMPTZ NOT NULL                      -- 写入触发器固定为 opened_at + 2160 hours
);

CREATE INDEX ON manual_review (status, opened_at) WHERE status = 'open';
```

`manual_review` 在这里是目标设计中的兼容表名，现行权威迁移链**尚未创建这张表**；当前数据库只在 `app_user.provisioning_state` 中保留同名状态。未来若实现运行异常表，只允许环境、发布或同步异常写入。身份或权限匹配出现零条、多条、冲突、重复或资料不完整时直接走无可用权限出口，不写运行异常表。Lingxi 不为这些低频运行异常建设复杂任务系统，因此目标表**没有** `due_at`、`assignee`、`escalated_at` 字段。

[#89](https://github.com/Moshuiwang/lingxi/issues/89) 只负责身份字段存取与匹配收口，不承担一条并不存在的 `manual_review` 迁移。未来实际创建运行异常表时，再以新的前滚 revision 落实本节 DDL，并按当时的真实数据库状态验收。

### 花名册持久快照

产品负责人 2026-08-08 的 **D2 裁定**（[Issue #52](https://github.com/Moshuiwang/lingxi/issues/52)）要求保存**最近一次成功、完整、非空**的花名册读取结果，跨进程重启与常规发布都还在；源头返回空、读取失败、超时或半轮读取一律**保留上一份**、不覆盖。载体是 `roster_snapshot`（元信息）与 `roster_snapshot_row`（行）两张表，DDL 与理由以 `migrations/alembic/versions/0063_roster_snapshot.py` 为准，本节不复制。

四条不可违反的约束：

1. **替换门槛只认读取层的四态结论**（`status` 为 `COMPLETE`），**不得以「读到的行非空」作判据**——`INCOMPLETE` 态刻意保留行（读到了，可信度没有），以行非空为判据会让不可信的一轮顶掉一份好快照。判定在 `core/identity/roster_snapshot.py`，断言 `V-花名册-41`。
2. **替换是整体替换且在同一个事务内完成**：删旧、写元信息、写行三步同事务，中途失败库里仍是替换前那一份（`V-花名册-42`）。
3. **任何时刻最多一份快照**，由 `singleton` 列的 `CHECK` + `UNIQUE` 在数据库层保证（`V-花名册-45`）；行表按 `ON DELETE CASCADE` 挂在元信息上，不积累历史版本。
4. **行原样保留、不去重**：同一人员 ID 多行是花名册实测常态，去重会把歧义变成静默的错误选择（`V-花名册-06`）。元信息表只存计数、列名与判定结果，**不含任何人员资料值**（`V-花名册-46`）。

这张表**不与 `app_user` 建外键**：花名册是全公司在册人员表，绝大多数行不是 Lingxi 用户；它是下游资料副本，不是权限权威（产品合同「外部平台边界」）。

**保留期已由产品负责人裁定**（2026-08-17）：**始终保留最近一份，豁免九十天规则**。本表因此**刻意没有** `expires_at`、没有到期触发器，也不在[第九节](#九保留与删除)受限清理函数的覆盖范围内——这是裁定的结果，不是遗漏。三条：

1. **始终保留最近一份**：它是每日比对的花名册侧基线，删掉等于让比对失去基线，按[「当前状态与历史内容分开」](#当前状态与历史内容分开)归入「继续提供服务所需的当前状态」；
2. **替换即删旧**：`singleton` 唯一约束 + `ON DELETE CASCADE` 保证库里永远只有一份，不积累历史版本——这是豁免九十天上限的前提，本表不会越攒越多；
3. **超龄不自动删，改为按日报告警提醒**：源头长期读不到导致快照变旧时，管理员要被告知「基线在变旧」，而不是某天发现基线被悄悄删了。告警事实（含上一份快照的读取时间与年龄）已由实现层产出，**接线到日报 / 告警状态机属 #52 的后续实现切片 S-B-04**。

## 四、开通与发布

**`publish_outbox` 已经落地**（[Issue #156](https://github.com/Moshuiwang/lingxi/issues/156) 的 S-C-01）：DDL 与逐条理由以 `migrations/alembic/versions/0064_permission_publish_outbox.py` 为准，本节不复制。与本节此前的蓝本相比有四处差异，均在 revision 文件头部写明理由：`id` 是 ULID `TEXT` 而不是 `BIGSERIAL`（与 0057–0063 一致）、多了 `superseded` 状态、多了 `UNIQUE (user_id, permission_version)`、多了 `claimed_at` / `last_outcome` / `external_record_id` 三列。

**outbox 模式**：权限变更与发布意图在同一事务落库，投递异步进行。若直接在权限变更后调飞书 API，调用失败会留下"数据库已改、发布未做"的静默不一致，而合同要求两者不一致时不得视为发布完成（`V-权限-01`）。

`payload` 存内容快照而非引用，让重试时发布的一定是当初决定发布的那一版，不会被后续变更污染。它存的是发布表那一行的**全部文本字段**，形状、序列化格式与 `record_key` 口径定稿在 `src/lingxi/core/permission/publish_row.py` 的模块文档，全仓库只有那一处实现。三条与本表直接相关的约束：

1. **`token_cipher` 的口径按 2026-08-17 裁定改写**（`V-权限-11`）：本条此前写的是「`token_cipher` 永不进 payload、也永不被写进发布表」，与实现以及本节下方 `mcp_access_token` 那一段的口径**自相矛盾**，现按实际语义订正。三句话：**payload 在有令牌时是七键快照，存的是密文**（明文与主密钥一步都不进 payload、日志与告警，这一条没有变——凭据不入 outbox 与日志是产品合同的原文，管的是**明文**）；**新建**发布行必须写 `token_cipher`，缺它就失败关闭、不新建；**更新**既有行时那一列既不清空也不覆盖，仅当它为**空**时补写我方密文（补空洞不是覆盖：「不覆盖」保护的是既有 26 行那些旧系统 biai-agent 签发、我们不知其明文的令牌，空值没有什么可保护的）。理由与逐条落点见迁移 `0064_permission_publish_outbox.py` 的文件头部、`src/lingxi/core/permission/publish_row.py` 的模块文档，以及[验收矩阵](验收矩阵.md)的 `V-权限-11`。
2. **同一用户同时只有一条发布在途**：认领语句除 `FOR UPDATE SKIP LOCKED` 外还要求"该用户不存在**更早的非终态**（`pending`/`publishing`）兄弟行"，否则旧版本的写入会落后到新版本之后把权限盖回去，用户侧表现为已经收回的权限被静默恢复（`V-权限-12`）。判据不能写成"有没有 `publishing`"——`READ COMMITTED` 下尚未提交的认领对另一个消费者不可见，那条判据会漏掉正在发生的并发认领；理由全文在 `adapters/postgres_permission_publish.py` 的 `claim_next` 文档。
3. **九十天保留由 `content_expires_at` + 应用层擦除落实**：`payload` 含邮箱与姓名，到期后由 `adapters/postgres_permission_publish.py` 的 `redact_expired_payloads` 擦成 `'{}'`；行本身随 `app_user` 删除按 `ON DELETE CASCADE` 消失。未进[第九节](#九保留与删除)受限清理函数的理由见 revision 文件头部。

**`app_user` 没有 `publish_state` 列**：本节上方蓝本里的那一列当前迁移链没有建，S-C-01 也刻意不引入——发布进度已经完整地由 `publish_outbox.status` 承载，再加一列就是第二个真相来源。

**`publish_outbox` 有两列记录"哪一行"，语义不同不可混用**（`created_record_id` 随 S-C-02 的迁移 `0065` 追加）：`external_record_id` 是**审计**——上一次尝试操作了哪一行，任何尝试都会写，包括既有行更新失败；`created_record_id` 是**出身**——这条意图**自己建过**的那一行，只有 `create_row` 明确返回了记录标识时才写；更新尝试一律不改它，重复创建时取**最近一次**成功创建的那一行（停在失效的旧标识上会让"我们建的行密文被改写"这道检查永远命不中当前活着的那一行，保护静默失效）。判定层拿出身回答"这一行是不是我们建的"（据此识别"我们建的行密文被改写"）。用审计列代替出身列会造成一个真实回归：既有 26 行只要有一次更新读回不明，行 ID 就进了审计列，重试时判据成立、而它们的旧密文当然不等于我方快照，于是这一行被判成**永久冲突**——S-C-01 的"更新可重试收敛"就被打断了。创建结果不明（没拿到记录标识）时出身保持空：那时无法把"自己建的"与"并发写入方建的"区分开，重试按普通路径收敛，就绪探针是最终的门。

**`mcp_access_token` 与 `mcp_sync_check` 已经落地**（[Issue #156](https://github.com/Moshuiwang/lingxi/issues/156) 的 S-C-02）：DDL 与逐条理由以 `migrations/alembic/versions/0065_mcp_token_and_sync_check.py` 为准，本节不复制。

`mcp_access_token` 是本节新增的一张表（蓝本没有它）：Lingxi 为建档用户签发问数 MCP 访问令牌，**只持久化 AES-256-CBC 密文**（`token_cipher`），明文只在签发瞬间与后续按需解密时存在于内存。四条结构性事实，**全部由数据库约束落实、不依赖应用层自觉**：**主键即 `user_id`**（同一个人两条令牌在结构上不可表达）；**没有任何明文列或指纹列**（指纹列会把"拿候选明文来碰"变成一次本地比对，而消费方走的是解密后等值匹配，根本不需要它）；**`token_cipher` 的 CHECK 钉住我方签发格式的精确 envelope**（`^[A-Za-z0-9+/]{86}==$`：明文恒 43 字符 → 密文恒 64 字节 → base64 恒 88 字符），因此把原样令牌明文写进这一列即使绕过全部应用层、直接执行 SQL 也会被拒——但它**不证明内容真的经过加密**，一段恰好 88 字符的合规 base64 文本仍能写进来，内容正确性由解密路径负责（解不开即失败关闭）；**BEFORE UPDATE 触发器让已签发的密文改不掉**（代价是形状合规却解不开的值会把那一行砖化，只能删行重签——取舍见迁移注释）。

因此**没有轮换路径**，这是刻意的：Lingxi 只在新建发布行时写 `token_cipher`，更新既有行时不清空不覆盖，轮换在当前发布语义下送不到消费方（库里换了、外部表还是旧的，用户侧表现为"某天开始问数忽然没有权限"）。要支持轮换必须先由产品负责人决定是否允许覆盖既有行的该列，那时连同触发器一起改。签发是幂等的：已存在即返回既有那一份。

`mcp_sync_check` 与本节此前的蓝本相比有四处差异，均在 revision 文件头部写明理由：`id` 是 ULID `TEXT` 而不是 `BIGSERIAL`（与 0057–0064 一致）；删掉 `observed_permission_version` / `observed_companies` / `observed_functions` 三列；`result` 的取值域从三态改为**五路互斥**（`ready` / `no_permission` / `waiting` / `timed_out` / `technical_failure`）；`detail` 自由文本换成 `error_code` + `metric_count`。

第二处差异是产品判定的变化，不是实现偏好：**当前权限多维表格没有版本字段**（2026-08-17 全表回源核对，G-155 终判），蓝本假设的「回读 `permission_version` 与生效范围、逐项比对一致后再发最小查询」因此不可行。就绪的唯一依据改为**探针法**——用该用户的明文令牌对问数 MCP 真实执行一次 `list_metrics`，返回的可见指标条数大于零才算就绪（`V-权限-06`）。没有可比对的观察值就不留三个永远为 `NULL` 的列：空列会让将来读表的人以为"曾经比对过"。

每次尝试独立成行，不是覆盖一个字段。**五路各自的精确形状由一条 CHECK 全表达完**：`ready` 必须看见大于零的指标且不带错误码——**明确空结果只证明这次查询没有报错，本身不构成权限同步证据**（产品合同「问数 MCP」一节）；`waiting` 必须带错误码，观察值只能缺省（明确拒绝）或恰为零（空结果）；`technical_failure` 与 `no_permission` / `timed_out` 必须带错误码且**不得携带观察值**。只挡"就绪没观察值"是不够的：一条 `waiting` 却带着 `metric_count=5`、或 `technical_failure` 带着观察值的行，读起来都像"探针跑通了、看见了指标"，而它们恰恰是"没就绪"。

`attempt_no` 由写入语句取 `COALESCE(MAX(attempt_no), 0) + 1`，不由调用方传：调用方传次序会在进程重启后从 1 重号，与已经落库的第一次冲突。取号前先取一把按（用户，权限版本）的事务级 advisory lock——`READ COMMITTED` 下两个并发记账会读到同一个 MAX、各自算出同一个 N+1，其中一个撞 `UNIQUE` 中止，而它对应的那次探针**已经真的发出去了**却不会留下记录。逐次记录还能在真实数据上回答"十五分钟是不是一个现实的上限"，作为复审该规则的输入。

保留：该表没有可识别内容列（只有内部 ULID、权限版本、次序、时间、结论与错误码），但 `user_id` 仍指向具体的人，因此仍按[第九节](#九保留与删除)走九十天上限——触发器固定 `content_expires_at`，到期由 `adapters/postgres_mcp_token.py` 的 `purge_expired_checks` **删整行**（没有列可擦）。两张表的 `user_id` 均 `ON DELETE CASCADE`。

## 五、会话与任务

```sql
CREATE TABLE conversation (
    id                 TEXT PRIMARY KEY,                    -- cnv_*
    user_id            TEXT NOT NULL REFERENCES app_user(id),
    feishu_chat_id     TEXT NOT NULL,
    feishu_thread_id   TEXT,                                -- NULL 表示私聊主窗口
    agent_session_id   TEXT,                                -- Agent SDK 会话；NULL = 下次不 resume
    last_task_ended_at TIMESTAMPTZ,                         -- 两小时规则的唯一依据
    running_task_id    TEXT,                                -- 同话题串行
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 私聊主窗口与每个话题各自独立
CREATE UNIQUE INDEX conversation_scope_uniq
    ON conversation (user_id, feishu_chat_id, COALESCE(feishu_thread_id, ''));
```

三条合同规则直接由这张表表达：

| 规则 | 字段 |
|---|---|
| 主窗口与每个话题是独立对话、互不共享上下文 | 每个 `conversation` 独立 `agent_session_id` |
| 会话延续按"上一条任务结束到下一条新任务开始"判断，任务执行时长本身不触发新会话 | 只读 `last_task_ended_at`，不涉及任务开始时间或时长 |
| `/new` 清空当前对话上下文，其他话题不受影响 | 置 `agent_session_id = NULL` |

### 同话题串行靠条件更新，不靠唯一索引

每个话题在 `conversation` 里只有一行，因此**没有可以用唯一索引表达的"同时两个运行中任务"状态**——冲突发生在同一行的字段覆盖上，不是行的重复上。抢占必须用条件更新，以影响行数判断成败：

```sql
-- 抢占：只有当前空闲才能占用
UPDATE conversation SET running_task_id = $task_id
 WHERE id = $conv_id AND running_task_id IS NULL;
-- 影响行数 0 → 话题忙碌，回复"当前任务仍在处理中"

-- 释放：只有持有者能释放，防止被别的任务误清
UPDATE conversation SET running_task_id = NULL, last_task_ended_at = now()
 WHERE id = $conv_id AND running_task_id = $task_id;
```

`UPDATE` 在 PostgreSQL 的默认隔离级别下会对目标行加行锁，并发抢占天然串行化，不需要额外的咨询锁。

> 这条曾经写成"由 `conversation (id) WHERE running_task_id IS NOT NULL` 的唯一部分索引保证"，是错的：`id` 已经是主键，该索引不增加任何约束，第二个任务会直接覆盖第一个。已在 PostgreSQL 16 上实测确认并改正。

```sql
CREATE TABLE task (
    id               TEXT PRIMARY KEY,                      -- tsk_*
    conversation_id  TEXT NOT NULL REFERENCES conversation(id),
    user_id          TEXT NOT NULL REFERENCES app_user(id),
    inbound_event_id TEXT NOT NULL,                         -- 溯源到飞书事件
    prompt           TEXT NOT NULL,
    status           TEXT NOT NULL DEFAULT 'queued'
        -- awaiting_delivery 随 #151 新增：Worker 写完 terminal 投递事件后先转入
        -- 这个中间态并继续占用话题，业务结论（succeeded/failed/stopped）要等
        -- 投递解析（confirm_delivery 确认送达，或二十四小时到期强制收敛）才最终
        -- 写定，不得复用 succeeded 冒充"等待投递"（issue 状态合同「失败与等待
        -- 分支」）。
        CHECK (status IN ('queued','running','awaiting_delivery','succeeded','failed','stopped')),
    resumed_session  BOOLEAN NOT NULL DEFAULT FALSE,        -- 是否续用旧会话
    card_id          TEXT,
    card_seq         INT NOT NULL DEFAULT 0,                -- 流式卡片序列号，严格递增
    fallback_text    BOOLEAN NOT NULL DEFAULT FALSE,        -- 是否已降级为文本兜底
    worker_id        TEXT,
    heartbeat_at     TIMESTAMPTZ,
    attempts         INT NOT NULL DEFAULT 0,
    scheduled_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    started_at       TIMESTAMPTZ,
    ended_at         TIMESTAMPTZ,
    stop_requested   BOOLEAN NOT NULL DEFAULT FALSE,        -- /stop
    error_kind       TEXT,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    content_expires_at TIMESTAMPTZ NOT NULL                  -- 写入触发器固定为 created_at + 2160 hours
);

CREATE INDEX task_queue_idx ON task (scheduled_at) WHERE status = 'queued';
CREATE INDEX task_stale_idx ON task (heartbeat_at) WHERE status = 'running';
CREATE INDEX ON task (conversation_id, created_at DESC);
```

- `task_queue_idx` 是部分索引，只覆盖 `queued` 行——队列表的常见陷阱是全表索引随历史增长而退化，部分索引让索引大小只与积压量相关。
- `task_stale_idx` 支持 scheduler 回收心跳超时的 `running` 任务。
- **忙碌期收到的消息不进这张表**（合同：不入历史、不排队），只记 `chat_message` 与审计。

### 问数结果投递事件与会话保留 Outbox

**系统代为收口同样接入 outbox（#178，红线修复，撤销 #151/#170 描述中"三个系统声明超时路径不接入 outbox"的范围排除）**：`PostgresTaskQueue` 的三条"任务从未被一个仍然存活的 worker 正常执行完"路径——`reclaim_stale` 心跳超时后判定不可再重试的终态分支、`reclaim_queued`（排队超时无人领取）、`fail_unavailable_versions`（目标 worker 版本连续不可用）——此前直接把 `task.status` 改成 `failed` 并释放话题，不写任何 `task_delivery_event`；S-A-07 r3 真实验收发现这条路径下用户会永远停在处理态收不到终态（Gateway 没有任何可投递内容）。修复后三条路径共用私有方法 `PostgresTaskQueue._write_system_terminal`：在已经持有的行锁下先写一条 `started` 事件（不带正文，`worker_id` 用固定哨兵 `"system"` 标识"没有真实 worker 持有过这个任务"，不是伪造一个执行者）、再写 `terminal` 事件（`terminal_kind='failed'`，`error_kind` 分别为 `retry_exhausted`/`side_effect_uncertain`/`queued_timeout`/`worker_version_unavailable`，`content` 复用 `config/content.toml` 既有、此前从未被任何生产代码真正渲染过的文案键 `worker.running_timeout`/`worker.side_effect_uncertain`/`worker.queued_timeout`/`worker.version_unavailable`），并把 `task.status` 转入 `awaiting_delivery`——**不释放 `conversation.running_task_id`**，话题继续占用直到 Gateway 消费 outbox 调用 `confirm_delivery`，或二十四小时到期由既有 `expire_undelivered_terminals` 兜底收敛为 `delivery_expired`（这正是"Gateway 不可用时由既有 24 小时到期路径兜底"这句话成立的原因：复用的是同一张表和同一组到期/确认机制，没有另起一套）。先写 `started` 再写 `terminal` 是必需的，不是可省略的对称性装饰：Gateway 消费循环（`apps/gateway/delivery.py` 的 `_handle_terminal`）只在 `stream.card_id is not None` 或 `stream.fallback_needed` 为真时才会建卡或走文本兜底，一个从未出现过 `started` 事件的任务两者都是假，`terminal` 事件会被无声消费（游标推进）而不产生任何外发——省略 `started` 会让这次修复看似完成、实则把"用户永远收不到终态"的窗口从"永不收口"缩小成"最长 24 小时才收口"，仍然违反本条修复的目标。幂等由既有 `idempotency_key` 机制承担（`terminal` 用与真实 worker 同形的 `f"{task_id}:terminal"`），housekeeping 重复轮询不产生第二条终态。

```sql
CREATE TABLE inbound_event (
    feishu_event_id  TEXT        PRIMARY KEY,
    received_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    event_type       TEXT        NOT NULL,
    user_open_id     TEXT,
    handled_as       TEXT,        -- task_queued / busy_hint / auto_provisioning / command / dropped
    trace_id         TEXT        NOT NULL,
    expires_at       TIMESTAMPTZ NOT NULL,                   -- 写入触发器固定为 received_at + 2160 hours
    onboarding_dispatched_at TIMESTAMPTZ                     -- NULL = 认领了但没确认交给开通编排
);

CREATE INDEX inbound_event_received_at_idx ON inbound_event (received_at);

CREATE INDEX inbound_event_onboarding_pending_idx
    ON inbound_event (received_at)
 WHERE handled_as = 'auto_provisioning' AND onboarding_dispatched_at IS NULL;
```

**`onboarding_dispatched_at`（交接账本，`0062_onboarding_dispatch_ledger`）**：未开通用户首条消息的处理分在事务两侧——事务内认领事件（`handled_as = 'auto_provisioning'`），事务提交之后才把事件交给开通编排。顺序不能反过来（提交前触发，事务一旦回滚就会重复触发一次带外部副作用的开通），代价是提交与交接之间存在一个窗口：进程在这个窗口里崩溃或被停机拿走，事件行已经存在、重投被幂等挡下，编排永远收不到它。这一列让这种孤儿行可判定，由 Gateway 的对账扫描（`core/conversation/onboarding_recovery.py`，挂在投递消费线程的每轮回调上）逐条认领并重新交接一次；认领与记账在同一条 `UPDATE … RETURNING` 里完成，多实例并发扫描时同一条只会被一个实例拿走。窗口默认三十分钟，宽于合同允许的十五分钟权限同步上限，避免把一次正在正常执行的开通判成孤儿。这一列不是第二套开通状态机——开通结论仍只由开通编排自己的持久化决定，它只回答“Gateway 这一侧的交接完成了没有”。

### 2026-08-06 随 #57（S4 前半）落地的差异

上面三张表由 alembic revision `0057_gateway_tables` 建立（DDL 内联在 revision 里；编号 SQL 自 #53 起冻结，基线之后的 revision 是 DDL 的唯一载体，见 [migrations/README.md](../../migrations/README.md)）。实际 DDL 在本蓝本之上有四处差异，逐条记录事实与理由：

| 差异 | 事实 | 理由 |
|---|---|---|
| `task.target_worker_version` | 新增列，`NOT NULL` 且**不给默认值** | [#45](https://github.com/Moshuiwang/lingxi/issues/45) 灰度决策提前到 S4 的两项预留之一。命名与 `pending_action.target_version`（权限版本号）区分，见架构设计「灰度发布」。不给默认值是为了让「忘记求值」直接违约失败，而不是静默落成 `stable` |
| 两个 `BEFORE` 触发器 | `task_freeze` 冻结 `target_worker_version` / `created_at` / `resumed_session` 并强制 `content_expires_at`；`inbound_event_expiry` 强制 `expires_at` | 改写目标版本的路径有三条（领取、重试、心跳超时回收），分处不同进程，靠代码审查逐条守住不现实；保留期由来源时间推导，写入方不得延长 |
| `task_queue_idx` | 索引键是 `(target_worker_version, scheduled_at)` 而不是单列 `scheduled_at` | 领取 SQL 带版本条件，不进索引会退化成全 `queued` 扫描 |
| `inbound_event.handled_as` | 取值域多一个 `not_provisioned` | 本批**不**启动自动匹配与开通（正向接线属后续 Issue），记 `auto_provisioning` 等于陈述一件没有发生的事；记 `dropped` 又会与「已停用」混为一谈。`auto_provisioning` 保留在取值域里备用 |

`conversation.running_task_id` 与 `task.inbound_event_id` 都**不设外键**：前者与 `task.conversation_id` 构成环，任一方向的外键都会让「先插任务再抢占」或反之其中一种顺序无法在单事务内完成，而抢占与入队必须同事务；后者与入站事件的九十天保留清理是两条独立的清理链，外键会让其中一条的删除顺序依赖另一条。

`feishu_event_id` 是单列主键，保证同一事件在幂等保留窗口内重投时都发生冲突。gateway 在一个事务内先插入事件，再创建任务或记录处理结果；插入冲突时直接返回成功且不创建第二个任务。不能把 `received_at` 放进主键，否则每次重投都会因接收时间不同而绕过去重。

**"最多成功执行一次"由条件更新的影响行数保证**：

```sql
UPDATE pending_action
   SET status = 'executing', confirmed_by = $clicker, confirmed_at = now()
 WHERE id = $action_id
   AND status = 'pending'                    -- 未执行过
   AND expires_at > now()                    -- 未过期
   AND initiated_by = $clicker               -- 只有发起人本人
 RETURNING *;
```

影响行数为 0 即不执行。重复点击、重复回调、多个 Agent 重复提交都会落到 0 行，返回既有结果——不需要额外的分布式锁。

随后在**同一个事务**内：写 `audit_event` → 改业务状态 → `status='executed'`。任一步失败整体回滚，用户状态不变，直接满足合同的"审计无法写入时一律不执行"。

`card_delivered = FALSE` 的操作视为作废（合同："卡片发送失败时本次操作不执行"）。

`params`、`effect_summary`、`reason` 和 `result` 可能包含用户身份、权限或处理详情，必须在 `content_expires_at` 到期时删除或替换为不可逆脱敏的状态摘要；待确认操作的幂等状态可以保留，但不能继续识别目标用户或原始参数。

## 七、正式产物交付（#140 前失败关闭）

`delivery` 仍表示正式文档、表格、图片或文件的逻辑交付记录，但旧版“机器人目录 + `drive_folder_token` + `authorized/sent`”DDL 已被 2026-08-13 的外部事实否定，**不再是可实施蓝本**。#140 必须根据 #97 证据选择责任主体、承载模型、用户访问与处置、保留清理和离职语义，再以前滚迁移冻结精确字段；不得直接实现旧代码块。

无论 #140 选择目录、逐份授权、长期服务主体或缩小首期范围，数据库都必须分别记录和约束以下事实：

| 事实 | 最小约束 |
|---|---|
| 请求与归属 | `idempotency_key` 唯一；绑定当前用户、来源任务或工作台会话、产物类型与获批路由版本 |
| 外部创建 | 只有权威 API 明确成功才记录对象标识；响应不明进入 `uncertain`，不自动重复创建 |
| 所有权或责任主体 | 保存 #140 批准模型所需的主体引用和真实回读结论，不能从“机器人创建”推断 |
| 用户访问 | 授权、链接范围与目标用户可访问性分别回读；只生成 token 或 URL 不算成功 |
| 发送 | 飞书权威 API 接受并绑定可回读消息标识后记 `platform_received`；这不等于 `user_read` |
| 生命周期 | 停用、离职、删除、保留、清理或交接分别有状态、Owner 与截止时间，不默认由飞书自动完成 |
| 运行侧保留 | 标题、外部引用、状态与错误分类等可识别运行记录最长九十天；正式产物自身按 #140 合同处理 |

#140 尚未批准可用路径时，正式产物端点不创建任何外部目录或文件，只能留下不含业务正文的失败关闭事实并告诉调用方“当前无法安全交付正式产物”。飞书与高级工作台复用的是同一份交付合同，**不是同一个目录 token**。普通问数卡片/文本正文使用上一节的会话保留 Outbox，不进入本节 `delivery` 逻辑实体，也不因正式产物失败关闭而受阻。

**append-only 的双重保证**：

```sql
CREATE FUNCTION audit_immutable() RETURNS TRIGGER AS $$
BEGIN
    -- 唯一例外：由无登录专用角色 lingxi_retention_owner 持有的
    -- SECURITY DEFINER 清理函数，且目标已经真实到期。
    IF TG_OP = 'DELETE'
       AND current_user = 'lingxi_retention_owner'
       AND OLD.expires_at <= clock_timestamp() THEN
        RETURN OLD;
    END IF;

    RAISE EXCEPTION 'audit_event 是只追加表，不允许 % 操作', TG_OP;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_event_no_mutate
    BEFORE UPDATE OR DELETE ON audit_event
    FOR EACH ROW EXECUTE FUNCTION audit_immutable();

REVOKE UPDATE, DELETE ON audit_event FROM lingxi_app;
```

权限收紧防误操作，触发器防误授权。分区表上的行级触发器会传播到各分区（PostgreSQL 13+）。保留清理由无登录专用角色 `lingxi_retention_owner` 持有的 `SECURITY DEFINER` 函数执行：该角色只拥有目标内容表的 `SELECT` / `DELETE` 和函数所需权限，没有 `INSERT`、`UPDATE`、`TRUNCATE`、DDL 或登录能力。每个清理函数必须声明 `SET search_path = pg_catalog`，并在函数体中使用带 schema 的目标表名和函数名，不能依赖调用方搜索路径。函数拒绝晚于当前时间的 `p_now`、只删除 `expires_at <= LEAST(p_now, clock_timestamp())` 的有限批次，且返回表名、数量和实际时间范围供 scheduler 写入不含用户内容的运行日志。创建后立即 `REVOKE ALL ON FUNCTION ... FROM PUBLIC`，再只向 `lingxi_scheduler` 授予精确函数签名的 `EXECUTE`。`lingxi_app` 既没有直接 `DELETE` 权限，也不能 `SET ROLE` 到该专用角色；即使误获普通 `DELETE`，触发器仍会拒绝。已经清空的分区只由 `lingxi_migrate` 或受控 Ops 维护任务删除，不向 scheduler 授予 DDL。

## 九、保留与删除

九十天是**可识别内容的最长上限**，不是“至少保留九十天”。承载用户内容的对象由 `BEFORE INSERT` 触发器忽略调用方传入值，**按内容类别写入适用期限**：一般内容（`chat_message.retention_class='general'` 等九十天上限类别）固定写入来源时间加 `interval '2160 hours'`；问数结果正文（`retention_class='result_delivery'`）固定写入来源时间加 `interval '24 hours'`，**不写九十天上限**——该值只在送达前阶段有效，取得 `platform_received` 后转为随会话保留，不再由 `expires_at` 到期驱动清理（见下文到期路径表与[问数结果投递事件与会话保留 Outbox](#问数结果投递事件与会话保留-outbox)）。`BEFORE UPDATE` 触发器拒绝修改来源时间或把已写入的到期时间后移。这里使用固定小时数而不是 `GENERATED` 列或“90 个日历日”，避免 PostgreSQL 对 `timestamptz + interval` 的生成列表达式限制和时区 / 夏令时造成的上限漂移。

scheduler 至少每小时小批量调用受限函数清理。`audit_event` 与 `chat_message` 可以继续按月分区，但最老分区必须先按 `expires_at` 精确删除到期行，不能等待整月到期；分区完全清空后再由受控维护删除。因此月分区不会把实际期限延长到 90–120 天。

超过 `expires_at` 仍能识别到用户或原文属于保留违规，必须告警并阻止把该版本作为可发布候选。清理失败只能重试或暂停发布，不能把到期时间后移。`chat_message.retention_class='result_delivery'` 的正文一旦取得 `platform_received`、转入会话保留阶段，不再受这条按 `expires_at` 判断的规则约束：保留违规检测改为比较会话边界状态（是否已触发 `/new`、空闲满两小时到点清理、停用感知或权限变化感知），而不是比较 `expires_at`；写入时按二十四小时计算的 `expires_at` 值保持不变、既不回填也不后移，只在“送达前”阶段有效，转入会话保留阶段后不再被清理函数或告警读取。**用于标记“已转入会话保留阶段”的字段已随 #151 冻结为 `task_delivery_event`（见下节）terminal 行的 `platform_received_at`：非空即表示已确认送达、脱离 `expires_at` 判断，转为受会话边界事件驱动的清理**——选它而不是新增一个专门列，是因为“已送达”与“已转入会话保留阶段”在方案 B 下是同一件事的两个名字，新增一个总是与它同步非空的独立列只会制造第二个真相来源。未来 `chat_message.retention_class='result_delivery'` 落地同一语义时应复用同一判断方式（“有没有对应的已确认送达记录”），不新增同名列。

### 正常运行内容载体的到期路径

| 数据对象 | 承载内容 | 最长期限与处理 |
|---|---|---|
| `chat_message.content`（`retention_class='general'`） | 原始聊天、用户可见回复（不含已送达的安全问数结果正文） | `occurred_at + 90 days` 前删除整行 |

| `chat_message.content`（`retention_class='result_delivery'`，已送达 `platform_received`） | 已送达的安全问数结果正文 | 不按 `expires_at` 清理；由会话边界事件（`/new`、会话空闲满两小时到点主动清除、停用感知、权限变化感知）触发整行删除，感知或到点即执行、不依赖下一次任务入队，见[问数结果投递事件与会话保留 Outbox](#问数结果投递事件与会话保留-outbox) |
| `task_delivery_event.content`（表名已随 #151 冻结） | 同一份安全问数结果正文在投递 Outbox 的副本 | 与上一行 `chat_message.content`（`result_delivery`）遵循同一规则，同一触发点统一清理；送达前二十四小时到期由 `expire_undelivered_terminals` 清空，送达后由会话边界触发（`/new`、空闲到点、`clear_delivered_content_for_user`）清空，均只清 `content`，`event_type`/`sequence`/`terminal_kind`/`error_kind` 等低敏事实保留最长九十天 |
| `audit_event` | 可关联的技术与管理审计 | `occurred_at + 90 days` 前删除；依法需继续保留时，先不可逆移除用户、内容和可回连标识 |
| `task.prompt`、错误详情、卡片标识 | 用户原始问题和运行结果 | `created_at + 90 days` 前清空内容字段或删除终态任务；仅保留不可识别聚合 |
| Agent SDK 会话 JSONL | 完整多轮对话与工具上下文 | 会话创建时写独立到期清单；到期前不再 `resume`，启动新会话并删除旧 JSONL。任何单个 JSONL 不跨越最早内容的九十天上限 |
| `manual_review.detail` | 环境创建、权限发布或 MCP 同步运行异常摘要 | `opened_at + 90 days` 前删除整行；需要原因与状态统计时另存不可识别聚合 |
| `pending_action.params`、`effect_summary`、`reason`、`result` | 管理动作的目标、影响和处理内容 | `created_at + 90 days` 前清空内容并把 `target_user_id` 置空；幂等状态可保留为不可识别摘要 |
| `publish_outbox.payload`、错误详情 | 用户权限发布快照 | `created_at + 90 days` 前删除终态行；当前有效权限仍以 `user_permission_scope` 表达 |
| `mcp_sync_check` 整行 | 用户权限同步的逐次判定（**没有自由文本列**：只有内部 ULID、权限版本、次序、时间、结论与错误码） | `started_at + 90 days` 前由 `purge_expired_checks` 删除历史尝试；随 `app_user` 删除按 `ON DELETE CASCADE` 消失 |
| `mcp_access_token.token_cipher` | 问数 MCP 访问令牌密文（**无明文列**） | 属“当前状态”：用户仍在使用服务时不按九十天删除；随 `app_user` 删除按 `ON DELETE CASCADE` 消失 |
| `inbound_event.user_open_id` 及事件行 | 飞书事件来源与幂等键 | `received_at + 90 days` 前删除；若外部重试规范超过九十天，须改用不含用户映射的去重机制，不能延长可识别内容保留期 |
| 正式产物运行侧引用（`idempotency_key`、外部对象标识、归属/授权/发送回读结论、状态与错误分类；精确字段随 #140 冻结） | 正式产物的运行侧引用与交付事实 | `created_at + 90 days` 前删除运行侧记录；正式产物自身的保留、清理与用户处置能力由 #140 最终合同决定，见[第七节](#七正式产物交付140-前失败关闭) |
| 用户工作目录中间文件 | 原始输入、转换文件和临时产物 | 任务完成、失败或送达状态不明后按最短必要时间清理，绝不以九十天作为默认等待期 |

数据库备份、WAL 归档和用户目录备份是上述规则的明确例外：它们用于故障恢复，不受九十天期限或单用户删除操作影响，保存时间由公司的灾备与恢复规则决定；它们不进入正常问数、用户找回、质量复核或日常审计路径。恢复历史备份可能重新带回备份时已有的用户内容。生产托管方式、备份落点和恢复流程仍按[第十二节](#十二未定项)确定。

### 当前状态与历史内容分开

`app_user`、当前有效的 `user_permission_scope`、`admin_identity`、`admin_role` 和 `mcp_access_token` 是继续提供服务所需的当前状态，用户仍在使用服务时不按九十天删除（令牌到期删除等于让该用户的问数从某天起静默失效，而它并不是"历史内容"）；它们的历史版本、撤销详情和其他可识别快照仍按上表清理。用户触发当前运行环境删除后不再适用“当前状态”例外，必须执行[当前运行环境删除编排](#当前运行环境删除编排)；灾备副本仍不受该操作影响。

`roster_snapshot` / `roster_snapshot_row` 按产品负责人 2026-08-17 的裁定同样归入“当前状态”例外：**始终保留最近一份，豁免九十天规则**。它是每日花名册比对的基线，删掉等于让比对失去基线；库里永远只有最近一份（替换即删旧，由唯一约束与 `ON DELETE CASCADE` 保证），不积累历史版本。快照因源头长期读不到而变旧时**不自动删除**，改为按日报告警提醒管理员，见[「花名册持久快照」](#花名册持久快照)。

正式产物的保留、清理与用户处置能力由 #140 最终合同决定；在此之前不以机器人专属目录交付正式产物，也不假定用户能够删除、转移或通过离职流程交接机器人名下对象（见产品合同「数据保留与删除」、[决策记录](../决策记录/2026-07-26-问数可信交付与数据保留边界.md)）。Lingxi 自己保存的正式产物运行侧引用、状态与交付记录仍受九十天上限约束。

受限清理函数由 `lingxi_migrate` 创建后移交给无登录的 `lingxi_retention_owner` 持有；该角色仅获目标内容表的 `SELECT` / `DELETE`，不获 `INSERT`、`UPDATE`、`TRUNCATE` 或 DDL。函数固定 `search_path` 为 `pg_catalog`，所有目标对象均使用带 schema 的名称；默认撤销 `PUBLIC` 的全部函数权限后，只按精确函数签名向 `lingxi_scheduler` 授予 `EXECUTE`。scheduler 只能传入不晚于当前时间的 `p_now` 和有上限的批量大小；函数只处理 `expires_at <= LEAST(p_now, clock_timestamp())` 的内容。普通应用角色没有相关表的直接 `DELETE` 权限，也不能取得专用角色。测试必须覆盖普通角色删除被拒绝、PUBLIC 和非 scheduler 调用被拒绝、伪造搜索路径不能改变目标对象、伪造未来 `p_now` 被拒绝、到期即清理、批量边界、每批返回可核对摘要和失败后告警。

## 十、权限与加固

五个数据库角色，最小权限：

| 角色 | 权限 |
|---|---|
| `lingxi_app` | gateway、worker 与 admin 的业务表最小读写；`audit_event` / `chat_message` **只 `INSERT`**；`inbound_event` `INSERT` + `handled_as`、`onboarding_dispatched_at` 两列的 `UPDATE`（见下方说明）；不能执行保留清理函数 |
| `lingxi_scheduler` | 定时职责所需的最小业务权限；可执行受限保留清理函数，但不能直接 `DELETE`，也不能 `SET ROLE` 到函数所有者 |
| `lingxi_migrate` | DDL；仅迁移时使用，不用于运行时连接 |
| `lingxi_retention_owner` | 无登录；持有受限保留清理函数及目标内容表的 `SELECT` / `DELETE`，不持有 `INSERT`、`UPDATE`、`TRUNCATE` 或 DDL；普通应用与 scheduler 均不能 `SET ROLE` 到它 |
| `lingxi_audit_ro` | `audit_event` 只读；**不含 `chat_message`** —— 治理系统接入用 |

`lingxi_audit_ro` 单独存在，是为了让"独立治理能力可接收审计事实、但不接管主链路、不读完整聊天内容"这条合同边界成为数据库权限而非应用约定。

**`inbound_event` 不是纯 `INSERT`（2026-08-18 核实，#206；2026-08-18 修订：补齐第二个 UPDATE 列）**：生产写路径对该表有两类 UPDATE，均在 `adapters/postgres_conversation/`（Issue #239 起是按读写边界拆分的包，既有调用点用到的名字全部保留，见包 __init__.py 的边界说明）：

1. **`handled_as`**（`_transaction.py` 的 `mark_handled_as`）：事件幂等去重要求先用 `INSERT ... ON CONFLICT DO NOTHING` 抢占 `feishu_event_id`（此时业务结果尚未判定），再由同一事务内的后续步骤把处理结论回写到这一列（`core/conversation/pipeline.py` 的 `_within_transaction`，其第 2 步到第 7 步落在同一个 `transaction()` 块内）。**「同一事务」这一条由 `V-队列-01` 要求**（`inbound_event` 插入、`conversation` 抢占、`task` 插入必须在同一事务内）；**「先插入、后回写结论」这一条则由幂等去重本身要求**——插入时业务结果尚未判定，冲突即判为重复投递并在加表情之前早退，反过来一次性插入会让并发重复投递失去这道早期互斥。
2. **`onboarding_dispatched_at`**（`_gateway_store.py` 的 `mark_onboarding_dispatched`、`claim_stale_onboarding`，迁移 `0062_onboarding_dispatch_ledger` 引入）：未开通用户首条消息被认领（`handled_as = 'auto_provisioning'`）之后，「是否已经交给开通编排」的账本列。`mark_onboarding_dispatched` 的 `SET ... WHERE ... AND onboarding_dispatched_at IS NULL` 保证只在第一次交接时写入，重复调用不把时间戳往后推；`claim_stale_onboarding` 用 `FOR UPDATE SKIP LOCKED` 锁住候选行再确认仍是 `NULL`，保证多实例对账扫描时同一条只被一个实例认领，不会被重复交接。

`inbound_event` 建表迁移（原 `013_create_conversation_task_inbound_event.sql`，现为 `0057_gateway_tables`）的 `handled_as` 列与 `BEFORE INSERT OR UPDATE` 触发器从一开始就是按会被 `UPDATE` 设计的；`onboarding_dispatched_at` 由 `0062` 后续新增，同样只能通过 `UPDATE` 维护。

对 `INSERT INTO inbound_event` 与 `UPDATE inbound_event` 两类直接 SQL 做过全仓库穷尽检索（本仓库不使用 ORM 或动态拼装的表写入），确认生产侧只有这两列会被 UPDATE，不存在第三列；两处 `INSERT` 的列清单也都不含这两列，因此它们只能经 UPDATE 产生：`postgres_onboarding.py` 里另外两处写入（`claim_inbound_event` 与授权回调记录）都是 `INSERT ... ON CONFLICT DO NOTHING`，不是 UPDATE；`inbound_event_expiry` 触发器只在函数体内重写 `NEW.expires_at`，不是调用方需要单独授权的列。`migrations/testing/001_create_app_user.sql` 里的 `record_authorized_identity()` 函数确实还有一处 `UPDATE inbound_event SET app_user_id = ...`，但该函数「在正式路径上没有对应动作」（`008_create_app_user.sql`/`20260806_baseline_006_012.py` 头部注释），是随 `.dockerignore` 排除、不进四个发布镜像的测试资产（`migrations/README.md` :386；生产只拉镜像、不现场构建，见架构设计「八、部署与发布」），因此不计入 `lingxi_app` 的目标权限面。

**此行只描述目标权限面，尚未通过 `GRANT`/`REVOKE` 落到数据库**：`inbound_event` 所在的任何业务表当前都没有表级授权语句（表级 `GRANT` 目前只在 `0054` 里对 `galaxy_import_batch`/`feishu_org_sync_run` 两张保留清理表出现），运行时进程也**尚未以这四个限权角色连库**——这是[当前能力](../当前能力.md)已披露的既有缺口（原文：四个数据库角色随迁移建立但运行时进程尚未以这些角色连库），不是本次核实新发现的问题，落地属独立的权限收紧工作。

**不启用行级安全（RLS）**：单租户、应用层已按 `user_id` 过滤，RLS 在此规模下增加的是调试难度而非安全性。若未来出现多租户或直连数据库的分析场景，再评估——写入[未定项](#十二未定项)。

## 十一、迁移约定

工具：Alembic。约定：

1. **每个迁移必须可前滚。** 破坏性变更（删列、改类型、加非空约束）拆成两次发布：先加新结构并双写，确认无误后再删旧结构。理由是[架构设计](架构设计.md)里的回滚策略是"切镜像 tag 重启"——旧镜像必须仍能在新库上工作。
2. **`CREATE INDEX CONCURRENTLY`** 用于生产上的索引新增，避免长时间持锁。
3. **按月分区预建和空分区删除**由迁移或受控 Ops 维护任务执行，不向 scheduler 授予 DDL；精确到期清理由 scheduler 至少每小时调用受限函数执行。
4. **不在迁移里写业务数据。** 种子数据（如首位超级管理员）用单独的、可重复执行的引导脚本，避免迁移历史与数据状态耦合。
