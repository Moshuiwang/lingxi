## 一、设计原则

1. **合同里的硬约束尽量落到数据库约束上**，用唯一索引、部分索引和条件更新表达，不靠应用代码自觉。
2. **状态用 `TEXT` + `CHECK` 而非原生 `ENUM`**：状态机会演进，`CHECK` 增删是普通迁移可回滚。
3. **不存凭据。** 飞书短期令牌、数据库认证材料、MCP 令牌明文一律不入库（合同明令）。需要长期持有的外部凭据放操作系统级密钥管理，数据库里只存**是否已配置**这类布尔状态。
4. **面向删除设计保留**：九十天是一般内容的最长上限，问数结果正文按 [#163](../决策记录/2026-07-26-问数可信交付与数据保留边界.md) 方案 B 取得前最长 24 小时，取得后随会话保留、由边界事件触发清理。
5. **业务实体不使用外部标识作主键**，内部实体统一用 ULID；`inbound_event.feishu_event_id` 是幂等键例外，直接作为主键。

### 关于表名 `user`

合同要求"建立统一的 `user` 用户表"。`user` 是 PostgreSQL 的保留字（`SELECT user` 返回当前数据库角色），裸用会导致语法错误，加引号则每一处查询都要写 `"user"`。

**取舍：表名用 `app_user`，语义与合同的 `user` 用户表完全一致。**

## 三、身份与权限

本节只记不由 `app_user` 字段名表达的约束（完整字段见[「二、表清单」](#二表清单)）。`drive_folder_token`/`drive_folder_state` 是历史候选字段，#140 前须保持 `NULL`/`none`。`account_state='deleting'` 一经写入即禁止新动作；`deleted` 须清空全部可识别字段。

**五个独立状态字段而不是一个总状态**：合同把"准入""用户环境""多维表格发布""MCP 同步""启停"列为并列信息，要求"从尚未确认完成的步骤安全恢复"，合成一个状态会丢掉"哪几步已完成"。

**`permission_version` 是乐观锁的锚点**：待确认操作在准备时记下它，确认时比对——合同要求"目标状态已经变化时一律不执行"。

**飞书在职状态不落库，每次按需回读**（[两条路径的连接与字段可得性](../参考证据/飞书关联组织两条路径的连接与字段可得性.md)），落成字段会产生陈旧窗口，花名册「账号状态」同理（`V-开通-07`）。`employee_no`/`email` 是匹配时刻的存档，构成每日审计日报比对基线（产品合同：每日比对已开通用户的花名册资料与存档，变化经日报通知）；花名册读取结果另需持久快照，见下节。

**收回用 `revoked_at` 而非物理删除**：合同要求"调岗时只收回明确失效的范围""恢复账号时不自动恢复曾被收回的权限"。后者需要知道"曾被收回"这件事，硬删除会丢失该信息。

`admin_identity` 是"管理 MCP 调用人 = 确认卡接收人 = 当前角色持有人"的锚点，凭据明文不进数据库；无超管时的恢复不进管理 MCP，由 Ops 手工恢复留痕。

**`admin_registry`（S-M-01，Issue #95）是方案 A 私聊命令面当前实际使用的表**，与上面的
`admin_identity`/`admin_role`（管理 MCP 触发式未来入口）是两套独立设计，不是同一张表
的别名：管理 MCP 身份认证与绑定退场后，`admin_registry` 只承接判定所需的最小字段——
飞书 `open_id`、三类角色的授予布尔列（合并授予，不拆逐角色行）、条目状态、时间戳。
判定语义是"默认拒绝 + 实时读表"：网关按发送者 `open_id` 查一次当前是否存在
`entry_status='active'` 的行，查询结果不缓存，条目一旦被改为 `revoked`，下一次请求立即
读到新结果。MVP 唯一初始条目是组织资料同步的专用授权主体账号，由一次性种子命令
（`python -m lingxi.apps.admin_bootstrap`）读取 `feishu_delegated_subject` 登记表播种，
仓库内不出现真实 `open_id`。登记表的授予/撤销写路径（本人确认卡 + 审计）留给 S-M-02
（#96）；本表当前只有种子命令这一个写入口。

### 花名册持久快照

**D2 裁定**（2026-08-08，Issue #52）要求保存**最近一次成功、完整、非空**的花名册读取结果，源头异常一律**保留上一份**。约束：替换只认 `status='COMPLETE'`，不以行非空作判据（`V-花名册-41`）；整体同事务替换（`V-花名册-42`）；`singleton` 保证最多一份（`V-花名册-45`）；行不去重，元信息不含人员资料值（`V-花名册-06`/`46`）。不与 `app_user` 建外键（产品合同「外部平台边界」）。**保留期已裁定**（2026-08-17）：**始终保留最近一份，豁免九十天规则**，超龄不自动删、改按日报告警。

## 四、开通与发布

`publish_outbox` 已落地（Issue #156 S-C-01）。

**outbox 模式**：权限变更与发布意图在同一事务落库，投递异步进行。若直接在权限变更后调飞书 API，调用失败会留下"数据库已改、发布未做"的静默不一致，而合同要求两者不一致时不得视为发布完成（`V-权限-01`）。

关键约束：`token_cipher` 新建必须写、更新不清空不覆盖仅空时补写（`V-权限-11`）；同一用户同时只一条发布在途（`READ COMMITTED` 下未提交认领不可见，`V-权限-12`）；九十天保留由 `content_expires_at` + 应用层擦除落实。`app_user` 没有 `publish_state` 列，进度完整由 `publish_outbox.status` 承载。

`mcp_access_token`/`mcp_sync_check` 已落地（S-C-02）。`mcp_access_token` 只持久化密文：主键即 `user_id`；无明文/指纹列；`BEFORE UPDATE` 让密文改不掉，因此**无轮换路径**；签发幂等。`mcp_sync_check` 改为**探针法**（2026-08-17，权限多维表格无版本字段）：明文令牌执行 `list_metrics`，可见指标条数大于零才算就绪（`V-权限-06`）——**明确空结果只证明查询没报错，不构成权限同步证据**（产品合同「问数 MCP」一节）。`attempt_no` 取 `MAX+1` 避免重启重号。按九十天上限清理。

## 五、会话与任务

三条合同规则由 `conversation` 表直接表达：主窗口与每个话题各自独立 `agent_session_id`；会话延续只读 `last_task_ended_at`；`/new` 置 `agent_session_id = NULL`。

### 同话题串行靠条件更新，不靠唯一索引

每个话题只有一行，冲突在同一行字段覆盖上、不是行的重复上，抢占用条件更新以影响行数判成败：`WHERE running_task_id IS NULL` 抢占，行数 0 即忙碌；`WHERE running_task_id = $task_id` 释放。`UPDATE` 天然行锁串行化。

> 曾写成"由唯一部分索引保证"，是错的：`id` 已是主键，不增加约束。已在 PostgreSQL 16 上实测改正。

忙碌期消息不进 `task` 表（合同：不入历史、不排队）；两表外键均省略以避免环依赖或跨清理链耦合；`feishu_event_id` 单列主键，`received_at` 不进主键以免绕过去重。

### 问数结果投递事件与会话保留 Outbox

字段与语义已冻结（#151，`task_delivery_event`）：`event_type`、按 `task_id` 递增的 `sequence`、唯一 `idempotency_key`、送达确认列、`expires_at` 固定 24 小时不可改。**#151**：Worker 持久化、终态转 `awaiting_delivery` 同事务、24 小时强制收敛。**#152**：Gateway 用 `dispatch_reserved_kind` 预留位防重复投递——拒绝立即清空重试，结果不明转 `uncertain` 人工核对，成功随游标同写入清空。**#178**：系统收口路径此前不写终态，现先写 `started`（`worker_id='system'` 哨兵）再写 `terminal`。**#153**：`agent_session_cleanup` 事务内排队，物理删除延后到 Worker 周期性收口。`inbound_event.onboarding_dispatched_at`（`0062`）让提交后崩溃的孤儿事件可判定，由 Gateway 对账扫描重新交接。

## 六、管理与待确认操作

**"最多成功执行一次"的落地机制**（`0068_pending_action.py`，Issue #96 S-M-02）：`confirm()`/`cancel()` 先 `SELECT ... FOR UPDATE` 锁定待确认操作行（与需要联动改动的目标 `app_user` 行），并发的第二次确认在同一把行锁上排队，等第一次事务提交后读到的就已经是终态——天然收敛为"返回既有结果"，不需要应用层分布式锁，也不依赖单条 `UPDATE` 语句的影响行数。核对通过后先在同一事务内调用注入的审计出口，成功才把目标 `account_state` 与 `pending_action.status` 一并提交；审计出口本身抛异常则整个事务回滚，`pending_action` 停在 `pending`（接口设计错误码 `audit_write_failed`，"调用方可重试"）——`audit_event` 表本身仍是"未建"（全仓审计通道现状是结构化日志，见[代码框架](代码框架.md)），"审计与状态变更同事务"因此落地为"审计调用与状态更新在同一个数据库连接的同一个事务块内顺序发生"，不是字面意义上的另一张表参与同一次提交。`card_delivered=FALSE` 视为作废，与"未找到"在调用方眼里不可区分；`reason`/`result` 须在到期时删除或脱敏。

### 当前运行环境删除编排

确认 `prepare_delete_user` 后按可恢复步骤执行，只处理当前运行库和在线文件：条件更新 `account_state='deleting'` 拒绝新动作 → 停止 Agent 会话、删除家目录 `.mcp.json`（见[架构设计 6.9](架构设计.md)） → 删除或脱敏可识别历史（已交付正式产物按 #140 处置）→ 删除权限与身份映射，写 `deleted`/`erased_at` → 写脱敏审计、`status='completed'`。任一步失败从 `last_completed_step` 恢复。

## 七、正式产物交付（#140 前失败关闭）

`delivery` 表示正式文档、表格、图片或文件的逻辑交付记录，旧版"机器人目录 + `drive_folder_token`"DDL 已被否定，**不再是可实施蓝本**。#140 须据 #97 证据选择责任主体、承载模型、访问与处置、保留清理，再以前滚迁移冻结字段。数据库须分别约束：归属（`idempotency_key` 唯一）、外部创建（响应不明进 `uncertain`）、所有权（真实回读）、访问（授权与可访问性分别回读）、发送（`platform_received` ≠ `user_read`）、生命周期与运行侧保留（最长九十天）。

#140 尚未批准前，端点不创建外部目录或文件，只留失败关闭事实。普通问数正文使用[第五节](#五会话与任务)的会话保留 Outbox，不进入本节 `delivery`。

## 八、审计与聊天记录

`audit_event` **append-only 的双重保证**：权限收紧（`REVOKE UPDATE, DELETE ... FROM lingxi_app`）防误操作，触发器（只放行 `lingxi_retention_owner` 对已到期行的 `DELETE`）防误授权；分区表的行级触发器传播到各分区。清理由 `lingxi_retention_owner` 执行，只拥有目标表 `SELECT`/`DELETE`，无写权限；`lingxi_app` 不能 `SET ROLE` 到该角色。

字段对应合同要求的审计内容：管理员身份、当时角色、所用管理入口、目标对象、动作类型、操作前状态、拟执行影响、确认或取消、操作后状态、结果与时间。

`chat_message` 与 `audit_event` 分开：合同对两者授权口径不同——**完整聊天与敏感业务内容只在获得相应授权后才可复核**，分表让这条边界成为一次 `GRANT` 就能表达的权限。

`content` 存原始内容不脱敏——合同要求"公司内部审计可以在九十天内审计完整聊天记录、完整业务内容及其中的敏感内容"，脱敏会让这条不成立。脱敏只发生在 `audit_event.detail`。

**开通前发送的内容不入库**：合同要求"不执行、不保存、不回显"。gateway 在识别出未开通用户后，只写 `inbound_event`（记录收到过一个事件及处理方式）与审计，**不写 `chat_message`**。

## 九、保留与删除

九十天是**可识别内容的最长上限**，不是"至少保留九十天"。`BEFORE INSERT` 触发器按内容类别写入适用期限：一般内容固定加 2160 小时；问数结果正文（`result_delivery`）固定加 24 小时、**不写九十天上限**——只在送达前有效，取得 `platform_received` 后转为随会话保留，`BEFORE UPDATE` 触发器拒绝把到期时间后移。scheduler 至少每小时清理。超过 `expires_at` 仍可识别用户或原文属保留违规，须告警并阻止作为发布候选。

### 正常运行内容载体的到期路径

| 数据对象 | 最长期限与处理 |
|---|---|
| `chat_message.content`（`general`） | `occurred_at + 90 days` 前删除整行 |
| `chat_message.content`/`task_delivery_event.content`（`result_delivery`） | 送达前 24 小时到期删除；已送达改由会话边界事件触发删除，低敏事实留九十天 |
| `audit_event`、`inbound_event` | +90 days 前删除；审计需保留时先不可逆移除用户与内容 |
| `task.prompt`、`manual_review.detail`、`pending_action`、`publish_outbox.payload`、`mcp_sync_check` | +90 days 前清空或删除 |
| Agent SDK 会话 JSONL | 到期前不再 `resume`，启动新会话并删除旧 JSONL |
| `mcp_access_token.token_cipher` | 当前状态，不按九十天删除 |
| 正式产物运行侧引用、用户工作目录中间文件 | 前者 90 天前删除（见[第七节](#七正式产物交付140-前失败关闭)）；后者按最短必要时间清理 |
| `innertest_content_capture`（问题/回答/工具调用原文） | `created_at + 90 days` 触发器兜底上限；轮次结束由运维显式清空（远早于 90 天，见下）——见「内测轮内容级采集」小节 |

数据库备份、WAL 归档、用户目录备份是明确例外：用于故障恢复，不受九十天或删除操作影响，落点按[第十二节](#十二未定项)确定。

### 内测轮内容级采集

`innertest_content_capture`（#251/#304 批次 3）是内测轮观察—修复循环用的**临时、
默认关闭**采集表，与本节其余长期保留、正式服务用途的对象性质不同，单列一节
避免混进上表的语义。

- **默认关闭，只在 stage**：`apps/worker/config.py` 的 `LINGXI_INNERTEST_CONTENT_CAPTURE`
  与第二确认变量 `LINGXI_INNERTEST_CONTENT_CAPTURE_ENVIRONMENT_CONFIRM` 须同时精确
  匹配才生效；正式环境即使误配了主开关，缺第二确认变量的精确字面量仍不生效——
  结构性保证的选型理由、已知残余风险见迁移 `0069_innertest_content_capture.py`
  文件头与 `apps/worker/config.py` 的 `_innertest_content_capture` 模块内文档。
- **口径**：产品负责人 2026-08-24 裁定全量开启，用户问题、模型回答、工具调用
  详情原文与结果正文不设限；结构约束不变——凭据类一律排除（写入前过滤，命中
  即占位符替换并计数），仅受控查询（不建面向使用者的查询界面），进库不进群
  （不触碰通报/群通道）。
- **保留**：`BEFORE INSERT/UPDATE` 触发器把 `expires_at` 固定为 `created_at + 90
  天`，与本节其余对象同一上限，但这是**结构性最长上限**，不是"内测轮期间就
  保留这么久"。「轮次结束即清」由运维在轮次结束时显式执行迁移文件头登记的受控
  SQL（`DELETE ... WHERE created_at >= ... AND created_at < ...` 或
  `TRUNCATE innertest_content_capture`），不依赖新增的定时清理职责——判断"轮次
  何时结束"是产品/运营决定，不是可由程序推导的时间点。

## 十、权限与加固

五个数据库角色，最小权限：`lingxi_app`（业务表最小读写，`audit_event`/`chat_message` 只 `INSERT`，`inbound_event` 另有两列 `UPDATE`，不能执行清理函数）、`lingxi_scheduler`（可执行受限清理函数但不能直接 `DELETE`/`SET ROLE`）、`lingxi_migrate`（DDL，仅迁移用）、`lingxi_retention_owner`（无登录，持有清理函数及目标表 `SELECT`/`DELETE`）、`lingxi_audit_ro`（`audit_event` 只读，**不含 `chat_message`**）。

`inbound_event` 两列 `UPDATE`（#206）：`handled_as`（幂等去重先插入抢占，同事务回写结论）、`onboarding_dispatched_at`（`0062` 交接账本，`FOR UPDATE SKIP LOCKED` 防重复交接）。

**此行只描述目标权限面，尚未落到数据库**：运行时进程尚未以四个限权角色连库——[当前能力](../当前能力.md)已披露的既有缺口。**不启用 RLS**：单租户、应用层已按 `user_id` 过滤；多租户场景再评估，见[未定项](#十二未定项)。

## 十一、迁移约定

工具：Alembic。约定：

1. **每个迁移必须可前滚。** 破坏性变更（删列、改类型、加非空约束）拆成两次发布：先加新结构并双写，确认无误后再删旧结构。理由是[架构设计](架构设计.md)里的回滚策略是"切镜像 tag 重启"——旧镜像必须仍能在新库上工作。
2. **`CREATE INDEX CONCURRENTLY`** 用于生产上的索引新增，避免长时间持锁。
3. **按月分区预建和空分区删除**由迁移或受控 Ops 维护任务执行，不向 scheduler 授予 DDL；精确到期清理由 scheduler 至少每小时调用受限函数执行。
4. **不在迁移里写业务数据。** 种子数据（如首位超级管理员）用单独的、可重复执行的引导脚本，避免迁移历史与数据状态耦合。
