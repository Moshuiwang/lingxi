## 一、设计原则

1. **合同里的硬约束尽量落到数据库约束上。** "同一话题同时只跑一个任务""同一待确认操作最多成功执行一次""不得移除最后一名超级管理员"——这些用唯一索引、部分索引和检查约束表达，而不是靠应用代码自觉。约束写在数据库里，任何代理写的任何代码路径都绕不过去。
2. **状态用 `TEXT` + `CHECK` 而非原生 `ENUM`。** 状态机会随实现演进；`CHECK` 的增删是一次普通迁移，`ALTER TYPE ... DROP VALUE` 则做不到。代价是少一点类型强度，换来的是可回滚。
3. **不存凭据。** 飞书短期令牌、数据库认证材料、MCP 令牌明文一律不入库（合同明令）。需要长期持有的外部凭据放操作系统级密钥管理，数据库里只存**是否已配置**这类布尔状态。
4. **面向删除设计保留。** 九十天保留期靠按月分区 + 整分区删除实现，而不是大批量 `DELETE`——后者在保留期到来时会长时间持锁。
5. **外部标识不做主键。** 飞书 `open_id` 等属于外部系统，语义可能变化；内部主键统一用 ULID。

### 关于表名 `user`

合同要求"建立统一的 `user` 用户表"。`user` 是 PostgreSQL 的保留字（`SELECT user` 返回当前数据库角色），裸用会导致语法错误，加引号则每一处查询都要写 `"user"`。

**取舍：表名用 `app_user`，语义与合同的 `user` 用户表完全一致。** 这是命名层面的适配，不改变"以一条用户记录关联飞书信息、权限信息、Lingxi 信息"这条规则。

## 三、身份与权限

```sql
CREATE TABLE app_user (
    id                      TEXT PRIMARY KEY,              -- ULID, usr_*

    -- 飞书信息
    feishu_open_id          TEXT UNIQUE NOT NULL,
    feishu_user_id          TEXT,
    feishu_union_id         TEXT,
    display_name            TEXT NOT NULL,                 -- name.default_value
    display_name_locale     TEXT,                          -- 来源租户的语言，影响姓名匹配可用性
    department              TEXT,                          -- 可得性尚未逐项确认
    tenant_key              TEXT,
    drive_folder_token      TEXT,                          -- 专属云盘目录
    drive_folder_state      TEXT NOT NULL DEFAULT 'none'
        CHECK (drive_folder_state IN ('none','creating','ready','failed')),

    -- 权限信息
    permission_record_id    TEXT,                          -- 匹配到的数据库权限记录
    permission_version      BIGINT NOT NULL DEFAULT 0,     -- 每次权限变更 +1，用于乐观锁
    permission_checked_at   TIMESTAMPTZ,

    -- Lingxi 信息
    provisioning_state      TEXT NOT NULL DEFAULT 'guest'
        CHECK (provisioning_state IN (
            'guest',            -- 未开通
            'authorizing',      -- 等待飞书授权
            'matching',         -- 姓名匹配中
            'manual_review',    -- 转人工核对
            'provisioning',     -- 环境 / 目录 / 发布进行中
            'mcp_syncing',      -- 权限正在同步（15 分钟窗口）
            'active',           -- 开通成功
            'aborted'           -- 终止开通
        )),
    workspace_state         TEXT NOT NULL DEFAULT 'none'
        CHECK (workspace_state IN ('none','creating','ready','failed')),
    posix_uid               INTEGER UNIQUE,                -- 用户环境的宿主机 uid，交付接口据此认定归属
    publish_state           TEXT NOT NULL DEFAULT 'none'
        CHECK (publish_state IN ('none','pending','published','failed')),
    mcp_sync_state          TEXT NOT NULL DEFAULT 'none'
        CHECK (mcp_sync_state IN ('none','checking','confirmed','timeout')),
    account_state           TEXT NOT NULL DEFAULT 'enabled'
        CHECK (account_state IN ('enabled','suspended','deleted')),
    workbench_granted       BOOLEAN NOT NULL DEFAULT FALSE, -- 高级工作台，链路外审批

    created_at              TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at              TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX ON app_user (provisioning_state) WHERE provisioning_state <> 'active';
CREATE INDEX ON app_user (display_name);
```

**五个独立状态字段而不是一个总状态**：合同把"准入""用户环境""多维表格发布""MCP 同步""启停"列为并列的五类信息，且恢复规则是"从尚未确认完成的步骤安全恢复，不重跑整个流程"。合成一个状态会丢掉"哪几步已完成"，让安全恢复无从判断。

**`permission_version` 是乐观锁的锚点**：待确认操作在准备时记下它，确认时比对——合同要求"目标状态已经变化时一律不执行"。

```sql
CREATE TABLE user_permission_scope (
    id            BIGSERIAL PRIMARY KEY,
    user_id       TEXT NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    company       TEXT NOT NULL,
    function      TEXT NOT NULL,
    granted_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_at    TIMESTAMPTZ,                              -- 软删除，保留调岗轨迹
    UNIQUE (user_id, company, function, granted_at)
);

CREATE INDEX ON user_permission_scope (user_id) WHERE revoked_at IS NULL;
```

**收回用 `revoked_at` 而非物理删除**：合同要求"调岗时只收回明确失效的范围""恢复账号时不自动恢复曾被收回的权限"。后者需要知道"曾被收回"这件事，硬删除会丢失该信息。

```sql
CREATE TABLE admin_role (
    id          BIGSERIAL PRIMARY KEY,
    user_id     TEXT NOT NULL REFERENCES app_user(id),
    role        TEXT NOT NULL CHECK (role IN ('permission_admin','ops_admin','super_admin')),
    granted_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    granted_by  TEXT REFERENCES app_user(id),
    revoked_at  TIMESTAMPTZ
);

-- 同一人同一角色同时只能有一条有效记录
CREATE UNIQUE INDEX admin_role_active_uniq
    ON admin_role (user_id, role) WHERE revoked_at IS NULL;
```

**"不得移除最后一名超级管理员"**放在数据库里，因为它是**安全属性**——不能只靠管理 MCP 的应用判断，未来增加任何入口时约束都要继续成立：

```sql
CREATE FUNCTION keep_last_super_admin() RETURNS TRIGGER AS $$
BEGIN
    IF OLD.role = 'super_admin' AND OLD.revoked_at IS NULL AND NEW.revoked_at IS NOT NULL THEN
        IF (SELECT count(*) FROM admin_role
             WHERE role = 'super_admin' AND revoked_at IS NULL AND id <> OLD.id) = 0 THEN
            RAISE EXCEPTION '不能移除最后一名超级管理员';
        END IF;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER admin_role_keep_last_super
    BEFORE UPDATE ON admin_role
    FOR EACH ROW EXECUTE FUNCTION keep_last_super_admin();
```

```sql
CREATE TABLE manual_review (
    id             TEXT PRIMARY KEY,                        -- rev_*
    user_id        TEXT NOT NULL REFERENCES app_user(id),
    reason         TEXT NOT NULL
        CHECK (reason IN ('duplicate_name','incomplete_record','state_unknown',
                          'workspace_error','publish_error','mcp_sync_timeout')),
    detail         JSONB NOT NULL DEFAULT '{}'::jsonb,      -- 脱敏摘要
    status         TEXT NOT NULL DEFAULT 'open'
        CHECK (status IN ('open','resolved','aborted')),
    opened_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    resolved_at    TIMESTAMPTZ,
    resolved_by    TEXT REFERENCES app_user(id)
);

CREATE INDEX ON manual_review (status, opened_at) WHERE status = 'open';
```

合同规定"一个工作日内至少给用户一次进展"由**管理员人工守护**，Lingxi 不建认领、倒计时、逾期升级机制。因此这张表**没有** `due_at`、`assignee`、`escalated_at` 字段——刻意不建，避免把低频异常处理扩成一套任务管理系统。

## 四、开通与发布

```sql
CREATE TABLE publish_outbox (
    id              BIGSERIAL PRIMARY KEY,
    user_id         TEXT NOT NULL REFERENCES app_user(id),
    permission_version BIGINT NOT NULL,                     -- 发布的是哪一版
    payload         JSONB NOT NULL,                         -- 待写入多维表格的内容快照
    status          TEXT NOT NULL DEFAULT 'pending'
        CHECK (status IN ('pending','publishing','published','failed')),
    attempts        INT NOT NULL DEFAULT 0,
    last_error      TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at    TIMESTAMPTZ
);

CREATE INDEX ON publish_outbox (status, created_at) WHERE status IN ('pending','failed');
```

**outbox 模式**：权限变更与发布意图在同一事务落库，投递异步进行。若直接在权限变更后调飞书 API，调用失败会留下"数据库已改、发布未做"的静默不一致，而合同要求两者不一致时不得视为发布完成。

`payload` 存内容快照而非引用，让重试时发布的一定是当初决定发布的那一版，不会被后续变更污染。

```sql
CREATE TABLE mcp_sync_check (
    id            BIGSERIAL PRIMARY KEY,
    user_id       TEXT NOT NULL REFERENCES app_user(id),
    permission_version BIGINT NOT NULL,
    attempt_no    INT NOT NULL,
    started_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at   TIMESTAMPTZ,
    result        TEXT CHECK (result IN ('confirmed','not_ready','error')),
    detail        TEXT,
    UNIQUE (user_id, permission_version, attempt_no)
);
```

每次尝试独立成行，不是覆盖一个字段。原因：合同把"十五分钟"定成硬上限，而这条时限依据的外部能力**尚未验证**。逐次记录才能在真实数据上回答"十五分钟是不是一个现实的上限"，作为复审该规则的输入。

## 五、会话与任务

```sql
CREATE TABLE conversation (
    id                 TEXT PRIMARY KEY,                    -- cnv_*
    user_id            TEXT NOT NULL REFERENCES app_user(id),
    feishu_chat_id     TEXT NOT NULL,
    feishu_thread_id   TEXT,                                -- NULL 表示私聊主窗口
    agent_session_id   TEXT,                                -- Agent SDK 会话；NULL = 下次不 resume
    last_task_ended_at TIMESTAMPTZ,                         -- 两小时规则的唯一依据
    running_task_id    TEXT,                                -- 同话题串行
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 私聊主窗口与每个话题各自独立
CREATE UNIQUE INDEX conversation_scope_uniq
    ON conversation (user_id, feishu_chat_id, COALESCE(feishu_thread_id, ''));
```

三条合同规则直接由这张表表达：

| 规则 | 字段 |
|---|---|
| 主窗口与每个话题是独立对话、互不共享上下文 | 每个 `conversation` 独立 `agent_session_id` |
| 会话延续按"上一条任务结束到下一条新任务开始"判断，任务执行时长本身不触发新会话 | 只读 `last_task_ended_at`，不涉及任务开始时间或时长 |
| `/new` 清空当前对话上下文，其他话题不受影响 | 置 `agent_session_id = NULL` |

### 同话题串行靠条件更新，不靠唯一索引

每个话题在 `conversation` 里只有一行，因此**没有可以用唯一索引表达的"同时两个运行中任务"状态**——冲突发生在同一行的字段覆盖上，不是行的重复上。抢占必须用条件更新，以影响行数判断成败：

```sql
-- 抢占：只有当前空闲才能占用
UPDATE conversation SET running_task_id = $task_id
 WHERE id = $conv_id AND running_task_id IS NULL;
-- 影响行数 0 → 话题忙碌，回复"当前任务仍在处理中"

-- 释放：只有持有者能释放，防止被别的任务误清
UPDATE conversation SET running_task_id = NULL, last_task_ended_at = now()
 WHERE id = $conv_id AND running_task_id = $task_id;
```

`UPDATE` 在 PostgreSQL 的默认隔离级别下会对目标行加行锁，并发抢占天然串行化，不需要额外的咨询锁。

> 这条曾经写成"由 `conversation (id) WHERE running_task_id IS NOT NULL` 的唯一部分索引保证"，是错的：`id` 已经是主键，该索引不增加任何约束，第二个任务会直接覆盖第一个。已在 PostgreSQL 16 上实测确认并改正。

```sql
CREATE TABLE task (
    id               TEXT PRIMARY KEY,                      -- tsk_*
    conversation_id  TEXT NOT NULL REFERENCES conversation(id),
    user_id          TEXT NOT NULL REFERENCES app_user(id),
    inbound_event_id TEXT NOT NULL,                         -- 溯源到飞书事件
    prompt           TEXT NOT NULL,
    status           TEXT NOT NULL DEFAULT 'queued'
        CHECK (status IN ('queued','running','succeeded','failed','stopped')),
    resumed_session  BOOLEAN NOT NULL DEFAULT FALSE,        -- 是否续用旧会话
    card_id          TEXT,
    card_seq         INT NOT NULL DEFAULT 0,                -- 流式卡片序列号，严格递增
    fallback_text    BOOLEAN NOT NULL DEFAULT FALSE,        -- 是否已降级为文本兜底
    worker_id        TEXT,
    heartbeat_at     TIMESTAMPTZ,
    attempts         INT NOT NULL DEFAULT 0,
    scheduled_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    started_at       TIMESTAMPTZ,
    ended_at         TIMESTAMPTZ,
    stop_requested   BOOLEAN NOT NULL DEFAULT FALSE,        -- /stop
    error_kind       TEXT,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX task_queue_idx ON task (scheduled_at) WHERE status = 'queued';
CREATE INDEX task_stale_idx ON task (heartbeat_at) WHERE status = 'running';
CREATE INDEX ON task (conversation_id, created_at DESC);
```

- `task_queue_idx` 是部分索引，只覆盖 `queued` 行——队列表的常见陷阱是全表索引随历史增长而退化，部分索引让索引大小只与积压量相关。
- `task_stale_idx` 支持 scheduler 回收心跳超时的 `running` 任务。
- **忙碌期收到的消息不进这张表**（合同：不入历史、不排队），只记 `chat_message` 与审计。

```sql
CREATE TABLE inbound_event (
    feishu_event_id  TEXT        NOT NULL,
    received_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    event_type       TEXT        NOT NULL,
    user_open_id     TEXT,
    handled_as       TEXT,        -- task_queued / busy_hint / guest_card / command / dropped
    trace_id         TEXT        NOT NULL,
    PRIMARY KEY (feishu_event_id, received_at)
) PARTITION BY RANGE (received_at);
```

主键即幂等键——飞书重投时插入冲突，gateway 直接返回成功。分区键必须进主键，这是 PostgreSQL 分区表的要求。

## 六、管理与待确认操作

```sql
CREATE TABLE pending_action (
    id                  TEXT PRIMARY KEY,                   -- pac_*
    action_type         TEXT NOT NULL,
    initiated_by        TEXT NOT NULL REFERENCES app_user(id),
    initiator_role      TEXT NOT NULL,                      -- 发起时的角色，审计用
    target_user_id      TEXT REFERENCES app_user(id),
    target_version      BIGINT,                             -- 准备时的 permission_version
    params              JSONB NOT NULL,
    effect_summary      JSONB NOT NULL,                     -- 卡片展示的影响说明
    reason              TEXT NOT NULL,

    status              TEXT NOT NULL DEFAULT 'pending'
        CHECK (status IN ('pending','executing','executed','cancelled','expired','failed')),
    card_message_id     TEXT,
    card_delivered      BOOLEAN NOT NULL DEFAULT FALSE,

    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at          TIMESTAMPTZ NOT NULL,
    confirmed_at        TIMESTAMPTZ,
    confirmed_by        TEXT REFERENCES app_user(id),
    executed_at         TIMESTAMPTZ,
    result              JSONB
);

CREATE INDEX ON pending_action (status, expires_at) WHERE status = 'pending';
CREATE INDEX ON pending_action (initiated_by, created_at DESC);
```

**"最多成功执行一次"由条件更新的影响行数保证**：

```sql
UPDATE pending_action
   SET status = 'executing', confirmed_by = $clicker, confirmed_at = now()
 WHERE id = $action_id
   AND status = 'pending'                    -- 未执行过
   AND expires_at > now()                    -- 未过期
   AND initiated_by = $clicker               -- 只有发起人本人
 RETURNING *;
```

影响行数为 0 即不执行。重复点击、重复回调、多个 Agent 重复提交都会落到 0 行，返回既有结果——不需要额外的分布式锁。

随后在**同一个事务**内：写 `audit_event` → 改业务状态 → `status='executed'`。任一步失败整体回滚，用户状态不变，直接满足合同的"审计无法写入时一律不执行"。

`card_delivered = FALSE` 的操作视为作废（合同："卡片发送失败时本次操作不执行"）。

## 七、交付

```sql
CREATE TABLE delivery (
    id                TEXT PRIMARY KEY,                     -- dlv_*
    idempotency_key   TEXT UNIQUE NOT NULL,
    user_id           TEXT NOT NULL REFERENCES app_user(id),
    task_id           TEXT REFERENCES task(id),             -- 高级工作台交付时为 NULL
    channel           TEXT NOT NULL CHECK (channel IN ('feishu','workbench')),
    kind              TEXT NOT NULL CHECK (kind IN ('doc','sheet','image','file')),
    title             TEXT,
    feishu_token      TEXT,                                 -- 文档 / 表格 token
    url               TEXT,
    authorized        BOOLEAN NOT NULL DEFAULT FALSE,       -- 授权确认成功才算交付完成
    status            TEXT NOT NULL DEFAULT 'creating'
        CHECK (status IN ('creating','created','authorized','sent','uncertain','failed')),
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    completed_at      TIMESTAMPTZ
);

CREATE INDEX ON delivery (user_id, created_at DESC);
```

`authorized` 与 `status` 分开的原因：合同规定"仅生成链接而未确认授权成功的产物不算交付"。`created` 与 `authorized` 必须是可区分的两个事实，否则无法在事后判断某次交付是否真的完成。

`status='uncertain'` 是合同要求的独立终态——送达状态不确定时明确说明并要求核对，**不自动重发**。`idempotency_key` 唯一索引兜住重复调用。

`channel` 区分飞书与高级工作台，用于验收时确认两条路径产出一致；两者写入的是**同一个** `drive_folder_token`。

## 八、审计与聊天记录

```sql
CREATE TABLE audit_event (
    id            TEXT        NOT NULL,                     -- ULID
    occurred_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    event_type    TEXT        NOT NULL,
    actor_kind    TEXT        NOT NULL
        CHECK (actor_kind IN ('user','admin','system','agent')),
    actor_id      TEXT,
    actor_role    TEXT,                                     -- 管理动作记录当时角色
    entry_point   TEXT,                                     -- feishu / admin_mcp / workbench / scheduler
    target_kind   TEXT,
    target_id     TEXT,
    conversation_id TEXT,
    task_id       TEXT,
    permission_version BIGINT,
    state_before  JSONB,
    state_after   JSONB,
    detail        JSONB NOT NULL DEFAULT '{}'::jsonb,       -- 已脱敏
    trace_id      TEXT,
    PRIMARY KEY (id, occurred_at)
) PARTITION BY RANGE (occurred_at);

CREATE INDEX ON audit_event (occurred_at DESC);
CREATE INDEX ON audit_event (target_id, occurred_at DESC);
CREATE INDEX ON audit_event (actor_id, occurred_at DESC);
CREATE INDEX ON audit_event USING GIN (detail);
```

字段对应合同要求的审计内容：管理员身份、当时角色、所用管理入口、目标对象、动作类型、操作前状态、拟执行影响、确认或取消、操作后状态、结果与时间。

**append-only 的双重保证**：

```sql
CREATE FUNCTION audit_immutable() RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'audit_event 是只追加表，不允许 % 操作', TG_OP;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_event_no_mutate
    BEFORE UPDATE OR DELETE ON audit_event
    FOR EACH ROW EXECUTE FUNCTION audit_immutable();

REVOKE UPDATE, DELETE ON audit_event FROM lingxi_app;
```

权限收紧防误操作，触发器防误授权。分区表上的行级触发器会传播到各分区（PostgreSQL 13+）。**保留期删除通过 `DROP TABLE <分区>` 完成，绕过行级触发器**——这是刻意的：整分区删除是运维动作，逐行删除是篡改。

```sql
CREATE TABLE chat_message (
    id             TEXT        NOT NULL,
    occurred_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    user_id        TEXT        NOT NULL,
    conversation_id TEXT,
    task_id        TEXT,
    direction      TEXT        NOT NULL CHECK (direction IN ('inbound','outbound')),
    content        TEXT        NOT NULL,                    -- 原始内容，审计可复核
    content_kind   TEXT        NOT NULL
        CHECK (content_kind IN ('text','card','file_ref','system_notice')),
    trace_id       TEXT,
    PRIMARY KEY (id, occurred_at)
) PARTITION BY RANGE (occurred_at);

CREATE INDEX ON chat_message (user_id, occurred_at DESC);
CREATE INDEX ON chat_message (conversation_id, occurred_at);
```

与 `audit_event` 分开的原因：合同对两者的授权口径不同。审计事实用于日常排查与治理；**完整聊天与敏感业务内容只在获得相应授权后才可复核**。分表让"给治理系统只读审计、不给聊天内容"成为一次 `GRANT` 就能表达的边界。

`content` 存原始内容不脱敏——合同要求"公司内部审计可以在九十天内审计完整聊天记录、完整业务内容及其中的敏感内容"，脱敏会让这条不成立。脱敏只发生在 `audit_event.detail`。

**开通前发送的内容不入库**：合同要求"不执行、不保存、不回显"。gateway 在识别出未开通用户后，只写 `inbound_event`（记录收到过一个事件及处理方式）与审计，**不写 `chat_message`**。

## 九、保留与删除

统一九十天（合同）。实现方式：

```sql
-- scheduler 每日执行
-- 1. 预建下个月分区（提前建，避免月初写入失败）
-- 2. 删除上界早于 now() - 90 天的分区
DROP TABLE IF EXISTS audit_event_2026_03;
DROP TABLE IF EXISTS chat_message_2026_03;
DROP TABLE IF EXISTS inbound_event_2026_03;
```

按月分区意味着实际保留 90–120 天（最后一个分区要整体过期才删）。这在合同的"统一保留九十天，到期后删除或脱敏"范围内，且换来了 O(1) 的删除代价。若需要精确到日，改为按日分区——代价是分区数从个位数升到上百，查询规划开销上升。**按月是当前规模下的正确档位。**

不参与保留期删除的：

| 数据 | 原因 |
|---|---|
| `app_user`、`user_permission_scope`、`admin_role` | 是当前状态而非历史记录 |
| 已交付到用户专属云盘目录的文档与表格 | 合同：用户取得的正式产物，由用户按飞书和公司规则管理 |
| `delivery` 记录本身 | 交付事实属于审计范畴，随分区策略另行评估 |

**中间文件及时清理**：用户环境工作目录内的临时文件由任务结束时清理，不进数据库。

## 十、权限与加固

三个数据库角色，最小权限：

| 角色 | 权限 |
|---|---|
| `lingxi_app` | 业务表读写；`audit_event` / `chat_message` / `inbound_event` **只 `INSERT`** |
| `lingxi_migrate` | DDL；仅迁移时使用，不用于运行时连接 |
| `lingxi_audit_ro` | `audit_event` 只读；**不含 `chat_message`** —— 治理系统接入用 |

`lingxi_audit_ro` 单独存在，是为了让"独立治理能力可接收审计事实、但不接管主链路、不读完整聊天内容"这条合同边界成为数据库权限而非应用约定。

**不启用行级安全（RLS）**：单租户、应用层已按 `user_id` 过滤，RLS 在此规模下增加的是调试难度而非安全性。若未来出现多租户或直连数据库的分析场景，再评估——写入[复审条件](#十二未定项)。

## 十一、迁移约定

工具：Alembic。约定：

1. **每个迁移必须可前滚。** 破坏性变更（删列、改类型、加非空约束）拆成两次发布：先加新结构并双写，确认无误后再删旧结构。理由是[架构设计](架构设计.md)里的回滚策略是"切镜像 tag 重启"——旧镜像必须仍能在新库上工作。
2. **`CREATE INDEX CONCURRENTLY`** 用于生产上的索引新增，避免长时间持锁。
3. **分区预建**属于运维任务而非迁移，由 scheduler 每日执行。
4. **不在迁移里写业务数据。** 种子数据（如首位超级管理员）用单独的、可重复执行的引导脚本，避免迁移历史与数据状态耦合。
