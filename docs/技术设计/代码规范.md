# 代码规范

> 本文回答"一段代码/注释写成什么样才算合规"；`代码框架.md` 回答"放在哪里、模块间守什么规则"。两处冲突时以本文为准并回去修正代码框架。规则由 `pyproject.toml` 的 `[tool.ruff]` 与三条棘轮脚本（见第三节）强制，不是散文倡议。

## 一、规范基准与本仓库口径

| 维度 | 口径 |
| --- | --- |
| 基准 | PEP 8（风格）、PEP 257（docstring）、Google Python Style Guide（docstring 结构） |
| 函数长度 | 目标 40 行、硬限 60 行（`check_function_size_ratchet.py`，只对 `src/lingxi/` 生效） |
| docstring 结构 | ruff `D`（google 约定：摘要行＋空行＋正文；`Args`/`Returns`/`Raises` 按签名自明程度取舍），忽略 `D400`/`D415`（摘要行必须以英文标点收尾，与中文写作习惯冲突，不采纳） |
| 注释与 docstring 内容 | 只写约束与理由（"为什么"），不写 Issue 号／日期／审查人／修复包等来历（去处见第二节） |
| 长度上限 | 模块 docstring ≤ 15 行、类/函数 docstring ≤ 10 行、连续 `#` 注释块 ≤ 5 行（`check_comment_ratchet.py`） |
| 行宽 | 100 列（`ruff format`／`ruff check` 的 `line-length`） |
| import | 顶部按 isort 规则排序；`src/lingxi/` 无模块级第三方 SDK import，一律函数内延迟导入（代码框架六） |
| 异常类命名 | 以 `Error` 结尾（ruff `N818`；存量违规见 per-file-ignores，本批不改名） |
| 自然语言 | 中文 |
| 抑制注释 | `src/lingxi/` 内一切形态（含限定到具体规则码的 `# noqa: CODE`）一律不允许；唯一合法豁免入口是 `pyproject.toml` 的 `per-file-ignores` |
| `D` 强制范围 | `src/lingxi/`；`tests/`／`migrations/`／`scripts/` 三个目录整体豁免（决策清单 D-21：测试不做注释清理、迁移是生成文件、脚本不在结构性拆分范围） |

## 二、"为什么"的去处

代码里删掉的不是内容，是**放错了地方的内容**——下表是它们该去的地方。

| 这类信息 | 去处 |
| --- | --- |
| 约束与不变量本身（"这里必须……否则……"） | docstring 摘要后一两句 |
| 设计选择的取舍论证（"为什么选 A 不选 B"） | 模块 docstring 一段，或 `docs/决策记录/` 的独立记录 |
| 来历：审查过程、修复包、Issue/PR 编号、日期、裁定人 | commit message 与 PR 正文——git 历史本身就是来历的权威记录，不需要在代码里再抄一份，抄了也会随时间腐烂（PR 关了、Issue 改了描述） |
| 论证细节（"为什么这个分支必须这样处理"） | 测试用例名与测试 docstring——一条命中该分支的测试比一段散文更能证明论证成立 |

三条棘轮（函数体量、文件体量、注释卫生）合力把"论证搬进测试、来历搬进 git 历史"变成会变红的门禁，不是靠自觉。

## 三、门禁与读数

强制这些规则的是四样东西：`ruff check`/`ruff format`（`pyproject.toml`）、`scripts/ci/check_size_ratchet.py`（文件体量）、`scripts/ci/check_function_size_ratchet.py`（函数体量）、`scripts/ci/check_comment_ratchet.py`（注释卫生）。只读、不进门禁的体检工具是 `scripts/dev/readability_report.py`——用于批次前后对照，不影响 CI 结论。

三条棘轮已知边界（不构成绕过许可，只是如实登记）：同一提交同步改基线与净增内容可绕过精确相等判定；函数体内非首句的裸字符串语句、装饰器行、`lambda` 不计入统计；连续 `#` 注释块以空行断开按独立块计数。
