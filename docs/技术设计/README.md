# 技术设计

本目录记录 Lingxi 的实现方案：架构如何组织、接口长什么样、数据怎么存。

## 与产品合同的分工

| | 产品合同 | 技术设计 |
|---|---|---|
| 回答 | 用户体验是什么、边界在哪、承诺什么 | 用什么架构、接口、数据结构实现它 |
| 变更触发 | 产品承诺或边界改变 | 实现方案改变 |
| 冲突时 | **以产品合同为准** | 按合同修正设计 |

技术设计**不重复合同正文**。需要引用某条规则时给出链接和章节名，不复制条文——同一段规则维护在两处，迟早会改一处漏一处。

技术设计也**不是能力证明**。文档写完不代表能力可用；实际可用能力以[当前能力](../当前能力.md)为准。

前三份共享同一组[约束前提](架构设计.md#一约束前提)。**前提变化时一起复审**，不要只改其中一份。

[验证与门禁](验证与门禁.md)定义“什么证据够用、走哪道关口”；[产品验收矩阵](验收矩阵.md)登记“具体判定哪一条”。规划者按 GitHub [#147](https://github.com/Moshuiwang/lingxi/issues/147) 生成或修订具体 `[tracking]` Execution Trace；实际角色、状态、冻结与修复合同写在获批 Trace 中。Trace 缺项时退回规划者修订，编排者不从 #147 或技术切片文档补合同。新增机制时只按需补充相关断言，不把整份矩阵复制回门禁正文。

## 状态

各文件状态以文件开头为准；[验证与门禁](验证与门禁.md)与[产品验收矩阵](验收矩阵.md)共同构成现行技术验收入口，其余设计仍可处于草案或分 Story 实现中。设计完成、代码存在或门禁通过都不等于用户能力已经可用；实际能力和未验证外部依赖统一看[当前能力](../当前能力.md)。
