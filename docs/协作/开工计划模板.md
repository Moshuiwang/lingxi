# 开工计划模板

> 状态：现行模板。仅在[协作约定](../协作约定.md#变更-issue-与-to-pm)规定的批次条件成立时读取和使用。

本文件是 `[tracking]` 开工计划模板的权威正文。规划者完成与产品负责人的确认后，用本模板创建批次计划；编排者应当能够在没有旧会话的情况下，仅凭开工计划和其中链接的工作 Issue 接手执行。单一低风险工作不使用本模板。

## 给人类

> **仅供人类快速阅读。** 本节是摘要，不是代理可以忽略用户目标的理由；同样的用户结果和人类介入事项必须写入下方“任务与授权”，供所有角色读取。

- **本批次得到什么**：{{一句话}}
- **仍需人类介入**：{{无 / 决策、授权、凭据、人工验收}}

## 给规划者

你是规划者，不是本批次执行者。你的交付物是一份已填完整、可直接交给编排者的 `[tracking]` Issue：

1. 基于与产品负责人的会话收敛目标和范围；确认所有工作 Issue 已创建，正文和最新评论足以让新 Agent 独立理解。不足就先补工作 Issue。
2. 从本次规划起点开始读取相关 Issue / PR 的全部增量和必要项目规则，不用固定“最近 24 小时”替代当前事实。
3. 完成“开工前事实确认”：用户结果、调用入口、依赖安装、Issue / PR 关系、授权终点、完成标准和待人类决定事项。
4. 读取本机工作区的 `.tmp/environment-inventory.md`。它只描述规划者所在研发机器可用的 AI Coding 工具、Agent、模型、推理档、沙箱和并发能力，不是实施者的项目运行环境；必须处于 Git 忽略路径，禁止 add、commit 或 push，也不得记录秘密值。
5. 环境清单存在、约 7 天内完成过全量刷新、覆盖本批所需 AI Coding 组合且上次无环境问题时可以沿用，并在分配角色前做轻量读回；否则先更新清单和必要冒烟。
6. 实施者、验收者或审核者如果运行在另一台机器，由该角色在接手时自行确认本任务所需的工具、依赖和环境，并报告实际使用的 AI Coding 工具、模型、推理档与限制；无需把不同机器的本地状态汇总进规划者的 `.tmp` 文件。
7. 在轻量、标准、高风险三个等级中选择本批流程，填好角色、预算、测试所有权、共享文件 owner、commit / PR / 合并规则和问题分流。模板建议值可改，不强制。
8. 删除全部占位符和不适用项，以真实换行创建 `[tracking] YYYY-MM-DD 开工批次：一句话目标`，创建后读回核对。除非产品负责人另行授权，到此停止，不开始实施。

> **仅供人类快速阅读。** 规划者负责根据会话填写；相同内容必须同步写入“任务与授权”，确保所有执行角色理解用户结果。

你是本批次唯一主 Agent，也是编排者。先读完本计划及所有工作 Issue 的正文与最新评论，再按计划调度 subagent。你负责分派、等待、反馈路由、证据核对、跨线整合、Issue 留痕及 Git / GitHub 流程；默认不亲自实现、测试或担任最终独立审核者，也不能自行改变用户结果、扩大权限或放宽验收标准。轻量流程或计划明确的降级方案可以由编排者兼任实施与基础自审。

### 流程等级的最低路径

| 等级 | 适用范围 | 最低路径与证据 |
| --- | --- | --- |
| 轻量 | 单文件或局部、可逆、不改变用户体验、权限、数据与外部依赖边界 | M0 事实确认 → M1 实施、相关测试和基础自审 → M4（授权需要 PR 时）；M2、独立 M3 和 M5 可标记不适用 |
| 标准 | 多文件或需要独立视角，但不属于高风险 | M0 → M1 → 独立 M3 → M4；是否增加 M2 独立验收和 M5 受控验收由工作 Issue 与项目现有规则决定 |
| 高风险 | 身份、权限、安全、用户隔离、数据范围、数据库迁移、真实外部交付或关键失败语义变化 | 完整 M0–M5；独立验收者和独立审核者均不得由实施者兼任，新增高风险断言按项目规则执行变异验证 |

流程等级只决定最低路径；工作 Issue 或项目现有规则可以要求更多证据，但规划者不得仅因模板中列出了某个角色就让轻量任务自动升级为完整流程。

## 四、编排者可调用的角色

> 规划者必须把建议值改成这批工作的实际配置。轮次和成本是调度预期，不是自动停止开关。

| 角色 | Agent / 模型 / 思考深度 | 数量或轮次预期 | 工作内容 | 权限与边界 |
| --- | --- | --- | --- | --- |
| 执行者 | {{建议：worker subagent / 高能力模型 / high–xhigh}} | {{建议：每个独立 Issue 1 个；初始实现 1 轮，修复约 2 轮}} | 实现、TDD、白盒单元 / 组件 / 集成测试、基础自审；按反馈修复并本地 commit | 只改分配范围；默认不 push、不建 PR、不改变产品决定 |
| 验收者 | {{建议：未参与实现的 worker subagent / high–xhigh}} | {{建议：每条线 1 次初验 + 受影响修复后的复验}} | 先依据 Issue 独立形成验收清单，再检查实现；运行与风险相称的黑盒、否定、回归、变异、全量门禁及真实依赖验证；必要时提交只改测试的验收用例 | 有权判定通过、退回或证据不足；不改产品代码、不放宽标准、无合并 / 发布权 |
| 审核者 | {{建议：未参与实现的 subagent 或外部 Agent / max}} | {{每个 PR 总计最多 2 轮}} | 审查 diff、未来部署可行性、Test 与 CI 有效性及风险 | 只提发现，不直接修；内部与外部 Review 都计入预算 |

- **角色兼任**：轻量流程可由一个 Agent 实施、测试和基础自审；标准与高风险流程中，执行者不得担任最终独立验收者或审核者。低风险任务可明确让验收者兼任审核者，高风险任务建议分开。
- **问题分级**：P1 指用户结果、权限、安全、数据、关键失败语义或合并门禁受到破坏，进入下一阶段前必须解决或交由产品负责人决定；P2 指不阻塞当前用户结果的质量问题，按本批阈值处理或另建 Issue。
- **预算使用**：超出预计轮次、时间或成本时，编排者记录原因并重新安排，可以换模型、换角色、缩小切片或继续返修。只有权限不足、用户目标不明确、安全风险或不可逆外部操作无法判断时，才停止相关线并请求人类决定。

## 五、测试用例所有权

- **工作 Issue**：提供可观察验收标准；缺失时由编排者退回规划者或人类补齐，不让 subagent 猜产品规则。
- **执行者**：编写与实现紧密相关的白盒测试并在交付前运行；没有测试证据不得进入验收。
- **验收者**：本批配置了独立验收者时，在看实现前先从 Issue 形成独立验收清单，负责与风险相称的黑盒、否定、回归和变异场景；发现稳定缺口时可提交只改测试的用例，再由执行者修产品代码。轻量流程未配置验收者时删除本项。
- **线上 CI**：只运行已入库、稳定且无真实业务副作用的测试；不设计用例，不替代本地测试或受控验收。
- **编排者**：只根据证据决定继续、返工、调整或请求人类决定，不能把任何一方的自报当成通过。

## 六、流程与动态基线

- [ ] **M0 开工**：记录执行合同版本和 `origin/main` 起点锚点；核对开工前事实、工作 Issue 与当前 HEAD。起点锚点用于回溯，不锁定工作分支；后续提交和分工状态由编排者持续更新。
- [ ] **M1 实施**：编排者按流程等级分派执行者；执行者完成实现、白盒测试、基础自审和本地 commit。同时由独立验收者仅基于 Issue 准备验收清单时，验收者不得提前读取实现。
- [ ] **M2 验收**：高风险流程必须执行；标准流程按计划执行；轻量流程可以标记不适用。执行时由验收者注明证据对应的候选提交并独立验收，失败交回执行者修复。后续代码变化只重新验证受影响的证据，不要求无关部分从头开始。
- [ ] **M3 Review**：标准与高风险流程由编排者以当前候选提交和最新 `origin/main` 为基线分派独立审核者；轻量流程以 M1 的基础自审为最低要求，可将本阶段标记不适用。执行者按发现修复，已配置的验收者复验受影响部分；轮次与阻塞处理按[Draft PR 前置审查](../协作约定.md#draft-pr-前置审查)。
- [ ] **M4 Draft PR 与 CI**：无 P1 阻塞项后由编排者 push、创建并读回 Draft PR；CI 失败按第七节分流。
- [ ] **M5 真实验收、合并与收尾**：按工作 Issue 和项目现有验收规则执行受控真实路径；仅在授权覆盖时按顺序合并。更新 Issue / 必要文档，登记后续项、清理已授权资源并复盘；生产发布另走 Ops 任务。

## 七、问题分流

| 情况 | 怎么办 |
| --- | --- |
| 原 Issue 内、可逆、不改变产品或权限边界 | 交回执行者解决，验收者复验受影响部分，写回对应 Issue / PR |
| 超出预计轮次、时间或成本，但仍在原目标和授权内 | 编排者记录原因并重排模型、角色、切片或顺序；不因预算预期自动停止整批工作 |
| 改变范围、用户承诺、权限、数据或产生不可逆副作用 | 停止相关线，向人类给出事实、选项和影响；独立线可继续 |
| 范围外且不阻塞 | 新建 Issue 并链接，当前批次继续 |
| 缺少本任务环境、依赖或资料 | 对应角色先自检、换可用路径或请求最小必要补充；不降低验收标准 |
| `main`、工作 Issue 或候选提交中途变化 | 编排者更新动态工作版本，判断影响范围，只重排和复验受影响部分；存在实际冲突时才暂停相关写入 |

## 八、记录与复盘

- 具体实现、测试、验收、Review、对应候选提交和未验证项写在工作 Issue / PR；本计划只更新执行合同版本、动态工作版本、里程碑时间、链接和跨线决策。
- 结束时留一条收尾评论：完成的 Issue / PR、证据等级、未验证项、后续 Issue / 人类待办，以及“下次保留什么、改掉什么、是否建议修改本模板及依据”。
- 本模板 Issue 的评论不属于当前执行规则；未来修订候选必须明确标记“当前不生效”，并在回写本模板文件和同步 GitHub Issue #59 正文前由所有执行角色忽略。
