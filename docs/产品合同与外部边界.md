## 产品是什么

Lingxi 是企业内部受控的 AI 业务分析服务。首期面向所有内部用户：未开通用户可以在飞书完成开通，数据库中已有明确有效权限记录且对应 MCP 权限已经确认同步完成的用户可以问数。用户通过飞书私聊提出问题，在外部 MCP 按该用户当前生效权限实际提供的数据范围内获得分析结果，并可接收飞书文档、飞书电子表格或其他允许交付的产物。

飞书私聊是唯一的用户入口，不受公司内部局域网限制。JumpServer 高级工作台已于 2026-08-28 由产品负责人裁定取消，不再属于产品范围（见「不提供」及[取消 JumpServer 高级工作台决策](决策记录/2026-08-28-取消JumpServer高级工作台.md)）。

Lingxi 不替代银河、MCP、模型平台或飞书，而是在这些平台提供的有效能力之上，形成自动准入、受控问数、连续对话和结果交付的完整用户体验。

**对外名称规范（产品负责人 2026-08-30 裁定）**：「Lingxi」是内部代号，仅用于仓库、代码标识、内部文档与内部日志；对外统一使用「BI Plus」或「BI-Plus」。「灵犀」「lingxi」「Lingxi」不得出现在任何用户可见面——包括但不限于开通与问数过程中的固定提示文案、每日通报、监控告警群消息、交付物内固定文案、确认卡文案；飞书机器人名称由飞书后台管理，现已为 BI-Plus 系列。本文其余段落沿用「Lingxi」指代本产品仅为内部文档行文习惯，不代表用户实际会看到这个名字；下方各处固定提示口径的引号内文字是用户实际收到的文本，已按本条统一为「BI Plus」。

## 用户与入口

| 角色 | 要完成的事 | Lingxi 提供的体验 |
|---|---|---|
| 未开通业务用户 | 首次使用 Lingxi | 发送消息后自动开始匹配和开通；不需要授权卡片或浏览器 OAuth。 |
| 已开通业务用户 | 问数、追问、理解趋势并取得交付物 | 开通成功后的下一条消息才进入正常问数；正常情况下无需填写权限申请或等待人工审批。 |
| 无法唯一确认有效权限的用户 | 知道自己为什么用不了、下一步找谁 | 无论是查无、多条、双键冲突、资料不完整还是没有受支持职能，都收到同一“当前没有可用的银河权限”结论和申请指引，不进入等待状态。 |
| 管理员 | 处理权限变化、账号、环境、发布和同步异常 | 驾驭经批准的 AI Agent 查询用户和运行状态；高风险动作在本人飞书私聊确认后才执行。管理员不替用户选择身份候选或银河权限记录。 |
| 运维管理员 | 保持服务和入口可用 | 在受控流程中处理环境、外部依赖和可用性异常，不代替业务权限判断。 |

## 首次对话与自动准入

普通员工使用 Lingxi 时不需要点击身份授权卡片，也不需要完成浏览器 OAuth。系统根据已由专用组织授权同步的关联企业、部门、员工资料和公司花名册多维表格，自动匹配银河当前有效权限记录并继续开通。

- 未开通用户发来的业务内容不进入问数、不保存也不回显；系统直接启动自动匹配与开通，并向用户展示可理解的进度或最终结果。
- 只有身份、花名册与银河权限记录唯一、完整、一致，且至少有一个 Lingxi 支持职能时才继续开通。零条、多条（包括字段相同的重复原始行）、工号与邮箱冲突、资料不完整、没有受支持职能或其他无法唯一确认的结果，都统一得到“当前没有可用的银河权限”结论，不进入人工等待，也不生成人工核对待办。
- 私聊事件的应用侧发送者标识无法在已同步员工资料中定位，该员工缺少姓名、部门、租户等必要资料，或经花名册无法取得工号与邮箱时，也走同一无可用权限出口；内部保留具体失败原因用于审计和排障，但不得猜测其他员工、替用户选择候选或把专用授权用户当作该员工。
- 只有名为“四达文档会议助手”的专用授权用户需要收到一次组织资料授权卡片。该授权只用于读取关联企业、部门和员工资料，不能替代任何普通员工的身份或权限确认。

首次开通期间使用以下固定提示口径：

- 开始核对时：“已收到，正在核对你的身份和银河权限，请稍候。无需重复发送。”
- 唯一匹配到完整且受支持的权限时：“已核对到你的银河权限，正在完成 BI Plus 开通和权限同步，请稍候。同步完成后会通知你。”这句话不代表已经开通成功。
- 当前用户的权限同步、环境创建和开通链路全部完成后：“开通完成，你现在可以开始使用 BI Plus。当前可用范围：公司：{公司名称}；职能：{职能名称}。”
- 无法得到唯一、完整、一致且有效的银河权限时（含查无、多条、双键冲突、身份或花名册资料不完整、没有受支持职能及其他确定性匹配失败）：“当前没有可用的银河权限，请先在银河申请或补充权限。银河权限生效并完成同步后，请再回到 BI Plus 使用。BI Plus 不能代替你申请或扩大银河权限。如果你在银河已经有权限但仍看到此提示，请联系银河管理员。”
- 除上述确定性无权限结果和权限同步超时之外，组织资料服务不可用、Lingxi 内部技术故障或开通链路意外失败时：“当前暂时无法完成开通，已转交管理员处理，你可以稍后重新发送消息重试。处理完成后我们会通知你。错误码：`LX-ONBOARD-001`，追溯号：`{追溯号}`。”该错误码用于管理员核查，不在用户提示中展开内部原因；追溯号是这一次事件的唯一标识，管理员凭它可以用受控只读命令核对具体经过（2026-08-21 裁定：去掉此前“请不要重复发送”的劝阻语义——它与“再发一条消息即可自愈”的既有恢复路径直接矛盾；同一次裁定要求“已转交管理员处理”这句话必须对应真实的管理群送达，不能只是一句无人接收的承诺）。
- 认领超过系统内部租约周期仍停在“正在核对/正在完成开通”的用户（例如处理进程在中途异常退出），系统会主动结束这次等待并告知：“距离你发起开通已经过了较长时间，仍然没有得到结果，本次已经停止等待。你可以再发一条消息重新开始。错误码：`LX-ONBOARD-001`，追溯号：`{追溯号}`。”这属于同一个错误码家族，不新增第二个开通错误码——新增错误码的唯一判据是“用户需要做的事不同”，而这里用户要做的事仍然是“再发一条消息”。

- 当该员工的邮箱**已经绑定在另一个人的用户记录上**时（花名册里两名在职员工共用同一个邮箱是真实存在的形态），系统在建档之前就停下，走上面同一条 `LX-ONBOARD-001` 出口并通知管理员，**不会**替这两个人挑一个、也不会让第二个人共用第一个人的正式表记录与问数令牌。内部原因码 `email_already_bound`，只进审计不进用户提示。这类冲突**需要人工处置**（决定这个邮箱归谁），系统不做自动收敛；在处置完成之前，第二个人每次重试都会得到同一条结果。

上述提示按可判定结果互斥使用：任何确定性的非唯一成功结果走同一银河申请指引；等待十五分钟仍未确认 MCP 权限同步成功走“权限同步未完成，已转交处理”；组织资料不可用或其他不属于已定义结果的 Lingxi 内部意外故障才使用 `LX-ONBOARD-001`。一旦选定终态分支，后置异常不得把它改写成另一种用户结论。

### 开通流程

普通员工首次使用时，系统自动执行以下流程，并展示当前进行到哪一步、每一步是否成功：

1. 使用“四达文档会议助手”已经授权并持续刷新的用户 token，同步其可见关联企业、部门和员工资料，并只读读取公司花名册多维表格；普通员工不参与此授权步骤。
2. 普通员工私聊事件提供应用侧的发送者 `open_id`；系统只在同一应用语义下用该标识定位专用授权同步的员工资料，取得 `user_id`、`union_id`、姓名、部门、租户与在职状态。绝不把“四达文档会议助手”的授权身份当作员工身份。
3. 以「人员ID = `user_id`」在公司花名册多维表格中定位该员工，取得工号、邮箱等人员资料；花名册只提供身份资料，不是权限权威，也不得由事件 `open_id` 直接查询花名册。
4. 建立统一用户记录，此时只关联该员工的飞书身份、花名册资料和 Lingxi 内部状态；数据库权限记录要等匹配确认后才写入，不得先占位再回填。
5. 产品负责人提供的银河用户数据已经通过受控流程进入 Lingxi 数据库后，以**工号为主、邮箱为辅**与数据库中当前有效的用户权限记录进行匹配：工号唯一命中即采用，工号缺失或未命中时以邮箱匹配。姓名只作诊断辅助，不是匹配键。银河权限链路不依赖在职状态。
6. 只有身份链原始记录唯一、匹配键结果唯一且一致、权限记录完整，并且至少有一个角色精确映射为 Lingxi 支持职能时，才自动确认用户身份；其他结果统一按无可用权限结束。用户的公司和职能范围直接采用该数据库记录，不由用户或管理员选择。角色映射使用仓库内的[银河角色职能配置](../src/lingxi/config/galaxy_role_function_map.toml)；APP 角色、「A海外本地员工营业厅」及其他未映射角色不产生支持职能。
7. 系统自动完成准入和用户环境创建，并将数据库确认的权限发布到飞书多维表格（权限发布表）。**[Issue #140](https://github.com/Moshuiwang/lingxi/issues/140) 尚未批准任何正式产物路径时，本步骤不存在可执行的产物前置：该前置记为「不适用」，开通不因此失败**（产品负责人 2026-08-17 裁定，见[长期执行计划 #203](https://github.com/Moshuiwang/lingxi/issues/203)）；一旦 #140 批准了某条路径，开通须完成其批准的产物前置。正式产物**交付**本身在路径尚未批准或验证时仍然失败关闭，不能用机器人专属目录冒充完成。权限发布后进入“权限正在同步”，此时用户尚未开通成功，也不能进入正常问数。
8. Lingxi 立即通过问数 MCP 校验一次该用户的权限，之后每三分钟校验一次，最多等待十五分钟。只有明确确认该用户应有的公司和职能权限已经同步且可以问数后，才宣告开通成功。

流式展示的开通过程既让用户知道系统正在做什么、还要等多久，也让开通失败时可以直接定位到卡在哪一步；展示内容使用用户可理解的表述，不暴露内部标识、令牌或服务器路径。

权限同步期间，卡片明确显示“权限正在同步，预计最多需要十五分钟”，用户无需重复开通。十五分钟后仍未确认成功时，停止自动等待，转交管理员处理，并告诉用户“权限同步未完成，已转交处理，无需重复开通。追溯号：`{追溯号}`。”（2026-08-21 裁定：加上追溯号，理由与用途同上一条 `LX-ONBOARD-001` 的追溯号）；后续确认成功后再主动通知用户可以开始使用。服务在线、其他用户可以问数或权限已经写入飞书多维表格，都不能代替对当前用户的同步确认。

普通员工首次使用时立即开始匹配和开通过程，不要求首批名单中的用户事先逐人完成身份核对，也不把预核对白名单作为上线门槛。正常路径不设置人工审批、卡片授权或用户填写公司、职能、申请理由；首次开通过程可以包含自动核验、用户环境创建、权限发布和可用性确认。身份或权限只要不能唯一、完整、一致地确认，就统一按无可用权限结束，不转人工选择；外部服务不可用或开通链路技术故障才转交运维处理。自动处理不产生或扩大数据库中不存在的权限；飞书多维表格只传递数据库已经确认的权限，不能反向创建、修改或扩大用户权限。**唯一例外（2026-09-02 裁定，rc25 S-1）**：正式权限表里已经有行、有令牌的存量用户首次开通时，系统读取该行一次，把「该行权限 − 银河当前翻译」作为管理员本地补充授权（原因「2.0 迁移导入」，逐行或整组可撤销）写入数据库；此后仍按「银河 ∪ 本地」单向发布，合成结果与表中现有行相同时不回写。旧行里的「全部公司」通配保留为公司维度的 `*`、指标维度按当时映射显式展开，新公司无需改表，新指标进入映射后随重算补齐。

### 开通成功后

只有当前用户的 MCP 权限同步已经明确验证通过，系统才告诉用户开通成功、可以开始提问，并展示当前可用的公司和职能范围。用户在开通前发送的内容一律丢弃：不执行、不保存、不回显、不作为建议再提供给用户。用户需要自己发送第一个业务问题，之后才进入正常问数流程。

成功卡片不提供预置的业务示例问题或可点击建议。用户的第一个问题完全由用户自己发起；卡片可以提示“不知道从哪里开始，可以直接问我‘你能查什么？’”。

## 匹配结果与异常处理

匹配只有两个用户出口，不能由实现者增加第三条“人工选择候选”路径：

| 匹配结果 | 系统动作 | 用户看到 |
|---|---|---|
| 身份、花名册和数据库当前有效权限记录均唯一、完整、一致，且至少有一个受支持职能 | 继续自动开通 | 流式开通进度，最终“可以开始使用”和当前公司、职能范围。 |
| 零条、多条、双键冲突、重复原始行、资料不完整、没有受支持职能、非在职或其他无法唯一确认的结果 | 结束本次开通；不创建用户环境、不发布权限、不生成人工待办；内部保留具体失败原因 | 统一结论：当前没有可用的银河权限，请联系银河管理员。 |
| 发消息的是**组织资料同步的专用授权账号本身**（不是员工） | 结束本次开通；不建用户记录、不建环境、不发权限 | 这个账号是组织资料同步的专用账号，不提供问数服务，也不会建立使用记录。 |
| 开通过程中发现该账号**已被管理员停用** | 停止开通；不建环境、不发权限，已建的档不改动 | 你的 BI Plus 账号当前已停用，暂时无法发起新的问数。 |

后两行不是“第三条人工选择路径”，而是两条**本来就存在、此前只写在实现里**的确定性终态：专用授权账号不是员工，不能落回普通员工路径（否则它会被建档并发权限）；而开通链最长会跨十七分钟，管理员在这期间停用账号是真实形状，系统必须停下来而不是继续把他推成“开通完成”。两者都不进入等待、不占用人工资源。

“查不到”是首期的常见正常结果，不是异常：内部用户中本来就只有一部分在银河拥有数据权限。多条、冲突、重复、记录不完整、没有受支持职能、非在职或其他确定性失败也采用同样的未授权终态。这类用户必须直接得到可行动的结论，不进入等待，也不占用人工资源。银河不需要提供在职状态；离职、未授权和其他银河权限异常在用户侧统一呈现为未授权。

确定性匹配失败时：

- 立即结束该用户的创建过程，不继续问数，不发布不确定权限，也不部分宣告成功；
- 不创建 `manual_review` 或候选选择待办，不允许管理员挑选一条记录后继续开通；
- 内部审计可以记录 `roster_not_found`、`multiple_hits`、`key_conflict`、`required_fields_missing` 等脱敏原因，但用户始终得到同一可行动结论；
- 不允许模糊匹配、按相似姓名或相近账号猜测，或用管理员权限替代用户权限完成开通。

环境创建、权限发布或 MCP 权限同步确认未获得明确成功结果时，不重新进入身份核对。系统暂停在相应步骤并通知运维管理员；运维先核对实际状态，再从尚未确认完成的步骤安全恢复。不得盲目重跑整个流程，避免重复创建环境、重复发布权限或重复通知用户。恢复并确认当前用户可以问数后才通知用户可以使用；最终无法恢复时通知用户尚未开通，并说明由谁继续处理。

## 管理员处理入口与安全确认

首期管理员通过经批准的 AI Agent 使用 Lingxi 管理能力，不建设完整网页管理后台，也不在飞书群聊中提供审批流程、管理命令或可执行的管理卡片。受控管理群只用于通知运行异常、处理进展或最终结果；管理员在自己的 AI Agent 中完成查询和操作准备，不处理身份候选选择。

**MVP 入口实例化（产品负责人 2026-08-24 裁定方案 A，理由与触发条件见[管理员职责集与银河外权限动作边界](决策记录/2026-08-24-管理员职责集与银河外权限动作边界.md)）**：首期「经批准的 AI Agent」即 Lingxi 机器人自身的飞书私聊会话——管理员在私聊中完成查询与动作发起（自确定性命令面起步），不引入新客户端、不新增对外入口。**唯一管理员为组织资料同步的专用授权主体账号**（即「文档会议助手」）：该账号本就被排除在员工开通路径外，管理员身份与业务用户身份结构性隔离；在管理入口实现落地前，其私聊维持现行专用账号提示出口。管理员身份以飞书平台验证的账号身份加 Lingxi 服务端管理员角色登记表为准，MVP 登记唯一条目并合并授予下述三类角色；登记表的任何变更须本人确认卡加审计。已知情接受的集中风险：该账号同时承载组织同步授权与管理员身份。下两段的管理 MCP 与外部管理 AI Agent 保留为未来入口，启用前相关条款按本段实例化理解。

管理 AI Agent 通过独立的 Lingxi 管理 MCP 使用受控能力。管理员是否有权查询或准备操作，以管理 MCP 当前认证的个人身份和角色为准，Lingxi 不重复维护或逐次校验另一份管理员名单。管理 MCP 身份必须与唯一的本人飞书身份绑定，确认卡接收人不能临时选择或替换。

管理 MCP 与业务用户问数使用的问数 MCP 职责分离，并提供三类可以分别授予的角色：

- **权限管理员**可以查询用户身份关联、当前公司和职能权限及准入状态，并准备停用、恢复、按银河职位与公司范围补充本地权限、按公司×指标屏蔽或撤销本地权限（这三个方向见下「本地权限覆盖」与「本地抑制只减不加」）、对单个用户的上游数据立即重同步（重拉快照、重算并重新发布，权威仍是银河）或从当前运行环境删除用户；不能替用户选择身份候选或银河权限记录。「终止开通」不作为独立动作提供：需要终止进行中的开通时使用停用——它同时停止开通并阻止重新触发（2026-08-24 调整，理由见[管理员职责集与银河外权限动作边界](决策记录/2026-08-24-管理员职责集与银河外权限动作边界.md)）；
- **运维管理员**可以查询用户环境、权限发布与 MCP 权限同步状态，并准备从尚未确认完成的步骤安全恢复或重试；
- **超级管理员**可以新增或移除权限管理员、运维管理员和其他超级管理员；同一个人可以被分别授予多个角色。若系统中已经没有超级管理员，普通管理入口暂停角色维护，由持有服务器 Root 权限的 Ops 运维工程师通过受控恢复流程，把一个身份已经核实并绑定飞书的现有用户恢复为超级管理员，并留下恢复对象、操作者、时间和结果的审计证据；
- **本地抑制只减不加**（2026-08-24 新增；#493 只收敛了发起入口，规则本身不变）：权限管理员可以对指定用户的指定公司×指标停止向权限发布表发布。抑制必须记录原因并经本人确认卡生效；生效期间该抑制项持续出现在审计记录与每日审计日报中，不得无限期静默存在；银河侧修正并同步后应予解除，或按固定周期复核。抑制优先于授予：用户的真实权限 =（银河翻译权限 ∪ 本地补充授权）− 本地抑制；某个用户的指标被抑制到空时按撤权处理，不当作「本来就没有银河权限」。**发起入口**：屏蔽与撤销由管理员在飞书私聊用文本命令逐笔发起（`/admin suppress_permission`、`/admin revoke_permission`），下方「本地权限覆盖」描述的管理卡表单只承载补充授权这一个方向，不承载抑制——这是表单入口的收敛，不是取消抑制能力；
- 管理 MCP 只提供范围明确的管理能力，不提供任意数据库查询、任意字段修改、直接执行系统命令或绕过既有权限规则的通用工具；
- 查询不到目标用户时返回明确的“不存在”结果，不猜测相似姓名、不自动改查其他用户，也不产生写操作；
- 管理 MCP 按当前角色只展示和允许相应能力：权限管理员不能执行运维恢复，运维管理员不能替代业务身份与权限判断，只有超级管理员可以改变管理员角色；
- AI Agent 可以帮助管理员理解运行异常和说明影响，但不能比较并选择身份候选、自行认定用户身份、扩大权限或直接完成高风险动作。

**本地权限覆盖**（2026-08-26 产品负责人就 [Issue #319](https://github.com/Moshuiwang/lingxi/issues/319) 裁定新增；#493 将入口收敛为职位+范围）：唯一管理员可以经本人飞书确认卡，对指定用户选择一个**银河职位**和一个**公司范围**补充授权。职位必须是 [galaxy_role_function_map.toml](../src/lingxi/config/galaxy_role_function_map.toml) 中的精确角色名，随后按 [company_function_metric_map.toml](../src/lingxi/config/company_function_metric_map.toml) 的职位职能映射展开为公司×指标行；公司范围是单个公司或“全部”（展示当前实际公司数量，不静默抑制缺失项）。这项本地补充授权独立于银河来源，不改变银河数据，也不改变任何管理员角色；它只能增加该用户的本地权限，不能替代银河职位授权。确认前的这张表单只提供补充授权，不提供本地抑制入口——**这是表单这一个入口的收敛，不是取消本地抑制**，屏蔽与撤销仍按上文「本地抑制只减不加」经管理员私聊文本命令逐笔发起；既有逐指标历史行可继续展示和按原机制撤销，不迁移、不改写。

本地补充授权不设生效后的有效期；确认时展开的公司×指标行共享 `permission_group_id`，管理卡按一个“职位+公司范围”项展示并一次事务性撤销全组。只有历史 `permission_group_id=NULL` 行继续沿用逐行撤销确认链；不迁移、不改写存量行。管理卡本身有懒过期的上下文边界：回调会重新读取目标状态并比较卡片快照，数据变化或上下文过期时拒绝旧提交、刷新原卡并要求重新查询；不运行主动到期清扫，后台 scanner 只重试已落库但尚未被 CardKit 接受的视觉更新。确认事务成功只表示“操作已记录，权限正在下发”；发布完成后才展示“已生效”，超过约定处理窗口仍未完成时展示未完成和追溯号，并由后续批处理修正。与本节讨论的 Lingxi 管理员身份不同，银河“后台管理员”角色（role_id 513）持有人本身即恒为全公司（含未来新增公司）× 全指标，不需要也不依赖本地权限覆盖。规则依据见[管理员职责集与银河外权限动作边界](决策记录/2026-08-24-管理员职责集与银河外权限动作边界.md)。

管理员处理异常时，先区分异常针对的是目标员工，还是当前发起操作的管理员：

- 如果目标员工不是唯一、完整、一致且权限有效的成功结果（含查无、多条、冲突、重复、资料不完整、没有受支持职能或其他确定性失败），Lingxi 不修改或扩大银河权限，不代员工申请，也不创建 Lingxi 权限人工待办。员工收到明确提示：“当前没有可用的银河权限，请先在银河申请或补充权限；银河权限生效并完成同步后，请再回到 BI Plus 使用。BI Plus 不能代替你申请或扩大银河权限。”银河中已有权限但 Lingxi 仍异常时，提示联系银河管理员。
- 如果是当前管理员自己的身份、角色、管理 MCP 身份、本人飞书绑定或确认链路异常，当前管理操作立即停止，不允许管理员自己修复、绕过确认或继续使用旧待确认卡片。系统提示联系 Ops 运维处理，生成可追踪的异常编号，并只向受控管理群发送不含敏感信息的处理通知。Ops 核对并修复权威来源后，管理员必须重新授权或登录管理 Agent；修复前产生的待确认操作全部失效，管理员需重新查询并发起新操作。
- 只有已经得到确定性匹配结论时才走无可用银河权限出口；组织资料服务不可用、Lingxi 内部技术故障、管理入口、同步或确认链路异常统一交由 Ops 处理，不冒充无权限。
- 重复原始行、双键冲突、资料不完整等**上游数据质量问题**由管理员归集并反馈给花名册与银河的维护方处理（2026-08-24 新增职责）；Lingxi 不代改上游数据，也不因此打开人工选择路径。

只读查询由管理 MCP 按当前认证身份和角色直接授权并返回；查询范围以处理当前管理职责所必需的信息为限。任何会改变用户身份关联、准入状态、数据权限、账号状态、用户环境、发布状态或管理员角色的动作，都必须先形成一项不可直接执行的待确认操作。

待确认操作发送到发起管理员本人的飞书私聊，卡片只承担最终确认，不承担搜索、比较、审批流或复杂信息填写：

- 卡片明确展示目标用户、当前状态、准备执行的动作、执行后的用户影响，以及「确认执行」「取消」两个动作；
- 卡片只发送到管理 MCP 身份所绑定的本人飞书账号，不能改发他人；卡片发送失败时本次操作不执行，不根据失败原因推断人员状态；
- 只有发起该操作且管理 MCP 当前角色仍有权执行的本人可以确认；管理群成员身份、卡片链接或 AI Agent 会话本身都不能代替个人授权；
- 管理员确认时重新读取目标对象、权限版本和管理 MCP 当前角色；卡片过期、角色已经被收回、目标状态已经变化、当前角色已无权执行、确认结果不明或审计无法写入时一律不执行，并要求管理员重新查询；
- 同一项待确认操作最多成功执行一次。重复点击、重复回调或多个 Agent 重复提交只能返回已有结果，不能重复改变用户状态；
- 执行完成、失败或取消后，原卡片更新为不可再次操作的最终状态；相关用户按产品合同收到可以使用、尚未开通或权限变化的最终通知。

用户权限管理卡是上述确认卡之前的查询与填写入口，只发送给发起管理员本人。它展示银河来源与本地覆盖，提供职位、公司范围和原因的必填表单，以及一个仅关闭卡片的“取消”按钮；表单提交后原管理卡更新为“已提交，请在下方确认卡片上确认（10 分钟内有效）”。管理卡上下文、卡片实体和 sequence 持久保存，重启后仍可恢复；管理卡提交不绕过确认卡，也不改变本地授权的长期有效期。

每次管理查询和操作都记录管理员身份、当时角色、所用管理入口、目标对象、查询或动作类型、操作前状态、拟执行影响、卡片确认或取消、操作后状态、执行结果和时间。管理员角色的新增和移除同样记录变更前后角色。对敏感数据只记录完成审计所需的范围，不在审计中保存凭据、完整令牌或无关个人信息。写操作的审计记录无法可靠保存时，用户状态不得改变。

这套管理入口只处理异常和管理动作，不把正常自动开通改回人工审批。现有 BI AI Agent 中已经实现的用户查询、权限收回、账号停用与恢复、用户删除、关闭待处理和权限发布重试可作为实现参考；其旧申请审批流程、审批群命令和群内操作卡片不属于 Lingxi 的产品规则。

## 统一用户记录与权限变化

Lingxi 数据库必须建立统一的 `user` 用户表，以一条用户记录关联三类信息：

- **飞书信息**：姓名、`open_id`、`user_id`、`union_id`、部门、租户、经花名册取得的工号与邮箱，以及经批准的正式产物路由（随对话文档/表格 + 文档级可管理授权）和后续投递所需状态；机器人专属目录方案已被 [#140](https://github.com/Moshuiwang/lingxi/issues/140) 否决，不预建、不承诺该模式；
- **权限信息**：匹配到的数据库权限记录、匹配键（工号/邮箱）、公司和职能范围，以及权限版本或核对时间；
- **Lingxi 信息**：内部用户标识、准入状态、用户环境状态、飞书多维表格发布状态、MCP 权限同步确认状态、启用或停用状态。

只保存完成身份关联、权限判断、服务和审计所必需的信息。飞书短期令牌、数据库认证材料、MCP 令牌明文及其他凭据不得进入用户表、日志、Issue、文档或用户交付物。

银河提供首期用户和权限的上游业务数据；数据经过受控流程进入 Lingxi 数据库后，数据库中的当前有效记录是 Lingxi 判断用户准入、记录公司和职能、控制启停以及向飞书多维表格发布什么内容的唯一权威。实际问数时可见和可查询的数据范围由外部 MCP 决定。

- 每次查询开始前重新读取数据库中的用户启停和服务状态，已停用用户不能继续使用 Lingxi；Lingxi 不根据数据库权限记录再次过滤 MCP 查询或结果。
- Lingxi 负责把数据库中的权限变化正确发布到飞书多维表格，并通过问数 MCP 验证当前用户应有的公司和职能权限已经同步且可以问数；未确认前不向用户宣告开通或权限变化已经生效。
- MCP 按当前用户已经同步生效的权限决定实际可见和可查询的数据范围。Lingxi 不在问数链路中增加另一套逐条数据过滤，但只允许已经完成 MCP 权限同步验证的用户进入问数。
- 用户离职或账号停用一经 Lingxi 感知，即禁止该用户发起新的问数；停用前已经开始的任务继续正常完成和交付，不额外停止或撤回，交付完成后该任务产生的结果正文随即按停用清除口径清除，不再保留（见「数据保留与删除」）。
- 调岗时只收回明确失效的范围，不影响仍有效的公司和职能；恢复账号时不自动恢复曾被收回的权限。
- 每次权限变化都通知用户本人，说明本次变化和当前仍可使用的范围；银河权限异常或无法确认时按未授权处理，不进入人工等待。
- 权限同步任务每日先刷新花名册，再刷新一次银河权限快照；新快照对新用户和已有用户都生效。权限变化后更新当前权限多维表格，供 MCP 同步并重新确认当前用户的可用范围。
- Lingxi 每日比对已开通用户的花名册资料与存档，发现姓名、账号状态等变化时经受控管理群的审计日报通知管理员人工处理；飞书账号复用换人（冻结后改名转交）不做自动拦截，依靠该日报发现（见[花名册身份链与工号邮箱匹配决策](决策记录/2026-08-05-花名册身份链与工号邮箱匹配.md)）。

## 问数与多轮对话

本节全部规则适用于飞书私聊入口。

- 收到用户在飞书私聊发送的任何消息后，Lingxi 立即给该条消息添加一个表情，只表示已经收到，不表示消息能够执行或任务已经开始。未开通用户的消息、任务忙碌时发送的消息以及 `/stop`、`/new` 等命令也遵循同一规则；表情添加失败不影响后续应有的引导、提示或任务处理。
- 同一用户在当前对话中连续提问时，Lingxi 保留该对话上下文与已投递的安全结果正文，支持基于上一轮结果继续追问；正文的保留窗口与清除触发点见「数据保留与删除」。
- 不同用户之间不共享对话、数据范围或交付物。
- 飞书私聊主窗口和每个由用户主动创建的飞书原生话题分别形成独立对话；不同话题可以并发执行，彼此不共享上下文。
- 消息已经收到但任务未成功进入队列时，用户收到“消息已收到，但当前暂时无法开始处理，请稍后重试。错误码：`LX-QUEUE-001`”。该提示不表示任务已经受理；相同事件的重复投递不重复发送该提示，管理员可按错误码核查。
- 同一话题同一时间只执行一个任务。占用期间除 `/stop` 外的后续消息（包括 `/new`）只收到一条如实反映当前阶段的提示——已经有 worker 在执行时是“当前任务仍在处理中”，已经入队但还没有 worker 领取时是“前面还有任务在排队，请稍等”；该消息不进入对话历史、不排队，也不会在当前任务结束后自动提交或自动生效。
- **排队可感知**（2026-08-30 裁定为产品合同级承诺，Issue #465）：任务入队后若超过 10~15 秒仍未被任何 worker 领取，Lingxi 主动补发一次“前面还有任务在排队，请稍等”；正常秒级领取时不产生这条提示。超过更长的排队等待上限仍未被领取时，按既有失败语义收口并如实告知（延续本节上一条“消息已收到但未能开始处理”的提示家族），不会让用户停留在无限期的静默等待里。
- **100% 响应覆盖**（2026-08-30 裁定为产品合同级承诺，Issue #465）：任何一条被 Lingxi 收下的私聊消息，最终都必须得到至少一条用户可见的回应（提示、结果或诚实的失败说明），不存在“收下之后系统内部出错、用户什么都收不到”的路径；无法归类到任何已知情形的内部异常，也会换成一条通用的诚实失败提示（带错误码与追溯号），而不是静默。**两个显式除外**（如实登记既有行为，不扩大也不缩小其余部分的承诺）：①系统停机窗口内，尽力而为的提示按既有姿态跳过发送，不在停机预算之外强行补发；②飞书平台事件体本身无法解析（缺少发送回应所需的会话与消息标识）时，Lingxi 只记 `event.unparsable` 审计、不产生任何回应——这类事件在结构上还没有到达"收下一条私聊消息"的地步，不适用本条其余部分。
- 用户在当前话题发送 `/stop` 时，Lingxi 停止该话题仍在运行的后续处理并明确回复停止阶段和已产生的结果；其他话题的任务不受影响。已经成功创建或发送的消息、文档、表格或图片不自动撤回。
- 用户在没有任务运行时输入 `/new`，立即清空当前所在对话的上下文；后续消息在同一位置以新上下文继续，其他话题不受影响。
- 会话是否延续按“上一条任务结束到下一条新任务开始”的间隔判断：间隔超过两小时时，新任务不恢复旧会话，直接以新会话服务用户。任务执行本身耗时多久都不触发新会话。
- 新会话不携带旧会话上下文，但继续使用该用户当前有效的身份、公司和职能范围，无需重新创建用户或重新准入。
- 系统明确告诉用户已经开启新会话，不让用户误以为旧上下文仍然有效。
- 用户问题不清楚、范围存在歧义或数据无法确认时，系统通过追问澄清，不自行猜测。
- 用户可以直接用自然语言询问“你能做什么”“我能查哪些指标”等能力问题，AI Agent 根据问数 MCP 当时实际提供的指标列表和说明回答。不开发 `/help` 命令，不由 Lingxi 维护固定示例问题或另一套能力清单。

## 用户记忆

用户记忆是显式登记式：Lingxi 不自动学习、不从对话内容中隐式提取记忆，只有用户在飞书私聊中通过下述 `/memory` 命令主动登记的内容才会成为记忆（见[决策记录](决策记录/2026-08-28-用户记忆显式登记边界.md)）。

- **登记**：`/memory remember <类型> <关键词> => <说明>`。类型仅限三类——`term_mapping`（术语映射）、`calibration_preference`（口径偏好）、`convention_template`（惯例模板）；登记只接受「关键词 => 说明」这一种键值对形状，不接受任意自由文本。**不存任何数据值**：查询结果、数字、表格内容等数据本身不得作为记忆内容写入，命令语法与登记侧安全校验共同兜底这条红线——登记内容命中疑似系统指令或内部标识的安全校验时明确拒绝并说明原因，不静默丢弃、也不代为改写。同一类型下重复登记同一关键词会更新原有说明，不产生重复记忆；单用户记忆条数存在上限（50 条），达到上限后新的登记被拒绝并提示先清理，不做静默截断。
- **查看**：`/memory list` 返回本人已登记的全部记忆。
- **删除**：`/memory forget <记忆 id>` 删除指定一条；`/memory clear` 一次性清空本人全部记忆，且不可恢复。
- 以上四个命令即使当前话题有任务正在处理中也可以执行，不受同一话题同一时间只执行一个任务的限制（与 `/stop` 同一姿态）。
- **跨用户隔离**：记忆按用户隔离存储，仅在登记者本人的问数任务中被读取和使用，不同用户之间不共享、不互相可见。
- **注入生效**：记忆在该用户下一次问数时由系统自动读取并用于生成回答（例如按登记的术语映射解释业务口径），用户不需要每次重复说明；取用记忆失败时该次问数正常降级为不使用记忆继续执行，不阻塞问数本身。
- **停用与权限变化即清**：用户被停用，或用户的数据权限发生真实变化后，Lingxi 一经感知即清除该用户已登记的全部记忆，不做部分清除或按类型/按内容甄别；与「数据保留与删除」中安全结果正文的停用/权限变化清除触发点同一姿态，清除后不可恢复。

## 问数结果的可信标准

- 数据结果必须让用户看清本次采用的公司、指标、时间范围，以及关键数字或趋势。MCP 返回数据最新时间时一并展示；没有返回时正常交付并省略该字段，不提示“数据时间未知”，不拒绝回答。Lingxi 不验证、不推算，也不为 MCP 补充数据新鲜度能力。
- 公司、指标或时间范围存在歧义时先追问；不能把相近指标、相近公司或猜测结果当作用户所问内容。
- 问数阶段只依据 MCP 实际提供的数据和状态回答。MCP 没有向当前用户提供某项数据时，Lingxi 不推断这是权限不足，不判断隐藏的数据或范围是否存在，也不生成“权限拒绝”。
- 只有 MCP 明确提供数据不存在、数据延迟或外部结果不完整的状态时，Lingxi 才向用户区分说明；否则只说明本次未取得可用结果，不把空结果或不确定结果标为完成。
- 用户经过一至三轮澄清后，应获得可用答案或明确失败说明；持续追问但无法收敛不能视为成功。
- 首期“问数质量八十五分”的可执行口径固定为 **20 个真实问数中至少 18 个通过，即最多允许 2 个未通过**。每个问数只按通过或未通过计一次，不设置不同权重；只有提出该问题的真实业务用户确认得到正确、可用的答案才算通过。清楚说明无法回答或未取得结果可以避免误导，不自动构成阻断问题，但该题仍计入最多 2 个未通过；关键数字错误、指标口径错误、跨用户泄露或三轮内既未收敛也未明确失败属于阻断问题，不能用其余题目的通过数抵消。
- 关键数字错误、指标口径错误、Lingxi 自身造成的跨用户会话或交付泄露，以及三轮内既未收敛也未明确失败，均属于不能上线或继续放量的阻断问题。Lingxi 必须在开通前确认 MCP 对当前用户的权限已经同步可用，但不逐条过滤 MCP 返回的数据。

## 结果与交付

### 交付样式

- 普通分析结果优先通过流式卡片展示。卡片标题使用公司、指标、时间范围等业务主题；正文底部状态区同时展示简短的当前动作和低频更新的已耗时间，例如“正在查询数据 · 18 秒”，回答区逐步展示用户可见内容；完成时显示“已完成”和总耗时。不展示预计剩余时间，也不把内部工具调用或过程日志展示给用户。
- 流式卡片只接收经过安全处理、允许向当前用户展示的内容。安全处理必须跨流式片段保持必要状态和有界尾部缓冲；未经处理的模型片段不得写入投递事件、日志或其他持久介质。无法安全释放的片段不得先展示后撤回。
- 流式卡片创建、更新或关闭失败时，在同一私聊或同一飞书话题用普通文本补发完整结果，不把回复散到其他位置。
- 完成态必须包含可见结果、明确的澄清问题或可理解的失败说明；内部 Agent 名称、过程日志和技术状态不占据用户结果主体。
- 飞书权威 API 明确接受卡片或文本，并返回或绑定可回读的消息、卡片标识时，只能记为“平台已接收”；这足以确认 Lingxi 已把结果提供到用户会话，但不等于用户已经阅读。只有飞书另行提供并经真实验证的阅读回执，才可以声称“用户已读”。API 结果不明、超时或无法回读时不得记为已送达，也不得自动重发。

### 正式产物归属与当前失败关闭

问数产物路由已裁定为随对话交付在线文档（含电子表格，见下「交付规则」同构条款），并授予接收人该产物的文档级「可管理」权限；所有权始终留在机器人名下、不设保留期上限；机器人专属共享目录方案已明确出局，不再是候选方案（[2026-08-23 决策记录](决策记录/2026-08-23-正式产物路由为随对话文档与文档级可管理授权.md)；[#140](https://github.com/Moshuiwang/lingxi/issues/140) 已于 2026-08-24 收口）。

飞书官方规范已经证实：离职交接按所有权而非协作者权限执行，机器人持有、员工仅为协作者的对象不会随员工离职自动交接，所有权也不能转给关联组织员工——这正是弃用机器人专属目录方案的依据。

- 该路由已于 2026-08-27（在线文档）与 2026-08-28（电子表格）完成实现，并分别经产品负责人真实旅程验证（全局证据 6 级）与受控验收（L4a）通过，详见下「交付规则」。创建、写正文、授权或发送任一环节失败，或最终结果状态不明确时，一律失败关闭：不暴露内部文件或服务器路径，不假称已经交付成功，也不因此阻断普通问数正文。
- 停用、离职、删除和权限变化后正式产物的访问、保留、清理或交接，按上文所有权归属处理：所有权留在机器人名下、不随用户离职自动交接；用户对产物的处置权在交付时随「可管理」权限一次性授予，后续传播边界由用户自行负责（见下「交付规则」实现细则）。

### 交付规则

- 正式产物路径已批准并完成真实验证，用户要求文档时应优先创建并只交付一个飞书文档链接；不把内部 Markdown 文件作为默认交付物。
- 经批准的正式产物路径可用时，用户要求表格应优先创建并交付飞书电子表格。电子表格单元格内容一律按文本原样存储：`=`、`+` 等前缀字符不会被解释为公式或触发计算，Lingxi 不提供电子表格公式能力（2026-08-28 H4 冒烟以 `=SUM(1,2)` 探针实证，[决策记录](决策记录/2026-08-28-电子表格纳入随对话交付同构路由.md)）；用户如需要带公式联动的表格，应在收到后自行添加，不应预期 Lingxi 交付的表格已包含可计算的公式。
- 用户要求图片时，应在飞书中直接可见、可打开或可下载，不暴露服务器路径。
- 交付只有在飞书确认创建、授权和发送成功后才能宣告完成；送达状态不确定时明确说明并要求核对，不自动重复创建或重发。
- 用户只能通过已经完成当前权限同步验证的 MCP 问数；实际返回的数据范围由 MCP 按该用户当前生效权限控制。Lingxi 只交付为该用户本人任务生成且允许交付的产物，不得发送其他用户文件、内部配置或认证材料。
- 首期只把交付物发送给当前用户，不由 Lingxi 直接发送给其他个人或群聊。用户可以在飞书中自行决定是否分享；若未来由 Lingxi 扩大接收人范围，必须重新核对接收人的数据权限。
- **飞书文档交付的归属、授权与传播边界实现细则**（2026-08-27 按 [Issue #341](https://github.com/Moshuiwang/lingxi/issues/341) 实现、Trace [#328](https://github.com/Moshuiwang/lingxi/issues/328) E-S 批次落地，兑现上文「正式产物归属与当前失败关闭」2026-08-23 裁定中「随实现 Story 补入本合同」的承诺，并回应 [#140](https://github.com/Moshuiwang/lingxi/issues/140) 裁定待办 #2）：问数产物以飞书在线文档交付时，随对话发给提出该次请求的用户本人，并对其授予该文档的「可管理」权限；文档所有权始终留在机器人名下、不设保留期上限，不转移给用户，也不随用户离职自动交接。Lingxi 内部用于生成该文档的交付请求记录（标题与正文段落）自写入起最长二十四小时后擦除其中的用户内容，记录行本身保留状态、时间戳等运行事实用于审计；**该擦除只作用于 Lingxi 内部记录，不影响已经交付给用户的飞书文档本身**——文档正文按前一句的所有权与保留期规则处理，不因内部记录擦除而改变。**文档交付成功后，其后续的权限调整、查看范围与再分享完全由收到文档的用户本人负责**：用户可以自行修改该文档权限或转发给他人，这部分传播行为超出 Lingxi 的控制范围，也不由 Lingxi 追踪。创建、写正文、授权或发送任一环节失败，或最终结果状态不明确时，用户会收到明确的失败或不确定告知，不得假称已经交付成功。
- **跨租户收件人边界**：当文档或表格的接收人属于机器人所在飞书租户的关联组织（外部租户）而非本租户员工时，「可管理」权限的授予与是否被平台或租户设置降级已经过真实验证——2026-08-27 [#341](https://github.com/Moshuiwang/lingxi/issues/341) S0 探针加产品负责人在关联组织租户内以本人账号完成的真人确认（全局证据 6 级）证实：跨租户授予「可管理」权限成立，且未被降级。但该验证只覆盖「授予是否成立、是否降级」两点；跨租户收件人在该权限下实际能否逐项执行修改权限、再分享、删除等具体处置动作尚未逐一验证，仅确认协作者管理面板本身可见可操作。**跨租户收件人场景下的完整处置动作清单尚未验证完成**：在补测之前，不得承诺跨租户收件人可以像同租户用户一样完整处置收到的产物（[#140](https://github.com/Moshuiwang/lingxi/issues/140) 裁定待办 #1，2026-08-24 收口时登记为实现级待办，非决策残项）。

## 数据保留与删除

- 当前会话上下文在用户输入 `/new` 重置当前所在对话，或按两小时规则开启新会话后，不再带入后续问答；同一触发点同时清除该会话已保留的安全结果正文（见下）。
- 除下一条明确的飞书问数结果正文例外外，Lingxi 后台保存的原始聊天记录和技术审计记录，连同承载这些内容的任务问题、Agent 会话文件、异常处理详情和待确认操作参数，**最长保留九十天**，用于问题排查、质量复核和审计；每份可识别内容自写入起不得晚于九十天删除或不可逆脱敏，不能用按月清理把实际期限延长到九十天以上。
- 飞书普通问数的**安全结果投递正文**分两个阶段保留（[Issue #163](https://github.com/Moshuiwang/lingxi/issues/163) 方案 B）：任务尚未形成最终送达结论前，待投递、明确失败或送达状态不明的正文自首次进入投递队列起最长保留二十四小时；已经成功展示的流式片段在最终送达确认前可以为完整文本降级而暂存，同样不得超过该上限。相应交付形态已经过真实验证、且最终卡片或文本获得“平台已接收”确认后，安全结果正文转为**随当前飞书会话保留**：清除触发点是用户输入 `/new`、会话空闲满两小时由系统**定时到点主动**结束该会话窗口、用户被停用一经 Lingxi 感知，或用户权限发生变化一经 Lingxi 感知；停用与权限变化两类触发**感知即清**，不等待下一次问数任务入队。活跃连续追问的会话中，正文实际留存时间可能超过两小时（直到下一次空闲满两小时被到点清除为止），这是产品负责人明确接受的取舍，不另设与会话无关的独立硬计时。会话窗口期间，正文可以同时存在于会话上下文（Agent 会话文件、聊天上下文副本）与 Outbox 等投递运行位置；触发上述任一清除点时统一、全部、不可逆清除，不逐位置单独判断或延后。未经安全处理的模型片段无论处于投递前或会话保留阶段，都不得写入任何持久介质。
- 会话空闲满两小时后，由系统**定时到点主动**执行一次清除，**不再等待下一次问数任务入队时才判定**；停用、权限变化一经感知同样立即清除，同样不依赖下一次任务入队（2026-08-14 补充决定，见[决策记录](决策记录/2026-07-26-问数可信交付与数据保留边界.md)）。这解决了此前方案的已知限制：即使用户在结果送达后不再发起新的问数，会话也会在空闲满两小时时被到点清除，不存在“长期不再提问、正文无限期保留至用户被停用或权限变化为止”的情形。判断“下一次新任务是否续用同一会话上下文”仍按「问数与多轮对话」的两小时规则在该任务入队时完成，这一判定只影响新任务能否复用旧上下文，与本节正文清除时机相互独立、互不依赖。
- 会话存续期间，结果依赖型追问直接引用仍保留的安全结果正文继续作答；会话结束、正文随之清除后，同一话题的下一次追问按新会话处理——系统不重建、不猜测旧答案，只能提示用户重新提问。
- 二十四小时到期仍未确认送达时，系统不可继续锁住该话题，也不可把任务写成用户已取得结果：不可逆清除结果正文，将任务收敛为“投递已过期、用户未取得结果”，保留最长九十天的低敏状态、时间、通道、外部标识和失败分类。系统不自动重新生成或重发原答案；只在用户下一次主动发来飞书消息时，先用不含原答案的固定提示告知“上一条结果未能送达且已过期，请重新提问”，再继续处理新消息，不为该过期状态主动推送通知。
- Lingxi 不提供被上述两类规则（会话结束清除、二十四小时到期清除）清除后的后台结果找回。只有经过真实验证、确认在正文清理后仍能由目标用户从同一飞书会话访问的交付形态，才可以作为用户找回入口；未验证前不得据此缩短上述后台保留或宣称用户可找回。飞书侧记录不因 Lingxi 运行库清理而删除，并按飞书及公司规则保留。
- 用于故障恢复的数据库备份、WAL 归档和用户目录备份不受上述九十天、会话保留窗口或二十四小时期限及单用户删除操作影响，按公司的灾备与恢复规则管理；它们不作为 Lingxi 正常问数、用户找回、质量复核或日常审计的数据入口。恢复历史备份可能重新带回备份时已有的用户内容，这是明确接受的灾备取舍；恢复后的当前运行环境必须按内容原始写入时间重新执行适用清理（含已经结束的会话窗口），不能把恢复时间当成新的保留起点，也不能借恢复重新打开一个已经结束的会话窗口。
- 公司内部审计在获得相应授权后，可以在上述九十天内审计当前运行环境仍保留的完整聊天和业务内容，以及已经清除正文的低敏投递事实；已按上述规则清除的问数结果正文不由 Lingxi 后台恢复。确需复核已送达正文时，使用仍按飞书及公司规则保留的飞书侧记录，并遵守相应审计授权、用途和追溯要求。
- 正式产物的保留、清理与用户处置能力由 #140 最终合同决定；在此之前不以机器人专属目录交付正式产物，也不假定用户能够删除、转移或通过离职流程交接机器人名下对象。#97 创建的测试对象按其受控执行卡清理，不成为长期用户资产。
- 一次性交付区和内部中间文件在交付完成、失败或送达状态不明后按最短必要时间清理，不作为长期用户资产。
- 用户从当前运行环境删除时，先阻止新的问数和交付，再删除当前环境中的用户身份关联、权限副本、会话文件、任务内容、异常处理详情、待确认操作参数、尚未到期或尚未随会话清除的安全结果正文及其他仍可识别的运行数据；只有当前环境中的全部步骤完成后才显示删除成功。该操作不修改数据库备份、WAL 归档或用户目录备份，不能解释为对历史灾备副本的彻底删除。依法或依公司制度必须保留的在线审计内容应先做不可逆脱敏，不能在当前环境继续识别到该用户。

## 审核、审计与持续优化方向

Lingxi 的开通、问数、权限判断、任务执行和飞书交付构成面向用户的主链路。审核、审计与持续优化采用独立治理能力，不接管用户问数或反向决定用户权限；首期不承诺自动审核、实时风险拦截或审核工作台。

Lingxi 应稳定记录能够关联用户、话题、任务、权限版本、问数 MCP 查询、交付、停止或失败，以及管理 MCP 查询、待确认动作、飞书卡片确认和人工处理结论的审计事实，供后续独立治理项目使用。公司内部审计在获得相应授权后可以复核完整聊天和敏感业务内容。治理工作以发现问题、归类原因、形成改进项和复核效果为闭环，但不得扩大用户的数据权限或改变用户的正常问数体验。详见[审核审计与持续优化治理边界决策](决策记录/2026-07-26-审核审计与持续优化治理边界.md)。

内测阶段，Lingxi 每日向受控管理群发送一条统计级通报：活跃用户与任务量分布、成功/失败/超时/停止分布、失败分类与守卫触发计数、时延与投递结果分布，均为统计数字与匿名分桶，不含用户对话原文、姓名、工号或邮箱。数据段暂时取不到时逐段显式标注「不可判定」，不得静默省略或显示为零；同一天至多发送一条，连续重复出现的失败分类节流为计数不再逐日展开明细；送达失败降级为结构化日志并触发运行告警，不影响其他定时职责。

数据库记录与飞书多维表格发布结果不一致，或 Lingxi 自身任一步骤没有给出明确成功结果时，都不能视为 Lingxi 侧发布已经完成。发布完成后仍须取得当前用户 MCP 权限同步成功且可以问数的明确结果，才能宣告开通成功；十五分钟内未确认则转运维处理。Lingxi 不从下游结果反写或扩大数据库权限，也不复制 MCP 的逐条数据过滤。自动重试和校验不得造成重复建档、重复授权、重复创建环境或重复交付。

## 不提供

- Codex 飞书对话、多 Agent 自助选择或普通用户自行修改模型配置。
- 群聊中的自由业务问数；受控管理群只发送管理待办和结果通知，不提供审批、管理命令或可执行操作。群聊中仅在被 @ 时回复一条固定私聊引导，其余群消息静默（Issue #328 v1.0 裁定 #5，2026-08-27 排入实施）。
- 完整网页管理后台，以及由 AI Agent、管理 MCP 或群聊消息直接执行未经管理员本人飞书卡片确认的高风险动作。
- 管理 MCP 中的任意数据库查询、任意字段修改、通用系统命令或共享管理员身份。
- 用户自行申请、选择或扩大数据库当前有效记录之外的公司和职能范围。
- 在公司和职能权限之外再由 Lingxi 增加一套数据源或下钻粒度限制；首期可查询范围由 MCP 实际提供能力决定。
- 绕过权限数据库或 MCP，直接暴露生产数据源、令牌、认证材料或内部路径。
- JumpServer 高级工作台（2026-08-28 取消，见[决策记录](决策记录/2026-08-28-取消JumpServer高级工作台.md)；重新提供需要新的产品决策）。
- 未经明确规则与门禁的自动扩权、生产变更、自动部署或高风险外部动作。
