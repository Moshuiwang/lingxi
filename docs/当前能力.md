## 已验证的飞书关联组织事实

以下为 Bot-Test 在 `biai-stage` 的受控测试；它们是正式开发的输入，不代表 Lingxi 用户准入、问数或文档交付能力已经上线。详细证据见[两条路径的连接与字段可得性](参考证据/飞书关联组织两条路径的连接与字段可得性.md)（全量事实）、[应用身份共享范围](参考证据/飞书关联组织应用身份共享范围.md)与[用户身份受控验证](参考证据/飞书关联组织用户身份受控验证.md)（两条路径各自的能力）。

- 以专用授权用户“四达文档会议助手”的用户身份，可以定位关联组织、逐部门读取可见范围并读取成员详情；普通员工不需要走这条卡片授权路径。
- 测试项目已真实验证 OAuth 授权码、`offline_access`、加密保存并轮换 `refresh_token`。短期 `user_access_token` 和授权码不保存；这只是 Bot-Test 测试能力，不是正式持续身份关联能力。
- **共享范围版图**：应用身份（不经用户 OAuth）可读**全部 8 个关联租户**的双方共享范围，当次共 272 个共享部门、**710 名成员**；各租户成员数之和与全部去重后同为 710，**`open_user_id` 跨租户唯一、重复 0**。因此按私聊标识定位员工**不需要预先知道对方属于哪个租户**。数字是当次快照，不是长期名单承诺。注意 `open_user_id` 的 6 位前缀会碰撞（710 人中 57 组），前缀只可用于日志脱敏，比对必须用完整标识。
- **应用身份的字段天花板**：共享范围的成员记录**只有** `open_user_id`、姓名、头像三个字段，部门记录只有部门标识和名称。获取关联组织详情与 `visible_organization` 两个接口在应用身份下被拒（`1971007`），因此双方共享范围是应用身份唯一可用路径。
- **私聊事件的发送者标识可以直接在共享成员中命中**：2026-07-29 的受控实验（[Issue #30](https://github.com/Moshuiwang/lingxi/issues/30)）中，2 位事先确认在共享范围内的员工各发一条 1:1 私聊消息，发送者 `open_id` **2/2 全部命中**共享范围返回的 `open_user_id`。因此「员工首次私聊 → 定位其已同步资料」这条自动开通接缝**成立**。边界：只统计 `chat_type=p2p`，群聊未纳入；2 条是排除巧合的最低样本量；命中只证明标识体系相同，不保证任何人必然在未来的共享范围内。这条**不推翻**「私聊 `open_id` 不能与浏览器 OAuth 的 `open_id` 当作同一标识」——那是另一条仍然不通的边界。
- **两条身份路径是同一标识体系**：产品负责人于 2026-07-29 在飞书管理后台补齐了此前 2 个租户缺失的可见范围配置，之后用户身份可见租户为 8/8。对 8 个租户逐个比对，应用身份共享范围的 `open_user_id` 与用户身份可见组织的成员标识**710/710 全部对上、0 例外**。因此「私聊 `open_id` → 共享范围 → 成员详情」这条拼接成立，`user_id` 与 `union_id` 对全部 710 人可得。此结论依赖上述后台配置，配置改回即失效。
- **成员详情的字段有值率**（710 人全量，字段缺失时整字段不出现）：`open_id` / `user_id` / `union_id` / 姓名 / 头像 / `status` / 上级部门均 100%；`mobile` 46.6%（331 人）、`job_title` 36.8%（261 人）、`leader_id` 6.6%（47 人）；**邮箱、职级、工号从不返回**。`mobile` 与 `job_title` 覆盖不到一半，只能作可选增强，不得作为必要输入或匹配前提，也不参与银河权限匹配。
- **在职状态可得，且非在职成员不会被自动移出**：成员详情返回 `status`（`is_activated` / `is_exited` / `is_frozen` / `is_resigned` / `is_unjoin`）。710 人中 702 正常、**5 人已冻结**、**1 人未加入**。即可见范围**不做状态过滤**，自动开通**必须在建档与发权限前逐人校验 `status`**，不得「定位到即视为在职」。当次无已离职样本，「离职后是否仍可见」未直接证实，但不能据此免除校验。
- **姓名并非全部含汉字**：两条路径分别对 710 人做姓名语言分类，结果一致——690 含汉字、9 中拉混合、**11 纯拉丁**。此前「82/82 全部含汉字、纯拉丁 0」是单租户样本外推，**已作废**。按姓名匹配必须能处理非中文姓名。
- **姓名不是唯一键**：710 人中存在 1 对重名（同租户内）。按姓名匹配的逻辑必须能处理歧义。

## 已验证的 Claude 执行链路事实

以下包含前身项目 `bi-ai-agent` 的生产复现，以及 Lingxi 在 `biai-stage` 的 Issue #23 受控验证。它们是执行层选型和后续实现的输入，不代表 Lingxi 的用户问数能力已经上线。背景详见[Claude 执行链路的已验证事实与管道投递风险](参考证据/Claude执行链路的已验证事实与管道投递风险.md)，本次验证结论见 [Issue #23](https://github.com/Moshuiwang/lingxi/issues/23)。

- 百炼兼容端点可以承载 Agent 会话：已在真实端点取得可回读证据，覆盖新建会话、`resume` 恢复、只读 MCP 调用与回执、终止事件。因此模型提供方不是这条链路的主要风险来源，Lingxi 不重跑这一项。
- 前身项目"运行完成但用户侧空结果"的根因**不是百炼**，而是 `claude` CLI 在非 TTY 管道下可能不写出终止事件。归因已由生产复现确认：模型已生成答案并落盘，承载进程未从 `stream-json` 通道收到。
- Lingxi 选定的 Python Agent SDK `0.2.128` 使用自带 Claude Code CLI `2.1.220`、真实百炼端点和真实只读 MCP 完成了 1 个连通回合及唯一一轮 39 个正式回合。40/40 回合均取得非空最终正文和唯一终止结果；正式回合 39/39 的最终助手正文与终止结果哈希一致，最长正文 13,049 字节。新建、`resume`、两会话交替和长结果均未观察到空结果、截断、串会话或终止事件缺失。**Agent SDK 双向流式非 TTY 路径的正文与终止事件投递在该固定组合下成立。**
- 同次验证确认受控 Skill 可以实际加载，`PreToolUse`、`PostToolUse` 和 `Stop` 可采集。
- **`allowed_tools` 加 `permission_mode="dontAsk"` 不是严格白名单**：第一轮中未明确禁用的 `CronCreate` 被实际执行（随后由 `CronDelete` 删除）。只列出允许的 MCP 工具不等于其他内置工具不可执行，新增内置工具默认可被调用，Skill 与 `CLAUDE.md` 的文字约束不能代替运行时强制限制。
- **在 `PreToolUse` 返回拒绝是执行前的真阻止**：2026-07-28 的定向补测在 `disallowed_tools` 完全为空、hook 为唯一屏障的条件下，3 次非白名单调用（`Bash`、`Write`、`CronCreate`）全部被拒且均无 `PostToolUse`，文件副作用探针确认目标文件未被创建，`CronCreate` 被拒后无 cron 残留。被拒回合仍取得非空正文和恰好一次终止结果，同回合内白名单工具照常执行。因此执行层的只读边界**可以做成强制的**。
- **`PostToolUseFailure` 可以采集，但语义是「工具抛错」而不是「用户没拿到结果」**：补测中 2 次真实工具执行失败（MCP 协议层 `isError=true`、MCP 进程调用中退出）均触发该回调 1 次且 `PostToolUse` 0 次，回调带工具名、入参和错误文本。被 MCP 包成正常响应的业务失败（如「指标不存在」）**不会**触发它——要审计「用户实际没拿到结果」，必须额外解析工具回执内容。
- **权限拒绝没有任何 hook 回调**：拒绝后 `PostToolUseFailure`、`PermissionDenied`、`PermissionRequest`、`PostToolUse` 均为 0。同批测试注册了 SDK 类型未声明的事件名并确认 CLI 会透传（`PostToolBatch` 实际触发 7 次），因此 0 次不是「没注册上」。拒绝在 SDK 消息流中**仍可采集**：每次拒绝产生一个 `is_error=True` 的工具结果块。审计链必须由「自己在 `PreToolUse` 记账的拒绝决定」加「消息流中的错误工具结果」两部分合成，**不需要为此改用 TypeScript SDK**。
- **只读工具边界的判定与审计组件已经实现，但还没有执行器在用**（Issue #29，2026-07-29）。判定层是 Lingxi 自己的 `PreToolUse`：默认拒绝、只放行显式精确白名单，新增内置工具自动落入拒绝分支，白名单不接受通配符与前缀匹配。证据层级：**当前提交只有 L2**，`V-执行-01…16` 在 CI 中强制执行。L4a 验证的是中途提交 `fb88f31`，此后审计记账与回执归类又改过多次，**最终提交未重跑受控验证**。当时在 `biai-stage` 的真实百炼端点与真实只读 MCP 上复现的是：`disallowed_tools` 完全为空时，同一回合内 `Write` 与 `CronCreate` 两次越界调用均在执行前被拒，副作用探针确认文件未创建、无 cron 残留，同回合白名单 MCP 工具照常执行，并取得非空正文与恰好一次终止结果。**但 L4a 用的是受控验证运行器，仓库里 `ToolGateway` 至今没有生产调用方——组件存在不等于屏障在生效，执行器切片接入并复验之前，不得据此认为只读边界已经在跑。**
- **`disallowed_tools` 的规则拒绝完全静默，而且会制造审计盲区**（Issue #29 实测）。把工具放进 `disallowed_tools` 后，模型确实发出了该调用，但 `PreToolUse` **一次都不触发**——拦截发生在 hook 之前，模型侧收到的是「工具不可用」而不是「调用被拒」。消息流里只留下一个 `is_error=True` 的工具结果块，其 `tool_use_id` 在执行层记账里没有对应记录。因此 `disallowed_tools` 只能作为纵深防御的外层；执行层把这类回执单独记为「本层未判定」的调用，不谎报为放行，也不谎报为本层拦截。
- **子代理内部的工具调用经过同一个 `PreToolUse` 屏障**（Issue #29 实测）。子代理工具在 CLI `2.1.220` 里名为 `Agent` 而非 `Task`；放行 `Agent` 后，其内部的 `Write` 与 `Bash` 调用均触发主会话注册的 `PreToolUse` 并被拒绝，副作用探针确认无文件写入。**但启用子代理会让同一回合出现 2 个终止结果与 2 次 `Stop`**，与编排层依赖的「恰好一次终止结果」冲突，因此首期对 `Agent` 与 `Task` 两个名字都保持默认拒绝；将来启用前必须先解决主会话与子代理终止结果的区分。

- 开通前发送的内容被丢弃；成功卡片不提供固定业务示例或可点击建议，只提示用户可以自然语言询问“你能查什么”。
- 统一 `user` 用户表，以及飞书身份、数据库权限、专属云盘目录和 Lingxi 状态的最小化保存、停用与审计规则。
- 自动准入、用户环境创建、数据库到飞书多维表格的权限发布链路，以及当前用户 MCP 权限同步与问数就绪确认；Lingxi 不复制 MCP 的逐条数据过滤。
- 生产数据库的具体产品、托管方式、备份恢复和 `biai-stage` 测试数据库隔离方案；这些实现选择尚未确定，但不改变“生产数据库是 Lingxi 准入、权限记录和发布内容唯一权威来源”的产品规则，实际问数范围仍由外部 MCP 决定。
- 数据库权限记录的字段、变更责任和有效性。

**管理员处理**

- 为重名、必要信息缺失、状态不可判定、环境创建异常和 Lingxi 侧权限发布异常建立可恢复、可追踪的管理待办。
- 管理员以个人身份通过经批准的 AI Agent 连接 Lingxi 管理 MCP；管理 MCP 身份绑定唯一的本人飞书身份，共享身份和普通业务用户不能查询或准备管理动作。
- 管理 MCP 按权限管理员、运维管理员和超级管理员三类角色分别提供能力：权限管理员处理用户准入和问数权限，运维管理员处理环境和同步异常，超级管理员新增或移除三类管理员；没有超级管理员时由持有服务器 Root 权限的 Ops 运维工程师通过受控流程恢复一个身份已经核实并绑定飞书的现有用户。
- 选择正确数据库记录并继续开通、终止开通、收回权限、停用、恢复、从当前运行环境删除用户、安全重试和管理员角色变化等写操作先形成待确认动作，不由 AI Agent 或 MCP 直接执行。
- 待确认动作发送到管理 MCP 身份所绑定的本人飞书私聊；卡片发送失败、过期、重复、角色被收回、目标状态变化、回调不明或审计失败均不执行。
- 受控管理群只接收待办和结果通知，不提供审批卡片、管理命令或群内执行入口。
- 管理查询、准备动作、卡片确认或取消、执行结果和拒绝结果形成可关联的审计记录，并在真实管理 Agent、真实管理 MCP 和真实飞书卡片链路上完成验收。

**问数与会话**

- 每次查询前读取当前有效的 Lingxi 用户与服务状态、权限变化发布到飞书多维表格并确认 MCP 同步、账号停用后阻止新问数但允许已开始任务正常完成、调岗记录更新及用户通知的完整链路。
- 同一对话的多轮上下文、`/new` 重置当前所在私聊或话题且不影响其他话题。
- 按“上一条任务结束到下一条新任务开始超过两小时”开启新会话，且任务执行时长本身不触发新会话。
- 收到消息立即添加表情、不同飞书话题并发、同一话题运行中消息（含 `/new`）只提示且不入历史不排队，以及 `/stop` 只停止当前话题后续处理、不撤回既有产物并说明停止阶段的完整体验。
- 飞书问数是否满足公司、指标、时间和关键结果均可核对，MCP 返回数据最新时间时展示、未返回时直接省略，MCP 未返回数据时不推断权限原因，以及三轮内收敛和阻断错误门槛。
- 用户自然语言询问“你能做什么”或“我能查哪些指标”时，Agent 根据 MCP 当前指标列表和说明回答；不实现 `/help` 命令或由 Lingxi 维护的固定能力清单。

**交付**

- 业务标题、正文底部当前动作与低频耗时、逐步回答、完成总耗时和同话题普通文本兜底的飞书交付样式；不展示预计剩余时间或内部过程日志。
- 为每个用户创建机器人名下的专属云盘目录，仅授予本人读写，并把全部正式产物创建在该目录内。
- 仅向当前用户交付飞书文档、电子表格、图片和其他允许文件的真实结果，交付前确认授权成功，以及送达不确定时不重复发送的体验。
- 只有已经完成当前权限同步验证的用户才能通过问数 MCP 查询；实际可见的数据范围、数据源、数据粒度和下钻程度由 MCP 按该用户生效权限决定，Lingxi 不增加逐条数据过滤。

**高级工作台**

- 用户通过飞书之外的方式单独申请 JumpServer、管理员在链路外通知、飞书与 JumpServer 不共享上下文的完整体验。
- 用户在浏览器终端中进入本人环境并运行 Claude CLI。
- 统一的交付 Skill：复用飞书通道转换文档、写入该用户的同一专属云盘目录、把链接发送给用户本人。

**保留、审计与验收**

- 正常运行中的原始聊天、用户可见结果、技术审计、任务问题、Agent 会话文件、人工核对详情和待确认操作参数最长不超过九十天，飞书聊天按飞书及公司规则保留；公司内部审计可在该期限内按授权复核完整聊天及敏感业务内容，正式产物由用户管理，中间文件及时清理。数据库备份、WAL 归档和用户目录备份不受九十天期限或单用户删除影响，按公司的灾备规则管理，恢复历史备份可能重新带回历史用户内容。从当前运行环境删除用户的完整编排尚待实现和验收。
- Lingxi 与独立审计治理能力的长期边界：后者可接收业务问数和管理员处理审计事实用于风险复核和持续优化，但不接管开通、管理授权、权限或问数主链路；该集成尚待实现和验收。
- 三名真实业务用户覆盖至少两种职能、两种公司权限范围并连续试用七个工作日的首期真实验收。
