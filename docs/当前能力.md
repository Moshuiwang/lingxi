## 已验证的 Claude 执行链路事实

以下包含前身项目 `bi-ai-agent` 的生产复现，以及 Lingxi 在 `biai-stage` 的 Issue #23 受控验证。它们是执行层选型和后续实现的输入，不代表 Lingxi 的用户问数能力已经上线。背景详见[Claude 执行链路的已验证事实与管道投递风险](参考证据/Claude执行链路的已验证事实与管道投递风险.md)，本次验证结论见 [Issue #23](https://github.com/Moshuiwang/lingxi/issues/23)。

- 百炼兼容端点可以承载 Agent 会话：已在真实端点取得可回读证据，覆盖新建会话、`resume` 恢复、只读 MCP 调用与回执、终止事件。因此模型提供方不是这条链路的主要风险来源，Lingxi 不重跑这一项。
- 前身项目"运行完成但用户侧空结果"的根因**不是百炼**，而是 `claude` CLI 在非 TTY 管道下可能不写出终止事件。归因已由生产复现确认：模型已生成答案并落盘，承载进程未从 `stream-json` 通道收到。
- Lingxi 选定的 Python Agent SDK `0.2.128` 使用自带 Claude Code CLI `2.1.220`、真实百炼端点和真实只读 MCP 完成了 1 个连通回合及唯一一轮 39 个正式回合。40/40 回合均取得非空最终正文和唯一终止结果；正式回合 39/39 的最终助手正文与终止结果哈希一致，最长正文 13,049 字节。新建、`resume`、两会话交替和长结果均未观察到空结果、截断、串会话或终止事件缺失。**Agent SDK 双向流式非 TTY 路径的正文与终止事件投递在该固定组合下成立。**
- 同次验证确认受控 Skill 可以实际加载，`PreToolUse`、`PostToolUse` 和 `Stop` 可采集。
- **`allowed_tools` 加 `permission_mode="dontAsk"` 不是严格白名单**：第一轮中未明确禁用的 `CronCreate` 被实际执行（随后由 `CronDelete` 删除）。只列出允许的 MCP 工具不等于其他内置工具不可执行，新增内置工具默认可被调用，Skill 与 `CLAUDE.md` 的文字约束不能代替运行时强制限制。
- **在 `PreToolUse` 返回拒绝是执行前的真阻止**：2026-07-28 的定向补测在 `disallowed_tools` 完全为空、hook 为唯一屏障的条件下，3 次非白名单调用（`Bash`、`Write`、`CronCreate`）全部被拒且均无 `PostToolUse`，文件副作用探针确认目标文件未被创建，`CronCreate` 被拒后无 cron 残留。被拒回合仍取得非空正文和恰好一次终止结果，同回合内白名单工具照常执行。因此执行层的只读边界**可以做成强制的**。
- **`PostToolUseFailure` 可以采集，但语义是「工具抛错」而不是「用户没拿到结果」**：补测中 2 次真实工具执行失败（MCP 协议层 `isError=true`、MCP 进程调用中退出）均触发该回调 1 次且 `PostToolUse` 0 次，回调带工具名、入参和错误文本。被 MCP 包成正常响应的业务失败（如「指标不存在」）**不会**触发它——要审计「用户实际没拿到结果」，必须额外解析工具回执内容。
- **权限拒绝没有任何 hook 回调**：拒绝后 `PostToolUseFailure`、`PermissionDenied`、`PermissionRequest`、`PostToolUse` 均为 0。同批测试注册了 SDK 类型未声明的事件名并确认 CLI 会透传（`PostToolBatch` 实际触发 7 次），因此 0 次不是「没注册上」。拒绝在 SDK 消息流中**仍可采集**：每次拒绝产生一个 `is_error=True` 的工具结果块。审计链必须由「自己在 `PreToolUse` 记账的拒绝决定」加「消息流中的错误工具结果」两部分合成，**不需要为此改用 TypeScript SDK**。
- **只读工具边界已经进入可执行 worker 并通过 L4a**（Issue #37/#51）。`python -m lingxi.apps.worker` 把默认拒绝的 `PreToolUse` 屏障和审计装进真实 Agent SDK `0.2.128` / Claude Code CLI `2.1.220`：基线提交 `90573e6` 的真实回合证明越权 `Write` 在执行前被拒且无文件副作用，MCP 以正常响应包装的业务失败被记为 `not_obtained`；PR #60 只修正成功 `metrics` 回执和飞书部门 ID 类型，因此两项负向结论按验收范围沿用，未追加真实模型调用。修复后的合并提交 `07732d9` 另以 1 次真实 `list_metrics` 证明正常结果被记为 `obtained`；合并提交的自动门禁继续覆盖三条路径。所有已执行真实回合均退出 0、正常收口、没有执行绕过或敏感值泄漏。审计仍保留两条知情接受的脱敏残余缺口（纯字母短秘密出现在自由文本里、模型把凭据伪装成合法形态的工具名），见门禁的 `V-审计-03`。这只证明单回合 worker 与真实百炼/MCP 的执行接缝，不代表飞书消息入口、多轮会话或生产服务已经接入。
- **`disallowed_tools` 的规则拒绝完全静默，而且会制造审计盲区**（Issue #29 实测）。把工具放进 `disallowed_tools` 后，模型确实发出了该调用，但 `PreToolUse` **一次都不触发**——拦截发生在 hook 之前，模型侧收到的是「工具不可用」而不是「调用被拒」。消息流里只留下一个 `is_error=True` 的工具结果块，其 `tool_use_id` 在执行层记账里没有对应记录。因此 `disallowed_tools` 只能作为纵深防御的外层；执行层把这类回执单独记为「本层未判定」的调用，不谎报为放行，也不谎报为本层拦截。
- **子代理内部的工具调用经过同一个 `PreToolUse` 屏障**（Issue #29 实测）。子代理工具在 CLI `2.1.220` 里名为 `Agent` 而非 `Task`；放行 `Agent` 后，其内部的 `Write` 与 `Bash` 调用均触发主会话注册的 `PreToolUse` 并被拒绝，副作用探针确认无文件写入。**但启用子代理会让同一回合出现 2 个终止结果与 2 次 `Stop`**，与编排层依赖的「恰好一次终止结果」冲突，因此首期对 `Agent` 与 `Task` 两个名字都保持默认拒绝；将来启用前必须先解决主会话与子代理终止结果的区分。
- **身份链路与银河权限的正式组件已合并并完成已认领范围的 L4a**（2026-08-06，PR #48/#49/#60、Issue #51）。已验证：宿主机 `0600` 加密凭据可真实轮换且不进入业务库；正式目录适配器可完整遍历；固定花名册 Base 可读取并以人员 ID 唯一关联 710 人；银河同批五表已完整导入测试库（331 / 1574 / 3334 / 6517 / 58），重复导入不产生第二完成批次；产品负责人王志鹏的 1 条真实私聊样本可唯一定位、实时确认在职并得到“准备建档”判定，本轮未实际建档。产品负责人已明确本次只验 1 人，原计划第二名样本未覆盖，不记作 2/2。**仍未接线**：正式首聊事件入口、持续组织同步、建档、权限发布和用户通知；组件通过不等于用户已经可以开通。

- **`delivery_expired` 的收敛与用户提示**：Worker 写出终态后在 `awaiting_delivery` 窗口停掉 Gateway，仅在隔离库把该终态事件置为已过期，由仍在运行的 Worker 收敛，得到 `failed / delivery_expired`、终态正文已清空、话题已释放；Gateway 恢复后用户下一条主动消息上收到固定过期提示且只出现一次，随后新任务正常成功（r20，候选 `7e60e79`，[评论 5307686612](https://github.com/Moshuiwang/lingxi/issues/154#issuecomment-5307686612)）。**边界**：24 小时是数据库触发器里的硬编码值，本轮受控构造验证的是「到期后如何收敛、用户看到什么」，**不是真实等满 24 小时**。

- **会话空闲满两小时由系统到点主动清除正文**：一条已送达结果在空闲满两小时并留出一个 scheduler 周期余量后，终态正文数据库字节数为 `0`、恰一条 `agent_session_cleanup` 记录（`reason=idle_timeout`）且已完成、临时用户卷中 Agent 会话 JSONL 数为 `0`；用户在同一飞书会话中原消息与机器人结果仍可读（r12，候选 `181312c`，[评论 5306400686](https://github.com/Moshuiwang/lingxi/issues/154#issuecomment-5306400686)）。该清理**不依赖下一次任务入队**。
- **输出安全的局部遮蔽与整段拒发各有确定的用户终态**：用候选内的受控 canary 开关 `LINGXI_WORKER_OUTPUT_SAFETY_CANARY` 分两档在真实队列链路验证。`withheld` 档：用户得到与内容目录逐字一致的「本次结果涉及需要保护的内容，已被安全策略拦截，未能提供结果；如有需要请联系管理员，系统不会自动重试。」，终态 `terminal_kind` 与 `error_kind` 同为 `redacted_withheld`，未输出任何业务结果。`masked` 档：用户拿到幸存的业务正文加「已隐藏」占位符、不含合成提示原文，任务 `succeeded`、输出安全记 `blocked=true`（r17，候选 `38790f5`，[评论 5308527441](https://github.com/Moshuiwang/lingxi/issues/154#issuecomment-5308527441)、[5308577363](https://github.com/Moshuiwang/lingxi/issues/154#issuecomment-5308577363)）。两档结束后 canary 变量均已撤除并回读进程环境确认为零。**边界必须写清**：该 canary 是**确定性注入夹具**——它把已配置的合成提示词在出口安全约束**之前**注入最终正文，随后走与真实泄露完全相同的检测、遮蔽与投影路径（并非直接改写判定结果）。因此本轮证明的是「出口检测对已知登记内容的命中，以及命中后的终态记录、用户可见文案、正文取舍与低敏审计整链正确」；**不证明**出口检测器能识别真实模型输出中**未预先登记**的敏感内容形态——该差异面由白盒与变异验红用例把守，不在真实链路验收范围内。此前在候选 `7e60e79` 上依赖模型「恰好复述」合成标记的尝试未产生任何可检测内容、回合正常结束（[评论 5307479170](https://github.com/Moshuiwang/lingxi/issues/154#issuecomment-5307479170)），确定性注入夹具正是为消除这种对模型行为的依赖而加入（[#142](https://github.com/Moshuiwang/lingxi/issues/142)）。
