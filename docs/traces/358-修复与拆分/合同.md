## 4. 验收标准

（逐条明细见 `验收.md`；此处为等级与纪律合同）

- **证据等级要求**：
  - Epic F 修复批：关键路径 ≥L3（本地真库测试含否定/变异用例）+ 合入后 stage L5；#353 追加受控重驱 L4a；#352/#349 的自然触发为机会型 L6，**不作关闭前置**（关闭以确定性测试+受控验证为准）。
  - Epic G 调度：**必须 L4a**——一次真实 stage 全量轮实测（非注入模拟），healthcheck 全程 healthy + 其他职责未漏跑（#340 验收标准原文）。
  - Epic H 拆分：工程结果——纯移动式重构，既有全部测试不改断言全绿（变异哨兵）、每步独立 commit 可回滚、棘轮基线归零、模块文档一句话职责；**不宣称任何用户能力变化**。
  - Epic D 文档：L2 回写 + 读回核对；#333 的 Project 写入需回读截图/API 确认。
- **双通道纪律**：用户可见断言=stage 结构化日志 + 平台 API/飞书页面任取其二，一致才定论；冲突升产品负责人。
- **受控触发夹具**：#353 重驱用既有检查点恢复路径（确定性）；#349 受控验证的「MCP 不可达」夹具只允许作用于受控会话配置，默认关、用后撤除并回读，**不得触碰共享真实 MCP 端点本身**；#352 确定性证据在测试层注入 denied 序列，不硬造线上模型行为。
- **请产品负责人做真实验证前**：先出示就绪自检（前提逐项核对+日志回读+预判断点）。

## 5. 成本预算

- **CI Epic Full ≤5 次**，仅批次终点消费：修复批 1、#340 批 1、拆分两批各 1、机动 1。文档批按 #298 收窄后的路径分类不提级；若意外提级计入机动额度。每次批次收口评论报「Epic Full 次数 / 合入 commit 数」。
- **stage 受控升级 2 次**：W2 一次（覆盖修复批+#340），收口末次一次（同步拆分与文档终态）。
- **模型配比**：实施 / 调查 / 校验一律 sonnet；opus 仅限：每批次一次批量审查、#340 设计短文（S-W0-1）、收口前对抗核账。
- **编排者模型（v14 必填）**：**Fable + xhigh 思考档位**（产品负责人 2026-08-28 随批准指定）；编排会话接力=v14 §6.8 tmux 命名窗口模式，产品负责人可随时 attach 查看与操作。
- **外部审查（codex）配额：0 次**——本 Trace 无权限面/入口面变更；若某批次实际触碰权限面，停下单独请示后再加一轮。
- 大 workflow（>50 万 token）仅收口核账一次，开跑前查配额余量；对抗验证分批派。

## 6. 主线声明

- **主线**：§1 六项里程碑。任何派发 / 立项 / 修复先过判据「不做它，里程碑能不能达成」；不能达成才进当前批次，其余进「里程碑后」队列默认不动。
- **批次纪律**：默认攒批进批次分支（子改动只跑 Story Fast）；批次终点一次本机 full + 一次 opus 批量审查 + Epic Full + 唯一合并人合并；**面向 `main` 串行合并，先就绪先合**。
- **单一写入者**：并行实施卡各用独立 worktree（R-WT）；`#350 拆分期间冻结对应文件的并行功能卡`（Issue 原文约束，冻结表由 S-W0-3 产出）；同一文件同一时刻只有一个 Owner。
- **收尾必含**：环境清理与残留盘点（临时进程/容器/worktree 谁建谁清；`lingxi-test-pg` 为登记保留项）、收口核账（多代理逐 Issue 完成标准核对）、批次收口评论（UTC+北京双标注、预算消耗、commit 数）、§6.8 接力序列（收口评论 → /cost 快照 → 交接评论 → 拉起继任或正常退场）。
