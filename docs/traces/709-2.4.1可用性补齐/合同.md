# 开工合同：2.4.1 可用性补齐与 stage 部署（Trace #709，Issue 链接：https://github.com/Moshuiwang/lingxi/issues/709）

> 方法版本：#678 v19。合同版本：**v1**。批准依据 = 产品负责人 2026-09-09 指令（原话要点：「足够快地完成、节省 CI 尤其 build」「大量安排 subagent 同步进行」「减少 PR 数量」「需要人类决策的你自己决策并记录」「**进 stage 吧，目标变成 stage 部署，时间窗口无限**」「**如果你能体验验证部分内容，给我留下的越少越好**」「**具体的验收项目，可以到时候写一个 Issue，方便交接**」）。**本 PR 合并即批准 v1**。

## 1. 目标

- **用户结果一句话**：把 2.4.0 那批功能从「代码在生产但开不出来」变成「装得上、切得动、查得到」，并**在 stage 上真的跑起来**，只把必须真人做的那几步留给产品负责人。
- **里程碑（何谓「到了」）**：四项实现通过完整门禁与内外审查 → 冻结候选 → **用同候选的四镜像测试包把 stage 部署起来** → 把代理能自验的验收项**全部自验完** → 把剩下必须真人做的项写成一张可直接照做的交接清单。
- **完成定义（哪些 Issue / 断言收口即 Delivered）**：#701、#702 的可观察完成标准达成并在 stage 实测；#657 的 gateway 缺口在三个容器实测可用；#668 的外审 P2-5 守卫回到候选；#703、#705 的全部内容由本 Trace 自验完成；#704 的可自验部分完成、真人部分转为交接清单。
- **既定条款**：交付终点按 #678 §3.2 逐项声明——PR 合并、组件存在、CI 通过都不自动升级实际终点。**本 Trace 的终点不含生产、不含 `release/**`、不含合并 PR。**

- **stage 授权依据**：产品负责人 2026-08-30 已登记的 stage 全权限常设授权（留痕 #469），加 2026-09-09「进 stage 吧，目标变成 stage 部署」的本次指令。**生产仍除外。**

## 4. 验收标准

### 4.1 代理自验（本 Trace 必须做完，产品负责人不参与）

- [ ] 不追加内测覆盖文件时，`docker compose config` 渲染结果与改动前逐字相同；stage 起来后监听器**不注册**，启动日志读得出「因缺配置不注册」。
- [ ] 追加覆盖文件并给全四个变量时，scheduler 起得来且监听器**注册**，`python -m lingxi.apps.innertest_status` 回读一致。
- [ ] 名单启用工具在 stage 真库上：`plan` 零写入；摘要不符时 `apply` 零写入并给确切拒绝码；`apply` 成功后 `verify` 回读 `mode=database`、版本、摘要、成员数一致；五类负例各一条。
- [ ] 追溯入口在 **gateway / scheduler / worker-queue 三个容器**各查一次同一号码，返回同一份记录；两个变量都缺时提示写明找过哪些变量名。
- [ ] 未登记动作类型的确认被明确拒绝、分类 `entry_not_assembled`；去掉守卫即复现 `KeyError` 判红。
- [ ] 受限通路：受限身份只能执行固定 relay；错 UID、错 socket 权限、主体绑定版本不符三种情形分别被拒绝；三个 MCP 工具可调用，且**准备扩员不新增任何资格**。
- [ ] 停止与恢复：强杀 scheduler 后监听器可恢复；SIGTERM 后按 #603 预算停止接收并排空，日志读得出「收到信号」。
- [ ] 三服务健康、飞书长连接建立、库停留 0092 且业务行数不变、启动日志逐条回读职责注册情况。
- [ ] 15 项静态门禁本机全绿；完整测试输出含 `Ran N tests`；同候选一次完整 Epic Full 全绿。
- [ ] 内部审查一轮 + 定向复核一轮；外审两路各一份报告，发现逐条回源裁定。

## 5. 成本预算

- **完整门禁次数上限：≤ 3 次**（预估 2 次：首推一次、外审修复包一次）。仅在批次终点消费。
- **时间窗：不设硬期限**（产品负责人 2026-09-09「时间窗口无限，因为除了你没人用 stage」）。规划期预估：代码阶段约 1 个工作日，stage 阶段约 1 个工作日；收口评论逐项对账。
- **PR 数：1 个**（按 #678「批次数 + 2」估法本应 ≤ 4，本 Trace 主动压到 1）。
- **为什么 1 个 PR 最省**：`scripts/ci/classify_story_changes.py` 的 `FULL_PREFIXES` 含 `deploy/` 与 `migrations/`，本批必然改 `deploy/`，因此即使走 `epic/**` 分支，Story Fast 也会直接复用同一份 Epic Full——拆 PR 不省 build，只多轮次；另外建 `epic/**` 分支还要先用 bootstrap PR 刷检查（先例 #106 / #164），白白多一次完整门禁。
- **攒批推送规则（硬规则，违反即浪费一次 build）**：
  1. 四项**全部**在本机通过 15 项静态门禁与完整测试之前，一次都不推。
  2. 首推即候选，不是探路；推之前内部审查的修复包必须已经并进去。
  3. 外审发现攒成**一个**修复包再推第二次；不逐条推。
  4. 同一 PR 连续推送会 `cancel-in-progress`；每次推送前确认没有正在跑且还需要其结论的 run。
  5. 门禁判红一律先本机复现再改，**不靠重推试**；注释卫生棘轮与用词门禁是最容易判红的两项，推送前必跑。
  6. **不 force-push、不 amend 已推送的提交**；修正一律追加提交。
  7. **stage 验收一旦开始，候选冻结不再改**——2.4.0 那轮的代价就出在改候选让已完成的验收失去绑定。
- **模型配比**：编排者 Opus 5 max；实施 / 复修 Sonnet xhigh；唯一独立审核者 Opus 5 xhigh；规划者 / 元守护 = 本规划会话（Opus 5）转任。
- **外部审查配额与指定位置**：**两路各一轮，只在冻结候选之后、首推之前消费一次**——Codex CLI 的 astra medium 看装配与权限面（覆盖 #701 / #702），本机 gemini flash 3.8 看回归与假证据六型（覆盖 #657 / #668 与全部新增测试）。外部审查**不作为**第二名独立审核者。
- **子代理人次上限：≤ 20**（预估 14：只读盘点 4、实施 4、外审 2、内部审核与定向复核 2、stage 阶段只读取证 2）。每次派发编排者自挂兜底观察；子代理不得再派子代理；单个子代理任务预计超 60 分钟必须切分。**stage 阶段不派写入型子代理**——同一时刻只允许一个客户端连 Bot-Test。
- **既定条款**：大 workflow 开跑前查配额余量；对抗验证分批派。

## 6. 主线声明

- **本 Trace 的主线是**：让四项一次做对、只花两次完整门禁，把 stage 跑起来并把能自验的全验完。任何派发前先问「不做它，stage 能不能跑起来并验完」。
- **`execution_adapter`**：`claude_tmux_named_session`——常驻 tmux session `TZ-server` + 批次代号 window `lingxi-241`；元守护 = 规划者转任，只以外部证据判活，不实施、不持合并权。
- **单一写入者**：当任编排者持批次工作树 `/tmp/lingxi-241-work-<日期>` 与推送权；实施子代理各用**独立 worktree + 独立测试库容器名与端口**，改完先 commit 再汇报；审核子代理只读固定候选。共享文档文件只由编排者改。
- **既定条款**：默认攒批进批次分支，批次终点一次完整门禁 + 一次批量审查；批次收口固定序列（收口评论 → 交接评论 → 继任 window → 接管登记 → 租约转移 → 退场）。
- **收尾必含**：环境清理与残留盘点、任务表勾选回写、批次收口评论（UTC + 北京双标注 + 预算消耗 + 完整门禁次数 / commit 数 / 子代理人次）。**本 Trace 的 stage 实例是「刻意留驻」，按 S-5-10 显式登记，不按谁建谁清停掉。**
