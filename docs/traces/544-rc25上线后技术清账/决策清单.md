## 二、产品负责人原话（逐字保留）

**花名册重复邮箱——认知更正**

> 「重复邮箱问题，我已经回答过一次，这属于离职后员工又入职导致的，花名册中已经做好了当前在职状态的标记，我们不用管哪些离职员工（或者说最多离职后需要停止授权，其实离职后，他的企业飞书账号也不能用了，所以即使我们不停止授权也问题不大），花名册不可更改。如上你要记录下来，否则总是认为花名册有问题。」

执行侧：**不向花名册方转发任何去重请求**（该项已从外部协调清单移除）；重复建档数（86 组）**不是风险量**；X-1 的生产预检必须**先按在职状态过滤**，只统计在职员工中是否存在同邮箱不同人。

**D-15 修订**

> 「按批来，但只读前置可随时开始。审核增加一个codex 的外部审核，轮次可以有3次。」

执行侧：W0 只读前置**立即开始**，不再等 09-03 09:00、也不以三件套 PR 合并为前置；内部审核 3 轮 ＋ codex 外部审核 1 次。

**独立审核者模型**

> 「独立审核者使用opus max吧，没有fable 5.1 可用」

执行侧：唯一独立审核者由 `Fable 5.1 / xhigh` 改为 `Opus 5 / max`。**已知代价**：编排、实施、审核同为 Opus 系，跨模型交叉只剩 codex 外审一次；产品负责人在 Fable 不可用的前提下知情选择（同源性风险与缓解见 [合同.md](合同.md) §5）。

**旧系统退役**

> 「旧系统可以清理退场了。」

追问后确认：**立刻开始完整退役**（不等 09-09 七天观察期）、**另起运维批**承载 → [#546](https://github.com/Moshuiwang/lingxi/issues/546)。元守护已提示「退役会拿掉 Lingxi 出大问题时最快的回滚手段」，产品负责人在知情后维持该选择。原 D-6 后半（请对方去掉 7 个手工脚本可执行位）并入退役批，**不在本 Trace**。

## 三、新增未裁项（W0-3 只读复核查出，编排者不自行改判）

| # | 事项 | 选项（单字可答） | 编排者建议 | 为什么需要你 |
| --- | --- | --- | --- | --- |
| **D-25** | **D-7「乙」在平台层面不可行**：GHCR 不接受 GitHub App 安装令牌（GitHub 员工在 community #171423 逐字答复，已标 Answered；#24636 另一位代表：只有 Actions `GITHUB_TOKEN` 与 PAT 可以）。fine-grained PAT 同样不支持。**失败形态尤其危险**：`docker login` 返回 Login Succeeded、`docker pull` 才 denied——按乙建的刷新单元会永远显示绿灯，故障只在升级窗口才爆。唯一可行形态＝**专用机器账号的 classic PAT（只勾 `read:packages`）**，长期有效、不需要小时级刷新 | **机**（建专用机器账号 + classic PAT）／ **人**（用你个人账号的 classic PAT）／ **缓**（本批不私有化） | **机** | 你已裁「乙」，但平台不支持；改用哪种凭据是你的账号级外部动作，且「机」能同时解掉 `deploy/README.md:158`「不得用个人凭据」那条冲突 |
| **D-26** | **私有化可能不可逆，且没有 API**：GitHub 官方文档三处逐字写「一旦公开就不能再改回私有」，另两处又说 admin 可双向设置——**自相矛盾，未坐实**；改包可见性**没有 REST 端点**（27 条全量端点已核），只能网页 UI 手动做，无法预授权给代理。另：stage 与 prod **都从未登录过 GHCR**（两台均无 `~/.docker/config.json`，一直匿名拉），改 private 那一刻**两台同时失去拉取能力**，而 runbook `:197` 禁止现场重建，**回滚路径一起断** | **探**（先用一次性探针包验证可逆性，再决定四包）／ **缓**（本批不私有化，只把凭据与就绪探针装好）／ **切**（不验直接切） | **探** | 不可逆的外部动作 + 可能同时打断两台机器的拉取能力，必须由你决定；**无论选哪个，都不能拿四个生产包试** |

**执行侧现状**：D-25/D-26 裁定前，W0-8（改 private）与 W0-12（凭据与就绪探针）停在原地，四包保持 public。**这两项不阻塞本批其余任何工作**——4 条 P1 根治、#538 修复、#541 实现、文档面、Codex 债都照常推进。
