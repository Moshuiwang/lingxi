## 给产品负责人

- **最终得到什么**：旧权限写入方与旧正式机器人退出；`biplus-prod` 运行经 stage 验收的 Lingxi 2.0 固定制品；`Bot-Prod` 成为唯一正式入口，存量用户与新用户都能走到“开通完成”，并真实问数成功。

- **当前外部前置**：没有产品决策待定；AWS 变更控制路径、实时报价与窗口必须在执行前读回。当前无法从本机直接执行实例规格变更时，相关 Step 保持 Pre-ready，不以降低生产容量替代。

## 六段式合同

### 1. 目标

按三批完成：P1 首发准备、P2 单向硬切与真实上线、P3 稳定观察与最终收口。真实上线成立必须同时具备固定制品、唯一旧写入方退出、唯一 Bot 长连接、生产数据库与服务健康、Bot-Prod 两类用户路径成功；其中任一缺失都不能以“服务已启动”代替。

### 2. 授权终点

授权在获批 Gate 内完成生产主机准备、实例规格变更、Docker / Compose 安装、最小权限配置、固定镜像拉取、生产数据库迁移、备份与隔离恢复演练、旧写入方和旧正式服务永久停用、正式权限差集导入、Lingxi 生产服务启动、Bot-Prod 切换、真实用户验收、`v2.0.0` 发布点、观察与 Issue 收口。

授权不等于跳过 Gate。没有 AWS 控制路径、候选不固定、备份恢复失败、第二写入方未排除或 Bot 独占未确认时，受影响步骤必须等待。

### 3. 不做清单

- 不在生产构建镜像、编辑源码、临时打补丁或拼装不同批次制品。
- 不做灰度；不让新旧 gateway、旧 Bot 或权限写入方同时运行。
- 不恢复旧权限写入归属。跨过 G-CUT 后是产品层单向门，失败只修 Lingxi；旧程序与数据保留只读证据，不重新启用写入。
- 不把 stage 凭据复制到生产；除既有百炼端点例外外，生产凭据与研发 / stage 全隔离。
- 不在本 Trace 提前清理 #411 保留的 stage 旧库与 dump；按其观察期独立收口。

### 4. 验收标准

- #445 产出的四镜像来自同一冻结候选，digest 固定且唯一 Sol xhigh 审核无 P0/P1。
- 生产主机达到仓库批准的 8 vCPU / 32 GiB 容量；默认目标 `m6a.2xlarge`，替换为其他规格须保持同等资源并修订 Ops 证据。
- 生产数据库从零迁移到当前 head；真实备份能在隔离目标完整恢复并通过关键表 / 约束抽查。
- 旧系统所有定时与事件写路径、旧 Bot/API/文件发送入口全部停用；跨满一个 15 分钟旧写周期后正式表无新写入、无删除、行键与令牌形状不变。
- 新栈启动后 15 分钟基础设施健康；一名存量令牌用户走 adopt、一名新用户走 issue，均到“开通完成”，至少一人通过 Bot-Prod 真问数得到可用结果。
- 上线即全量整体切换；48 小时为上线后样本观察，7 天为完整观察。两段未走完时可声明“已上线、观察中”，不得声明 Trace 已最终关闭。

### 5. 成本、窗口与频率预算

- P1 目标 ≤4 小时，P2 切换窗口目标 ≤2 小时，P3 为 48 小时 + 7 天观察；等待时间不计代理墙钟，但必须用自动监控 / heartbeat 留痕。
- 每批最多一次完整独立审核；没有第二审核者。高风险动作前后都由同一个审核者核对固定执行包与结果。
- 生产变异严格串行；可并行的只有只读盘点、脱敏证据核对、本地配置契约和观察面。
- AWS 实时报价与预计停机时长在 P2 前再次读回；未得到可执行控制路径时停止，不以当前低配承载生产并发。

### 6. 主线与批后自动接力

- **P1 首发准备**：新编排任务完成生产运行依赖、固定制品、生产配置、数据库迁移、真实备份恢复和硬切执行包；不启动新 Bot / 外部消费。
- **P2 硬切上线**：另一新编排任务冻结最终时间线，经唯一审核后停旧写入与旧入口、变更主机规格、跨周期证明唯一性、导入差集、启动新栈、完成 Bot-Prod 验收并形成 `v2.0.0`。
- **P3 观察收口**：第三个新编排任务通过 heartbeat / 监控完成 48 小时和 7 天观察，关闭 #263、#449、#448 及符合条件的尾项。

P1 和 P2 收口时，必须依次写收口评论、自足交接、创建继任顶层任务、继任登记、转移写租约，旧任务才退出。P3 是最终批，可在 Trace Closed 后不再创建继任。

## 规划事实快照（2026-08-30，只读）

- `biplus-prod` 当前低于批准容量，未安装 Lingxi 容器运行栈；生产 Supabase 凭据事实源已就位，但生产迁移、备份恢复和服务启动均未执行。
- 旧系统仍是正式权限表的真实写入方：定时写周期为 15 分钟，且旧 Bot / API / 文件发送路径也能触发写入。旧写入逻辑会删除不在其期望集中的行，因此硬切后严禁重启旧写入方。

- [#263](https://github.com/Moshuiwang/lingxi/issues/263) 已有单向硬切裁定；旧正文的“尚无只读事实”和旧重签方案已被后续证据推翻，执行以本 Trace、#263 最新回写及 [#449](https://github.com/Moshuiwang/lingxi/issues/449) 为准。

## 授权与停止条件

| 动作 | 授权 | 前置 | 恢复 / 失败语义 |
| --- | --- | --- | --- |
| 安装运行时、配置、拉镜像 | 已授权 | P1 唯一 ops Owner、零凭据回显 | 恢复包 / 文件前态；不启动外部入口 |
| 生产 DB 迁移与备份恢复 | 已授权 | 固定代码、隔离恢复目标 | 数据只前滚；失败不进入 P2 |
| 主机扩容 | 已授权但 Pre-ready | G-AWS 与已知停机窗口 | 扩容失败恢复旧主机服务，不跨硬切门 |
| 停旧写入 / 旧 Bot/API/文件路径 | 已授权 | P2 reviewer 通过、切前快照 | 产品层单向门；跨门后不恢复旧写入 |
| 正式差集导入、启动新栈与 Bot-Prod | 已授权 | G-CUT | 失败停受影响新入口并前修 |
| 删除旧系统、旧数据或生产证据 | 未授权 / 不需要 | 不适用 | 保留只读；另行清理合同 |

出现以下任一情况立即停止受影响步骤：候选 / digest 不一致；第二写入方或第二 Bot 连接；正式表意外删除、密文变化或权限扩大；数据库迁移 / 恢复失败；存量令牌无法安全 adopt；用户路径无法到可理解终态；需要现场改代码、降低容量、扩大权限或改变单向门。
