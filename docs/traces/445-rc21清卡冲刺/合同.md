## 六段式合同

### 1. 目标

单批完成 #437、#438、#439、#440、#441、#442、#443、#444 的实现、独立审核、合并、发布和 stage 自证；按各卡可观察完成标准关闭八卡，并关闭 #418。最终产物是一个可以直接进入生产 Trace 的冻结 rc21 制品组，不是“代码已写但用户路径未验”的半成品。

### 2. 授权终点

授权编排者在 MacBook Air 本地研发环境创建 worktree、分支、提交、Story PR 与 Epic PR，运行相称测试；合并通过门禁的 PR；触发 Main Publish；按 runbook 升级 `biai-stage`；使用 `Bot-Test`、测试数据库和受控注入完成 L4a；回写并关闭范围内 Issue；批终创建 [#448](https://github.com/Moshuiwang/lingxi/issues/448) 的新顶层编排任务。

不授权生产写入、生产服务变更、`Bot-Prod` 使用、正式权限表切换、权限白名单扩大、用户数据删除、#411 旧库与 dump 清理。

### 3. 不做清单

- 不做生产部署或硬切；不以 stage 健康冒充正式上线。
- #441 只交付幂等导入工具与 stage 测试副本演练；正式旧表差集导入留在 #263 的硬切窗口。
- #444 不做每秒读秒；采用 10～15 秒兜底更新与停滞自述。
- #439 不引入自然语言管理 Agent，不使用同卡二次确认替代独立确认卡。
- 新发现默认只登记；不影响本里程碑的范围不得塞进当前批次。

### 4. 验收标准

- 每卡同时满足 Issue 正文与“自证闭环条款”；能由代理完成的真实验证一律由执行方完成。
- #438 的真人点击确认卡是唯一需 PM 配合的关卡（约 10 秒）：真库回调集成先由代理自证；等待 PM 点击不阻塞其余卡继续，但 #438 与本 Trace 在真人一步完成前不得关闭。
- 固定候选经唯一 Sol xhigh 审核，无 P0/P1 遗留；候选变化使旧审核结论失效。
- `Epic Full` 通过并且合并树等于候选树；`Main Publish` 产出同一候选的四镜像 tag 与 digest。
- stage 三个常驻容器 healthy；八卡所需的 L4a / 真库 / API 回读证据逐卡落 Issue；受控测试身份必须显式标注为非生产。
- #437 作为生产挡板必须在 stage 复现“过期释放、未过期仍拦截”后才能关闭。

### 5. 成本与频率预算

- 目标墙钟 ≤6 小时，4 小时仍未冻结候选时预警；时间不是质量上限。
- `Epic Full` 目标 1 次、最多 2 次；本机 `full` 只在批终或统一修复后运行，不为每张卡重复。
- 高成本真实链路集中到候选阶段；每卡开发期只跑定向测试与适用 Story Fast。
- 模型固定为 Sol max 编排、Luna max 实施、单一 Sol xhigh 审核；没有第二独立审核者。

### 6. 主线与批次纪律

本 Trace 只有一个 rc21 批次，内部按三个 Wave 填满安全并发。实施者只交付 commit / PR / 自测证据；编排者持有 `epic/rc21-fixes` 唯一集成与合并租约。Story PR 串行进入集成分支，共同文件按本合同顺序解冲突；集成树冻结后才启动唯一审核者。

批次完成后，编排者必须先更新三件套与 Issue、写自足交接，再创建 [#448](https://github.com/Moshuiwang/lingxi/issues/448) 的全新 Sol max 顶层编排任务；继任登记接管后，本编排任务退出。
