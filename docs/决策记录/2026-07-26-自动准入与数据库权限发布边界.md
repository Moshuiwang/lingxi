# 决策：自动准入以数据库权限为准并通过多维表格发布

> 状态：现行
> 决定日期：2026-07-26（同日补充开通交互与匹配结果分层）
> 来源：[GitHub Issue #7](https://github.com/Moshuiwang/lingxi/issues/7)；产品负责人于 2026-07-26 确认权限权威、发布通道与开通体验
>
> 规则正文见[产品合同与外部边界](../产品合同与外部边界.md)的「首次对话与自动准入」「匹配结果与人工处理」「统一用户记录与权限变化」。本文只说明为什么这样定。

## 要解决的长期问题

Lingxi 首次面对一名飞书用户时，需要确认该用户是谁、可以访问哪些公司和职能，并把正确权限发布给 MCP。数据库、飞书多维表格和 MCP 分别保存不同阶段的状态，必须明确谁决定权限、谁只负责传递，以及状态不一致时用户能否继续问数。

同时还要回答：用户要为开通付出什么动作、开通过程中看到什么，以及“数据库里没有这个人”应该被当成故障还是正常结果。

## 决定要点

- **Lingxi 生产数据库是运行时权限的唯一权威。** 银河数据必须经受控流程进入数据库；飞书多维表格只是数据库向 MCP 发布权限的下游通道，不能反向授权。三者一致且均确认成功后，用户才可以问数。
- **开通由用户主动确认触发，并包含一次飞书授权。** 未开通用户收到引导卡片，点击「开始使用」或发送确认文本才开通；卡片同时提供「暂不需要」退出。
- **开通过程向用户流式展示**，用户看得到进行到哪一步、每一步是否成功。
- **首期只按姓名匹配数据库中当前有效的权限记录**，唯一命中且记录完整才自动通过。
- **匹配结果分三层**：唯一命中自动开通；查不到直接给出“联系 BI 同事开通银河权限”的终态；重名或记录不完整才转人工核对。
- **开通成功后由用户自己提问**，开通前发送的内容一律丢弃；成功卡片不提供示例问题或可点击建议。
- **权限变化按感知延迟承诺**：每次查询前重读权限，变更三十分钟内被感知；不承诺“权限收回即刻阻断”。

## 为什么这样定

**开通必须包含一次用户授权，不能设计成纯后台无感。** 已验证事实是：中心应用以应用身份调用 `trust_party` 系列接口返回 `1971007 App not visible to target tenant`，只有用户完成授权后、以用户身份才能取得该用户的 `user_id`、`open_id` 和 `union_user_id`。既然这一步无法回避，就把它做成用户能够理解的一次确认动作，而不是藏在后台后再失败。

**开通过程流式展示，是因为这条链路步骤多且每一步都可能失败。** 授权、匹配、建档、环境创建、云盘目录、权限发布、生效确认，任何一步卡住，用户如果只看到静默等待，既无法判断该继续等还是该找人，团队也无法快速定位问题。把过程可见化同时解决用户预期和排查成本两件事。

**“查不到”是正常结果，不是异常。** 首期面向所有内部用户，但银河的数据权限名单只覆盖其中一部分人。如果把“查不到”和“重名”一样转人工，每一个好奇点进来的同事都会变成一条人工待办和一条一个工作日的服务承诺，人工核对会被正常情况淹没，真正的异常反而被延误。把它做成带申请指引的明确终态，用户立刻知道下一步找谁，也不占用人工资源。

**只按姓名匹配，不引入部门或租户作为二次判据。** 加入部门确实能降低重名概率，但会显著增加匹配逻辑的复杂度，而且当前部门信息本身的准确性不可信——用不可信字段做判据，可能把本可唯一命中的用户误判成异常。重名转人工的成本可以接受，误判和复杂度的成本不能接受。

**不承诺权限收回即刻阻断。** 即刻阻断要求数据库变更的实时推送和运行中任务的持续复核，首期不具备这些机制，写成承诺会导致无法验收。改为“每次查询前重读权限 + 三十分钟感知上限”后，规则既可实现也可验证。已开始的任务不中途复核权限，风险窗口限于单个任务的执行时长，这是明确接受的取舍。

**本决策不选择数据库产品、托管位置、备份方案或表结构**，这些属于后续实施工作。

## 对用户和边界的影响

- 用户的数据范围只由数据库当前有效记录决定，不会因为飞书多维表格被误改、残留旧值或 MCP 状态异常而被扩大。
- 用户为开通付出的动作是明确的：点一次按钮、完成一次授权，其余由系统完成并且可见。
- 没有数据权限的用户很快得到确定结论和申请路径，不进入等待。
- 进入人工核对的用户在一个工作日内至少收到一次明确进展或最终结论；这是服务承诺，不代表 Lingxi 自动催办。
- 即使数据库中已有权限，只要发布或 MCP 生效尚未确认，用户也不会收到虚假的“已经可以使用”。
- `user` 用户表只保存身份关联、权限判断、发布状态、服务和审计所必需的信息，不保存短期令牌或认证材料。

## 不采用的选择及原因

- **把飞书多维表格作为权限权威**：它是发布通道，误改或同步延迟不能改变用户应有权限。
- **直接用银河导出名单作为运行时权限权威**：任何上游信息都必须经过受控流程进入数据库，运行时只认数据库当前有效记录。
- **以 MCP 当前状态反向覆盖数据库**：MCP 是权限执行端，异常或旧状态不能成为授权决定。
- **纯后台无感开通**：已验证的飞书接口不支持以应用身份取得必需的用户标识。
- **把“查不到”转人工核对**：会用最常见的正常结果淹没人工资源，并让无权限用户无谓等待一个工作日。
- **用部门或租户辅助姓名匹配**：部门信息当前不可信，且会增加匹配复杂度。
- **模糊姓名匹配或自动选择同名记录**：存在把其他人的权限授予当前用户的风险。
- **所有用户都等待人工审批**：唯一有效匹配时继续人工处理没有用户价值。
- **把用户首次发送的业务问题自动排队到开通后执行**：用户尚未确认开通，该内容不应进入业务处理。
- **把开通前的内容保留下来、在成功卡片上作为可点击建议回显**：需要跨越开通边界保存一段未经确认的用户内容，换来的只是省下一次输入。用户重打一遍问题的成本很低，而“不保存”是一条更干净、更容易验收的边界。
- **在成功卡片上提供按用户权限范围生成的示例问题**：示例问题要正确反映该用户可查询的公司、指标和粒度，本身依赖尚未确定的指标目录和数据新鲜度语义，会把一项未定的能力提前写进开通体验。首期不做；用户如何知道能问什么，作为独立问题另行确认。
- **承诺权限收回即刻阻断**：首期缺少实时变更推送和运行中复核机制，该承诺无法验收。

## 复审或替代条件

出现以下情况时必须重新评估本决策：

- 权限数据库的治理责任或权威地位发生变化；
- 关联租户用户无法完成飞书授权，或授权可取得的字段发生变化；
- 姓名唯一匹配在实际运行中产生不可接受的错配风险，或部门等字段变得可信；
- 出现更可靠、可直接对齐的稳定身份标识；
- 飞书多维表格不再承担权限发布通道；
- MCP 的权限发布或生效确认机制发生变化；
- 公司要求权限收回必须即刻阻断，或要求所有用户重新引入人工审批。
