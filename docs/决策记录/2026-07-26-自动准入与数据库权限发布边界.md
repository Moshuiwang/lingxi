# 决策：自动准入以数据库权限为准并验证 MCP 权限同步

> 状态：现行（其中「只按姓名匹配」要点已于 2026-08-05 被[花名册身份链与工号邮箱匹配](2026-08-05-花名册身份链与工号邮箱匹配.md)替代）
> 决定日期：2026-07-26（同日补充匹配结果分层与 MCP 权限同步验收）
> 最后修订：2026-08-08（补充银河职能映射、每日快照刷新、既有用户生效范围和首次开通提示；最终确认所有非唯一成功结果统一按无可用权限结束，不进入人工核对）
> 来源：[GitHub Issue #7](https://github.com/Moshuiwang/lingxi/issues/7)；[GitHub Issue #9](https://github.com/Moshuiwang/lingxi/issues/9)；[GitHub Issue #17](https://github.com/Moshuiwang/lingxi/issues/17)；[GitHub Issue #65](https://github.com/Moshuiwang/lingxi/issues/65)；[GitHub Issue #69](https://github.com/Moshuiwang/lingxi/issues/69)；产品负责人于 2026-07-26 确认权限权威、发布通道、MCP 权限同步与开通体验，并于 2026-08-07、2026-08-08 确认当前银河文件仅为临时输入来源、本次权限规则及首次开通提示

## 要解决的长期问题

Lingxi 首次面对一名飞书用户时，需要确认该用户是谁、可以访问哪些公司和职能，把正确权限发布到飞书多维表格，并确认问数 MCP 已经按该用户权限完成同步、能够提供问数服务。只有发布完成而没有验证当前用户可以问数，不能向用户宣告开通成功。

同时还要回答：用户要为开通付出什么动作、开通过程中看到什么，以及“数据库里没有这个人”应该被当成故障还是正常结果。

## 决定要点

- **Lingxi 生产数据库是 Lingxi 发布权限的唯一权威。** 银河数据必须经受控流程进入数据库；飞书多维表格只是数据库向 MCP 发布权限的下游通道，不能反向授权。
- **当前银河权限文件只是临时输入来源。** 它进入 Lingxi 数据库后，运行时仍只认数据库中的当前有效记录；未来正式银河权限数据库可以替换当前输入来源，但接入方式、刷新方式和具体数据库设计不在本次决定中。
- **当前不为临时文件增加永久摘要墓碑。** 九十天清理后，同一份旧导出可以再次导入；这是临时来源下保持简单的处理，不作为未来正式数据库接入的规则。
- **权限导入主链路与来源形式解耦。** 文件导入只是可替换的输入适配方式，未来接入数据库来源时，不应要求重写权限匹配和发布主链路。
- **银河不需要提供或维护在职状态。** 银河权限链路只判断权限记录；离职、未授权、权限记录不完整或其他权限异常，统一按未授权处理，不进入人工处理队列，用户得到联系银河管理员的明确提示。
- **用户成功后直接看到公司和职能范围。** 公司范围按银河记录展示；职能只取配置文件中精确映射出的 Lingxi 支持职能，不把用户交给 Lingxi 自行选择范围。
- **职能映射是可替换配置。** 当前支持的职能标签为商务、CEO、内容、财务、运营、OTT、销售；APP 开头角色和「A海外本地员工营业厅」不映射。角色名按配置精确匹配，不做通用前缀猜测；同时含 OTT 和运营时优先归为 OTT。配置文件位于[`galaxy_role_function_map.toml`](../../src/lingxi/config/galaxy_role_function_map.toml)。
- **权限快照每天刷新一次，顺序在花名册刷新之后。** 新快照对新用户和已有用户都生效；权限变化后更新当前权限多维表格，交由 MCP 完成下游同步确认。
- **开通由员工首次使用自动触发。** 组织资料授权分工见[关联组织专用授权与普通员工自动开通边界](2026-07-28-关联组织专用授权与普通员工自动开通边界.md)。
- **开通过程向用户流式展示**，用户看得到进行到哪一步、每一步是否成功。
- ~~**首期只按姓名匹配数据库中当前有效的权限记录**~~ **本条已于 2026-08-05 替代**：匹配键改为经花名册取得的工号（主）与邮箱（辅），见[花名册身份链与工号邮箱匹配](2026-08-05-花名册身份链与工号邮箱匹配.md)；「唯一命中且记录完整才自动通过」不变。下文「为什么这样定」中关于姓名匹配的论证保留为历史背景。
- **匹配结果只有两个用户出口**：只有身份、花名册和银河权限记录均唯一、完整、一致且至少有一个受支持职能时继续自动开通；零条、多条（含重复原始行）、双键冲突、资料不完整、没有受支持职能或其他无法唯一确认的结果，全部按无可用权限终止并提示联系银河管理员，不生成 `manual_review` 或候选选择待办。内部仍保留失败原因用于审计。
- **开通成功后由用户自己提问**，开通前发送的内容一律丢弃；成功卡片不提供固定业务示例或可点击建议，只提示用户可以自然语言询问“你能查什么”。
- **开通成功必须包含当前用户的 MCP 权限同步确认**：权限发布后立即校验，之后每三分钟校验一次，最多十五分钟；未确认前只显示“权限正在同步”，不进入正常问数。
- **首次开通提示按结果分层**：开始核对时说明正在核对且无需重复发送；找到有效权限时说明正在开通和同步但不提前宣告成功；全部完成后展示当前公司和职能范围；任何确定性的非唯一成功结果都给出同一申请或联系银河管理员指引；权限同步超时继续走专用超时提示，组织资料不可用或其他 Lingxi 内部意外故障才提示已转交管理员并给出 `LX-ONBOARD-001`，不展开内部原因。
- **MCP 决定实际数据范围**：Lingxi 不复制逐条数据过滤，但必须确认当前用户应有的公司和职能权限已经同步且可以问数。

## 为什么这样定

**开通过程流式展示，是因为这条链路步骤多且每一步都可能失败。** 资料同步、匹配、建档、环境创建、云盘目录、权限发布和飞书多维表格发布结果确认，任何一步卡住，用户如果只看到静默等待，既无法判断该继续等还是该找人，团队也无法快速定位问题。把过程可见化同时解决用户预期和排查成本两件事。

**任何非唯一成功都不建立人工选择流程。** 首期面向所有内部用户，但银河的数据权限名单只覆盖其中一部分人；多条、冲突、重复或资料不完整时也没有一条可由 Lingxi 安全采用的记录。让管理员挑一条继续既会扩大人工量，也会把权限判断变成 Lingxi 自己的审批。统一给出带申请指引的无可用权限终态，既保持失败关闭，也让用户立刻知道下一步找谁；具体失败原因只留在内部审计中。

**不把银河在职状态引入权限链路，是因为它不是本次体验所需的信息。** 用户能否使用 Lingxi 取决于身份能否可靠定位和银河是否有完整、受支持的权限记录；银河没有权限、记录不完整或出现权限异常时，用户都得到同一个可行动的未授权结论，避免为临时状态增加额外分支。

**把角色映射放在精确配置里，是因为银河角色名是自由文本。** 当前确认的规则可以覆盖首批需要的角色，但角色命名仍可能演进。精确配置能让产品负责人增删一行即可维护范围，同时避免把 APP、个人角色或未来未知角色误判成 Lingxi 职能。

**先刷新花名册再刷新银河快照，是因为两条数据链在同一天需要有稳定的身份基线。** 快照是当前权限版本，既影响新用户也影响已开通用户；权限变化必须重新发布当前多维表格内容并等待 MCP 同步确认，用户看到的范围才与新版本一致。

**不为临时导出文件引入永久防重机制。** 当前银河权限文件会继续更新，未来还会接入正式的银河权限数据库；现在为文件摘要建立永久墓碑，会把临时文件的处理方式提前固化成长期规则。保持九十天清理后的简单行为，把真正需要长期约束的来源切换、版本和回退问题留到正式数据库接入时解决。

**导入逻辑与来源解耦。** 当前文件只是把银河数据送入 Lingxi 数据库的一种方式，未来数据库来源的业务结构预计与当前文件相近，但接入方式和具体设计仍未确定。先固定来源无关的权限导入边界，才能在替换输入来源时不改变当前权限匹配和发布规则。

**旧版“只按姓名匹配、重名转人工”已经被替代。** 2026-08-05 起姓名只作诊断辅助，匹配使用花名册工号（主）和邮箱（辅）；2026-08-08 又明确任何多条、冲突或无法唯一确认的结果都直接失败关闭，不允许管理员选择候选继续开通。部门或租户也不作为猜测身份的二次判据。

**“权限已发布”不等于“用户已经开通”。** 用户只关心自己能不能真正问数。如果 Lingxi 在多维表格写入完成后立即宣布成功，用户第一次提问仍可能没有可用结果。Lingxi 因此必须通过问数 MCP 明确确认当前用户的权限已经同步且可以问数，再发送成功通知。

**验证 MCP 就绪不等于复制 MCP 的数据过滤。** Lingxi 只核对当前用户应有的公司和职能权限是否已经同步并可用于问数，不重新检查每一条返回数据。实际返回的数据范围仍由 MCP 按当前用户生效权限控制。

**本决策不选择数据库产品、托管位置、备份方案或表结构**，这些属于后续实施工作。

## 对用户和边界的影响

- Lingxi 只把数据库中的当前有效权限发布到飞书多维表格，不允许用户通过 Lingxi 修改或扩大这份记录；实际数据范围由 MCP 决定。
- 用户无需完成身份授权；首次使用后由系统自动匹配和开通，并展示可理解的进度或结果。
- 任何无法唯一、完整、一致确认有效权限的用户都很快得到同一确定结论和申请路径，不进入等待，也不创建人工候选待办。
- 数据库写入、飞书多维表格发布或当前用户 MCP 权限同步任一项未明确完成时，用户都不会收到“开通成功”提示。
- 权限同步期间用户看到预计最多十五分钟；超时后停止自动等待并转运维处理，后续确认成功时再主动通知用户。
- 当前银河文件只是临时输入来源；不增加永久摘要墓碑，不改变 Lingxi 数据库作为权限权威的边界，也不改变用户可见的开通规则。
- `user` 用户表只保存身份关联、权限判断、发布状态、服务和审计所必需的信息，不保存短期令牌或认证材料。

## 不采用的选择及原因

- **把飞书多维表格作为权限权威**：它是发布通道，误改或同步延迟不能改变用户应有权限。
- **直接用银河导出名单改变 Lingxi 准入或发布内容**：任何上游信息都必须经过受控流程进入数据库，Lingxi 只认数据库当前有效记录；实际问数范围仍由外部 MCP 决定。
- **以 MCP 当前状态反向覆盖数据库**：MCP 是权限执行端，异常或旧状态不能成为授权决定。
- **多维表格发布完成后立即宣告开通成功**：这不能证明当前用户已经能够问数，会把权限同步窗口暴露给刚开通用户。
- **在 Lingxi 中复制 MCP 的逐条数据过滤**：实际数据范围由 MCP 按当前用户生效权限控制，Lingxi 只验证用户权限同步和问数就绪。
- **把查无、多条、冲突、重复、资料不完整或未支持角色送入人工处理**：这些结果都没有可供 Lingxi 安全采用的唯一权限范围；统一给出未授权结论更直接，也避免管理员替用户选择身份或权限。
- **把银河在职状态复制到 Lingxi 作为权限前提**：这会为当前不需要的临时状态增加另一条判断链；本次统一按权限记录结果处理。
- **把角色名按前缀或关键词自动推断**：会把 APP、个人角色或含多个关键词的角色误归类；当前规则只认配置，且 OTT 优先于运营。
- **用部门、租户或姓名辅助猜测身份**：这些字段不能把非唯一结果变成可靠的唯一结果，且会增加误配风险。
- **模糊姓名匹配或自动选择同名记录**：存在把其他人的权限授予当前用户的风险。
- **所有用户都等待人工审批**：唯一有效匹配时继续人工处理没有用户价值。
- **把用户首次发送的业务问题自动排队到开通后执行**：用户尚未确认开通，该内容不应进入业务处理。
- **把开通前的内容保留下来、在成功卡片上作为可点击建议回显**：需要跨越开通边界保存一段未经确认的用户内容，换来的只是省下一次输入。用户重打一遍问题的成本很低，而“不保存”是一条更干净、更容易验收的边界。
- **在成功卡片上提供按用户权限范围生成的固定示例问题**：固定示例容易与 MCP 当时实际提供的公司、指标和粒度不一致。首期不维护示例清单或 `/help` 命令；用户直接询问“你能查什么”时，由 AI Agent 根据 MCP 当前能力回答。

## 复审或替代条件

出现以下情况时必须重新评估本决策：

- 权限数据库的治理责任或权威地位发生变化；
- 关联组织资料的可得性、员工私聊身份定位规则或银河匹配规则发生变化；
- 姓名唯一匹配在实际运行中产生不可接受的错配风险，或部门等字段变得可信；
- 出现更可靠、可直接对齐的稳定身份标识；
- 飞书多维表格不再承担权限发布通道；
- 飞书多维表格与 MCP 之间的发布接口发生变化，影响 Lingxi 写入结果；
- 正式银河权限数据库开始接入，或当前临时文件不再是主要输入来源，需要重新确定来源适配、刷新、版本、去重和回退规则；
- 银河角色体系、支持职能范围或角色命名发生变化，导致现有精确映射无法覆盖；
- 每日花名册与银河快照刷新顺序、既有用户生效或多维表格同步结果无法稳定复现；
- 当前文件允许重复导入的简单行为在真实运行中造成了可接受范围之外的权限回退风险；
- 公司要求 Lingxi 独立承担 MCP 权限隔离或验收责任，或要求所有用户重新引入人工审批。
