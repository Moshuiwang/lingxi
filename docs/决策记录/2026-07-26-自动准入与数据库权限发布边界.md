# 决策：自动准入以数据库权限为准并验证 MCP 权限同步

> 状态：现行
> 决定日期：2026-07-26（同日补充开通交互、匹配结果分层与 MCP 权限同步验收）
> 来源：[GitHub Issue #7](https://github.com/Moshuiwang/lingxi/issues/7)；[GitHub Issue #9](https://github.com/Moshuiwang/lingxi/issues/9)；产品负责人于 2026-07-26 确认权限权威、发布通道、MCP 权限同步与开通体验
>
> 规则正文见[产品合同与外部边界](../产品合同与外部边界.md)的「首次对话与自动准入」「匹配结果与人工处理」「统一用户记录与权限变化」。本文只说明为什么这样定。

## 要解决的长期问题

Lingxi 首次面对一名飞书用户时，需要确认该用户是谁、可以访问哪些公司和职能，把正确权限发布到飞书多维表格，并确认问数 MCP 已经按该用户权限完成同步、能够提供问数服务。只有发布完成而没有验证当前用户可以问数，不能向用户宣告开通成功。

同时还要回答：用户要为开通付出什么动作、开通过程中看到什么，以及“数据库里没有这个人”应该被当成故障还是正常结果。

## 决定要点

- **Lingxi 生产数据库是 Lingxi 发布权限的唯一权威。** 银河数据必须经受控流程进入数据库；飞书多维表格只是数据库向 MCP 发布权限的下游通道，不能反向授权。
- **开通由用户主动确认触发，并包含一次飞书授权。** 未开通用户收到引导卡片，点击「开始使用」或发送确认文本才开通；卡片同时提供「暂不需要」退出。
- **开通过程向用户流式展示**，用户看得到进行到哪一步、每一步是否成功。
- **首期只按姓名匹配数据库中当前有效的权限记录**，唯一命中且记录完整才自动通过。
- **匹配结果分三层**：唯一命中自动开通；查不到直接给出“联系 BI 同事开通银河权限”的终态；重名或记录不完整才转人工核对。
- **开通成功后由用户自己提问**，开通前发送的内容一律丢弃；成功卡片不提供固定业务示例或可点击建议，只提示用户可以自然语言询问“你能查什么”。
- **开通成功必须包含当前用户的 MCP 权限同步确认**：权限发布后立即校验，之后每三分钟校验一次，最多十五分钟；未确认前只显示“权限正在同步”，不进入正常问数。
- **MCP 决定实际数据范围**：Lingxi 不复制逐条数据过滤，但必须确认当前用户应有的公司和职能权限已经同步且可以问数。

## 为什么这样定

**开通必须包含一次用户授权，不能设计成纯后台无感。** 已验证事实是：中心应用以应用身份调用 `trust_party` 系列接口返回 `1971007 App not visible to target tenant`，只有用户完成授权后、以用户身份才能取得该用户的 `user_id`、`open_id` 和 `union_user_id`。既然这一步无法回避，就把它做成用户能够理解的一次确认动作，而不是藏在后台后再失败。

**开通过程流式展示，是因为这条链路步骤多且每一步都可能失败。** 授权、匹配、建档、环境创建、云盘目录、权限发布和飞书多维表格发布结果确认，任何一步卡住，用户如果只看到静默等待，既无法判断该继续等还是该找人，团队也无法快速定位问题。把过程可见化同时解决用户预期和排查成本两件事。

**“查不到”是正常结果，不是异常。** 首期面向所有内部用户，但银河的数据权限名单只覆盖其中一部分人。如果把“查不到”和“重名”一样转人工，每一个好奇点进来的同事都会变成一条人工待办和一条一个工作日的服务承诺，人工核对会被正常情况淹没，真正的异常反而被延误。把它做成带申请指引的明确终态，用户立刻知道下一步找谁，也不占用人工资源。

**只按姓名匹配，不引入部门或租户作为二次判据。** 加入部门确实能降低重名概率，但会显著增加匹配逻辑的复杂度，而且当前部门信息本身的准确性不可信——用不可信字段做判据，可能把本可唯一命中的用户误判成异常。重名转人工的成本可以接受，误判和复杂度的成本不能接受。

**“权限已发布”不等于“用户已经开通”。** 用户只关心自己能不能真正问数。如果 Lingxi 在多维表格写入完成后立即宣布成功，用户第一次提问仍可能没有可用结果。Lingxi 因此必须通过问数 MCP 明确确认当前用户的权限已经同步且可以问数，再发送成功通知。

**验证 MCP 就绪不等于复制 MCP 的数据过滤。** Lingxi 只核对当前用户应有的公司和职能权限是否已经同步并可用于问数，不重新检查每一条返回数据。实际返回的数据范围仍由 MCP 按当前用户生效权限控制。

**本决策不选择数据库产品、托管位置、备份方案或表结构**，这些属于后续实施工作。

## 对用户和边界的影响

- Lingxi 只把数据库中的当前有效权限发布到飞书多维表格，不允许用户通过 Lingxi 修改或扩大这份记录；实际数据范围由 MCP 决定。
- 用户为开通付出的动作是明确的：点一次按钮、完成一次授权，其余由系统完成并且可见。
- 没有数据权限的用户很快得到确定结论和申请路径，不进入等待。
- 进入人工核对的用户在一个工作日内至少收到一次明确进展或最终结论；Lingxi 只说明这项服务承诺并通知管理员新待办，由管理员人工守护，不建设自动催办、升级或进展通知。
- 数据库写入、飞书多维表格发布或当前用户 MCP 权限同步任一项未明确完成时，用户都不会收到“开通成功”提示。
- 权限同步期间用户看到预计最多十五分钟；超时后停止自动等待并转人工处理，后续确认成功时再主动通知用户。
- `user` 用户表只保存身份关联、权限判断、发布状态、服务和审计所必需的信息，不保存短期令牌或认证材料。

## 不采用的选择及原因

- **把飞书多维表格作为权限权威**：它是发布通道，误改或同步延迟不能改变用户应有权限。
- **直接用银河导出名单改变 Lingxi 准入或发布内容**：任何上游信息都必须经过受控流程进入数据库，Lingxi 只认数据库当前有效记录；实际问数范围仍由外部 MCP 决定。
- **以 MCP 当前状态反向覆盖数据库**：MCP 是权限执行端，异常或旧状态不能成为授权决定。
- **多维表格发布完成后立即宣告开通成功**：这不能证明当前用户已经能够问数，会把权限同步窗口暴露给刚开通用户。
- **在 Lingxi 中复制 MCP 的逐条数据过滤**：实际数据范围由 MCP 按当前用户生效权限控制，Lingxi 只验证用户权限同步和问数就绪。
- **纯后台无感开通**：已验证的飞书接口不支持以应用身份取得必需的用户标识。
- **把“查不到”转人工核对**：会用最常见的正常结果淹没人工资源，并让无权限用户无谓等待一个工作日。
- **用部门或租户辅助姓名匹配**：部门信息当前不可信，且会增加匹配复杂度。
- **模糊姓名匹配或自动选择同名记录**：存在把其他人的权限授予当前用户的风险。
- **所有用户都等待人工审批**：唯一有效匹配时继续人工处理没有用户价值。
- **把用户首次发送的业务问题自动排队到开通后执行**：用户尚未确认开通，该内容不应进入业务处理。
- **把开通前的内容保留下来、在成功卡片上作为可点击建议回显**：需要跨越开通边界保存一段未经确认的用户内容，换来的只是省下一次输入。用户重打一遍问题的成本很低，而“不保存”是一条更干净、更容易验收的边界。
- **在成功卡片上提供按用户权限范围生成的固定示例问题**：固定示例容易与 MCP 当时实际提供的公司、指标和粒度不一致。首期不维护示例清单或 `/help` 命令；用户直接询问“你能查什么”时，由 AI Agent 根据 MCP 当前能力回答。

## 复审或替代条件

出现以下情况时必须重新评估本决策：

- 权限数据库的治理责任或权威地位发生变化；
- 关联租户用户无法完成飞书授权，或授权可取得的字段发生变化；
- 姓名唯一匹配在实际运行中产生不可接受的错配风险，或部门等字段变得可信；
- 出现更可靠、可直接对齐的稳定身份标识；
- 飞书多维表格不再承担权限发布通道；
- 飞书多维表格与 MCP 之间的发布接口发生变化，影响 Lingxi 写入结果；
- 公司要求 Lingxi 独立承担 MCP 权限隔离或验收责任，或要求所有用户重新引入人工审批。
