## 决定要点

- **管理员职责集定稿（MVP 核心五项）**：查询用户状态（配套「用户自查」产品候选以压量）；停用/恢复（日报驱动、刻意不自动化）；花名册日报处置；运行告警响应；追溯与审计查询（同一查询面回答「发生了什么」与「谁对谁做过什么」）。
- **砍除**：独立的「终止开通」动作（停用即终止且防重触发）；十五分钟转运维单列项（迟到就绪自动恢复已覆盖）；提示词维护移出管理员清单（属产品调优）。
- **推迟/按需**：删除用户工具（首例走 Ops 受控执行卡）；管理员任免工具（角色模型保留，工具待 ≥2 名真实管理员）；开通链恢复工具与发布重试工具（真实形状由内测遥测定义）。
- **银河体系外权限动作按方向四分**（产品负责人 2026-08-24 采纳编排者建议组合）：
  1. 数据质量上报：入职责清单（纯上报，不违架构）；
  2. 单用户立即重同步：入职责清单（同步从每日变可按需，权威仍是银河）；
  3. 本地抑制（只减不加）：采纳，带三个强制条件——带原因+本人卡片确认、生效期间持续出现在审计与日报、银河修正后解除或定期复核。**[入口已收敛，规则不变]** 2026-08-31 #493 把管理卡表单收敛为「补充授权」单一方向，抑制与撤销改由管理员私聊文本命令逐笔发起（仍走同一条本人确认卡与审计链）；本条三个强制条件与「只减不加」方向**继续现行**，不因表单收敛而失效。规则正文见[产品合同与外部边界](../产品合同与外部边界.md)「本地抑制只减不加」；
  4. 本地开通/扩权：**不做**。**[已替代]** 产品负责人 2026-08-26 就 [Issue #319](https://github.com/Moshuiwang/lingxi/issues/319) 裁定推翻本条，新增「本地授权」方向：唯一管理员可经本人飞书确认卡为指定用户补授访问（Trace [#328](https://github.com/Moshuiwang/lingxi/issues/328) E-P 批次已实现，当时的形状是逐笔公司×指标）。**[入口已收敛，方向不变]** 2026-08-31 #493 把管理卡表单的补授入口改为「一个银河职位 + 一个公司范围」，由服务端按职位职能映射展开成公司×指标行；逐笔公司×指标的文本命令入口保留，存量逐指标行不迁移、不改写。本地授权不设有效期、不设定期复核（产品负责人明确裁定不需要）——上一条「本地抑制」的三个强制条件（含「银河修正后解除或定期复核」）维持不变、不受本条影响。实现采用单表双极性 `local_permission_override` 同时承载授权（grant）与抑制（suppress）两个方向，真实权限聚合语义 = (银河翻译 ∪ 本地授权) − 本地抑制、抑制优先于并集（**订正 2026-09-02**：原文写的「∪ 存量沿用」是四源旧公式，存量沿用机制已于 2026-08-30 随 [Issue #441](https://github.com/Moshuiwang/lingxi/issues/441) 退役，改为存量用户首聊差集导入为本地授权，见[存量用户首开差集导入与发布只在变化时回写](2026-09-02-存量用户首开差集导入与发布只在变化时回写.md)）。规则正文见[产品合同与外部边界](../产品合同与外部边界.md)「本地权限覆盖」。
- **归属**：指标映射表维护、内测采集开关=产品负责人本人；专用授权凭据维护=Ops；成本/用量观察并入独立审计治理线（与审计本质同一条数据流）；安全事件复核维持治理线。
- **实现形态（How 层，产品负责人 2026-08-24 终裁）：方案 A**——管理走 Lingxi 机器人飞书私聊（确定性命令面起步）+ 服务端管理员角色登记表 + 本人确认卡；管理 MCP 与外部管理 AI Agent 保留为未来入口，按触发条件启动（管理任务超出卡片承载 / 确需外部客户端 / 决定开放公网 / 客户端出现服务端可核验的到场批准证据）。缓解策略（第二管理员知会 / 冷却期）MVP 暂不加，内测观察后按需引入。
- **唯一管理员 = 组织资料同步的专用授权主体账号（「文档会议助手」）**：该账号在员工开通路径上本就有确定性专用出口、永远不会成为业务用户（规则见[产品合同与外部边界](../产品合同与外部边界.md)「匹配结果与异常处理」的专用授权账号行），管理员与业务用户身份结构性隔离、不可能混同；MVP 登记表唯一条目、三类角色合并授予。知情接受的集中风险：该账号同时承载组织同步授权与管理员身份，账号失守即两者同时失守——由该账号仅产品负责人本人控制这一现实缓解。

## 为什么

**先定「做什么」再定「怎么做」。**职责集从三个证据源反推：产品合同的权威分配、Trace #203 七天真实运行中实际发生的人工介入点、旧系统实际承担过的职责。逐项做必要性测试后，合同原有分配里有多项经不起推敲：「终止开通」没有独立语义；手工「收回单项权限」会被每日银河同步覆盖，除非制造第二权威——这正是旧系统（权限权威=审批流本身）与本系统（权限权威=上游同步）的结构差异，照抄旧系统职责会引入架构矛盾。

**管理员的真实痛点用不违架构的工具优先解决。**「看到不合理权限无从动手」的多数场景是「银河已改、每日同步未跟上」——单用户立即重同步直接消解它，不需要任何权威变更。剩余场景中确需人为干预的方向只有「减」：本地抑制在数据方向上失败安全（只会更少不会更多），代价是与银河的显性分歧，因此三个强制条件的目的都是防止抑制层退化为静默的影子权限系统。

**不做本地开通/扩权，是责任归属问题而非架构洁癖。**一旦 Lingxi 管理员能在银河之外放开数据访问，「谁批准他看这些数据」的答案就从一个有流程的上游系统变成某个管理员的个人判断，审计链在此断裂、合规责任整体转移。替代路径（证据齐备的转银河上报 + 改完立即重同步）覆盖了正当需求。

**极低频动作不预建产品代码。**删除用户与管理员任免均为合同义务，但频率不配自助工具；旧系统「不可逆删除与普通收回同等交互摩擦」的实测缺陷说明，为低频危险动作草率建工具比不建更危险。

## 不采用的选择及原因

- **本地开通/扩权（含「临时授权+自动过期」的最小形态）**：审计归属断裂与合规责任转移，编排者明确不推荐，产品负责人 2026-08-24 裁定不做；若未来出现真实场景，按复审条件重估。**[已替代]** 复审条件已触发：产品负责人 2026-08-26 就 [#319](https://github.com/Moshuiwang/lingxi/issues/319) 推翻本条，见「决定要点」第 4 条批注。
- **把手工收回单项权限保留为管理员动作**：与每日上游同步互相覆盖，要么无效要么制造第二权威；由「本地抑制」以明确的分歧登记语义取代。
- **自动停用离职/换人账号**：花名册数据质量（2026-08-24 实测 37 个重复人员 ID）会让自动化误伤，维持日报+人工判断（#34 方案 C 既定选择）。

## 2026-08-27 补充：S-P-6 管理命令面路由设计结论

来源：Trace [#328](https://github.com/Moshuiwang/lingxi/issues/328) E-P 批次 S-P-6（本地权限层落地后复核管理命令面与业务问数面是否需要改路由）。

**结论**：管理命令面（`_try_admin_route`，`src/lingxi/core/conversation/pipeline.py`）与业务问数面的分流现状自洽；MVP 阶段不需要为本地权限命令改造 `pipeline.py`，也不需要在既有「自我目标防呆」之外新增结构隔离。

**三个后续触发条件（现状均未触发，达到条件再评估，不预先实现）**：

1. 「真实管理员 ≥ 2 人，且该管理员本身也是问数用户」触发时，须把 `_try_admin_route` 的调用点从当前只覆盖 `UserState.NOT_PROVISIONED` 扩展到同时覆盖 `PROVISIONING`/`ACTIVE`/`SUSPENDED` 三态——当前唯一管理员是专用授权账号、结构性排除在员工问数路径之外，因此该缺口尚不构成真实风险；
2. 自我目标防呆（管理员不能对自己发起本地权限动作）目前只在私聊 `AdminCommandRouter`（`core/admin/router.py`）单点实现，尚未下沉到 `pending_action.py` 的 `prepare()` 共用层；新增管理入口（管理 MCP）前必须把这条防呆补齐到共用层，否则新入口可以绕过 router 直接调用 `prepare()`；
3. 本地授权/抑制不新增对目标用户的主动通知，沿用停用（suspend）场景的反应式获知模式——用户下次问数时按新权限生效，才发现变化；管理群通知、审计记录与日报口径复用现状，不为本地权限动作单独新增一套通知语义。

**另记：管理面未来若迁移为独立进程，须保持的五条不变量（当前不实现，供该迁移设计时对齐）**：

1. 确认卡链复用同一张 `pending_action` 表与同一套纯函数判定，不为独立进程另建一套；
2. 写操作与其审计记录同事务提交；
3. 唯一管理员判定用单一 `admin_registry` 表，不引入缓存（角色收回后新请求必须立即拒绝）；
4. 同一目标对象的在途待确认操作唯一性约束共享同一张表，不按入口分表；
5. 自我目标防呆判定下沉到 `prepare()` 共用层，不留在某个入口的单点实现。

## 复审或替代条件

- 抑制项数量持续增长或长期不解除——说明上游修正通道不畅，应重估同步机制而非继续堆抑制；
- 单用户重同步使用频次高——说明每日同步节奏不满足业务，重估同步频率；
- 出现「必须在银河之外授予访问」的真实业务场景——重启四分法第 4 条评估，且必须连同审计归属与合规责任设计一起做；**已触发**：2026-08-26 就 [#319](https://github.com/Moshuiwang/lingxi/issues/319) 裁定推翻第 4 条，见「决定要点」第 4 条批注。
- 真实管理员达到两人以上——启动任免工具与角色模型实现，并重估「唯一管理员=专用授权主体账号」与集中风险的缓解策略；同一条件也是上文 S-P-6 触发条件①的前提之一；
- 删除用户出现第二例真实请求——产品化删除流程。
