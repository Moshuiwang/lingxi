# 决策：审核审计与持续优化治理边界

> 状态：现行
> 决定日期：2026-07-26
> 来源：[GitHub Issue #7](https://github.com/Moshuiwang/lingxi/issues/7)；[GitHub Issue #9](https://github.com/Moshuiwang/lingxi/issues/9)；产品负责人于 2026-07-26 确认治理方向、管理员入口与审计内容范围
>
> 规则正文见[产品合同与外部边界](../产品合同与外部边界.md)的「审核、审计与持续优化方向」。本文只说明为什么这样定。

## 要解决的长期问题

Lingxi 首期首先要让所有内部用户获得受控、可信的问数体验；但长期运行后，还必须能够复核风险、发现服务与回答质量问题，并把问题沉淀为持续改进。审核、审计和优化不能反过来接管用户的问数主链路，也不能因为暂未建设审核工作台而失去必要的治理方向。

## 决定要点

- **Lingxi 是主产品**，审核、审计与持续优化由独立治理能力承载，不接管开通、权限判断或问数决策。
- **首期不承诺自动审核、实时风险拦截、审核工作台或自动优化功能**，这些不阻塞首期上线与三名真实用户验收。
- **Lingxi 首期只负责稳定记录可关联的审计事实**：用户与话题、任务状态、权限版本变化、问数 MCP 查询与数据范围摘要、交付状态、停止或失败类别，以及管理 MCP 查询、待确认动作、飞书卡片确认、确定性匹配失败原因和运行异常处理结论。
- **公司内部审计在授权后可复核完整聊天与业务内容**，按公司审计制度管理并可追溯。
- **治理以“发现问题—归类原因—形成改进项—复核效果”为闭环**，问题按数据源或指标、权限、模型回答、产品交互、交付链路、人工处理分类。
- **`bi-agent-audit` 可作为独立治理底座**，通过审计事件接收事实，不接管主链路。

## 为什么这样定

**治理能力独立建设，但审计事实必须在首期就记录到位。** 审计工作台可以推迟，事实不能事后补——没有记录下来的执行过程无法回溯。所以首期的约束不是“建审核系统”，而是“别丢事实”，这两件事的成本差距很大。

**AI Agent 参与管理后，人的决定与模型建议必须能够区分。** 管理 MCP 查询和准备动作可以由 AI Agent 发起，但真正改变用户状态的是管理员本人在飞书卡片上的确认。审计必须同时记录准备、确认和执行结果，不能只留一条“Agent 调用了工具”的日志。

**审计不设内容限制，但设职责限制。** 公司内部审计需要看到完整聊天和业务内容才能判断一次问数是否存在问题，证据不完整等于审计失效，所以在内容上不做删减。但审计系统只能读，不能反向改变 Lingxi 的用户准入、权限记录或发布内容，也不能代替用户执行查询。

**问题归类不能笼统归因于用户提问。** 如果所有问不出结果的情况都记成“用户没问清楚”，指标口径错误、交付链路故障和权限配置问题都会被掩盖，改进闭环就没有输入。

## 对用户和边界的影响

- 用户仍只面对 Lingxi 的开通、问数和交付体验；审核流程不应使正常问数额外等待或改变结果接收位置。
- 出现错误数字、错误指标、Lingxi 自身造成的跨用户会话或交付风险、失败交付、反复无法收敛或人工处理异常时，团队有一致的归类和后续改进方向；MCP 数据权限正确性仍由 MCP 自身负责。
- 审核人员可以在公司制度授权的范围内复核完整事实，避免因证据不完整而无法判断一次问数、查询和交付是否存在问题。
- 审计系统与 Lingxi 主链路可以独立建设、独立演进。

## 不采用的选择及原因

- **把审核能力完全写进 Lingxi 首期主链路**：会把独立的治理建设与用户问数体验绑定，增加首期上线范围和风险。
- **首期完全不记录审计事实**：事实无法事后补齐，会让未来的治理建设失去输入。
- **只看系统是否成功、不复核用户结果与问题类型**：无法发现指标错误、交付体验问题或反复无法收敛的问题，也无法形成有效改进闭环。
- **让审核系统反向改变用户准入、权限记录或直接执行问数**：会绕过 Lingxi 的受控管理边界，并扩大治理系统职责。

## 复审或替代条件

- 公司审计、合规或数据保留制度发生变化；
- 审核工作台、风险提醒或质量优化项目正式立项并确认其用户与管理体验；
- Lingxi 扩展到新的入口、模型、数据源或多人交付场景；
- `bi-agent-audit` 不再作为适用的独立治理底座。
