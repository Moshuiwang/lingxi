# 决策：首期服务范围与真实验收

> 状态：现行
> 决定日期：2026-07-26；2026-07-27 随超级管理员 Root 应急恢复边界调整同步验收覆盖项
> 来源：[GitHub Issue #7](https://github.com/Moshuiwang/lingxi/issues/7)；[GitHub Issue #9](https://github.com/Moshuiwang/lingxi/issues/9)；产品负责人于 2026-07-26 确认首期范围、真实试用人数和管理员入口
>
> 首期服务范围的规则正文见[产品合同与外部边界](../产品合同与外部边界.md)。本文只说明范围如何划定，并保留验收门槛这一份唯一正文。

## 要解决的长期问题

Lingxi 首期需要明确先服务哪些用户、解决哪些任务，以及什么证据才足以把目标体验宣告为真实可用，避免把机器人回复、自动测试或环境健康误当成用户已经能够完成工作。

## 决定要点

- **首期面向所有内部用户**，不设白名单；能否问数取决于数据库中是否有明确有效的权限记录。
- **首期核心任务**是查询指定公司、指标和时间范围的数字，比较趋势和相关指标变化，并把结果交付为飞书消息、文档、电子表格或图片。
- **飞书私聊和 JumpServer 高级工作台都在首期范围内**，飞书是默认入口。
- **管理员通过 AI Agent 与管理 MCP 处理异常**，写操作由发起管理员本人在飞书私聊卡片最终确认。
- **上线前先完成 Lingxi 自身功能的自动测试和受控测试账号回归**，包括权限发布不串人和当前用户 MCP 权限同步就绪，再由三名真实业务用户连续试用七个工作日；不复制 MCP 的逐条数据过滤验收。
- **只有真实用户在真实入口完成任务并确认结果可用，才可以宣告首期通过。**

## 为什么这样定

**首期面向所有内部用户，而不是一份白名单。** 银河已经持有权限数据，权限本身就是天然的准入边界，再叠加一层名单没有增量控制价值，反而会让“不在名单里”和“没有数据权限”两种不同的拒绝混在一起，用户无法理解自己该找谁。

**三名真实用户，不是五名。** 在覆盖至少两种职能和两种公司权限范围的前提下，三名用户已经能验证不同业务问题下的结果可信和交付路径；再增加人数提高的是样本量，不是覆盖的场景类型，而首期的目标是尽快取得真实反馈。

**测试账号和真实用户的证据不能互相替代。** 测试账号能证明 Lingxi 自身的开通、会话、异常和交付稳定性，但证明不了真实飞书身份、真实业务问题和真实交付体验；真实用户能证明结果对人有用，但不适合用来反复触发异常路径。两类证据各自不可缺，均不替代 MCP 自己的质量责任。

**JumpServer 不放到第二阶段。** 首期已经包含持续、深度分析的内部用户场景，把它推迟等于让这部分用户在首期完全没有可用路径。

## 首期验收门槛

本节是验收标准的唯一正文。

### 试用规模

- 三名真实业务用户，覆盖至少两种职能和两种公司权限范围，各自完成不少于三个真实业务问题，连续试用七个工作日。
- 三名用户只用于真实试用和验收，不构成首期用户范围的白名单或限制。

### 必须覆盖的用户旅程

- 开通引导卡片、点击「开始使用」与文本确认两种路径、点击「暂不需要」后的行为；
- 飞书授权流程，以及授权取消或失败时不保存不完整记录；
- 开通过程的流式展示，包括中途失败时用户能看出卡在哪一步；
- 三种匹配结果各一次：唯一命中自动开通、查不到时得到申请指引终态且未生成人工待办、重名或记录不完整时进入人工核对；
- 数据库权限记录与飞书多维表格中当前用户的公司和职能逐项一致；新增、收回或修改一个用户的权限不改变其他用户的发布内容；
- 权限发布后立即校验、每三分钟再次校验、最多等待十五分钟；同步期间不宣告成功，超时转人工，只有当前用户 MCP 权限已经同步且可以问数才发送开通成功通知；
- 管理员在真实 AI Agent 中通过管理 MCP 查询人工核对待办、比较候选记录、准备继续或终止动作，并由发起管理员本人在飞书私聊卡片确认；
- 管理 MCP 身份与本人飞书身份唯一绑定；普通用户、共享身份和职责不匹配的管理员均不能直接调用只读管理查询，也不能看到超出当前职责范围的待办、用户或权限信息；
- 权限管理员、运维管理员和超级管理员分别只能使用当前角色允许的能力；超级管理员可以新增和移除三类管理员；在受控测试环境中演练“系统无超级管理员时，由 Root 运维把身份已核实并绑定飞书的现有用户恢复为超级管理员”，且普通管理入口不获得 Root 能力；
- 未确认、取消、卡片发送失败、过期、重复点击、非发起管理员点击、管理员角色已被收回、当前角色已无权执行、目标状态或权限版本变化、审计写入失败时均不改变用户或管理员状态；
- 受控管理群只收到待办和结果通知，群内不存在审批按钮、管理命令或可执行操作；
- 用户查询、权限收回、账号停用与恢复、用户删除、关闭待处理和权限发布安全重试分别覆盖成功、明确拒绝和状态不明三类结果；
- 开通前发送的内容被丢弃且未在任何位置回显，用户重新提问后才进入问数；
- 用户自然语言询问“你能查什么”时，Agent 根据 MCP 当前指标列表和说明回答；不存在 `/help` 命令、固定业务示例或独立能力清单；
- 正常问数、模糊问题澄清、MCP 未返回可用数据时不推断权限原因、权限变化通知；
- 用户停用后不能发起新问数，停用前已经开始的任务继续正常完成和交付；
- 不同飞书话题并发、同一话题忙碌时普通消息与 `/new` 均只收到提示且不入历史、`/stop` 只停止当前话题；
- 连续追问、`/new` 重置当前所在话题且不影响其他话题、按任务间隔超过两小时开启新会话；
- 流式卡片及其同话题文本兜底；
- 文档、电子表格、图片交付进入本人专属云盘目录且仅本人可访问；
- 空结果、服务异常和送达状态不确定时的说明。

### 高级工作台验收

JumpServer 另行完成受控真实用户验收：用户在公司内部局域网通过浏览器终端进入独立工作环境并运行 Claude CLI，不依赖或共享飞书会话，并能通过交付 Skill 把正式产物写入同一专属云盘目录并送达用户。

### 通过标准

- Lingxi 自身的用户身份、权限发布、会话和交付隔离场景必须全部通过；开通前必须确认当前用户 MCP 权限已经同步可用，但不复制 MCP 的逐条数据过滤；
- 问数质量达到八十五分以上，且不存在关键数字错误、错误指标、Lingxi 导致的跨用户泄露或三轮不收敛等阻断问题；
- 连续试用期间不得存在阻断核心使用的严重问题；
- CI、测试账号、服务运行或单次机器人回复都不能替代真实用户的确认。

## 对用户和边界的影响

- 首期用户获得的是一组明确可验收的日常问数和交付能力，不是“任何业务问题都能回答”的泛化承诺。
- 数据库中没有明确权限或超出首期核心任务的用户，不属于首期承诺范围；不具备公司内部局域网条件只影响 JumpServer，不影响飞书问数。
- 测试账号用于证明 Lingxi 自身功能、权限发布和隔离稳定性，并确认当前用户 MCP 权限同步后才能开通；真实业务用户用于证明任务结果对人真正可用。两类证据不能互相替代，Lingxi 也不复制 MCP 对每条返回数据的权限过滤。

## 不采用的选择及原因

- **把三名真实试用用户当作首期可使用用户范围**：三名用户只用于验证体验，首期面向所有内部用户。
- **只用测试账号验收**：测试账号不能证明真实飞书身份、真实业务问题和真实交付体验。
- **要求五名真实用户试用**：三名用户在覆盖职能、公司范围和关键旅程的前提下已经足够，更快取得真实反馈优先。
- **把 JumpServer 放到第二阶段**：首期已经包含持续、深度分析的内部用户场景。

## 复审或替代条件

- 首期真实试用完成并进入扩大开放阶段；
- 首期用户范围或内部用户定义发生变化；
- 公司内部局域网或 JumpServer 的可用边界发生变化；
- 核心任务、质量门槛或上线方式发生变化。
