# 决策：版本维护分支与候选提升

状态：现行。决定日期：2026-09-08。来源：[Issue #669](https://github.com/Moshuiwang/lingxi/issues/669)，产品负责人在 Codex Desktop 会话讨论确认后授权实施。执行状态只看该工作项。

## 要解决的问题

生产文案热修曾因打包只绑定 main 而携带下一版整改与迁移（[#643 发布对账](https://github.com/Moshuiwang/lingxi/issues/643#issuecomment-5564998467)）。生产维护必须能与后续研发独立推进。

## 决定与理由

main 持续研发；版本在准备验收时建立维护分支，独立打包预发布，经审查的验收记录将同一镜像组提升为正式版。完整操作规则在[版本发布](../../deploy/releases/README.md)，检查分层在[验证与门禁](../技术设计/验证与门禁.md#五ci-分层)。

采用 VS Code、Python、Django 的版本维护思路，保留当前生产与必要的下一版，不增加永久测试/生产代码分支。代价是修复需同步到受支持版本；通过发布记录明确去向，不整条合入未来代码。测试库也必须兼容相应版本，代码分支不能代替数据库隔离。

## 与已有选择的关系

取代 2026-09-03 记录中“只从 main 产出发布镜像”的出口假定；#566 有人执行的部署脚本、#567 无人值守目标及不向生产开放新入站通道的选择继续有效。正式发布记录就绪不代表生产部署，后者仍由独立 Ops 工作执行。

## 复审条件

维护多个长期支持版本、引入第二套生产服务或变更部署通道时，重新评估支持期限与自动化；不能仅为缩短一次热修而省去候选核对与恢复验证。
