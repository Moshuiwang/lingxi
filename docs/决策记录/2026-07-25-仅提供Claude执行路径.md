# 决策：当前只提供 Claude 执行路径

> 状态：现行
> 决定日期：2026-07-25（2026-07-26 明确管理员入口不属于业务用户执行路径；2026-07-27 将 Claude Agent SDK + 百炼兼容性升级为开工门禁；2026-07-28 门禁完成第一轮验证，会话、MCP、Skills 通过，审计采集与运行时工具边界未通过，本决策及其门禁不变）
> 来源：[GitHub Issue #7](https://github.com/Moshuiwang/lingxi/issues/7)；[GitHub Issue #9](https://github.com/Moshuiwang/lingxi/issues/9)；[GitHub Issue #14](https://github.com/Moshuiwang/lingxi/issues/14)
>
> 规则正文见[产品合同与外部边界](../产品合同与外部边界.md)的「系统与外部依赖边界」「不提供」。本文只说明为什么这样定。
>
> 本决策约束的是**产品交付给用户的执行路径**，与团队用哪个代理工具开发本仓库无关；研发工具的约定见[协作约定](../协作约定.md)。

## 要解决的长期问题

历史材料同时出现 Claude、Codex 和多 Agent 方案。Lingxi 需要一个不会让用户、管理员或实施者误解的现行范围。

## 决定要点

- 当前飞书问数和 JumpServer 高级工作台只提供 Claude Code + 百炼执行路径。
- 依赖该执行路径的业务实现开始前，必须先在受控环境跑通 Agent SDK + 百炼的最小真实链路，包括会话、MCP、Skills 和实际可用的审计采集点；未通过时只允许继续修复或收窄这条门禁，不进入业务功能实现。
- 普通用户不选择 Agent、模型或推理档位。
- 管理员使用的经批准 AI Agent 是独立的受控管理入口，不属于业务用户问数或高级工作台执行路径；具体管理 Agent 客户端不由本决策指定。
- Codex 飞书对话、Codex 私聊和多 Agent 自助选择不属于当前产品。
- 历史 Codex 文档只能用于理解过去的探索，不能作为 Lingxi 的实现、部署、验收或用户承诺依据。

## 对用户和边界的影响

- 用户只需要理解“向 Lingxi 提问”，不需要先选择底层 Agent。
- 管理员不会因为历史文档把普通用户问数切换到 Codex，或把管理 Agent 的身份与业务用户身份混用。
- 未来即使替换或增加执行路径，也必须保持用户权限、会话隔离、结果可信和交付边界。
- 实施团队会在投入完整业务实现前得到明确的“执行路径成立或不成立”结论，避免到上线前才发现 SDK、百炼、MCP 或审计能力无法组合工作。

## 不采用的选择及原因

- **同时提供 Claude 与 Codex 供用户选择**：增加用户理解成本，也会形成两套配置、会话和验收口径。
- **按用户静默切换不同 Agent**：用户无法判断上下文和能力为何变化，异常也更难解释。
- **把兼容性留到实现期逐步发现**：执行路径同时跨 Agent SDK、百炼、MCP、Skills 和审计采集，任一基础假设不成立都会推翻后续实现；先通过最小真实链路的成本远低于完成业务功能后返工。

## 复审或替代条件

- 产品负责人明确决定引入新的执行路径；
- 新路径已经具备与现有权限、会话、交付和可用性规则相同的验收证据；
- Claude Code + 百炼不再满足产品的有效能力或合规要求。
