# 决策：生产 secret 注入与凭据隔离

> 状态：现行
> 决定日期：2026-08-28
> 来源：[GitHub Issue #135](https://github.com/Moshuiwang/lingxi/issues/135)（承接 [Issue #62](https://github.com/Moshuiwang/lingxi/issues/62)）；产品负责人 2026-08-14 在 #135 的澄清与决定评论；Trace #373 H2 批 S-H2-4 落盘。
>
> 规则正文见 [`deploy/生产部署runbook.md`「九、secret 注入与凭据隔离」](../../deploy/生产部署runbook.md)与 [`deploy/README.md`「部署前置检查」](../../deploy/README.md)。本文只说明为什么这样定。

## 要解决的长期问题

`biai-stage` 研发环境的 secret 注入是手工做法（`0600` env 文件，逐服务拆分）；#135 提出生产部署需要一个明确的凭据隔离与注入边界，但当时明确标注「待生产阶段处理，不阻塞 Stage 验收」，长期悬而未决。#369 生产就绪盘点把它列为第 1 条已知缺口，指出「散落在 6+ 处、无统一台账」的问题。本决定把这条长期悬而未决的边界钉死，避免生产部署 Trace 开工时重新论证。

## 决定要点

- **完全隔离**：生产凭据集与研发/Stage 凭据集不共用任何值；唯一例外是百炼模型端点凭据，产品负责人明确授权生产可沿用当前研发环境使用的同一套百炼凭据，且该例外只注入 worker/模型执行路径，不给 gateway、scheduler 或无关进程继承。
- **Stage 维持现状**：`biai-stage` 继续使用现行 `0600` env 文件机制，本决定不改动 Stage 的注入方式。
- **生产首发起步方案**：docker compose secrets 或 `0600` env 文件（与 Stage 同型机制），二选一均可满足首次生产发布的边界要求。
- **OS 级密钥管理迁移路线书面化，不落地**：作为后续路线登记触发条件与大致形态，本次不做任何迁移实施。
- **生产执行本身不在本决定或本 Trace 范围**：真实凭据值的生成、分发、写入生产主机等执行动作留给独立 `[ops]` Issue，本决定与配套 runbook 只提供边界与操作正文。

## 为什么这样定

- 产品负责人 2026-08-14 的澄清已经给出了可执行的边界：生产使用当前已运行的正式飞书机器人及生产应用凭据、`Bot-Test` 继续只留在研发/Stage、百炼凭据按明确授权可以复用、其余凭据类别（生产数据库连接、专用飞书授权主体的 refresh token 及其加密密钥、OAuth Bridge token、问数 MCP 端点/用户级凭据、私有 GHCR 拉取 token、状态完整性密钥）不预设复用。这条澄清此前只停留在 Issue 评论，未落回长期文档，本决定把它固化为可复审的正文。
- `deploy/README.md`「凭据文件权限」一节已经证明：在 OS 级密钥管理落地之前，文件权限是这套边界的唯一保护层——研发环境已经用同一套逻辑跑通，生产首发复用同一机制成本最低，不需要为了"首发就要有 KMS"而新增一个尚无必要性证据支撑的长期运维对象。
- #369 台账把「secret 注入机制待决策」列为生产部署 Trace 的输入缺口之一；不钉死这条边界，规划者起草生产部署 Trace 开工合同时会重新陷入同样的讨论。

## 对用户和边界的影响

- 对最终用户不可见；只影响运维与实施边界。
- 生产部署机、CD 脚本与任何自动化都不得引用或读取研发/Stage 凭据文件，反之亦然；`.env.prod.*` 与 `.env.stage.*` 系列在内容上必须互不重叠（百炼凭据这一项例外）。
- 生产数据库连接与迁移连接、专用飞书授权主体的 refresh token 及其加密密钥、OAuth Bridge token、问数 MCP 端点/用户级凭据、私有 GHCR 拉取 token、状态完整性密钥均只存在于生产侧凭据集合，不进入仓库、Issue、PR、镜像或日志。

## 不采用的选择及原因

- **生产首发直接接入 OS 级密钥管理（KMS/Vault 类方案）**：当前没有促使这么做的真实需求证据（轮换频率、多主机分发、监管审计要求均未出现），首发前引入会增加一个尚未被真实运维验证过的长期依赖；改为登记触发条件，需要时再评估选型。
- **生产沿用研发/Stage 的凭据集合**：与「凭据不外泄、不跨环境复用」的安全边界直接冲突，唯一被接受的例外仅限百炼凭据且有明确产品负责人授权，未被采纳为更宽的默认做法。

## 复审或替代条件

- 出现监管、审计或密钥轮换的强制要求；
- 生产运维负担证明 `0600` env 文件或 compose secrets 不可持续（例如需要频繁轮换、需要向多主机分发）；
- 产品负责人另行拍板迁移窗口或迁移方案。
