# 决策：按中文姓名自动准入并采用银河权限范围

> 状态：已替代
> 决定日期：2026-07-25
> 来源：[GitHub Issue #7](https://github.com/Moshuiwang/lingxi/issues/7)
>
> 本决策关于自动准入和权限来源的规则已由 2026-07-26 的[自动准入与数据库权限发布边界](2026-07-26-自动准入与数据库权限发布边界.md)完整替代。本文只保留历史口径，不再作为实现或验收依据。

## 要解决的长期问题

Lingxi 首次面对一名飞书用户时，需要确认该用户是谁、可以访问哪些公司和职能，以及正常用户是否仍要填写申请并等待人工审批。

飞书与银河分别保存不同的用户信息。Lingxi 必须在不猜测身份、不扩大银河既有权限的前提下，把两边信息关联成一个可持续使用的用户。

## 已接受的规则

- 用户第一次私聊时，系统自动取得飞书允许提供的中文姓名、`open_id`、`user_id`、`union_id`、部门和租户等必要信息。
- 系统建立统一 `user` 用户表，关联飞书身份、银河权限身份和 Lingxi 内部状态。
- 首期以飞书中文姓名与银河导出的用户权限名单中文姓名进行匹配。
- 只有唯一命中且权限信息完整时才自动通过；公司和职能范围直接采用银河记录。
- 正常路径不要求用户填写权限申请，不设置人工审批。
- 唯一命中后，系统继续自动创建用户环境、发布权限并确认可用；全部明确成功后才允许问数。
- 未查到、重名、必要信息缺失或名单不可用时，暂停整个创建过程并通知管理员人工处理。
- 管理员人工处理只负责确认正确银河记录或终止创建，不得借此扩大银河已有权限；终止创建时必须通知用户最终未开通结果和下一步。
- 身份已确认后，环境创建、权限发布或可用性确认结果不明确时，转由运维核对实际状态并从未确认步骤安全恢复，不重新进行身份判断，也不盲目重跑整个流程。

## 对用户和边界的影响

- 正常用户首次私聊后即可等待系统自动开通，不需要理解公司、职能、权限发布或内部环境。
- 异常用户看到“正在人工核对”，不会收到虚假的成功或永久失败说明。
- 人工核对或运维处理结束后，用户一定收到“可以使用”或“尚未开通”的最终结果。
- 银河导出的权限名单决定用户的公司和职能范围；Lingxi 只保存映射和处理状态。
- `user` 用户表只保存身份关联、权限判断、服务和审计所必需的信息，不保存短期令牌或认证材料。
- MCP 只能在银河确定的范围内执行查询和运行时控制，不得扩大该范围。

## 不采用的选择及原因

- **用户自行选择公司和职能**：可能申请或获得银河名单之外的范围，也给正常用户增加不必要步骤。
- **所有用户都等待人工审批**：银河已经提供权限名单，唯一有效匹配时继续人工处理没有用户价值。
- **模糊姓名匹配或自动选择同名记录**：存在把其他人的权限授予当前用户的风险。
- **把工作邮箱作为飞书实时反查条件**：已验证中心应用不能依靠该方式核对关联组织成员。

## 复审或替代条件

出现以下情况时必须重新评估本决策：

- 银河导出名单不再包含稳定的中文姓名、公司或职能范围；
- 中文姓名唯一匹配在实际运行中产生不可接受的错配风险；
- 飞书或银河提供更可靠、可直接对齐的稳定身份标识；
- 公司身份治理要求所有用户重新引入人工审批；
- 用户表的隐私、保留或审计要求发生变化。
