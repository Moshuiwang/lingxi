# 决策：飞书作为默认入口并固定会话边界

> 状态：现行
> 决定日期：2026-07-25（2026-07-26 明确会话计时起点、任务运行中的指令行为与高级工作台形态；2026-08-13 撤销对机器人专属目录这一承载模型的预选；2026-08-13 按 [Issue #163](https://github.com/Moshuiwang/lingxi/issues/163) 明确会话边界同时是已送达安全结果正文的清除边界；2026-08-14 撤销"超两小时的新会话"作为正文清除触发点的惰性判定耦合，改为空闲满两小时到点主动清除、续用判定与正文清除时机相互独立）
> 来源：[GitHub Issue #7](https://github.com/Moshuiwang/lingxi/issues/7)、[GitHub Issue #97](https://github.com/Moshuiwang/lingxi/issues/97)、[GitHub Issue #140](https://github.com/Moshuiwang/lingxi/issues/140)、[GitHub Issue #163](https://github.com/Moshuiwang/lingxi/issues/163)
>
> 规则正文见[产品合同与外部边界](../产品合同与外部边界.md)的「问数与多轮对话」「高级工作台」。本文只说明为什么这样定。

## 要解决的长期问题

Lingxi 同时规划飞书和 JumpServer 两种入口，需要明确普通用户从哪里开始、两个入口是否代表不同权限，以及连续追问在什么情况下继续或重新开始。

会话规则还要能回答几个具体问题：一个长任务跑了很久算不算“中断过”、任务运行时用户敲的指令去哪了、以及高级工作台里的用户到底在操作什么。

## 决定要点

- **飞书私聊是默认入口**，承载首次自动准入、日常问数、多轮追问和结果交付，不受公司内部局域网限制。
- **飞书私聊主窗口和每个用户主动创建的原生话题各自形成独立对话**，可以并发执行、上下文隔离；同一话题同一时间只执行一个任务。
- **任务运行中，除 `/stop` 外的所有消息（包括 `/new`）只收到忙碌提示**，不入历史、不排队、不在任务结束后自动生效。
- **会话是否延续，按“上一条任务结束到下一条新任务开始”的间隔判断**，超过两小时用新会话服务用户；任务本身执行多久都不触发新会话。
- **会话规则只适用于飞书**，与高级工作台无关。
- **会话边界同时是已送达安全结果正文的清除边界**（[#163](https://github.com/Moshuiwang/lingxi/issues/163) 方案 B）：清除触发为 `/new`、会话空闲满两小时由系统定时到点主动清除、用户停用或权限变化一经感知立即清除；续用判定（上一条任务结束到下一条新任务开始的间隔）与正文清除时机相互独立，不是同一惰性判定（2026-08-14 补充决定，[#163 评论 5290450443](https://github.com/Moshuiwang/lingxi/issues/163#issuecomment-5290450443)）；具体保留规则见[问数可信交付与数据保留边界](2026-07-26-问数可信交付与数据保留边界.md)。
- **高级工作台首期由 JumpServer 提供**，是公司内部局域网中浏览器里的终端，用户自行进入 Claude CLI；只面向能使用命令行的用户，单独申请，不增加数据权限，不与飞书共享上下文。
- **高级工作台与飞书复用同一份正式产物交付合同**，由统一的交付 Skill 使用 #140 最终批准且经 #97 所需真实探针验证的承载路径；在该路径可用前正式产物失败关闭，不以机器人专属目录作为交付或开通前提。

## 为什么这样定

**会话计时从“上一条任务结束”起算，而不是从“上一条消息”起算。** 用消息时间起算会产生一个真实矛盾：一个跑了两小时以上的深度分析任务，用户在任务运行中发消息时，“超时开新会话”和“任务运行中只提示忙碌”两条规则会同时命中且互相冲突。改用任务结束时间起算后，任务运行期间不可能超时，矛盾从定义上消失，不需要额外的优先级规则。两小时衡量的是用户真实的中断时长，这本来就是它的本意。

**`/new` 在任务运行中不生效，和普通消息一致。** `/new` 的语义是清空当前上下文，但任务还在跑，结果返回时上下文归属会变得不确定。让 `/new` 和普通消息一样只收到忙碌提示，用户模型最简单：任务运行时这个话题只接受 `/stop`。`/new` 也不排队，因为用户在等待期间的意图，等任务结束后未必还成立。

**`/stop` 是唯一豁免。** 用户必须始终有一个可以中止的出口，否则一个长任务会让整个话题失去响应。

**高级工作台只面向能使用命令行的用户。** 它的形态就是浏览器里的终端加 Claude CLI，不是一个另做的图形界面。与其为不会用命令行的用户勉强包装，不如明确这条边界：这类用户继续用飞书私聊，不损失任何数据范围。这样高级工作台不需要承担“对所有人友好”的设计负担。

**高级工作台复用同一份交付合同，而不是预选同一个目录。** 两种入口都必须使用受控交付端点，并对归属、授权、发送、状态不明、保留和清理执行相同规则。2026-07-25 曾用“同一机器人专属目录”来避免两套产物管理方式；2026-08-13 的外部事实已否定其自动离职交接前提，因此这一承载模型只保留为历史背景，不构成实施授权。具体路径由 #97 提供证据、#140 作最终选择。

## 对用户和边界的影响

- 普通用户无需理解服务器、SSH、模型配置或会话编号，直接在飞书完成主要任务。
- 中断两小时以内的连续追问可以利用已有上下文；长时间中断后不会让过期上下文影响新问题。长任务不会因为执行时间长而被误判为中断。
- `/new` 给用户提供明确、可控且不需要另建飞书话题的上下文重置方式；任务运行时的行为可预期。
- 高级工作台只是使用方式变化，飞书查不到或无权访问的数据不能从 JumpServer 绕过。
- JumpServer 不是第二阶段设想，而是首期提供给另行获批用户的正式入口；局域网限制不影响用户在飞书中的问数体验。

## 不采用的选择及原因

- **让飞书和 JumpServer 成为同等默认入口**：会把登录、环境和选择成本推给普通用户。
- **把 JumpServer 延后到第二阶段**：不能满足首期持续、深度分析用户进入个人工作环境的需要。
- **默认给所有用户开通 JumpServer**：高级工作台需要独立申请和管理，不属于飞书自动准入的一部分。
- **为不会用命令行的用户在高级工作台上再做一层界面**：飞书私聊已经覆盖这类用户，重复建设没有增量价值。
- **让飞书与 JumpServer 共享上下文**：两条链路独立，强行共享会增加用户对当前会话、执行环境和结果来源的误解。
- **从上一条消息时间起算会话超时**：会与“任务运行中只提示忙碌”产生无法自洽的规则冲突。
- **让 `/new` 在任务运行中立即生效或排队执行**：前者使运行结果的上下文归属不确定，后者会执行用户可能已经放弃的意图。
- **让每条消息都成为新对话**：无法支持围绕同一业务问题连续追问。
- **永久复用一个对话**：过期上下文容易干扰新的业务问题。
- **新会话时重新准入**：会重复创建用户和权限处理，且与用户身份生命周期不符。

## 复审或替代条件

- 实际使用证明两小时不符合主要业务节奏；
- 飞书平台会话机制发生变化；
- 产品引入用户可见的会话列表或历史会话恢复；
- 高级工作台不再由 JumpServer 提供，或需要覆盖不使用命令行的用户。
