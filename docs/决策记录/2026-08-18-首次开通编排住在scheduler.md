# 决策：首次开通编排住在 `lingxi-scheduler`，gateway 只记事件

> 状态：现行
> 决定日期：2026-08-18
> 来源：产品负责人在 [Issue #203](https://github.com/Moshuiwang/lingxi/issues/203) 的裁定（三个方向中选定「把开通链整体移进 scheduler」）
>
> 落地正文见[架构设计](../技术设计/架构设计.md)与 `src/lingxi/apps/scheduler/onboarding.py`。本文只说明为什么这样定、放弃了什么、什么条件下要重新评估。

## 要解决的长期问题

首次开通的第一步是**定位员工并确认他在职**。产品合同把在职校验写成硬门槛（非在职不建档、不发权限），而在职状态**只能实时回读**飞书成员详情——组织快照刻意不保存它（保存会立刻产生「库里在职、飞书已冻结」的陈旧窗口，而这个字段的唯一用途恰恰是拦截这种情况）。

那次回读需要专用授权主体派生的短期令牌，而派生它要消费一条**一次性** `refresh_token`。**全系统只允许一个消费者**：2026-08-08 的事故正是两个客户端抢同一条独占通道，静默烧掉了产品负责人的一次性授权码，用户侧表现为「点了授权、页面显示处理中、后台什么也没发生」。那个唯一的合法消费者（凭据轮换职责与进程内的派生令牌持有者）住在 `lingxi-scheduler`。

于是问题变成：编排要读在职状态，而令牌只在 scheduler 里。

## 决定要点

- **首次开通编排整体住在 `lingxi-scheduler`**，在职回读复用该进程里**已有**的派生令牌供给，不新建第二条凭据通道。
- **gateway 只做两件事**：把未开通用户的首聊事件落进 `inbound_event`（标成 `auto_provisioning`），并**立刻**回一条合同要求的「已收到，正在核对」。它不再持有任何会产生外部副作用的开通实现。
- **交接走数据库**：scheduler 按既有的「认领一条待交接事件」路径取走事件，认领即记账；没跑成的必须显式把认领**放回去**。
- **接受首触延迟**：首次开通要等一个扫描周期才开始（stage 约 30 秒）。合同要求的第一条提示不受影响——它由 gateway 即时发出。

## 为什么这样定

- **凭据边界是硬约束，进程边界是软的。** 让 gateway 也去换令牌，等于把已经出过事故的形状重新造一遍；而把编排搬个进程，代价只是一段可接受的首触延迟。
- **编排本身与进程无关。** 它的判定层是纯逻辑、协作者全部注入，搬迁没有改动任何一条判定；这正是当初把它写成注入式的收益兑现。
- **搬迁顺带消掉了一类缺陷。** 编排原先跑在 gateway 的长连接线程 / 投递线程附近，一条十五分钟的等待会让「收不到消息」或「发不出投递」；现在它跑在 scheduler 里自己的线程池上，两条用户可见循环都碰不到它。
- **延迟落在正确的地方。** 用户感知的第一条回复仍然是即时的；被推迟的是他看不见的后台步骤，而那一步本来就要花几十秒到几分钟。

## 对用户和边界的影响

- **首次开通的第一条提示仍然即时**；「正在同步、最多十五分钟」与最终结论比搬迁前晚约一个扫描周期到达。
- **进程数不变**，不新增常驻服务、不新增外部权限、不新增凭据通道。
- **scheduler 的职责面变宽**：它从「定时职责进程」变成「定时职责 + 首次开通编排」。因此它的停机语义要同时对两者成立——在途开通链在每一步之间看停止标志，中止时把认领放回去，不留下「外部副作用已经产生、账本却已平」的形状。
- **gateway 的故障不再中断开通**：事件已经落库，gateway 重启不影响 scheduler 继续跑。反过来 scheduler 不可用时，事件原样积压在库里，配置或进程恢复后照常被认领——**不会被烧掉**。

## 不采用的选择及原因

- **scheduler 派生令牌后经受控通道供给 gateway**：要新建一条跨进程的凭据传递面（新的载体、新的鉴权、新的失效语义），而它保护的只是一次在职回读。收益与新增攻击面不成比例。
- **让 gateway 成为第二个 `refresh_token` 消费者**：与 2026-08-08 事故的形状完全一致，直接否决。
- **把在职状态存进组织快照，让 gateway 自己判**：合同与实测都否决过——可见范围不做在职过滤（710 人中含 5 名冻结、1 名未加入），存下来就会产生「库里在职、飞书已冻结」的陈旧窗口，而这正是该字段要拦的情况。
- **gateway 同步跑完整条链**：一条链最长十七分钟，跑在长连接线程上等于 gateway 十七分钟收不到任何消息，而现场只表现为「机器人不理人」。

## 复审或替代条件

出现下列任一情况时重新评估：

1. 飞书提供了不消费一次性 `refresh_token` 的在职状态读取方式（例如应用级 tenant token 可读），凭据独占的前提消失；
2. 首触延迟被证明不可接受（例如产品要求首次开通在数秒内出结论），需要重新讨论跨进程供给或事件通知；
3. scheduler 因为承载开通链出现容量或停机语义问题，需要把它拆成独立进程（那将是一次新增常驻进程的决定，须重新批准）；
4. 出现第二个必须实时读飞书身份的用户路径，使「谁持有派生令牌」的答案不再唯一。
