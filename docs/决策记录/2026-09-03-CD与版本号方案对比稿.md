## 一、要解决的问题

产品负责人 2026-09-02 提出：以后每次更新不要再「模型逐步执行 + 产品负责人逐步放行」，要简单；同时把版本号管理纳入 CI/CD。

**今天一次发布实际发生什么**（现状事实，非推测）：

1. 代码合入 `main` → `Main Publish` 回读 `Epic Full` 候选证明，树一致后构建并推送四个不可变 tag 镜像（`<日期>-<sha 前 12 位>`），每个镜像的 digest 由 `scripts/ci/push_image.py` 向仓库独立回读后写进 run summary。
2. **自动化到此为止。** 之后的每一步都是人（模型）在终端里逐条执行：把四个 tag 各解析成 digest、抄进 `deploy/.env.<环境>` 的四个变量、跑 `migrate`、`--profile mvp up -d`、`images` 逐服务核对 digest、15 分钟观察期回读健康。
3. 对 `biplus-prod`，上述每一条写命令都需要产品负责人在 tz 本机单独放行（本机分类器把 prod 主机判为敏感，写命令要产品负责人亲手加权限规则，一次一条扁平命令）。
4. 版本号：整仓单一版本写在 `pyproject.toml`，发布随批次打 `v<版本>` git tag（当前 `v2.0.0`），`CHANGELOG.md` 按批次维护。这三处**目前全部由编排者手工保持一致**，没有任何机器核对。

所以诉求其实是两件不同的事：**（a）把第 2、3 步的放行次数从 N 次降到 1 次或 0 次**；**（b）给第 4 步加机器核对**。两件事可以分别决定，本文分开给方案。

## 二、不能放弃的底线（用作逐条核对表）

来自 `AGENTS.md`「Code Review Rules」、[`deploy/生产部署runbook.md`](../../deploy/生产部署runbook.md)与[决策：生产 secret 注入与凭据隔离](2026-08-28-生产secret注入与凭据隔离.md)：

| 编号 | 底线 | 今天靠什么成立 |
| --- | --- | --- |
| L1 | 不在生产环境现场构建 | 机制：三个 compose 文件里没有任何 `build:` 键 |
| L2 | 只部署已验收并冻结的制品，通过外部配置发布 | 机制：`Main Publish` 是唯一构建点；主机只改 env 指向 |
| L3 | digest 固定 | 纪律：人工把四个 digest 抄进 `.env.<环境>` 后 `images` 回读核对 |
| L4 | 单实例、不灰度 | **纪律**：`gateway`/`worker-queue` 没有代码级互斥，靠「同一时刻只有一个操作者」 |
| L5 | 重启/重试不丢用户结果，有可验证的恢复路径 | 机制 + 纪律：回滚 = 回退四个 digest 变量后 `up -d`，不碰库与卷；前提「迁移先加后删」由 `V-部署-05` 每次 CI 机械核对 |
| L6 | 凭据零接触代理 | 机制：根 `.env.<环境>` 只装镜像仓库前缀、tag 与四个 digest，**不含任何凭据**；凭据在六份 `.env.<环境>.<服务>` 里（0600） |
| L7 | 不硬编码生产路径或配置、不人工修改生产文件 | 纪律：runbook 里的命令都参数化到 `--env-file` |

L6 这条对下面的比较特别重要：**部署自动化只需要写根 env 那一个文件，而那个文件里没有凭据**——这不是纪律，是现有文件切分带来的结构性事实。

## 三、本项目的现实约束

这一节是三个方向能不能成立的前提，事实与未知分开列。

**已核实的事实：**

- **仓库是 public**（`visibility: public`，2026-09-03 回源）。
- **本机机器人身份对本仓库 `admin: false`**（2026-09-03 回源）。任何需要仓库管理员权限的配置（GitHub Environment、保护规则、self-hosted runner 注册、Actions 策略）**必须由产品负责人本人的 GitHub 账号完成**，代理做不了。
- **仓库当前没有任何 GitHub Environment**（`environments.total_count = 0`）。
- **仓库当前没有任何 GitHub Release**；`v2.0.0` 与 `l4a-accepted-2026-08-06` 两个 tag 已推到 origin。当前 rulesets 只有两条分支规则（`main`、`epic/**`），没有 tag 规则。
- **`Main Publish` 现在只有 `contents: read`**，checkout 用 `persist-credentials: false`。要让它打 tag，必须给它 `contents: write`。
- **`pyproject.toml` 在 `scripts/ci/classify_story_changes.py` 的 `FULL_FILES` 里**，且在 `publish.yml` 的路径过滤里。任何单独改它的 PR 都会强制跑完整 `Epic Full`（含四镜像双构建），合并后又触发一次 `Main Publish` 多产四个镜像。
- **tz 本机访问两台主机都经本地回环端口**（`biai-stage` :22022、`biplus-prod` :22023，反向隧道形态）。据此，两台主机**没有面向公网的入站 SSH 端口**；GitHub 托管 runner（出口 IP 不固定）今天没有任何到 prod 的通路。
- **prod 有出站能力**：首发当日从系统软件源装 docker 与 python3.12 成功，且以匿名身份从 GHCR 拉到四个镜像（镜像包当日为公开）。
- **prod 今天没有备份点**：每日手工 `pg_dump -Fc` 是过渡方案，托管控制台的每日备份/PITR 开启后才撤销（runbook「十一、实录偏差」11.6）。
- **告警链路今天不完整**：`monitoring-push` 需要的数据库监控角色首发时未创建，登记为观察期项；容器日志留存首发未安装（同上 11.6）。

**未知（缺乏事实，不猜）：**

- prod 能否出站访问 `api.github.com` / `objects.githubusercontent.com`：**未实测**。能到 GHCR 与系统软件源不等于能到 GitHub API。方向 A 的自托管 runner 与方向 B 的清单轮询都依赖它。
- 两台主机的实际入站网络策略（防火墙、安全组）：只从 tz 侧的连接形态推断，**未回源核实**。
- 本文所有成本估算是**量级估算，未经实测**；实际耗时取决于审查轮次。

**需要产品负责人裁定、代理不替他判断的点**：方向 A 必须新开一条入站通路，或在 public 仓库上引入自托管 runner。**这两者都是扩大攻击面的决定**，不是实现细节。本文只把两种形态的代价摆出来，不给出「可控 / 可接受」的结论。

## 五、逐方向详述

### A. GitHub Actions 推式部署

**形态**：`Main Publish` 成功后触发 `deploy-stage` 自动执行；`deploy-prod` 由 GitHub Environment 保护规则（一次点击审批）触发；runner 经 SSH 到主机执行 `migrate` + `up -d` + 回读，四个 digest 由 Publish 产物注入。

**通路只有两种形态，代价不同：**

- **A1：给 prod 开一条能从公网到达的入站入口**（或引入一个双方都能到达的中转）。这是把「生产主机当前不可从公网直接到达」这条现状换掉。GitHub 托管 runner 的出口 IP 不固定，无法用 IP 白名单收窄。
- **A2：在 prod 上装自托管 runner**。它主动出站长轮询，**不需要入站端口**——但它把「谁能改工作流、谁能让工作流跑起来」变成「谁能在生产主机上执行任意命令」。**本仓库是 public 仓库**，公开仓库上跑自托管 runner 是 GitHub 官方明确警告的组合（fork PR 的工作流可在 runner 上执行外部提交者的代码）。要用它必须额外配一整套限制（只在受保护环境运行、禁 fork PR 触发、runner 跑一次性容器…），而这些限制本身也需要仓库管理员权限来设。

**实现成本**：2–3 张实施卡。其中「通路」那一张的成本完全取决于产品负责人对 A1/A2 的裁定，现在**未知**。

**运行风险**：

- 部署凭据（SSH 私钥或 runner 注册令牌）进 GitHub Secrets。代理不接触值，L6 成立；但凭据持有方从「主机本地 0600 文件」扩大到「GitHub 平台 + 任何有仓库管理员或工作流写权的人」。
- **审批点看不见内容**：GitHub 网页审批展示的是工作流名与分支，不是这次要部署的四个 digest。要做到「点的那一下确实对应看过的那批镜像」需要额外把 digest 写进审批可见位置。
- **观察期**：15 分钟窗口里的健康回读可以自动化；但「业务异常」类判据（scheduler 日志持续报错、gateway 连不上长连接）今天没有机器判据——这条限制三个方向同样存在。
- **单实例纪律（L4）**：自动触发意味着「同一时刻只有一个操作者对 prod 发 compose 命令」要靠 workflow concurrency 保证。concurrency 挡得住同一工作流的并发，挡不住有人同时在主机上手工执行。

**底线逐条核对**：L1 符合（部署工作流只 pull），但 A2 下主机上有了具备 docker 权限的 runner，「不现场构建」从机制退成配置；L2 符合；L3 **优于现状**（自动注入四个变量，消除抄错）；L4 见上，从纪律变成半机制；L5 **需要工作流自己实现自动回滚，实现前不符合**——工作流中途失败会把 prod 留在半升级状态（迁移跑完但服务没起，或部分服务起了）；L6 符合但新增平台侧凭据；L7 需注意工作流里不硬编码主机路径。

**失败与回滚**：这是 A 最需要设计的部分。回滚动作本身是确定的（回退四个 digest 变量 + `up -d`），但要在 runner 上可靠执行，且要能区分「migrate 失败」「up 失败」「观察期不达标」三种入口。

**半夜谁能关掉**：能登 GitHub 的人可以取消运行、停用工作流、撤销 Environment 审批。**但 A2 下关掉 GitHub 侧不等于关掉主机上的 runner**——那需要有人 ssh 上 prod 停服务，而这条路今天只有 tz 本机和产品负责人。

### B. 主机拉式部署

**形态**：prod/stage 各装一个 systemd timer 触发的一次性单元，轮询仓库里的「发布清单」（tag + 四个 digest）；发现与本地不一致就本地执行 `migrate` + `up -d` + 回读。产品负责人批准 = 合并一个「发布清单」PR。

**实现成本**：2 张实施卡。① 让 `Main Publish` 把本批四个 digest 产出成机器可读清单——**这一步几乎白送**：`push_image.py` 已经在推送后向仓库独立回读 digest 并写进 run summary，只需要把它同时落成一个入库文件或 Release 资产。② 写拉取代理（一个脚本 + 两个 systemd 单元）与回读、自动回滚。

**结构性优势**：代理只需要写 `deploy/.env.prod` 这一个文件，而该文件**不含任何凭据**（L6）。因此「代理零接触凭据」在 B 下是结构上的，不靠纪律。仓库与镜像当前均为公开，主机匿名拉取清单与镜像即可，**不需要在主机上放任何 GitHub 凭据**。

**运行风险**：

- **清单可信度**：谁能改清单，谁就能让 prod 拉任意镜像。缓解是「清单只能经 PR 合入 `main`，代理只接受 `main` 上的清单」（`main` 已有 ruleset）。要不要再加签名是一个取舍：签名多一套密钥要管，不签则信任面是 GitHub 平台加分支保护。**需要裁定。**
- **无人值守的观察期**：timer 在任意时刻触发，没人盯着那 15 分钟。代理必须自己做完整回读并在不达标时自动回滚 + 告警。**但今天告警链路并不完整**（`monitoring-push` 的数据库监控角色未创建）。这是 B 的硬前置，不是可以边跑边补的项。
- **无人值守的迁移**：`migrate` 失败必须被识别并阻止 `up -d`。`V-部署-05`（旧镜像 + 新库结构）每次 CI 机械核对，让「先加后删」这条前提有机器保证，实质降低了风险但不消除。叠加「prod 今天没有备份点」这条，无人值守迁移的最坏后果目前没有兜底。
- **静默失败**：timer 挂掉的表现是「什么也没发生」。代理必须有一个「上次成功检查时间」的可观测出口，否则会出现「以为在自动部署，其实两周没动过」。
- **与人工操作撞车**：代理必须持锁（`flock`），否则会破坏 L4 单实例纪律。

**底线逐条核对**：L1 符合且仍是机制（主机不需要 docker build）；L2 符合，且清单就是 digest；L3 符合并优于现状；L4 需代理持锁实现；L5 回滚路径确定、代理可实现；L6 **结构性符合**；L7 代理脚本入库，须参数化环境，stage/prod 同一份脚本不同配置。

**失败与回滚**：回滚路径确定（回退四个 digest 变量 + `up -d`，不碰库与卷）。最坏情况是代理自身坏了——那时退回 C 的人工路径，不会比现在更糟。这一点是 B 相对 A 的重要优势：**B 的失败模式是「不动」，A2 的失败模式可能是「动了不该动的」**。

**半夜谁能关掉**：能登 prod 的人一条 `systemctl disable --now <timer>`。今天 = tz 本机 + 产品负责人。**注意：这条关停命令本身今天也要过 tz 分类器与产品负责人放行**，也就是说「关掉它」现在也不快。若选 B，应一并给产品负责人一条他自己能直接执行的关停命令。

### C. 现状精简（幂等脚本，一次放行）

**形态**：仍由模型执行，但把 runbook 整段做成一个幂等脚本，一次放行。

**实现成本**：1 张实施卡，素材齐全——runbook「三、镜像 digest 固定」「六、回滚判据与步骤」「十一、实录偏差」已经把命令、判据和坑写得很细（含首发实测的五条命令形态偏差）。

**运行风险**：

- **单次放行的爆炸半径变大**：现在是 N 个小动作各放行一次，产品负责人在每一步能看见并叫停；改成一次放行整段脚本后，中途看不见。缓解：脚本默认 dry-run、每个闸口输出机器可核对的判据、任一判据不达标即停并打印回滚命令。
- **只解决了一半诉求**：放行次数从 N 降到 1，但「要有个模型在场跑」这件事没变。
- 脚本的 prod 路径无法在 CI 覆盖，只能在 stage 上演练。

**底线逐条核对**：L1–L7 **全部原样保持**——脚本只是把现有命令固化，不改变任何机制，不新增攻击面、常驻物或凭据持有方。

**失败与回滚**：与今天完全一样，且脚本可以把回滚也做成一条命令（今天回滚是四个变量手改后 `up -d`）。

**半夜谁能关掉**：Ctrl-C。风险最低的一项。

## 六、版本号 / CHANGELOG / tag 纳入 CI 的两个候选做法

### 候选 ①：合并前 CI 校验三处一致，合并后自动打 tag

**做法**：新增 `scripts/ci/check_release_version.py`，当改动触碰 `pyproject.toml` 的 version 或 `CHANGELOG.md` 时校验三件事一致——`pyproject` 的 version、`CHANGELOG.md` 里存在同号的已发布小节（不是空的 `[Unreleased]`）、该版本号尚无同名 git tag。合并到 `main` 后由 `Main Publish` 的一个新增 step 打 `v<版本>` tag 并生成 Release 说明。

**成本**：低。1 张实施卡（校验脚本 + 单测 + 接进现有文档门禁与 gate + Publish 里一个打 tag 的 step）。

**这条最重要的成本发现**：升版必须**放进批次收口 PR 一起合，不要单开 bump PR**。因为 `pyproject.toml` 同时在 `classify_story_changes.py` 的 `FULL_FILES` 和 `publish.yml` 的路径过滤里——单开一个只改版本号的 PR 会强制跑一整轮完整 `Epic Full`（含四镜像双构建），合并后又触发一次 `Main Publish` 多产四个没人会用的镜像。这与[验证与门禁](../技术设计/验证与门禁.md)「金字塔频率纪律」（不允许为单个 commit 触发上层昂贵验证）直接冲突。

**失效模式**：

- 打 tag 需要给 `Main Publish` 加 `contents: write`（现为 `contents: read`）。这是给发布工作流扩写权限，要显式登记裁定。
- tag 必须打在 `Main Publish` 实际构建那批镜像的 commit 上，且只能在 publish job 成功之后打，否则 tag 与镜像对不上。
- 重跑要幂等：`Main Publish` 的 concurrency 是 `cancel-in-progress: false`，同一 commit 重跑时 tag 已存在必须跳过，绝不能 force。
- `[Unreleased]` 今天是空段。校验规则必须允许「本批没有用户可见变化」这种合法情况，否则会逼着人写假条目。
- 它只能证明三处一致，**证明不了版本号选得对**（该升次版本却升了补丁版本，机器判不了；SemVer 的判断依据是有没有破坏用户承诺，见 [`deploy/README.md`](../../deploy/README.md)「版本号规则」）。

### 候选 ②：release-please 类工具生成版本 bump PR

**做法**：引入 release-please（或等价工具），读 Conventional Commits 自动开一个「版本 bump + CHANGELOG 生成」PR，合并即打 tag、建 Release。

**成本**：表面低（一个 Action + 一份配置），实际中等。本仓库提交信息是中文、形如 `docs(#540): …`，与 Conventional Commits 形式兼容但 scope 用的是 Issue 号；工具生成的是逐 PR 条目列表，而现行 `CHANGELOG.md` 的体例是**按发布批次、面向用户写、每条引用 Issue**（见 2.0.0 那一节）。要保住现行体例就得大量定制或人工重写，那正好抵消它的主要收益。

**失效模式**：

- **它的 bump PR 正好是上面那个最贵的形态**：只改 `pyproject.toml` + `CHANGELOG.md`，每个发布批次多付一整轮完整 `Epic Full` 加一次多余的 `Main Publish`。
- 它按提交信息自动决定版本号级别，而本仓库「破坏用户承诺才升主版本」的判断不是提交信息能表达的；自动结论可能与产品判断不一致，仍需人工覆写。
- **本仓库最可能踩的雷**：用 `GITHUB_TOKEN` 开的 PR 不会触发其他工作流（GitHub 既有语义），意味着 bump PR 上可能不跑 `Epic Full`——那会让一个没跑过门禁的提交进 `main`，随即撞上 `Main Publish` 的候选证明回读而整批发布失败关闭。绕开要换成 App 令牌，那又是新增一份凭据。
- 往发布路径上新增一个第三方 Action，是新增供应链依赖。现行工作流里第三方 Action 都钉了 commit sha，沿用同一纪律即可，但依赖本身是净新增。

### 顺带的近零成本项

镜像加一个 `org.opencontainers.image.version` label（值取自 `pyproject` 的 version）。它对同一提交恒定，因此**不破坏两次构建内容等价**（`V-部署-06`）——Dockerfile 里已有的 `org.opencontainers.image.revision` 就是同一理由。成本近零，收益是「拿到一个镜像就能读出它是哪个语义版本」。

## 七、建议

**部署方向：C 立刻做，B 作为目标态，A 现在不做。**

1. **C 是唯一能在本批之后立刻拿到收益、且不新增任何攻击面/常驻物/凭据持有方的选项。** 它把产品负责人触点从「N 次逐步放行」降到 1 次，直接回应诉求里最痛的那一半。
2. **B 是唯一能真正做到「一次点击、不需要模型在场」，同时不开入站通路、不引入平台侧部署凭据的选项。** 它的凭据零接触是结构性的。但它有两条今天还不成立的硬前置：**告警链路不完整**、**prod 没有备份点**。在这两条闭合之前，让一个无人值守的东西在 prod 上跑迁移和升级，等于拿「没人看着 + 没有备份」去赌。
3. **A 的稳态收益（一次网页点击）与 B 等价，代价不等价**：A 要么换掉「生产主机不可从公网直接到达」这条现状（A1），要么在 public 仓库上引入自托管 runner（A2）；两者都需要产品负责人本人的 GitHub 管理员操作，且都扩大攻击面。**「A 与 B 收益等价、代价不等价」是我给出的事实；选不选 A 是产品负责人的裁定，本文不替他判断风险是否可接受。**

**版本号方向：候选 ①。** 成本低一个量级、不新增供应链依赖与凭据，并且能顺手把「升版放进批次收口 PR」这条纪律机器化。

**如果产品负责人选另一个，最小可行第一步：**

- **选 A** → 不碰 prod，先只做 **stage 的推式部署**。stage 是受控测试环境且已有多次滚动升级实录，用它把「工作流注入 digest → migrate → up -d → 回读 → 失败自动回滚」整条链路跑通并留证据；prod 通路形态（A1/A2）单独立卡、单独裁定。即使最后 prod 不走 A，这份投入也不浪费——同一套工作流可以改成 B 的清单生产者。
- **选 B** → 第一步只做「**让 `Main Publish` 产出发布清单**」（tag + 四个 digest 落成入库文件或 Release 资产），主机侧什么都不装。这一步单独就有价值：今天 digest 是人工逐个 `docker manifest inspect` 解析再抄进 env 的，清单一出，抄错的可能性归零，而且 C 的脚本可以直接读它。
- **选 ②（release-please）** → 先不让它接管版本号，只用它对着已有的 `v2.0.0` tag **生成一份 Release 说明草稿**，看它产出的条目与现行 CHANGELOG 体例差多少；确认能接受再谈让它接管 bump。

## 九、本稿不做什么

- **不实施任何 CD**，不改任何工作流文件、compose 文件、runbook 或部署脚本。
- **不打 tag、不动 prod、不动 stage。**
- 不替产品负责人判断任何一项风险「可控」或「可接受」。
- 裁定后由另立的实施卡承担落地，并把本文改写为正式决策记录、并入[决策记录索引](README.md)。

## 十、复审或替代条件

- 产品负责人对「八、待裁定点」给出裁定——本文随即失去草案身份，由实施卡改写。
- prod 的备份点与告警链路两条观察期项闭合——B 的硬前置消失，需重新评估 B 的启动时机。
- 镜像包改回 private（观察期项）——B 与 A 都需要主机侧持有只读拉取令牌，凭据结论要重算。
- 仓库改为 private，或出现第二个有权写发布清单的身份——D-4 的签名结论要重算。
- 出现 prod 的第二台主机或多实例需求——L4 单实例纪律的成立方式改变，三个方向的比较全部要重做。
