# 决策：内容目录文案变更必须递增版本

> 状态：现行
> 决定日期：2026-08-17
> 来源：产品负责人在 [Issue #190](https://github.com/Moshuiwang/lingxi/issues/190) 的[决定评论](https://github.com/Moshuiwang/lingxi/issues/190#issuecomment-5310857003)选定方案 1；问题由 [#162](https://github.com/Moshuiwang/lingxi/issues/162) 的 E-022 批次审核在 [PR #182](https://github.com/Moshuiwang/lingxi/pull/182) 上发现
>
> 规则正文见[代码框架](../技术设计/代码框架.md)的「内容目录的版本纪律」。本文只说明为什么这样定。

## 要解决的长期问题

`src/lingxi/config/content.toml` 的 `[meta] version` 会随投递与审计事件落库，是排查「用户反馈的文案与预期不符」时判断**用户当时实际看到的是哪一版文案**的唯一依据。但它此前只是一句口头约定：PR #182 改了多处用户可见文案（问数卡片去 header、状态文案改为「正在查询」「查询完成」）而版本号没动，审核同时确认「历史同样如此」。一个从未被强制的版本号会逐渐变成看起来存在、实际不可信的信号——排查时不但帮不上忙，还会把人引向错误结论。

## 决定要点

- 采用 #190 的方案 1：任何改变 `content.toml` 用户可见文案的变更，必须在同一提交里递增版本标识，并由会变红的程序门禁强制，不依赖人工审核把关。
- 版本标识不得复用历史用过的值；只调整排版、注释或键顺序不算文案变更，不需要递增。
- 一次性校准：版本由 `2026-08-08` 递增为 `2026-08-17`，并生成初始登记 `content.lock.toml`。**不追溯**校准之前的偏差——版本号从这一刻起才可信。
- 不采用方案 3（移除版本字段）：产品负责人核实 `content_version` 已随投递/审计事件落库，拆除要动事件结构，代价与收益不成比例。

## 为什么这样定

- 治理规则只要没有会变红的检查，就等于没有规则。这条纪律恰恰是在一次人工审核**已经发现问题**之后仍被确认为「历史同样如此」，说明依赖审核人肉眼（方案 2）在本仓库已经被证伪。
- 门禁刻意做成**静态、确定性、不看 git 历史**：只读 `content.toml` 与紧邻的 `content.lock.toml` 两个文件，比对与 TOML 排版无关的文案摘要和登记的 (version, digest)。因此本机与 CI 得到同一个结论，不依赖 base 分支、不依赖网络，也不会因为分支合并顺序产生假红假绿。
- 刷新登记的命令在「文案变了但版本没递增」时**拒绝写入**。如果刷新可以顺手把版本问题一起抹平，这道门禁三个月内就会退化成一条无人在意的机械步骤。
- 登记文件与 `content.toml` 同目录（`src/lingxi/config/`）而不是放在 `scripts/ci/`：后者会让每一次纯文案调整都触发完整门禁而不是快检，把一条轻量纪律变成持续的 CI 成本。

## 对用户和边界的影响

- 对用户无直接影响，是内部治理；用户可见文案本身不因本决策改变。
- 运维与排查：从 2026-08-17 起，落库的 `content_version` 能可靠对应一批确定的文案，可用于定位「用户看到的是哪一版」与回滚判断；此日期之前的版本值不具备该保证。
- 开发：改文案的提交多一步固定操作（递增版本 + 刷新登记），遗漏会被门禁拦下并直接给出修复步骤。

## 不采用的选择及原因

- **方案 2 保持现状、依赖 PR 审核**：同一问题已被审核发现却仍长期存在，人工把关不足以维持该纪律。
- **方案 3 移除版本字段**：`content_version` 已是落库的审计事实，移除要改事件结构，且会失去唯一的文案追溯口径。
- **按 git base diff 判断文案是否变化**：需要可信的 base、在合并与 rebase 后结论不稳定，本机也难以复现 CI 的判断。
- **追溯修复历史版本偏差**：历史哪一批文案对应哪个版本已无法可靠还原，追溯只会制造新的不可信记录。

## 复审或替代条件

- 内容目录改为按语言、按租户或按灰度分批发布，单一版本标识不再足以描述「用户看到的是哪一版」；
- 投递与审计事件不再记录 `content_version`，或改用其它追溯口径；
- `content.toml` 新增承载用户可见文案的顶层结构（届时门禁会失败关闭，需同步扩展检查范围）。
