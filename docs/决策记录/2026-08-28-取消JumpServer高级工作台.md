# 决策：取消 JumpServer 高级工作台

> 状态：现行
> 决定日期：2026-08-28
> 来源：产品负责人于 2026-08-28 生产就绪审查（[Issue #368](https://github.com/Moshuiwang/lingxi/issues/368)）结论提交后当日裁定取消；本记录随裁定当日落盘。
>
> 规则正文变化见[产品合同与外部边界](../产品合同与外部边界.md)：「高级工作台」一节改为取消声明（保留标题仅为既有引用不断链），相关条目删除，「不提供」新增对应条目。本文只说明为什么这样定。

## 决定要点

- **取消 JumpServer 高级工作台**：它不再属于产品范围，首期验收不包含高级工作台，飞书私聊成为唯一用户入口。
- 由此撤销或缩窄的既有决定：
  - [首期服务范围与真实验收](2026-07-26-首期服务范围与真实验收.md)中「JumpServer 属首期范围」与「高级工作台验收」两部分不再有效；三名真实用户七个工作日等其余验收门槛不变。
  - [飞书作为默认入口并固定会话边界](2026-07-25-飞书默认入口与会话边界.md)中的高级工作台条款失去对象；飞书入口与会话边界条款不变。
  - [用户之间的操作系统级隔离本轮不做](2026-08-19-用户间操作系统级隔离本轮不做.md)的「设为 JumpServer 硬前置」失去对象；该记录的其余约束（用户间不被越权读取当前唯一依赖执行层工具白名单、给 Agent 增加任何读文件或执行命令能力的工具前必须回到该决策）**继续有效**——取消 JumpServer 后，操作系统级用户隔离不再有任何已排定的落地载体，该约束反而更加关键。
- 重新提供高级工作台（无论是否由 JumpServer 承载）需要新的产品决策，并重新评估操作系统级用户隔离前置。

## 为什么这样定

2026-08-28 生产就绪审查确认了三项事实（Issue #368）：高级工作台在合同承诺一年内零实现、零工作项；其硬前置（操作系统级用户隔离：uid 分配 + worker 降权）同样未实现，且 2026-08-19 决策已评估其代价为「新增宿主机权限面 + 一套长期运维对象」的量级；项目临近首次生产部署，保留承诺但不排期会使首期验收口径不可判定。产品负责人在该结论基础上裁定取消，而不是继续挂账。

## 对用户和边界的影响

- 对现有用户零影响：从未有用户获得过高级工作台。
- 需要持续、深度分析的用户继续使用飞书私聊入口，数据范围不变（高级工作台按原设计也不增加数据权限）。
- 安全边界：用户间操作系统级隔离缺口不再被任何已排定入口暴露，但缺口本身仍存在（用户环境目录同属主），相关约束以 [2026-08-19 决策记录](2026-08-19-用户间操作系统级隔离本轮不做.md)为准。
- 技术设计文档（[架构设计](../技术设计/架构设计.md)的高级工作台与用户隔离相关小节、[验证与门禁](../技术设计/验证与门禁.md)风险表中的 JumpServer 提法）中的对应内容按「以产品合同为准」原则理解，其正文清理登记在 [Issue #371](https://github.com/Moshuiwang/lingxi/issues/371)，随后续维护批处理。

## 不采用的选择及原因

- **保留为「首期后」承诺**：无真实需求证据支撑一个长期挂账的承诺（是否曾有用户按既定方式申请过高级工作台：未知，无登记渠道记录）；需要时按复审条件重新立项，成本更低、口径更诚实。
- **改用其他形态提供高级工作台**：当前没有这方面的输入，不预设方案。

## 复审或替代条件

- 出现真实用户提出持续、深度分析且飞书私聊入口无法满足的需求；
- 届时须先重新评估操作系统级用户隔离前置（2026-08-19 决策）再立项，不得在隔离未落地时提供任何让用户取得 shell 的入口。
