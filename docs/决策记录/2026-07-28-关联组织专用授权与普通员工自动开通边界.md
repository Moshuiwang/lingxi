# 决策：关联组织专用授权与普通员工自动开通边界

> 状态：现行
> 决定日期：2026-07-28
> 来源：[GitHub Issue #19](https://github.com/Moshuiwang/lingxi/issues/19)；[关联组织用户身份受控验证](../参考证据/飞书关联组织用户身份受控验证.md)
>
> 规则正文见[产品合同与外部边界](../产品合同与外部边界.md)的「首次对话与自动准入」「开通流程」。本文只说明为什么这样定。

## 要解决的长期问题

Lingxi 需要读取关联企业的企业、部门和员工资料，以匹配银河当前有效权限记录并自动为员工开通 MCP 权限；这一资料读取不应把浏览器授权成本转嫁给每一位普通员工。

## 决定要点

- 只有“四达文档会议助手”执行一次专用组织资料授权；其可轮换用户 token 用于读取关联组织资料。
- 普通员工首次使用 Lingxi 时不经过授权卡片或浏览器 OAuth；系统基于已同步的员工资料自动匹配银河权限。
- 匹配使用姓名与银河当前有效权限记录；关联组织资料中的 `open_id`、`user_id`、`union_id`、部门和租户用于身份关联、投递和核对，不以手机号、邮箱、职务、职级或工号为前提。
- 专用授权与员工权限是两条边界：专用用户不能代表员工获得数据权限，银河数据库仍是权限权威。

## 为什么这样定

受控验证已经证明专用用户身份可以读取“四达集团”的可见部门和成员详情，并取得成员三类身份标识；这足以为正式编码提供资料来源。更关键的是，已实测机器人私聊入口的应用侧 `open_id` 与浏览器 OAuth 所得 `open_id` 不是同一标识，飞书公开规则也没有提供跨该边界的自动桥接接口。因此每位员工重复授权既不能可靠完成私聊身份绑定，也不会改善银河权限记录的权威性；专用资料同步是当前唯一已验证可行的方向。

## 对用户和边界的影响

员工只会看到自动开通的进度、成功、无权限或人工核对结果，不需要理解专用授权、关联组织或 token。专用授权仅由指定用户完成，正式实现负责其加密保存、轮换、撤销和故障处理。

管理员本人确认高风险动作的飞书卡片仍按既有决策保留；它与本决策中的组织资料授权不是同一类卡片。

## 不采用的选择及原因

- **每位员工在首次使用时授权**：不增加银河权限判断的可靠性，却增加普通用户的操作成本。
- **用手机号、邮箱等私密资料匹配**：不是必要前提，也会扩大资料处理范围。
- **用专用授权用户直接代表员工问数**：会混淆资料读取与员工数据权限，不能接受。

## 复审或替代条件

当关联组织可见范围、专用授权用户、飞书 OAuth 规范，或银河权限记录的匹配规则发生变化时，重新评估本决策。
