# 决策：飞书组织快照与多维表格使用人员 ID 关联

> 状态：现行
> 决定日期：2026-08-05
> 来源：2026-08-05 `biai-stage` 真实 User OAuth、多维表格回读、测试库快照回读；详细实现见[飞书组织快照与多维表格关联](../技术设计/飞书组织快照与多维表格关联.md)。
>
> 本文只说明关联键为什么这样选。权限权威、用户准入和多维表格的下游边界以[产品合同与外部边界](../产品合同与外部边界.md)为准。

## 要解决的长期问题

组织快照和飞书多维表格分别保存了成员身份资料与业务人员资料。若没有稳定关联键，后续只能按姓名猜测，无法可靠核对人员、部门、状态和业务字段。

## 决定要点

- 当前测试架构使用 `多维表格.人员ID = feishu_org_member_snapshot.user_id` 作为主关联键。
- `open_id`、姓名和工号不作为当前主关联键；姓名只能辅助核对。
- 关联是读取时的受控分析，不把多维表格反向变成权限权威，也暂不新增正式关系表。
- 若未来需要持久化关系，必须先确认多维表格「租户」与组织快照 `tenant_key` 的语义，并优先评估 `(tenant_key, user_id)` 复合键。

## 为什么这样定

真实回读得到：组织快照有 712 条成员行、710 个不同 `user_id`；多维表格有 1206 条记录、1177 个不同「人员ID」。逐行比较后，710 个不同组织快照 `user_id` 全部命中多维表格，命中 718 行，说明存在重复业务记录但身份值可以精确对齐。

相同回读中，多维表格 `open_id` 与组织快照 `open_id` 没有精确交集；当前证据不能判断这是不同应用命名空间、历史同步还是字段口径差异，因此不应为了“看起来像 ID”而强行拼接。工号在多维表格存在，但关联组织成员详情接口不返回工号；姓名有 29 行存在多候选，均不满足主键要求。

## 对用户和边界的影响

这项选择只影响内部资料核对和后续实现的连接方式，不改变用户可见权限、不扩大任何数据范围、不改变数据库作为权限权威的规则。测试脚本只输出统计和字段名，不交付员工原始资料。

## 不采用的选择及原因

- **按姓名连接**：重名、改名和中英文姓名都会造成误连或漏连。
- **按工号连接**：另一条组织接口没有工号，无法形成双源证据。
- **按 `open_id` 连接**：本次两张表没有精确交集，且不同应用/租户命名空间的语义尚未证明。
- **把多维表格原始记录复制进快照库**：会扩大敏感资料复制面，也会把下游发布通道误当成组织资料权威。

## 复审或替代条件

- 多维表格字段含义或数据生产链路发生变化；
- 组织快照出现同一 `(tenant_key, user_id)` 对应多个有效成员，或多维表格「人员ID」不再唯一可复现；
- 多维表格 `open_id` 经源头确认与组织快照 `open_id` 属于同一应用身份命名空间；
- 正式用户开通、权限发布或生产数据库需要消费这条关系；届时必须补齐持久化结构、权限隔离、增量同步、重复记录处理和真实入口验收。
