# 决策：电子表格纳入随对话交付同构路由

> 状态：现行（[2026-08-23 正式产物路由决策](2026-08-23-正式产物路由为随对话文档与文档级可管理授权.md)的延伸，不改变其任何要点）
> 决定日期：2026-08-28
> 来源：产品负责人 2026-08-28 确认窗口批准 [Trace #373 开工合同](https://github.com/Moshuiwang/lingxi/issues/373)先行裁定 D2；真实 API 形状探针见 [#354 W0 评论](https://github.com/Moshuiwang/lingxi/issues/354)，实现与受控验收见 Issue #354（PR #399 等，L4a 证据在 #373 S-H3-4 与 H4 冒烟评论）。

## 要解决的长期问题

用户要求以电子表格（而非在线文档）形态交付结果时，走什么路由、权限归属如何定——是复用 08-23 已裁定的文档路由，还是为表格另设一条。

## 决定要点

- 电子表格**复用 #341 文档交付的同构路由**：随对话交付、接收人获文档级「可管理」授权、所有权留机器人、失败关闭；
- 复用同一套检查点架构（请求落库、状态机、恢复路径与文档交付同型）；
- 单元格内容按**文本原样存储**：`=`、`+` 等公式前缀字符不被解释执行（2026-08-28 H4 冒烟以 `=SUM(1,2)` 探针实证：ToString 与 Formula 两种渲染视图均返回原文本）。

## 为什么这样定

- 08-23 决策的全部理由（授权面最小、交付后控制权归用户、所有权与离职交接语义）对表格同样成立，同构复用避免出现第二套需要单独审计的交付语义；
- 检查点架构复用使表格交付直接继承文档交付已验证的失败关闭与恢复行为，不新增恢复路径。

## 放弃了什么

- 表格专用交付通道或独立权限模型（无新增收益，徒增第二套语义）；
- 公式能力（表格作为数据交付载体，单元格一律文本——避免用户内容被当公式执行的注入面）。

## 重新评估条件

- 用户真实需要「带公式的表格」时，公式白名单与注入面控制作为独立 Story 评估；
- 表格体量/结构超出检查点架构承载（如多 sheet、超大行数分页写入）时重估路由。
