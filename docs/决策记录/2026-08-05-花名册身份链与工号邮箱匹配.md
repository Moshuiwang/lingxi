# 决策：花名册身份链与工号邮箱匹配

> 状态：现行
> 决定日期：2026-08-05；2026-08-08 补充确认所有非唯一成功结果统一按无可用权限结束
> 来源：产品负责人在 [Issue #34](https://github.com/Moshuiwang/lingxi/issues/34)、[Issue #17](https://github.com/Moshuiwang/lingxi/issues/17)、[Issue #65](https://github.com/Moshuiwang/lingxi/issues/65) 与 [Issue #89](https://github.com/Moshuiwang/lingxi/issues/89) 的回复及对话确认；受控验证证据见[飞书组织快照与多维表格关联](../技术设计/飞书组织快照与多维表格关联.md)
>
> 规则正文见[产品合同与外部边界](../产品合同与外部边界.md)的「首次对话与自动准入」「匹配结果与异常处理」。本文只说明为什么这样定。

## 要解决的长期问题

自动开通需要把飞书私聊里的员工可靠对应到银河权限记录。原方案按姓名匹配，而全量核对证明姓名既不是唯一键（存在重名）也不稳定（11/710 纯拉丁、9 中拉混合）；同时公司花名册多维表格实际到手，提供了以 `user_id` 精确关联、且含工号与邮箱的第二个数据面。

## 决定要点

- 身份链固定为：私聊事件应用侧 `open_id` → 关联组织快照定位成员取得 `user_id` → 以「人员ID = `user_id`」关联公司花名册多维表格 → 取得工号、邮箱与人员资料 → 以工号/邮箱匹配银河当前有效权限记录。
- 产品负责人于 2026-08-07 确认：花名册的工号和邮箱来自公司内部人力资源系统（PS），工号与邮箱当前及历史唯一，离职等人员状态变更可靠，并可与银河稳定对应。该确认作为身份链的产品事实；实际同步链路的新鲜度、断更发现和故障告警仍按受控验收确认。
- **姓名不再是匹配键**，只作辅助核对与展示。
- 匹配键以**工号为主、邮箱为辅**：工号唯一命中即采用；工号缺失或未命中时以邮箱匹配。只有身份、花名册原始记录与银河结果唯一、完整、一致且权限有效才成功；零条、多条（包括字段相同的重复原始行）、两键冲突、必要资料缺失或其他无法唯一确认的结果，全部得到同一无可用银河权限终态，不创建人工核对状态或待办。内部仍保留具体失败原因。（产品负责人给出「缺邮箱按工号」与「全部按工号」两种口径并授权选择；取工号为主是因为两侧覆盖率更高——花名册工号约 99%，银河 `user_name` 实测即纯数字工号——且邮箱在银河侧少量缺失并混有公共邮箱与海外域。）
- 「四达文档会议助手」的专用授权**保留**，并在原组织资料同步之外新增花名册多维表格的只读读取职责；普通员工仍不经过任何授权卡片。
- 飞书账号复用换人（冻结后改名转交）**不做自动拦截**（[#34](https://github.com/Moshuiwang/lingxi/issues/34) 方案 C）：由每日定期比对已开通用户的花名册资料变化，经受控管理群的**审计日报**通知管理员人工处理。
- 花名册成为开通链路的必经数据面；其工号和邮箱的来源、唯一性、离职状态可靠性及与银河的稳定对应关系已由产品负责人确认。实际同步机制、新鲜度、断更发现和故障告警仍需在身份切片验收中确认。

## 为什么这样定

- 姓名匹配的两个缺陷（重名、非中文姓名）都已被 710 人全量核对证实，而工号/邮箱是银河与花名册两侧天然共有的账号级标识。
- 工号与邮箱来自公司内部人力资源系统（PS），当前及历史唯一，离职等状态变更可靠，并可与银河稳定对应；因此身份匹配不再依赖姓名，也不需要另开“邮箱是否替代姓名”的产品决策。
- `人员ID = user_id` 的关联已在 2026-08-05 受控验证：710 个快照 `user_id` 全部命中花名册，重复行可识别（718 行对 710 值）；花名册 `open_id` 与快照 `open_id` 零交集，证明不能拿事件 `open_id` 直接查花名册，必须经组织快照取 `user_id`。
- 自动拦截账号复用需要不存在的强信号（职级、工号在组织接口从不返回），误伤正常改名的代价高；日报比对把该风险交给已有的管理员通知通道，实现成本与风险相称。

## 对用户和边界的影响

- 员工仍是发消息即自动核对，无授权卡片；只有唯一成功才继续开通，其他确定性匹配失败统一收到无可用银河权限提示，不等待管理员选择候选。
- 花名册只提供身份资料，不是权限权威；不得通过花名册反向创建或扩大 Lingxi 权限，银河数据仍是唯一权限来源。
- 邮箱、工号进入统一用户记录的保存范围（原「不以工号邮箱为前提」的边界随之替代）；仍只保存完成身份关联、权限判断与审计所必需的信息。

## 不采用的选择及原因

- **继续按姓名匹配**：重名与非中文姓名两个缺陷已被全量数据证实。
- **事件 `open_id` 直接查花名册**：受控验证证明两个 `open_id` 字段零交集，不成立。
- **自动拦截账号复用换人**（#34 方案 A/B）：缺乏强信号、误伤正常改名，由审计日报承接。
- **假定私聊事件直接携带 `user_id`**：对关联组织员工未经验证，且组织快照链路已验证可用，不引入未验证假设。

## 复审或替代条件

- 花名册的实际同步机制、新鲜度、断更发现或故障告警经受控验收后与本决策假设不符；
- 银河数据源从 excel 导出改为直连接口，或其账号字段语义变化；
- 关联组织可见范围配置、专用授权用户或飞书接口行为变化，导致组织快照链路失效；
- 审计日报运行后发现账号复用换人的实际频率或风险超出人工处理能力。
