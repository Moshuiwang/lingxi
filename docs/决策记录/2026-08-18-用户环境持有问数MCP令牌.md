# 决策：问数 MCP 的逐用户令牌放进用户环境

> 状态：现行（**取代**此前「用户环境里不放任何凭据」的架构承诺与「本机 MCP 代理」方案）
> 决定日期：2026-08-17（裁定）／2026-08-18（存量令牌处置补充）
> 来源：产品负责人在 [Issue #203](https://github.com/Moshuiwang/lingxi/issues/203) 的裁定评论第 3 条与 2026-08-18 裁定第 6 条
>
> 落地正文见[架构设计 6.9](../技术设计/架构设计.md)与[接口设计 7.2](../技术设计/接口设计.md)。本文只说明为什么这样定、放弃了什么、什么条件下要重新评估。

## 要解决的长期问题

worker 代表某个用户调用问数 MCP 时，必须带上**那个用户自己的**凭据——问数 MCP 逐行解密权限发布表的 `token_cipher`，与请求 `Authorization: Bearer` 的明文**等值匹配**，解密失败即不放行。这是现行外部系统的既有事实，不是我们可以选择的接口。

架构设计原先的落法是「本机 MCP 代理」：用户环境经 Unix domain socket 调用一个持有全部凭据的本机服务，服务端用 `SO_PEERCRED` 取得真实 uid、映射到用户与权限版本后代为发起调用。那条路的好处是用户环境里一个凭据都没有；代价是要新建并长期维护一个常驻代理服务、一套 socket 权限模型和一份 uid→用户映射，而它保护的对象是**用户自己的**权限凭据。

## 决定要点

- worker → 问数 MCP 的逐用户令牌**沿用旧系统 biai-agent 的做法**：把明文 Bearer 写进该用户环境的 `.mcp.json` header。
- 本机 MCP 代理方案**不实现**，架构设计与接口设计中断言「用户环境不放任何凭据」的正文一并改写。
- 落盘凭据参照 biai-agent 先例做权限纪律：**文件 `440`、目录 `700`、日志与异常一律脱敏**。
- 范围**只有这一个令牌**：飞书机器人凭据、专用授权凭据（`refresh_token`）、MCP 加密主密钥一个都不进用户环境；[交付接口](../技术设计/接口设计.md)（飞书凭据）的「凭据不进用户环境」语义完全不变。
- 存量 26 行（旧系统签发、Lingxi 不知其明文）的处置：**硬切窗口由 Lingxi 统一重签、覆写发布行密文，并经用户环境链重投 `.mcp.json`**；不做「对存量行豁免探针门」的双轨。

## 为什么这样定

- **保护对象与泄露面等价。** 用户在自己的环境里有 shell，因此放进去的东西等于交给他。但这个令牌的能力**恰好等于他本人已经拥有的数据范围**——他读到它，一个字节的额外可见面都没有增加。这与飞书机器人凭据完全不同：那一份代表整个租户的能力，交给任何一个用户都等于把全体用户的数据面交出去，因此那条边界不动。
- **代理服务保护不了它真正该保护的东西。** 代理的价值在于「用户拿不到凭据」，而这里的凭据本来就是他自己的；用它换来的是一个新的常驻进程、一套 socket 权限模型和一份必须与账号体系同步的 uid 映射——每一样都是新的故障面和新的运维负担。
- **互操作方向已经被外部系统决定。** MCP 侧按 Bearer 等值匹配，我们没有第二种把「这次调用是谁」告诉它的办法；代理方案最终也要在服务端持有同一批明文。差别只是明文放在哪里，不是有没有明文。
- **旧系统已经在跑同一条路。** 现行权限发布表的 26 行正是 biai-agent 按这个模型写入并消费的。选一条与现行生产一致的路，硬切时才有可比对的行为基线。

## 对用户和边界的影响

- **对用户没有可见变化**：他仍然只在飞书里问数，也不需要知道这个文件存在。
- **安全边界的实际变化**：用户环境从「零凭据」变成「持有他本人的问数 MCP 令牌」。补偿是三条可验证的纪律（`440` / `700` / 日志脱敏），由 `tests/test_user_environment.py` 钉住，不是注释里的承诺。
- **运维**：令牌以明文落盘，因此**用户家目录的备份与快照现在含凭据**——备份介质的访问控制要按凭据级别对待。这条是本决策引入的新要求。
- **一旦发出去就换不掉**：发布语义上「更新既有行不覆盖 `token_cipher`」（`V-权限-11`），所以不存在「库里换了、外部表没换」的静默失效；真要换，只能走硬切窗口那条重签 + 重投的编排。

## 不采用的选择及原因

- **本机 MCP 代理（原方案）**：见上。保护的是用户自己的凭据，代价是一个新的常驻服务与两套权限模型。
- **令牌只放进 worker 进程内存、由 worker 代填 header**：Agent 子进程以目标用户身份运行、加载的是用户环境里的 MCP 配置，worker 无法在不改 SDK 行为的前提下逐调用注入 header；绕过它就等于自建代理，回到上一条。
- **对存量 26 行豁免就绪探针门**：那要修改「就绪只以探针成功为准」的合同，制造两套就绪语义——一批用户的开通成功从此没有真实证据支撑。
- **给用户环境的令牌加短有效期并频繁轮换**：发布路径不覆盖既有行的 `token_cipher`，轮换只会让库与外部表不一致、用户静默失去问数能力。

## 复审或替代条件

出现下列任一情况时重新评估本决策：

1. 问数 MCP 改变认证模型（例如支持按调用方身份的服务端鉴权、或支持短期令牌换取），使「明文常驻用户环境」不再是唯一可行路径；
2. 用户环境的隔离前提变化——例如出现同一家目录被多人共享、或备份介质的访问控制无法按凭据级别管理；
3. 令牌的能力范围超出「这个用户本人已有的数据范围」（例如同一份令牌被用于管理面或跨用户查询）；
4. 硬切窗口的重签编排实施时发现「覆写既有行的 `token_cipher`」在产品上不可接受，需要另一种令牌承载方式。
