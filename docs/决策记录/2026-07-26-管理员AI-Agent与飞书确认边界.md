## 要解决的长期问题

环境创建、权限发布、MCP 同步和账号管理等运行异常需要管理员查询事实并作出处理。身份或权限匹配的零条、多条、冲突、重复和资料不完整不再交给管理员选择，而是统一失败关闭。Lingxi 必须为真正的运行异常与管理动作提供一个可以持续扩展、能够明确归到具体管理员、又不会把自动开通重新变成人工审批的管理入口。

旧 BI AI Agent 已经实现用户查询、权限收回、账号停用与恢复、用户删除、关闭待处理和权限发布重试，但这些能力主要通过审批群卡片和文字命令触发。随着管理能力增加，搜索、比较、解释、确认和历史状态全部挤在聊天中，会让入口与业务规则耦合，也更难保持一致。

## 决定要点

- **管理能力独立于具体入口**，AI Agent、管理 MCP 和飞书卡片只分别承担理解、受控调用和最终确认。
- **管理员通过经批准的 AI Agent 使用管理 MCP**，以个人身份查询事实、比较异常和准备操作。
- **管理员身份和角色以管理 MCP 的认证为准**，Lingxi 不重复维护另一份管理员名单；管理 MCP 身份必须绑定唯一的本人飞书身份。
- **管理 MCP 提供权限管理员、运维管理员和超级管理员三类角色**：权限管理员管理普通用户准入与问数权限，运维管理员处理环境与同步异常，超级管理员可以新增或移除三类管理员。
- **超级管理员角色允许正常新增和移除**；若系统中已无超级管理员，由持有服务器 Root 权限的 Ops 运维工程师通过受控流程恢复一个身份已经核实并绑定飞书的现有用户并留下审计证据。管理员角色被收回后，其尚未确认的旧卡片立即失效。
- **所有改变用户、权限或管理员角色的动作都由发起管理员本人在飞书私聊卡片最终确认**，AI Agent 和管理 MCP 不能直接执行。
- **受控管理群只发送通知**，不提供审批流、管理命令或群内执行入口。
- **真正的运行异常由管理员守护**，系统按对应错误提示通知用户并把需要处理的技术异常通知管理群，不为身份匹配建立任务认领、倒计时提醒、逾期升级或自动进展通知。
- **正常用户继续自动开通**，管理入口只处理运行异常和明确的管理动作；不提供身份候选比较、选择记录并继续开通的能力。
- **目标员工所有非唯一成功结果都由银河入口承接**：Lingxi 只向员工说明先去银河申请或补充权限，不能代申请、扩权、修改银河权限，也不把零条、多条、冲突、重复或资料不完整变成 Lingxi 权限人工待办；银河已有权限但 Lingxi 仍异常时，引导联系银河管理员。
- **当前管理员自身的身份或管理链路异常由 Ops 处理**：停止当前操作，不允许管理员自修、绕过确认或继续使用旧待确认动作；系统给出异常编号并通知受控管理群，Ops 修复权威来源后，管理员重新授权并重新发起操作。
- **管理查询、确认、执行与拒绝都必须可审计**，写操作在身份、目标状态、确认或审计不明确时默认不执行。

## 为什么这样定

**把核心管理能力与入口分开，才是真正的解耦。** 如果用户管理规则写在飞书卡片回调、群命令或某个 Agent 的提示词中，未来更换入口就要重写规则。把查询、权限判断、待确认动作、执行和审计作为 Lingxi 自己的管理能力后，AI Agent 与飞书都只是可替换的入口。

**AI Agent 适合帮助管理员理解，不适合成为最终授权人。** 管理员经常需要从自然语言问题开始，查用户、理解运行失败状态和评估管理动作影响，AI Agent 比固定网页表单更灵活。但模型可能误解目标或遗漏影响，因此它只能准备动作，不能比较并选择身份候选，也不能凭自己的判断改变身份、权限或账号状态。

**飞书私聊卡片比完整管理网页更适合首期最终确认。** 卡片只展示一个已经准备好的动作和确定影响，交互只有确认或取消；不需要建设搜索、列表、筛选和复杂页面。它同时不依赖不同 AI Agent 客户端是否提供一致的工具确认界面，管理员在桌面端和移动端都能看到同一结果。

**确认卡发给发起管理员本人，而不是管理群。** 一项管理动作由谁发起、谁看过影响、谁最终确认应当保持一致。群内任何管理员都能点击会增加责任不清、并发处理和误确认风险；管理群更适合提醒“有待办”，不适合承载具体用户的最终操作。

**管理 MCP 认证与飞书身份各自解决不同问题。** 管理 MCP 决定当前管理员是谁、拥有什么角色；与其一一绑定的飞书身份保证确认卡只到达发起者本人。卡片发送成功不代表角色有效，发送失败也不用于推断人员状态；发送失败时本次操作不执行，确认时仍由管理 MCP 按当前角色授权。

**超级管理员让管理员体系可以自我维护，Root 恢复只处理管理入口完全失效的极端情况。** 超级管理员可以新增和移除权限管理员、运维管理员及其他超级管理员，所有正常变化仍需本人卡片确认。若误操作或并发变化导致系统中没有超级管理员，普通管理入口不能自行提权；由服务器 Root 权限下的 Ops 受控恢复一个身份已经核实并绑定飞书的现有用户。这样不为极低频故障增加复杂的产品代码，同时不把数据库或系统权限暴露给管理 MCP。

**技术异常处理不等于建设一套身份核对任务系统。** 身份或权限只要不能唯一、完整、一致地确认，就立即给出无可用权限终态，不等待管理员选择。环境、发布或同步等真正的运行异常仍由管理员按固定错误码和状态处理，但首期不为此增加复杂的认领、计时、催办或升级机制。

**把银河异常和管理员自身异常分开，才能把处理责任交给正确的人。** 银河是普通员工权限的上游来源，Lingxi 没有权限替员工申请或扩大银河权限；管理员自己的身份、角色、绑定和确认链路则属于 Lingxi 管理入口的可信边界，必须由独立的 Ops 运维处理。异常编号、旧动作失效和重新授权提供足够的追踪与恢复路径，不额外建设一套复杂的工单系统。

**现有 BI AI Agent 只作为能力和风险参考。** 已实现的用户管理与防重复处理证明这些动作可以被稳定封装；旧申请审批流程、群命令和卡片路由不代表 Lingxi 必须继承同样入口。Lingxi 只复用被产品合同确认的业务能力，不复用旧产品的交互包袱。

## 对用户和边界的影响

- 正常用户仍然无需等待管理员审批；确定性的身份与权限匹配失败也不会进入人工选择流程。
- 运行异常不会因为 AI Agent 已经提出建议就被误报成功；需要改变状态的管理动作只有管理员完成个人确认后才执行。
- 管理员可以用自然语言完成复杂查询和比较，但每个实际变化都有清楚、统一的最终确认。
- 超级管理员可以在同一受控入口维护三类管理员；角色收回后旧卡片不能继续生效。管理入口完全失去超级管理员时，用户服务不自动扩权，由 Ops 通过 Root 受控恢复。
- 管理群不再充斥命令、身份候选、审批表单和可重复点击的操作卡，只保留需要关注的运行异常与结果。
- 问数 MCP 与管理 MCP 分离；业务用户的数据查询凭据不能调用管理能力，管理员身份也不能绕过 Lingxi 的准入、管理和发布边界。
- 员工遇到银河权限异常时会得到可执行的下一步，而不是停留在含糊的“联系管理员”；管理员自身的异常会被明确转给 Ops，并在修复后重新授权，旧操作不会悄悄恢复。

## 不采用的选择及原因

- **完整飞书网页管理后台**：可以提供稳定的列表和表单，但首期需要额外建设整套页面；当前管理动作更适合由 AI Agent 查询并由单一确认卡收口。
- **继续扩展审批群卡片和文字命令**：功能增加后，搜索、比较、状态和操作会散落在消息中，并把管理规则绑定到飞书群聊。
- **纯 MCP 直接执行写操作，或把最终确认收回 MCP 内部**：不同 AI Agent 客户端的确认体验并不一致，不能把最终授权完全委托给客户端或模型。2026-07-29 按 MCP `2026-07-28` 规范复核后，这条理由补充为：协议不提供任何可供服务端核验的「本人已到场批准」证据，详见下文复审一节。
- **把确认卡发到管理群**：无法保证发起人和确认人一致，也增加多个管理员同时处理同一动作的风险。
- **以管理群成员或卡片是否发送成功判断管理员角色**：群成员和飞书送达只说明入口状态，不能替代管理 MCP 的当前角色授权。
- **为“最后一名超级管理员”增加复杂的数据库并发与删除保护**：Root 运维可以通过受控流程恢复已核实身份，极低频风险不值得增加多路径一致性和数据库锁设计。
- **把 Root 恢复做成管理 MCP 工具**：会把服务器与数据库权限暴露到日常管理入口，扩大攻击面。
- **为运行异常建设复杂的自动催办和升级机制**：首期异常量不值得引入额外任务状态和通知规则，由管理员按固定状态和错误码处理即可；身份匹配失败根本不进入该流程。
- **让 Lingxi 代员工申请或扩大银河权限**：银河是权限来源，Lingxi 不越过上游系统替员工改变授权；这类异常只给出申请或联系银河管理员的提示。
- **允许管理员自行修复自己的身份、角色或确认链路异常**：会让故障处理与授权判断形成自我证明，且可能让旧待确认动作继续生效；统一交给 Ops 修复，修复后重新授权并重新发起。
- **把 Lingxi 自身管理链路故障也提示员工去银河申请**：会误导用户，只有银河来源的权限异常才走银河申请路径。
- **允许任意数据库查询或通用修改工具**：会扩大敏感数据暴露面，并让 Agent 绕过产品规则直接改变权威数据。
- **让所有用户重新走管理员审批**：与唯一有效匹配自动开通的既定体验冲突，也会用正常用户淹没异常处理资源。

## 2026-07-29 复审：MCP `2026-07-28` 是否满足「确认通道」的替代条件

MCP 于 2026-07-28 发布修订 `2026-07-28`，把服务端向用户征询输入的方式统一改为 Multi Round-Trip Requests（MRTR）。`elicitation` 本身在更早的修订中就已存在，本版新增的是传递方式；但这是本项目**第一次**对替代条件之二做定向复核。规范事实、引用出处与其中的歧义见[MCP 规范 `2026-07-28` 与管理入口](../参考证据/MCP规范2026-07-28与管理入口.md)。

**复核结论：替代条件不成立，维持「管理 MCP 只做查询与准备、飞书私聊卡片做最终确认」。** 理由分三层：

**一、`form` 模式提供不了本决策需要的证据强度。** 本决策的核心安全属性是「高风险动作由发起管理员**本人**最终确认」，它要求一份可供 Lingxi 自己核验的到场批准证据。`form` 模式返回的 `action: "accept"` 完全由客户端自报：规范对客户端有 MUST 级的展示与拒绝义务，但**服务端无法验证这些义务是否被履行**，协议也不提供任何机制证明有特定自然人看见并批准过。规范并没有禁止用 `form` 模式做操作确认——它禁止的是把客户端自报的**用户标识**当权威，而我们的调用方身份本来就来自服务端验证的个人凭据。因此这一条不是「违规」，而是「证据不够」：把它当作本人确认，等于把合同里最强的一条安全属性降级为一句客户端的声明。

**二、`url` 模式能提供足够强度，但它不是「仅使用 MCP」。** 规范强制服务端在接受信息前验证打开该 URL 的人的身份，并确保发起者与完成者是同一人。规范本身没有规定该 URL 必须指向服务端自建页面（自建 connect 页只是它给的非规范性示例），但在 Lingxi 的部署条件下，能满足这条强制要求的现实做法只有自建一个具备独立会话身份的确认端点——也就是以一个内网网页取代飞书卡片。它不比现状简单，要新增一个对外面，并且部分推翻「不建设网页管理后台」这一既定选择。规范另有一条「服务端 MUST NOT 依赖 `url` 模式 elicitation 为自身授权用户」，其是否覆盖「确认单次高风险动作」规范没有说清；这一歧义本身也是不宜把安全属性押在该路径上的理由。

**三、即使技术可行，仍有两项净损失，属于产品取舍而非实现细节。** 其一，确认的独立性下降：现在「谁确认的」来自飞书验签过的卡片回调操作者身份，与管理 MCP 的个人凭据是**两条独立通道**；把确认收回 MCP 内部后，发起与确认合用同一条凭据、同一个 Agent 会话，产品合同中「AI Agent 会话本身不能代替个人授权」这条会被架空。其二，移动端覆盖丢失：飞书在手机端可确认，管理 Agent 客户端在手机端基本不可用，而本决策当初正是把「桌面端和移动端看到同一结果」作为选择卡片的理由之一。

**还有一项新的失败模式。** 规范规定服务端 **MUST NOT** 下发客户端未声明支持的 `inputRequests`，且客户端可以只声明 `form` 而不支持 `url`。因此在「仅使用 MCP」的前提下，管理员更换客户端时结果不是体验降级而是**高风险管理动作彻底不可用**；现行飞书路径在送达失败时至少有「本次操作不执行」这一明确终态。

### 一并评估过的两种中间形态

产品负责人问的是「仅使用 MCP 会带来哪些变动」，因此除两个极端外，另评估了两种保留飞书确认的混合形态。两者都**不采用**，但理由不同，将来条件变化时可以单独重估：

- **只带 `requestState`、不带 `inputRequests` 的 MRTR 等待态。** `prepare_*` 返回 `input_required` 而不含任何 elicitation，管理员的 Agent 可立即重发直到飞书卡片被确认。它不引入 elicitation、不改变授权模型、不新增对外面，飞书仍是独立确认通道。不采用的原因是它只把「去飞书点一下」包装成协议原生的等待态，而 `get_pending_action` 已经能如实回答同一个问题；换来的是 Agent 侧的重复轮询成本和一条多余的状态路径。
- **`url` 模式指向一个只做转发的薄端点**（校验会话身份后把管理员导向既有的飞书卡片）。它保留飞书卡片与移动端覆盖，成本远低于自建完整确认页。不采用的原因是它并不减少任何**已经发生**的成本：管理员本来就能在飞书收到卡片，多这一跳只是把入口从「飞书通知」换成「Agent 里点链接」，却要新增会话身份端点及其运维面。若将来管理员反馈「在 Agent 里看不到卡片状态」成为真实痛点，这一形态是首选的最小改动。

本次复核不改变确认通道。管理 MCP 服务端采用哪个协议版本是纯实现选择，规则正文不变，写在[接口设计](../技术设计/接口设计.md#六管理-mcp提供方)与[架构设计](../技术设计/架构设计.md)。

## 复审或替代条件

- 管理任务发展为大量批量处理、复杂筛选、跨对象比较或持续浏览历史，飞书确认卡已不能清楚展示影响；
- 经批准的 AI Agent 客户端形成一致、可验证且满足公司要求的个人确认能力。按 2026-07-29 的复核，这一条在下列**任一**情形下成立：
  - **协议或客户端提供服务端可核验的到场批准证据**（例如由客户端或其身份提供方签名、可由 Lingxi 独立验证的确认凭据），而不再是客户端自报的 `accept`。这是最干净的触发路径，一旦出现应直接重估本决策；
  - 客户端稳定声明并实现 `elicitation` 的 `url` 模式，且该路径覆盖管理员常用终端（含移动端）。此时确认者身份仍需 Lingxi 自建端点验证，因此复审必须**连同**「不建设网页管理后台」这一选择一起重估，不能只看本条成立就切换；
  - 仅支持 `form` 模式在任何情况下都不满足本条。
- 飞书私聊卡片无法稳定识别操作者、更新最终状态或覆盖管理员常用终端；
- 公司要求高风险动作由两人复核、由专门审批系统承载，或采用不同的管理员身份体系；
- 管理职责扩展到本决策未覆盖的生产发布、数据修复或其他高风险外部动作。
