# MCP 规范 `2026-07-28` 与管理入口

> 最后核对：2026-07-29，来源为 modelcontextprotocol.io 官方规范页面、官方博客发布公告与官方扩展支持矩阵的当日读取。
>
> 本文回答一个长期问题：**MCP 协议自身提供了什么，因而 Lingxi 的管理 MCP 可以依赖什么、不能依赖什么。**
> 适用范围：协议层事实与规范的规范性要求（MUST / MUST NOT / SHOULD），以及这些要求的直接协议后果。
> 不适用范围：本文不定义 Lingxi 的产品规则，也不重复[技术设计](../技术设计/README.md)中的实现义务；本文也不证明任何客户端的实际行为——客户端支持情况是快照，且**未经 Lingxi 实测**。管理入口的产品规则见[产品合同与外部边界](../产品合同与外部边界.md)的「管理员处理入口与安全确认」，为什么这样定见[管理员 AI Agent 与飞书确认边界决策](../决策记录/2026-07-26-管理员AI-Agent与飞书确认边界.md)。

## 版本事实

- `2026-07-28` 是**已正式发布的最新修订**：官方博客当日公告称「Today, we're officially pushing the release button on the next version of the MCP specification, `2026-07-28`」，其 changelog 以 `2025-11-25` 为上一版。
- **一处站点自身不一致，采用前需再确认**：`/specification/versioning` 页在 2026-07-29 读取时仍写着「The **current** protocol version is **2025-11-25**」，而 `/specification/2026-07-28` 首页没有任何 Draft / Current / Final 状态标注（该页的扩展段落还留着「negotiated during initialization」这类本版已不成立的旧文字）。因此「`2026-07-28` 已成为 current」在官方页面上得不到一致支持，只能确认它已发布。这不改变「新实现应按它编码」的判断，但会削弱「不采用即建成即过时」这一论据的强度。
- 版本号格式 `YYYY-MM-DD`，只在发生**向后不兼容**变化时递增。本版包含多项破坏性变化（见下表）。
- 本版引入**特性生命周期与弃用政策**：弃用特性至少保留十二个月（加速移除例外为九十天）才可被移除，并登记在弃用特性注册表中。这为「依赖某项特性」提供了此前没有的时间保证。

## 与管理 MCP 服务端形态相关的破坏性变化

下表右列只写**协议后果**；由此产生的 Lingxi 实现义务写在[接口设计](../技术设计/接口设计.md#六管理-mcp提供方)，不在本文重复。

| 变化 | 协议后果 |
|---|---|
| 移除 `initialize` / `notifications/initialized` 握手，协议变为无状态 | 每个请求在 `_meta` 自带 `io.modelcontextprotocol/protocolVersion` 与 `io.modelcontextprotocol/clientCapabilities`；服务端不能假设存在连接级初始化状态 |
| 移除协议级会话与 `Mcp-Session-Id` 头 | **协议层不再有会话标识**。需要跨调用状态的服务端只能改用服务端签发、作为普通工具参数传递的显式句柄 |
| `tools/list` / `resources/list` / `prompts/list` 不再随连接变化 | 按调用者不同返回不同列表，只能依据每次请求携带的认证信息决定，不能依据连接级状态 |
| 新增 `server/discover`，服务端 **MUST** 实现 | 服务端必须公布支持的协议版本、能力与身份 |
| 移除 SSE 续传与消息重投（`Last-Event-ID`、事件 ID） | 响应流断开即丢失在途请求，客户端 **MUST** 以**新的请求 ID** 重发原请求；协议不保证重发时的请求内容与首次一致 |
| `tools/list`、`prompts/list`、`resources/list`、`resources/read`、`resources/templates/list` 的结果新增必填 `ttlMs` 与 `cacheScope` | 结果可被客户端缓存；`ttlMs` 是给客户端的新鲜度提示，服务端无法强制客户端何时重取；`cacheScope` 为 `public` 时允许共享中间件缓存 |
| 新增标准请求头 `Mcp-Method`、`Mcp-Name` | Streamable HTTP POST 的固定要求 |
| 错误码分区：`-32020`～`-32099` 保留给规范，`-32000`～`-32019` 留给实现 | 约束的是 JSON-RPC 层的数字错误码，与各服务端自定义的业务错误信封无关 |
| `Roots`、`Sampling`、`Logging` 进入弃用窗口 | 新实现不应采用 |
| OAuth 动态客户端注册（RFC 7591）被弃用，倾向 Client ID Metadata Documents | 仍可用于与不支持 CIMD 的授权服务器向后兼容 |
| 授权硬化：授权服务器 **SHOULD** 返回 RFC 9207 的 `iss`；客户端对**存在的** `iss` **MUST** 校验；客户端凭据 **MUST** 按签发方绑定，不得跨授权服务器复用 | 影响管理员个人授权的注册与凭据保存方式 |

## 服务端向用户征询确认的机制及其规范限制

`elicitation` 本身不是本版新增：`form` 模式与 `url` 模式分别在更早的修订中引入（`url` 模式引入于 `2025-11-25`）。本版新增的是**传递方式**——**Multi Round-Trip Requests（MRTR）** 取代了服务端发起请求的旧模式（破坏性移除）。服务端在 `tools/call` 中途返回 `resultType: "input_required"`，携带 `inputRequests`（可为 `elicitation/create`、`sampling/createMessage`、`roots/list`）与不透明的 `requestState`，客户端补齐后**以新的请求 ID 重发原请求**并带上 `inputResponses`。仅 `prompts/get`、`resources/read`、`tools/call` 支持该返回。

评估「能否用它承担高风险动作的最终确认」时，以下规范条目是决定性的：

1. **服务端 MUST NOT 在未经自身验证的情况下依赖客户端提供的用户标识**，规范给出的理由是它可以被伪造；规范给的反例是把用户输入的「我是 joe@example.com」当权威，正例是依靠 MCP 授权识别用户。**注意这条针对的是「谁在调用」，不是「谁按下了确认」**——如果调用方身份来自服务端自己验证的凭据，这条并未被触发。
2. **`form` 模式 MUST NOT 用于敏感信息**（口令、API key、访问令牌、支付凭据）；此类交互 **MUST** 使用 `url` 模式。规范同时说明，姓名、邮箱、用户名这类一般资料不在禁止之列。
3. **协议不提供任何证明「有特定自然人看见并批准」的机制。** `form` 模式返回的 `action` 是客户端自报的三态之一（`accept` / `decline` / `cancel`）。规范对客户端有 MUST 级要求（标明是哪个服务端在请求、提供拒绝与取消、允许用户在发送前检查与修改）与 SHOULD 级的用户批准控制，但这些是**客户端实现义务，服务端无法验证其是否被履行**。规范自己在安全原则中也承认：MCP 无法在协议层强制用户同意与授权原则，只能要求实现者自建。
4. **`url` 模式的定位与强制要求**：交互在带外完成，数据（URL 本身除外）不经客户端与 LLM。规范强制两点：服务端 **MUST** 在接受信息前验证打开该 URL 的人的身份；服务端 **MUST** 确保「发起该 elicitation 的人」与「完成该流程的人」是同一人（规范为此专门描述了一类钓鱼攻击）。**规范并未规定该 URL 必须指向服务端自建页面**——用会话 cookie 校验的自建 connect 页是规范给出的**非规范性示例**（原文标注 “As a common, non-normative example”）。
5. **一条含义待定的限制**：规范写有「MCP 服务端 **MUST NOT** 依赖 `url` 模式 elicitation 来为自身授权用户」，其上下文是「授权 MCP 客户端访问 MCP 服务端」这件事应由 MCP 授权负责。**「确认某一次高风险动作」是否落入这条禁止，规范没有说清**；引用时应如实标注这一歧义，不应单方面解读。
6. **服务端 MUST NOT 下发客户端未在能力中声明支持的 `inputRequests`**。客户端可以只声明 `form` 而不支持 `url`；空的 `elicitation` 能力对象等价于只声明 `form`。
7. `requestState` **MUST** 被视为攻击者可控输入；若它影响授权、资源访问或业务逻辑，服务端 **MUST** 做完整性保护（HMAC 或 AEAD）并拒绝校验失败的状态；**SHOULD** 在其中绑定认证主体、短 TTL 与原请求摘要以限制重放。规范明确指出：这些措施**不保证单次使用**，需要 at-most-once 的服务端 **MUST** 自行在服务端强制该不变量。
8. MRTR 允许 `InputRequiredResult` **只带 `requestState` 而不带 `inputRequests`**（两者至少有其一）；此时客户端 **MAY** 立即重发原请求。这构成一种不涉及 elicitation 的「稍后再试」协议原生等待态。

**据此可以得出的结论**：`form` 模式的 `accept` 是一种**用户体验机制**——它能表达「客户端声称用户点了确认」，但协议不提供任何可供服务端核验的到场证据。它是否足以承担某项授权，取决于该产品要求的证据强度，规范本身并未禁止把它用于操作确认。`url` 模式能承担更强的确认，代价是服务端必须自行解决「打开 URL 的人是谁」这一强制要求。

## 扩展框架

`Tasks`（长任务）、`MCP Apps`（服务端渲染的交互式 UI，标识 `io.modelcontextprotocol/ui`）、`Skills over MCP`（工作组孵化中）、`Enterprise-Managed Authorization`（企业 IdP 集中授权）、`OAuth Client Credentials` 均为**可选扩展**，不属于核心协议。

- 扩展**默认关闭，必须由开发者显式启用**；双方在各自能力声明的 `extensions` 字段中协商。
- SDK 实现扩展**不是**协议一致性要求，SDK 维护者自行决定是否支持。
- 一方支持而另一方不支持时，支持方要么回退到核心协议行为，要么在扩展为强制时拒绝请求。

## 客户端支持快照（2026-07-29，官方矩阵，社区维护）

官方扩展支持矩阵**只有三列**：MCP Apps、OAuth Client Credentials、Enterprise-Managed Authorization。

- **MCP Apps**：Claude（web）、Claude Desktop、VS Code GitHub Copilot、Microsoft 365 Copilot、Goose、Postman、MCPJam、ChatGPT、Cursor、Archestra.AI、PostHog Code。**Claude Code 不在该矩阵中。**
- **Enterprise-Managed Authorization**：仅 Archestra.AI。
- **OAuth Client Credentials**：矩阵中无客户端。

**矩阵不覆盖 `Tasks` 与 `Skills over MCP` 两项扩展，也不覆盖 `elicitation`**——后者属于核心协议特性，官方没有统一的客户端支持表。因此「某个客户端是否声明 `elicitation` 能力、声明了 `form` 还是 `url`」**只能实测**，不能从官方文档推断。
