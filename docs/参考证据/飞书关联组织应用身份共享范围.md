# 飞书关联组织应用身份共享范围

> 状态：2026-07-28 完成共享范围受控复验，2026-07-29 完成私聊标识体系受控实验；仅限 `biai-stage` + `Bot-Test`，使用应用的 `tenant_access_token`。
> 来源：[GitHub Issue #16](https://github.com/Moshuiwang/lingxi/issues/16) 与 [Issue #11](https://github.com/Moshuiwang/lingxi/issues/11) 的依赖核对。
> 本文只记录**应用身份**能读到什么；**用户身份**（专用授权用户的浏览器 OAuth）的验证结论见[飞书关联组织用户身份受控验证](飞书关联组织用户身份受控验证.md)。两者是不同的身份路径，结论互补，不可互相替代。

## 为什么需要这一份

自动开通的第一步是：员工私聊机器人后，用**私聊事件里的发送者标识**找到该员工的已同步资料。私聊事件由**应用**收到，因此这一步能否成立，取决于应用身份自己能读到什么——而不是专用授权用户的 OAuth 能读到什么。

## 已确认：应用身份可以读到的共享资料

用应用的 `tenant_access_token` 调用关联组织双方共享范围接口，并从根部门递归读取：

| 信息 | 当次实测 | 用途 |
| --- | --- | --- |
| 关联租户目录 | `directory/v1/collaboration_tenants` 返回 `code=0`，8 个关联租户；记录含 `tenant_key`、`name`、`short_name`、`brand`、`avatar`、`connect_time`，目标租户在列表内 | 确定应查询的共享组织 |
| 共享范围入口 | `directory/v1/share_entities` 携带 `target_tenant_key` 调用 `code=0` | 进入递归读取 |
| 共享部门 | 24 个真实部门（`od-` 前缀）；接口另返回一条伪根记录 `open_department_id="0"`，计数时须排除 | 展示或匹配用户所在的已共享部门 |
| 共享成员归属 | 82 条记录，去重后 82 个唯一 `open_user_id`；26 次接口调用，0 次分页或权限错误 | 把私聊发送者匹配到共享成员 |

**字段范围就是全部天花板**：成员归属记录**只有** `open_user_id`、`name`、`avatar` 三个字段；部门记录**只有** `open_department_id`、`name` 两个字段。

24 和 82 是当次快照，不是稳定人数承诺；组织共享范围变化后必须重新读取。2026-07-28 的两次独立实测这两个数字一致。

## 不能取得的资料

共享范围接口**不返回** `user_id`、`union_id`、邮箱、手机号、职务、职级或在职状态。接缝虽已被证明成立（见下节），应用身份也只够做「私聊身份 → 已共享部门 + 姓名」的最小映射，**不足以补齐开通所需的完整员工身份**，更不能替代数据库的当前有效权限记录。`user_id` 与 `union_id` 只在**用户身份**路径的关联组织成员详情中返回。

以下关联组织接口在 Bot-Test 应用身份下对目标租户的当次结果：

| 接口能力 | 当次结果 |
| --- | --- |
| 获取可见关联组织列表 | `code=0 success`，但 `data` 只含 `has_more`，返回 **0 项**；**不是**权限错误 |
| 获取关联组织详情 | **`1971007 App not visible to target tenant.`** |
| 获取关联组织的部门和成员信息（`visible_organization`） | **`1971007 App not visible to target tenant.`** |

即：可用的只有双方共享范围这一条路径，`visible_organization` 系列不可用。

## 已验证：私聊标识与共享标识是同一体系

2026-07-29 完成一次性受控实验（[Issue #30](https://github.com/Moshuiwang/lingxi/issues/30)），结论**成立**：

> **同一应用**收到的 1:1 私聊事件的发送者 `open_id`，可以直接在**同一应用**共享范围接口返回的 `open_user_id` 集合中命中。

| 观察 | 结果 |
| --- | --- |
| 计入结论的私聊事件 | 2 条，来自 2 位不同发送者 |
| 命中 / 未命中 | **2 / 0** |
| 两位发送者是否事先确认在共享范围内 | 是。发消息前已按姓名在内存中核对过标识前缀，因此「未命中」若出现将是干净的否定结论 |
| 标识形态 | 均为 `ou_` 前缀、长度 35，与共享成员标识一致 |
| 同批被排除的事件 | 1 条群聊消息（`chat_type=group`），发送者不在目标租户共享范围内，按口径不计入 |

实验方法：探针**只收不回**——启动时读一次共享范围只保留 `open_user_id` 集合，订阅 `im.message.receive_v1`，事件到达时在内存中做一次相等比对，只记录命中与否、标识前缀和长度，比对后立即丢弃标识。全程不回复消息、不发卡片、不写数据库、不建用户、不发起开通。

### 结论边界

- **只统计 1:1 私聊**（`chat_type=p2p`）。群聊消息的发送者标识未纳入结论；第一轮曾误把群聊当私聊，已作废重跑。
- 2 条是排除单条巧合的最低样本量，不是大规模统计。
- 命中只证明**标识体系相同**，不证明任何一位员工必然在未来的共享范围内——共享范围会随组织配置变化，每次仍须重新读取。
- 这条结论**不推翻**[飞书关联组织用户身份受控验证](飞书关联组织用户身份受控验证.md)中「私聊事件的应用侧 `open_id` 不能与浏览器 OAuth 的 `open_id` 当作同一标识」的判定。两者说的是不同边界：那一条比的是**私聊标识与用户 OAuth 标识**，本条比的是**私聊标识与应用身份共享范围标识**。前者仍然不通，后者通。

## 已验证：共享范围内姓名默认值稳定为中文

同一次读取中对 82 个成员的 `name` 字段做了全量语言分布核对。该字段结构为 `{default_value, i18n_value}`，`default_value` 的分布：

| 类别 | 数量 |
| --- | ---: |
| 含汉字 | **82** |
| 纯拉丁字母 | 0 |
| 其他 | 0 |

即当次共享范围内**没有任何一个成员的默认姓名是非中文**。

**边界**：这是**应用身份共享范围**这条路径上 82 个成员的分布，不等于**用户身份**路径读取的 117 个成员（见[飞书关联组织用户身份受控验证](飞书关联组织用户身份受控验证.md)）的分布——两条路径的成员集合与接口都不同。若正式实现的资料同步走用户身份路径，需要在该路径上另做一次同样的核对。

## 复验方法

1. 用 Bot-Test 凭据换取 `tenant_access_token`；不打印令牌或凭据。
2. 读取关联租户目录，确认目标租户在列表内。
3. 调用双方共享范围接口，从根部门递归读取；排除伪根记录后统计唯一部门与成员归属。
4. 分别调用可见关联组织列表、关联组织详情与 `visible_organization`，如实记录返回码；不得把应用身份的 `1971007` 伪装成「用户没有权限」。
5. 只保留字段名、计数、错误码与标识前缀作为证据。

复验私聊标识体系时另加三条：

6. 探针**只收不回**，且必须在员工发消息**之前**启动——飞书长连接事件不重放，接收端未启动时发出的消息无法补捞。
7. 发消息前先按姓名确认发送者在当次共享范围内，否则「未命中」无法区分「标识体系不同」与「此人本就不在范围内」。
8. 只统计 `chat_type=p2p`；群聊消息单独记录、不计入结论。

复验时不得输出、提交或在文档中保存成员标识全文、姓名、头像 URL、令牌或密钥。
