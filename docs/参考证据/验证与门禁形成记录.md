# 验证与门禁形成记录

> 状态：历史依据，最后整理于 2026-09-06。本文只解释现行门禁与协作底线为什么形成（含触发它们的事故经过），不定义当前规则，不证明当前提交已经通过任何断言。

现行断言、证据层级和执行要求只看[验证与门禁](../技术设计/验证与门禁.md)；每次任务都适用的协作底线只看 [AGENTS.md](../../AGENTS.md#工作底线)；已经具备和仍未验证的能力只看[当前能力](../当前能力.md)。本文中的日期、版本、数量和提交状态都是当时快照，使用前必须重新核对。

## 为什么门禁必须属于仓库

- [PR #12](https://github.com/Moshuiwang/lingxi/pull/12) 自审发现，“同一话题只跑一个任务”曾被实现成对主键 `id` 再建唯一索引。该索引没有新增约束，第二个任务仍可能覆盖第一个；问题只因当次代理临时运行真实 PostgreSQL 才暴露，当时没有仓库规则要求这样做。
- `scripts/ci/verify_repository.sh` 曾因本机缺少 `shellcheck` 而使两名代理先后只运行部分检查。后来确认 `shellcheck-py` 可在无 root 环境安装，也由此形成“缺工具必须明确失败、报告版本、本机与 CI 不得静默分叉”的要求。

两件事说明：验证不能依赖某个代理刚好想到什么；稳定检查必须进入仓库，并在不满足时可靠变红。

## L4a 与最小真实执行链路

初稿曾把 L4 整体交给真人执行。为避免把可自动化验证变成人工等待，后来拆成代理驱动的 L4a 和确实需要真人的 L4b；二者都使用真实外部系统，证据强度不因执行者不同而降低。

2026-07-28 的 [Issue #23](https://github.com/Moshuiwang/lingxi/issues/23) 在 `biai-stage` 验证了 Agent SDK + 百炼的最小真实链路：

| 探针 | 当时结果 |
|---|---|
| 真实百炼端点启动和恢复会话，取得非空正文与唯一终止结果 | 40/40 回合成立；39 个正式回合正文与结果哈希一致 |
| 测试身份调用真实只读 MCP | 40 回合共取得 189 次工具调用与回执，覆盖 4 个只读工具 |
| 隔离 cwd、只读 Skill、无用户环境凭据 | 4 个回合实际加载 Skill |
| `PreToolUse`、`PostToolUse`、`PostToolUseFailure` 与 `Stop` | 常规回合及两次工具抛错补测均取得对应事件 |
| 默认拒绝的越界探针 | 3 次非白名单调用均在执行前被拒，无文件或 cron 副作用 |
| 证据脱敏 | 只保留字段名、计数、长度与哈希，不保存凭据 |

这轮只证明当时组合的机制可行，不自动覆盖后来修改过的执行器、审计归类或当前候选提交。它同时暴露两条长期约束：MCP 正常响应也可能是业务失败，审计必须自行解析回执并合成；只读边界必须由执行层默认拒绝，不能依赖 SDK 工具列表或提示词。

## 断言怎样补齐

- 2026-07-28 普通员工不再经过授权卡片或浏览器 OAuth 后，原来的身份断言随路径作废，`V-身份-01…04` 重新分配。旧同号“已验证”记录因此不能继续引用。
- Issue #29 的独立复查发现过判定绕过无留痕、记账异常带走拒绝、同名回执挂错、跨回合污染、分类随哈希顺序变化和 SDK 绑定零测试等问题，形成 `V-执行-10…16`。
- `V-执行-17` 来自同一类归类问题的第三层：单次调用归类正确，不代表回合合成正确。一次辅助调用成功曾把同回合的业务失败覆盖为 `OBTAINED`，因此混合回合必须保守处理。
- “开通与匹配”初稿漏掉了先占位、模糊匹配、错误生成人工待办和非法状态回退四类拒绝路径，促成每条“不得”规则都要有会变红的否定断言。
- `V-审计-03` 的两个残余缺口曾经产品负责人知情接受：自由文本中的纯字母短秘密无法被长度规则识别；合法形态的未知工具名保留在审计核心。后续 `V-执行-20` 收紧了 worker 出口，但没有假装关闭审计核心缺口。

这些经过只用于解释编号和边界；当前行为以主文的 `V-*` 行为、层级与状态列为准。

## 部署与本机门禁怎样补齐

Issue #29 暴露了三类只存在于散文、没有实际门禁的要求：安全边界依赖的 Agent SDK 与 CLI 未声明版本；门禁使用裸 `python3`，CI 恰好满足而本机可能低于项目下限；测试只覆盖源码目录，无法证明安装制品包含新增模块。由此形成 `V-部署-08/09/10`。

教训是：要求审查者“说明某件事”只会产生一段文字。可自动化的合并要求必须有 `V-*` 编号和实际会变红的 CI 检查，否则仍只是提醒。

本机门禁随后增加了解释器下限检查、ShellCheck 版本输出和真库半开状态守卫。长期目标仍是让新代理用一条命令得到与 CI 同构的结论；尚未完成的容器化入口属于实施工作，不应在历史记录里写成已具备。

## 文案类变异实测为什么会给出假红假绿（2026-08-31，Trace #469）

rc22 收尾批修复包 E 的独立审查里，同一组变异第一轮跑出 6 条**假红**。成因是 Python 字节码缓存的失效判据：`__pycache__` 只比对源文件的修改时间与字节数，而「收回 → 撤销」这类**等字节数的中文替换**配上同一秒内的 `git checkout` 恢复，两个判据同时失灵，解释器继续用陈旧字节码。表现是变异已经恢复、用例却还在红，或变异已经生效、用例却还在绿——**红绿都不可信**。

因此：**凡是改动只涉及字符串字面量的变异实测，必须带 `python3 -B`（或 `PYTHONDONTWRITEBYTECODE=1`）并在每一轮之前清掉 `__pycache__`**。加上这一条之后，同一组变异的失败用例数才与实施者报告逐一吻合。

这条不属于开工必读集（它是做变异实测时才查的操作细节，不是每次开工都要读的底线），但它影响的是本仓最基本的一条验证纪律——「光有绿测不算数，必须变异验红」。判据本身失灵时，那条纪律就是空的。

## 残留的临时实例烧掉了一次性授权码（2026-08-08，E1-A 真实验收）

现行规则见 [AGENTS.md「工作底线」](../../AGENTS.md#工作底线)：临时进程 / 容器 / worktree / 测试实例谁建谁清；共享的外部通道（Bridge / 长连接 / 队列 / 独占令牌）同一时刻只允许一个客户端。本节只记这条底线怎么来的。

E1-A 真实验收中，一个为身份发现临时起的进程与正式入口抢占同一条 OAuth Bridge 通道（Worker 侧「新连接踢掉旧连接」），**静默劫持并烧掉了产品负责人的一次性授权码**。用户侧表现是「点了授权、页面显示处理中、后台什么也没发生」，两侧都没有报错。

排查过程还被同一类残留误导了一次：另一台机器上跑了近四天的僵尸进程持旧凭据每 3 秒被拒一次，被误读为「服务在疯狂重连」。**残留的临时实例不是无害的**——它既能吃掉不可再生的外部授权，也能制造指向错误方向的现象。因此起临时实例前先查有没有同类实例在跑，用完即停。

## 并发提交把审查代理的变异行卷进提交（2026-08-23）

现行规则见 [AGENTS.md「工作底线」](../../AGENTS.md#工作底线)：做变异实测或跑测试的并行代理必须使用独立 worktree，同一工作树同一时刻只允许一个写入者。

那次实测里，编排者在共享工作树上并发提交，把审查代理正在做变异实测的改坏行一起提交了进去，险些推送坏提交。变异实测本身要求「先改坏、确认变红、再恢复」，中途的工作树状态天然是坏的；只要同一棵树上还有第二个写入者，这个中间状态就可能被固化成提交。

## L3 权限影响面的「正道」方案为什么不做（2026-09-01，Issue #520 / rc25）

现行规则见[验证与门禁「已知边界与上线后项」](../技术设计/验证与门禁.md#已知边界与上线后项issue-5202026-09-01)：registration 缺失记为 `unregistered` 的降级、四条「为什么接受 / 补偿措施 / 未削弱 / 解除条件」、以及「正道不做、本节即唯一正文」的结论都在那里，本节不复制。

「正道」方案指 `pull_request_target` + 仓库外可信注入链：要新建仓库级 ruleset 与 CODEOWNERS、受保护的 stage job / artifact 通道，并引入本仓库**第一个** `pull_request_target`。PR [#518](https://github.com/Moshuiwang/lingxi/pull/518) 因此 CLOSED 不合，四条理由是：

1. 不引入首个 `pull_request_target`（跑在目标分支上下文、带写权限的公认高危面）；
2. 不引入 1216 行新脚本；
3. 不引入未接线的检查；
4. 不改动仓库治理配置。

唯一收益只是把权限影响面的「数量」从人工复核换成机器验证，与上述代价不相称。

**源分支三条 P2 的逐条回源**（rc25 复评）：源分支 `codex/rc23-fix498-owner-attestation` @ `4a0acd793b3a7b7d2a328e5fa294af16d869d93d` 带的三条 P2 一条也没摘进 `main`，且都不该摘——两条的宿主文件 `main` 上根本不存在，摘过来等于把 #518 被拒的 1216 行重新引进；第三条要改的那段措辞**是该分支自己前两个提交引入的**，merge-base `c34b698` 与 `main` 都没有它，而 `main` 现有正文写的是另一套机制且准确。
