# 飞书关联组织用户身份受控验证

> 状态：2026-07-28 已完成受控实测，2026-07-29 完成全量复验并更正两处结论；仅限 `biai-stage` + `Bot-Test` 测试项目。
> 来源：[GitHub Issue #19](https://github.com/Moshuiwang/lingxi/issues/19)。本文件是本次关联组织验证的唯一长期证据；它不代表正式开通、权限发布、问数或生产入口已经可用。
>
> **本文各节是 2026-07-28 对单个关联组织（`118d12…`，73 个部门）的一次验证。**其后的全量事实——8 个关联租户 710 人、字段有值率、在职状态分布、姓名语言分布——见[两条路径的连接与字段可得性](飞书关联组织两条路径的连接与字段可得性.md)。凡本文与该文冲突处，以该文为准。

## 验证了什么

专用授权用户“四达文档会议助手”在 Bot-Test 完成飞书浏览器 OAuth 同意。`biai-stage` 以该专用用户身份读取其可见关联组织，选择“四达集团”，逐部门下钻并读取成员详情；普通员工不需要完成此授权。

| 能力 | 实测结论 |
| --- | --- |
| 专用用户授权与回调 | 成功；仅用于“四达文档会议助手”的组织资料读取。 |
| 关联组织定位 | 成功定位“四达集团”。 |
| 部门下钻 | 根组织及 63 个部门范围，共读 64 个分页范围，最大下钻 2 层。 |
| 可见范围 | 73 个部门、117 个成员；这些是当次快照，不是长期名单承诺。 |
| 目标成员 | 成功在成员详情接口命中王志鹏。 |
| 部门资料 | 目标成员的可见上级部门为“OTT业务部”。 |
| OAuth 续期 | 成功加密保存并实际轮换 1 条 `refresh_token`；短期 `user_access_token`、授权码不保存。 |

## 王志鹏可返回资料

成员详情实际返回：姓名、英文名、4 种尺寸头像、激活/离职/冻结等状态、`open_id`、`user_id`、`union_id`、上级部门标识及其可见部门详情。所有标识在日志和测试报告中只保留前缀。

本次接口对王志鹏**没有返回**：邮箱、手机号、职务、职级、工号或完整部门成员名册。

> **2026-07-29 更正：其中「手机号、职务」这两项不成立。**上面这句原本写作「本次接口没有返回：邮箱、手机号、职务、职级、工号」，是把**一个人**的详情当成了接口的字段天花板。对全部 8 个关联租户 710 人逐一读取详情后，`mobile` 有值 331 人（46.6%）、`job_title` 有值 261 人（36.8%）、`leader_id` 有值 47 人（6.6%）——王志鹏恰好属于没有这两个字段的那部分。邮箱、职级、工号确实从不返回，那部分原结论成立。
>
> 更正后的用法：`mobile` 与 `job_title` 覆盖不到一半，**只能作为可选增强，不得作为任何流程的必要输入或匹配前提**。完整有值率见[两条路径的连接与字段可得性](飞书关联组织两条路径的连接与字段可得性.md)。

本次专用授权链路已取得 `user_id`，关联组织成员详情也实际返回三类身份标识；本次产品设计据此把姓名、部门和三类身份标识作为自动匹配和后续投递的资料来源。手机号、邮箱、职务、职级和工号不参与银河权限匹配——这条不因上面的字段更正而改变：`mobile` 与 `job_title` 虽然部分可得，覆盖率不到一半，仍不足以作为匹配依据。

## 安全与边界

- 只使用 `biai-stage`、独立测试数据库和 Bot-Test；未触碰 Bot-Prod、生产数据库或生产发布。
- `refresh_token` 仅以密文保存在测试数据库；解密密钥仅在受控环境变量中。刷新成功立即替换旧凭据；刷新结果不明时删除旧凭据并要求重新授权。
- 授权码、短期 access token、完整身份标识和成员资料不写入日志、文档、Issue、PR 或临时结果文件。
- 测试查询不会创建正式 `app_user`、不会匹配数据库权限、不会发布权限或向普通员工宣告开通成功。
- 仓库较早的 `scripts/verify_feishu_association.sh`、`scripts/verify_feishu_user_message.sh`、`scripts/verify_feishu_org_path_email_message.sh` 与 `scripts/verify_feishu_email_message.sh` 使用应用身份，部分还会发送测试消息；它们不是本次用户身份验证的证据或复验入口。

## 复验与测试代码

唯一的测试项目代码说明见[飞书关联组织测试项目](../../experiments/feishu-oauth-associated-organization/README.md)。复验使用其中的受控脚本和自动测试；运行后只保留字段、计数和标识前缀的日志，立即删除包含成员资料的临时结果。

> **2026-08-05 在 `tz` 复验，结论不变**：因当时无法从 `tz` 连接 `biai-stage` 内部测试数据库，改用 `tz` 本机新起的独立 Docker PostgreSQL 容器复验，结果与本文一致（73 个部门、117 个成员、王志鹏命中于成员详情接口）。按产品负责人要求，这份容器和其中加密保存的 `refresh_token` 保留在 `tz` 上，作为 `biai-stage` 之外另一个常驻落点；例外记录与凭据过期时间（2026-08-12 05:36 UTC）见[测试项目 README](../../experiments/feishu-oauth-associated-organization/README.md#tz-上的本地测试数据库例外记录)。

## 对正式开发的输入

正式实现可以复用“专用用户明确同意 → 用户身份下钻关联组织 → 加密轮换续期凭据”的模式，用同步到的员工资料匹配银河权限记录。普通员工不走授权卡片；正式实现仍需完成密钥管理、撤销回收、最小权限、建档和权限发布代码，不得直接把本测试项目作为生产入口部署。

本次同时证实：机器人私聊事件的应用侧 `open_id` 不能与浏览器 OAuth 的 `open_id` 直接当作同一标识；飞书公开规则没有提供跨该边界的自动桥接接口。因此不得恢复“每位员工授权一次即可自动绑定”的方案。

**这条限于「私聊标识 ↔ 用户 OAuth 标识」这一对，不要读成「私聊标识无法与任何组织资料对上」。**另一条边界已在 2026-07-29 验证成立：私聊事件的发送者 `open_id` 可以直接在**应用身份**双方共享范围返回的 `open_user_id` 中命中，见[飞书关联组织应用身份共享范围](飞书关联组织应用身份共享范围.md)。自动开通的身份定位走的是后者，不是本节否定的那条。
