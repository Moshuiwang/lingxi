# 飞书关联组织两条路径的连接与字段可得性

> 状态：2026-07-29 完成受控实测；仅限 `biai-stage` + `Bot-Test`。
> 来源：[GitHub Issue #16](https://github.com/Moshuiwang/lingxi/issues/16) 的字段冲突核对。
> 本文只记录**两条身份路径之间的关系**：它们读到的是不是同一批人、同一套标识，以及拼接后每个字段实际能拿到多少。单条路径各自能做什么见[应用身份共享范围](飞书关联组织应用身份共享范围.md)与[用户身份受控验证](飞书关联组织用户身份受控验证.md)。

## 为什么需要这一份

自动开通用**应用身份**（私聊事件方）定位员工，但开通所需的 `user_id`、`union_id` 与在职状态只出现在**用户身份**（专用授权用户 OAuth）读到的成员详情里。因此存在一个此前没有答案的问题：**这两条路径读到的是不是同一批人、同一套标识？**如果不是，两边的资料就拼不起来。

## 前置事实：一次管理后台配置变更

2026-07-29 之前，专用授权用户只能看到 8 个关联租户中的 6 个，另外 2 个（含当时 `.env` 配置的目标租户）返回 0 条成员。**产品负责人当日在飞书管理后台补齐了这两个租户的可见范围配置**，之后用户身份可见租户数为 8/8。本文所有结论都是在配置补齐**之后**取得的；配置若被改回，结论随之失效。

## 已确认：8 个关联租户的共享范围版图

应用身份可以读到全部 8 个关联租户的双方共享范围。当次快照：

| 租户 | 共享部门 | 共享成员 |
| --- | ---: | ---: |
| `118d12…` | 73 | 128 |
| `2eee88…` | 39 | 100 |
| `111545…` | 17 | 91 |
| `10976a…` | 24 | 82 |
| `10b94e…` | 4 | 81 |
| `118920…` | 77 | 80 |
| `10b815…` | 20 | 80 |
| `10b94f…` | 18 | 68 |
| **合计** | **272** | **710** |

**`open_user_id` 跨全部关联租户唯一**：各租户成员数之和 710，全部去重后仍是 710，**跨租户重复 0**。

这条的直接后果是：**用私聊 `open_id` 定位员工不需要预先知道对方属于哪个租户。**租户归属是查出来的结果，不是必需的配置输入。此前测试脚本里的 `FEISHU_TARGET_TENANT_KEY` 是随手填写的单租户配置，不构成产品选择。

**警告（口径）**：`open_user_id` 的 6 位前缀**会碰撞**——710 人中有 57 组前缀被多人共用。前缀只用于日志脱敏，任何比对都必须用完整标识。

## 已确认：两条路径是同一标识体系

对 8 个租户逐个比对「应用身份共享范围返回的 `open_user_id`」与「用户身份可见组织返回的成员标识」：

| 租户 | 路径 A 成员 | 路径 B 成员 | 标识交集 | 姓名交叉核对 | 结论 |
| --- | ---: | ---: | ---: | --- | --- |
| `118d12…` | 128 | 128 | 128 | 128/128 | 成立 |
| `2eee88…` | 100 | 100 | 100 | 100/100 | 成立 |
| `111545…` | 91 | 91 | 91 | 91/91 | 成立 |
| `10976a…` | 82 | 82 | 82 | 82/82 | 成立 |
| `10b94e…` | 81 | 81 | 81 | 81/81 | 成立 |
| `118920…` | 80 | 80 | 80 | 78/78 | 成立 |
| `10b815…` | 80 | 80 | 80 | 80/80 | 成立 |
| `10b94f…` | 68 | 68 | 68 | 68/68 | 成立 |

**710 个标识全部对上，0 例外。**因此「私聊 `open_id` → 共享范围 → 用户身份成员详情」这条拼接成立，`user_id` 与 `union_id` 对全部 710 人可得。

`118920…` 的姓名交叉核对是 78/78 而非 80/80：该租户内有一对**重名**成员，姓名对标识不构成函数，这 2 条被排除在姓名旁证之外。主证据是标识交集 80/80。

## 已确认：成员详情各字段的有值率

对全部 710 人逐一读取关联组织成员详情（710/710 成功，重试后失败 0）。字段缺失时是**整个字段不出现**，不存在「字段存在但值为空」，因此下表的有值数即真实覆盖：

| 字段 | 有值 / 710 | 有值率 |
| --- | ---: | ---: |
| `open_id`、`user_id`、`union_id` | 710 | 100% |
| `name`、`i18n_name`、`avatar` | 710 | 100% |
| `status`、`parent_department_ids` | 710 | 100% |
| `mobile` | 331 | **46.6%** |
| `job_title` | 261 | **36.8%** |
| `leader_id` | 47 | **6.6%** |
| 邮箱、职级、工号 | 0 | **从不返回** |

**这推翻了[用户身份受控验证](飞书关联组织用户身份受控验证.md)原先「本次接口没有返回手机号、职务」的结论**——那条结论基于王志鹏一个人的详情，他恰好没有这两个字段。原结论对邮箱、职级、工号仍然成立。

`mobile` 与 `job_title` 覆盖不到一半，**只能作为可选增强，不得作为任何流程的必要输入或匹配前提**。这与「手机号、邮箱不参与银河权限匹配」的既有决策方向一致。

## 已确认：在职状态可得，且非在职成员不会被自动移出

成员详情返回 `status` 对象，含 `is_activated`、`is_exited`、`is_frozen`、`is_resigned`、`is_unjoin` 五个布尔字段。710 人的分布：

| 状态组合 | 人数 |
| --- | ---: |
| 已激活、未冻结、未离职、未退出、已加入 | 702 |
| 已激活但 **`is_frozen=True`** | **5** |
| **`is_activated=False` 且 `is_unjoin=True`** | **1** |

**结论：可见范围不做在职状态过滤，非正常状态的成员仍会被读到。**因此自动开通**必须在建档与发权限前逐人校验 `status`**，不得「定位到即视为在职」。

**边界**：当次没有 `is_resigned=True` 或 `is_exited=True` 的样本，因此「已离职成员是否仍留在可见范围」未被直接证实。但冻结与未加入两类已经证明该范围不按状态过滤，不能据此免除校验。

## 已确认：姓名并非全部含汉字

两条路径分别对 710 个成员的姓名做全量语言分类，结果**完全一致**：

| 类别 | 路径 A（`name.default_value`） | 路径 B（`user_name`） |
| --- | ---: | ---: |
| 含汉字（无拉丁） | 690 | 690 |
| 中拉混合 | 9 | 9 |
| **纯拉丁** | **11** | **11** |

**这修正了[应用身份共享范围](飞书关联组织应用身份共享范围.md)原先「82/82 全部含汉字、纯拉丁 0」的结论。**那 82 人是 `10976a…` 单个租户的样本，该租户内确实无纯拉丁姓名；放到全部 710 人上，**有 11 人的姓名完全不含汉字**。

因此按姓名与银河权限记录匹配时，必须能处理非中文姓名，不能假定姓名一定是中文。

## 已确认：姓名不是唯一键

710 人中存在 **1 对重名**（同一租户内）。任何按姓名匹配的逻辑都必须能处理歧义，不得默认姓名唯一。

## 复验方法

1. 用 Bot-Test 凭据换取 `tenant_access_token`；读关联租户目录，对每个租户递归读双方共享范围。
2. **`transport_error` 必须重试**。本次首轮实测因为把网络抖动当作正常终止，静默少算了 11 人（一个租户报成 117，实为 128）。任何一个范围读取失败，整轮人数与唯一性结论都不成立，应判「暂时无法验证」而不是照常输出。
3. 刷新专用授权用户凭据换取 `user_access_token`。**刷新成功后的第一条语句必须是写回保险库**，中间不插入任何其他操作——`refresh_token` 一次性，中途失败会导致专用授权失效并需要人工重新授权。每轮只刷新一次。
4. 比对两条路径时，**主证据是标识交集**；姓名只作旁证，且必须先排除两边的重名，否则按姓名建索引会把第二个同名者对到别人的标识上，产生假的不一致。
5. 判断字段可得性时必须区分「字段不存在」「字段存在但为空」「字段有值」，只统计有值数；不得因字段名出现就认定该字段可用。
6. 姓名语言分类只在内存中完成，只落盘计数。
7. 复验时不得输出、提交或在文档中保存成员姓名、手机号、职务、头像 URL、完整标识、令牌或密钥。证据只保留字段名、计数、状态布尔组合、错误码与标识前缀。
