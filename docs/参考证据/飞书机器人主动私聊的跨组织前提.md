# 飞书机器人主动私聊的跨组织前提

> 最后核对：2026-09-07（生产实测，Trace [#606](https://github.com/Moshuiwang/lingxi/issues/606) 块 Z）。
>
> **本文回答的长期问题**：本产品的机器人能不能主动给一个用户发起单聊？答案有前提，前提由飞书平台决定，不是本仓库的配置能改的。
>
> **不适用范围**：本文只覆盖**关联组织（跨组织）**场景下的**单聊主动发起**。群消息、用户先开口之后的回复、同企业内部的私聊都不在本文结论内。本文是证据与外部事实，**不定义产品规则**——受它影响的产品承诺以[产品合同与外部边界](../产品合同与外部边界.md)「主动告知」一节为准。

## 一、结论

**机器人无法向「从未与该机器人对话过」的跨组织用户发起单聊。** 平台一律拒绝，返回：

```text
230013  Bot has NO availability to this user.   (HTTP 400)
```

这是平台规则，不是可用范围、权限、身份标识或代码能修的问题（逐条排除见第四节）。

**推论**：任何「先由系统主动推送、用户被动接收」的首次触达形态，对新用户不成立。要让一个新用户拿到主动消息，顺序必须反过来——**先让用户自己开启会话**，系统随后再发。

## 二、实测样本（2026-09-07 生产与受控环境，13 次尝试，无一例外）

| 收件人 | 与该机器人有过历史会话 | 结果 |
| --- | --- | --- |
| 产品负责人 ← 生产机器人 | 有 | ✅ 送达（3 次预检卡） |
| 赵晋霞 ← 生产机器人 | **有**（产品负责人确认） | ✅ 送达 |
| 陆啸 ← 生产机器人 | **有**（产品负责人确认） | ✅ 送达 |
| 八位 CEO ← 生产机器人 | 无 | ❌ `230013`（三轮重发：08:03 / 08:47 / 09:54 UTC） |
| 宋威 ← 生产机器人 | 无 | ❌ `230013` |
| 赵晋霞 ← 测试机器人 | **无**（她没跟这个机器人说过话） | ❌ `230013` |

### 决定性对照

两组对照把「有无历史会话」单独隔离出来：

1. **同一天、同一段代码、同一张卡、同一个租户**：陆啸与那八位 CEO 一切相同——同租户（`118d1226…`）、同为 `A运营_CEO` ＋全部公司、同一天开通、同一次运行形态。**唯一差别是他跟机器人说过话**，他收到了，八位没有。
2. **同一个人、两个机器人**：赵晋霞收得到生产机器人（有会话），收不到测试机器人（无会话）。两个机器人**同属同一家企业**（实测 `tenant_key` 一致），面对的是同一个跨组织用户。

## 三、飞书官方对 `230013` 给出的三个成因

发送消息接口文档列出：① 目标用户不在机器人的可用范围内；② 用户在应用的停用成员名单里；③ 目标用户已离职。**这三条都不是本次的成因**（见下节）。官方文档另有一处措辞可作旁证：对外共享文档中说明外部用户「通过开启对话」进行单聊，且「外部用户移除后，单聊会被禁止，需要再通过开启对话后才能继续」——**「开启对话」是外部用户单聊的前置条件**，与本次实测方向一致。

## 四、逐条排除（每条都有实测）

| 假设 | 排除依据 |
| --- | --- |
| 跨组织本身阻断 | 成功与失败**两边都跨组织**：十二人**无一属于机器人所在的企业**（组织快照 8 个租户、711 人），产品负责人本人与赵晋霞同样是跨组织，照样收得到 |
| 可用范围 / 停用成员 | 用「获取用户可用的应用」（`application/v1/user/visible_apps`）逐人查：本应用**出现在十个人每一个人的可用应用列表里**，含全部八位 |
| 已离职 | 十二人全部通过了开通链的**在职状态实时回读**，一个人也不会漏 |
| 身份标识不对 | `open_id` 与 `union_id` **都撞同一堵墙**；标识本身无效会返回别的错误码（跨应用用 `open_id` 得 `99992361 open_id cross app`），返回 `230013` 说明应用认得这个人。`user_id` 跨租户不适用（`99992360`） |
| 应用权限不够 | 产品负责人在 08:5x / 09:1x 给应用加了「获取用户可用的应用」与 `contact:user.employee_id:readonly` 两项权限；**加完之后八人重发仍 8/8 失败** |
| 代码或卡片内容 | 同一次运行、同一段代码、同一个渲染函数、同一张卡 |
| 传播延迟 | 隔 40 分钟原样重发，8/8 同样失败 |

## 五、可复用的外部平台事实

- **`open_id` 按应用隔离**：同一个人在不同应用下是不同的 `open_id`；拿甲应用的值去乙应用发消息得 `99992361 open_id cross app`。
- **`user_id` 按企业签发**，跨租户不可用（`99992360`）。**`union_id` 在同一开发者名下的多个应用之间通用**，但它解决的是标识互通，**不解决本文的会话前提**。
- **「应用对用户可用」不等于「用户能搜到这个机器人」**：`visible_apps` 说可用，用户在飞书客户端里仍可能搜不到该机器人。可用范围与搜索可见性是两件事，不要用前者的读数去解释后者的现象。
- **AppLink 可以绕开「搜不到」**（已验明可用）：`https://applink.feishu.cn/client/bot/open?appId=<本应用的 appId>`，飞书客户端 3.40.0 及以上支持。用户点开即进入与机器人的会话，发一句话之后重发主动消息即可成功。`<本应用的 appId>` 的取值在飞书开发者后台该应用的凭证页，**不写进本仓库**。

## 六、一条操作规矩：批量发送的收件人必须用白名单圈定

2026-09-07 同批次踩到的一次误发，记在这里当反例。补发守望脚本的收件人筛选条件写成「已激活 ＋ 有过入站消息 ＋ 没有正式送达记录」这样的**反向排除**，产品负责人本人完全符合这三条（他一直在与机器人对话、名下只有预检记录），于是在 10:01:00Z **收到了一张本不该发给他的正式欢迎卡**。已核实只误发这一张，其余待发人员未受影响。

**规矩**：面向真实用户的批量发送，收件人必须由**写死的白名单**圈定；不得用「排除已完成的人」这类反向条件推导收件人集合。反向条件的失效方式是安静的——它不会报错，只会多圈进一个你没想到的人，而发出去的消息不可撤回。
