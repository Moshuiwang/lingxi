    - **⚠️ 未关闭的边界：服务端静默丢块，我们察觉不到**。探针实测原始 HTML 块被飞书直接丢弃，**不产生任何 warning**、`result` 仍是 `success`——这一类丢弃在响应里没有任何痕迹，本实现看不见，也不会告知用户。模型产出是普通 markdown，暴露面很低，但**不得声称「所有降级都会被如实告知」**。本批未加建档后回读校验（每次交付要多一次 API 调用），如需关闭这条边界另立卡。同类未知还有一条：该接口在飞书开放平台没有公开文档页，**限流与正文长度上限官方无契约**，20 000 字符这道守卫取的是实测安全带，不是官方数字。

    - **代码侧不再调用 `docx:document.block:convert`**：一次建档用应用身份令牌直接可用，探针实测没有出现任何 scope 类错误码，客户端转换接口已不被任何代码调用。**「代码不再需要它」不等于「飞书后台已经回收它」**——后台回收是一次运维动作，本批**没有做**，建议发版并观察一轮之后再收；回收失败不影响交付。
  - **worker 巡检移出事件循环**（rc25 S-2b）：巡检的四次同步数据库往返此前压在事件循环上，数据库一慢就会把同一条循环上的只读屏障应答一起卡住，而上游 CLI 的 hook 超时是**失败关闭**——代价是在途用户回合的工具调用被判死，用户侧看到问数中途失败。现改为线程池执行。同批把 CLI 工作目录与用户目录根「互不包含」做成会变红的部署门禁（细节见[架构设计 6.9](../技术设计/架构设计.md)）。

  - **停用即时撤权的覆盖面扩大到「开通尚未完成」的用户**（rc25 S-3a P-6）：此前停用一个正在首聊开通中的用户，即时撤权会因为该用户还不是 `active` 而被跳过，其在途的开通发布意图仍可能落到正式权限表；现在撤权走独立的撤权身份查找口（不看开通进度，仍排除已删除账号），这类用户的在途意图在认领时判 `superseded`、一次外部调用都不发。**方向是更保守**：授权侧的重算与发布口径一个字没放宽，只有撤权侧的覆盖面变大。
  - **九十天擦除之后不再把「没变的权限」误判成「变了」**（rc25 S-3a P-3，迁移 `0086_publish_outbox_digest`）：发布意图新增两列 SHA-256 摘要，「这一版和上一版一样吗」不再依赖会被九十天擦除的 `payload`。此前擦除之后判据读到空对象，一份内容完全没变的权限被判成变了，于是重排一条发布并把该用户的记忆与全部会话已送达正文清空——用户侧表现为「什么也没发生，记忆和历史答案却没了」。**两列不参与九十天擦除**（摘要是单向的，说不出邮箱、姓名或权限内容）；升级时按同一算法回填尚未被擦除的存量行，已擦过的历史行保持 `NULL`、读侧退回原 `payload` 比较，行为逐字不变。
  - **管理面健壮性三条**（rc25 S-3a）：①管理员发超长参数不再把命令处理挂住（实测 20000 字 token 从 25 秒以上降到毫秒级）；②`/admin audit <open_id> ²⁴` 这类上标数字不再打挂成「本次管理命令处理失败」，而是明确回「参数不对」（同类缺陷在用户侧 `/memory forget ²⁴` 一并修掉——**这一条任何用户都能触发**）；③非发起人点一张已过期的确认卡，不再被记成决定人、也不再触发管理群通知，发起人随后点仍得到「已过期」。
  - **指标映射外置文件的值卫生**（rc25 S-3a P-5）：映射文件里的指标**值**拒 `*`（含混进名字里的 `日活*`）、拒纯空白、拒不可见字符类；公司键仍不查目录、`*` 仍合法。口径与差集导入侧（S-2d）逐条对齐，两处不会分叉。
  - **「已激活重认领」通知正文的未翻译职能标签已修**（体验批 [#605](https://github.com/Moshuiwang/lingxi/issues/605)；rc25 S-3a 只定位未改、退回登记，本条取代那条已知边界登记）：已开通的用户再次触发开通链时，通知正文的职能位此前显示的是**内部职能标签**，用户读完仍不知道自己能查什么；现在这条分支在渲染前先过既有翻译层，与「开通完成」正常路径同口径，翻译查不到「公司 + 职能」组合时按本侧故障收口、**绝不回落成职能标签**（宁可让用户收到内部故障终态，也不发一句他读不懂的「开通完成」）。**证据等级 3**：本机单测（渲染出的正文只含指标中文名、不含职能标签原文；变异去掉翻译即变红）＋ 静态对账（`src/lingxi/` 里未翻译序列化入口已无任何调用点）；**stage 未构造触发该分支**，按 [#605](https://github.com/Moshuiwang/lingxi/issues/605) 完成标准 3 如实登记为「仅单测＋静态对账」。
  - **数据库连接串不再随进程环境进入 Claude CLI 子进程**（rc25 S-3b R6-D2）：worker 的真实进程入口（`python -m lingxi.apps.worker`）在进入主流程**之前**把 `LINGXI_POSTGRES_DSN` 从进程环境里摘掉，并把摘除前的快照交给主流程读配置，因此本进程照常连库、而此后 fork 出去的 Claude CLI 与 MCP 子进程都拿不到它。这条补上的正是 `deploy/README.md` 此前登记为「尚未实现」的那项加固（stage 探针实测过：子进程环境里确实有 `postgres://`）。**证据等级 3**：本机起真实子进程读 `/proc/<pid>/environ`，含 DSN 的子进程数为 0（另有反向对照证明不摘时是 1），**不是一次真问数**；`options.env` 只能加不能减这条 SDK 前提是回源确认的（读了随包 CLI 的源码）。
  - **主密钥配错不再删掉专用授权凭据文件**（rc25 S-3b C-2）：解密失败此前与「解开了、内容为空」不可区分，于是走到删除或撤销分支——一次配错主密钥就把凭据文件删了，只能重新走一次人工授权。现在解不开就是解不开：不删文件、不连库，留一条指名 `LINGXI_DELEGATED_CREDENTIAL_KEY` 的错误日志。
  - **日志与审计脱敏补三处**（rc25 S-3b C-4/C-5/C-6）：①连接串/URL 里 `用户:口令@主机` 那段口令现在会被盖住（此前既够不着长串规则的 16 字符下界、又没有键名上下文，三道旧规则一道都不覆盖）；②中文键名（密码/口令/密钥/私钥/令牌/凭据/凭证/授权码）＋全角分隔符的赋值也会被盖住（`会话`/`签名` **有意不收**——中文里它们常指诊断事实，抹掉是拿可读性换假的安全感）；③异常正文不再进日志：全仓 `logger.exception` 与 `exc_info=` 清零并加了会变红的整仓扫描，改为只记异常类型与调用栈，**在哪失败、失败的是哪一类**全部保留。**残余如实**：调用栈里会带上本仓库自己的源码行，因此「把秘密写成源码字面量」仍会经调用栈进日志（本仓库源码不含真实凭据）。
  - **内测内容采集在生产多一道结构性兜底，采集表也终于有人清了**（rc25 S-3b C-7）：①新增部署变量 `LINGXI_DEPLOY_ENVIRONMENT`，由 `compose.prod.yaml` 的 `environment:` 块直接给值（**不写进 env 文件**——compose 的 `environment:` 覆盖 `env_file`，因此哪怕有人把 stage 的 worker env 文件整份抄进生产，抄来的开关也不再可能生效）；声明为生产时采集一律不启用，两个开关配得再对也不生效。②`innertest_content_capture` 表的九十天到期行现在真的会被删——迁移 `0069` 建的 `expires_at` 触发器与扫描索引此前**没有任何调用方**，上限只存在于一个没人读的列里；现由 scheduler 新增的第 12 条职责按小批量 DELETE 回收（生产该表恒空，这条职责在生产每轮删 0 行）。

  - **部署配置的两个静默默认值被去掉**（rc25 S-3b R6-D4/P3）：①生产 `scheduler`/`gateway` 的内存上限改成无默认值，漏配 `deploy/.env.prod` 里那两行现在**直接让 `docker compose config`/`up` 失败**，不再静默退回 `1G`把三个常驻服务的加总从 3G 推到 4G、越过主机 3.74GiB；②一次性 worker 的内存默认值 `4G` 降到 `2G`——`4G` 大于宿主机可用内存，一个不会生效的上限比没有上限更糟。另有日志面两条：容器日志收集脚本固定 `umask 0027`（新建文件恒 `0640`）、监控采样目录按天数自清、推送日志加体量上限。
