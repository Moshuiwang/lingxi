# 银河用户权限数据结构

> 来源：产品负责人于 2026-07-28 提供的银河后台导出。首次提供三张表（`user`、`user_role`、`role_menu`），同日补充两张表（`sys_user_datacountry`、`sys_country`）；两次导出中原三张表逐字节相同。
> 该导出是**首期上线的用户权限唯一来源**；未来计划改为直接读取银河的同三张表。
> 本文只记录结构、连接关系与已核对的数据形态；**不含任何人员姓名、邮箱、账号或权限明细**。当次统计值随导出批次变化，此处保留的是会影响设计的性质，不是快照数值。

## 三张表与连接关系

合同要求的「公司范围」与「职能范围」是两条互相独立的授权链，各自从 `user_id` 出发：

```
user (1 行 1 账号)
  user_id ──┬──< user_role >── role_id ──< role_menu >── menu_id      ← 职能范围
            │
            └──< sys_user_datacountry >── country_key ──< sys_country ← 公司范围
  dept_id, user_name, nick_name, email, create_time
```

两条链互不约束：一个账号可以只有其中一条。按合同「记录完整才自动开通」的判定，导出中约五分之四的账号两条链齐备可自动开通，其余各类缺失都落到人工核对或查无记录分支——**这个比例远高于设计时的预期，见下方待决策**。

| 表 | 字段 | 说明 |
|---|---|---|
| `user` | `user_id` | 主键，导出中唯一 |
| | `dept_id` | 数字部门标识，**本次导出不含部门名称表** |
| | `user_name` | 登录账号；实测绝大多数是纯数字工号，全部为 ASCII——**匹配主键**（与花名册工号对应；非工号形态的少数账号回退邮箱匹配） |
| | `nick_name` | 中文姓名所在字段；~~这是与飞书员工资料匹配的字段~~ **2026-08-05 起仅作辅助核对**，匹配键改为工号（`user_name`）与邮箱（`email`），见[花名册身份链与工号邮箱匹配决策](../决策记录/2026-08-05-花名册身份链与工号邮箱匹配.md) |
| | `email` | **匹配辅键**；少量缺失；域名以公司域为主，另有少量公共邮箱与海外子公司域 |
| | `create_time` | 建号时间，跨度约十年 |
| `user_role` | `user_id`, `role_id` | 多对多关联 |
| | `user_name` | **列名具有误导性**，见下 |
| | `role_name` | 角色名冗余副本 |
| `role_menu` | `role_id`, `menu_id` | 多对多关联 |
| | `role_name`, `menu_name` | 名称冗余副本 |
| `sys_user_datacountry` | `USER_ID`, `DATACOUNTRY_ID` | 用户可见的数据国家，多对多；**列名为大写** |
| | `USER_NAME`, `DATACOUNTRY_NAME` | 姓名与国家名的冗余副本 |
| `sys_country` | `country_key` | **与 `DATACOUNTRY_ID` 连接的键**，见下 |
| | `id`, `name`, `code`, `name_cn` | 主键与中英文国名；`name_cn` 可直接用于向用户展示 |
| | `region_key`, `region_name` | 大区归属，**未覆盖全部国家** |
| | `ott_/view_/boss_/solar_/mall_*_id` | 各下游业务系统的自有国家或公司编号；其中 **`boss_company_id` 已确认为未来向问数 MCP 申请权限时使用的公司字段**（2026-08-05 产品负责人在 [Issue #17](https://github.com/Moshuiwang/lingxi/issues/17) 确认），其余与本链路无关 |

## 已核对的数据性质

**连接完整，无悬空引用。** `user_role` 中出现的每个 `user_id` 都能在 `user` 表找到；被分配的每个角色都在 `role_menu` 中有菜单。反向存在两类空缺：部分账号不持有任何角色，且没有字段能区分「离职残留」与「在职但未授权」。

**`user_role.user_name` 不是 `user.user_name`。** 该列的值实测几乎全部等于 `user.nick_name`（中文姓名），而非登录账号。**实现必须按 `user_id` 连接三张表，不得按任何名称列连接**，否则会取到与列名语义相反的值。

**姓名重复规模很小但不为零。** `nick_name` 存在少量重名，属于合同中「重名转人工核对」分支的真实触发场景；该分支必须实现，但预期人工量极低。

**公司范围连接键是 `country_key`，不是 `id`。** `sys_user_datacountry.DATACOUNTRY_ID` 与 `sys_country.country_key` 完全对上，与主键 `id` 几乎完全对不上。`sys_country` 中约五分之一的行没有 `country_key`，无法从授权表连接到；但被实际授权的国家全部可连接，且国家名与冗余副本完全一致。

**`全非` 是一行哨兵记录，不是国家。** `sys_country` 中存在一行 `country_key=0` / `name=ALL` / `name_cn=全非`。持有它的账号接近全部账号的一半，**但没有任何一个持有者同时枚举了全部已授权国家**，且这些账号之间的国家集合有二十余种不同组合。因此**无法从数据判断 `全非` 是「覆盖所有国家」的通配符，还是与具体国家并列的一个可选项**——这直接决定 Lingxi 向用户展示的公司范围是否属实，已列为待决策。

**大区归属不完整。** 被实际授权的国家中约五分之一没有 `region_name`，因此不能可靠地按大区汇总展示公司范围。

**权限粒度是菜单，不是数据范围。** 一个用户经多个角色获得数百个菜单权限中的一部分，人均角色数中位数为个位数、上限为二十余个。菜单是银河的界面功能项，与问数 MCP 所需的「数据范围」是否同构尚未验证。

**`menu_name` 不唯一。** 存在同名菜单对应不同 `menu_id` 的情况（同一名称出现在菜单树的不同位置）。任何展示或匹配都必须以 `menu_id` 为准。

**角色名是自由文本，不能作为结构化字段解析。** 74 个角色的命名规则不统一：部分含国家或归属地区词，部分只含职能词，另有少量明显的临时角色、个人专用角色和带测试痕迹的名称。含地区词的角色不足四分之一，且相当比例的用户同时持有跨多个地区词的角色——因此**无法从角色名可靠反推用户的公司范围**。

## 2026-08-05 产品负责人决定（Issue #17 回复）

以下三条以产品负责人 2026-08-05 在 [Issue #17](https://github.com/Moshuiwang/lingxi/issues/17) 的回复为准；上文与下文中与之相抵的分析保留为历史背景，不再作为待决策：

1. **`全非` 是通配符**：语义为「所有国家、所有公司」。此前「无法从数据判断」的分析（见上）就此终结。
2. **职能范围来自「A 打头」角色名的映射**：`A运营`=运营、`A销售`=销售等。该映射抽象为**配置文件**并随角色演进持续人工维护——角色名是自由文本、无法结构化解析的结论仍然成立，配置文件正是为此建立的人工维护层。不以 A 开头的角色不映射为职能。
3. **对接问数 MCP 的公司字段是 `sys_country.boss_company_id`**：申请与发布权限时使用它；`name_cn` 仍用于向用户展示中文国名。

尚未回答的仍是：在职状态与银河权限时效（决策 2）、快照刷新机制（决策 3）。另注意 2026-08-05 [Issue #34 回复](https://github.com/Moshuiwang/lingxi/issues/34)已把身份匹配键从姓名改为经花名册取得的**工号与邮箱**（工号主、邮箱辅，见[花名册身份链与工号邮箱匹配决策](../决策记录/2026-08-05-花名册身份链与工号邮箱匹配.md)）；`user.email`「少量缺失、混有公共邮箱与海外域」的性质决定邮箱回退可用的范围。

## 对产品合同的影响（2026-07-28 登记）

以下当时不是实现选择、需要产品负责人决定，已登记在 [Issue #17](https://github.com/Moshuiwang/lingxi/issues/17)；其中第 1 项的职能展示形态与「全非」语义已由上一节决策，第 4 项的比例判断随邮箱匹配键的引入需要重新统计：

1. **公司范围已有结构化来源，职能范围仍然没有。** 补充的两张表解决了公司维度：`sys_user_datacountry` → `sys_country.name_cn` 可直接展示中文国名。职能维度仍只有 74 个自由文本角色名与数百个菜单项，需要决定展示形态。另有两个悬而未决的点：`全非` 的语义，以及 `dept_id` 与公司范围是否为同一维度（`dept_id` 至今没有名称表）。
2. **缺少在职状态字段。** 合同中的「当前有效权限记录」「账号停用后阻止新问数」「调岗记录更新」都依赖它，而 `user` 表只有建号时间。
3. **首期是快照而非接口。** 需要定义快照如何进入 Lingxi 数据库、刷新周期，以及刷新期间的一致性与并发问数行为。
4. **「记录完整」的实际不通过率远高于预期。** 按现合同判定，导出中约六分之一的账号会落入人工核对或查无记录分支，主要来自只有公司范围而无任何角色的账号。需要决定这些账号按什么处理，否则首期人工量会集中在开通环节。
