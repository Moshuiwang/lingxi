## 一、背景

当前 `scripts/run_e2e_test.py` 只围绕 `wangzp@startimes.com.cn`、`Rwanda`、单个 Linux 用户跑完整流程。这个账号是用户的真实个人账号，适合验收真实邮箱、开户注册、SSH、Claude 和 MCP 的普通用户体验，但不适合承担日常全量指标监控和 Benchmark。

新的日常维护需要覆盖三类体验：

- 新指标出现后，系统能及时发现，不依赖人工追问。
- 全权限 Benchmark 能看到所有已开放指标，并验证自然语言查询体验。
- 单公司、最小权限账号能持续证明权限边界没有被放宽。

## 二、目标

把现有 E2E runner 从“单账号、单国家、跑完即收回”升级为“固定测试账号矩阵、可批量执行、可选择保留账号”的日常验证工具。

用户最终看到的效果：

- 以后新增指标后，`mcpmonall` 能发现指标变化。
- Benchmark 用 `benchall1` / `benchall2` 跑，不再占用个人账号。
- 权限回归用 `benchugops` / `benchnigops` 跑，能验证“只能看自己的公司”和“全量账号能看全部指标”。
- 建账号、清残留、跑验证、是否保留账号，全部有明确脚本入口和结果摘要。

## 四、范围

本次纳入：

- Runner 支持从账号规格文件读取多个账号。
- 支持只跑一个账号、跑全部账号、或只列出账号。
- 支持“创建并保留账号”和“跑完收回账号”两种模式。
- 默认保护真实账号，清理前必须命中测试账号清单。
- 输出每个账号的申请、审批、DB/Bitable、邮件、SSH、Claude/MCP/Plugin、收回结果；其中邮件/SSH/Claude 默认只在具备可读邮箱时开启。

本次不纳入：

- 不把 fake 邮箱变成真实可收信邮箱。若没有 IMAP 可读邮箱，默认跳过邮件读回，避免把测试失败误判为开户失败。
- 不把一个测试 open_id 伪装成多个真实飞书用户。当前测试机器人链路仍使用 `E2E_TEST_OPEN_ID` 作为统一测试申请人。
- 不直接上线定时任务；本次先提供可手动或 CI 调用的稳定入口。

## 五、成功标准

最低成功标准：

- 能用一条命令跑 5 个固定测试账号。
- 每个账号都能独立产出 PASS/FAIL/SKIP 摘要。
- 不会清理 `wangzp`、`maosy`、`zhaojx`、`liuds`。
- `benchnigops` 使用 Nigeria，且权限为单公司全指标。
- 账号可选择保留，用于后续日常 MCP 状态维护。

完整成功标准：

- 在 EC2 上用测试机器人跑完整申请和审批，并发布 DB/Bitable 权限。
- 具备可读邮箱后，全量账号能列出所有当前指标。
- Uganda 最小权限账号跨公司查询被拒绝。
- Nigeria 单公司全指标账号查询 Nigeria 成功、查询其他公司拒绝。
- 结果可以直接用于每日 Benchmark 和准入巡检。

## 六、风险与约束

- 当前测试命令归属校验绑定 `E2E_TEST_OPEN_ID`。这保证测试命令不能操作真实用户，但也意味着这批账号不是 5 个真实飞书身份。
- fake 邮箱如果没有真实邮箱或可读 catch-all，就不能证明“用户本人收到邮件”，也不能拿到本轮 SSH 私钥继续跑 SSH/Claude smoke。真实邮件体验仍由 `wangzp` 负责验收。
- Bitable 权限发布必须由部署用户执行，避免 `/tmp` lock 权限问题导致发布失败。
- 真正有验收意义的 live run 必须在 EC2 `/home/wangzhipeng/projects/bi-ai-agent` 执行，本机只能跑单测和静态检查。
