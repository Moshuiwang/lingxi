# 飞书卡片流程 V2 架构升级设计

> 日期：2026-06-08
> 状态：已按本设计施工落地，待真实飞书 live run / 人工点击复验
> 依据：`docs/feishu-card-flow-v2.md`
> 范围：用户申请权限、审批、管理员取消授权、文字通知、配置来源。

## 一、设计目标

V2 的目标不是把现有卡片逻辑简单改名，而是把飞书交互收敛成一条更清楚的用户体验主线：

- 用户只在私聊发送“申请权限”时看到申请卡。
- 审批人只在审批群处理审批卡。
- 管理员只在审批群 `@Bot 取消授权` 时进入取消授权。
- 没有按钮的结果全部改成文字通知。
- 后台判断仍然严格，用户看到的入口更少、更稳定。

架构升级的目标：

- `start_bot.py` 只做路由和顶层编排，不再承载业务规则。
- 卡片只负责展示和提交动作，不做判断。
- 申请、审批、取消授权分别有清楚的 owner。
- 公司和职能只有一个配置来源，卡片展示和后台校验共用。
- 结果文案放配置文件，后续产品可以直接改文案。

## 二、最终模块分工

| 模块 | V2 责任 | 不做什么 |
|---|---|---|
| `scripts/start_bot.py` | 接收飞书事件，判断入口路由，调用对应服务，发送卡片或文字 | 不写状态判断、不写表单校验、不拼权限列表、不写卡片结构 |
| `app/services/permission_options.py` | 读取公司/职能配置，提供选项，校验提交值 | 不连接 MCP，不做运行时同步，不发飞书消息 |
| `app/services/application_form.py` | 继续负责字段级校验：必填、邮箱归一化、邮箱后缀等 | 不决定入口状态，不发飞书消息 |
| `app/services/application_flow.py` | 用户申请入口判断、调用字段校验、创建申请、生成审批上下文 | 不直接构造飞书卡片，不直接调用飞书 API，不重复实现 `application_form.py` 已有规则 |
| `app/services/approval_service.py` | 保留 submit / approve / reject，负责审批数据落库和权限幂等写入 | V2 不再主动超时关闭审批 |
| `app/services/approval_followup.py` | 审批通过后的后续结果汇总：开户、权限落库、权限发布、SSH 交付的结果归一化，判断是否需要人工处理，生成文字通知上下文 | 不直接发飞书消息，不写审批状态 |
| `scripts/start_bot.py` 的审批后编排 | 审批通过后作为顶层编排者，按顺序调用开户、权限发布、SSH 交付等现有服务，并把结果交给 `approval_followup.py` 汇总 | 不自己判断复杂业务结果，不把这些步骤下沉到 `approval_service.py` |
| `app/services/revoke_flow.py` | 生成可取消的“用户-公司-职能”组合，准备 004 确认内容，执行取消授权流程 | 不做飞书卡片结构，不绕过 `user_service.revoke_authorization` |
| `app/services/pending_admin_flow.py` | 管理员人工关闭长期未处理的待审申请，复用退回通知口径 | 不做自动超时，不新增卡片 |
| `app/services/user_service.py` | 用户查询、当前权限查询、实际取消权限 | 不做飞书交互 |
| `app/services/permission_publish.py` | 权限发布同步到多维表格 | 不决定用户能不能申请或取消 |
| `app/services/permission_publish.py` | 继续提供 `publish_permissions_now()` 立即发布能力；管理员手动重试命令直接复用它 | 不改变用户权限事实，不发飞书消息 |
| `app/services/permission_publish_flow.py` | 管理员“重试权限发布”文字命令的权限校验、并发保护和文字结果归一化，内部复用 `publish_permissions_now()` | 不新增另一套发布逻辑，不改变用户权限事实 |
| `app/feishu/cards.py` | 只保留 V2 需要的 4 张可操作卡片构造 | 不放业务规则 |
| `config/permission_options.yaml` | 公司/职能下拉选项的唯一配置源 | 不放用户权限事实 |
| `config/messages.yaml` | 扩展现有文案配置，新增用户和管理员看到的 V2 文字通知 | 不放业务判断 |

这样拆分后，用户体验规则集中在两个流程服务里：

- 申请体验：`application_flow.py`
- 取消授权体验：`revoke_flow.py`

飞书入口、卡片样式、数据库落库、权限发布都各自保持单一职责。

取消授权链路和审批通过链路有一个有意的差异：取消授权第一版只有“删库 + 权限发布”两步，放在 `revoke_flow.py` 内完成；审批通过链路包含开户、权限发布、SSH 交付等多步外部副作用，因此保留入口层顶层编排，并用 `approval_followup.py` 统一汇总结果。

## 三、路由设计

### 3.1 用户申请入口

只接受：

```text
私聊 Bot：申请权限
```

处理方式：

1. `start_bot.py` 判断这是私聊，且文本等于“申请权限”。
2. 调用 `application_flow.build_entry_response()`。
3. 如果可以申请，返回 001。
4. 如果不能申请，返回文字原因。

其它私聊内容不弹 001。群聊不弹 001。

### 3.2 管理员取消授权入口

只接受：

```text
审批群：@Bot 取消授权
```

处理方式：

1. `start_bot.py` 判断这是审批群，且命令是“取消授权”。
2. 调用 `revoke_flow.py` 校验触发人是否管理员。
3. 调用 `revoke_flow.list_revoke_choices()`。
4. 有可取消权限时返回 003。
5. 没有权限或无管理员权限时返回文字原因。

私聊不弹 003。其它群聊不弹 003。

### 3.3 管理员关闭待审申请

V2 不做 002 主动超时关闭。为避免申请长期待审导致用户无法重新申请，保留一个无卡片的管理员文字兜底：

```text
审批群：@Bot 关闭申请 <用户邮箱或 open_id> <原因>
```

处理方式：

1. `start_bot.py` 判断这是审批群，且命令是“关闭申请”。
2. 调用 `pending_admin_flow.py` 校验触发人是否管理员。
3. 找到该用户当前待审申请。
4. 将待审申请按退回处理，写入原因，通知用户重新发送“申请权限”。

这不是自动超时，只是人工兜底；不新增卡片。

### 3.4 管理员重试权限发布

审批通过或取消授权后，如果权限发布失败，管理员可在审批群手动重试：

```text
审批群：@Bot 重试权限发布
```

处理方式：

1. `start_bot.py` 判断这是审批群，且命令是“重试权限发布”。
2. 调用 `permission_publish_flow.py` 校验触发人是否管理员，并避免和 systemd timer 的发布任务并发执行。
3. 将当前数据库权限事实重新发布到权限多维表格。
4. 用文字通知管理员本次重试成功或失败。

现网已有兜底：`scripts/sync_permission_bitable.py` 由 systemd timer 以 ≤15 分钟周期重试同一套 `sync_permissions` 逻辑。`@Bot 重试权限发布` 只是强制立即同步，不必等待下一次 timer；不新增新的发布逻辑。

施工时如果现有同步脚本没有全局锁，需要给 timer 入口和 `permission_publish_flow.py` 加同一把跨进程文件锁，例如同一个 lockfile / `flock`。不能只用 Python 进程内的 `threading.Lock`，因为 systemd timer 和 Bot 是两个独立进程。拿不到锁时，管理员手动重试直接返回“权限发布任务正在执行，请稍后再试”。同步结果沿用 `publish_permissions_now()` 的返回值，文字里展示 `created / updated / deleted`。

## 四、配置设计

新增一个配置文件：

```text
config/permission_options.yaml
```

建议结构：

```yaml
companies:
  - label: Rwanda
    value: Rwanda

functions:
  - label: 运营
    value: 运营
  - label: 财务
    value: 财务
```

口径要求：

- `label` 是用户在下拉框看到的名字。
- `value` 是后台收到、落库、发布权限时使用的稳定值。
- 公司来源于当前 MCP 数据中的公司字段，或当前系统已有公司数据，一次性整理进配置。
- 职能来源于当前已有职能数据，一次性整理进配置。
- `value` 必须和权限多维表格口径对应清楚，避免卡片提交值、数据库值、权限发布值不一致。
- 后台只接受配置里的 `value`，旧卡片或异常请求传入其它值时直接拒绝。

V2 的选择是：下拉展示和申请提交校验以 `permission_options.yaml` 为准，不再依赖运行时同步结果来决定用户能不能选择。现有 `company_sync.py` 和数据库公司表可以继续作为历史数据、管理后台或后续对账来源，但不再作为 001 下拉框的实时来源。

不做运行时同步。后续如果 MCP 团队新增公司或职能，先改配置，再发布。这样用户看到什么、后台接受什么、权限发布使用什么，三者能在一次改动里对齐。

## 五、申请流程架构

### 5.1 001 展示

`application_flow.py` 负责判断用户应该看到什么。判断必须按优先级执行，不能只看单一用户状态：

| 优先级 | 判断 | 返回 |
|---|---|
| 1 | 停用 / 离职 | 文字提示账号不可用 |
| 2 | 有待审申请 | 文字提示已有申请正在审批 |
| 3 | 已通过 | 001，带当前姓名、邮箱、已有权限；如上一单补充申请被退回，退回原因只做文字提示 |
| 4 | 退回 | 先文字提示退回原因，再返回 001 |
| 5 | 无记录 | 001 |

已通过用户的姓名和邮箱展示当前已通过账号信息，默认沿用，不可编辑。

### 5.2 001 提交

001 提交后由 `application_flow.submit_from_card()` 处理：

1. 校验卡片是否过期。
2. 校验是否已有待审申请。
3. 校验账号当前仍然可用，未停用、未离职。
4. 调用 `application_form.py` 校验必填项、姓名/邮箱归一化。
5. 调用 `application_form.py` 校验邮箱必须是 `@startimes.com.cn` 后缀。
6. 校验公司和职能都来自 `permission_options.py`。
7. 调用 `approval_service.submit_application()` 创建申请。
8. 生成 002 的审批上下文。
9. 返回给入口层：发审批卡 + 发用户文字通知。

提交成功后不再弹提交结果卡，只发文字：“申请已提交，等待审批”。

职能是多选。一次提交只有一个公司，但可以包含多个职能；审批上下文按“公司 + 多个职能”展示。审批通过落库时，必须展开成多条单职能权限：

```text
用户 + 公司 + 职能 A
用户 + 公司 + 职能 B
用户 + 公司 + 职能 C
```

后续取消授权仍以单条“用户-公司-职能”为粒度。

### 5.3 重复申请

V2 采用简单口径：重复申请也进入审批。

但审批通过落库必须幂等：

- 同一用户、同一公司、同一职能已存在时，不再生成第二条权限。
- 多职能申请逐条幂等；已存在的职能跳过，不存在的职能新增。
- 审批卡仍展示“当前已有权限”和“本次申请内容”，由审批人判断是否通过。

这样用户体验简单，数据库也不会产生重复权限。

## 六、审批流程架构

002 仍由 `approval_service.py` 负责审批落库：

- 通过：写审批结果，写用户状态，写权限。
- 退回：写退回状态和退回原因。
- V2 不再做主动超时关闭，不再设置 002 TTL。

审批通过后的后续程序编排沿用现有顶层编排方式，由 `start_bot.py` 调用开户、权限发布、SSH 交付等服务。每一步的原始结果交给 `approval_followup.py` 归一化，生成统一的文字通知上下文。`approval_service.py` 不接管这些飞书侧编排，也不直接发消息。

如果审批长期无人处理，不由系统自动关闭。管理员通过审批群文字命令走 `pending_admin_flow.py` 人工关闭，关闭后的用户体验等同退回：用户收到原因，并可重新私聊发送“申请权限”。

审批处理后，原 002 必须变成不可操作状态。实现上选择更简单的一种：

- 更新原卡为“已处理，不可点击”。
- 或删除/替换原卡，再发文字结果。

审批通过后的文字通知在后续程序执行完之后再发，内容包括：

- 申请是否通过。
- 本次通过的公司和职能。
- 当前权限状态。
- 开户结果。
- 权限落库结果。
- 权限发布结果。
- SSH 交付结果。
- 是否需要人工处理。

后续程序部分失败时，不回滚审批。文字通知逐项标注成功/失败，失败项标记为需要人工处理。是否需要人工处理由 `approval_followup.py` 根据各服务返回结果判断，方便单独测试。

权限发布失败时，不能告诉用户“新权限已生效”。此时文字结果应表达为：审批已通过，数据库已记录本次权限，权限发布正在重试同步中，通常 15 分钟内生效；若长时间仍不可用，请联系管理员。用户侧“已生效权限”只以权限发布成功后的状态为准。

发布失败后的重试不绑定某一张审批卡。系统已有 ≤15 分钟周期的 timer 兜底；管理员也可使用审批群文字命令 `@Bot 重试权限发布`，立即按当前数据库事实重新发布权限。手动重试只把结果通知管理员。

这些文案模板扩展到现有 `config/messages.yaml`，后续可以直接编辑。

## 七、取消授权流程架构

### 7.1 003 选择卡

`revoke_flow.list_revoke_choices()` 从当前真实权限生成选项：

```text
姓名（邮箱） / 公司 / 职能
```

每个选项对应一条真实存在的用户-公司-职能权限。

第一版不做动态联动，不做多选。后台最终校验选中的组合是否仍然存在。

如果组合数量超过飞书下拉上限，后续再拆成搜索或分步选择。第一版不预先复杂化。

### 7.2 004 确认卡

管理员在 003 选择后，进入 004。

`revoke_flow.build_confirmation()` 返回：

- 将要取消的是谁。
- 将要取消的公司。
- 将要取消的职能。
- 该用户当前全部权限。
- 确认后的影响说明。

004 的作用是防止误操作。

003 选中的“用户-公司-职能”组合通过卡片 `form_value` 带入 004，服务端不保存中间会话状态。004 的“返回重选”选择最简单的实现：重新生成一张新的 003；旧 004 同时变为不可操作。

### 7.3 确认取消

管理员点击 004 的“确认取消”后：

1. `revoke_flow.confirm_revoke()` 再次校验操作者是否管理员，以及这条权限是否仍然存在。
2. 调用 `user_service.revoke_authorization()` 删除权限。
3. 调用 `permission_publish.py` 同步权限发布。
4. 生成管理员文字结果。
5. 生成被取消用户文字结果。

如果权限已经不存在，直接文字提示管理员，无需重复取消。

权限发布失败时，不能只说“已取消”。管理员文字结果必须明确写成“数据库已删除，权限发布正在重试同步中，通常 15 分钟内生效；如需立即处理，可在审批群执行 `@Bot 重试权限发布`”。被取消用户的文字通知应说明“权限取消已记录，系统正在同步，通常 15 分钟内生效”，避免让用户误以为这一秒已经完全生效。核心原则是：用户侧通知必须说明同步状态，不能把“数据库已删除”说成“权限已经实时回收”。

这里的“重试”包括现有 systemd timer 的自动兜底和管理员手动立即同步。第一版不保存待补发用户通知队列，因此不会在 timer 成功后自动补发第二条用户通知。

## 八、卡片和文字边界

V2 只保留 4 张可操作卡片：

| 卡片 | 是否有按钮 | 生命周期 |
|---|---|---|
| 001 填写申请卡 | 有 | 2 小时 |
| 002 审批卡 | 有 | 无 TTL，处理后不可操作 |
| 003 取消授权选择卡 | 有 | 2 小时 |
| 004 取消授权确认卡 | 有 | 2 小时 |

本表是 V2 四张卡片生命周期的当前事实源。V2 中 002 不主动超时关闭；历史方案中的审批超时后台任务和 `expired` 自动关闭逻辑不进入 V2 主链。

四张卡片的动作清单：

| 卡片 | 动作 |
|---|---|
| 001 | 提交、取消 |
| 002 | 通过、退回 |
| 003 | 下一步、取消 |
| 004 | 确认取消、返回重选、取消 |

其它内容一律文字通知：

- 申请已提交。
- 申请通过。
- 申请退回。
- 后续程序执行结果。
- 取消授权结果。
- 权限已不存在。
- 无权限操作。
- 卡片过期。
- 账号不可用。

## 九、建议施工顺序

1. 新增 `config/permission_options.yaml` 和 `permission_options.py`，先测公司/职能读取与校验。
2. 新增 `application_flow.py`，先测入口状态和 001 提交判断。
3. 新增 `revoke_flow.py`，先测组合下拉、004 确认、权限不存在等场景。
4. 新增 `pending_admin_flow.py`，支持管理员文字关闭卡死待审申请。
5. 在 `cards.py` 增加 V2 四张卡片构造，旧卡片先保留但不走 V2 主链。
6. 改 `start_bot.py` 路由，接入私聊“申请权限”、审批群 `@Bot 取消授权`、审批群 `@Bot 关闭申请 ...`、审批群 `@Bot 重试权限发布`。
7. 调整审批处理后的文字通知，文案迁入 `config/messages.yaml`。
8. 取消 V2 主链里的主动审批超时逻辑，删除或停用旧 B1 审批超时后台任务及 `expired` 自动关闭路径。
9. 为所有旧卡 action 保留迁移兜底：旧卡被点击时，统一文字提示“该卡片已失效，请私聊发送‘申请权限’或在审批群 @Bot 取消授权重新开始”，不要静默失败。
10. 跑通端到端测试后，再清理旧卡片、旧 handler、旧测试；清理前确认旧 action 兜底仍在。

## 十一、验收标准

做到以下结果，即认为架构升级完成：

1. 用户私聊普通内容不会弹申请卡。
2. 用户私聊“申请权限”才弹 001 或返回明确文字原因。
3. 已通过用户再次申请时，001 展示当前姓名、邮箱和已有权限。
4. 001 提交成功后直接进入审批，不弹二次确认，不弹无按钮结果卡。
5. 审批群收到 002，审批处理后原卡不可继续操作。
6. 002 不再主动超时关闭。
7. 审批通过后的文字结果包含后续程序执行状态；权限发布失败时，不把新权限描述成实时已生效。
8. 管理员可用文字命令关闭长期待审申请，用户不会永久卡死。
9. 管理员可用文字命令立即重试权限发布；系统原有 timer 仍负责周期性兜底。
10. 审批群 `@Bot 取消授权` 才弹 003，私聊不弹。
11. 003 用“用户-公司-职能”组合单选。
12. 004 做二次确认，并展示该用户当前全部权限。
13. 取消授权完成后，管理员和被取消用户都收到文字结果。
14. 取消授权发布失败时，管理员和用户都知道权限正在同步，不会误解为实时回收。
15. 旧卡点击不会静默失败，会提示重新从 V2 入口开始。
16. 所有公司/职能选项都来自同一个配置文件。
17. `start_bot.py` 没有新增业务规则，仍只是入口和编排。

## 十二、为什么这个方案更可维护

这个方案的核心是把“用户体验规则”和“飞书实现细节”分开。

产品规则变化时，主要改：

- `application_flow.py`
- `approval_followup.py`
- `revoke_flow.py`
- `pending_admin_flow.py`
- `permission_publish.py`
- `config/messages.yaml`
- `config/permission_options.yaml`

飞书卡片样式变化时，主要改：

- `app/feishu/cards.py`

审批、权限落库、权限发布仍复用现有服务，不重新造一套权限系统。

这样后续再调整入口文案、取消方式、通知内容、公司/职能选项时，不需要在入口脚本里翻一大段飞书事件处理代码，也不容易把申请、审批、取消授权三条链路改乱。
