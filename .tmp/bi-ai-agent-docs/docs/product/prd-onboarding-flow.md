## 一、触发机制（状态驱动）

不设冷却。**用户每次向 bot 发送消息，bot 都根据该用户当前状态返回对应响应。**

| 用户状态 | bot 响应 |
|----------|----------|
| 无申请记录 | 发送**申请入口卡片**（见第二节） |
| pending（已提交，待审核） | 文案提示「您的申请正在审核中，请耐心等待」，**不再发申请卡片** |
| 退回（rejected） | 提示已退回 + 审核理由，并**重新展示申请卡片**（可预填上次内容）供修改后再次提交 |
| approved（已通过） | 提示「您的申请已通过，授权已记录」（Phase 4 起替换为正常 Agent 响应） |
| disabled（已停用） | 提示「您的账号已停用，如需恢复请联系管理员」 |

> 状态以服务端记录为准，状态机由 FastAPI 后端维护。

## 二、申请入口卡片

### 2.1 卡片内容

| 区域 | 内容 |
|------|------|
| 标题 | 申请使用 BI AI Agent |
| 简介 | BI Agent 能力介绍（自然语言查询、多国数据、核心业务指标） |
| 表单字段 | 首次申请：姓名、工作邮箱、申请公司（单选）、职能（多选）、说明（选填）；已开通用户补申请：只填写申请公司、职能、说明，并展示当前已有授权 |
| 底部说明 | 提交后送审，预计 1 个工作日内完成审核，结果将通过本对话通知 |

> 不在用户侧卡片展示「您来自哪个飞书组织」。飞书 `tenant_key` 与申请公司无关，仅在审批环节提供给审批者（见第四节）。

### 2.2 表单字段

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 姓名 | 文本输入 | 首次申请必填 | 已开通用户补申请时沿用当前账号，不再让用户重复填写 |
| 工作邮箱 | 文本输入 | 首次申请必填 | 需校验公司邮箱；已开通用户补申请时沿用当前账号 |
| Linux 用户名 | 系统生成 | 否 | 首次申请审批通过后由系统按邮箱派生并消歧；补申请不重复开户 |
| SSH 公钥 | 系统生成 | 否 | 首次申请审批通过后由系统生成 key pair，公钥写入 `authorized_keys`，私钥加密 ZIP 发送 |
| 申请公司 | **单选**下拉 | 是 | 公司选项来自 SQLite `companies` 登记表；用户申请多公司时通过多次补申请完成 |
| 职能 | **多选**下拉 | 是 | 审批后写入 `user_functions`；同步到 MCP 时按公司映射进 `permissions` |
| 说明 | 文本输入 | 否 | 申请原因 / 特殊说明 |

### 2.3 公司列表

申请卡片不写死三家公司。Bot 启动后从 SQLite `companies` 登记表读取可申请公司；展示名可来自 `physical_companies.name_en`，提交值仍使用内部公司名。

> 「北京/总部」是我们侧的特殊授权集合，MCP 端不会看到集合语义；同步到多维表格前由我方展开成实体 `company_id`，再聚合进用户行的 `permissions`。

## 三、表单提交与验证

### 3.1 前端校验（卡片层）

- 必填项未填时，禁用「提交申请」按钮（若飞书卡片支持）
- 若卡片不支持动态禁用，则提交后由后端返回错误提示（以后端校验为准）

### 3.2 后端校验

提交后服务端检查：
- 邮箱是否符合标准格式（正则校验）
- 必填项是否均已填写

校验不通过时：更新卡片，在对应字段下方展示错误提示，用户修正后可重新提交。

### 3.3 二次确认

校验通过后，不直接进入审核，先向用户展示**确认卡片**：

```
您填写的申请信息如下，请确认：

姓名：xxx
邮箱：xxx@xxx.com
申请公司：Rwanda
职能：运营、财务
说明：（无）

[修改]   [确认提交]
```

用户点击「确认提交」后，申请才正式进入审核流程。

**幂等性与旧卡处理：** 「确认提交」点击后，当前卡片会被替换为无按钮的“申请已提交”状态卡，并落库为 pending；状态卡展示本次申请内容与当前已生效权限。用户如果从历史消息点击更早的申请入口卡，服务端不重复创建申请，而是把该旧卡也替换为同一张无按钮状态卡。

## 四、审核群通知

用户确认提交后，bot 向审批群发送审核卡片：

| 区域 | 内容 |
|------|------|
| 标题 | 新的 BI Agent 使用申请 |
| 申请人信息 | 姓名、open_id、**飞书组织标识（tenant_key 原始值）** |
| 申请内容 | 邮箱、SSH 登录材料为系统自动生成、申请公司、职能、说明、提交时间 |
| 操作按钮 | 「通过」 / 「退回」 |
| 理由输入框 | 「通过」可选填；**「退回」必填理由** |

> - 「退回」替代「驳回」，措辞更友好。
> - `tenant_key` 仅供审批者识别来源组织，**与申请公司无任何对应关系**，不做名称映射，原样展示。

**幂等性：** 审批卡片被任一审核人操作后，立即将「通过/退回」按钮置灰，记录操作人与操作时间；二次点击或并发操作不重复写入授权、不重复通知。

---

## 五、审核结果通知申请人

审核人操作后，bot 向申请人私聊发送结果卡片。

### 5.1 通过

卡片内容：
- 恭喜通知：申请已通过，授权已记录
- 账号开通状态说明：首次申请展示 Linux 用户名，并提示邮件收 ZIP、飞书收口令；补申请说明不重复开户
- 本次申请内容：公司、职能、说明
- 当前已生效权限：展示到“公司 -> 职能”这一层

### 5.2 退回

卡片内容：
- 退回通知
- 审核人填写的理由（必填）
- 提示用户可修改后重新申请（再次发消息即重新展示申请卡片）

## 六、授权开通（本阶段范围）

审核通过后，系统自动完成：

1. **创建/更新账号记录**：写入 SQLite `users` 表，`status = approved`
2. **写入授权**：按申请公司 + 职能写入 `user_grants` / `user_functions`
3. **签发/复用 MCP token**：新用户自动签发，补充授权复用原 token
4. **自动开户/环境创建与 SSH 交付**：首次申请审批通过后生成 SSH key pair，触发 `create_user.py` 写入 Linux 账号、SSH 公钥、Claude 环境与真实 HTTP `bi-metric` `.mcp.json`，再通过邮件发送加密 ZIP、飞书私聊发送 ZIP 口令
5. **立即发布权限副本**：写入飞书多维表格，timer 仅作兜底
6. **通知用户**：发送开通成功卡片（见 5.1）

> **授权 vs 上下文配置（当前 live run 设计要点）：**
> - **授权与数据隔离（与目录无关）**：用户能查哪些公司 / 指标由 `user_grants` / `user_functions` + MCP token 强制过滤决定，不依赖文件系统目录结构（见 ADR-006）。
> - **上下文配置不靠目录继承，而是开户时「种默认模板」进用户 home**：
>   - `~/.claude/settings.json`、`~/CLAUDE.md`：开户时种入默认模板，**用户属主、可改**，并提供「恢复默认」能力；当前测试已确认不要依赖父目录 / 祖父目录 prompt 叠加。
>   - `.mcp.json`：**唯一例外**，带身份 token，必须 **root 属主、用户只读**，防止用户改 token 伪造身份、越权查别家公司数据。当前 live run 写真实 HTTP MCP URL + Bearer token；正式上线仍待服务端隔离验收。
>   - 多业务（如 DVB + Solar）：当前不再依赖 `cd` 到不同业务子目录切换 prompt；开户时按用户当前授权生成默认 home 环境，业务维度后续由 MCP / 指标过滤承载。
> - 详见 ADR-008。
