# 审批后 MCP 验证与审批卡体验优化 PRD

> 日期：2026-06-25
> 状态：待实现
> 范围：用户申请 / 补充授权审批通过后的审批群提示、MCP 验证等待体验、审批卡信息表达。

## 一、背景事实

当前审批通过后的系统行为是：

1. 审批人点击“通过”；
2. 系统完成 SSH 密钥配置；
3. 系统立即把授权发布到飞书多维表格；
4. 系统马上在审批群发起“审批后 Smoke 验证”，其中包含 Claude / MCP / BI Plus Plugin 验证；
5. 如果 MCP 此时还没有同步到最新多维表格权限，MCP 验证会失败，审批群看到“验证未通过”。

这里的失败不一定代表用户权限真的有问题。它可能只是 MCP 服务端还没有完成多维表格权限同步。

已确认的外部约束：

- 我方把 SQLite 授权发布到飞书多维表格；
- MCP 团队定期从飞书多维表格读取权限副本并本地校验；
- MCP 同步生效最慢可到 15 分钟；
- 因此审批通过后立刻跑 MCP 验证，天然存在时间窗口。

## 二、用户体验问题

### 2.1 审批者看到的误导

审批者刚批准申请，就看到 MCP 验证失败，直觉会认为：

- 刚才的审批没有开通成功；
- 用户账号不可用；
- 系统不稳定，需要人工介入。

但真实情况可能只是“权限已写入多维表格，MCP 尚未同步”。这会降低审批者对系统的信任。

### 2.2 用户看到的误导

用户收到“开通完成”后，如果马上尝试查询，可能遇到 MCP 不可用或权限不可见。用户不理解 15 分钟同步窗口，会觉得账号开通失败。

### 2.3 审批卡信息过长、不够业务化

当前审批卡已经展示申请人、邮箱、公司、职能、说明、当前权限，但审批者真正需要快速判断的是：

- 这是谁；
- 申请什么；
- 是首次开通、补充授权，还是权限变更；
- 当前已有权限是什么；
- 批准后会发生什么；
- 有什么风险或注意事项。

机器字段、执行状态、英文技术词或过长说明不应该占据主视觉。审批者应先看到中文业务摘要，再按需查看技术细节。

## 三、目标

本次后续实现的目标不是改变 MCP 团队的同步机制，而是把我方审批后的提示和验证节奏改成符合真实系统状态。

目标体验：

1. 审批者点击“通过”后，先明确看到“授权已发布，MCP 正在等待同步”；
2. 第一次 MCP 验证如果失败，不直接定性为开通失败；
3. 系统在等待窗口后自动复验，并把每次验证状态清楚告诉审批群；
4. 如果最终仍失败，再明确提示需要人工处理；
5. 审批卡改成中文、短、业务化，让审批者 10 秒内能判断是否批准。

## 四、推荐方案

### 4.1 MCP 验证改为“两阶段结果”

审批通过后，结果拆成两层：

| 层级 | 含义 | 面向审批者的表达 |
|---|---|---|
| 开通处理 | 我方已经完成开户、权限落库、多维表格发布 | “开通处理已完成” |
| MCP 可用性 | MCP 是否已经同步并可用 | “等待同步中 / 已验证通过 / 最终未通过” |

审批者不应把“第一次 MCP 没通”理解成“开通失败”。

### 4.2 第一次验证失败时进入等待态

审批通过后可以继续立即跑第一次 Smoke，但文案要改变：

- 第一次 MCP 验证通过：显示“已验证通过”；
- 第一次 MCP 验证失败，且错误符合权限未同步特征：显示“权限已发布，MCP 可能仍在同步，系统将在约 15 分钟内自动复验”；
- 第一次 MCP 验证失败，且不是同步类错误：显示“验证异常，系统会复验；若复验仍失败再人工处理”。

第一版不必过度识别所有错误类型。只要避免把第一次失败直接写成最终失败即可。

### 4.3 自动复验节奏

建议复验策略：

1. T0：审批通过后立即发布权限，并跑一次快速验证；
2. T+5 分钟：如果第一次未通过，自动跑第二次；
3. T+20 分钟：如果第二次仍未通过，自动跑最终验证；
4. 最终仍失败：审批群收到“需要人工处理”的明确提示。

这样做的原因：

- 5 分钟复验可以覆盖 MCP 已较快同步的情况；
- 20 分钟最终复验覆盖当前已知最慢 15 分钟同步窗口，并留出少量边界缓冲；
- 审批者不需要自己记得回来检查；
- 不把用户体验卡在一次偶发失败上。

### 4.4 审批群提示口径

审批群应看到连续、可理解的状态，而不是只看到一条失败日志。

建议状态文案：

| 场景 | 审批群文案方向 |
|---|---|
| 审批刚通过 | “已批准，正在开通账号并发布权限。” |
| 权限发布完成 | “权限已发布到多维表格，MCP 可能需要最多 15 分钟同步。” |
| 第一次 MCP 未通过 | “第一次 MCP 验证未通过，当前判断为等待同步中；系统将自动复验。” |
| 第二次 MCP 通过 | “MCP 已同步，验证通过。用户可以开始使用。” |
| 最终仍未通过 | “MCP 复验仍未通过，需要人工检查 MCP 同步、Token 和权限行。” |

这里不要使用“失败”作为第一次验证的主标题。第一次只应表达为“等待同步 / 自动复验中”。

### 4.5 用户提示口径

用户侧要避免过度暴露 MCP 细节，但要降低焦虑。

首次开户通过后的用户通知建议：

```text
你的 BI AI Agent 权限已通过。
权限已提交同步，通常几分钟内可用，最慢可能需要约 15 分钟。
如果刚登录时暂时查不到指标，请稍后再试；系统会自动完成后台验证。
```

补充授权通过后的用户通知建议：

```text
你的补充授权已通过，权限已提交同步。
新权限通常几分钟内可用，最慢可能需要约 15 分钟。
```

最终复验失败时，是否通知用户需要谨慎。第一版建议只通知审批群管理员，不直接给用户发“失败”，避免用户收到无法处理的信息。

## 五、审批卡内容优化

### 5.1 审批卡首屏结构

审批卡应该先让审批者快速判断，而不是展示技术上下文。

建议结构：

```text
权限申请审批

申请类型：首次开通 / 补充授权 / 权限变更
申请人：张三（zhangsan@startimes.com.cn）
本次申请：Rwanda / 运营、财务
当前已有权限：Uganda / 运营
申请说明：需要负责 Rwanda 月度经营分析

批准后：
- 首次开通：系统会开通飞书聊天权限、发布数据权限，并等待 MCP 同步
- 补充授权：系统会追加数据权限，并等待 MCP 同步
- 如用户申请高级数据分析工作台：系统会继续准备工作台和 JumpServer 授权待办
- MCP 可用性：权限发布后可能需要最多 15 分钟同步
```

### 5.2 信息优先级

必须展示：

- 申请类型；
- 申请人姓名和邮箱；
- 本次申请的公司和职能；
- 当前已有权限；
- 申请说明；
- 批准后的用户可见影响。

可以弱化或移出首屏：

- open_id；
- tenant_key；
- record_id；
- Linux username；
- raw status；
- 英文技术错误；
- 过长日志。

这些字段可以保留在日志或调试输出里，不应该作为审批者的主要阅读内容。

### 5.3 中文化要求

审批者看到的主文案应全部为中文。必要技术词可以保留，但要解释为业务含义：

| 技术词 | 审批卡表达 |
|---|---|
| MCP smoke | MCP 可用性验证 |
| Bitable | 权限多维表格 |
| token | 访问凭证 |
| sync | 同步 |
| permission publish | 权限发布 |

### 5.4 卡片长度控制

审批卡首屏建议控制在 6 行以内。详细信息通过“当前已有权限”和“申请说明”承载，不把后续执行日志塞进审批卡。

审批通过后的执行进度应放在后续进度消息或审批群状态卡，不反向塞回审批卡主体。

## 六、后续实现任务包

### 任务 A：审批后 MCP 验证等待态

目标：

- 第一次 MCP 验证失败不再直接显示最终失败；
- 审批群能看到“等待同步中”和“将自动复验”；
- 用户通知中说明新权限最慢约 15 分钟可用。

验收：

- 模拟第一次 MCP 验证失败时，审批群文案不出现“开通失败”；
- 文案明确说明权限已发布、MCP 等待同步；
- 用户侧收到的通知不要求用户理解技术细节。

### 任务 B：自动复验

目标：

- 对等待同步中的审批记录自动复验；
- 复验通过后通知审批群；
- 最终仍失败时通知审批群人工处理。
- 服务重启后仍能恢复等待复验任务，等待态最终必须收敛到“验证通过”或“需要人工检查”。

验收：

- T+5 分钟复验通过时，审批群看到“验证通过”；
- T+20 分钟仍失败时，审批群看到“需要人工检查”；
- 同一审批记录不会并发重复复验；
- Bot 重启后，pending_sync 记录会被补偿扫描继续复验或转人工；
- 复验日志不打印 token 或密钥。

### 任务 C：审批卡中文业务摘要

目标：

- 审批卡首屏改成中文业务摘要；
- 申请类型、当前已有权限、批准后影响更清楚；
- 技术字段不占据主视觉。

验收：

- 审批者无需理解 open_id、tenant_key、MCP smoke 等技术词，也能判断是否批准；
- 首屏能看清“谁申请什么、为什么、批准后发生什么”；
- 首次开通和补充授权的卡片差异清楚。

## 七、暂不做

本轮文档不要求立即实现以下内容：

- 不改变 MCP 团队的 15 分钟同步机制；
- 不新增实时 MCP 回调接口；
- 不改变现有权限多维表格结构；
- 不改变 SQLite 授权事实源；
- 不把复验失败直接通知普通用户；
- 不新增实时回调；复验状态需要持久化，以保证服务重启后不会丢失等待态。

## 八、风险与待确认

1. 需要确认 MCP 未同步时的典型错误文本，方便未来把“等待同步”与真实故障区分得更准。
2. 如果 MCP 20 分钟后仍未同步，人工处理 SOP 需要写到 runbook 或 live-run checklist。
3. 审批卡首屏压缩后，是否还需要一个“查看技术信息”的管理入口，后续按审批者反馈决定。

## 九、成功标准

这件事完成后，审批者的感受应该是：

- “我知道审批已经生效了”；
- “我知道 MCP 还在同步，不是系统马上坏了”；
- “系统会自己复验，不需要我盯着”；
- “如果最终真的失败，我知道该找谁处理”；
- “审批卡能快速看懂，不需要读技术字段。”
