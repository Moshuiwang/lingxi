# BI Plus 运行环境切换 PRD

## 1. 目标

让同一套生产服务可以在正式机器人与 `bi-plus-测试用机器人` 之间安全切换。运维只选择一个明确的环境 profile，机器人身份、数据库和飞书资源随 profile 一起切换；不允许逐项手工拼装配置。

## 2. 用户体验

- 正常时只有一个活动机器人和一套活动服务。
- 活动环境只有两个：`bi-plus-production` 与 `bi-plus-test-bot`。
- 页面健康信息和启动日志分别显示 `PRODUCTION` 或 `TEST-BOT`。
- 测试机器人使用独立空数据库，测试用户、管理员和会话不进入生产数据库。
- 切换失败时恢复原环境，原机器人重新可用。

## 3. 成功标准

1. 运维一次选择即可切换完整环境，不编辑多份配置。
2. profile、机器人 App 指纹和数据库三者必须匹配；测试机器人不可能连接生产数据库，正式机器人不可能连接测试数据库。
3. 管理员 open_id 只存在对应数据库，不存在 env profile。
4. 切换前后均可从 `/health` 确认活动环境，不暴露凭据。
5. 未经第二次明确批准，只允许预置 `bi-plus-test-bot`，不得激活。
6. 首位测试 owner 初始化时同时绑定一个已存在且通过校验的 Linux 运行身份；同一飞书用户随后既能管理，也能按该 Linux 身份普通对话，不需要手工补库。

## 4. 固定环境

| profile key | 用户可见标识 | 数据库 |
|---|---|---|
| `bi-plus-production` | `PRODUCTION` | `/var/lib/bi-ai-agent/app.db` |
| `bi-plus-test-bot` | `TEST-BOT` | `/var/lib/bi-ai-agent/profiles/bi-plus-test-bot/app.db` |

环境名和数据库映射是产品合同，不接受自定义第三种环境或任意路径。

## 5. 范围

- 两个受控 profile 的加载、校验、健康展示和原子切换。
- 管理员判断改为当前数据库中的 active owner/admin。
- 测试 profile、独立数据库和服务器目录的未激活预置。
- 首位测试 owner 的一次性 challenge 与既有 Linux 运行身份绑定。
- 切换失败回滚、审计结果和运维文档。

## 6. 非范围

- 同时在线运行两个飞书机器人。
- 自动复制生产用户、会话或权限到测试数据库。
- 跨飞书应用映射 open_id。
- 由本次合并或部署自动激活测试机器人。
- 创建、删除或修改 Linux 用户与 Home。
- 复制生产聊天、会话、MCP token、业务权限或 open_id 到测试库。

## 7. 切换前置条件

- 目标 profile 文件完整、权限正确且是普通文件。
- profile key、固定数据库路径与独立 binding manifest 中的机器人 App 指纹完全匹配。
- 目标数据库可初始化或已通过完整性检查。
- 目标数据库已将当前 VERSION 精确绑定到当前部署 commit。
- 三项服务可整体停止和启动。
- 激活 `bi-plus-test-bot` 已获得单独人工批准。
- 初始化首位 owner 时提供的 Linux 用户已存在且不是保护账户，Home 与 `bi-agent-work` 符合受控路径、owner、mode、非 symlink 合同；该 username 在当前数据库中未绑定其他飞书身份；固定测试数据库已存在且满足 service owner、0700/0600 和非 symlink 合同。

## 8. 失败体验

任何校验失败都在停服前拒绝。若服务启动或健康检查失败，系统恢复原活动配置并重启原环境；结果只显示稳定错误码和环境名，不显示配置值。若回滚也失败，服务保持停止并明确标记需要人工恢复。

## 9. 验收边界

代码、部署和未激活预置完成，不等于测试机器人已可用。测试机器人“已可用”至少要求第二次批准后的真实切换、首位 owner 与既有 Linux 运行身份的原子绑定、该 owner 的普通消息路径，以及 production 回退预检。完整环境切换 readiness 还必须至少完成一次真实回切和正式机器人消息复验；某次 scoped 验收是否执行该步骤只记录在 Issue，不能改变长期合同。
