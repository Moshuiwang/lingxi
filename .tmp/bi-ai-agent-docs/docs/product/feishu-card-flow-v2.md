# 飞书卡片流程 V2

> 日期：2026-06-08
> 状态：已施工落地，待真实飞书 live run / 人工点击复验
> 范围：用户申请权限、审批、管理员取消授权、结果通知这四段飞书交互体验。

## 一、目标

本次调整的目标是把飞书交互收敛成 **4 张可操作卡片 + 文字通知**。

可操作卡片只用于用户必须填写、审批人必须处理、管理员必须选择的场景。没有按钮、只展示结果的内容，不再做卡片，直接用文字消息通知用户或管理员。

后台校验仍然保留：必填项、邮箱格式、公司是否可选、职能是否可选、是否已有待审申请、卡片是否过期等，都以后端判断为准。

## 二、4 张可操作卡片

| 卡片 ID | 名称 | 面向谁 | 触发时机 | 是否可操作 |
|---|---|---|---|---|
| 001 | 填写申请卡 | 用户 | 用户私聊 Bot 发送“申请权限” | 是 |
| 002 | 审批卡 | 审批人 | 申请进入审批流后发到审批群 | 是 |
| 003 | 取消授权选择卡 | 管理员 | 管理员在审批群 `@Bot 取消授权` | 是 |
| 004 | 取消授权确认卡 | 管理员 | 管理员在 003 选择要取消的权限后 | 是 |

说明：
- 旧的“已通过状态卡 + 申请更多授权按钮”不再使用。
- 旧的“二次确认卡”不再使用。
- 旧的“提交反馈卡、成功卡、失败卡、取消结果卡”等无按钮卡片不再使用，统一改成文字通知。
- 旧的“查看授权用户”入口不再进入本流程。

## 三、用户申请流程

### 3.1 入口路由

只有用户在 **私聊** 中发送：

```text
申请权限
```

才进入申请流程，并返回 001 填写申请卡。

普通私聊不弹申请卡。这样可以避免用户随便和 Bot 说一句话就被申请卡打断。

群聊不触发用户申请卡。

### 3.2 不同状态下的体验

| 用户状态 | 用户发送“申请权限”后看到什么 |
|---|---|
| 无记录 | 返回 001 |
| 已通过 | 返回 001，并在卡片里展示当前已有权限 |
| 退回 | 先文字提示上次退回原因，再返回 001 |
| 停用 / 离职 | 文字提示账号不可用，不返回 001 |
| 待审批 | 不返回新的 001，文字提示已有申请正在审批 |

状态判断优先级：停用 / 离职优先级最高；除此之外，只要用户当前存在待审申请，就优先按“待审批”处理，不再返回新的 001。用户已有权限继续有效，不因新申请待审而暂停。

如果用户当前没有待审申请、且已经是已通过用户，即使上一单补充申请曾被退回，也按“已通过用户再次申请”展示 001；上一单退回原因只做文字提示，不改变 001 的已通过用户形态。

如果用户点击历史 001 再次提交，后台仍要校验当前状态。若已有待审申请，直接文字提示“已有申请正在审批”，不重复建单。

### 3.3 卡片 001：填写申请卡

001 是唯一的用户填写入口。

首次申请时：
- 姓名
- 工作邮箱
- 公司，单选
- 职能，多选
- 说明，选填

已通过用户再次申请时：
- 姓名和邮箱展示为当前已通过账号的信息，默认沿用，不让用户重新编辑
- 公司仍然单选
- 职能仍然多选
- 仍然可填写说明
- 卡片展示当前已有权限，帮助用户理解自己现在有什么

001 底部有两个动作：
- 提交：提交后不再出现二次确认
- 取消：取消后把当前卡片替换为不可操作状态，让这张旧卡不能再填写或提交

### 3.4 公司和职能选项来源

公司和职能选项统一放到一个配置文件中维护，作为卡片展示和后台校验的共同来源。

建议配置文件包含：
- 可申请公司列表：来源于当前 MCP 数据中的公司字段，或当前系统已有公司数据；一次性整理成配置，不做运行时同步
- 可申请职能列表：来源于当前已有职能数据；一次性整理成配置，不做运行时同步
- 公司展示名和提交值：必须和交给 MCP 团队使用的权限多维表格口径对应清楚，避免展示值、提交值、发布值不一致
- 职能展示名和提交值：必须能稳定映射到权限多维表格中的指标 / 职能口径

用户体验保持两个控件：
- 公司：一个下拉框，单选
- 职能：一个下拉框，多选

后台只接受配置文件里存在的公司和职能。配置外的值即使通过旧卡片或异常请求提交，也应拒绝。

### 3.5 提交后的后台判断

用户点击 001 的“提交”后，后台先校验：
- 卡片是否过期
- 是否已有待审申请
- 必填项是否完整
- 邮箱是否符合集团邮箱规则：必须是 `@startimes.com.cn` 后缀，不接受其它后缀；该规则与用户选择的公司无关
- 公司是否在配置文件中
- 职能是否在配置文件中
- 首次申请时账号信息是否可用

校验不通过时，直接用文字告诉用户原因，不再弹结果卡。

校验通过后：
- 直接创建申请记录
- 直接推送 002 到审批群
- 直接用文字告诉用户：申请已提交，等待审批

### 3.6 重复申请处理

重复申请也进入审批，代码和体验都更简单。

也就是说，只要用户提交内容合法，且当前没有待审申请，就创建申请并进入审批。审批人通过 002 看到用户当前已有权限和本次申请内容，再判断是否通过。

审批通过后的权限落库必须幂等：同一用户、同一公司、同一职能如果已经存在，不再重复生成第二条权限记录。这样既保留“重复申请也进审批”的简单体验，也避免取消授权时出现两条完全相同的可取消项。

## 四、卡片 002：审批卡

002 发到审批群，现有主体逻辑保持不变。

002 应展示：
- 申请人
- 申请人 open_id / tenant_key
- 本次申请公司
- 本次申请职能
- 申请说明
- 当前已有权限

002 的操作：
- 通过
- 退回，退回必须填写原因

审批处理后：
- 原 002 不能继续保持可操作。实现时选更简单的方式：要么把原卡更新为已处理且不可点击，要么销毁原卡后发文字结果。
- 申请人收到文字通知，文案放到配置文件中，后续可直接编辑。
- 审批通过时，先执行后续程序，再发送最终文字结果。最终文字结果除申请结论外，还要描述后续程序执行结果，例如开户、权限落库、权限发布、SSH 交付等状态。
- 如果后续程序部分失败，不回滚审批；文字结果里要明确写出哪些成功、哪些失败、是否需要人工处理。

审批通过后的用户文字通知应包含：
- 申请已通过
- 本次通过的公司和职能
- 当前已生效权限
- 首次开户时的账号/交付说明，如有

审批退回后的用户文字通知应包含：
- 申请被退回
- 退回原因
- 如需重新申请，请私聊 Bot 发送“申请权限”

002 不做主动超时关闭，也不设置 TTL。审批卡在审批人处理前保持可操作；处理后必须变为不可操作状态。

如果审批卡长期没人处理，系统不自动超时关闭。需要人工处理时，管理员可在审批群使用文字命令关闭该待审申请，并按退回流程通知用户重新申请；该兜底不新增卡片。

如果审批通过或取消授权后出现权限发布失败，现有 systemd timer 会在 15 分钟内周期性重试权限发布。管理员也可在审批群使用文字命令立即重试权限发布，把当前数据库权限状态重新同步到权限多维表格；重试结果用文字通知管理员。

## 五、管理员取消授权流程

### 5.1 入口路由

管理员必须在 **审批群** 里发送：

```text
@Bot 取消授权
```

才进入取消授权流程，并返回 003。

私聊不弹 003。其它群聊不弹 003。

是否是管理员，仍然后台判断；非管理员触发时，直接文字提示无权限。

### 5.2 卡片 003：取消授权选择卡

003 让管理员选择一条要取消的权限。

选择方式：
- 一个“用户-公司-职能”组合下拉框，单选
- 选项展示格式建议为：`姓名（邮箱） / 公司 / 职能`

数据来源：
- 只要用户在数据库中存在，且当前有权限，就可以列出来
- 每个选项对应一条当前真实存在的用户-公司-职能权限
- 后台最终校验这条组合权限是否仍然存在；展示只是帮助管理员选择，最终以后端校验为准

这样可以避免飞书卡片动态联动问题：不需要先选用户再刷新公司和职能，第一版直接展示所有可取消的组合。

规模边界：第一版先接受组合下拉；如果组合数量超过飞书下拉上限，或管理员实际使用时难以查找，再拆成搜索或分步选择。无论展示方式如何，后台校验始终是最终依据。

003 的操作：
- 下一步：进入 004
- 取消：把当前卡片替换为不可操作状态，让旧卡不能继续提交

### 5.3 卡片 004：取消授权确认卡

004 用于二次确认取消授权，避免管理员误操作。

004 应展示：
- 将要取消的是谁
- 将要取消的公司
- 将要取消的职能
- 该用户当前已有的全部权限
- 提醒：确认后会落库、同步权限发布，并通知被取消权限的用户

004 的操作：
- 确认取消：执行取消授权
- 返回重选：回到 003 或重新触发 003，具体实现选更简单的方式
- 取消：把当前卡片替换为不可操作状态，让旧卡不能继续提交

### 5.4 多权限取消

003 和 004 都不做多选。

管理员如果要取消多个权限，就重复多次操作：
1. 在审批群 `@Bot 取消授权`
2. 在 003 单选一个用户-公司-职能组合
3. 在 004 确认取消内容
4. 收到文字结果
5. 如需继续，再次触发

这样做的好处是每次取消结果更清楚，也更容易审计。

### 5.5 取消后的文字通知

管理员收到文字结果：
- 被取消权限的用户
- 被取消的公司
- 被取消的职能
- 权限落库结果
- 权限发布同步结果
- 用户通知结果
- 该用户当前剩余权限

被取消权限的用户收到文字结果：
- 哪个公司权限被取消
- 哪个职能权限被取消
- 当前还剩哪些权限
- 如有疑问联系管理员

如果本次取消时发现权限已不存在，直接文字提示管理员：这项权限已经不存在，无需重复取消。

## 六、生命周期

需要生命周期的卡片：

| 卡片 ID | TTL | 到期动作 |
|---|---|---|
| 001 | 2 小时 | 拦截点击，文字提示重新发送“申请权限”获取新卡 |
| 003 | 2 小时 | 拦截点击，文字提示重新在审批群 `@Bot 取消授权` |
| 004 | 2 小时 | 拦截点击，文字提示重新在审批群 `@Bot 取消授权` |

文字通知不需要生命周期。

## 七、当前代码差异

当前代码与本草案不一致的地方：

| 当前实现 | V2 目标 |
|---|---|
| 用户私聊按状态自动回复申请卡或状态卡 | 只有私聊“申请权限”才返回 001 |
| 已通过用户先收到“申请更多授权”状态卡 | 已通过用户发送“申请权限”后直接收到 001 |
| 表单提交后进入二次确认卡 | 表单提交后直接进入审批流，并文字通知已提交 |
| 提交成功、审批成功、退回、收权结果多处使用无按钮卡片 | 无按钮内容统一改为文字通知 |
| 管理员入口是审批群 @Bot 后弹菜单 | 审批群 `@Bot 取消授权` 直接弹 003 |
| 管理员私聊/旧命令可能触发收权入口 | 私聊不弹 003 |
| 管理员取消授权拆成选用户、选范围、最终确认多张卡 | 003 选择用户-公司-职能组合，004 二次确认后执行 |
| 用户收权通知是文字消息 | 继续保持文字消息，但内容补充当前剩余权限 |

## 八、后续施工原则

1. 先改测试，再改代码。
2. 只保留 4 张可操作卡片。
3. 无按钮结果一律文字通知。
4. 公司和职能选项共用同一个配置来源。
5. 入口严格按路由触发：私聊“申请权限”、审批群 `@Bot 取消授权`。
6. 重复申请不做复杂拦截，合法就进审批。
