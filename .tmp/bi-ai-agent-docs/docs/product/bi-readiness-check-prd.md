# BI Agent 统一巡检 PRD

> 日期：2026-06-26
> 状态：待实现
> 范围：把现有 MCP 指标目录快照、准入健康检查和新增数据新鲜度检查收敛成一个用户可感知的巡检结果。本文件只定义产品目标和用户体验，不代表已实现。

## 一、背景

线上现在已经有两段自动循环：

| 线上循环 | 当前作用 |
|----------|----------|
| `bi-metric-snapshot.timer` | 每小时用全量账号抓 MCP 当前可见指标目录 |
| `bi-admission-health-check.timer` | 每小时读取指标目录快照，检查新指标、删指标、指标未分配职责、用户 token 和权限发布副本异常 |

这两段不是重复任务，而是“采集原料”和“做准入判断”的前后关系。

但用户和管理员真正关心的是一件事：

```text
BI Agent 现在能不能可靠查数？
```

现状缺一块关键能力：**数据新鲜度巡检**。例如 2026-06-26 线上只读核查发现，5 个日指标最新数据停在 2026-06-24；现有准入巡检仍会显示“无异常”，因为它只知道指标存在、权限配置正常，不知道业务数据是否断更。

## 二、目标

把三类检查合成一个用户可理解的“BI Agent 数据可用性巡检”：

1. 指标目录：MCP 当前暴露哪些指标，有没有新增、删除、描述变化。
2. 准入状态：已获批用户是否具备可用 token、权限展开、权限发布副本。
3. 数据新鲜度：各指标最新数据到哪一天或哪一月，是否超过允许延迟。

最终审批群或运维群看到一条统一摘要：

```text
BI Agent 巡检

指标目录：正常，当前 7 个指标
权限准入：正常
数据新鲜度：异常

日指标最新到 2026-06-24，已落后 2 天：
- 新增用户数
- 充值用户数
- 充值金额
- 扣费用户数
- 扣费金额

建议动作：联系数据/MCP 侧确认 ETL 或上游同步状态；当前不要向用户承诺 2026-06-25 以后日数据可查。
```

## 三、成功标准

- 线上只保留一个用户可感知的巡检结果，不再让管理员理解两个 timer 的内部关系。
- 巡检消息同时回答：
  - 现在有多少指标；
  - 权限准入有没有异常；
  - 日指标最新到哪天；
  - 月指标最新到哪个月；
  - 哪些问题需要人工处理。
- 数据新鲜度异常必须能在审批群或指定运维群中被看见。
- “无异常”必须只在三类检查都通过时出现；不能再出现“准入无异常但数据实际断更”的误导。
- 旧的指标目录快照和准入检查能力不丢失，只是统一入口和统一展示。
- 本期只读巡检，不自动修复数据、不自动放权、不自动重启 MCP。

## 四、用户角色

| 角色 | 关心的问题 |
|------|------------|
| 审批群管理员 | 用户是否会因为权限配置问题查不到数 |
| 业务负责人 | 当前 BI 指标是否可用，是否需要解释数据延迟 |
| 运维/开发 | 是 MCP 指标目录问题、权限发布问题，还是上游数据断更 |
| 普通用户 | 不直接看到巡检细节，但能减少“问了今天数据却没有结果”的困惑 |

## 五、产品范围

本期做：

- 统一巡检入口。
- 保留现有指标目录检查。
- 保留现有准入健康检查。
- 新增数据新鲜度检查：
  - 日指标：检查最新有数据日期；
  - 月指标：检查最新有数据月份；
  - 支持按指标设置默认延迟阈值；
  - 默认只做小窗口聚合查询，避免拉大表。
- 统一飞书消息：
  - 无异常时可静默或按手工参数强制发摘要；
  - 有异常时一条消息按模块分段；
  - 数据新鲜度异常优先展示用户影响。
- 文档和进度看板标记。

本期不做：

- 不直接修改 MCP 服务端。
- 不直接连接生产数据库。
- 不绕过 MCP 执行 SQL。
- 不把行为审计并入本巡检；审计仍归 `bi-agent-audit` 项目。
- 不处理“用户具体问法是否回答正确”，那属于 Benchmark 和对话体验治理。
- 不实现数据修复、ETL 重跑或 MCP 重启。

## 六、巡检结果分级

| 状态 | 含义 | 用户影响 |
|------|------|----------|
| `ok` | 三类检查都正常 | 可以继续对外说明 BI Agent 当前可用 |
| `warning` | 有轻微延迟或高权限复核提醒 | 不一定阻塞使用，但需要关注 |
| `failed` | 指标目录、准入或数据新鲜度存在明确异常 | 不应对用户承诺完整可用 |
| `unknown` | 巡检自身失败或 MCP 查询失败 | 不能判断当前状态，需要先恢复巡检 |

状态合成规则：

- 任一子检查 `failed`，总状态为 `failed`。
- 无 `failed` 但存在 `warning`，总状态为 `warning`。
- 任一关键阶段 `unknown`，总状态为 `unknown`，不得输出“无异常”。关键阶段包括指标目录整体失败、准入检查整体失败、全部数据新鲜度不可判定。单个新增指标缺周期配置只作为 `warning`。
- 只有全部 `ok` 才输出整体正常。

## 七、数据新鲜度口径

### 7.1 当前指标分组

| 指标 | 中文名 | 期望周期 | 默认口径 |
|------|--------|----------|----------|
| `sub_new_count` | 新增用户数 | 日 | 最新有数据日期 |
| `sub_recharge_count` | 充值用户数 | 日 | 最新有数据日期 |
| `sub_recharge_money` | 充值金额 | 日 | 最新有数据日期 |
| `sub_deduction_count` | 扣费用户数 | 日 | 最新有数据日期 |
| `sub_deduction_money` | 扣费金额 | 日 | 最新有数据日期 |
| `exchange_rate` | 汇率 | 月 | 最新月份 |
| `vat_rate` | 增值税率 | 月 | 最新月份 |

第一版可以把周期配置写在应用内或配置文件中；后续若 MCP `describe_metric` 能稳定返回周期，再迁到 MCP 元数据。

### 7.2 默认阈值

| 指标类型 | 默认报警阈值 | 达到阈值后的状态 |
|----------|--------------|------------|
| 日指标 | 2 天 | `failed` |
| 月指标 | 当前月或上月，按业务约定配置 | `warning` 或 `failed` |

默认阈值不是业务承诺，只是巡检报警线。日指标第一版按 `lag_days >= max_lag_days` 判定异常，因此 2026-06-26 看到最新日期仍停在 2026-06-24 时应报 `failed`。具体指标是否应 T+1、T+2 或月初第几天更新，需要后续和数据/MCP 团队确认。

## 八、飞书消息体验

### 8.1 正常摘要

默认自动巡检无异常时可以静默。手工执行或强制通知时输出：

```text
BI Agent 巡检无异常

指标目录：7 个指标
权限准入：无异常
数据新鲜度：
- 日指标最新到 2026-06-24
- 月指标最新到 2026-06

巡检时间：2026-06-26 09:05
```

### 8.2 异常摘要

```text
BI Agent 巡检发现 1 类异常

数据新鲜度异常
5 个日指标最新只到 2026-06-24，已落后 2 天：
- 新增用户数
- 充值用户数
- 充值金额
- 扣费用户数
- 扣费金额

用户影响：
用户查询 2026-06-25 或 2026-06-26 的日指标时，可能查不到数据或得到空结果。

建议动作：
联系数据/MCP 侧确认 ETL 或上游同步；对外说明当前日指标最新到 2026-06-24。
```

### 8.3 多类异常

多类异常按用户影响排序：

1. 数据新鲜度异常。
2. 权限准入异常。
3. 指标目录变化。
4. 高权限复核提醒。

原因：用户问数直接受数据断更影响最大；权限异常影响特定用户；指标目录变化通常需要管理员决策。

## 九、和现有巡检的关系

| 能力 | 现状 | 目标 |
|------|------|------|
| 指标目录快照 | 独立 timer | 并入统一巡检的采集阶段 |
| 准入健康检查 | 独立 timer | 并入统一巡检的准入阶段 |
| 数据新鲜度 | 缺失 | 新增为统一巡检的数据阶段 |
| 审计行为巡检 | 独立 audit 项目 | 不合并 |

目标不是删除已有能力，而是让用户只理解一个“BI Agent 巡检”。

## 十、验收标准

- 构造指标目录新增/删除时，统一巡检能在“指标目录”段展示。
- 构造 approved 用户缺 token 或权限发布副本缺行时，统一巡检能在“权限准入”段展示。
- 构造日指标最新数据达到或超过阈值时，统一巡检能在“数据新鲜度”段展示，并列出受影响指标。
- MCP 查询失败时，总状态为 `unknown` 或 `failed`，不得输出“无异常”。
- 自动巡检默认只在有异常时通知；手工强制执行可输出完整摘要。
- 现有 admission health 的测试用例仍能覆盖旧规则；新增测试覆盖数据新鲜度和总状态合成。

## 十一、开放问题

- 日指标默认延迟阈值最终是 T+1、T+2 还是按指标配置，需要数据/MCP 团队确认。
- 月指标在月初第几天视为应更新，需要业务确认。
- 数据新鲜度异常通知发审批群、运维群还是两者都发，需要产品确认。
- 是否需要把最近一次成功巡检结果展示给普通用户，目前暂不做。
