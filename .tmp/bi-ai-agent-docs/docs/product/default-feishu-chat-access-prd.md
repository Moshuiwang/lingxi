# 默认飞书聊天权限与高级工作台可选开通 PRD

> 日期：2026-06-25
> 状态：待实现
> 范围：定义未来用户申请时“默认开通飞书聊天权限、可选开通高级数据分析工作台”的产品改造。JumpServer 登录迁移不在本文展开，见 `docs/product/jumpserver-access-migration-prd.md`。

## 一、当前事实

当前实现里，用户申请通过后，**飞书聊天并不是默认开通的权限**。

现有开户把两件事绑在一起了：

- 系统创建 EC2 Linux 用户；
- 系统准备 SSH/工作台登录材料；
- 用户通过终端或后续 JumpServer 进入机器；
- 在机器上运行 `claude` 做分析。

未来不再把“后台运行身份”和“用户可见工作台入口”混为一谈。普通用户最容易理解、也最适合日常使用的入口应该是飞书聊天；系统内部仍可以为他准备专属 Linux / Claude / Codex 运行环境，用于会话延续、经验沉淀和审计。

## 二、产品目标

未来用户申请后，默认开通的是：

```text
飞书聊天权限
```

只有用户主动选择额外能力时，才开通：

```text
高级数据分析工作台
```

产品原则：

- 飞书聊天是默认入口，适合日常问数、看趋势、拿分析结论；
- 飞书聊天不是可选项，而是审批通过后必开的基础能力；
- 高级工作台是额外入口，适合持续、深度、可沉淀、可复用 skill 或自动发送类任务；
- 高级工作台默认不开，只有用户在申请表里主动选择时才进入后续准备；
- 高级工作台不是更高数据权限，而是更重的使用方式；
- 用户没有选择高级工作台时，不应该收到 SSH、EC2、JumpServer、工作目录相关提示；
- 用户没有选择高级工作台时，系统仍可准备后台专属运行身份，但这个身份不作为用户可见登录入口；
- 高级工作台开通进度不能阻塞用户先使用飞书聊天。

2026-06-26 产品确认：

- 用户第一次私聊 Bot 申请权限时，不出现“选择入口类型”页面。
- 用户直接进入公司/职能申请表。
- 飞书聊天作为默认必选能力，不给用户勾选或取消。
- 表单里只询问“是否额外开通高级数据分析工作台”，默认不开通。
- 审批人整体审批用户这次申请，要么通过，要么拒绝，不拆成“飞书聊天通过、高级工作台拒绝”的分段审批。
- 只开通飞书聊天的用户，审批通过后在原私聊继续追问，不跳转到单独入口。
- 不提供单独的“申请高级工作台”入口；高级工作台只作为申请表里的附加项。

## 三、给用户的说明口径

建议用户说明文档这样表达：

```text
默认开通飞书聊天权限，适合日常问数、看趋势和获取分析结论。

如果你需要持续、深度的分析工作台，例如沉淀分析过程、复用 skill、长期跟进专题或未来配置自动发送任务，可以额外申请高级数据分析工作台。
```

入口选择：

| 用户场景 | 推荐入口 | 用户理解 |
|---|---|---|
| 基于当前已接入指标问数、看趋势、要一段解释 | 飞书聊天 | 最简单，直接问，直接拿结果 |
| 想把分析结论快速转发给同事或群 | 飞书聊天 | 适合协作和移动端 |
| 不想进入服务器、不熟悉终端 | 飞书聊天 | 不需要理解 JumpServer、SSH、工作目录 |
| 持续跟进一个专题，反复追问和补充分析 | 高级数据分析工作台 | 适合长任务 |
| 希望沉淀分析过程、复用 skill 或工作文件 | 高级数据分析工作台 | 适合个人工作区 |
| 希望未来做定时/持续自动发送类任务 | 高级数据分析工作台 | 适合更深度的自动化能力 |

必须强调：

- 高级工作台不是更高权限的数据入口；
- 飞书和高级工作台能看到的数据都受同一套 BI/MCP 权限控制；
- 飞书查不到的数据，不应通过高级工作台绕过权限；
- 不确定选哪个入口时，默认先用飞书。

## 四、用户用例

飞书就可以完成的例子：

```text
我想看一下昨天肯尼亚充值收入，比上周同一天涨跌多少？如果下降，主要是哪几个指标拖累？
```

适合原因：

- 问题基于当前已接入的数据指标；
- 用户要的是快速结果和解释；
- 结果可以直接在飞书里转发或继续追问；
- 不需要进入个人工作区沉淀过程。

需要高级工作台的例子：

```text
我想持续跟进尼日利亚新增用户质量下降的问题，后面几天都要围绕注册、激活、付费、留存和渠道结构持续分析，并沉淀分析过程，后续还希望复用 skill 或自动发送固定分析。
```

适合原因：

- 这是一个持续性专题，不是一次问答；
- 需要保留中间过程、文件或分析上下文；
- 可能需要反复使用同一套分析能力；
- 更像分析师在自己的工作台里长期处理一个任务。

## 五、对申请流程的影响

申请表单需要从“默认开通高级工作台”改为“直接申请 BI 权限，飞书聊天默认必开，高级工作台可选”。

用户基础信息仍只填写：

- 姓名；
- 工作邮箱；
- 申请公司；
- 职能；
- 说明。

表单里不出现“是否开通飞书聊天”，只增加一个用户能理解的附加项：

```text
是否额外申请高级数据分析工作台？
```

选项文案建议：

| 选项 | 默认 | 用户说明 |
|---|---|---|
| 飞书聊天权限 | 必开，不可取消 | 适合日常问数、看趋势、获取分析结论 |
| 高级数据分析工作台 | 默认不开，用户主动选择 | 适合持续深度分析、沉淀过程、复用 skill、未来自动发送任务 |

高级工作台选项后面可以要求用户补一句用途说明，但不要让用户填写 JumpServer、SSH key、EC2 用户名这类技术字段。

## 六、对审批流程的影响

审批卡需要让审批者清楚看到本次申请包含哪些能力，但审批操作仍是整体通过或拒绝：

| 权限层 | 审批者看到的含义 |
|---|---|
| 飞书聊天权限 | 用户可在飞书里问数、看趋势、获取分析结论 |
| 高级数据分析工作台 | 用户还需要可登录入口做持续深度分析，后续涉及登录材料交付和 JumpServer 授权 |

审批卡建议文案：

```text
基础能力：飞书聊天权限（审批通过后默认开通）

附加能力：高级数据分析工作台（用户已申请 / 未申请）

审批通过后：系统按本次申请整体开通；系统会准备用户专属 AI 运行环境。若包含高级工作台，会继续交付登录入口和 JumpServer 授权待办。
```

审批者需要知道：

- 未申请高级工作台，不应该触发 JumpServer 登录材料；
- 批准高级工作台，不等于用户马上能在 JumpServer 看到机器；
- 审批结果不拆分为两段：审批人要么通过本次申请，要么拒绝本次申请；
- 如果高级工作台后续准备或 JumpServer 授权有等待，不影响用户先在飞书私聊继续使用基础能力。

## 七、对执行流程的影响

未来建议把开通状态拆成四层：

| 层级 | 含义 | 用户/审批群表达 |
|---|---|---|
| 飞书聊天权限 | 用户可在飞书里和 BI AI Agent 对话 | “飞书聊天已开通” |
| 数据权限 | SQLite 授权、MCP token、多维表格发布完成 | “可查询指标已开通” |
| 后台 AI 运行环境 | EC2 Linux 用户、Claude/Codex session、MCP 工作区配置已准备 | “后台运行环境已准备” |
| 高级工作台 | 用户可见登录入口和个人工作台材料 | “高级工作台已交付 / 未申请” |
| JumpServer 访问 | 用户在 JumpServer 中能看到并进入目标机器 | “JumpServer 访问已开通 / 待运维开通 / 未申请” |

对只申请飞书聊天的用户：

- 创建专属 EC2 Linux 运行身份，用于 Claude/Codex 会话、经验沉淀和审计；
- 可以生成服务端所需 SSH key / MCP 配置，但不向用户交付登录材料；
- 不发送 JumpServer 指引；
- 开通飞书聊天可用所需的数据权限、MCP token 和私聊 entitlement。

对申请高级工作台的用户：

- 先保证飞书聊天不被阻塞；
- 再交付可登录工作台材料；
- 再触发 JumpServer 授权流程，或给运维团队产生明确待办。

## 八、对用户通知的影响

默认飞书聊天开通后，通知应表达：

- “你的 BI AI Agent 飞书聊天权限已通过”；
- “可以直接在飞书里问数、看趋势和获取分析结论”；
- “如果需要持续深度分析工作台，可额外申请高级数据分析工作台”。

未申请高级工作台的用户，不应收到：

- SSH 私钥 ZIP；
- ZIP 解压口令；
- EC2 主机、端口、私钥说明；
- JumpServer 登录教程；
- `claude` 或 `~/bi-agent-work` 说明。

## 九、后续补开高级工作台

用户可以先只使用飞书聊天。后续是否允许补开高级工作台，本轮不新增单独入口。

若未来要补开，应复用现有申请表或由管理员引导，不在“已开通状态”里新增单独“申请高级工作台”入口。

本轮实现只保证：

- 新用户第一次申请时可以选择是否额外申请高级工作台；
- 未选择高级工作台的用户不会收到高级工作台材料；
- 不新增单独的高级工作台申请入口。

## 十、停用和回收

禁用用户时需要区分飞书聊天和高级工作台。

未来停用应包含：

- BI Agent 用户状态禁用；
- 飞书聊天权限停用；
- 数据权限发布为空或 disabled；
- 如果用户开通过高级工作台，EC2 目标账号封锁；
- 如果用户开通过高级工作台，JumpServer 资产授权回收。

## 十一、后续实现任务包

### 任务 A：申请表单改造

目标：

- 新用户申请默认开通飞书聊天权限；
- 用户可以额外选择是否申请高级数据分析工作台；
- 申请表不要求用户先选择入口类型。

验收：

- 不选择高级工作台的用户，审批通过后可以直接在飞书聊天使用；
- 不选择高级工作台的用户，不收到 SSH、EC2、JumpServer 登录材料；
- 飞书聊天不可取消，高级工作台默认不开。

### 任务 B：审批卡改造

目标：

- 审批者能看到用户是否申请高级工作台；
- 审批者整体通过或拒绝本次申请，不做分段审批；
- 高级工作台未准备好时，不影响用户先使用飞书聊天。

验收：

- 审批者能理解高级工作台只是本次申请的附加项；
- 审批者不会把基础飞书聊天权限和高级工作台混在一起；
- 审批群能看到高级工作台是否申请、是否进入后续准备或待处理。

### 任务 C：执行状态重定义

目标：

- 把当前 `ssh_delivery_status` 从“账号是否存在”调整为“登录材料是否交付”；
- 未申请高级工作台仍准备后台运行身份，但不触发 JumpServer 授权、不发送 JumpServer 指引；
- 审批群能看到飞书聊天是否已开通、高级工作台是否申请。

验收：

- 只申请飞书聊天的用户，收到的是飞书聊天可用指引；
- 额外申请高级工作台的用户，才进入高级工作台准备流程；
- 不发送无意义的 ZIP 口令。

### 任务 D：帮助文档和用户说明

目标：

- 用户帮助文档说明飞书聊天和高级工作台的区别；
- 新帮助文档优先覆盖飞书聊天默认路径；
- 高级工作台帮助文档链接到 JumpServer 迁移文档对应内容。

验收：

- 新用户知道日常问数和当前指标分析优先用飞书聊天；
- 新用户知道持续、深度、可沉淀、可复用 skill 或自动发送类任务适合高级工作台；
- 新用户知道高级工作台不是更高权限的数据入口。

## 十二、暂不做

本文件只固定产品目标和任务包，不立即要求：

- 不修改代码；
- 不承诺当前已经实现默认飞书开通；
- 不设计 JumpServer 具体登录教程；
- 不承诺 JumpServer API 已可用。

## 十三、成功标准

改造完成后，普通用户的体验应是：

- “我在飞书申请权限”；
- “我不需要选择入口类型，也不需要理解飞书聊天是否可选”；
- “默认审批通过后，我可以直接在飞书里问数和看分析”；
- “如果我额外申请高级数据分析工作台，才需要看高级工作台/JumpServer 文档”；
- “如果我没有申请高级工作台，就不会收到 SSH、EC2、JumpServer 登录材料”。

管理员的体验应是：

- 能清楚区分飞书聊天权限、数据权限、高级工作台、JumpServer 授权四层状态；
- 能整体通过或拒绝用户本次申请，同时让用户先用飞书聊天，不被高级工作台准备进度阻塞；
- 停用用户时能按需收回飞书聊天权限、高级工作台、EC2 登录和 JumpServer 资产权限。
