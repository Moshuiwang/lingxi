# Codex 私聊机器人 PRD

> 日期：2026-06-13
> 状态：历史归档。产品已决定不再提供 Codex；当前飞书查询只保留 Claude 路径（2026-07-22）。下文不是当前生产部署、验收或排障指引。
> 范围：在现有 BI AI Agent 飞书机器人内，新增仅王志鹏可用的 Codex 私聊能力；本次 PR 在私聊主链上支持“人类主动打开的飞书原生话题”，不新增群聊 Codex 触发。

## 一、产品目标

让王志鹏可以直接在飞书私聊现有 BI AI Agent 机器人，像和 Codex 聊天一样持续对话，并看到回复逐步出现。

第一版不是新建机器人，也不是简单 webhook 机器人，而是在当前已部署的 BI AI Agent 机器人路由里新增一个受控入口：

- 只有王志鹏本人进入 Codex 对话能力。
- 其他用户继续走原有机器人消息路由，不因为这个新能力改变体验。
- 当前隐藏 Codex 私聊申请入口；未来再开放给用户申请。
- 机器人在飞书里输出原生流式卡片，用户看到“打字机效果”，不是等全部生成完再发一整段。
- 会话有明确 session 绑定，不使用 `resume --last`。

本次 PR 增量目标：

- 普通私聊主窗口体验保持不变。
- 如果王志鹏在私聊里使用飞书原生“回复/话题”能力，Bot 把该飞书话题映射为独立 Codex 会话。
- Bot 不主动创建飞书话题；只有人类用户先开话题，Bot 才进入该话题上下文。
- 不在群聊里新增 `@Bot` 触发 Codex 的能力。
- 流式卡片体验改为“状态区 + 回答区 + 明确完成态 + 低频计时”，减少过程日志对最终回答的干扰。

## 三、权限与开放策略

当前阶段采用隐藏白名单：

- 王志鹏直接拥有“含上下文 Codex 私聊”权利。
- 飞书里不展示“申请 Codex 私聊”的入口。
- 其他用户发送任何消息，都按原 BI AI Agent 路由处理。
- 其他用户不会收到“你没有 Codex 权限”这类提示，避免暴露尚未开放的能力。

未来开放时，产品路径可以扩展为：

1. 用户私聊机器人，说“申请 Codex 私聊”或点击入口。
2. 机器人展示申请卡片，说明能力边界、可执行命令风险和使用责任。
3. 管理员审批。
4. 审批通过后，用户获得 Codex 私聊权利。
5. 用户开始使用 `/new` 和普通对话。

第一版只做架构和数据预留，不开放这个申请入口。

## 四、核心用户路径

### 4.1 开始新会话

1. 王志鹏私聊机器人发送 `/new`。
2. 机器人创建一个新的 Codex 工作线程。
3. 机器人回复普通文本：“已开始新的 Codex 会话。”
4. 后续普通消息进入这个新会话。

第一版只保留 `/new` 一个显式命令。

### 4.2 持续追问

1. 王志鹏私聊机器人发送问题。
2. 机器人先发一个 emoji 响应，让用户知道消息已被接住。
3. 机器人发出一张“思考中...”的流式卡片。
4. Codex 开始处理问题。
5. 飞书卡片里的回答逐步出现。
6. 生成结束后，卡片关闭流式状态，聊天列表不再显示“生成中”。
7. 王志鹏继续发下一条消息，机器人带着同一个 Codex session 的上下文继续回答。

### 4.3 执行本机命令

Codex 可以直接执行本机命令。用户体验上不额外弹确认，除非命中危险操作。

危险操作需要二次确认，但第一版按实现能力分阶段：

- 最小上线版：Codex 运行在后端配置的安全策略内，后端不承诺拦截 `codex exec --json` 进程内部已经开始执行的命令。
- 可交付确认版：只有当 Codex runner 能在命令执行前拿到明确的 pending approval / tool-call 事件时，才展示确认卡片并等待王志鹏确认。
- 如果当前 runner 无法拦截危险操作，危险确认卡片不得标记为已完成能力；上线前必须选择更强的 runner 形态（例如 app-server delta/tool event）或调整 Codex CLI 的审批策略。

确认卡片和生成中卡片分开处理，避免流式卡片期间交互回调无法立即更新的问题。

## 五、私聊与飞书原生话题

本能力仍然定位为私聊能力。本次只把飞书私聊里的原生话题作为可选上下文边界，不做群聊 Codex。

私聊会话边界采用“当前活跃会话”：

- `/new` 创建新会话，并切换为当前活跃会话。
- 普通消息进入当前活跃会话。
- 如果没有当前会话，第一条普通消息自动创建会话。

这样用户不需要理解 thread_id、message_id 或 session_id。

飞书原生话题会话边界采用“一个话题一个 Codex 会话”：

- 用户在私聊主窗口直接发消息：继续使用 `private_chat` 当前活跃会话。
- 用户对私聊里的某条消息使用飞书原生“回复/话题”：使用 `feishu_thread` 会话。
- 同一个飞书话题内连续追问：复用同一个 Codex session。
- 不同飞书话题：上下文互相隔离。
- 话题里不支持 `/new`；用户发送 `/new` 时，Bot 只提示“话题里不用 /new；请新开一个飞书话题开始新上下文。”。
- Bot 回复必须回到同一个飞书话题，不能散到私聊主窗口。
- 只有消息明确带 `thread_id` 时才进入飞书话题 Codex 会话；单独的 `root_id` / `parent_id` 可能只是普通引用回复，不得触发话题或 `reply_in_thread=true`。
- 如果同一个飞书话题消息同时带 `thread_id` 和 `root_id`，系统可以把 `root_id` 作为别名辅助查找，但不能用单独 `root_id` 主动创建话题会话。
- 话题里如果上一条 Codex 还在处理，忙碌提示也必须回到同一个话题。

## 六、不做群聊 Codex

本次不做群聊内 Codex 触发。原因：

- 当前线上事实是正式 Codex 入口只在私聊；群聊只在审批群/测试群处理管理命令，且必须 `@Bot`。
- 群聊 Codex 会引入权限、多人插话、公开上下文和审批群噪音问题，不进入本次 PR。
- 没有明确触发条件的群消息不得触发 Codex。
- 非授权用户仍走原 BI AI Agent 路由或静默，不暴露 Codex 能力。

## 七、流式输出体验

第一版使用飞书 CardKit v1 原生流式更新卡片。

私聊主窗口已验证的用户体验：

- 机器人先发送一张 CardKit 卡片。
- 卡片开启 `streaming_mode`。
- 后端持续把“完整回答文本”更新到卡片中的 markdown 元素。
- 飞书客户端自动计算新增内容，并以打字机效果逐字渲染。
- 生成结束后关闭 `streaming_mode`。

这不是普通消息编辑，也不是分段发送多条消息。

本次体验优化：

- 卡片展示拆成“状态区”和“回答区”。
- 状态区只显示短状态和低频计时，例如“正在处理 · 18 秒”。
- 回答区只展示最终面向用户的回答，不把大段过程日志和结论混在一起。
- 完成时状态改为“已完成 · 用时 42 秒”，再关闭流式模式。
- 如果长时间无新回答，后台低频刷新计时，让用户知道 Bot 仍在处理。
- 不做每秒刷新，避免飞书 API 压力和限流风险。

飞书话题里的 CardKit 流式支持需要真实 smoke：

- 飞书回复消息接口支持 `reply_in_thread=true` 和卡片消息。
- CardKit 支持创建、更新、关闭流式卡片。
- 但“reply 到话题里的 CardKit 卡片是否能稳定继续流式更新”必须用测试机器人真实验证。
- 如果话题内流式不可用，本次仍必须保证普通文本兜底回复在同一个话题内。

技术验证证据：

```text
create 0 success 7650544048899214522
send 0 success om_x100b6df75a4174a0c1bcd2bce9fe74d
content 1 0 success
content 2 0 success
content 3 0 success
close 0 success
```

官方文档：`https://open.feishu.cn/document/cardkit-v1/streaming-updates-openapi-overview`

## 八、命令范围

第一版只做：

| 命令 | 用户看到 |
|---|---|
| `/new` | 开启一个新的 Codex 会话 |

补充：`/new` 只在普通私聊主窗口生效。飞书原生话题里不支持 `/new`，也不需要 `/new`。

第一版不做：

- Codex 私聊申请入口
- `/forget`
- `/summary`
- `/sessions`
- 群聊 Codex 触发
- Bot 主动创建飞书话题
- 多用户共享会话
- 手动选择历史 session

## 九、失败体验

| 场景 | 用户看到 | 系统处理 |
|---|---|---|
| Codex 启动失败 | “Codex 启动失败，请稍后重试。” | run 标记失败，保留用户消息 |
| Codex 卡住 | 卡片显示“仍在处理中”，超时后给出失败提示 | 超时终止本次 run，不切断 session |
| Codex 生成失败 | 卡片更新为失败说明 | 保存错误原因摘要 |
| 飞书流式更新失败 | 当前卡片停止更新，发送一条普通文本兜底 | run 继续记录，但标记 streaming_failed |
| 关闭流式模式失败 | 收到完整普通文本兜底 | stream 标记失败，保留最终答案 |
| 话题内 CardKit 流式不可用 | 同话题收到普通文本回答 | 不把回复发散到私聊主窗口 |
| 添加 emoji 反应失败 | 用户不感知；主回复继续进行 | 记录 warning，不影响 Codex run |
| 会话恢复失败 | “上次会话恢复失败，已为你新建会话。” | 不使用 `resume --last`，新建明确 session |
| 危险命令待确认 | 看到确认卡片 | 点击确认后继续；取消则停止 |

## 十、第一版不做什么

- 不支持除王志鹏外的用户使用 Codex 私聊。
- 不展示 Codex 私聊申请入口。
- 不支持群聊 Codex 触发。
- 不由 Bot 主动创建飞书话题。
- 不在飞书话题中支持 `/new`。
- 不支持普通用户看到“无权限”提示。
- 不把 BI AI Agent 改造成全员通用聊天机器人。
- 不使用 `resume --last`。
- 不把 Codex session 只存在内存里。
- 不依赖普通消息编辑模拟流式输出。
- 不在流式卡片上直接处理危险命令确认。

## 十一、成功标准

1. 王志鹏私聊机器人发送普通问题，能收到逐步出现的流式回答。
2. 同一私聊连续追问，Codex 带上下文回答。
3. `/new` 后上下文切到新会话。
4. 数据库能看到飞书私聊 / 飞书话题和 Codex session 的明确绑定。
5. 任何后端恢复逻辑都不使用 `resume --last`。
6. 无权限用户仍走原有机器人路由。
7. 危险操作出现确认卡片，不直接执行。
8. 生成结束后流式卡片不再停留在“生成中”。
9. 飞书里没有对普通用户暴露 Codex 私聊申请入口。
10. 同一飞书话题连续追问复用同一个 Codex session。
11. 不同飞书话题上下文隔离。
12. Bot 在话题里的回复必须回到同一个话题。
13. 群聊不新增 Codex 触发能力。
14. 卡片结束态明确展示“已完成 / 用时”，用户能判断本轮已结束。

其中第 7 条是上线闸门：如果第一版选择 `codex exec --json` 且无法在命令执行前拦截危险操作，则不能宣称危险确认能力已完成，必须在开发阶段改用可拦截 runner 或限制 Codex 执行策略。
