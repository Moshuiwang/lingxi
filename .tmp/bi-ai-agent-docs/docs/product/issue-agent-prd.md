# GitHub Issue AI 施工 Agent PRD

> 版本：0.1
> 日期：2026-06-14
> 状态：历史方案；2026-07-09 已暂停，不作为当前开发入口
> 首个接入项目：BIAIAgent
> 产品定位：可复用到多个仓库的 AI 施工自动化能力

> 2026-07-09 产品决策：Issue Agent 暂停使用；后续只恢复了与 Issue Agent 无关的无密钥测试 CI，仍不启用自动施工、自动合并或自动部署。稳定协作边界见 `docs/ops/repository-host-migration.md`，工作状态见 GitHub Project / Issues。

---

## 一、目标

建设一个可以定时扫描 GitHub Issue 的 AI Agent。它先判断 issue 是否具备施工条件，再在满足门禁后自动完成分支、文档、测试、代码、PR，并通过飞书卡片让负责人审批合并和部署。

第一版的用户体验目标是：

- 产品经理不用频繁打开 GitHub 查 issue。
- AI 能主动告诉产品经理：哪些 issue 可以做，哪些缺信息。
- 符合条件的 issue 可以自动变成 ready PR。
- 产品经理只需要在飞书卡片里批准关键动作。
- 所有代码改动仍然保留 GitHub PR、CI、合并和部署留痕。

本能力不是 BIAIAgent 专用功能，而是一个可复用的 Issue-to-PR Agent。BIAIAgent 只是第一个实施项目。

## 二、第一版范围

### 2.1 做什么

第一版做以下能力：

1. 每 10 分钟扫描已接入仓库的 GitHub issues。
2. 对新 issue 做 AI 分诊。
3. 判断 issue 类型、风险、缺少哪些前置条件。
4. 自动评论 issue，说明当前缺口或建议进入 AI 施工。
5. 通过飞书卡片请产品经理确认是否允许施工。
6. 产品经理确认后，系统给 issue 打 `ai-ready`。
7. 施工 Agent 只处理 `ai-ready` issue。
8. 自动创建分支和隔离工作区。
9. 按需补充 PRD、架构、数据、接口等文档。
10. 写测试、改代码、跑测试。
11. 创建 ready PR。
12. 通过飞书卡片请求产品经理批准合并。
13. 产品经理批准后，系统检查 PR 状态和 CI，再自动合并。
14. 合并后等待人工受控发布；旧飞书部署审批已停用。
15. 替代发布入口确定前不自动部署。
16. 发布后发送上线结果和 smoke 结果。

### 2.2 MVP 交付方式

第一版 MVP 一次性交付完整 A/B/C 闭环，不拆成多次人工确认后再继续开发：

| 层级 | 能力 | 用户能看到什么 | 是否产生真实影响 |
|------|------|----------------|------------------|
| MVP-A | EC2 定时扫描、dry-run、指定 issue write smoke | dry-run 只看运行日志；write smoke 会在 GitHub 留评论，并向产品经理发飞书施工审批卡 | write smoke 只允许处理指定 issue |
| MVP-B | `ai-ready` 后自动施工、开分支、调用 Codex、跑测试、创建 ready PR | GitHub 出现 `codex/issue-*` 分支和 ready PR；飞书收到 PR 合并审批卡 | 只改 feature branch，不碰 main |
| MVP-C | 飞书批准合并后检查 PR/CI/head_sha，再合并；合并后交给人工受控发布 | PR 合并后不再发送旧部署确认卡 | 替代发布入口确定前不自动部署 |

MVP 可以一次性开发完整代码，但真实动作必须由系统自检和审批门禁控制。当前实现保留 `ai-ready` 施工放行和 PR 合并审批；旧部署审批已停用。后续若要进一步减少人工参与，应先把清晰低风险 issue 的施工放行改成策略自动化；需求不清或风险异常时仍必须请求人工确认。

### 2.3 运行模式

| 模式 | 入口 | 行为 | 适用场景 |
|------|------|------|----------|
| `dry-run` | EC2 timer 默认安全模式或人工命令 | 扫描 GitHub issue，记录分诊结果，不写 GitHub，不发飞书，不调用 Codex | 验证扫描范围和判断口径 |
| `write-smoke` | 人工指定 issue | 只对指定 issue 写 GitHub 评论、打流程标签、发施工审批卡 | 验证 GitHub + 飞书链路 |
| `build` | issue 已有审批产生的 `ai-ready` | 自动施工、测试、创建 ready PR、发合并审批卡 | 真正推进 issue 到 PR |
| `merge` | 飞书合并审批回调 | 校验 PR 状态、CI、head_sha、分支保护后合并 | 产品经理批准合并后 |

`dry-run` 看不到 GitHub 评论。第一版所有会发施工审批卡的写入都必须指定 issue；`scan --write` 不允许对全量 open issue 批量发施工审批卡。

EC2 timer 有两个运行档位：

- `observe`：默认档，只做 dry-run 扫描和本地记录，不写 GitHub、不发飞书、不建 PR。
- `active`：替代发布流程完成上线后显式开启，timer 会扫描、领取已审批的 `ai-ready` issue，并自动推进到 ready PR。

代码可以一次性交付 `active` 能力，但正式环境只有在替代发布流程完成后才打开 active 档。旧部署审批已停用。打开后不需要产品经理中途陪跑；当前版本仍要求产品经理通过 `ai-ready` 放行施工。低风险自动施工放行属于后续策略项，不是当前已上线能力。

### 2.4 不做什么

第一版不做：

- AI 自己决定合并 main。
- AI 自己决定生产部署。
- 绕过 PR 直接 push main。
- 绕过 CI 或测试。
- 自动处理密钥、生产数据、权限边界不清楚的 issue。
- 跨多个 issue 做大范围重构。
- 多审批人、多角色审批流。
- 多项目统一治理后台。
- 自动把 PR 从 draft 转成 ready for review。
- 自动跳过失败 review、失败测试或失败 CI。
- 让产品经理在每个中间阶段手工帮系统判断是否继续。

## 三、角色

| 角色 | 第一版职责 |
|------|------------|
| 产品经理 | 唯一审批人；确认 issue 是否允许施工、PR 是否允许合并、部署是否允许继续 |
| 分诊 Agent | 扫描 issue，判断类型、风险、前置条件和是否建议施工 |
| 施工 Agent | 只处理 `ai-ready` issue，完成代码、文档、测试和 PR |
| GitHub | issue、标签、分支、PR、CI 和合并留痕 |
| 飞书 | 审批入口、结果通知、异常提醒 |
| CD 系统 | PR 合并后的部署执行和部署确认 |

第一版只有产品经理可以在飞书卡片上批准施工和批准合并。旧飞书部署审批已停用；后续再扩展产品、技术、设计、安全、运维等分角色审批。

## 四、Issue 状态流

```text
新 issue
  -> AI 分诊中
  -> 缺信息 / 等确认
  -> 建议施工
  -> 产品经理飞书确认
  -> ai-ready
  -> AI 施工中
  -> ready PR 待审批
  -> 产品经理批准合并
  -> PR 已合并
  -> 人工受控发布（旧飞书部署审批已停用）
  -> 已部署或明确阻断
  -> smoke 通过 / smoke 失败
```

异常状态：

- `ai-blocked`：缺少产品、设计、技术、安全、数据或运维确认。
- `ai-paused`：产品经理主动暂停。
- `ai-failed`：AI 施工失败或连续重试失败。
- `ai-needs-human`：需要人工介入，不适合继续自动施工。

用户可见失败口径：

- GitHub issue 必须有评论说明卡在哪、下一步谁处理。
- 飞书卡片必须更新为已暂停、已退回、失败或需要人工处理。
- 失败不能静默留在 `ai-ready` 或 `ai-in-progress`。
- 如果失败发生在代码施工阶段，PR 不存在时要说明“未创建 PR”；PR 已存在时要在 PR 或 issue 回填链接和失败原因。

## 五、标签体系

### 5.1 前置条件标签

前置标签表达“这个 issue 的关键条件是否已经确认”。

| 标签 | 含义 | 典型场景 |
|------|------|----------|
| `product-ok` | 产品目标、验收标准、用户体验已确认 | 新需求、体验调整、流程变化 |
| `design-ok` | 交互或视觉方案已确认 | 卡片、页面、复杂交互 |
| `tech-ok` | 技术方案、模块边界、实现路径已确认 | 跨模块改动、架构调整 |
| `data-ok` | 数据口径、字段、统计规则已确认 | 指标、报表、数据模型 |
| `security-ok` | 权限、密钥、越权、安全边界已确认 | MCP、授权、生产数据、密钥 |
| `ops-ok` | 部署、回滚、运维影响已确认 | CD、服务、定时任务、线上配置 |

不是所有 issue 都需要全部前置标签。分诊 Agent 要根据 issue 类型给出建议。

### 5.2 门禁和流程标签

| 标签 | 含义 |
|------|------|
| `ai-ready` | 最终施工门禁；只有出现该标签，施工 Agent 才能改代码 |
| `ai-blocked` | 当前缺少必要信息或确认 |
| `ai-in-progress` | AI 正在施工 |
| `ai-pr-ready` | AI 已创建 PR，等待审批 |
| `ai-approved-to-merge` | 飞书合并审批已通过 |
| `ai-done` | 已合并、部署或完成验收 |
| `ai-failed` | 自动处理失败 |

`ai-ready` 不等于产品 OK、设计 OK 或技术 OK。它只表示：当前 issue 所需的前置条件已经满足，可以交给 AI 施工。

第一版中，`ai-ready` 必须由产品经理在飞书卡片确认后打上；AI 可以建议，但不能自己给自己发施工通行证。

## 六、飞书卡片体验

### 6.1 分诊卡片

触发时机：分诊 Agent 判断 issue 信息足够，建议进入施工。

卡片展示：

- 仓库名
- Issue 标题和链接
- AI 判断的 issue 类型
- 需要的前置标签
- 当前已满足和缺失的条件
- 用户可见目标
- 风险提示
- AI 建议

按钮：

- `允许施工`
- `退回补充信息`
- `暂停`
- `查看 Issue`

点击 `允许施工` 后，系统给 issue 打 `ai-ready`。

### 6.2 PR 审批卡片

触发时机：施工 Agent 创建 ready PR 并完成自检。

卡片展示：

- Issue 标题和链接
- PR 链接
- 本次用户体验变化
- 改动范围
- 测试结果
- 是否涉及权限、MCP、部署、数据库、生产数据
- 风险提示
- AI 建议：可合并 / 建议人工 review / 不建议合并

按钮：

- `批准合并`
- `退回修改`
- `暂停`
- `查看 PR`

点击 `批准合并` 后，系统必须重新检查：

- PR 仍然存在且未关闭。
- PR 分支没有被新的 unknown commit 污染。
- CI 通过。
- 必要 review 或状态检查满足仓库规则。
- main 分支没有造成不可自动合并的冲突。

检查通过后才允许 merge。

### 6.3 部署确认卡片

旧 CD 飞书部署确认卡片已停用。PR 合并后不自动部署，等待替代发布入口。

### 6.4 完成卡片

触发时机：合并、部署或 smoke 完成。

卡片展示：

- Issue 和 PR 链接
- 合并结果
- 部署结果
- smoke 结果
- 用户现在能看到什么
- 如果失败，下一步需要谁处理

### 6.5 机器自检替代人工中途确认

第一版不要求产品经理在 dry-run、write smoke、自动施工、测试、review 每一步都中途确认。系统必须自己检查以下条件：

- 当前 issue 属于配置仓库，且为 open issue。
- 只有被飞书审批产生 `ai-ready` 的 issue 才能进入施工。
- 同一时间只允许一个 active run 处理同一个 issue。
- 工作分支只能是 `codex/issue-*`，不能是 `main`。
- PR 默认是 ready PR；只有需求不清、风险异常或需要人工补充说明时才允许 draft。
- PR 合并前必须重新校验 head_sha、PR open、CI 通过、无冲突。
- 部署不得走已停用的 CD 飞书确认卡。
- 如果 `ai-ready` 标签和本地审批记录不一致，进入阻断态并要求人工确认，不能自动施工。

系统自检失败时，直接阻断并通知，不要求产品经理判断技术细节。

## 七、第一版安全边界

AI 可以：

- 读取 issue、PR、CI 状态。
- 评论 issue。
- 打流程标签。
- 开分支。
- 创建 ready PR。
- 发飞书卡片。
- 在隔离工作区运行测试。
- 在产品经理批准后合并 PR。

AI 不可以：

- 未经飞书审批给 issue 打 `ai-ready`。
- 未经飞书审批合并 PR。
- 通过已停用的 CD 卡片审批部署。
- 直接 push main。
- 打印、读取或提交密钥。
- 绕过 MCP 权限边界。
- 直接连接生产数据库做业务查询。
- 用管理员账号替代普通用户体验验收。

## 八、不能自动施工的 issue

以下 issue 第一版必须阻断：

- 目标或验收标准不清楚。
- 只有一句话，无法判断用户体验。
- 权限模型不清楚。
- MCP 安全边界不清楚。
- 涉及密钥、生产数据、越权风险。
- 需要真实用户验收但没有验收标准。
- 大型架构调整。
- 需要跨多个仓库同时修改。
- 需要外部团队先确认口径或日期。

阻断后，AI 应评论缺口，并通过飞书提醒产品经理。

## 九、BIAIAgent 首个接入边界

BIAIAgent 作为第一版接入项目时，必须遵守本仓库红线：

- 所有代码变更必须通过 PR 合入 main。
- PR 合入前必须通过测试。
- 部署动作在 PR 合并后执行。
- 不得直接 push main 后部署。
- 不得绕过 MCP 边界写 SQL 查询。
- 不得宣称已经具备正式多用户权限隔离。

BIAIAgent 的第一版推荐策略：

- 文档、小修复、测试补充、小型体验修正可以进入 AI 施工。
- 飞书、MCP、权限、部署、数据库相关 issue 默认需要更严格前置标签。
- 涉及真实用户体验的 PR 必须说明是否完成真实 smoke。

### 9.1 当前第一版实现说明

当前第一版实现优先服务 BIAIAgent 的真实落地，因此会复用本项目已有能力：

- 复用现有飞书 Bot 回调入口和卡片更新能力。
- 复用现有 SQLite 数据库和 SQLAlchemy 初始化流程。
- 旧 CD 飞书部署确认卡片已停用；替代发布入口确定前不自动部署。
- 使用 BIAIAgent 当前文档、测试、PR 和部署红线作为首个项目策略。
- 默认高风险词贴近 BIAIAgent 当前风险：飞书、MCP、权限、密钥、生产数据、数据库、部署、开户。

这意味着第一版还不是一个可以直接复制到任意仓库的独立平台。它的产品目标是先跑通 BIAIAgent 的 Issue-to-PR 闭环，再沉淀可复用边界。

### 9.2 复用前必须拆出的边界

第二个项目接入前，必须把能力拆成两层：

| 层级 | 职责 |
|------|------|
| Issue Agent Core | GitHub issue 扫描、分诊、状态机、审批记录、标签门禁、PR 合并门禁、失败重试 |
| Project Adapter | 项目 repo、审批人、高风险词、测试命令、文档规则、部署确认方式、smoke 口径 |

BIAIAgent 只应保留 adapter/config，不应长期承载通用 Agent 的全部平台逻辑。

### 9.3 Issue #46 首条试跑口径

GitHub issue #46「部署申请卡片需要展示更多审批决策信息」作为第一条真实闭环试跑 issue。它命中“部署”高风险词，因此不能因为是 smoke 就降低门禁。

试跑目标：

- 验证 EC2 `wangzhipeng` 账号下的 Issue Agent 能扫描到 #46。
- 验证 write smoke 能在 #46 写入分诊评论，并向产品经理发送施工审批卡。
- 施工通过后，Agent 自动创建 `codex/issue-46-*` 分支和 ready PR。
- PR 说明必须写清：部署申请卡片中产品经理会多看到哪些审批决策信息。
- 合并仍需飞书 PR 合并审批；部署不得使用已停用的 CD 卡片。

#46 进入施工前必须满足：

- issue 写清用户体验目标和验收标准。
- 具备 `product-ok`、`tech-ok`、`ops-ok`。
- 分诊结论明确为“部署申请卡片展示信息改造”，不涉及真实部署执行权限变更。

如果 #46 在分诊或 write-smoke 阶段不满足这些条件，Agent 必须阻断并说明缺口，不发送“允许施工”卡，不能为了跑通流程强行施工。

## 十、成功标准

第一版上线后，达到以下效果即算成功：

1. 产品经理可以只在飞书里处理 AI 施工关键审批。
2. AI 能把清晰的 GitHub issue 自动推进到 ready PR。
3. 不清晰的 issue 能被自动识别并说明缺口。
4. PR 里能清楚写出用户体验变化、测试结果和风险。
5. 合并和部署都有明确人工确认。
6. 没有出现绕过 PR、绕过 CI、误部署生产的问题。

- 多审批人。
- 按仓库配置不同标签规则。
- 低风险 issue 自动 `ai-ready`。
