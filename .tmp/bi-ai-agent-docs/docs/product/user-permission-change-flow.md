# 用户权限变更流程

> 版本：0.1 · 日期：2026-06-06
> 范围：用户权限从新增、追加、降级保留到管理员收回的产品流程与后续实现方向。
> 当前状态：流程已记录，代码调整与收回 live run 暂放后续任务 2.22。

## 一、核心原则

权限不是一次性固定结果，而是会随着入职、兼岗、调岗和高权限收回持续变化。

本流程采用两个独立动作：

1. **用户申请权限**：用户主动申请自己需要的公司 / 职能，走审批。
2. **管理员收回权限**：管理员按管理或 HR 流程收回旧权限，不走用户审批。

调岗不是“用户重新申请后系统自动清旧权限”，而是：

1. 用户先申请未来需要保留的新权限；
2. 管理员再收回不应继续保留的旧权限。

这样做的原因是：系统不能默默猜测哪些旧权限应该删除。自动清旧权限容易误删仍在使用的兼岗权限；不收回旧权限则会造成权限累积。因此收回必须是明确的管理员动作。

## 二、三类申请场景

### 1. 新增权限

新用户首次申请 BI AI Agent：

- 用户填写姓名、邮箱、申请公司、职能和说明；
- 审批通过后系统完成开户；
- 系统写入授权记录，并发布到多维表格；
- 用户收到审批通过和登录信息。

### 2. 追加权限

已开通用户申请更多公司或职能：

- 用户从“申请更多授权”入口提交申请；
- 不重复开户，不重新生成账号；
- 审批通过后只追加授权；
- 多维表格立即同步，定时同步只作为兜底。

追加权限采用合并式授权：新权限叠加到旧权限上，不自动删除旧权限。

### 3. 降级保留权限

用户当前已经拥有更高权限时，仍然允许继续申请被覆盖的具体公司 / 职能权限。

例如用户已有：

```json
{"*":["*"]}
```

这表示“全部公司 + 全部指标”。此时用户再申请“布隆迪 / 运营”，短期内不会扩大实际访问范围，因为当前大权限已经覆盖它。

但这次申请仍然有价值：它是未来收回大权限后的保留权限。

审批通过后：

- 数据库记录“布隆迪 / 运营”这条具体授权；
- 多维表格仍可能保持 `{"*":["*"]}`，这是正常结果；
- 当管理员后续收回“北京/总部 / 全部”后，“布隆迪 / 运营”会继续生效。

因此，系统不应简单用“你已拥有该权限”阻止这类申请。

## 三、重复提醒口径

“你已拥有该权限，无需重复申请”不能作为所有覆盖场景的强拦截。

后续实现应按以下口径处理：

| 场景 | 用户是否可继续申请 | 说明 |
|------|--------------------|------|
| 同一公司、同一职能完全重复 | 可提示无需重复 | 这是纯重复申请，不产生新价值 |
| 已有同公司“全部”，再申请该公司普通职能 | 应允许继续申请 | 可作为后续收回“全部”后的保留职能 |
| 已有“北京/总部 / 全部”，再申请具体国家 / 职能 | 应允许继续申请 | 可作为后续收回总部大权限后的保留权限 |
| 已有具体国家 / 职能，再申请更高权限 | 应允许继续申请 | 这是权限扩大，需要审批人判断 |

用户侧不需要理解权限展开细节。系统只需要把含义说清楚：这次申请可能不会马上改变可访问范围，但会作为后续权限收回后的保留权限。

## 四、用户和审批人的提示

### 用户确认卡

当系统发现本次申请已被现有更高权限覆盖时，确认卡不应阻止提交，而应提示：

> 你当前已有更高权限，本次申请不会立即扩大访问范围。审批通过后，它会作为后续收回高权限后的保留权限。

### 审批卡

审批人需要看到这不是普通新增，而是“降级保留”：

> 当前用户已有更高权限。本次申请不会立即扩大访问范围，但审批通过后会记录为具体保留权限；后续管理员收回高权限时，该权限仍会保留。

审批卡应展示：

- 当前已有权限；
- 本次申请权限；
- 审批后实际权限可能不变；
- 后续收回高权限后会保留哪些具体权限。

## 五、标准示例

### 场景：从北京总部全部权限降级到布隆迪运营

当前权限：

```text
北京/总部 / 全部
```

多维表格发布结果：

```json
{"*":["*"]}
```

用户申请：

```text
布隆迪 / 运营
```

审批通过后：

- 数据库新增“布隆迪 / 运营”；
- 用户仍然拥有“北京/总部 / 全部”；
- 多维表格仍是：

```json
{"*":["*"]}
```

管理员收回：

```text
北京/总部 / 全部
```

收回后：

- “北京/总部 / 全部”失效；
- “布隆迪 / 运营”继续保留；
- 多维表格重新发布为布隆迪运营对应的公司和指标权限。

## 六、后续实现方向

本文件先固定产品流程和判断口径；代码实现另行施工。

后续代码调整应包括：

- 去掉当前确认提交阶段对“高权限已覆盖小权限”的强阻断；
- 保留纯重复申请的提示能力，但不要阻止降级保留申请；
- 确认卡和审批卡增加“降级保留”提示；
- 审批通过仍沿用合并式授权，写入具体 `user_functions`；
- 多维表格继续按当前最大有效权限发布；
- 管理员收回旧权限后立即同步多维表格；
- 补一条真实环境 live run：先申请保留权限，再收回高权限，确认保留权限继续生效。
