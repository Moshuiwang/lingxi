# BI AI Agent 产品需求（统一产品合同）

> 文档版本：2.0-current
>
> 核对日期：2026-07-23
>
> 定位：这是本项目唯一的产品视角总入口。它说明产品为谁服务、各角色能做什么、用户如何完成任务，以及成功、等待和失败时会看到什么；不描述接口、表结构、命令、部署或内部实现。项目优先级、交付进度和验收证据以 [GitHub Project #2](https://github.com/orgs/startimes-bi/projects/2) 及关联 Issue 为准。

## 1. 产品是什么

BI AI Agent 是企业内部的 BI 服务入口。业务人员在飞书中申请数据权限，审批通过后即可在私聊中提出业务问题、查看分析结果并接收可交付文件；管理员在受控审批群中完成审批、授权维护和服务健康跟进。

产品的核心承诺是：

- 用户不需要理解数据查询语言、底层系统或 Agent 的工作方式，就能完成申请、获批、提问、续问和取得结果。
- 用户只能看到自己获准的公司和指标范围；无权、无法确认或服务暂不可用时，系统必须明确说明，不能编造或静默给出错误结果。
- 日常问数以飞书私聊为默认入口；需要更重的持续分析工作时，可单独申请高级数据分析工作台。
- 审批、授权变更、禁用、恢复和关键管理操作均可追溯。

当前飞书问数只提供 Claude 路径，不提供 Codex。历史 Codex 方案不属于当前产品能力，也不能作为用户承诺或验收依据。

## 2. 如何阅读状态

本文把产品能力分为三种状态，避免把设计或代码误解为用户已经可用：

| 状态 | 对产品的含义 |
|---|---|
| 当前能力 | 已纳入当前产品合同；是否已部署、启用和实测仍以项目看板和相应证据为准。 |
| 已承诺待完善 | 目标体验已确定，但尚未完整交付或尚有已知缺口；不能对用户承诺已可用。 |
| 不提供或历史内容 | 明确不属于当前产品，不应出现在用户引导、审批判断或运营承诺中。 |

## 3. 角色与各自体验

| 角色 | 想完成的事 | 产品提供的体验 |
|---|---|---|
| 未开通申请人 | 获得业务数据查询资格 | 在飞书私聊发起申请，填写必要信息，查看申请进度和审批结果。 |
| 已开通聊天用户 | 日常问数、看趋势、追问和取得交付物 | 在飞书私聊直接提问；在同一话题继续追问；收到流式结果、明确完成状态或可理解的等待/失败说明。 |
| 高级工作台用户 | 做持续、深度或可沉淀的分析工作 | 在拥有基础聊天能力后，额外申请高级工作台；按引导通过 JumpServer 进入工作环境。该入口不增加数据权限。 |
| 审批员 | 判断一项申请是否应通过 | 在审批卡上看清“谁、申请什么、已有何种权限、为什么申请、通过后用户会获得什么”，再整体通过或退回。 |
| 权限管理员 | 维护用户、公司、职能和指标可见范围 | 在受控审批群中查看用户与权限、收回权限、禁用或恢复账号、处理异常、分配新指标。 |
| Agent 管理员 | 维护已开通用户的受控对话配置 | 在受控管理入口查看配置、调整允许的 Claude 配置或恢复默认；普通用户不能自行修改。 |
| 运维管理员 | 保持服务可用且可安全切换 | 查看服务健康与环境状态，按受控流程切换正式或测试机器人、处理故障和恢复服务。 |
| 业务负责人 | 知道 BI 服务与指标是否可靠 | 接收统一巡检中的业务化摘要，看到哪些数据延迟、权限异常或指标尚待归属，以及下一步该找谁处理。 |

## 4. 用户旅程一：申请、审批与首次使用

### 4.1 申请数据权限

**目的**：让尚未开通的业务人员用明确、可审阅的方式申请所需数据范围。

**用户怎么做**：申请人在飞书私聊发送“申请权限”，在卡片中填写姓名、工作邮箱、申请公司、一个或多个职能及选填说明。飞书聊天为基础能力；高级数据分析工作台由用户自行选择申请。

**用户会看到什么**：

- 未开通时，除申请引导外不进入问数能力。
- 提交前可核对申请内容；提交后卡片变为不可再次提交的“申请已提交”状态。
- 已有待审批申请时，系统说明正在审批，不重复创建新申请。
- 被退回后，用户能看到退回原因并可据此重新申请。

**基本手段**：用结构化申请卡收集业务信息，用状态驱动的提示避免重复申请和信息丢失。

### 4.2 审批员处理申请

**目的**：让审批员不用理解内部术语，也能作出可追溯的业务判断。

**审批员怎么做**：在受控审批群打开审批卡，阅读申请类型、申请人、公司和职能、已有权限、申请说明及通过后的影响，选择整体通过或退回；退回时必须填写原因。

**审批员会看到什么**：

- 首次开通、补充授权和高级工作台请求有清晰区别。
- 已处理卡片再次操作时，收到“已处理”提示，不会重复开通或重复撤权。
- 技术编号、密钥、内部日志不会占据卡片首屏。
- 权限发布需要等待时，看到“正在同步、系统会自动复验”，而不是“开通失败”。

### 4.3 通过后，用户何时能开始问数

**目的**：把“审批通过”和“数据服务已经可用”讲清楚，避免用户和审批员误判。

**用户会看到什么**：审批通过后，用户收到聊天权限及本次授权范围的通知；如数据服务仍在同步，通知会说明正在等待并会自动复验。同步完成后可开始问数；超过等待窗口仍无法确认时，系统转为“需要人工检查”，不把临时问题说成永久失败。

**基本手段**：权限先发布，再自动复验；用户只接收业务化的等待和结果信息，不需要理解同步机制。

### 4.4 补充授权与调岗

**目的**：让已开通用户可以增加新的公司或职能，同时使离岗或调岗后的旧范围被及时收回。

**目标体验**：已开通用户可查看当前公司和职能，发起补充授权申请；通过后只增加新范围，不覆盖旧范围。调岗由“申请新范围”和“收回旧范围”两个可追踪动作组成。

**当前状态：已承诺待完善。** 目前已开通用户在私聊中可能直接进入对话，无法稳定进入补充授权申请；该缺口由 GitHub Issue #91 跟踪。在该能力完整前，管理员应通过受控管理流程处理增量授权，不能向用户承诺自助补申请已可用。

## 5. 用户旅程二：飞书 BI 对话

### 5.1 开始提问

**目的**：让已开通用户用自然语言完成日常指标查询、趋势解释和分析请求。

**用户怎么做**：在与 BI Plus 的飞书私聊直接提出业务问题，例如查询某公司某项指标、比较趋势或要求解释变化。

**用户会看到什么**：

- 系统先给出正在处理的反馈和以业务主题为主的卡片标题，而不是内部 Agent 名称。
- 处理过程中逐步展示可见答案和必要的简短状态；完成时明确标记完成与耗时。
- 用户的问题不清楚、同名公司可能对应多个范围时，系统要求用户选择或补充，而不是自行猜测。
- 无权查询、数据不可确认、服务不可用或结果为空时，系统给出下一步可理解的说明，不把空答案标为完成。

### 5.2 续问、话题与新会话

**目的**：让用户能够沿着一个业务问题继续追问，同时避免不同话题串台。

**用户怎么做**：在私聊主窗口继续发消息即可续问；也可以在飞书原生话题中围绕某条回复继续讨论；在主窗口发送 `/new` 开始新的话题。

**用户会看到什么**：

- 同一话题中的追问保留该话题上下文；不同用户、不同飞书话题不会共享上下文。
- 私聊主窗口长期无互动后，系统会以新会话开始，避免过期上下文影响回答。
- 在原生话题中发送 `/new` 时，系统提示另开话题，而非悄悄丢失上下文。
- 短追问不会把已有业务话题标题改成“继续”“结果呢”等无意义文本。

### 5.3 结果、文件与文档交付

**目的**：让分析结论和产物能在飞书中直接使用，且只交给有权的当前用户。

**用户会看到什么**：

- 正常答案以清晰、可阅读的卡片或消息交付；卡片更新失败时，系统仍以普通消息补发结果。
- 需要图像时，用户能在飞书中直接查看或打开图像。
- Markdown 类内容优先交付为飞书文档；表格类内容优先交付为飞书表格；转换不能完成时，按安全规则选择可用的降级方式。
- 用户只能收到自己分析工作中生成且允许交付的文件；系统不发送敏感配置、认证材料、其他用户文件或不安全路径的文件。

### 5.4 对话的可信边界

**目的**：确保“能回答”不等于“可以随意取数或编造答案”。

产品必须做到：

- 只在用户获准的公司和指标范围内回答。
- 不允许用户通过本产品直接访问生产数据库、绕开数据权限或获取认证信息。
- 当数据不存在、权限不足、数据延迟或服务返回不完整结果时，明确说明限制；不得用猜测填补数据。
- 不在用户之间共享会话、文件或上下文。

## 6. 高级数据分析工作台

**目的**：为确有持续分析、深度分析、可复用技能或自动化交付需求的用户提供更重的工作入口，同时不把它误解为更高的数据权限。

**用户怎么做**：在首次申请时勾选高级工作台，或在后续通过补开流程提出申请；获批后按照飞书引导进入 JumpServer 的浏览器工作环境。

**用户会看到什么**：

- 不申请高级工作台的用户只使用飞书聊天，不会收到服务器地址、私钥、压缩包口令或终端操作指引。
- 申请高级工作台后，用户先获得飞书聊天；工作台准备不阻塞日常问数。
- 工作台授权尚未完成时，用户看到“正在准备”或“请联系运维完成授权”，而不是误以为已经可以登录。
- 日常产物仍优先从飞书交付；工作台不是面向普通业务用户的文件传输入口。

**当前状态：已承诺待完善。** 高级工作台和 JumpServer 交付仍需按项目看板的实际进度确认，不能仅凭本文视为已启用。

## 7. 用户生命周期与权限变化

### 7.1 收回授权

**目的**：在岗位、公司或职责变化时，精确减少不再需要的数据范围，不影响仍有效的权限。

**管理员怎么做**：在受控审批群查询目标用户后，选择整家公司、单个职能或多项已存在权限进行收回，并确认操作。

**管理员和用户会看到什么**：管理员先看到当前真实权限和本次将收回的内容；确认后得到结果与剩余权限摘要。用户收到本人的权限变化通知。重复点击或过期卡片不应造成额外收回。

### 7.2 禁用、删除与恢复

**目的**：让管理员能够按风险和业务需要停止服务，同时保留必要的可追溯性。

| 操作 | 对用户的体验 |
|---|---|
| 仅收回授权 | 失去选定的数据范围，账号和其他已获准权限仍保留。 |
| 禁用账号 | 无法再发起新的对话或交付；系统停止其正在进行的服务，并向用户说明账号已停用。 |
| 彻底删除 | 在完成撤权和必要清理后，账号不再作为可用业务身份保留；审计保留遵循公司政策。 |
| 恢复 | 在管理员确认后恢复符合当前授权范围的服务，不自动恢复已被收回的范围。 |

**当前状态：部分待完善。** 撤权、禁用和删除的统一状态规则仍在项目看板中跟进，管理员应以当前受控流程为准。

## 8. 管理员体验

### 8.1 用户与权限管理

**目的**：让权限管理员在一个受控入口内完成常用处理，而不是依赖个人记忆或分散脚本。

管理员可在审批群中：查看用户、公司和当前权限；关闭待处理申请；重试权限发布；收回权限；禁用、启用或删除用户。机器人对未识别的管理消息给出当前可用操作提示；在非受控群不插话。

### 8.2 指标分配闭环

**目的**：当出现新指标时，确保它被明确分配给合适职能，而不是悄悄让已获批用户看不到或错误看到数据。

**管理员怎么做**：在审批群查看当前指标及分配状态；对未分配指标，先选择公司和职能，再多选指标并确认。

**管理员会看到什么**：系统清楚标出“未分配”“已分配”“快照过期，暂不可判断”等状态。分配完成后，已获批且匹配该职能的用户在权限生效后自然获得可见范围；管理员能追溯谁在何时作了哪项分配。

**当前状态：已承诺待完善。** 该闭环按专题 PRD 分阶段建设，不能把规划中的卡片分配当作已上线能力。

### 8.3 对话配置管理

**目的**：让管理员可以在受控范围内调整服务配置、处理故障或恢复默认，而不把复杂配置暴露给业务用户。

用户不会看到也不能修改模型、推理档位、凭据或内部路径。管理员的操作结果只说明变更前后和是否生效，不展示敏感信息；配置改变后，用户下一次提问以新的会话开始，避免把不同配置的上下文混在一起。

## 9. 服务健康与业务可用性

### 9.1 统一 BI 巡检

**目的**：让业务负责人和管理员用一条业务化结果判断“当前能否对外说 BI 服务可用”。

巡检把三类信息合在一起：指标目录是否变化、已批准账号的权限是否健康、关键业务数据是否按预期更新。结果分为正常、提醒、异常和无法判断；只有全部检查正常时才会显示“整体正常”。

**用户会看到什么**：默认仅在出现异常时向受控群发送消息。摘要会说明受影响的指标、数据最新时间、账号或权限问题和建议动作；无法判断时明确说“需要先恢复巡检”，不会误导为无异常。

**当前状态：已承诺待完善。** 统一巡检尚待实施；现有准入健康巡检仍是独立的过渡能力。

### 9.2 准入健康提醒

**目的**：及时发现“已批准但不能使用”“新指标无人负责”等问题，防止用户在提问时才发现服务异常。

在工作日工作时段，系统定期检查新指标、指标描述变化、未分配职责指标和账号准入异常。无变化且无异常时不打扰管理员；出现问题时在审批群给出受影响对象和处理建议。巡检只报告和提醒，不自动扩大任何用户的数据权限。

### 9.3 正式与测试环境

**目的**：让运维可以安全验证服务，同时避免测试数据、测试用户或测试会话影响正式用户。

对普通用户而言，任一时刻只会有一个活动机器人提供服务；切换失败时，系统恢复原环境。测试机器人使用独立数据与身份，不能进入正式用户体验。此能力面向运维管理员，不是用户可自行选择的产品功能。

## 10. 产品质量与验证

为保证用户体验，产品设有两类不向普通用户开放的质量能力：

- **真实流程验证**：用受控测试账号检查申请、审批、授权、对话、交付和撤权是否能连贯完成。
- **问数质量评测**：围绕现有指标检查回答是否覆盖正确范围、能否给出可验证的结果；没有可靠标准答案时必须标注待验证，不能伪造通过。

这些能力用于发现问题和指导发布，不会自动替用户审批、自动放权、自动部署或自动修改生产数据。

## 11. 明确不提供的能力

- Codex 飞书对话、Codex 私聊或多 Agent 自助选择。
- 群聊中的自由 BI 问答；审批群和测试群只处理受控管理或测试操作。
- 用户直接连接生产数据库、编写绕过权限的数据查询，或查看认证材料和内部配置。
- 用高级工作台替代权限审批，或将其作为普通用户的文件传输通道。
- 无人值守的自动部署、自动放权、自动修复数据或自动施工。
- 将审计项目的行为审计功能混入本产品的日常巡检。

## 12. 已知产品缺口与后续依据

以下是当前产品合同中需要持续跟进、但不应被包装成已完成体验的重点：

| 主题 | 当前限制 | 跟踪依据 |
|---|---|---|
| 已开通用户补充授权 | 私聊可能直接进入对话，尚不能稳定进入补申请。 | GitHub Issue #91 |
| 审批员来源与身份校验 | 审批卡的服务端身份和来源群校验仍有风险项。 | GitHub Issue #92 |
| 聊天用户补开高级工作台 | 后补工作台的状态体验尚需收口。 | GitHub Issue #93 |
| 重复投递与结果完成态 | 重复消息、结果持久化与交付前完成标记仍有可靠性风险。 | GitHub Issues #94、#95 |
| 审批后的等待说明 | 是否在验证通过前发送“审批通过”卡片，以及异常误判问题仍待决策和修复。 | GitHub Issues #139、#140 |
| 统一巡检与指标分配闭环 | 产品体验已定义，尚需按计划实施。 | 专题 PRD 与 GitHub Project |
