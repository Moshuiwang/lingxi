# 用户机器人入口路由表产品方案

> 日期：2026-06-10
> 状态：方案
> 范围：用户与飞书机器人私聊时的入口识别、审批群/测试群 @Bot 时的命令帮助、命中后的下一步流程、未命中时的引导文案。

## 一、用户体验目标

用户不需要记住系统菜单，也不需要理解后台流程。

用户在飞书私聊机器人时，只要说出系统支持的话，机器人就直接进入下一步；说错或说了系统暂不支持的话，机器人给出明确、可复制的说法。

管理员在审批群或测试群 @Bot 时，如果命中具体命令就执行原流程；如果没有命中具体命令，或者只是 @Bot 不带问题，机器人直接返回当前可用命令列表，类似 Linux 命令的 `--help`。

本期只解决入口体验：

- 命中：直接进入已有流程，不额外解释。
- 私聊未命中：不沉默，告诉用户现在可以直接说什么。
- 审批群/测试群未命中：不沉默，返回命令列表。
- 其他群：不响应，避免机器人在非受控群里插话。
- 不扩展 BI 查询能力，不把准入层机器人升级成通用问答机器人。

## 二、成功标准

| 场景 | 用户输入 | 用户看到 |
|---|---|---|
| 命中申请权限 | `申请权限` | 直接收到申请权限卡片或当前状态提示 |
| 私聊未命中 | `你好`、`我要查数据`、空泛表达 | 收到一条引导：可以直接说 `申请权限` |
| 文案带空格 | ` 申请权限 ` | 仍然进入申请权限流程 |
| 审批群管理员命令 | 审批群 `@Bot 取消授权` | 继续走原管理员流程 |
| 审批群 help | 审批群 `@Bot`、`@Bot 帮助`、`@Bot 你好` | 收到当前可用命令列表 |
| 测试群 help | 测试群 `@Bot`、`@Bot 帮助`、`@Bot 随便问` | 收到测试群可用命令列表 |
| 非受控群 | 其他群 `@Bot` | 不响应 |

## 三、私聊路由表

本期私聊路由表只放已落地的用户入口：

| 用户可以说 | 命中条件 | 下一步 |
|---|---|---|
| `申请权限` | 去掉首尾空格后完全等于 `申请权限` | 进入申请权限流程 |

暂不支持模糊语义识别，例如“我要开权限”“帮我申请 BI”。原因是当前准入层需要确定性入口，避免用户以为机器人已经具备完整自然语言理解能力。

## 四、审批群/测试群 help 路由

审批群和测试群是唯一支持群聊 help 的群。触发前提：

- 消息来自审批群或测试群。
- 消息里明确 @ 了本 Bot，而不是 @ 群里其他人或 @所有人。
- 既没有命中已有管理员命令，也没有命中测试群 E2E 命令。

实现时不能复用“消息中存在任意 @”作为触发条件。必须识别被 @ 对象的 open_id，并与本 Bot 的 open_id 对比；`@所有人` 也必须显式排除。只根据“去掉 @ 后文本为空”判断裸 @Bot 是错误的，因为裸 @所有人也可能得到空文本。

两种 mention 形态都要支持：

- XML 形态：`<at user_id="ou_xxx">...</at>`，open_id 在文本里，E2E/live-run 发送命令使用这一路。
- Placeholder 形态：`@_user_N`，文本里没有 open_id，必须用飞书消息 `mentions` 数组把 key 映射到 `id.open_id`，真实飞书客户端常见这一路。

本 Bot 的 open_id 来源必须明确：优先读取 `LARK_BOT_OPEN_ID`；如果未配置，可用 tenant token 调飞书 `/bot/v3/info` 获取并缓存。不能使用 `LARK_APP_ID` / `get_app_id()`，它是应用 ID，不是 Bot 的 open_id。若启动时无法解析 Bot open_id，应 fail-fast 或明确报错，不能让审批群命令静默失效。

| 群 | 命中条件 | 用户看到 |
|---|---|---|
| 审批群 | `@Bot`、`@Bot 帮助`、`@Bot help`、或任何未支持内容 | 审批群命令列表 |
| 测试群 | `@Bot`、`@Bot 帮助`、`@Bot help`、或任何未支持内容 | 审批群命令列表 + 测试命令列表 |

审批群命令列表建议包含：

```text
我现在支持这些审批群命令：
- @Bot 取消授权
- @Bot 关闭申请 <申请ID或用户> <原因>
- @Bot 重试权限发布
- @Bot 列出用户
- @Bot 查看用户 <姓名或邮箱>
- @Bot 查看公司 <公司>
- @Bot 禁用用户 <姓名或邮箱>
- @Bot 启用用户 <姓名或邮箱>
- @Bot 收回授权 <姓名或邮箱> <公司> [职能]
```

用户也可以发送 `@Bot 帮助` 或 `@Bot help` 获取这份列表；它们是 help 入口，不是独立业务命令。

命令列表必须和实际路由保持一致。当前中文管理命令以 `admin_command_flow.is_admin_command_text()` 为准；如果未来要把 `查看用户` 改成 `查询用户`，必须同步修改代码路由和测试，不能只改 help 文案。

测试群额外展示测试命令：

```text
测试群还支持：
- @Bot 测试申请 name=<姓名> email=<邮箱> company=<公司> functions=<职能1,职能2>
- @Bot 测试审批通过 record_id=<申请ID>
- @Bot 测试审批拒绝 record_id=<申请ID> reason=<原因>
- @Bot 测试收回 email=<邮箱> company=<公司>
```

测试群 help 的判定必须和测试命令执行判定一致：使用不 fallback 的测试群判断（当前为 `_is_test_chat` / `LARK_TEST_CHAT_ID`），不能使用会回落到审批群的 `get_test_chat_id()`。未配置 `LARK_TEST_CHAT_ID` 时，测试群 help 不可达，审批群只展示审批群命令。

## 五、未命中文案

私聊未命中建议文案：

```text
我现在可以帮你开通 BI 权限。你可以直接说：申请权限
```

文案原则：

- 只说用户下一步能做什么。
- 不解释内部系统状态。
- 不列未实现能力，避免制造预期。
- 不把用户导向人工客服，除非后续产品明确增加人工兜底。

群聊未命中使用命令列表，不复用私聊文案。

## 六、不做范围

- 不新增飞书菜单。
- 不新增数据库表。
- 不接入大模型做意图识别。
- 不支持 BI 数据查询聊天入口。
- 不改变审批群管理员命令。
- 不让普通群获得 help 响应。
- 不改变卡片 001/002/003/004 的业务流程。

## 七、验收方式

从用户视角验收三条路径：

1. 用户私聊 `申请权限`，能进入申请流程。
2. 用户私聊任意未支持内容，收到“可以直接说：申请权限”。
3. 审批群 @Bot 管理员命令仍按原流程响应。
4. 审批群 @Bot 未命中具体命令时，收到审批群命令列表。
5. 测试群 @Bot 未命中具体命令时，收到审批群命令列表 + 测试命令列表。
6. 审批群 @ 其他人或 @所有人，不触发 help。
7. `LARK_TEST_CHAT_ID` 未配置时，审批群 @Bot 未命中只展示审批群命令，不展示测试命令。
8. XML 形态 `<at user_id="Bot open_id">` 能触发审批群/测试群路由。
9. Placeholder 形态 `@_user_N` 必须结合 `mentions` 数组识别 Bot open_id。
10. Bot open_id 未配置但飞书 `/bot/v3/info` 可用时，仍能识别 @Bot。
11. Bot open_id 无法解析时，服务 fail-fast 或明确报错，不静默丢掉审批群命令。
12. `LARK_APP_ID` 不得被当作 Bot open_id 使用。
13. 其他群 @Bot 不响应。
